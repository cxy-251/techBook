第014章：继承与 MRO
===================

核心知识点
----------

继承把类属性合并到一条查找序列
   对象属性查找会沿实际类型的 ``__mro__`` 推进。MRO 名称中包含 method，但它决定的是所有类侧属性的解析顺序；方法只是在命中函数 descriptor 后进一步发生绑定。

``__bases__`` 是输入，``__mro__`` 是结果
   类定义中的直接基类顺序表达局部优先级。类创建时，解释器把各基类已有 MRO 与直接基类列表合并成一条线性序列，并保存在类对象上。

第一个命中点决定类侧候选
   实例读取属性时，先根据其实际类展开 MRO，再找到第一个包含目标名字的类。命中的对象随后还要经过 descriptor 与实例字典优先级判断。

C3 线性化维持三项性质
   它保留直接基类的局部顺序，保持父类中已经建立的先后关系具有单调性，并让公共祖先只在线性序列中出现一次。菱形继承因此能够稳定收束到共享根类。

C3 通过合格头部逐步合并
   候选类必须位于某个待合并序列的头部，并且不能出现在其它序列的尾部。每次选出候选后，从所有序列中移除，再继续处理剩余约束。

不一致的继承约束在类创建时失败
   当多个基类同时要求互相矛盾的先后顺序时，C3 找不到合格候选，解释器抛出 MRO ``TypeError``。此时类对象尚未创建。

``super`` 是沿 MRO 继续查找的代理
   ``super(Start, obj)`` 保存起点类和绑定对象，并从 ``type(obj).__mro__`` 中起点类之后的位置继续查找。它不是“调用直接父类”的固定语法。

零参数 ``super()`` 依赖当前类和首个参数
   普通实例方法中，编译器通过 ``__class__`` cell 提供方法定义所在类，并以第一个形参对应对象作为绑定对象。下一站仍由该对象实际类型的 MRO 决定。

协作式继承要求每一站继续委派
   多个 mixin 组成调用链时，各实现需要使用兼容签名、完成局部工作、调用 ``super()`` 并保持兼容返回协议。任一实现提前返回或直接点名父类，都会截断或绕开后续 MRO 路径。

Mixin 应表达可组合的单一能力
   Mixin 越依赖固定父类位置、私有初始化顺序和不兼容参数，越难参与协作式链路。稳定 mixin 应声明所需协议，并尽量通过 ``super`` 与其它实现组合。

Descriptor 仍服从 MRO 与属性优先级
   查找会先沿 MRO 找到第一个同名类侧对象，再判断它是 data descriptor、non-data descriptor 还是普通类属性。继承不会跳过 descriptor 规则。

MRO 冲突与 metaclass 冲突不同
   MRO 冲突来自基类线性化约束无法合并；metaclass 冲突来自各基类的类型创建者无法选出共同最派生 metaclass。两者都在类定义阶段暴露，但排查对象不同。

关键路径
--------

属性与方法解析：

::

   取得实例的实际类型
   → 读取 type(obj).__mro__
   → 沿序列找到第一个定义 attr 的类
   → 判断命中对象是否为 descriptor
   → 与实例字典按 descriptor 优先级竞争
   → 返回值或生成 bound method
   → 调用时 self 仍是原始实例

协作式 ``super`` 调用：

::

   当前方法调用 super()
   → 得到起点类与绑定对象
   → 在绑定对象实际类型的 MRO 中定位起点类
   → 从下一项开始查找目标属性
   → descriptor 绑定到原始对象
   → 调用下一站实现
   → 各层按调用栈反方向完成后处理

C3 合并：

::

   收集每个直接基类的 MRO
   → 加入直接基类列表
   → 选择不出现在其它列表尾部的头部候选
   → 写入结果并从所有列表移除
   → 重复直到列表为空
   → 无候选时抛出 MRO TypeError

概念辨析
--------

* **``__bases__`` 与 ``__mro__``**：前者只列直接基类；后者是类创建后用于实际查找的完整线性序列。
* **继承与方法调用链**：MRO 让实现可达；方法是否调用 ``super`` 决定后续实现是否真正执行。
* **``super`` 与直接父类调用**：``super`` 按实际对象 MRO 继续查找；直接写 ``Base.method(self)`` 固定跳到某个类，破坏可组合性。
* **覆盖与扩展**：完全覆盖可在子类结束调用；协作式扩展需要执行局部逻辑并继续委派。
* **菱形继承与重复调用**：C3 让共享祖先只出现一次；各层正确使用 ``super`` 时，根实现通常只执行一次。
* **Mixin 与基类**：mixin 主要提供可组合行为；业务基类还可能定义对象核心状态和生命周期，两者设计约束不同。
* **MRO 冲突与 metaclass 冲突**：前者检查类之间的顺序约束；后者检查创建这些类对象的 metaclass 兼容性。

本章结论
--------

阅读继承代码时，应先打印或推导实际类的 ``__mro__``，定位目标属性的第一命中类，再检查 descriptor 和实例覆盖，最后沿每个 ``super`` 的起点与绑定对象追踪执行链；多继承能否可靠组合，取决于 C3 给出的稳定顺序和各实现是否遵守统一协作协议。

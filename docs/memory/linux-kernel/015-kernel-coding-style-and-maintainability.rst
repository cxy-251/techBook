第015章：Linux 内核代码风格、评审与可维护性
=========================================

本章必须记住
------------

#. Linux 内核代码风格不是个人排版偏好，而是让控制流、对象关系、错误路径和行为变化容易审查的维护契约。
#. 统一缩进、命名、换行和括号风格的目的，是降低评审者识别真实语义变化的成本。
#. ``scripts/checkpatch.pl`` 可以发现基础格式、命名、空白、注释和常见写法问题，但不能证明代码逻辑正确。
#. 一个补丁应只表达一个可独立理解、验证、回退和 ``git bisect`` 的逻辑改动。
#. 机械格式调整、重命名、重构、行为修改和文档更新应尽量拆成不同补丁。
#. 每个补丁在自身位置应保持可构建、可阅读和可测试，不能依赖后续补丁才恢复正确状态。
#. 清晰的提交说明应回答：问题是什么、影响是什么、代码怎样改变、证据是什么以及存在什么取舍。
#. 修复类补丁应说明触发条件、错误表现和受影响范围；适用时使用 ``Fixes:`` 指向引入问题的提交。
#. 性能改动应提供可复查的测量方法和结果，不能只写“更快”或“减少开销”。
#. ``scripts/get_maintainer.pl`` 根据路径、维护记录和历史帮助找到维护者与邮件列表，但最终评审责任仍属于对应子系统。
#. Kernel-doc 用结构化注释描述函数、结构体、参数、返回值、上下文和锁约束，并可以被文档工具抽取。
#. 导出函数、跨文件接口和模块可见 API 应优先写清参数所有权、调用上下文、锁要求和返回约定。
#. 注释应解释代码本身看不出的原因和约束，例如硬件顺序、锁规则、内存屏障、生命周期和 ABI 兼容。
#. 逐行翻译代码动作的注释会增加噪声，并可能在代码改变后变成错误信息。
#. 注释给维护者阅读；``lockdep_assert_held()`` 等断言可以在调试构建中验证关键锁约束。
#. 关键路径代码应让重要状态检查、分支、错误码和回调调用在本地保持可见。
#. 过度抽象会增加跳转次数，隐藏热路径成本、锁状态和错误语义；提取 helper 必须带来明确复用或边界收益。
#. helper 名称、参数和返回值应暴露真实语义，不能要求读者记住模糊函数背后的隐式规则。
#. 可维护性影响性能回归定位、稳定分支回溯、补丁评审速度和长期优化能力，因此也是长期工程性能的一部分。
#. 一个可维护补丁应让问题、行为变化、错误路径、文档和测试证据相互对应。

必背路径
--------

准备或审查一个内核改动时采用以下顺序：

::

   明确一个具体问题
   → 区分机械清理、重构、行为变化和文档修改
   → 把不同逻辑改动拆成独立 patch
   → 让每个 patch 独立可构建和可验证
   → 在提交说明中写明问题、影响、改动和证据
   → 检查关键状态、分支、错误码和回调是否在 diff 中可见
   → 同步更新 kernel-doc 和必要注释
   → 运行风格、构建、静态检查和相关测试
   → 发送给对应维护者和子系统列表

关键路径审查：

::

   找高频入口
   → 找影响正确性或延迟的主要分支
   → 检查对象、锁和状态是否能在局部确认
   → 检查错误码和回滚路径
   → 评估 helper 是否隐藏了关键语义
   → 检查测试是否覆盖风险最高的路径

提交系列的典型拆分：

::

   Patch 1：纯机械整理或重命名
   → Patch 2：保持行为不变的局部重构
   → Patch 3：真正的状态检查或行为修改
   → Patch 4：对应 API 文档和说明更新

必须区分
--------

风格正确与语义正确
   风格检查减少基础噪声；并发、生命周期、错误路径和硬件语义仍需人工与测试验证。

重构与行为修改
   重构应保持外部行为不变；行为修改会改变状态、返回值、时序或调用者可见结果，应单独审查。

代码注释与代码翻译
   有效注释解释隐藏约束和设计原因；无效注释只是重复源码表面动作。

抽象复用与关键路径显式性
   抽象可以减少重复；关键路径仍需让成本、分支和错误语义容易确认。

构建通过与补丁完成
   构建通过只证明代码可编译；补丁还需要测试、接口文档、风险说明和维护者评审。

一句话结论
----------

Linux 内核的风格、补丁拆分、文档和评审规则都服务于同一个目标：让未来维护者能够快速确认代码行为、风险边界和回退方式。

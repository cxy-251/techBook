第015章：Linux 内核代码风格、评审与可维护性
=========================================

核心知识点
----------

代码风格是维护契约
   Linux 内核风格规则服务于可读性、评审和长期维护。统一缩进、命名和控制流写法，让评审者能把注意力放在对象关系、状态变化和错误路径上，而不是个人格式差异。

风格检查不等于语义正确
   ``scripts/checkpatch.pl`` 可以发现基础格式、命名、空白和常见写法问题，但不能验证并发、生命周期、硬件顺序或返回值语义。

一个补丁应表达一个逻辑改动
   Reviewable patch 应能被独立理解、构建、验证、回退和 ``git bisect``。机械整理、重命名、重构、行为修改和文档更新应尽量拆开。

提交说明解释问题与行为变化
   Commit message 应说明问题是什么、怎样触发、影响什么，以及代码如何解决。修复、性能和接口变化还要提供对应证据、测量或兼容边界。

清晰 diff 降低评审风险
   一个补丁中的每一行都应服务同一个目的。格式噪声和无关重构会隐藏真正行为变化，增加回归定位、稳定分支回溯和 backport 成本。

Kernel-doc 描述接口合同
   导出函数、跨文件接口和模块可见 API 应说明参数、所有权、调用上下文、锁要求和返回值。Kernel-doc 让这些信息靠近代码，并可由文档工具检查格式。

注释解释代码无法直接表达的约束
   有价值的注释说明设计原因、硬件顺序、内存屏障、锁规则、生命周期或 ABI 边界。逐行翻译代码只会制造噪声，并可能随实现变化而过期。

关键路径应保持显式
   高频或高风险路径中的状态检查、锁、主要分支、错误码和回调应容易在局部确认。抽象只有在减少真实重复或建立清晰边界时才有价值。

工具和维护者承担不同角色
   ``checkpatch``、kernel-doc 工具和 ``get_maintainer.pl`` 帮助发现格式问题、验证文档结构和找到评审对象；最终语义判断仍依赖子系统维护者、源码上下文和测试证据。

可维护性影响长期性能和可靠性
   易于理解的代码更容易发现回归、优化热路径、修复错误和安全回溯。可维护性不是性能之外的附加目标，而是长期保持性能与正确性的基础。

关键路径
--------

准备一个内核改动：

::

   明确一个具体问题
   → 区分机械整理、重构、行为变化和文档修改
   → 拆成独立且可构建的 patch
   → 写明问题、影响、改动和证据
   → 检查关键状态、错误路径和回调是否清晰
   → 更新必要的 kernel-doc 与注释
   → 运行风格、构建、静态检查和相关测试
   → 发送给对应维护者和邮件列表

审查关键路径：

::

   找到高频或高风险入口
   → 确认对象、锁和状态
   → 阅读主要成功分支
   → 阅读错误码和回滚路径
   → 检查 helper 是否隐藏关键语义
   → 确认测试覆盖行为变化

补丁系列的典型拆分：

::

   Patch 1：机械整理
   → Patch 2：保持行为不变的重构
   → Patch 3：真正的行为修改
   → Patch 4：接口文档或说明更新

概念辨析
--------

风格正确与语义正确
   风格检查减少基础噪声；并发、生命周期、硬件和错误语义仍需源码分析与测试验证。

重构与行为修改
   重构应保持调用者可见行为不变；行为修改会改变状态、返回值、时序或接口结果，必须单独审查。

代码注释与代码翻译
   有效注释解释隐藏约束和原因；无效注释只是重复代码表面动作。

抽象复用与关键路径显式性
   抽象用于建立稳定边界和消除真实重复；关键路径仍需让成本、状态和错误语义容易确认。

构建通过与补丁完成
   构建通过只证明代码可编译；完整补丁还需要测试、文档、风险说明和维护者评审。

工具检查与维护者判断
   自动工具检查形式和已知模式；维护者判断接口、子系统设计和长期维护成本。

本章结论
--------

内核风格、补丁拆分、提交说明和接口文档共同服务于一个目标：让行为变化、风险边界和回退方式能够被快速、准确地审查和长期维护。

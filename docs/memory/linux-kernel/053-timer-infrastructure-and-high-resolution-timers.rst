第053章：定时器基础设施与高精度定时器
=====================================

核心知识点
----------

定时器把时间条件变成异步控制流
   当前路径登记未来截止时间后即可继续执行；时间系统在条件满足时调用回调，避免为了等待时间而持续占用 CPU。

定时器的生命周期依附宿主对象
   ``timer_list`` 或 ``hrtimer`` 通常嵌入请求、设备或连接对象中。回调只能在宿主对象仍然存活时访问状态，因此取消、重新启动和对象释放必须形成完整协议。

普通 timer 面向低成本粗粒度超时
   ``struct timer_list`` 使用 ``jiffies`` 表达到期点，适合设备请求超时、缓存维护和连接管理。它强调大量 timer 的管理效率，而不是最高时间精度。

普通 timer 回调属于不可睡眠路径
   回调通常运行在 timer softirq 上下文，只应完成状态标记、计数更新、唤醒或排入 workqueue。复杂恢复和阻塞操作应迁移到线程上下文。

到期时间只是最早处理边界
   timer 进入到期状态，不代表回调会在同一时刻开始。中断关闭、softirq 拥塞、CPU 负载和前序回调都会产生实际交付延迟。

hrtimer 提供高分辨率截止时间
   ``struct hrtimer`` 使用 ``ktime_t`` 表达绝对或相对时间，并按最早到期关系组织活动对象，适合精细睡眠、POSIX timer 和时间敏感唤醒。

高精度依赖 clocksource 与 clockevents 协同
   Clocksource 提供当前时间，one-shot clockevent 在未来时刻产生中断。只有精确读取能力而没有可编程事件设备，无法完成高分辨率定时交付。

周期定时应按截止时间推进
   周期性 hrtimer 应把下一次截止时间建立在计划时间轴上，而不是简单使用本次回调结束时刻，从而避免回调延迟不断累积成漂移。

取消 timer 不等于对象已经安全
   删除队列中的 timer 后，还要同步可能正在执行的回调、回调已排入的 work，以及可能重新 arm timer 的路径。teardown 必须先设置停止状态，再分别收束所有异步入口。

timer 类型应由语义和成本决定
   对精度不敏感的维护任务使用普通 timer 或聚合唤醒更节省中断与功耗；只有截止误差影响正确性或延迟目标时，才需要 hrtimer。

关键路径
--------

普通请求超时：

::

   初始化宿主请求与 timer
   → 提交请求并设置 jiffies 截止点
   → 正常完成路径取消 timer
   或到期后进入 timer softirq 回调
   → 原子地标记超时结果
   → 唤醒等待者或 queue_work
   → teardown 阻止重新 arm
   → 同步 timer、work 与宿主对象

高精度 timer：

::

   选择 clock id 与绝对/相对模式
   → 初始化并启动 hrtimer
   → 按 ktime 加入到期队列
   → 最早截止变化时重编程 clockevent
   → 硬件到期产生中断
   → 时间路径处理到期对象
   → 执行短回调或转移复杂工作
   → 周期任务推进到下一计划截止点

安全销毁带 timer 的对象：

::

   设置 stopping 状态
   → 阻止业务路径重新启动 timer
   → 同步删除 timer
   → 取消并同步回调排入的 work
   → 等待其它对象引用退出
   → 最后释放宿主对象

概念辨析
--------

线程睡眠与 timer
   线程睡眠把当前 task 交给调度器等待条件；timer 把一个未来回调交给时间系统管理。

普通 timer 与 hrtimer
   普通 timer 以较低成本提供 jiffies 级超时；hrtimer 提供更精细的时间表达和最早截止排序。

逻辑到期与实际回调
   逻辑到期说明时间条件已经满足；实际回调还要等待中断和执行上下文获得处理机会。

Clocksource 与 clockevents
   Clocksource 负责读取现在；clockevents 负责安排未来中断。

取消 timer 与对象可释放
   取消只处理 timer 入口；对象释放还必须同步运行中的回调、派生 work 和重新启动路径。

本章结论
--------

定时器是时间驱动的异步执行对象：普通 timer 解决低成本超时，hrtimer 解决精细截止，而正确性最终取决于回调上下文与宿主对象生命周期是否同步。

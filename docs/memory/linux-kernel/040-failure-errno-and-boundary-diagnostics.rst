第040章：失败、errno 与边界诊断
===============================

本章必须记住
------------

#. Linux 内核内部通常用负错误码表示失败，例如 ``-EBADF``、``-EFAULT``、``-EINVAL`` 和 ``-EIO``。
#. 用户态可见的 ``errno`` 常量是正整数；常见 libc 系统调用包装函数把内核负错误码转换成返回 ``-1`` 并设置正 ``errno``。
#. 内核返回寄存器、libc 返回值和应用 ``errno`` 是同一个失败在三个层次中的不同表示。
#. 应用只能在函数明确报告失败后读取 ``errno``；成功调用后 ``errno`` 的旧值没有诊断意义。
#. 失败后应立即保存 ``errno``，因为后续库函数和日志函数也可能修改它。
#. ``EBADF`` 通常说明 fd 在当前文件描述符表中无效或不适合该操作。
#. ``EFAULT`` 通常说明用户地址访问失败，不等于内核发生普通 page fault 就必然向用户返回该错误。
#. ``EINVAL`` 表示参数组合、flag、长度或对象状态不符合接口要求，必须结合具体系统调用文档解释。
#. ``EAGAIN`` 或 ``EWOULDBLOCK`` 常表示非阻塞对象当前不能立即完成，并不等于永久故障。
#. ``EINTR`` 表示调用在用户态边界因信号处理而返回；应用是否重试取决于接口语义、已完成进度和业务状态机。
#. ``EIO`` 表示较通用的 I/O 错误，根因可能在文件系统、块层、设备、网络或驱动，需要日志和 trace 补证据。
#. 系统调用返回正数时通常表示成功进展，即使返回量小于请求量也可能只是短操作。
#. ``read`` 返回大于零表示已经读取的字节数；应用必须先消费这些数据，再决定是否继续读取。
#. ``read`` 返回零通常表示普通文件 EOF，或 pipe/socket 对端关闭等对象特定结束语义。
#. 短读不是错误；普通文件尾部、pipe、终端、socket、信号和对象实现都可能产生短读。
#. 写操作也可能部分成功，调用者必须根据已完成字节数更新缓冲区和偏移，不能从头盲目重试。
#. 阻塞系统调用被信号打断时，内核可能返回内部 ``-ERESTART*`` 状态，由退出和信号路径决定自动重启或转换成 ``EINTR``。
#. ``-ERESTARTSYS``、``-ERESTARTNOHAND`` 和 ``-ERESTART_RESTARTBLOCK`` 是内核内部控制值，不是稳定用户态 errno ABI。
#. ``strace`` 有时显示 ``ERESTARTSYS`` 等内部标记，用于解释重启过程；应用最终处理的仍是实际返回值和 ``errno``。
#. ``strace`` 是系统调用边界的第一层诊断工具，能观察调用名、参数、fd 映射、返回值、errno、信号和耗时。
#. ``strace -f`` 用于跟踪线程和子进程，``-tt`` 提供时间，``-T`` 提供调用耗时，``-yy`` 补充 fd 对象信息。
#. ``strace`` 显示一个 syscall 耗时较长，只能证明线程长时间停留在该边界调用中，不能直接说明时间消耗在哪个内核函数。
#. vDSO 中完成的操作没有普通 syscall 入口，因此 ``strace`` 可能看不到每次相关 libc 调用。
#. ``strace`` 使用 ptrace 类机制，会增加开销并改变时序；高频、竞态和低延迟问题需要控制观察范围。
#. 边界错误应先按参数、权限、对象、非阻塞状态和信号分类，再进入内核源码，不能一开始就假设是驱动 bug。
#. ftrace 或 tracepoint 用于补充实际内核路径，perf 用于补充 CPU 样本与调度，dmesg 用于补充设备和子系统错误时间线。
#. 用户态时间戳、strace 时间、tracefs 时间和 dmesg 时间可能使用不同基准，关联前必须先统一或记录转换关系。
#. ``errno`` 说明内核路径最终选择了什么失败原因，不保证它就是故障的最早原因。
#. 排查时应寻找第一条异常、首次对象状态变化和最早底层错误，而不是只解释最后一个 errno。
#. 可重复诊断必须保存程序版本、参数、环境变量、namespace、fd 来源、内核版本、模块和复现动作。

必背路径
--------

从应用失败定位边界事实：

::

   检查函数返回值是否表示失败
   → 立即保存 errno
   → 记录系统调用名和完整参数
   → 判断返回是失败、零结果还是部分成功
   → 判断 fd、路径、权限、flags 和非阻塞状态
   → 检查信号是否打断调用
   → 再决定是否进入内核 trace 和源码

``read`` 返回值分类：

::

   返回值 > 0
   → 已完成部分或全部读取
   → 消费已返回字节
   → 根据协议或对象类型决定继续读取

   返回值 = 0
   → 普通文件 EOF 或对象特定关闭语义
   → 按对象类型结束或切换状态

   返回值 < 0
   → 读取 errno
   → 按 EINTR、EAGAIN、EBADF、EFAULT、EIO 等分类

跨边界诊断：

::

   应用日志固定返回值和 errno
   → strace 固定 syscall 参数、fd、信号与耗时
   → /proc 和 sysfs 固定对象与系统状态
   → dmesg 固定设备和子系统错误
   → tracefs 固定内核实际路径与调度事件
   → perf 固定热点和等待上下文
   → 回到当前内核源码解释最早失败点

分析一个耗时 syscall：

::

   strace 确认调用和总耗时
   → 判断是否阻塞、短操作或信号重启
   → 使用 sched trace 判断运行与睡眠时间
   → 使用目标子系统 tracepoint 判断等待对象
   → 使用 function tracing 缩小执行路径
   → 使用日志确认设备或文件系统错误

必须区分
--------

* 内核负错误码与用户态 ``errno``：内核路径返回负值；常见 libc 包装返回 ``-1`` 并设置正 ``errno``。
* 失败与部分成功：返回正字节数表示已有进展；只有失败返回才进入 errno 处理。
* 短读与 EOF：短读返回正数；EOF 或对象结束语义通常返回零。
* ``EINTR`` 与底层对象损坏：``EINTR`` 表示信号边界结果；对象损坏需要其它错误、日志或 trace 证明。
* 内部 ``-ERESTART*`` 与用户 ABI：内部重启码控制退出路径；应用通常看到重启后的结果或 ``EINTR``。
* syscall 总耗时与 CPU 执行时间：调用耗时可能包含睡眠、I/O、锁等待和调度，不等于内核函数一直占用 CPU。
* 最后 errno 与最早根因：errno 是最终边界结果；真正原因可能发生在更早的资源、设备或并发路径。

一句话结论
----------

errno 是系统调用边界的失败分类，短操作是成功进展；诊断必须先固定返回值、参数、信号和耗时，再用 trace、perf 与日志进入真正的内核路径。

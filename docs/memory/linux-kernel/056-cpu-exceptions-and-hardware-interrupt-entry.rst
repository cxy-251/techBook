第056章：CPU 异常与硬件中断入口
===============================

核心知识点
----------

异常与中断都改变 CPU 控制流
   CPU 会暂停当前执行位置，保存最小返回现场，并跳转到架构预先建立的入口。入口代码再把硬件现场整理成 ``pt_regs`` 或等价结构，交给后续内核代码处理。

异常与当前指令同步相关
   Page fault、除零、无效指令和断点由当前指令、地址转换或调试状态触发。处理结果可能是修复后重试、转换成用户信号，或者在内核态升级为 Oops、panic。

硬件中断来自外部事件
   网卡收包、磁盘完成、定时器和键盘事件由设备或中断控制器异步送入 CPU。它们与被打断指令没有直接语义关系，只是借用了当前 CPU 的执行时刻。

入口规则由架构定义
   x86 使用 IDT 和向量入口，arm64 使用异常向量表。保存哪些寄存器、是否携带错误码、是否切换栈以及返回指令都属于架构协议。

``pt_regs`` 保存被打断现场
   该结构让异常、IRQ、信号、ptrace、审计和 tracing 路径能够读取入口寄存器。它属于内核内部表示，不能当作跨架构固定 ABI。

通用 entry 维护上下文状态
   低级入口之外，内核还要更新 hardirq、RCU、lockdep、tracing、时间记账、抢占计数和上下文跟踪状态。入口与退出共同构成完整协议。

``current`` 不是事件发起者
   硬中断发生时，``current`` 仍指向被打断的 task。调用栈中出现某个进程，只能说明该 task 当时占用 CPU，不能证明设备事件由它产生。

硬中断必须保持非阻塞
   Hardirq context 不能睡眠，不能使用阻塞 mutex、普通用户地址访问或 ``GFP_KERNEL``。处理器应只确认来源、收集最小状态、清除或屏蔽事件，并安排后续工作。

异常后果取决于来源与可恢复性
   用户态非法访问通常转为信号；内核态用户访问失败可能通过 exception table fixup 返回错误；不可恢复的内核异常会形成 Oops 或 panic。

退出路径可能继续处理工作
   返回被打断位置前，内核可能处理 softirq、重新调度请求、信号和用户态返回工作。因此 IRQ handler 返回不等于 CPU 必然立即恢复原 task。

关键路径
--------

同步异常路径：

::

   当前指令触发异常
   → CPU 保存指令位置、状态与错误信息
   → 架构入口建立 pt_regs
   → 通用 entry 更新上下文状态
   → 异常处理器检查地址、权限或指令
   → 修复并重试、发送信号、Oops 或 panic
   → 通用 exit 恢复入口状态
   → 返回原执行流或终止当前任务

外部硬件中断路径：

::

   设备产生事件
   → 中断控制器选择目标 CPU 与入口向量
   → CPU 进入架构 IRQ 入口
   → 保存现场并建立 pt_regs
   → 建立 hardirq 上下文状态
   → generic IRQ 层定位 IRQ 描述符
   → 调用 flow handler 与设备 handler
   → 确认设备并安排延迟处理
   → 退出 hardirq 上下文
   → 返回被打断路径或进入调度

判断异常后果：

::

   确认触发指令与故障地址
   → 解析架构错误码
   → 区分用户态与内核态
   → 检查 VMA、页表、权限与异常修复表
   → 判断是否能够修复或重试
   → 否则转换为信号、Oops 或 panic

概念辨析
--------

异常与外部中断
   异常与当前指令同步相关；外部中断由当前执行流之外的设备事件异步触发。

入口现场与 task 身份
   ``pt_regs`` 保存被打断现场；``current`` 只表示当时运行的 task，不表示它是设备事件的来源。

Fault 与硬件损坏
   架构术语 fault 描述一种异常及其重试语义，不表示物理硬件必然损坏。

硬中断与进程上下文
   Hardirq 不能睡眠，也没有普通用户请求语义；进程上下文通常可调度，并可在受控条件下访问用户空间。

关闭本地 IRQ 与多核同步
   关闭本地中断只限制当前 CPU 的普通可屏蔽 IRQ，不能阻止其它 CPU 并发访问共享对象。

本章结论
--------

异常解释当前指令为何无法正常继续，硬件中断解释外部设备事件怎样进入 CPU。两者都依赖架构入口保存现场，再由通用内核完成状态管理、分发和安全退出。

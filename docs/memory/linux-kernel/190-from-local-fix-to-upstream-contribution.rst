第190章：从本地修复到 Upstream Contribution
===========================================

核心知识点
----------

本地可用不等于可上游
   Local Hack 可以依赖单机配置、硬编码设备或临时绕过；Upstreamable Fix 必须解释真实根因、适用范围、兼容性、验证方法和长期维护成本。

修复目标是恢复不变量
   症状消失可能只是改变触发概率。资源泄漏应修复所有权和回滚关系，释放后访问应修复 Publish、Use、Remove 与 Free 顺序，数据竞争应补全允许的同步语义。

适用范围必须有证据
   硬件 Quirk、Firmware 条件、Capability 判断和性能优化都需要明确边界，不能从单台机器或一次 Workload 推广到整个设备类别。

公共合同必须保持或显式迁移
   上游补丁应说明 ABI、错误码、配置和既有用户行为是否保持不变。新增参数、导出符号、UAPI 和控制面会形成长期承诺，因此需要更广评审。

测试应与风险匹配
   Build 验证编译和链接；KUnit 验证局部逻辑；kselftest 验证用户态合同；真实硬件覆盖 Firmware、IRQ、DMA、总线和电源时序。正常路径、失败回滚和 Teardown 应同时验证。

上游化包含公开评审
   补丁需要正确基线、逻辑 Commit、自包含说明、真实 Trailer 和维护者路由，并持续处理 Review、机器人结果和 v2、v3 迭代。

进入 Mainline 仍需继续负责
   维护者树、``linux-next`` 和 Mainline ``-rc`` 可能暴露新的配置、架构和用户回归。作者应跟踪实际入树状态并参与后续修复。

Stable 是上游修复的后续阶段
   Stable 通常评估已经进入上游、范围明确且风险较低的修复。Backport 需要适配旧版依赖和对象模型，并在目标版本重新构建与验证。

关键路径
--------

本地修复上游化：

::

   本地症状
   → 定位首个可信失败点
   → 重建对象不变量
   → 去除硬编码和旁路
   → 形成通用最小修复
   → 验证兼容性与测试边界
   → 组织逻辑 Patch

贡献生命周期：

::

   正确路由与 Patch Mail
   → Review 和 Reroll
   → Maintainer Tree
   → linux-next
   → Mainline -rc
   → 用户回归跟踪
   → Stable Backport 或后续修复

概念辨析
--------

* **Local Hack 与 Upstreamable Fix**：前者恢复私有环境；后者恢复明确范围内的通用系统不变量。
* **症状消失与根因修复**：症状可能因时序或配置变化消失；根因修复必须恢复所有权、状态机或同步合同。
* **构建通过与运行正确**：构建只验证语法、类型和链接；运行测试还要覆盖正常、错误和并发路径。
* **虚拟环境与真实硬件**：Mock、UML 和 VM 适合逻辑验证；真实硬件还包含 Firmware、DMA、IRQ 和物理时序。
* **Mainline 修复与 Stable Backport**：前者面向当前上游；后者要在旧版本依赖和语义下重新适配。
* **Patch 已发送与贡献完成**：发送只是评审开始；贡献还包括入树确认、回归响应和后续维护。

本章结论
--------

把本地修补转化为上游贡献，必须从局部症状还原通用对象不变量，用风险匹配的测试和可评审 Patch 证明修复，并持续跟进 Mainline、回归与 Stable 生命周期。

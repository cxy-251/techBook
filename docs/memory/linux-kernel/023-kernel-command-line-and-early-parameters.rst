第023章：内核命令行与早期参数
=============================

核心知识点
----------

命令行是早期运行时控制面
   Kernel command line 在用户态出现之前向内核传递根设备、控制台、日志、调试和 init 等运行期选择。Bootloader 或固件按架构协议把字符串交给内核。

原始文本与解析副本分离
   架构代码保存原始命令行，通用启动代码再建立保存副本和可修改的解析副本。``/proc/cmdline`` 展示传入文本，但不能证明每个参数已经成功生效。

参数语义由注册点和解析阶段决定
   参数名称只是线索。真正的语义来自参数注册宏、所属参数表、解析时机、回调返回值以及被修改的内核对象。

``early_param`` 服务最早期环境
   ``early_param(name, fn)`` 在普通子系统建立前解析，适合 early console、日志级别和部分架构或内存开关。回调只能依赖极少的早期设施。

``__setup`` 处理普通启动参数
   ``__setup(name, fn)`` 注册启动期回调，用于根文件系统、init 程序和其它核心启动选择。它晚于 early 参数处理，但仍发生在用户态 init 启动前。

``core_param`` 与 ``module_param`` 绑定有类型变量
   ``core_param`` 面向核心内核变量；``module_param`` 面向内建组件或可加载模块。参数类型决定解析方式，权限位决定运行后是否通过 sysfs 暴露。

未知参数可能被转交而不是报错
   未被内核识别的无点号参数可以进入 PID 1 的参数或环境；带点号的参数通常保留给模块参数路径；``--`` 之后的内容直接传给 init。因此命令行中出现文本不等于内核接受了预期语义。

调试参数必须匹配启动阶段
   ``earlycon`` 恢复早期输出，``loglevel`` 和 ``ignore_loglevel`` 控制控制台可见性，``log_buf_len`` 扩大日志缓冲区，``initcall_debug`` 记录初始化函数的调用、返回和耗时。

关键路径
--------

命令行解析主路径：

::

   bootloader 或固件准备命令行
   → 架构代码保存 boot_command_line
   → setup_arch() 整理架构参数
   → setup_command_line() 建立保存副本与解析副本
   → parse_early_param() 处理 early_param
   → parse_args() 处理 kernel_param 类参数
   → 普通 setup 回调与未知参数分流
   → saved_command_line 供 /proc/cmdline 观察

未知参数分流：

::

   已注册参数
   → 执行对应解析器

   未识别且名称含点号
   → 保留给模块参数机制

   未识别且包含等号
   → 作为 init 环境变量候选

   未识别且不含等号
   → 作为 init 参数候选

   位于 -- 之后
   → 直接传给 init

概念辨析
--------

参数文本与参数生效
   参数文本出现只证明它被传入；注册点匹配、回调成功和目标状态改变才能证明参数生效。

``early_param`` 与 ``__setup``
   ``early_param`` 在最低依赖环境中处理最早期控制；``__setup`` 在稍后的启动阶段处理普通核心参数。

``core_param`` 与 ``module_param``
   ``core_param`` 面向无普通模块前缀的核心变量；``module_param`` 面向内建组件或可加载模块的参数接口。

``rdinit=`` 与 ``init=``
   ``rdinit=`` 选择 initramfs 中的 init；``init=`` 选择最终根文件系统中的 init。

未知参数与无效参数
   未知参数可能被转交给模块或 PID 1；被保留下来不表示拼写正确，也不表示产生了预期作用。

本章结论
--------

内核命令行是一组按阶段登记和解析的控制接口；判断一个参数必须同时确认注册表、解析时机、回调结果和最终状态。

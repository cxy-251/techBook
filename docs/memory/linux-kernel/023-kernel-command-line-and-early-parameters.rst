第023章：内核命令行与早期参数
=============================

本章必须记住
------------

#. Kernel command line 是内核在用户态出现之前接收运行期配置的主要输入通道。
#. Bootloader、固件接口或架构启动协议把命令行字符串交给内核，内核再按不同阶段解析参数。
#. 启动参数可以决定根设备、控制台、日志级别、早期调试、init 程序、模块参数和其它启动行为。
#. 架构代码先把原始字符串保存为 ``boot_command_line``，通用启动代码再建立用于保存和解析的副本。
#. ``saved_command_line`` 保留原始启动参数，通常可通过 ``/proc/cmdline`` 观察；``static_command_line`` 等解析副本会被参数解析器原地切分。
#. ``/proc/cmdline`` 只能证明某段文本被传入，不能单独证明对应回调执行成功或目标状态已经改变。
#. 参数名称只是入口线索，真正决定语义的是参数注册表、解析阶段、回调函数和被修改的内核对象。
#. ``early_param(name, fn)`` 注册必须在普通子系统准备前生效的参数，例如早期控制台和部分日志、内存或架构开关。
#. ``early_param`` 条目在 ``parse_early_param()`` 阶段处理，此时可依赖的内核设施很少。
#. ``__setup(name, fn)`` 注册普通启动期 setup 参数，处理时间通常晚于 early 参数，但仍发生在用户态 init 启动之前。
#. ``core_param()`` 绑定核心内核变量和参数类型，不使用普通模块名前缀，并可携带 sysfs 权限语义。
#. ``module_param()`` 把内建组件或可加载模块的变量登记为有类型参数；可加载模块参数通常在模块初始化函数执行前解析。
#. 内建代码的模块参数可以从内核命令行取得，常使用 ``module_name.parameter=value`` 形式区分所属组件。
#. 参数的权限位决定相应模块参数是否在 ``/sys/module/<name>/parameters/`` 中可读或可写。
#. 可写参数属于运行时控制面，setter 必须处理并发、非法值、对象状态和失败回滚。
#. ``earlycon`` 用于普通 console 驱动准备前建立输出通道，必须在足够早的参数阶段生效。
#. ``loglevel=`` 改变控制台日志级别，``ignore_loglevel`` 可让更多消息输出到控制台，``log_buf_len=`` 调整日志缓冲区容量。
#. ``initcall_debug`` 打开 initcall 的调用、返回值和耗时日志，用于定位启动初始化阶段。
#. ``root=``、``rootfstype=``、``rootflags=`` 和 ``rootwait`` 等参数影响最终根文件系统选择和挂载行为。
#. ``init=`` 指定最终根文件系统中的用户态 init，``rdinit=`` 指定 initramfs 中的 init，两者对应不同启动阶段。
#. 普通参数解析器无法识别的无点号参数，可能被传递给 PID 1 的参数或环境，而不是立即报成内核错误。
#. 未知参数包含 ``=`` 时通常可进入 init 环境变量集合；不包含 ``=`` 时通常可进入 init 参数集合。
#. 参数名中包含点号的未知项通常保留给模块参数处理，例如 ``usbcore.foo=1``。
#. 命令行中的 ``--`` 表示后续内容不再按内核参数处理，而直接作为用户态 init 的参数。
#. 未知参数被转交给 init 或模块，不表示拼写错误一定会被明显报告；启动参数必须与目标版本文档和源码注册点核对。
#. 启动命令行常通过日志和 ``/proc/cmdline`` 对用户可见，不应直接放入密码、私钥或其它长期秘密。
#. 参数是否可用还受 Kconfig、架构、内建或模块形态以及内核版本限制，文档中存在参数不表示目标构建一定支持。

必背路径
--------

命令行进入内核：

::

   bootloader 或固件准备命令行
   → 架构代码保存到 boot_command_line
   → setup_arch() 接收并整理架构参数
   → setup_command_line() 建立保存副本和解析副本
   → parse_early_param() 处理早期参数
   → parse_args() 处理 core_param 与 module_param 等参数
   → __setup 回调处理启动 setup 参数
   → 未识别参数进入模块候选或 init 参数路径
   → saved_command_line 供 /proc/cmdline 等接口观察

四类参数入口：

::

   early_param
   → 最早期解析
   → 修改 early console、日志、内存或架构状态

   __setup
   → 普通启动阶段回调
   → 修改 root、init 或其它启动核心状态

   core_param
   → 核心变量与类型绑定
   → 可携带运行期权限

   module_param
   → 内建组件或模块参数
   → 加载前解析，并可能导出到 sysfs

未知参数分流：

::

   参数已被内核注册表识别
   → 执行对应解析器

   未识别且名称包含点号
   → 保留给模块参数机制

   未识别且包含等号
   → 作为 init 环境变量候选

   未识别且不含等号
   → 作为 init 命令行参数候选

   位于 -- 之后
   → 直接传给 init

早期调试参数组合：

::

   earlycon
   → console=ttyS0,115200n8
   → loglevel=8
   → ignore_loglevel
   → log_buf_len=4M
   → initcall_debug

必须区分
--------

* 参数文本与参数生效：命令行出现某个字符串只证明它被传入；对应注册点、解析返回值和运行对象状态才能证明它生效。
* ``early_param`` 与 ``__setup``：``early_param`` 服务最早期环境；``__setup`` 在稍后的启动阶段处理普通核心参数。
* ``core_param`` 与 ``module_param``：``core_param`` 面向核心内核变量且无普通模块名前缀；``module_param`` 面向内建组件或可加载模块参数。
* ``init=`` 与 ``rdinit=``：``rdinit=`` 选择 initramfs 中的 init；``init=`` 选择切换到最终根文件系统后执行的 init。
* 未知参数与无效参数：未知参数可能被传给模块或 PID 1；被接收不代表它对内核产生了预期作用。

一句话结论
----------

内核命令行不是一张同时解析的键值表，而是一组按启动阶段登记和扫描的控制接口；判断参数必须同时看注册宏、解析时机和目标状态。

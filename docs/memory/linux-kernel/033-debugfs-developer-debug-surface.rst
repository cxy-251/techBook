第033章：debugfs 是开发者控制的调试面
=====================================

核心知识点
----------

debugfs 面向开发和诊断
   ``debugfs`` 通常挂载在 ``/sys/kernel/debug``，用于快速暴露队列、寄存器、统计、内部状态和测试开关。它服务当前版本的开发调试，不是稳定产品接口。

debugfs 不承诺稳定 ABI
   文件名、目录结构、输出格式和写入语义都可能随内核或驱动实现变化。长期依赖的用户态接口应使用 sysfs、netlink、ioctl 或其它受维护 ABI。

可用性取决于多层条件
   目标内核需要启用 ``CONFIG_DEBUG_FS``，debugfs 需要实际挂载，相关模块或设备需要完成初始化，安全策略与权限还必须允许访问。路径缺失不能直接说明核心功能不存在。

文件回调连接到私有对象
   驱动通常通过 ``debugfs_create_*()`` 创建目录和文件，并把私有对象指针交给读写回调。文件内容的含义取决于该对象字段、更新位置、同步规则和生命周期。

读取也可能产生副作用
   读取某些文件可能访问设备寄存器、唤醒 runtime PM、遍历高成本队列或清除硬件状态。不能把所有 debugfs 读取都视为零成本、无副作用观察。

写入属于高风险调试控制
   控制文件可能打开故障注入、改变驱动行为、重置统计、触发硬件动作或放大日志。写入前必须明确作用对象、持续时间、恢复方法和失败边界。

调试入口必须服从对象生命周期
   文件存在期间宿主对象必须有效。对象移除时应先阻止新访问并同步正在运行的回调和异步活动，再删除 debugfs 条目，最后释放对象。

生产环境需要限制暴露面
   debugfs 可能暴露地址、寄存器、内存内容或故障注入能力，也可能增加锁竞争和时序扰动。生产系统应严格控制挂载、权限和使用范围。

关键路径
--------

确认 debugfs 条目是否可用：

::

   检查 CONFIG_DEBUG_FS
   → 确认 debugfs 实际挂载
   → 确认模块或设备已经初始化
   → 确认驱动创建了目标条目
   → 检查权限、LSM 与 lockdown
   → 再读取文件

读取内部状态：

::

   确认文件来源和回调语义
   → 判断是否访问硬件或执行高成本操作
   → 保存时间、内核版本和原始输出
   → 回到源码确认字段单位和更新位置
   → 与日志和 tracing 交叉验证

安全拆除调试入口：

::

   标记对象停止服务
   → 阻止新的读写和业务事件
   → 同步正在执行的回调与异步工作
   → 删除 debugfs 目录
   → 最后释放宿主对象

概念辨析
--------

调试接口与稳定 ABI
   debugfs 追求开发效率和实现可见性；稳定 ABI 必须长期维护名称、格式和语义。

路径位于 ``/sys`` 与属于 sysfs
   ``/sys/kernel/debug`` 常是独立挂载的 debugfs，不能仅根据路径前缀判断文件系统类型。

读取文件与无副作用观察
   某些读取会触发硬件访问、唤醒设备或消耗大量 CPU，是否安全必须看具体回调。

删除文件与释放对象
   删除文件关闭用户入口；对象释放还要等待回调、异步任务和其它持有者退出。

文件缺失与功能缺失
   配置、挂载、初始化、硬件和权限任一条件不满足都可能导致条目缺失。

权限受限与接口安全
   权限只减少访问者；回调仍必须验证输入并维护锁、状态和生命周期。

本章结论
--------

``debugfs`` 是版本敏感的内核内部调试面；可靠使用它必须同时确认接口来源、副作用、安全权限和宿主对象生命周期。

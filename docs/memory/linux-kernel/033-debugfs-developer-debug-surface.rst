第033章：debugfs 是开发者控制的调试面
=====================================

本章必须记住
------------

#. ``debugfs`` 是内核开发者向用户空间暴露内部调试状态和测试开关的伪文件系统，常见挂载点是 ``/sys/kernel/debug``。
#. debugfs 的主要服务对象是开发、测试和故障诊断，不是长期稳定的产品接口。
#. debugfs 文件名、目录层级、输出格式和写入语义通常没有稳定 ABI 承诺，内核升级后可以发生变化。
#. 生产程序不应把 debugfs 文本格式当成稳定协议；需要长期兼容的接口应选择正式 sysfs、netlink、ioctl 或其它受维护 ABI。
#. debugfs 是否可用要经过多层判断：内核是否启用 ``CONFIG_DEBUG_FS``、启动策略是否允许、文件系统是否挂载、子系统是否创建条目、权限和安全策略是否允许访问。
#. ``/sys/kernel/debug`` 位于 ``/sys`` 目录下，不表示它属于 sysfs；应通过挂载类型确认它是独立的 debugfs。
#. 驱动和子系统通常通过 ``debugfs_create_dir()``、``debugfs_create_file()`` 以及整数、布尔、blob、regset 和 seqfile helper 创建条目。
#. 一个 debugfs 文件常把私有对象指针传给读写回调，回调再读取队列、计数器、寄存器、状态位或测试配置。
#. 多行状态、内部队列、寄存器快照和临时统计适合放在 debugfs，因为这些内容与实现细节紧密相关。
#. 读取 debugfs 文件不一定完全无副作用；读取设备寄存器可能唤醒设备、触发 runtime PM 或改变某些硬件状态。
#. 写入 debugfs 控制文件可能打开故障注入、修改驱动行为、重置统计、触发硬件访问或扩大日志量，属于高风险操作。
#. debugfs 权限只是第一层保护；接口本身还要正确验证输入、限制范围并遵守锁、上下文和对象状态机。
#. debugfs 文件可见只证明子系统创建了调试入口，不证明对应功能、硬件或数据一定正确。
#. 文件缺失可能来自配置关闭、没有挂载、模块未加载、硬件不存在、初始化未走到创建点、权限或 lockdown/LSM 限制。
#. debugfs 创建失败通常不应破坏核心设备功能；调试面应与业务正确性保持清晰边界。
#. 创建目录后应保存返回的 ``dentry``，以便对象移除或模块卸载时统一删除整棵调试目录。
#. ``debugfs_remove()`` 或 ``debugfs_remove_recursive()`` 关闭文件入口，但不能自动停止回调可能访问的 work、timer、IRQ 或设备操作。
#. 删除 debugfs 条目前必须先阻止新的业务事件，必要时等待正在执行的读写回调和异步工作结束。
#. 回调持有的私有对象必须在文件存在期间保持有效；对象先释放、debugfs 后删除会产生 use-after-free。
#. debugfs 中可能暴露内核地址、寄存器、密钥相关状态、内存内容或故障注入能力，因此生产系统需要严格限制挂载和访问。
#. 大量读取高成本调试文件或打开高频调试开关可能造成性能下降、锁竞争、日志覆盖和时序变化。
#. sysfs 强调设备对象和属性纪律；procfs 强调进程与系统状态；tracefs 提供统一追踪控制面；debugfs 强调低约束的开发诊断效率。
#. 调试结论必须记录内核版本、配置、模块版本和 debugfs 文件格式，因为这些接口具有版本敏感性。
#. debugfs 是证据入口，不是设计文档；读到内部字段后仍要回到源码确认字段单位、更新位置、同步规则和生命周期。

必背路径
--------

确认 debugfs 是否可用：

::

   检查目标内核是否启用 CONFIG_DEBUG_FS
   → 检查启动参数和安全策略
   → 确认 debugfs 已挂载
   → 确认目标模块或设备已经初始化
   → 确认驱动调用 debugfs_create_* 创建条目
   → 检查目录权限、LSM 和 lockdown
   → 再读取目标文件

驱动导出调试状态：

::

   初始化驱动私有对象
   → 创建 debugfs 目录
   → 创建状态或控制文件
   → 把私有对象指针绑定到文件
   → read/write 回调访问对象状态
   → 对象移除时阻止新访问
   → 等待旧回调和异步执行退出
   → 删除 debugfs 目录
   → 最后释放私有对象

安全读取调试文件：

::

   确认文件来源和语义
   → 查看权限和当前设备状态
   → 判断读取是否访问硬件或唤醒设备
   → 保存原始输出与时间
   → 结合日志和源码解释字段
   → 不把当前格式写入长期稳定协议

写入调试控制前：

::

   使用测试机或可恢复环境
   → 明确写入副作用和停止方法
   → 保存修改前状态
   → 缩小作用对象和持续时间
   → 执行写入并捕获证据
   → 立即验证行为
   → 恢复开关并清理调试状态

必须区分
--------

调试接口与稳定 ABI
   debugfs 服务当前版本的开发诊断；稳定 ABI 要长期维护名称、格式和语义。

路径位于 ``/sys`` 与文件系统属于 sysfs
   ``/sys/kernel/debug`` 常挂载独立 debugfs，不能仅按路径前缀判断文件系统类型。

读取文件与无副作用观察
   某些读取会访问硬件、唤醒设备或计算高成本状态，必须阅读对应回调。

删除调试文件与对象安全释放
   删除文件关闭用户入口；对象释放还要同步回调、异步工作和其它持有者。

文件缺失与功能缺失
   文件缺失可能发生在构建、启动、挂载、初始化或权限任一层，不能直接判定核心功能不存在。

权限受限与接口安全
   权限减少访问者；回调仍必须进行正确验证和生命周期保护。

一句话结论
----------

``debugfs`` 是为开发者快速暴露内核内部状态而存在的版本敏感调试面；使用时必须同时管理接口不稳定性、副作用、安全权限和宿主对象生命周期。

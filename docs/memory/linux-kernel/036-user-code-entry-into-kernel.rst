第036章：用户代码怎样进入内核
=============================

本章必须记住
------------

#. 系统调用是用户态请求内核服务的正式入口，是一次受 ABI、CPU 架构和内核入口协议共同约束的边界穿越。
#. 用户程序运行在用户态，不能直接执行任意内核代码，也不能直接访问内核对象和内核地址空间。
#. ``read(fd, buf, count)`` 在用户态看起来像函数调用，实际会经过 libc 包装、syscall ABI、CPU 入口和内核分发。
#. libc 包装函数把 C 函数参数转换成目标架构规定的系统调用号、参数寄存器和返回值约定。
#. 普通 C 函数调用 ABI 与系统调用 ABI 是两套不同约定；系统调用参数寄存器必须按目标架构单独确认。
#. x86-64 通常使用 ``syscall`` 指令进入内核；arm64 通常使用 ``svc #0``。入口指令和寄存器布局属于架构 ABI。
#. 在 x86-64 Linux syscall ABI 中，调用号放在 ``rax``，前六个参数通常使用 ``rdi``、``rsi``、``rdx``、``r10``、``r8``、``r9``，返回值放在 ``rax``。
#. x86-64 系统调用第四参数使用 ``r10``，不能照搬普通 System V C ABI 的第四参数寄存器 ``rcx``。
#. 在 arm64 Linux syscall ABI 中，调用号通常放在 ``w8``，参数通常放在 ``x0`` 到 ``x5``，返回值放在 ``x0``。
#. CPU 执行系统调用指令后，会从用户权限级进入内核权限级，并跳转到内核预先配置的架构入口。
#. 架构入口首先处理寄存器、栈、特权状态和返回现场，不能把它当成普通 C 函数入口阅读。
#. Linux 常用 ``struct pt_regs`` 保存或表示进入内核时的寄存器现场，供 syscall、signal、ptrace、audit 和 tracing 路径共同读取。
#. ``pt_regs`` 是内核内部对象，不是用户态 ABI；它的字段布局随架构变化。
#. 架构入口负责解释当前 CPU 的 syscall ABI，通用 entry 代码负责上下文状态、追踪、审计、过滤和退出工作。
#. 系统调用号经过当前 ABI 对应的分发表，最终连接到 wrapper 和具体系统调用实现。
#. ``SYSCALL_DEFINE*`` 一类宏生成或参与生成系统调用入口；具体符号名称和 wrapper 层级具有版本与架构差异。
#. 系统调用入口只把请求带入内核，不代表参数已经可信，也不代表操作一定被允许。
#. ``fd`` 的有效性由文件描述符路径检查，用户缓冲区由 uaccess 路径检查，访问权限由对象和安全路径检查。
#. seccomp、ptrace、audit、tracing 和安全机制都可能在系统调用入口或退出附近观察、过滤或改变处理流程。
#. 系统调用执行期间，当前任务仍是发起调用的进程上下文；它可以进入内核子系统、阻塞、睡眠或被调度出去。
#. 内核返回用户态前必须处理返回值、待处理信号、调度请求、审计、追踪和用户态寄存器恢复。
#. 返回路径会验证能否使用快速返回形式；不满足条件时会选择更通用、更严格的返回路径。
#. 系统调用成功或失败的最终 ABI 结果放入架构规定的返回寄存器，用户态包装层再转换成语言或 libc 接口语义。
#. 静态源码只能说明入口可能怎样分支；实际机器走过的路径还要用 tracepoint、ftrace 或 perf 验证。
#. 阅读 syscall 入口必须分四层：用户 API、syscall ABI、架构入口、通用内核与子系统实现。

必背路径
--------

一次系统调用的主干：

::

   用户代码调用 libc 包装函数
   → 包装函数准备系统调用号和参数寄存器
   → CPU 执行 syscall 或 svc 指令
   → 处理器切换到内核权限级和入口地址
   → 架构汇编入口保存用户现场
   → 建立 pt_regs 视图
   → 架构 C 入口解释调用号与参数
   → 通用 entry 逻辑执行追踪、审计和过滤
   → syscall table 分发到具体实现
   → 内核子系统处理请求
   → 退出路径处理信号、调度、审计和 tracing
   → 恢复用户寄存器与权限级
   → 返回用户代码

阅读某个架构的入口：

::

   查目标架构 syscall ABI
   → 确认入口指令和调用号寄存器
   → 确认参数与返回值寄存器
   → 找架构汇编入口
   → 找 pt_regs 的保存方式
   → 找架构 C 分发函数
   → 找通用 syscall entry/exit
   → 最后进入具体系统调用实现

验证一次 ``read``：

::

   用户态 read(fd, buf, count)
   → syscall ABI 提交 fd、用户指针和长度
   → 入口代码取得调用号
   → 分发到 read 系统调用实现
   → fd 查找得到 struct file
   → 文件操作路径产生数据
   → uaccess 把数据写回用户缓冲区
   → 返回已读字节数或错误

必须区分
--------

用户 API 与系统调用 ABI
   ``read()`` 是用户可见接口；调用号、寄存器和返回约定是二进制边界协议。

普通 C ABI 与 syscall ABI
   普通函数调用和用户态进入内核使用不同寄存器规则，不能混用。

架构入口与通用内核逻辑
   架构入口处理 CPU 现场；通用逻辑处理状态、过滤、审计和分发。

进入内核与参数可信
   进入内核只完成控制权转移；用户参数仍必须逐层验证。

``pt_regs`` 与用户寄存器 ABI
   ABI 规定用户怎样提交寄存器；``pt_regs`` 是内核保存和解释现场的内部结构。

系统调用返回与普通函数返回
   syscall 退出还要处理信号、调度和权限恢复，远多于普通 ``ret``。

一句话结论
----------

系统调用是一次契约化的权限转换：用户态按 ABI 提交调用号和参数，架构入口接管 CPU 现场，通用内核完成检查与分发，退出路径再安全恢复用户态。

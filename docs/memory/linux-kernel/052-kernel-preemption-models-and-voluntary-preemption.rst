第052章：内核抢占模型与自愿抢占
===============================

核心知识点
----------

抢占模型决定何时允许切换
   上下文切换回答 CPU 怎样从一个 task 转给另一个 task，抢占模型回答内核代码执行期间何时允许发生这种切换。

need_resched 只是调度请求
   更合适的 task 变为 runnable 后，当前 CPU 可以设置 ``need_resched``。真正切换仍要等待合法调度边界，并满足抢占计数、锁和中断状态要求。

抢占能力由配置与运行状态共同决定
   内核构建选择 none、voluntary、full 或其它抢占模式；运行时还要检查 ``preempt_count``、hardirq、softirq、锁和显式抢占禁止状态。

非抢占模型延长连续内核执行段
   普通内核代码通常运行到阻塞、显式 ``schedule()`` 或返回用户态附近才让出 CPU。它减少并发插入点，但最坏延迟受最长不可让出路径限制。

自愿抢占依赖明确让出点
   ``cond_resched()`` 允许长循环在状态稳定且可以睡眠的位置检查调度需求。它缩短长批处理路径，但不能突破关中断区、原子区和两个检查点之间的最长执行段。

完全可抢占模型增加内核交错
   临界区外的内核代码可以在更多位置被高优先级 task 抢占，从而降低响应延迟。代码不能再依赖“进入内核后会连续执行到函数返回”的隐含假设。

preempt_count 表达不可抢占嵌套
   ``preempt_disable()``、spinlock、hardirq 和 softirq 等状态会增加或影响抢占禁止层级。只有恢复到允许值，延后的抢占请求才可能被处理。

可抢占不等于可以主动睡眠
   内核被动可被抢占，只说明调度器可以切走当前 task；函数主动睡眠仍要求进程上下文、没有原子锁、没有关闭中断，并满足所用 API 的上下文规则。

PREEMPT_RT 改变部分执行与锁语义
   实时抢占通过 IRQ 线程化、优先级继承和部分锁实现变化缩短最坏延迟。``raw_spinlock_t`` 仍保护真正不可睡眠的底层区间，不能假设实时内核中所有路径都可抢占或可睡眠。

抢占策略是多目标工程取舍
   更积极的抢占通常改善长尾延迟，同时增加同步复杂度、上下文切换和局部性损失。正确模型取决于实时性、吞吐和目标工作负载。

关键路径
--------

一次抢占请求：

::

   更合适的 task 变为 runnable
   → 当前 CPU 设置 need_resched
   → 检查当前抢占模型
   → 检查 preempt_count、IRQ、softirq 与锁状态
   → 到达显式调度点或抢占检查点
   → 条件允许时进入调度器
   → 选择并切换到新 task

长循环中的自愿调度：

::

   完成一批对象处理
   → 把共享状态恢复到稳定边界
   → 确认没有禁止睡眠的锁或上下文
   → cond_resched 检查调度需求
   → 必要时让出 CPU
   → 恢复后重新确认对象与循环条件
   → 继续下一批

不可抢占区的进入与退出：

::

   preempt_disable 或取得 spinlock
   → 抢占禁止层级增加
   → 完成短小临界更新
   → 释放锁或 preempt_enable
   → 抢占禁止层级恢复
   → 若 need_resched 已设置则执行延后检查

概念辨析
--------

need_resched 与实际切换
   ``need_resched`` 记录重新调度需求；只有到达合法边界后才会发生上下文切换。

非抢占内核与用户态不可抢占
   非抢占模型主要限制普通内核态执行段，用户态仍受时间片和高优先级任务调度。

自愿抢占与完全可抢占
   自愿模式依赖显式让出点；完全可抢占模式允许临界区外更细粒度地切换。

禁止抢占与禁止中断
   禁止抢占阻止 task 切换；禁止中断还会推迟本地 IRQ、clockevent 和 timer 入口。

可抢占与可睡眠
   可抢占描述调度器能否切走当前 task；可睡眠描述当前代码能否主动阻塞，两者约束不同。

spinlock_t 与 raw_spinlock_t
   PREEMPT_RT 下部分 ``spinlock_t`` 可能采用可调度实现；``raw_spinlock_t`` 保留原始不可睡眠语义。

本章结论
--------

内核抢占由构建模型和当前临界状态共同决定；``need_resched`` 只提出请求，CPU 必须退出不可抢占区并到达合法检查点后才能真正切换 task。

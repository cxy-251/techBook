第037章：系统调用表、入口代码与 ABI 稳定性
==========================================

本章必须记住
------------

#. 系统调用 ABI 是用户程序与内核之间长期稳定的二进制契约，包括调用号、参数布局、返回值和错误语义。
#. 系统调用表是内核实现 ABI 的分发结构，它把当前架构和当前 ABI 的调用号映射到入口函数。
#. 系统调用名称相同，不代表不同架构或不同 ABI 使用相同调用号。
#. 阅读某个 syscall number 前，必须先确认目标架构和用户程序 ABI，例如 x86-64、i386、x32、arm64 或 RISC-V。
#. x86 源码通常分别维护 64 位和 32 位系统调用表；其它架构的表文件与生成规则可能不同。
#. 系统调用表的文件位置、生成脚本和 wrapper 名称可以随内核版本重构，用户态编号和语义仍必须保持兼容。
#. 表项通常表达调用号、ABI 类别、系统调用名称和入口符号；具体列格式应以当前源码树为准。
#. 调用号经过表项后，可能先进入自动生成 wrapper，再进入 ``sys_*``、``compat_sys_*`` 或共同内部实现。
#. ``SYSCALL_DEFINE*`` 描述系统调用实现入口；宏展开后的实际符号不能只靠表面函数名猜测。
#. 已发布系统调用的编号、参数含义、结构体布局和返回语义不能随意改变，否则会破坏已有二进制。
#. 内核内部可以移动文件、重命名辅助函数、替换锁和重写子系统路径，只要用户态 ABI 仍保持原有行为。
#. 新增接口需要为未来扩展预留空间，常见方式是 ``flags`` 参数、带 ``size`` 字段的用户结构体或新增系统调用。
#. 对未知 flag 返回 ``-EINVAL`` 可以防止旧内核静默接受自己不理解的新语义。
#. 带 ``size`` 字段的 UAPI 结构体可以支持新旧用户程序和新旧内核之间的长度协商。
#. 系统调用未实现、未接线或当前配置不支持时，通常通过标准路径返回 ``-ENOSYS``。
#. ``-ENOSYS`` 表示当前 syscall 接口不可用，不等于对应业务能力在系统中完全不存在；用户态可能还有其它接口或 fallback。
#. 64 位内核运行 32 位用户程序时，compat 层负责解释 32 位 ABI 的指针宽度、整数宽度、对齐和结构体布局。
#. 简单标量参数可能直接转换后复用共同实现；包含指针、``long``、时间类型或显式 64 位字段的结构体通常需要专门 compat 转换。
#. ``include/linux/compat.h`` 中的 compat 类型和入口用于表达 32 位用户数据布局，不能把 64 位内核结构体直接当成 32 位 UAPI。
#. compat wrapper 的任务是把旧 ABI 数据转换成内核内部表示；转换完成后，native 与 compat 路径可以汇合到共同实现。
#. vDSO 是内核映射到用户地址空间的一小段辅助代码和数据，用于在用户态完成部分受支持操作。
#. 支持 vDSO 的调用可以不执行普通 syscall 指令，因此 ``strace`` 不一定能看到每次用户态时间查询。
#. vDSO 仍属于内核提供的 ABI，用户程序通常通过 libc 或动态链接机制查找，而不是硬编码地址。
#. vDSO 无法完成或当前场景不支持时，用户态实现可以退回真实系统调用。
#. seccomp 规则、审计工具和追踪程序也依赖 syscall number，因此 ABI 编号稳定性影响整个用户态生态。
#. 判断 syscall 是否可用必须综合架构表项、配置、运行内核版本和用户程序 ABI，不能只看源码中存在实现函数。

必背路径
--------

从系统调用名称定位实现：

::

   确认用户程序架构与 ABI
   → 查该 ABI 的系统调用号
   → 查当前内核版本的 syscall table
   → 确认表项映射的入口符号
   → 展开 wrapper 或 SYSCALL_DEFINE 宏
   → 找到通用实现函数
   → 再进入具体内核子系统

compat 系统调用：

::

   32 位用户程序提交 32 位 ABI 参数
   → 64 位内核进入 compat syscall table
   → compat wrapper 读取 32 位寄存器和用户结构体
   → 转换指针宽度、整数宽度和字段布局
   → 形成内核内部参数
   → 调用共同实现
   → 按 32 位 ABI 返回结果

vDSO 快速路径：

::

   用户程序调用 libc 接口
   → libc 查找 vDSO 符号
   → 在用户态读取内核提供的共享数据
   → 完成受支持操作
   → 无法完成时退回真实系统调用

检查 ABI 变化：

::

   先判断调用号是否变化
   → 判断参数顺序和宽度是否变化
   → 判断 UAPI 结构体布局是否变化
   → 判断返回值和 errno 是否变化
   → 判断 flags 的未知位处理是否变化
   → 最后再检查内核内部函数和文件重构

必须区分
--------

* 系统调用 ABI 与内核内部实现：ABI 面向用户二进制长期稳定；内部 wrapper、函数名和源码位置可以演进。
* 系统调用名称与调用号：名称可以相同；编号属于具体架构和 ABI 的编号空间。
* native 与 compat：native 按内核主要字长解释参数；compat 按较旧或较窄用户 ABI 转换数据布局。
* 实现函数存在与接口可用：源码中有函数不代表当前架构表项、配置和运行内核已经暴露该系统调用。
* vDSO 与普通 syscall：vDSO 在用户态执行受支持辅助操作；普通 syscall 通过 CPU 指令进入内核。
* ``-ENOSYS`` 与普通业务失败：``-ENOSYS`` 表示接口不可用；``-EINVAL``、``-EFAULT`` 等表示接口存在但请求失败。

一句话结论
----------

系统调用表把具体 ABI 的编号连接到内核入口；表和 wrapper 可以重构，已经发布的调用号、参数布局与返回语义必须长期稳定。

第037章：系统调用表、入口代码与 ABI 稳定性
==========================================

核心知识点
----------

系统调用 ABI 是长期二进制合同
   系统调用号、参数宽度、结构体布局、返回值和错误语义共同构成用户程序与内核之间的 ABI。已经发布的 ABI 不能随意改变，否则旧二进制会失效。

系统调用表负责编号分发
   系统调用表把某个架构、某种 ABI 下的调用号映射到入口符号。相同名称的系统调用在不同架构或 ABI 中可能使用不同编号。

查调用号必须先确认 ABI
   x86-64、i386、x32、arm64、RISC-V 等拥有各自的编号空间和入口规则。脱离目标 ABI 单独讨论 syscall number 没有意义。

表项之后通常还有 wrapper
   调用号命中表项后，代码可能先经过自动生成的 wrapper、compat wrapper 或参数整理层，再进入 ``SYSCALL_DEFINE*`` 生成的入口和共同内部实现。

内核内部实现可以重构
   文件位置、辅助函数、锁和子系统路径都可以改变，只要用户可见的调用号、参数、返回值和副作用保持兼容。ABI 稳定不等于源码结构稳定。

新接口必须为扩展预留边界
   常见做法包括 flags 参数、带 ``size`` 字段的 UAPI 结构体和保留字段。旧内核应拒绝未知 flag，避免静默接受自己无法理解的语义。

``-ENOSYS`` 表示接口不可用
   当调用号未接线、当前 ABI 没有该入口或运行内核不支持时，通常返回 ``-ENOSYS``。它说明这个系统调用入口不可用，不代表整个业务能力完全不存在。

Compat 层翻译不同数据布局
   64 位内核运行 32 位程序时，compat 路径按 32 位 ABI 解释指针、``long``、时间类型、对齐和用户结构体，再转换成内核内部表示。

vDSO 提供不陷入内核的快速路径
   某些时间等辅助操作可以通过内核映射到用户空间的 vDSO 完成。vDSO 仍是内核提供的 ABI，无法完成时通常退回真实系统调用。

接口可用性需要多层确认
   源码中存在实现函数，只能证明代码存在。还要确认当前架构表项、Kconfig、运行内核版本、用户程序 ABI 和安全策略。

关键路径
--------

从系统调用名称定位实现：

::

   确认目标架构和用户 ABI
   → 查该 ABI 的系统调用号
   → 查当前源码的 syscall table
   → 确认表项入口符号
   → 展开 wrapper 或 compat 层
   → 找到 SYSCALL_DEFINE 入口
   → 进入共同内部实现
   → 进入具体子系统

Compat 调用路径：

::

   32 位程序提交参数
   → 64 位内核进入 compat table
   → compat wrapper 按 32 位布局取数
   → 转换指针、整数和结构体字段
   → 形成内核内部参数
   → 调用共同实现
   → 按 32 位 ABI 返回结果

vDSO 路径：

::

   用户程序调用 libc
   → libc 查找 vDSO 符号
   → 在用户态读取内核共享数据
   → 能完成则直接返回
   → 不能完成则退回系统调用

检查一次 ABI 修改：

::

   检查调用号
   → 检查参数顺序与宽度
   → 检查 UAPI 结构体布局
   → 检查 flags 和保留字段
   → 检查返回值与 errno
   → 再审查内部实现变化

概念辨析
--------

系统调用 ABI 与内部实现
   ABI 面向用户二进制并要求稳定；wrapper、函数名和源码位置属于内核内部，可以演进。

系统调用名称与调用号
   名称表达接口语义；调用号属于具体架构和 ABI 的编号空间。

Native 与 compat
   Native 按主要用户 ABI 解释参数；compat 把较窄或旧 ABI 的数据布局转换成内核表示。

实现存在与接口可用
   实现函数存在不保证表项已接线、配置已启用或运行内核允许调用。

vDSO 与系统调用
   vDSO 在用户态执行内核提供的辅助逻辑；系统调用通过 CPU 入口切换到内核态。

``-ENOSYS`` 与请求参数错误
   ``-ENOSYS`` 表示入口不可用；``-EINVAL`` 等表示入口存在，但本次请求不符合接口合同。

本章结论
--------

系统调用表把特定 ABI 的编号连接到内核入口；内核内部可以持续重构，已经发布的编号、数据布局和返回语义必须长期兼容。

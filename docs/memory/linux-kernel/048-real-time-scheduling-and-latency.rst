第048章：实时调度类与延迟保证
=============================

核心知识点
----------

实时调度追求可预测响应
   实时并不表示任务永远最快或延迟为零，而是让任务在已知约束下更可预测地获得 CPU，并控制最坏响应时间。

SCHED_FIFO 与 SCHED_RR 属于固定优先级实时类
   二者都按实时优先级竞争，数值越大优先级越高。可运行的高优先级实时任务通常会压过低优先级实时任务和公平类任务。

FIFO 与 RR 的同优先级规则不同
   ``SCHED_FIFO`` 会持续运行到阻塞、让出、退出、被更高优先级抢占或被带宽机制节流；``SCHED_RR`` 在同优先级任务之间增加时间片轮转。

实时任务可能造成饥饿
   高优先级实时线程若持续计算且不阻塞，会长期压制普通任务。实时任务必须有明确执行时间、阻塞点、周期和故障恢复边界。

实时带宽限制失控占用
   period 定义统计窗口，runtime 定义窗口内实时类可使用的 CPU 预算。预算耗尽后实时队列会被暂时节流，为普通任务和系统恢复路径保留运行机会。

SCHED_DEADLINE 使用三参数约束
   ``runtime`` 表示每周期 CPU 预算，``deadline`` 表示相对截止时间，``period`` 表示激活周期，通常满足 ``runtime <= deadline <= period``，并受准入控制约束。

调度保证只是端到端延迟的一部分
   任务及时获得 CPU 后，仍可能受到锁等待、IRQ、softirq、不可抢占区、缺页、内存回收和设备响应影响。调度延迟小不等于任务一定按时完成。

优先级反转来自资源依赖
   高优先级任务等待低优先级持有的锁时，会被间接阻塞。优先级继承可以临时提升持锁者，但不能消除错误的锁依赖和死锁。

关键路径
--------

固定优先级实时选择：

::

   task 变为 runnable
   → 根据 policy 进入 RT sched_class
   → 放入对应实时优先级队列
   → 选择当前 CPU 上最高可运行优先级
   → 高优先级任务抢占低优先级或 fair task
   → FIFO 运行到阻塞、让出或被抢占
   或 RR 在同优先级内按时间片轮转

实时带宽控制：

::

   period 窗口开始
   → RT task 消耗 runtime 预算
   → 更新实时带宽统计
   → 预算未耗尽时继续按优先级调度
   → 预算耗尽后 throttle 实时队列
   → 低调度类获得运行机会
   → 下个 period 补充预算并解除节流

Deadline 调度：

::

   用户提交 runtime、deadline、period
   → 内核验证参数和权限
   → 执行带宽准入控制
   → task 进入 deadline class
   → 每次激活获得 runtime 预算
   → 按有效 deadline 参与选择
   → 预算耗尽后等待补充
   → 进入下一周期

排查实时延迟：

::

   确认 policy、priority 或 deadline 参数
   → 确认 task 何时变为 runnable
   → 测量 wakeup 到 sched-in 延迟
   → 检查更高优先级任务与带宽节流
   → 检查 IRQ、softirq 和不可抢占区
   → 检查锁等待与优先级反转
   → 检查缺页、内存分配和 I/O
   → 用最坏情况样本验证截止时间

概念辨析
--------

SCHED_FIFO 与 SCHED_RR
   FIFO 没有同优先级时间片轮转；RR 在同一实时优先级内按时间片轮换。

实时优先级与 nice
   实时优先级决定 RT 类内顺序；nice 只调整公平类份额。

固定优先级与 deadline
   FIFO/RR 使用静态优先级；deadline 使用预算、截止时间和周期约束。

调度延迟与执行时间
   调度延迟是 runnable 后等待 CPU 的时间；执行时间是获得 CPU 后完成工作的时间。

实时与高吞吐
   实时关注延迟上界和可预测性；高吞吐关注单位时间完成的总工作量。

普通抢占与优先级反转
   普通抢占是高优先级任务直接取得 CPU；优先级反转是高优先级任务被低优先级持有的资源阻塞。

本章结论
--------

实时调度通过固定优先级或 runtime、deadline、period 预算缩短可运行任务的等待时间；真正的端到端保证还必须控制执行时间、锁、中断、内存和设备路径。

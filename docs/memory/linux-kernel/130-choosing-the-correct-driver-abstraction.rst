第130章：选择正确的驱动抽象
============================

本章必须记住
------------

#. 驱动抽象的第一项设计不是寄存器如何访问，而是内核和用户态将以什么业务对象看见设备。
#. 先写出设备的数据模型，再选择字符、块、网络、专业子系统、控制接口或共享内存路径。
#. 同一硬件可以被包装成多种接口，但只有与真实数据模型一致的抽象才能获得正确调度、工具、权限和 ABI。
#. 字节流/消息/私有命令适合字符设备或 misc；固定随机访问地址空间适合块设备；packet 适合 netdev。
#. Sample、event、frame、audio stream、terminal、sensor channel 等已有标准对象时，应优先接入对应专业子系统。
#. “底层能按字节读写”不能推出应做字符设备；几乎所有硬件最终都能被序列化成字节。
#. “硬件有一块内存”不能推出应做块设备；块设备必须提供稳定 sector 地址、随机访问、容量和存储完成语义。
#. “底层通过 USB bulk 传输”不能推出应做网络设备；只有对外对象真正是网络 packet 并进入协议栈时 netdev 才成立。
#. “只需要一个 `/dev` 节点”也不能推出 misc 最优；应先检查现有子系统是否已定义同类设备的数据模型。
#. 独立字符节点给驱动最大自由度，也让驱动独自承担 UAPI、工具、权限、并发、版本兼容和测试责任。
#. 专业子系统限制接口形状，但提供标准对象、用户工具、事件模型、统计、命名、命名空间和维护审查。
#. 传感器采样通常应评估 IIO；硬件健康温度/电压/风扇通常应评估 hwmon。
#. 按键、触摸和输入事件应评估 input；串口、终端与 line discipline 应评估 tty。
#. 摄像头、视频采集和编码应评估 media/V4L2；显示、GPU 和 modeset 应评估 DRM。
#. 声音流应评估 ALSA；网络 packet 应评估 netdev；固定存储地址空间应评估 block。
#. GPIO、clock、regulator、reset、PWM、watchdog 等也有专用框架，不应先发明私有 ioctl。
#. 一个设备可以同时接入多个子系统，但每个接口必须拥有清晰且不重叠的数据/控制责任。
#. 例如硬件采样数据可进入 IIO，少量固件管理命令可由受控 misc 节点提供。
#. 多接口驱动必须有单一硬件状态机，防止字符节点、sysfs 和专业子系统并发修改同一资源。
#. 控制面和数据面必须分开判断：数据面强调吞吐、队列和所有权；控制面强调配置、状态和权限。
#. Sysfs 适合单值、可发现、对象相关的文本属性，不适合大块数据、复杂事务或高频命令。
#. Ioctl 适合文件对象上的私有控制命令，但会形成长期二进制 ABI，应保持命令族、结构体和错误语义稳定。
#. Netlink 适合可扩展结构化消息、事件通知、多对象管理和异步控制，代价是协议与策略设计更复杂。
#. Configfs 适合用户态创建、配置和销毁内核对象，语义是配置对象生命周期，不是普通设备寄存器入口。
#. Debugfs 只适合调试，不提供稳定 ABI；生产工具不应把 debugfs 文件当正式控制协议。
#. Procfs 主要表达进程和系统运行状态，不应作为新设备私有控制接口的默认位置。
#. Mmap 是数据传输优化方式，不是独立设备分类；字符、媒体、DRM、VFIO 等多种抽象都可以提供映射。
#. 设计 mmap 前必须先有明确对象、buffer ownership、producer/consumer、通知、权限和 teardown 协议。
#. Read/write 是可靠基线时，应先实现清晰语义，再用 mmap、DMA-BUF、io_uring 等优化特定瓶颈。
#. DMA-BUF 适合跨设备/子系统共享 buffer ownership，不等于任意驱动都应自行导出物理内存。
#. UIO/VFIO 把更多设备控制交给用户态，适用边界、IOMMU 隔离、中断和安全模型必须单独证明。
#. VFIO 面向受控设备直通和用户态驱动，需要 IOMMU group 等隔离；不能用普通 mmap/ioctl 仿造同等安全性。
#. 用户态 ABI 一旦发布，节点名、读写单位、阻塞语义、poll 事件、ioctl、结构体、mmap offset 都会形成兼容负担。
#. 内核内部结构体不是 UAPI；不能把 ``struct device``、链表指针、内核地址或驱动私有对象布局直接复制给用户态。
#. UAPI 结构应使用固定宽度类型、显式大小/版本、保留字段和清晰字节序。
#. 新字段应保持旧调用者可用，未知 flag 应按约定拒绝或忽略，不能默默改变原字段含义。
#. ABI 版本字段不是万能补丁；优先设计可扩展结构和 feature query，避免并行维护大量互不兼容版本。
#. 错误码也是 ABI，``-EAGAIN``、``-ENODEV``、``-EINVAL``、``-EOPNOTSUPP`` 应各自表达稳定情况。
#. 阻塞、非阻塞、超时、取消和设备移除时的结果必须在接口定义阶段确定。
#. 权限模型必须与操作风险匹配，不能只依赖节点 mode；敏感命令还需 capability、LSM 和对象所有权检查。
#. 把寄存器、DMA 地址或固件接口直接暴露给用户态，会扩大攻击面并把硬件细节固化成 ABI。
#. 专业子系统通常已有权限与策略入口，绕过它们的私有 ioctl 可能破坏资源仲裁和隔离。
#. 容器与 namespace 支持取决于子系统：netdev 有网络 namespace，字符设备通常依赖 device cgroup 和挂载视图。
#. 一个全局 misc 节点可能绕过 per-device/per-namespace 隔离，设计前必须确认作用域。
#. 性能选择必须基于真实瓶颈，不应因为“ioctl 慢”“read 有复制”就跳过标准子系统。
#. 系统调用、copy、锁、DMA、IRQ、queue、cacheline 和设备服务时间应分层测量。
#. 小控制命令的 syscall 开销通常不值得引入共享内存协议和长期 pinning 复杂度。
#. 高频大数据流可能需要 buffer queue、batch、mmap 或 DMA-BUF，但仍应优先采用专业子系统已有机制。
#. 标准子系统常提供批处理、队列、poll、streaming、buffer negotiation 和 zero-copy 边界，复用它们比私有协议更可维护。
#. 块层提供合并、拆分、I/O scheduler、flush 和统计；字符驱动自行模拟这些功能通常意味着抽象选错。
#. 网络栈提供 routing、qdisc、GRO/GSO、NAPI、ethtool 和 namespace；私有 packet 字符节点会失去这些能力。
#. 可观测性也是抽象选择的一部分：标准子系统已有 tracepoint、sysfs、ethtool、media-ctl、iio tools 等证据面。
#. 私有接口必须自己提供统计、trace、状态转储和错误关联，否则生产故障难以定位。
#. 可测试性应在设计阶段考虑，包括模拟设备、故障注入、ABI 自测、并发 teardown 和兼容测试。
#. 标准子系统通常已有 kselftest、工具和维护者审查；私有接口需要自行建立长期测试矩阵。
#. 设备的总线模型与用户接口抽象是两个维度：PCI 设备可以注册 netdev、block、DRM 或字符接口。
#. Bus 解决发现、资源、probe/remove；功能子系统解决用户态和内核其它模块如何使用设备。
#. 不应因为驱动位于 ``drivers/misc`` 就忽略真实总线 parent、DMA、PM 和 hotplug 生命周期。
#. 不应因为设备注册为字符节点就绕过 driver core；总线设备与用户接口对象需要明确父子/引用关系。
#. 抽象选择还会决定 teardown：字符设备要收束 fd/VMA，块设备要收束 request/open，netdev 要收束 skb/NAPI。
#. 专业子系统可能有额外对象，例如 V4L2 queue、DRM GEM、ALSA PCM、IIO buffer，remove 必须遵守其注销顺序。
#. 在选择抽象前，应列出所有长期所有者：用户 fd、mmap、socket、文件系统、buffer queue、DMA、IRQ 和子设备。
#. 若接口需要多个用户共享硬件，必须定义仲裁、优先级、配额和故障隔离，而不是让最后写 ioctl 的进程获胜。
#. 若接口只服务一个受控 daemon，也仍是 UAPI；daemon 升级、内核升级和崩溃恢复都要求稳定协议。
#. Firmware 管理、诊断和恢复接口应与正常数据面隔离，并限制在安全状态下执行。
#. 重置命令必须定义在途请求、映射、队列和其它 fd 的行为，不能只写寄存器 reset 位。
#. 新接口应先搜索内核现有子系统和 UAPI，避免为同类设备创造第二套不兼容模型。
#. 评审抽象时应准备“为什么现有子系统不适合”的技术证据，而不是以实现方便作为理由。
#. 临时 bring-up 接口不应未经文档和审查直接变成生产 ABI；debugfs 或内部测试路径应明确非稳定性质。
#. 若确实需要私有 ABI，应在 ``Documentation/ABI`` 或对应 UAPI 文档中说明对象、操作、权限和版本策略。
#. 驱动内部 API 可以随内核版本重构，用户态 ABI 则需要长期兼容；不要把内部实现偶然细节泄漏出去。
#. 选择抽象的正确标准是：它是否准确表达数据对象、复用已有内核能力、限制安全边界，并能在十年后继续维护。
#. 稳定设计顺序是：业务对象 → 已有子系统 → 用户接口 → 并发/生命周期 → ABI → 性能 → 安全 → 可观测性。
#. 精确注册 helper、子系统对象和内部回调具有版本差异；稳定原则是用户数据模型决定功能抽象，总线模型决定设备怎样出现。

必背路径
--------

选择数据抽象：

::

   写出用户态每次处理的最小业务对象
   → 字节/消息/私有命令
   → 字符设备或 misc
   → 稳定 sector 地址空间
   → block
   → network packet
   → net_device
   → sample/event/frame/audio/terminal
   → 查找对应专业子系统

选择控制接口：

::

   单值对象属性
   → sysfs
   → 文件对象私有控制
   → ioctl
   → 可扩展多对象消息与事件
   → netlink
   → 用户态创建/配置内核对象
   → configfs
   → 仅开发调试
   → debugfs

评估专业子系统：

::

   搜索同类设备已有内核对象和用户工具
   → 比较数据模型是否一致
   → 检查 buffer、event、PM、namespace 和 hotplug 支持
   → 评估驱动需要实现的映射层
   → 评估私有 ABI 将重复的能力
   → 优先注册到专业子系统
   → 仅保留必要且受控的私有控制面

设计私有 UAPI：

::

   定义对象和操作的稳定语义
   → 使用固定宽度结构与保留字段
   → 定义阻塞、poll、取消和错误码
   → 定义权限、namespace 和并发
   → 定义设备 reset/remove 时的行为
   → 编写 ABI 文档与兼容策略
   → 建立自测、模糊测试和跨版本测试

性能优化：

::

   先建立标准接口的正确基线
   → 测量 syscall、copy、锁、queue、DMA 和设备延迟
   → 找到主要瓶颈
   → 调整 batch、queue 和 buffer
   → 必要时增加 mmap/DMA-BUF/异步路径
   → 保留原 ABI 或 feature negotiation
   → 对比吞吐、尾延迟、内存和复杂度

必须区分
--------

* Bus 抽象与功能抽象：Bus 决定发现、资源和绑定；字符、块、网络或专业子系统决定设备如何被使用。
* 可实现与适合：一个设备可以被包装成字符节点，不表示字符 ABI 能正确表达其业务模型。
* 数据面与控制面：数据面搬运 stream/block/packet/frame；控制面配置状态、策略和生命周期。
* Mmap 与设备类型：Mmap 是 buffer 访问机制，不是字符、块、网络或媒体之外的新设备分类。
* 私有节点与低维护成本：注册代码可以很少；长期 ABI、安全、工具和 teardown 成本可能很高。
* 内部接口与用户 ABI：内核内部 API 可演进；已发布的用户态结构、命令和行为必须兼容。

一句话结论
----------

正确驱动抽象由用户态业务对象决定：优先复用能准确表达该对象的内核子系统，再以最小私有控制面补充，并把 ABI、安全、性能和 teardown 作为同一项长期设计。

第002章：为什么 Linux 内核源码难读
=================================

本章必须记住
------------

#. Linux 内核没有唯一的程序入口；系统调用、中断、异常、定时器、工作队列、设备事件和模块初始化都可以启动执行路径。
#. 用户看到的接口、内核通用处理层和最终具体实现通常位于不同文件与不同子系统中。
#. 找到系统调用入口只能说明请求从哪里进入，不能说明最终由哪个文件系统、协议或驱动完成操作。
#. ``SYSCALL_DEFINE`` 等宏是系统调用入口的声明与包装机制；阅读时应先找到它把参数交给哪个普通 C 函数。
#. 内核大量使用函数指针和操作表，调用链的下一步经常由运行时对象决定，而不是直接写在调用位置。
#. 看到 ``object->ops->callback`` 时，必须先确定对象类型、操作表从哪里赋值以及回调实际指向哪个函数。
#. 一次用户操作通常跨越多个子系统；系统调用名称只表示统一入口，不表示全部实现都在同一个源码文件中。
#. 阅读内核源码应先追踪对象怎样被查找、转换和交接，再根据对象进入对应子系统。
#. 同一段代码能否睡眠、能否访问用户内存以及可以使用哪种锁，取决于当前运行上下文。
#. 进程上下文通常允许阻塞，但持有自旋锁、关闭中断或处于原子区时仍不能睡眠。
#. 硬中断和软中断上下文不能执行可能睡眠的操作；工作队列通常运行在进程上下文，可以执行允许阻塞的工作。
#. 内核配置、硬件能力、对象状态、锁状态和并发时序都可能改变实际执行分支。
#. 内核故障的定位需要结合源码、日志、调用栈和运行时跟踪，不能只凭一个函数名或一个源码文件下结论。

必背路径
--------

阅读任意内核操作时采用以下顺序：

::

   判断入口类型
   → 确定当前运行上下文
   → 找到核心内核对象
   → 追踪对象状态与所有权
   → 找到操作表或回调
   → 进入具体子系统实现
   → 用日志或跟踪证据验证实际路径

三个典型对象交接：

::

   read
   → fd
   → struct file
   → VFS
   → 文件系统、管道或设备实现

   send
   → fd
   → struct socket / struct sock
   → socket 层
   → 具体协议与网络设备路径

   fork
   → 当前 task_struct
   → 进程创建层
   → 内存、文件表、信号与命名空间
   → 新任务进入调度系统

必须区分
--------

* 入口函数与最终实现：入口负责接收请求；最终实现由对象类型、操作表和运行状态决定。
* 直接调用与回调分派：直接调用的目标写在源码中；回调目标保存在运行时对象的函数指针中。
* 进程上下文与中断上下文：进程上下文可能允许阻塞；中断上下文不能睡眠，也没有普通系统调用的用户执行语义。
* 源码目录与运行路径：目录表示代码组织边界；运行路径由对象交接、回调和状态变化连接起来。

一句话结论
----------

阅读 Linux 内核时，先问“当前是哪条路径、什么对象、什么上下文”，再问“代码在哪个文件”。

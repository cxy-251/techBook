第011章：Linux 内核 C 的运行时约束
==================================

本章必须记住
------------

#. Linux 内核使用 C 语言，但内核 C 运行在特权级、共享地址空间、强并发和硬件中断环境中，不能按普通用户态 C 理解。
#. 内核代码不依赖用户态 ``libc``；内存分配、日志、用户访问和错误传播都使用内核自己的接口。
#. 用户态的 ``malloc()``、``free()`` 和 ``printf()`` 在内核中分别对应不同类别的分配器、释放接口和日志接口，不能机械替换。
#. ``kmalloc(size, GFP_KERNEL)`` 中的分配标志属于接口语义；``GFP_KERNEL`` 表示分配路径允许睡眠、回收或等待。
#. 可能睡眠的接口只能用于允许睡眠的上下文；硬中断、软中断、持有自旋锁或其它原子上下文不能随意调用它们。
#. ``__user`` 表示指针属于用户地址空间，内核不能把它当成普通内核指针直接解引用。
#. 用户空间数据应通过 ``copy_from_user()``、``copy_to_user()``、``get_user()`` 和 ``put_user()`` 等接口访问。
#. 用户访问接口可能触发缺页和睡眠，因此调用点必须满足相应上下文条件。
#. ``__iomem`` 表示 I/O 内存地址，通常应通过 ``readl()``、``writel()`` 等设备访问器读写。
#. ``__percpu``、``__rcu`` 等标记把地址空间、并发或访问约束写入类型附近，供维护者和静态分析工具检查。
#. Linux 内核通常使用 GNU C 方言，并大量使用 ``typeof``、statement expression、属性和复杂宏。
#. ``__init``、``__exit``、``__always_inline``、``__cold``、``__noreturn``、``__must_check`` 等标记表达额外的编译期和生命周期语义。
#. ``container_of()`` 依靠成员偏移和类型信息，从结构体成员地址反推出宿主对象地址。
#. 内核指针可能表示普通内核地址、用户地址、I/O 地址、错误编码或物理地址；不同类型必须使用不同访问规则。
#. 物理地址不是可以直接解引用的 C 指针；需要经过映射或架构规定的转换后才能访问。
#. 一个内核接口能否调用，首先取决于当前执行上下文、锁状态、中断状态和地址空间，而不是函数本身能否编译。

必背路径
--------

阅读一段内核 C 时采用以下顺序：

::

   确定入口属于系统调用、工作队列、软中断还是硬中断
   → 判断当前是否允许睡眠
   → 检查是否持有自旋锁、关闭中断或处于原子区
   → 识别每个指针所属的地址空间
   → 检查分配标志和用户访问接口
   → 识别编译器属性、宏和静态分析标记
   → 追踪失败后的资源释放与负错误码返回

用户数据复制的基本路径：

::

   用户指针 char __user *ubuf
   → 在允许睡眠的进程上下文中执行
   → 分配内核缓冲区
   → copy_from_user() 完成受控复制
   → 复制失败时释放已申请资源
   → 返回 -EFAULT 或其它负错误码

必须区分
--------

用户态运行时与内核运行时
   用户态依赖 libc 和进程运行时；内核本身提供底层运行环境，并使用带上下文约束的内核 API。

普通内核指针与 ``__user`` 指针
   普通内核指针指向内核可访问对象；``__user`` 指针属于用户地址空间，必须通过用户访问接口处理。

``__iomem`` 地址与普通内存
   ``__iomem`` 表示设备 I/O 映射，访问顺序和宽度可能具有硬件语义，不能当普通 RAM 直接读写。

进程上下文与原子上下文
   进程上下文在条件允许时可以睡眠；中断、持有自旋锁和其它原子路径不能执行可能睡眠的操作。

类型标记与实际访问
   ``__user``、``__iomem`` 等标记提供类型和检查语义；真正访问仍必须调用对应 helper。

一句话结论
----------

内核 C 不是另一种语法，而是运行在上下文、地址空间、并发和硬件约束下的 C；先判断环境，才能判断代码是否合法。

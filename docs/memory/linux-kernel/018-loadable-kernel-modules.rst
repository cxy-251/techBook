第018章：Linux 可加载内核模块
=============================

本章必须记住
------------

#. 可加载内核模块是运行中的内核按需接纳的内核代码，构建产物通常是 ``.ko`` 文件。
#. 模块运行在内核态，具有与内建代码相同的高权限；模块不是进程、容器或安全隔离边界。
#. 用户态通常通过 ``finit_module()`` 或 ``init_module()`` 系统调用把模块内容交给内核。
#. 内核加载模块时需要完成格式检查、内存分配、符号解析、重定位、参数解析、签名或策略检查、初始化入口调用和状态登记。
#. ``module_init(fn)`` 指定模块加载阶段的初始化入口；初始化函数返回 ``0`` 后，模块才进入可用状态。
#. 初始化函数返回负错误码时，模块不能进入正常运行状态，加载路径必须撤销已经完成的部分工作。
#. ``module_exit(fn)`` 指定可卸载模块的清理入口；它必须撤销模块向其它子系统公开的所有入口和资源。
#. 相同源码构建为内建代码时，``module_init`` 通常进入 initcall 体系；``module_exit`` 不具有普通运行期卸载意义。
#. ``__init`` 标记初始化阶段代码，初始化完成后相关内存可以被释放；长期回调不能继续指向已经释放的初始化代码。
#. 模块卸载前必须阻止新的调用进入，并处理现有引用、打开文件、回调、定时器、工作队列、IRQ 和异步任务。
#. 模块仍被引用或正在使用时，正常卸载应被拒绝；强制卸载会破坏生命周期保证，并可能造成悬空函数指针和 use-after-free。
#. 初始化成功只证明模块进入运行状态，不证明其并发、错误路径、硬件操作和卸载路径一定安全。
#. ``insmod`` 按给定文件路径把一个具体 ``.ko`` 交给内核，通常不主动解析完整依赖关系。
#. ``modprobe`` 按模块名、别名、配置和依赖数据库查找模块，并安排依赖模块的加载或卸载。
#. ``depmod`` 根据已安装模块生成 ``modules.dep``、``modules.dep.bin`` 和别名等索引，供 ``modprobe`` 使用。
#. ``lsmod`` 主要展示 ``/proc/modules`` 中当前已加载模块的状态；它不证明模块内部功能已经正确工作。
#. ``modinfo`` 读取模块文件中的许可、别名、依赖、参数、版本标识和签名等元数据。
#. ``module_param()`` 把变量暴露为有类型的模块参数；参数通常在模块初始化函数执行前完成解析。
#. 模块参数的权限决定它是否在 ``/sys/module/<name>/parameters/`` 中可读或可写。
#. 可写模块参数属于运行时控制面，修改时必须考虑并发、锁、硬件状态、非法值验证和失败回滚。
#. Kconfig 决定代码是否内建、模块化或关闭；模块参数只改变已经构建并被加载的代码行为。
#. ``EXPORT_SYMBOL()`` 和 ``EXPORT_SYMBOL_GPL()`` 决定模块可引用哪些内核符号；未导出符号不能作为稳定模块接口使用。
#. Linux 不承诺稳定的内核内部模块 ABI；模块必须针对目标内核版本、配置和构建接口重新构建。
#. ``vermagic``、符号版本 CRC、目标架构和配置不匹配都可能导致模块加载失败。
#. 模块签名可以证明模块由某个密钥签发；是否强制拒绝未签名模块取决于内核配置和安全策略。
#. ``MODULE_LICENSE()`` 是许可元数据，会影响 GPL-only 符号使用和内核 taint 判断，但它不会自动证明模块代码质量或安全性。
#. 内建代码适合启动早期和根文件系统依赖的功能；模块适合按需加载和独立交付，但增加了文件、依赖、签名和生命周期管理要求。

必背路径
--------

模块加载主路径：

::

   用户态找到 .ko 文件
   → insmod 或 modprobe 发起加载
   → 内核检查格式、架构、版本和策略
   → 分配模块内存并解析导出符号
   → 完成架构重定位和参数解析
   → 调用 module_init 指定的初始化函数
   → 返回 0 后模块进入 LIVE 状态
   → 注册的设备、文件、协议或回调开始可用

模块加载失败路径：

::

   初始化过程中申请资源
   → 某一步失败并返回负错误码
   → 撤销已经注册的接口
   → 停止已经启动的异步工作
   → 按反向顺序释放资源
   → 模块不进入正常运行状态

模块卸载主路径：

::

   用户请求 rmmod 或 modprobe -r
   → 检查模块是否允许卸载以及是否仍被引用
   → 阻止新的外部入口
   → 调用 module_exit 指定的清理函数
   → 注销设备、文件、回调和参数接口
   → 取消并同步定时器、工作和 IRQ
   → 释放资源和模块内存

``modprobe`` 依赖解析：

::

   模块名或设备别名
   → 查询 modprobe 配置和 modules.alias
   → 查询 modules.dep.bin
   → 按依赖顺序加载前置模块
   → 加载目标模块并传递参数

必须区分
--------

内建代码与可加载模块
   内建代码随镜像存在并参与启动；模块以独立文件交付，在运行时经过加载和卸载生命周期。

``insmod`` 与 ``modprobe``
   ``insmod`` 面向具体文件；``modprobe`` 面向模块名、别名、配置和依赖关系。

模块文件存在与模块已加载
   ``.ko`` 存在只说明文件可供尝试加载；``lsmod`` 或 ``/proc/modules`` 才说明模块已进入运行内核。

模块加载成功与功能正确
   加载成功只说明初始化入口返回成功；设备绑定、I/O、并发和错误恢复仍需单独验证。

参数可写与参数安全
   sysfs 权限允许写入不代表任意时刻修改都安全；参数 setter 必须维护运行对象一致性。

一句话结论
----------

可加载模块是具有完整内核权限和严格生命周期的运行时代码：加载前要匹配内核，初始化失败要回滚，卸载前要撤销全部入口并等待所有使用者离开。

第009章：怎样结合状态追踪内核调用链
===================================

核心知识点
----------

调用链不等于机制
   函数顺序只说明控制流经过哪里。完整机制还必须包含当前对象、对象状态、执行上下文、配置条件、返回值和错误处理。

直接调用与间接调用需要不同读法
   直接调用的目标写在源码中，可以继续查定义；间接调用通过操作表、函数指针或静态分支选择目标，必须先找对象和绑定位置。

适配层负责转换调用模型
   一个函数可以先被直接调用，再构造新的控制对象并进入回调。例如同步读取包装会构造 ``kiocb`` 和 ``iov_iter``，再调用 ``read_iter``。

路径由触发条件分类
   fast path 处理常见状态，slow path 处理缓存未命中、等待或复杂条件，fallback path 在首选实现未完整处理请求时转入另一种实现。分类依据是触发条件和成本，不是函数名。

运行对象携带分支状态
   ``struct file`` 的模式、位置和操作表，``kiocb`` 的 I/O 标志，页缓存状态和文件类型都会改变同一入口的后续路径。

执行上下文限制合法操作
   进程上下文、中断上下文、持有自旋锁或关闭中断等状态决定代码能否睡眠、等待资源或调用特定接口。

配置与硬件改变可执行路径
   ``CONFIG_*``、CPU 架构、文件系统特性和设备能力可以改变结构体、分支和具体实现。源码结论必须绑定目标版本和配置条件。

错误与部分完成属于正常语义
   提前退出、负错误码、部分字节完成和异步排队都属于调用链结果。资源申请失败时，应只释放已经取得的资源，并按相反顺序回滚。

关键路径
--------

追踪一条调用链：

::

   找到入口和核心对象
   → 标出直接调用与间接调用
   → 找到操作表或状态的绑定位置
   → 记录影响分支的字段、标志和配置
   → 判断当前上下文能否睡眠
   → 区分 fast、slow 与 fallback 路径
   → 追踪返回值、部分完成和错误回滚

读取路径的状态分叉：

::

   vfs_read 收到 struct file
   → 检查访问模式、用户地址和范围
   → 根据 f_op 选择 read 或 read_iter
   → 根据 kiocb 标志选择 I/O 策略
   → 页缓存命中时直接读取
   → 缓存未命中时预读、提交 I/O 或等待
   → 部分完成时合并已读字节数与后续结果

资源回滚：

::

   取得资源 A
   → 取得资源 B
   → 资源 C 失败
   → 释放 B
   → 释放 A
   → 返回原始错误

概念辨析
--------

直接调用与间接调用
   直接调用目标在编译时固定；间接调用目标由对象、操作表或运行状态绑定。

函数链与机制
   函数链描述调用关系；机制还要解释对象转换、状态条件、上下文和结果语义。

slow path 与错误路径
   slow path 可能以较高成本成功完成请求；错误路径以失败、回滚或部分完成结束。

阶段成功与用户目标完成
   当前函数成功可能只表示请求被接受、排队或完成一个阶段，不表示最终外部效果已经发生。

本章结论
--------

追踪内核调用链必须同时追踪对象和状态；只有明确间接目标、分支条件、上下文及错误语义，函数序列才构成可解释的机制。

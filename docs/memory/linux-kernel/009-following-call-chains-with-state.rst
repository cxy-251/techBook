第009章：怎样结合状态追踪内核调用链
===================================

本章必须记住
------------

#. 内核机制不是函数名的简单串联，而是调用关系、对象状态、执行上下文、配置条件和错误处理共同形成的路径。
#. 直接调用的目标写在源码中，可以继续搜索函数定义；间接调用的目标保存在对象字段、操作表或静态分支状态中。
#. 遇到 ``ops->fn()``、``file->f_op->read_iter()`` 或 ``mapping->a_ops->read_folio()`` 时，必须先找当前对象和回调赋值位置。
#. 一个适配函数可以先直接被调用，再构造新对象并执行间接分派；例如同步读取包装可以构造 ``kiocb`` 和 ``iov_iter`` 后调用 ``read_iter``。
#. fast path 是常见状态下的低开销路径，slow path 是缓存未命中、缺页、等待、异常输入或复杂处理触发的高成本路径。
#. fallback path 表示首选路径没有完整处理请求后，继续使用另一种实现完成剩余工作。
#. 判断 fast path、slow path 和 fallback path 时，应查看触发条件、对象状态、返回值和部分完成语义，不能只看函数名称。
#. 相同函数在不同 ``struct file``、``kiocb`` 标志、页缓存状态、锁状态和文件类型下可以走不同分支。
#. ``file->f_mode`` 决定打开文件允许的操作，``file->f_op`` 决定回调集合，``file->f_pos`` 表示当前文件位置。
#. ``IOCB_DIRECT``、``IOCB_NOWAIT`` 和 ``IOCB_NOIO`` 等 I/O 标志会改变直接 I/O、等待和是否允许发起新 I/O 的策略。
#. 进程上下文、中断上下文、持有自旋锁和关闭中断等状态决定当前路径能否睡眠和使用哪些接口。
#. ``CONFIG_*``、CPU 架构、文件系统能力和设备能力可以让源码分支存在、消失或选择不同实现。
#. 错误返回和提前退出属于机制的一部分，它们规定无权限、地址无效、资源不足和对象状态不匹配时怎样结束。
#. 资源申请到一半失败时，错误路径必须只释放已经取得的资源，并通常按照申请顺序的反方向回滚。
#. 内核常用 ``goto`` 把多个失败点汇入分阶段清理标签，以避免复制清理代码并保持释放顺序一致。
#. 一个函数返回成功不一定表示整个用户目标完成；返回字节数、部分完成、排队成功和异步提交具有不同语义。

必背路径
--------

追踪调用链时采用以下顺序：

::

   找到入口和当前核心对象
   → 标出直接调用
   → 标出操作表、函数指针和静态分支
   → 找到间接目标的赋值位置
   → 记录影响路径的对象字段和标志
   → 判断当前执行上下文能否睡眠
   → 区分 fast、slow 和 fallback 路径
   → 追踪错误码、部分完成和资源回滚
   → 写出每个分支成立所需的条件

读取路径的状态分叉：

::

   vfs_read 收到 struct file
   → 检查 f_mode、用户地址和读取范围
   → 根据 f_op 选择 read 或 read_iter
   → read_iter 检查 kiocb 标志
   → 页缓存命中时走较短路径
   → 缓存未命中时可能预读、提交 I/O 或等待
   → 直接 I/O 部分完成时可能转入缓冲读取
   → 合并已完成字节数与后续错误形成返回值

错误回滚的通用顺序：

::

   申请资源 A
   → 申请资源 B
   → 申请资源 C 失败
   → 释放 B
   → 释放 A
   → 返回原始错误码

必须区分
--------

* 直接调用与间接调用：直接调用目标在源码中固定；间接调用目标由对象、回调表或运行状态绑定。
* 函数链与机制：函数链只列出调用者和被调用者；机制还必须包含对象、状态、上下文、分支和错误语义。
* slow path 与错误路径：slow path 可能成功完成较昂贵的处理；错误路径以失败、回滚或部分完成结束。
* 函数成功与用户目标完成：函数成功可能只表示数据被接受、请求被排队或当前阶段完成，不一定表示最终外部结果已经发生。

一句话结论
----------

追踪内核调用链时必须同时追踪对象状态和上下文；只有写清每个间接目标、分支条件和错误回滚，函数列表才成为机制。

第003章：Linux 内核的核心设计取舍
=================================

本章必须记住
------------

#. Linux 内核设计通常不是追求单一指标，而是在性能、安全、通用性、硬件差异、延迟、吞吐、兼容性和维护成本之间作取舍。
#. 性能要求热路径减少不必要的分支、复制和共享锁竞争；安全要求内核仍然检查权限、用户指针、长度、对象状态和访问边界。
#. 安全检查通常集中在系统调用入口、对象查找边界和数据复制边界，检查完成后，内部路径继续使用受内核管理的对象。
#. ``__user``、``access_ok()``、``copy_to_user()`` 和 ``copy_from_user()`` 表示代码正在跨越用户态与内核态的内存访问边界。
#. 性能优化不能以直接信任用户指针、跳过权限检查或破坏对象生命周期为代价。
#. 通用性由统一接口和通用对象提供，具体差异由操作表、协议实现、文件系统或设备驱动承担。
#. VFS 使用 ``struct file`` 和 ``file_operations`` 统一文件操作，但普通文件、管道、套接字和设备仍然拥有不同实现。
#. 抽象层负责统一入口和公共规则，不负责消除所有底层差异。
#. 延迟表示单个请求从提交到完成所需的时间；吞吐表示单位时间内完成的工作总量。
#. 页缓存命中、及时唤醒和较短队列有利于降低单次请求延迟。
#. 预读、请求合并、批量处理和硬件队列并发通常有利于提高整体吞吐。
#. 提高吞吐的批量和排队策略可能增加部分请求的等待时间；降低延迟的立即处理也可能增加每个请求的固定开销。
#. Linux 对用户态公开的系统调用语义、返回值、错误码和用户态 ABI 需要长期兼容。
#. 内核内部的结构体、辅助函数、锁、回调形式和驱动接口可以随着重构、修复和硬件支持持续变化。
#. 阅读源码时应先识别当前代码承受的设计压力，再判断检查、抽象、队列、缓存和错误路径为什么存在。

必背路径
--------

分析一段内核代码时采用以下顺序：

::

   确定输入来自哪里
   → 找到权限、长度、地址和对象状态检查
   → 确定通用内核对象
   → 找到操作表或回调分派
   → 找到等待、唤醒、缓存、批量或队列位置
   → 进入具体文件系统、协议或驱动实现
   → 区分稳定用户接口与可演进内部实现

以 ``read(fd, buf, count)`` 为例：

::

   用户输入 fd、buf、count
   → 系统调用边界完成检查
   → fd 转换成 struct file
   → VFS 执行通用读取规则
   → file_operations 选择具体实现
   → 普通文件进入页缓存和文件系统
   → 特殊文件进入管道、套接字或设备实现

必须区分
--------

性能与安全
   性能要求降低正常路径成本；安全要求不可信输入和对象状态始终受到检查。二者需要共同成立。

通用接口与统一实现
   通用接口允许不同对象使用相同入口；它不表示所有对象执行相同代码。

延迟与吞吐
   延迟关注单个请求完成速度；吞吐关注一段时间内完成的总工作量。

用户态 ABI 与内核内部接口
   用户态 ABI 需要长期稳定；内核内部实现可以随版本演进。

一句话结论
----------

Linux 内核的代码形态来自多种工程压力的平衡：边界必须安全，入口尽量通用，热路径控制成本，内部实现允许演进。

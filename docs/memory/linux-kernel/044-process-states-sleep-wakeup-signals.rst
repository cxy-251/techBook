第044章：进程状态、睡眠、唤醒与信号
===================================

核心知识点
----------

运行状态与退出状态是两套状态机
   task 的 ``__state`` 描述它是否可运行或正在等待，``exit_state`` 描述退出后的 zombie 与回收阶段。二者不能混为同一组状态。

TASK_RUNNING 包含运行与等待运行
   ``TASK_RUNNING`` 表示 task 对调度器可运行。它可能正在某个 CPU 上执行，也可能已经进入 runqueue 等待调度。

睡眠表示等待条件
   ``TASK_INTERRUPTIBLE`` 允许信号改变等待路径，常对应用户态 ``S``；``TASK_UNINTERRUPTIBLE`` 主要等待内核条件，常对应 ``D``。``D`` 说明等待强度，不自动证明死锁。

等待队列连接等待者与事件
   wait queue 保存等待 task，条件变量或对象状态表达真正事件。等待路径必须把入队、状态切换、条件检查和 ``schedule()`` 按规定顺序组合，避免丢失唤醒。

条件必须循环检查
   ``wake_up*()`` 只表示条件可能已经变化，并把等待者重新置为可运行。task 真正获得 CPU 时，条件可能再次变化，因此必须重新检查。

唤醒与调度是两个阶段
   唤醒负责让 task 进入可运行集合，调度器再决定它何时在哪个 CPU 上执行。被唤醒不等于立即继续运行。

信号可以改变可中断等待
   信号先进入 pending 状态，并按阻塞掩码和投递类型处理。可中断等待检测到信号后，可以返回内部重启状态或最终向用户态表现为 ``EINTR``。

用户信号处理器在返回用户态时运行
   内核负责信号选择、pending 状态和用户现场修改。用户 handler 通常在安全返回用户态的边界获得执行机会，而不是在任意内核指令中直接执行。

zombie 是已退出但未回收的 task
   zombie 已不再参与调度，只保留退出码和统计信息。父进程通过 ``wait*()`` 读取这些信息后，task 才进入最终释放阶段。

关键路径
--------

普通阻塞等待：

::

   检查条件尚未满足
   → 准备并加入等待队列
   → 设置睡眠状态
   → 再次检查条件
   → 条件仍不满足则 schedule
   → 生产者更新共享条件
   → 生产者执行 wake_up
   → task 变为 TASK_RUNNING
   → 调度器选中 task
   → task 醒来后重新检查条件

可中断等待收到信号：

::

   task 进入 TASK_INTERRUPTIBLE
   → 信号进入 pending 状态
   → task 被唤醒
   → 等待函数检查 signal_pending
   → 返回重启状态或中断结果
   → 系统调用退出路径决定自动重启或 EINTR
   → 返回用户态时处理信号动作

退出与回收：

::

   task 进入退出路径
   → 停止普通执行
   → 归还运行资源引用
   → 保存退出码与统计
   → 进入 EXIT_ZOMBIE
   → 通知父进程
   → 父进程执行 wait
   → 读取退出信息
   → task 最终释放

定位长时间等待：

::

   确认具体 TID 与状态
   → 找到等待函数和等待对象
   → 确认条件由谁更新
   → 确认唤醒路径是否执行
   → 区分已唤醒未调度与仍未满足条件
   → 判断慢 I/O、资源故障、丢失唤醒或死锁

概念辨析
--------

可运行与正在运行
   ``TASK_RUNNING`` 同时覆盖 CPU 上执行和 runqueue 中等待的 task。

可中断睡眠与不可中断睡眠
   可中断睡眠允许信号提前改变路径；不可中断睡眠主要等待内核条件完成。

睡眠与停止
   睡眠由代码主动等待条件产生；停止通常来自作业控制或调试器。

唤醒与执行
   唤醒改变调度状态；真正执行还要等待调度器选择。

pending 信号与 handler 执行
   pending 是内核中的待处理状态；用户 handler 通常在返回用户态时执行。

D 状态与死锁
   ``D`` 只证明 task 正处于不可中断等待；死锁还要证明等待条件无法再被满足。

zombie 与运行任务
   zombie 已停止运行，只保留父进程回收所需的信息。

本章结论
--------

Task 的睡眠是对条件的等待，唤醒只让它重新具备运行资格，调度器决定何时继续；诊断“卡住”必须找到等待对象、条件更新者和唤醒路径。

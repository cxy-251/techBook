第126章：字符设备注册与 file_operations
=======================================

本章必须记住
------------

#. 字符设备把一个内核对象通过文件描述符暴露给用户态，访问单位由驱动定义，可以是字节流、消息、事件或控制命令。
#. 字符设备的最小身份链是：路径名 → inode 中的 ``dev_t`` → 字符设备映射 → ``struct cdev`` → ``file_operations``。
#. ``dev_t`` 由 major 和 minor 组成；major/minor 是内核查找键，不应被当作稳定的硬件序列号。
#. 新驱动通常使用 ``alloc_chrdev_region()`` 动态申请设备号，再以 ``unregister_chrdev_region()`` 归还。
#. ``struct cdev`` 是字符设备号范围与文件操作表之间的注册对象，不等于完整硬件状态。
#. 驱动常把 ``struct cdev`` 嵌入私有设备对象，通过 ``container_of(inode->i_cdev, ...)`` 回到宿主对象。
#. ``cdev_init()`` 初始化对象和操作表，``cdev_add()`` 才把设备号范围发布到字符设备查找结构中。
#. ``cdev_add()`` 成功后用户态可能立即打开设备，因此锁、队列、状态和引用协议必须在发布前完成初始化。
#. ``cdev_del()`` 撤销新打开入口，但已经打开的 ``struct file`` 仍可能继续持有原操作表和私有对象。
#. ``/dev`` 节点只是用户态路径入口；节点存在不表示驱动已绑定、硬件可用或操作一定成功。
#. 节点通常由 devtmpfs/udev 根据设备号和 uevent 创建；具体名称、权限与符号链接属于用户空间策略。
#. 删除 ``/dev`` 节点不会注销内核 ``cdev``；删除 ``cdev`` 也不会自动结束已经打开的 fd。
#. 打开字符设备时，VFS 根据 inode 的设备号找到 ``cdev``，再把驱动的 ``file_operations`` 安装到当前 ``struct file``。
#. ``struct inode`` 表示设备节点对象，``struct file`` 表示一次打开实例，两者不能混为同一生命周期。
#. ``file_operations`` 是驱动对用户态公开的长期合同，包含支持的操作、阻塞语义、错误码、数据格式和并发规则。
#. ``.owner = THIS_MODULE`` 帮助文件操作期间保持模块代码可用，但不能替代设备私有对象引用。
#. ``open`` 常把设备或会话对象保存到 ``file->private_data``，后续 ``read/write/poll/ioctl/mmap`` 通过它定位状态。
#. 若一个设备允许多次打开，必须明确各 fd 是共享同一设备状态，还是拥有独立会话状态。
#. 独占打开必须使用原子状态、mutex 或引用协议实现，不能用无锁布尔量检查后再设置。
#. ``release`` 在某个打开文件的最后引用释放时执行，用于归还该 fd 持有的会话和设备引用。
#. ``close(fd)`` 不一定立即调用驱动 ``release``，因为 ``dup``、fork、异步请求或内核引用可能继续持有同一 ``struct file``。
#. ``read`` 和 ``write`` 返回成功传输的字节数；短读、短写可以是合法结果，调用者必须按返回值继续处理。
#. 返回 0 的 ``read`` 通常表示 EOF 或当前接口定义的永久结束，不能用它表达“暂时没有数据”。
#. 暂无数据且 fd 为阻塞模式时，驱动可进入等待队列；非阻塞模式通常返回 ``-EAGAIN``。
#. 可被信号中断的等待应返回相应错误，不能丢失已完成的部分传输字节数。
#. ``copy_to_user()`` 和 ``copy_from_user()`` 返回未复制字节数，不是普通负 errno；驱动必须转换成正确的部分完成或 ``-EFAULT`` 语义。
#. 用户指针不能直接解引用，也不能在持 spinlock、关闭中断或其它不可 fault 的上下文中执行可能睡眠的用户复制。
#. 从用户态读取长度、偏移、索引和结构体前必须验证范围、溢出、对齐和对象当前状态。
#. 用户输入决定分配大小时，应使用数组溢出 helper 和业务上限，不能只依赖 ``size_t`` 乘法。
#. ``llseek`` 定义文件偏移是否有意义；无随机定位语义的设备应使用 ``no_llseek`` 或等价策略。
#. ``read``/``write`` 是否使用 ``*ppos`` 必须与接口模型一致，不能让多个 fd 在共享状态上意外争用同一隐式偏移。
#. ``poll``/``epoll`` 回调的职责是登记等待队列并返回当前就绪掩码，不是执行实际数据传输。
#. ``poll_wait(file, waitq, table)`` 把等待者关联到驱动等待队列；状态变化后驱动使用 ``wake_up*()`` 通知重新检查。
#. 就绪状态必须在登记等待关系后重新检查或由正确锁序保证，避免检查与睡眠之间丢失唤醒。
#. ``POLLIN`` 表示读取可能推进，``POLLOUT`` 表示写入可能推进；它们不保证后续操作一定完成全部请求。
#. 设备断开或永久错误应通过 ``POLLHUP``、``POLLERR`` 及实际读写错误共同表达，具体合同必须稳定。
#. ``ioctl`` 适合无法自然表达为读写、属性或标准子系统操作的控制命令，不应成为无结构的万能入口。
#. Ioctl 命令通常使用 ``_IO``、``_IOR``、``_IOW``、``_IOWR`` 编码方向、类型、编号和参数大小。
#. 命令号、结构体布局、字段语义、错误码和权限一旦发布即成为 UAPI，不能随内部重构随意改变。
#. UAPI 结构应使用固定宽度类型、明确 padding、保留字段和版本/大小策略，避免直接暴露内核指针、``long`` 或内部结构。
#. ``_IOC_SIZE`` 只能证明命令编码中的声明大小，驱动仍需验证具体版本、保留字段和用户缓冲区内容。
#. 32 位用户态运行在 64 位内核上时，指针大小和布局可能不同；必要时实现 ``compat_ioctl`` 或使用天然兼容结构。
#. Ioctl 输入必须先复制到内核缓冲区并完整验证，再修改设备状态，避免验证中途产生部分副作用。
#. 管理、复位、固件更新和 DMA 控制命令通常需要能力检查、设备状态检查和单一所有者协议。
#. Sysfs 适合单值、可发现的对象属性；复杂事务、批量数据或异步命令不应被拆成不可靠的 sysfs 写序列。
#. ``mmap`` 把内核页、DMA 缓冲区或设备 MMIO 映射给用户态，必须明确映射对象、offset、长度、权限和缓存属性。
#. 用户传入的 ``vm_pgoff`` 是页单位偏移，驱动必须防止整数溢出和映射越界。
#. 普通 RAM、vmalloc、DMA buffer 和设备 BAR 需要不同映射 helper，不能统一用 ``virt_to_phys`` 加 ``remap_pfn_range``。
#. 映射设备 MMIO 会把硬件寄存器暴露给用户态，通常只适用于受信任进程和严格限定范围。
#. VMA 可以在 fd 关闭后继续存在，因此 mmap backing object 必须拥有独立于 ``struct file`` 的引用生命周期。
#. 设备移除时，旧 VMA、旧 fd 和异步 I/O 可能仍存在；必须设置 disconnected 状态并禁止继续访问已消失硬件。
#. 驱动不能在 ``cdev_del`` 后立即 ``kfree`` 私有对象，除非已经证明没有 open、VMA、work、IRQ、DMA 或其它引用。
#. 常见安全 teardown 是先阻止新 open，再撤销设备节点和 ``cdev``，随后排空异步访问，最后等待引用归零。
#. ``file->private_data`` 保存裸指针时，``open`` 必须取得覆盖整个 fd 生命周期的引用，``release`` 再归还。
#. 驱动 remove 不应无限等待恶意进程关闭 fd；可以保留软件对象到最后 release，同时让旧操作返回 ``-ENODEV``。
#. 多线程同时操作同一 fd 时共享同一 ``struct file`` 和 private data，驱动必须明确操作级原子性。
#. 多进程打开同一节点时通常拥有不同 ``struct file``，但可共同指向同一设备对象和硬件队列。
#. 锁只保护指定状态；等待队列、引用计数、RCU、DMA completion 和设备状态机仍需分别设计。
#. 调试打开失败时，应按节点权限 → major/minor → ``cdev`` 注册 → 模块/驱动状态 → ``open`` 返回码逐层定位。
#. 调试阻塞卡死时，应检查等待条件、生产者、唤醒点、断开状态和信号路径，而不是只看睡眠任务栈。
#. 调试 UAF 时，应把最后 open/release、``cdev_del``、remove、VMA close 和异步 callback 放在同一时间线。
#. 精确 ``file_operations`` 字段、字符设备注册 helper 和 VFS 包装函数具有版本差异；稳定模型是设备号找到 ``cdev``，打开实例持有对象并分发文件操作。

必背路径
--------

字符设备注册：

::

   分配并初始化驱动私有对象
   → 初始化锁、等待队列、引用和 disconnected 状态
   → alloc_chrdev_region 申请 dev_t
   → cdev_init 绑定 file_operations
   → cdev_add 发布设备号范围
   → 创建 class/device 或发送 uevent
   → devtmpfs/udev 建立 /dev 节点
   → 用户态可以立即 open

打开与访问：

::

   open /dev/demo0
   → 路径解析得到字符设备 inode
   → inode->i_rdev 提供 dev_t
   → 字符设备映射找到 struct cdev
   → 安装驱动 file_operations
   → 驱动 open 取得设备引用
   → file->private_data 保存实例/会话
   → read/write/poll/ioctl/mmap 分发到驱动
   → release 归还当前打开引用

阻塞读取：

::

   read 检查缓冲区是否有数据
   → 有数据则复制并返回字节数
   → 无数据且 O_NONBLOCK
   → 返回 -EAGAIN
   → 无数据且允许阻塞
   → 登记等待队列并睡眠
   → IRQ/work 写入数据并更新状态
   → wake_up 唤醒
   → 重新检查条件后复制数据

Ioctl：

::

   解码 cmd 并检查命令族、编号和大小
   → 检查权限与设备状态
   → copy_from_user 到内核 UAPI 结构
   → 验证版本、flags、reserved、范围和溢出
   → 在统一锁/状态机中执行命令
   → 填写输出结构
   → copy_to_user
   → 返回 0、结果值或稳定负 errno

安全移除：

::

   设置 disconnected 并阻止新硬件请求
   → 撤销用户态新入口和设备节点
   → cdev_del 阻止新 open
   → 停止 IRQ、DMA、work、timer 和等待生产者
   → 唤醒阻塞 fd 使其返回断开错误
   → 等待 VMA、异步请求和打开引用结束
   → unregister_chrdev_region
   → 最后释放私有对象

必须区分
--------

* 设备节点与内核设备：``/dev`` 只是路径和设备号；真实状态位于 ``cdev``、驱动对象和硬件资源中。
* ``inode`` 与 ``struct file``：Inode 表示节点；file 表示一次打开实例，并承载偏移、标志和 private data。
* ``cdev_del`` 与对象释放：Del 阻止新打开；已有 fd、VMA 和异步路径仍可能延长对象寿命。
* 阻塞等待与 Poll 就绪：Read 可以睡眠等待数据；poll 只登记等待关系并报告当前是否可能推进。
* Ioctl 编码与参数安全：命令宏编码方向和大小；驱动仍需复制、验证版本、范围、权限和对象状态。
* 关闭 fd 与硬件移除：Close 结束一个打开引用；remove 撤销硬件能力，两条生命周期可能交叉。

一句话结论
----------

字符驱动用设备号和 ``cdev`` 把路径映射到 ``file_operations``，真正正确性取决于每个打开实例的引用、阻塞/就绪语义、UAPI 验证以及设备移除后旧 fd 与 VMA 的安全收束。

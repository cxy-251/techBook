第103章：异步 I/O 与完成模型
============================

本章必须记住
------------

#. 异步 I/O 的核心不是“调用更快”，而是把请求提交和结果完成拆成两个独立阶段。
#. 同步调用中，函数返回值同时承担完成通知；异步提交返回值通常只说明请求是否被接受。
#. 请求被接受、进入底层路径、设备完成、完成事件入队和用户消费完成事件是不同时间点。
#. 提交返回后，请求对象、buffer、文件引用和身份标记通常仍必须保持有效。
#. 一个完整异步模型必须定义请求身份、完成结果、通知方式、队列容量、背压、取消和最终资源回收。
#. 没有完成队列或等价结果对象的“异步提交”无法可靠表达每个请求的字节数、错误和生命周期终点。
#. Outstanding work 表示已经提交但尚未被业务完整回收的请求集合。
#. 系统吞吐依赖适当数量的 outstanding requests；数量过少不能展开设备并行，过多会放大排队和内存占用。
#. 每个未完成请求都可能占用请求结构、文件引用、buffer、页固定、队列槽位和业务上下文。
#. 异步系统必须在提交入口设置上限，不能把“队列未报错”当成无限容量。
#. Backpressure 的稳定目标是让提交速率不长期超过完成消费速率。
#. 背压可以表现为提交数量小于请求数量、``EAGAIN``、队列满、信用不足或应用主动限深。
#. 只观察提交速率会掩盖完成队列积压；必须同时观察在途数和完成消费速率。
#. 请求身份不能依赖完成顺序，因为不同缓存状态、文件、设备和队列会让请求乱序完成。
#. 应用应为每个请求保存 token、ID、索引或用户数据，并从完成结果映射回原始业务状态。
#. 短读、短写和部分完成是合法结果，完成处理不能只区分成功与失败。
#. 异步请求的业务错误通常在完成对象中返回；提交接口自身的错误属于另一层。
#. 入口错误说明请求没有正常进入该异步实例；CQ/事件中的负错误表示具体请求完成为失败。
#. Readiness 模型和 Completion 模型必须区分。
#. ``epoll`` readiness 回答“这个 fd 当前可能可以推进 I/O”，不表示某个先前提交请求已经完成。
#. AIO/``io_uring`` completion 回答“带特定身份的请求已经产生结果”。
#. Readiness 事件之后通常还要执行非阻塞 read/write；completion 事件已经携带本次操作结果。
#. ``eventfd`` 可以把内核事件转换成可被 poll/epoll 监控的 fd 通知，但完整请求结果通常仍在另一完成队列中。
#. 通知只负责唤醒，不一定携带全部完成数量、请求身份和错误。
#. 完成队列可以批量消费，减少每个请求一次唤醒和系统调用的固定成本。
#. 批量完成提高吞吐，也会增加完成等待时间；批量阈值必须和延迟目标平衡。
#. 轮询完成可以降低中断和调度唤醒成本，同时持续消耗 CPU，并可能影响同核任务延迟。
#. 中断、睡眠等待和 busy polling 是完成等待策略，不是不同的数据一致性保证。
#. POSIX AIO、legacy Linux AIO、线程池、readiness loop 和 ``io_uring`` 属于不同执行与完成模型。
#. POSIX AIO 的用户可见 API 不保证由内核原生异步执行；具体实现可能使用用户态工作线程。
#. Legacy Linux AIO 通常指 ``io_setup``、``io_submit``、``io_getevents``、``io_cancel``、``io_destroy`` 系列接口。
#. Legacy Linux AIO 使用 AIO context 管理请求容量和 completion ring，用户通过 ``io_getevents`` 取得结果。
#. ``struct iocb`` 描述请求，``struct io_event`` 描述完成；用户数据字段用于关联请求身份。
#. Legacy Linux AIO 的稳定收益长期更集中于支持良好的文件 Direct I/O 路径，buffered 与其它对象能力具有实现限制。
#. ``io_submit`` 成功返回已提交数量，该数量可以小于请求数量；未提交部分仍由用户态负责。
#. ``io_getevents`` 可以按最小完成数和超时等待，等待策略会直接影响批量效率和尾延迟。
#. AIO context 的 ring、活动请求和系统计数都有容量限制，创建成功不表示未来提交不会 ``EAGAIN``。
#. ``io_destroy`` 不是简单释放一个整数句柄，它需要收束 context 中的请求和完成状态。
#. 取消请求和销毁 context 的具体阻塞、失败和完成语义应按目标接口与内核版本验证。
#. 线程池通过多个阻塞线程实现用户态可见的异步：提交线程不阻塞，worker 仍会阻塞在普通 I/O 中。
#. 线程池适合包装不提供内核异步能力的操作，并能保持普通 syscall 与文件系统语义。
#. 线程池的代价包括线程栈、调度、上下文切换、队列锁、唤醒和过量并发。
#. Worker 数量过少会形成用户态排队；过多会把压力推给文件系统、内存和设备队列。
#. 线程池需要单独设计任务队列、完成队列、取消、超时、进程退出和 worker 崩溃处理。
#. 内核原生异步路径能让请求离开提交线程后继续推进，但不保证路径中所有准备阶段都不阻塞。
#. Buffered I/O 可能需要 Page Cache folio、文件系统锁、块分配、writeback 或内存回收，提交阶段仍可能遇到同步工作。
#. Direct I/O 更容易把数据请求直接交给块层异步完成，但仍可能因 extent、元数据和对齐进入慢路径。
#. ``RWF_NOWAIT`` 等语义允许路径在将要阻塞时快速完成为 ``-EAGAIN``，支持范围取决于文件系统和操作。
#. “异步 API”不等于“没有线程”；内核可以把无法直接推进的工作转交 worker 上下文。
#. “异步 API”也不等于“没有系统调用”；提交、等待、注册、唤醒仍可能需要进入内核。
#. 异步提交不会自动提高单个请求服务时间，它主要通过重叠等待和批量控制提高总体利用率。
#. 当设备已经饱和，继续增加队列深度通常只增加排队时间和 P99/P999 延迟。
#. Little's Law 可用来理解在途数、吞吐和平均响应时间的关系，但生产结论仍需真实分布和尾延迟证据。
#. 同一文件上的请求完成乱序不代表数据可见顺序也随意；文件 offset、追加、fsync 和应用协议仍要建立顺序。
#. 异步写完成表示该请求的 I/O 语义完成，不自动等于事务提交或数据达到稳定介质。
#. 多个写请求后提交一个 fsync 时，必须明确 fsync 与哪些写建立依赖；仅按提交先后不能无条件推断。
#. 链接、栅栏或显式状态机可以表达请求依赖，但取消和上游失败时必须定义下游处理。
#. 请求超时和请求取消属于控制操作，不等于底层设备工作一定从未发生。
#. Cancel 成功、找不到目标、已完成和不可取消是不同结果，应用必须处理竞态。
#. 写请求已到设备后取消，已写数据通常不能由取消机制自动回滚。
#. 请求超时后，原请求仍可能随后产生 completion；状态机必须防止重复释放和重复响应。
#. Buffer 只有在请求最终 completion 被确认并且不再有内核访问后才能归还池。
#. 文件被用户 close 后，异步请求可能仍持有 ``struct file`` 引用并继续完成；close fd 不等于取消所有在途 I/O。
#. 异步对象 teardown 必须先停止新提交，再取消/等待在途请求，再消费完成，最后释放 ring、context、file 和 buffer。
#. 错误路径必须防止“提交失败后仍等待不存在的 completion”和“完成后重复回滚”。
#. 完成队列容量不足会导致积压、丢失保护机制或提交受限；具体行为依接口而定。
#. 应用处理 CQ/事件的速度必须至少长期匹配完成产生速度，并为突发完成保留空间。
#. 多消费者完成队列需要定义谁拥有某个 completion，避免同一请求被处理两次。
#. 多提交者需要定义队列槽位发布和内存顺序，不能仅依赖普通变量读写。
#. 异步系统观测必须同时覆盖提交时间、排队时间、开始服务、设备完成、completion 入队和用户消费。
#. 只测 API 调用耗时会把后续排队和设备延迟遗漏在外。
#. ``strace`` 能观察提交和等待系统调用，但异步请求的真实生命周期需要结合文件系统、块层和 completion trace。
#. ``perf`` 可定位提交、完成、worker、copy 和锁竞争 CPU；ftrace/eBPF 可连接请求身份与内核事件。
#. 块层 trace 能区分请求何时进入块层、何时 dispatch 和完成，不能单独解释用户完成队列为何未及时消费。
#. 最稳定的异步 I/O 分析顺序是：请求创建 → 提交结果 → 在途归属 → 底层执行 → 完成入队 → 通知 → 用户消费 → 资源释放。

必背路径
--------

同步与异步对照：

::

   同步 read
   → 当前线程进入内核
   → 等待缓存/文件系统/设备
   → 返回字节数或错误
   → 请求生命周期随调用栈结束

   异步 submit
   → 创建请求身份与 buffer
   → 内核接受请求
   → 提交函数返回
   → 请求在后台继续推进
   → completion queue 产生结果
   → 用户消费结果
   → 才能释放请求资源

Legacy Linux AIO：

::

   io_setup 创建 AIO context
   → 准备 iocb 数组与用户身份
   → io_submit 提交部分或全部请求
   → 请求进入文件系统/Direct I/O 路径
   → aio_complete 写入 io_event ring
   → 唤醒 io_getevents 或 eventfd
   → 用户批量取得 io_event
   → 按 data 字段回收业务请求
   → io_destroy 收束 context

Readiness 事件循环：

::

   epoll 监控 fd
   → 内核报告 fd ready
   → 用户执行 nonblocking read/write
   → 操作可能完成、短 I/O 或 EAGAIN
   → 更新连接/文件状态
   → 再次等待 readiness

线程池模拟异步：

::

   提交线程把任务放入用户队列
   → worker 取任务
   → worker 执行阻塞 read/write/fsync
   → 内核完成后 worker 得到返回值
   → worker 写入应用完成队列
   → 事件循环/调用者消费结果
   → 归还 worker、buffer 和任务对象

安全 teardown：

::

   设置 stopping 并拒绝新提交
   → 记录所有 outstanding requests
   → 发起取消或等待自然完成
   → 持续消费 completion
   → 确认在途计数归零
   → 解除 buffer/page/file 引用
   → 销毁 context/ring/worker
   → 释放业务对象

必须区分
--------

提交成功与请求完成
   提交成功只说明请求被接收；完成结果要从 completion 对象取得。

Readiness 与 Completion
   Readiness 表示现在可能可做 I/O；completion 表示先前指定请求已经产生结果。

异步接口与异步执行
   API 允许提交/完成分离；具体路径可能直接异步、在提交点工作或转交 worker。

完成通知与完整结果
   Eventfd/唤醒只提示有事件；请求身份、字节数和错误通常仍在完成队列中。

取消请求与回滚数据
   Cancel 管理未完成请求状态，不能自动撤销已经发生的设备写入。

Close fd 与结束异步 I/O
   Close 移除 fd 表项；在途请求可能仍持有 file 引用并继续完成。

一句话结论
----------

异步 I/O 的本质是管理有界的未完成工作：提交、执行、完成入队、通知、消费和资源释放必须由同一请求身份与背压协议闭合。

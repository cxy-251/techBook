第010章：建立个人内核源码阅读工作流
===================================

本章必须记住
------------

#. 稳定的内核阅读工作流应把模糊问题逐步转换成入口、核心对象、操作表、状态分支、错误路径和运行证据。
#. ``grep``、``ripgrep`` 和 ``git grep`` 主要用于文本检索，它们提供候选位置，不证明运行时一定经过这些位置。
#. ``git grep`` 只搜索当前 Git 版本库跟踪的文件，适合确认目标提交中实际存在的符号和引用。
#. ``ctags`` 主要用于跳到符号定义，``cscope`` 适合查找调用者、引用和字符串位置。
#. LSP 根据头文件、编译参数和条件编译提供语义跳转；它的判断只适用于生成编译数据库时使用的架构和配置。
#. 本地工具链的稳定顺序是：先文本搜索缩小范围，再跳到定义和引用，最后人工确认对象关系、回调赋值和条件编译。
#. 在线源码浏览器适合快速查看上下文和交叉引用，但学习记录必须固定内核版本或提交，不能只保存会变化的 ``latest`` 链接。
#. 在线源码页面不能代表本机内核，因为发行版补丁、架构、配置和版本都可能不同。
#. 官方文档主要解释接口、对象模型、开发规则和子系统约束；源码决定当前版本的实际实现。
#. Git 提交历史适合解释某个辅助函数、字段、分支或锁规则为什么被引入、修改或删除。
#. ``git log`` 查看文件和提交历史，``git log -S`` 追踪字符串增删，``git blame`` 定位行的来源提交，``git show`` 阅读完整补丁和提交说明。
#. 提交说明提供设计动机线索，但最终判断仍要与补丁、当前源码和运行条件一致。
#. 个人阅读成果应保存为源码地图，而不是保存大量搜索输出和无上下文函数名。
#. 一张合格的源码地图至少记录：问题、目标版本、入口、核心对象、操作表、主要状态、关键分支、错误回滚、运行证据和未确认边界。
#. 子系统源码地图应持续更新入口函数、核心结构体、生命周期、回调表和关键运行路径。
#. 阅读内核本质上是在逆向一个持续演进的运行系统；工具只负责定位，真正的结果是可复查的对象关系和机制判断。

必背路径
--------

个人阅读工作流：

::

   把模糊问题写成一个具体动作或现象
   → 固定目标内核版本、架构和配置范围
   → 用 rg 或 git grep 找候选入口
   → 用 ctags、cscope 或 LSP 跳到定义和引用
   → 找到核心对象和操作表赋值
   → 记录状态分支、错误码和回滚路径
   → 查阅官方文档理解接口边界
   → 查阅 Git 历史理解设计动机
   → 用 /proc、sysfs、ftrace、tracepoint 或 perf 验证运行表现
   → 形成一张可复查的源码地图

一张源码地图的固定字段：

::

   问题与现象
   目标版本、架构和配置
   第一入口
   核心对象
   对象来源与生命周期
   操作表和间接回调
   fast、slow 与错误路径
   返回值和状态变化
   运行时证据
   已证明范围与未确认边界

工具使用顺序：

::

   文本检索找候选
   → 符号工具提高跳转效率
   → 人工还原对象关系
   → 文档确认接口语义
   → Git 历史解释变更原因
   → 运行证据确认当前路径

必须区分
--------

搜索结果与运行证据
   搜索结果证明源码中存在候选位置；运行证据证明目标时间窗口出现了对象、函数或事件。

符号跳转与路径理解
   跳转工具找到定义和引用；路径理解还需要对象状态、回调赋值和上下文条件。

在线最新源码与目标源码
   在线最新源码便于快速浏览；可靠结论必须绑定目标版本或固定提交。

源码实现与设计动机
   当前源码说明现在怎样实现；文档和提交历史帮助解释为什么这样设计。

工具记录与源码地图
   工具记录是临时检索结果；源码地图是可复查、可迁移的机制知识。

一句话结论
----------

个人内核阅读工作流的核心不是安装更多工具，而是固定版本、定位对象、追踪状态、验证路径，并把结果沉淀成源码地图。

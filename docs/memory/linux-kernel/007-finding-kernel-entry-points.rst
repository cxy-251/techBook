第007章：怎样在巨大源码库中找到入口
===================================

本章必须记住
------------

#. 在 Linux 内核中寻找入口时，应先判断手中的线索属于系统调用、设备绑定、内核日志还是运行时跟踪事件。
#. 不同线索对应不同入口模型，不能用同一种搜索方式处理所有问题。
#. 系统调用入口通常分为架构 ABI 与系统调用表、``SYSCALL_DEFINE*`` 生成的 C 入口、通用子系统入口和对象回调四层。
#. 从系统调用名开始时，应先找到系统调用号和表项，再找 C 层实现，随后确认它进入哪个通用子系统和哪个核心对象。
#. 系统调用实现通常负责参数接收、对象查找和通用检查，不一定包含最终的文件系统、协议或驱动逻辑。
#. 看到 ``file->f_op->read_iter`` 等间接调用时，入口定位必须转向“当前对象的操作表在哪里赋值”。
#. 驱动 ``probe`` 是设备和驱动匹配成功后的初始化入口，它负责申请资源、建立私有状态和注册运行期接口。
#. ``probe`` 与用户请求属于不同时间线：``probe`` 先建立对象和回调，后续 ``read``、发送、请求队列或中断路径再使用这些状态。
#. ``platform_set_drvdata()``、``dev_set_drvdata()``、``pci_set_drvdata()`` 和 ``file->private_data`` 等位置通常是私有对象的关联点。
#. 驱动注册结构中的 ``.probe`` 是生命周期钩子；``file_operations``、``net_device_ops`` 和块设备操作表是运行期操作钩子。
#. 内核日志中的函数名、偏移、模块名和调用栈可以反查已执行的源码位置，但必须匹配同一内核版本和构建产物。
#. Oops、WARN 和 panic 的调用栈表示故障附近已经执行的路径，不表示调用栈之外的所有条件都已查明。
#. tracepoint 和 ftrace 可以先提供运行时事件线索，再回到事件定义、调用位置和对象状态解释路径。
#. 源码中存在 tracepoint 只表示可以记录该事件；只有实际跟踪输出才能证明目标时间窗口触发了它。
#. 找入口的目标不是一次找到完整机制，而是找到第一条可信、可继续追踪的源码线索。

必背路径
--------

从系统调用寻找入口：

::

   用户态系统调用名
   → 目标架构的系统调用号与表项
   → SYSCALL_DEFINE* C 层入口
   → 第一个通用子系统函数
   → 核心运行对象
   → 操作表或回调
   → 具体实现

从驱动寻找运行期入口：

::

   设备被枚举
   → 总线匹配设备与驱动
   → driver core 调用 probe
   → probe 申请资源并建立私有对象
   → 注册操作表或子系统接口
   → 用户请求或硬件事件进入运行期回调

从故障证据寻找入口：

::

   日志、Oops、WARN 或 trace 事件
   → 确认内核版本与模块
   → 解析符号、偏移和调用栈
   → 找到触发位置
   → 检查该位置使用的对象和状态
   → 向前追来源，向后追结果与回滚

必须区分
--------

系统调用入口与最终实现
   系统调用入口接收用户请求；最终实现通常由对象类型和回调表决定。

``probe`` 与运行期操作
   ``probe`` 建立设备状态；运行期回调处理后续用户请求或硬件事件。

日志位置与根本原因
   日志指出症状或检测位置；根本原因可能发生在更早的对象、状态或并发路径中。

tracepoint 定义与实际事件
   定义表示事件可被记录；跟踪输出才表示该事件在目标时间窗口真实发生。

一句话结论
----------

先给线索分类，再沿对应入口模型找到第一个可信对象；入口定位完成后，调用链才能有稳定方向。

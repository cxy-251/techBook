第076章：内核分配器家族与分配上下文
====================================

本章必须记住
------------

#. Linux 内核没有一个适合所有场景的通用分配器；分配接口按资源粒度、连续性、上下文和访问模式专门化。
#. 选择分配器前，必须先确定申请的是物理页、普通字节对象、固定类型对象、虚拟连续区域还是每 CPU 副本。
#. Page allocator 以页和 ``order`` 为单位管理物理页框，常见接口包括 ``alloc_pages()``、``__get_free_pages()`` 和对应释放接口。
#. ``order-n`` 表示 ``2^n`` 个物理连续页，越高阶越依赖连续空闲块形状和 compaction 结果。
#. Slab/SLUB 对象分配器位于 page allocator 之上，把一组页切分成固定大小对象槽位。
#. ``kmalloc()`` 使用通用大小等级缓存，适合普通小对象和字节缓冲区。
#. ``kmem_cache_alloc()`` 使用专用对象缓存，适合高频、同型、需要对齐、构造、统计或调试属性的内核对象。
#. ``vmalloc()`` 用多个可分散物理页建立连续内核虚拟地址，适合只要求 CPU 线性访问的大块区域。
#. Per-CPU allocator 为每个 possible CPU 建立独立副本，适合高频本地更新和低频聚合读取。
#. 分配器选择的第一维是粒度：页级需求走 page allocator，对象级需求优先走 ``kmalloc`` 或专用 slab cache。
#. 第二维是连续性：CPU 指针访问只要求虚拟连续；DMA、硬件描述符和部分低层接口还要求设备可访问的物理或总线布局。
#. 第三维是上下文：能否睡眠、能否直接回收、能否进入 I/O 或文件系统路径，决定可使用的 GFP 语义。
#. 第四维是频率和局部性：高频同型对象应尽量复用对象缓存和 per-CPU 快路径，避免反复进入页级慢路径。
#. 第五维是生命周期：分配成功只建立内存所有权，注册、发布、引用、异步回调和最终释放仍需单独协议。
#. Page allocator 关心 node、zone、watermark、migratetype、order 和 reclaim；对象分配器关心大小、对齐、cache、freelist 和对象状态。
#. 小对象直接占用完整页会造成严重内部碎片，也会增加 TLB、cache 和页分配器路径成本。
#. 对象缓存通过固定大小槽位、批量取页和复用空闲对象降低高频分配成本。
#. 专用 ``kmem_cache`` 可以绑定对象名称、大小、对齐、标志和可选构造函数，使运行时统计与对象类型对应。
#. 构造函数只适合初始化可跨复用周期保持稳定的底层字段，不能代替每次分配后的完整业务初始化。
#. 对象从 cache 取出后，旧对象内容可能仍残留；除非使用清零接口或调用者逐字段初始化，否则不能假设内容为 0。
#. GFP flags 是调用者与分配器之间的执行上下文契约，不是单纯的性能提示。
#. ``GFP_KERNEL`` 适合可睡眠的普通进程上下文；原子、中断或持 spinlock 路径不能因为方便而使用它。
#. ``GFP_ATOMIC`` 只提供受限的紧急尝试，不保证成功，也不应替代预分配、mempool 或明确降级方案。
#. ``GFP_NOIO``、``GFP_NOFS`` 等限制用于阻止回收递归进入不安全层次，错误放宽可能形成死锁或递归依赖。
#. 任何可失败分配都必须检查返回值，并在后续失败路径中按依赖逆序回滚已取得资源。
#. 分配失败可能来自容量、碎片、zone、NUMA、memcg、GFP、上下文或调试限制，不能只用“系统还有空闲内存”判断。
#. 内存来自哪个分配器，决定对应的释放接口；来源和释放方式必须成对设计。
#. ``kmalloc``/``kzalloc``/``kcalloc`` 结果通常由 ``kfree()`` 释放，专用 cache 对象由 ``kmem_cache_free()`` 归还原 cache。
#. ``vmalloc``/``vzalloc`` 结果由 ``vfree()`` 释放；``kvmalloc`` 结果应使用 ``kvfree()``。
#. Page allocator 返回的页必须用与分配阶数和接口匹配的页释放路径归还，不能交给 ``kfree()``。
#. 动态 per-CPU 内存由 ``alloc_percpu()`` 一类接口分配，并用 ``free_percpu()`` 释放。
#. 释放接口匹配只解决存储归还，不解决对象仍被 RCU reader、work、timer、IRQ、DMA 或其它引用访问的问题。
#. 关键路径需要前进保证时，应优先考虑启动时预分配、对象池或 mempool，而不是假设运行时分配永不失败。
#. NUMA 系统上，分配位置会影响访问延迟；对象 cache、page allocator 和 per-CPU 分配都可能带有节点与本地性语义。
#. DMA 缓冲区应使用 DMA API 表达设备地址能力、IOMMU、缓存一致性和映射生命周期，不能只凭 ``kmalloc`` 或物理连续性推断可用。
#. 调试分配问题时，应同时记录分配接口、大小/order、GFP、调用上下文、CPU/node、失败分支和释放路径。
#. 选择更重的分配器不是自动更安全；``vmalloc``、调试 slab 和强回收都会增加页表、TLB、CPU 或延迟成本。
#. 选择更轻的分配器也不是自动更快；错误的 GFP、跨 CPU 共享写、过高 order 和频繁 cache miss 会破坏快路径。
#. 正确的分配器选择应让资源形态、访问者能力、执行上下文和生命周期同时闭合。

必背路径
--------

选择分配器：

::

   明确申请的是页、对象、虚拟区域还是 per-CPU 副本
   → 明确大小、对齐和连续性要求
   → 明确 CPU 访问还是设备访问
   → 明确当前上下文能否睡眠和回收
   → 明确频率、NUMA 与缓存局部性
   → 选择 alloc_pages / kmalloc / kmem_cache / vmalloc / alloc_percpu
   → 设计失败处理与匹配释放接口

小对象路径：

::

   子系统申请结构体对象
   → 通用对象进入 kmalloc 大小等级
   → 高频同型对象进入专用 kmem_cache
   → SLUB 优先从本 CPU freelist 取槽位
   → 必要时向 page allocator 申请 slab backing pages
   → 调用者完成本次对象初始化
   → 生命周期结束后归还原 cache

分配失败处理：

::

   分配接口返回 NULL
   → 保留原始错误语义
   → 停止发布半初始化对象
   → 按逆序撤销注册和引用
   → 取消已排队的异步工作
   → 使用匹配接口释放已取得内存
   → 返回错误或执行预先设计的降级路径

检查释放完整性：

::

   确认对象已从所有查找结构摘除
   → 阻止新引用
   → 等待 RCU、timer、work、IRQ 和 DMA
   → 等待普通引用归零
   → 确认分配来源
   → 使用 kfree / kmem_cache_free / vfree / free_pages / free_percpu
   → 清除外部可见指针

必须区分
--------

* 页分配与对象分配：Page allocator 管理物理页块；slab/SLUB 把页切成可复用的小对象槽位。
* 通用大小缓存与专用对象缓存：``kmalloc`` 按大小等级分配；``kmem_cache`` 还携带对象类型、对齐、构造和调试语义。
* 虚拟连续与物理连续：CPU 线性指针只要求虚拟连续；DMA 和低层硬件路径必须按设备接口证明实际可访问布局。
* 分配上下文与内存用途：GFP 描述调用者允许分配器执行什么动作；对象用途描述返回内存随后怎样被使用。
* 释放存储与结束生命周期：释放接口归还内存；对象必须先停止所有可见性、引用和异步访问。
* 快速失败与前进保证：``GFP_ATOMIC`` 仍可失败；真正需要保证的路径应使用预分配、对象池或 mempool。

一句话结论
----------

内核内存分配必须先按资源粒度、连续性、访问者和执行上下文选择专用分配器，再用匹配的失败与生命周期协议保证对象最终安全归还。

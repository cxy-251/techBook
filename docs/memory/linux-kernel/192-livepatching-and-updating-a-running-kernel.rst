第192章：Livepatching 与运行中内核更新
=====================================

核心知识点
----------

Livepatch 是受限的运行时代码替换
   它主要用于高可用系统中的紧急安全修复和严重缺陷修复，适合边界清晰、状态兼容的函数级改动，不是任意内核升级机制。

函数重定向只是第一步
   Linux 可借助 ftrace 将旧函数入口导向新实现。真正的难点是新旧函数在参数、返回值、锁、引用和共享对象语义上保持兼容。

补丁由三层对象描述
   ``struct klp_patch`` 表示补丁集合，``struct klp_object`` 表示目标 ``vmlinux`` 或模块，``struct klp_func`` 描述旧函数与新函数的替换关系。

切换按任务逐步完成
   Livepatch 通常使用 Per-task Consistency Model。Transition 期间，部分任务可能仍执行旧实现，部分任务已经使用新实现，因此补丁必须允许新旧语义短暂并存。

安全点决定任务何时切换
   返回用户态、显式 Patch Point 或可靠栈检查可帮助任务更新 Patch State。长期停留在受影响调用栈中的内核线程可能阻塞 Transition 完成。

回滚同样需要一致性证明
   回滚不是直接卸载模块，而是执行反向 Transition。恢复旧函数入口不会自动撤销新代码已经造成的不可逆数据变化或外部副作用。

Livepatch 二进制绑定具体构建
   目标 Kernel、Config、Compiler、Architecture、符号和对象布局必须匹配。构建、签名、分发和加载共同构成供应链安全边界。

关键路径
--------

补丁激活：

::

   加载 Livepatch 模块
   → 注册 klp_patch / klp_object / klp_func
   → 解析目标符号
   → 准备函数入口重定向
   → 启动 Per-task Transition
   → Task 在安全点更新 Patch State
   → 所有 Task 收敛
   → 验证原故障与业务状态

回滚路径：

::

   发现回归
   → 检查补丁依赖与不可逆状态
   → 启动反向 Transition
   → Task 回到旧 Patch State
   → 恢复旧函数入口
   → 验证共享对象与业务状态
   → 卸载补丁或安排完整升级

概念辨析
--------

* **函数可替换与系统语义一致**：入口重定向只改变控制流；共享状态、锁和引用合同仍需人工证明。
* **模块已加载与全部任务已切换**：加载只注册代码；所有任务到达安全点后，Transition 才真正完成。
* **Transition 完成与修复验证完成**：前者证明任务状态收敛，后者还要验证原故障、数据和性能结果。
* **恢复旧代码与恢复旧状态**：反向切换能恢复函数实现，不能自动撤销不可逆数据或外部副作用。
* **Livepatch 与完整升级**：Livepatch 处理有限紧急修复；完整升级更新全部代码、初始化和数据结构，通常仍需要重启。
* **相同源码补丁与相同二进制**：源级修改可以相同，Livepatch 二进制仍必须匹配具体 Kernel Build。

本章结论
--------

Livepatching 的核心不是把函数入口换成新地址，而是在共享内核状态持续运行时，证明新旧实现能够安全并存、逐步收敛并可受控回滚。

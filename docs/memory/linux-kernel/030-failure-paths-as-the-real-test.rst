第030章：失败路径是内核设计的真实检验
=====================================

核心知识点
----------

失败路径负责恢复稳定状态
   成功路径把对象推向可用状态，失败路径必须把半初始化、部分注册或已经启动异步活动的对象恢复到调用者能够理解的安全状态。

回滚依据是当前构造阶段
   每次资源申请、状态设置、索引插入、回调注册和上层发布都会增加一项回滚责任。失败发生时，首先要判断对象已经完成了哪些阶段。

资源账本应记录状态变化
   只记录调用过哪些函数不够。审查时需要列出已经取得的资源、已经发布的入口、已经增加的引用以及已经启动的异步执行。

错误标签表达恢复边界
   ``goto err_*`` 标签通常代表明确的半初始化状态。每个失败点应跳到与当前状态匹配的标签，既不能遗漏已取得资源，也不能清理尚未建立的资源。

外部可见状态必须优先撤销
   对象一旦进入索引、sysfs、VFS、driver core 或通知机制，回滚时应先关闭这些入口，再等待已经进入的调用链和异步执行结束，最后释放底层资源。

原始错误原因必须保留
   下层返回的负错误码应沿调用链传播。清理代码负责恢复状态，不应覆盖真正的失败原因，也不应在返回前留下仍可被发现的残缺对象。

自动托管不能覆盖全部副作用
   devres 可以回收已登记资源，但全局注册、外部通知、引用转移、工作队列和其它非托管状态仍需显式撤回。API 的自动清理边界必须逐项确认。

失败路径需要主动测试
   正常运行很难覆盖低概率分配失败、I/O 错误、probe 失败和超时。Fault injection 应指定注入点、预期错误码、预期清理动作和可观察结果。

诊断工具各自提供不同证据
   KASAN 发现越界和 use-after-free，refcount warning 指向引用错误，lockdep 检查锁依赖和上下文，Oops 与调用栈提供故障附近的动态路径。根因仍要回到对象生命周期和回滚顺序。

可靠失败的标准是无残留
   返回错误后，对象不应仍可查找，资源不应泄漏，引用应归还，异步任务不应继续访问，外部状态应回到未注册、未绑定或已停止等稳定状态。

关键路径
--------

失败路径审查：

::

   列出成功路径的构造阶段
   → 标记每一步新增的状态和责任
   → 找到所有失败点
   → 判断失败时已完成的阶段
   → 检查 err 标签是否匹配
   → 先撤销外部可见状态
   → 同步停止异步执行
   → 按依赖逆序归还资源和引用
   → 返回原始错误码
   → 确认对象恢复稳定状态

对外发布后失败：

::

   标记对象停止服务
   → 从索引和用户入口撤下
   → 阻止新的回调与查找
   → 等待在途调用离开
   → 取消并同步异步工作
   → 归还引用和资源
   → 最终释放对象

失败注入验证：

::

   选择一个可控失败点
   → 写明预期返回与清理结果
   → 注入分配、I/O、probe 或超时失败
   → 检查错误码和标签路径
   → 检查索引、入口、引用和异步任务
   → 使用 KASAN、lockdep 和日志复查
   → 重复执行确认结果稳定

概念辨析
--------

业务失败与回滚失败
   业务失败是原始操作不能完成；回滚失败是清理过程又产生泄漏、重复释放或释放后访问。

错误标签与普通跳转
   ``err_*`` 标签描述对象构造阶段和恢复边界，不只是减少代码缩进。

返回失败与状态恢复
   负错误码只证明失败被报告；还必须证明对象和资源已经恢复到安全状态。

正常测试与失败注入
   正常测试主要覆盖成功路径；失败注入主动验证半初始化和低概率错误路径。

KASAN 报告与根因
   KASAN 证明发生非法内存访问；根因可能是引用、入口关闭、异步同步或 RCU 等待缺失。

本章结论
--------

内核设计是否可靠，要看它能否在任意中间阶段失败时准确识别当前状态、关闭所有入口、归还所有权并恢复稳定边界。

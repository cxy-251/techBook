第014章：Linux 内核日志与诊断语法
===============================

核心知识点
----------

日志是运行时证据
   内核日志记录某个调用点在特定时间输出的对象、动作、结果和严重程度。它能提供入口和时间线线索，但不能单独证明根因或完整并发关系。

日志缓冲区与控制台相互独立
   ``printk()``、``pr_*()`` 和 ``dev_*()`` 把消息写入内核日志缓冲区；是否实时显示到控制台由日志级别和 ``console_loglevel`` 决定。``dmesg`` 主要读取缓冲区中的记录。

日志级别表达报告者判断的严重程度
   ``pr_emerg()`` 到 ``pr_debug()`` 对应从紧急故障到调试信息的不同等级。级别帮助筛选和控制输出，但不自动等于真实故障影响范围。

设备日志绑定具体对象
   ``dev_err()``、``dev_warn()`` 和 ``dev_info()`` 让日志携带设备实例信息。高质量日志应说明哪个对象执行了什么动作、得到什么结果，并保留原始错误码。

Dynamic debug 控制调试调用点
   源码中的 ``pr_debug()`` 只表示存在观察点。是否输出取决于配置、模块状态和 dynamic debug 规则；调用点可以按模块、文件、函数、行号或格式字符串选择。

限速和单次日志会改变可见数量
   ``*_ratelimited()`` 限制高频消息，``*_once()`` 通常只报告第一次命中。日志条数少不表示事件只发生了相同次数。

``WARN`` 表示不变量被破坏
   ``WARN_ON()`` 等宏记录调用点和调用栈，并通常允许系统继续运行。真正要分析的是触发条件表达了哪个状态不变量，以及后续路径是否仍能安全恢复。

``BUG`` 与 ``panic`` 表示更严重的继续执行边界
   ``BUG`` 或 Oops 表示当前执行上下文可能已失去安全前提；``panic()`` 进入系统级停止、重启或 kdump 策略。实际结果还受配置和启动参数影响。

调用栈必须绑定匹配的构建产物
   ``function+offset/size [module]`` 提供函数内位置和模块来源。精确解析需要与运行内核一致的 ``vmlinux``、模块和调试信息，否则符号或源码行可能错误。

关键路径
--------

日志可见路径：

::

   源码执行 printk / pr_* / dev_*
   → 消息进入内核日志缓冲区
   → 日志级别与控制台策略决定实时显示
   → 用户态通过 dmesg 或 /dev/kmsg 读取

读取故障日志：

::

   按设备、模块和时间筛选记录
   → 判断日志级别与故障类别
   → 提取对象、错误码、CPU、进程和模块
   → 找最近的 function+offset/size
   → 向上读取调用栈
   → 回到源码检查条件、返回值和恢复路径
   → 用其它观测证据补充时序

故障严重程度：

::

   普通信息或调试日志
   → pr_warn / pr_err 报告异常或失败
   → WARN 记录不变量违反
   → BUG / Oops 表示当前上下文严重失效
   → panic 进入系统级终止策略

概念辨析
--------

日志缓冲区与控制台
   缓冲区保存日志记录；控制台只实时显示满足当前级别策略的部分消息。

日志级别与真实影响
   级别是调用点对严重程度的分类；真实影响还要结合返回路径、对象状态和后续行为判断。

调试调用点与实际输出
   ``pr_debug()`` 存在只说明源码提供观察点；配置、动态开关和路径执行共同决定是否产生记录。

``WARN`` 与 ``panic``
   ``WARN`` 报告异常后通常继续执行；``panic`` 启动系统级停止或重启处理。

函数符号与精确源码行
   函数名和模块是初步定位线索；精确偏移和行号依赖完全匹配的构建产物。

日志缺失与事件未发生
   没有看到日志可能来自级别过滤、限速、单次输出、缓冲区覆盖或调用点未启用，不能直接等同于事件未发生。

本章结论
--------

内核日志用于确定对象、严重程度和第一处动态路径；可靠诊断还必须回到匹配版本源码，并用其它证据补齐状态与时序。

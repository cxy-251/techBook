第166章：Kernel Command Line Parameters 与早期运行控制
========================================================

核心知识点
----------

Kernel Command Line 是用户态出现前的控制面
   Bootloader 把命令行字符串交给内核，内核在设备模型、文件系统和普通服务尚未完整建立时据此决定启动、内存、CPU、日志、安全和驱动行为。

参数语义取决于消费阶段
   同一个字符串可能由架构早期代码、``early_param``、``__setup``、核心参数框架、内建驱动或第一个用户态 ``init`` 消费。确认阶段比只确认参数值更重要。

``early_param`` 处理最早依赖
   早期控制台、内存布局和部分架构状态必须在普通初始化设施可用前确定；处理函数不能依赖尚未初始化的调度、设备模型或文件系统服务。

``__setup`` 与通用参数框架承担后续解析
   ``__setup`` 常连接传统启动处理函数，``core_param`` 和 ``module_param`` 则使用通用类型转换与参数元数据。解析成功只表示输入被接受，不保证后续初始化成功。

内建驱动参数属于启动命令行
   编译为 ``=y`` 的驱动通常通过 ``module_name.parameter=value`` 接收参数；``modprobe.d`` 只影响经用户态模块加载路径装入的 ``=m`` 驱动。

内核参数与 ``init`` 参数必须分开
   内核消费已识别参数，并按规则把剩余参数、环境变量或 ``--`` 之后内容交给第一个用户态程序。不能假设命令行中的每个词都由内核处理。

启动诊断参数只提供证据或回退
   ``earlycon``、``console=``、``loglevel=``、``initcall_debug`` 和 ``nomodeset`` 可暴露更早日志或缩短故障路径，但不会自动修复锁死、硬件故障或错误回滚。

根文件系统参数依赖完整启动链
   ``root=``、``rootfstype=``、``rootflags=``、``rdinit=`` 与 ``init=`` 只描述选择策略；设备驱动、Initramfs、文件系统和用户态程序仍必须真实存在并成功初始化。

架构与设备参数可能改变整机边界
   CPU、IOMMU、ACPI、PCI、内存、安全和具体驱动参数可改变地址空间、DMA、探测顺序与攻击面，应按目标内核、固件和硬件验证。

参数具有不同生命周期
   有些只在启动早期读取，有些在对象创建时复制，有些变量随后仍可运行时修改。能够读回变量不表示早期硬件决策可以在线重做。

``/proc/cmdline`` 只证明输入存在
   参数是否被识别、是否被裁剪、是否产生副作用以及最终对象状态，必须结合启动日志、参数处理函数和子系统运行证据判断。

安全修改依赖可启动回退项
   启动参数实验应保留已知可用 Boot Entry、串口或 BMC 入口，一次只改一个变量，并记录内核版本、Boot ID、旧值与失败恢复路径。

关键路径
--------

启动参数解析：

::

   Firmware / Bootloader 选择 Boot Entry
   → 传递 Kernel Command Line
   → 架构代码保存原始字符串
   → 解析 early_param
   → 解析 __setup / core_param / 内建 module_param
   → Initcall 与 Driver 使用已建立状态
   → 剩余参数交给用户态 init

参数生效验证：

::

   读取 /proc/cmdline
   → 定位参数注册宏与处理函数
   → 确认解析阶段、类型和返回语义
   → 搜索变量最终使用点
   → 对齐 Initcall / Probe / 运行状态
   → 用日志和对象状态证明效果

启动故障回退：

::

   保留可用 Boot Entry
   → 增加早期 Console 与必要日志
   → 单独启用一个诊断或禁用参数
   → 收集最早异常阶段
   → 恢复旧 Entry
   → 回到对应子系统寻找根因

概念辨析
--------

* ``early_param`` 与 ``module_param``：前者在极早启动阶段处理；后者属于通用内核参数框架，内建和可加载形态具有不同输入路径。
* ``earlycon`` 与 ``console=``：Early Console 服务早期输出；正式 Console 在驱动和控制台子系统建立后接管。
* 命令行存在与参数生效：``/proc/cmdline`` 证明字符串被传入，最终状态才证明目标代码真正消费并执行。
* 内建驱动与可加载模块：内建驱动从启动命令行取值；可加载模块通常从 ``modprobe``、``insmod`` 或配置文件取值。
* 临时回退与长期修复：禁用设备或特性可以定位问题，长期方案仍应修复驱动、固件、硬件或配置根因。

本章结论
--------

Kernel Command Line 是分阶段、一次启动生效的最早控制面。正确分析必须连接输入字符串、参数拥有者、解析时机和最终内核状态。

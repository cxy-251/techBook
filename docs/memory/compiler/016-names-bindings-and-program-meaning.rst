第016章：Names, Bindings, and Program Meaning
============================================

核心知识点
----------

* 名字的程序意义来自绑定关系，而不是字符拼写；同一拼写在不同位置可以指向不同实体。
* 应区分 spelling、name occurrence 与 entity：源码名字只是出现点，语义分析负责把使用点连接到声明实体。
* binding 是从名字使用点到声明点的编译期边；绑定后才能稳定取得声明类别、类型、作用域、属性与诊断位置。
* name resolution 通常先于大部分类型检查，因为类型检查首先需要知道当前名字究竟引用哪个声明。
* 名字查找依赖当前语法角色、可见声明集合、作用域规则、模块规则、成员规则以及语言特有的重载或动态派发机制。
* 遮蔽意味着内层同名声明改变普通名字查找的停止位置；成员覆盖则还需要结合接收者类型、成员查找和派发规则判断。
* 查找得到多个同等有效候选时属于歧义；编译器必须通过限定名、类型信息、重载规则或显式别名把候选收敛。

关键路径
--------

1. Parser 先构造带 ``Identifier`` / ``Name`` 节点的 AST，此时节点主要保存拼写、语法角色和源码范围。
2. 语义分析定位名字 occurrence 所在的当前作用域，并根据该语法位置确定应查找变量、函数、类型、模块还是成员。
3. 从当前作用域收集可见声明，必要时沿外层 scope、导入集合、类型成员表或语言规定的其它路径继续查找。
4. 应用遮蔽、可见性、成员访问、重载等规则筛选候选。
5. 唯一成功时把名字节点改造成 bound name，记录内部 declaration/symbol ID；无候选时报 unresolved name，多候选时报 ambiguous name。
6. 类型检查、调用检查、IR lowering 与 IDE 跳转随后直接复用该绑定，不再依赖名字字符串重新猜测目标。

概念辨析
--------

* **名字 vs 实体**：``value`` 是文本名字；局部变量、参数、函数或类型才是实体。名字必须经过绑定才能获得实体身份。
* **声明处 vs 使用处**：声明把实体放入可查找空间；使用处沿语言规则寻找并引用声明。
* **binding vs type checking**：binding 回答“它是谁”，type checking 回答“这个实体在当前操作中是否类型合法”。
* **shadowing vs overriding**：shadowing 改变词法名字查找；overriding 发生在成员层级并受动态或静态派发规则控制。
* **unresolved vs ambiguous**：前者没有合法目标，后者存在多个同等有效目标。
* **静态解析 vs 运行时派发**：编译器可以静态解析名字与候选集合，虚函数、动态成员、运行时模块等机制仍可能把最终目标选择推迟到执行期。

本章结论
--------

程序意义由名字关系图连接起来。阅读语义分析时，应始终从名字使用点出发，定位当前作用域、候选声明、筛选规则与最终 binding；只有目标实体确定后，类型检查、调用检查和代码生成才拥有稳定输入。

第002章：Source Code as a Structured System
==========================================

核心知识点
----------

* 源码首先是文本；编译器必须依次建立字符边界、token、语法结构、名字绑定、类型事实和更低层表示。
* 格式、注释和命名主要服务人类阅读；它们可能参与诊断或工具链，但不会自动成为程序执行语义。
* token 保留类别与源码位置，AST 保留语言结构，semantic facts 补充作用域和类型，IR 保留更适合执行分析的数据流与控制流。
* 源码直觉与语言语义之间可能存在 semantic gap；undefined behavior、implementation-defined behavior、ABI 和平台约束都会改变编译器可做的判断。
* 优化后的代码可以显著偏离源码形态，调试器看到的源码变量、行号和栈帧依赖 debug info 对优化后机器状态的映射。

关键路径
--------

* source bytes / characters → lexer 划分 token，并记录文件、行列和 source range。
* parser 将 token 组合为声明、表达式、语句和作用域结构；semantic analysis 再完成名字解析、类型检查和语言规则验证。
* 中端和后端根据已建立的语义事实压缩源码结构，变量可能变成 SSA value、寄存器、栈槽，也可能完全被消去。
* 分析异常优化时，先检查类型、取值范围和语言规则，再判断优化器使用的前提是否合法。
* 调试优化代码时，证据链应是：机器地址/PC → debug info → source location / variable location，而不是假设源码每行都对应固定指令。

概念辨析
--------

* **文本结构 vs 编译结构**：缩进和注释属于人类结构；token、AST、binding 和 type 才是编译器内部结构。
* **标识符名字 vs 名字绑定**：编译器不理解名字的英文含义，只关心标识符绑定到哪个声明。
* **undefined behavior vs implementation-defined behavior**：前者失去语言层面的行为约束；后者仍有实现必须文档化的具体选择。
* **源码变量 vs 运行时存储位置**：变量可能只存在为一个值关系，优化后不一定有独立内存地址。
* **源码行 vs 指令**：二者不是一一对应；优化、内联和调度都可能让多行源码共享或重排机器指令。

本章结论
--------

源码只是程序进入编译器的表层形态。可靠的编译器阅读方法是把文本、结构化语义、IR、机器代码和调试证据分层观察；先判断当前证据属于哪一层，再决定它能证明什么，避免用源码外形直接推断优化后执行行为。

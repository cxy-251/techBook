第018章：Declarations, Definitions, and Resolution
=================================================

核心知识点
----------

* declaration 向编译器引入实体记录，使名字、签名、类型或接口可以被后续阶段引用；definition 在声明基础上提供函数体、完整类型、存储、初始化器或实现。
* 前向声明解决源码线性顺序与程序依赖图之间的矛盾；编译器可以先建立实体占位记录，再在后续定义出现时补全。
* 使用点需要的信息层级不同：形成指针类型可能只需要类型声明，访问成员需要完整类型定义，调用函数通常需要声明，链接最终还需要可用实现。
* resolution 根据 AST 上下文把名字绑定到具体变量、函数、类型、模块或成员；同一拼写在不同语法位置会进入不同查找域。
* 支持重载的语言中，名字查找先得到候选集合，再根据实参类型、转换规则、模板/泛型约束等选择唯一目标。
* Bound AST 应使用稳定的 symbol/declaration ID 表示解析结果，并携带类型、声明位置、可见性和必要元数据。
* 一部分目标可以在编译期解析，一部分会因为虚派发、动态加载、反射等机制延后到运行期。

关键路径
--------

1. 第一阶段扫描声明，把类型名、函数签名、变量、模块成员等实体写入当前 symbol table。
2. 前向声明先创建“不完整”实体；后续完整定义到达时补充成员、布局、函数体、初始化器或实现状态。
3. 遍历 AST 名字使用点，根据语法角色进入变量、类型、函数或成员查找路径。
4. 普通名字从当前作用域向外解析；成员访问先解析接收者类型，再查询成员集合；调用表达式在名字查找后建立 overload candidate set。
5. 根据类型与语言规则筛选候选，得到唯一 declaration/symbol target；失败时区分未声明、歧义、签名不匹配或定义不完整。
6. 检查当前操作是否要求完整 definition；满足条件后把目标 ID 写回 Bound AST，交给类型检查、IR 生成和链接相关阶段。

概念辨析
--------

* **declaration vs definition**：declaration 证明实体存在并给出可引用接口；definition 提供当前动作需要的完整内容。
* **forward declaration vs definition**：前向声明是占位语义事实，完整定义会补全同一实体，而不是创建另一个无关实体。
* **name lookup vs overload resolution**：lookup 找到同名候选；overload resolution 在候选中依据调用上下文选出最终函数。
* **type resolution vs member resolution**：类型位置查找类型实体；成员访问先确定接收者，再在其成员命名空间中解析。
* **编译期解析 vs 链接期解析**：源码阶段可确认声明和调用签名，跨编译单元的最终符号实现可能到链接阶段才验证。
* **静态目标 vs 动态派发**：静态解析确定可调用实体或方法集合；虚函数/动态对象可能在运行时再选择具体实现。

本章结论
--------

声明、定义与解析共同把“合法语法”变成“带有明确实体边的程序”。阅读语义路径时，应先判断当前名字需要哪一级实体信息，再追踪声明收集、定义补全、候选建立、目标选择与完整性检查。

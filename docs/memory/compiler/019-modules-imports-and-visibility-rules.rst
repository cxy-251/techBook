第019章：Modules, Imports, and Visibility Rules
==============================================

核心知识点
----------

* 模块系统把局部 name resolution 扩展到大型程序，核心对象是模块身份、本地符号表、导入声明、导出集合、可见性属性、依赖边和初始化状态。
* import resolution 至少产生三个结果：目标模块身份、当前作用域中的绑定、模块之间的依赖关系。
* 名字“存在”和“当前模块可以访问”是两个不同判断；lookup 成功后通常还要执行 visibility/privacy 检查。
* public、private、internal、exported 等词语都表示访问范围，具体语义必须回到语言的 package、crate、module、assembly 或文件边界。
* 模块依赖天然形成有向图；无环区域可按依赖顺序处理，有环区域需要更细的初始化、占位或强连通分量策略。
* 循环导入的关键风险不是“有环”本身，而是在模块尚未完成初始化时读取对方尚未建立的名字或状态。
* 动态语言中常出现“模块对象已经创建并缓存，但命名空间尚未填充完整”的半初始化状态。
* 模块系统最终承担 API 边界、依赖方向、初始化时序和架构隔离，而不只是文件查找。

关键路径
--------

1. 读取模块声明或文件/包信息，建立唯一 module identity，并收集本地声明与导出集合。
2. 解析 import path，将相对路径或短名规范化为目标模块身份。
3. 定位或加载目标模块记录，检查请求的名字是否存在于目标模块可导出的接口中。
4. visibility 检查通过后，把目标 symbol 绑定到当前模块的本地作用域，并建立 ``current -> target`` 依赖边。
5. 基于依赖图安排解析、编译或初始化顺序；遇到环时识别强连通区域并维护“已创建、正在初始化、已初始化”等状态。
6. 动态加载过程中，只有目标导出实际完成初始化后，读取该名字才安全；否则可能得到缺失、未初始化或部分状态错误。

概念辨析
--------

* **module vs file**：模块是名字与可见性边界；文件只是常见承载方式，一个模块不一定严格等于一个文件。
* **import vs local binding**：import 先解析目标模块和导出，再决定哪些名字进入当前 scope；导入行为和本地绑定是两个步骤。
* **存在 vs 可见**：symbol table 中能找到实体，不代表当前模块有权使用它。
* **public/exported vs internal/private**：前者形成外部接口，后者把实现细节限制在更小范围，允许内部演化。
* **dependency graph vs initialization order**：图描述依赖事实；初始化顺序是系统基于这些事实选择的执行策略。
* **cycle vs partial initialization**：环是结构事实，真正的运行时失败通常来自环中某个模块过早读取尚未初始化的绑定。

本章结论
--------

模块系统把名字解析提升为工程架构约束。分析模块问题时，应依次确认模块身份、导出集合、导入绑定、可见性、依赖图和初始化状态；循环导入尤其要追踪“名字何时真正可用”，而不是只看依赖图里是否存在环。

第023章：Type Checking Expressions, Statements, and Functions
==============================================================

核心知识点
----------

* 类型检查以完成名字绑定的 AST 为输入，为表达式计算类型，并用语句和函数上下文验证这些类型是否满足语言规则。
* 表达式检查的稳定模型是：输入类型 + 节点规则 → 结果类型；字段访问、索引、运算符和函数调用都遵循这一模式。
* 类型综合从表达式内部推出结果类型；按期望类型检查则从上下文给出目标类型，再验证表达式能否放入该位置。
* ``return`` 把局部表达式接到函数返回契约；函数体内所有返回路径都必须满足声明的返回类型规则。
* ``if``、``while`` 等语句给条件表达式施加条件类型约束，并可能在分支中形成更精确的局部类型事实。
* 变量声明和赋值同时涉及目标类型、右侧表达式类型、兼容性规则与左侧可写性。
* 函数调用需要验证被调用对象是否可调用、实参数量、实参与形参兼容性，并产生调用结果类型。
* 子类型、结构兼容、隐式转换和显式 cast 都是“一个值能否进入目标位置”的不同机制，必须由语言规则明确区分。
* 错误类型或 invalid 类型可作为占位符，使局部类型失败后仍能继续检查外层结构，减少级联诊断。

关键路径
--------

``绑定后的 AST → 建立类型环境 → 自底向上检查表达式 → 把结果类型送入语句上下文 → 检查函数参数与返回契约 → 统一执行兼容性/转换规则 → 生成带类型 AST 或诊断``。

表达式节点应依次检查子节点、查询当前操作规则、得到结果类型并记录到节点上。调用节点应先解析 callee 类型，再逐个检查实参与形参，最后得到返回类型。函数体检查还需要维护当前返回类型、循环上下文和路径相关类型环境。

概念辨析
--------

* **类型综合 vs 按期望类型检查**：前者从表达式推出类型，后者从上下文要求验证表达式；实际 checker 常双向使用。
* **赋值兼容 vs 类型相同**：很多语言允许子类型、结构兼容或规定好的转换，因此可赋值不要求类型文本完全相同。
* **隐式转换 vs 显式 cast**：隐式转换由语言自动插入；显式 cast 是源码中的转换请求，编译器仍要检查其合法方向与风险边界。
* **表达式类型错误 vs 语句上下文错误**：前者发生在操作本身，例如不支持的二元运算；后者发生在表达式放入 ``return``、条件或赋值位置时不满足上下文契约。
* **错误类型 vs 正常类型**：错误类型是诊断恢复工具，表示当前位置已失败，不应被当作真实程序类型继续推导语义结论。

本章结论
--------

稳定的类型检查顺序是：先建立环境，再检查表达式，再把表达式结果放入语句上下文，最后用函数签名统一收束参数、返回和调用边界。所有兼容性和转换都应通过明确规则，而不是在各节点中散落特殊判断。

第001章：Compiler Transformation Model
=====================================

核心知识点
----------

* 编译器的稳定处理对象不是源码外形，而是程序语义；变量名、排版、局部表达式和最终指令都可以变化。
* 编译过程由多层表示组成：source text → token → AST/semantic facts → IR → optimized IR → machine representation → executable behavior。
* translation 强调跨表示翻译，transformation 强调在同层或相近表示中保持语义地改写。
* frontend 负责语言结构、名字、类型与诊断；middle-end 负责分析与优化；backend 负责 ISA、寄存器、ABI 和目标文件约束；runtime 承担执行期支持。
* 编译正确性的核心是 semantic preservation：每一步转换都必须保持语言规定的可观察行为。

关键路径
--------

* 源码进入前端后，先建立 token、语法结构、名字绑定和类型事实。
* 前端把语言结构降低到 IR，中端围绕控制流、数据流、别名、常量和副作用执行 analysis / transformation pass。
* 后端把 IR 约束到具体机器：指令选择 → 寄存器分配 → 调用约定 → 栈帧 → object file / machine code。
* 排查编译结果时固定追踪：当前表示 → 输入语义事实 → 本次转换新增约束 → 必须保持的不变量 → 输出证据。
* 若优化后行为异常，应寻找“最早出现语义不一致”的表示层，而不是只比较源码和最终汇编。

概念辨析
--------

* **源码文本 vs 程序语义**：源码是输入材料；语义才是编译器必须保持的契约。
* **程序语义 vs 可执行行为**：前者由语言规则定义，后者是在目标机器、ABI 和运行时约束下实现这些规则。
* **translation vs transformation**：前者改变表示语言，后者改写当前表示；真实编译管线通常交错使用二者。
* **frontend / middle-end / backend / runtime**：这是责任边界，不是所有编译器都必须按四个物理模块实现。
* **源码形态变化 vs miscompilation**：变量、分支或表达式消失并不代表错误；可观察语义被破坏才是编译错误。

本章结论
--------

编译器应被理解为连续的语义保持转换系统。阅读源码、IR、汇编或运行时现象时，先定位当前表示层，再追踪该层拥有的事实和约束；只要这条路径清楚，编译器的大多数分析、优化和后端行为都能落到“表示发生了什么变化、为什么仍然合法”这一核心问题上。

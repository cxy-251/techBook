第025章：Type Inference and Constraint Solving
==============================================

核心知识点
----------

* 类型推导的目标是在源码省略部分类型标注时，仍为表达式、绑定点和调用点恢复可验证的类型事实。
* 编译器通常把未知类型表示成显式类型变量，而不是保留为模糊的“待确定状态”。
* 类型规则会持续生成约束：字面量固定基础类型，条件要求布尔条件和分支汇合，调用把实参类型送入形参位置，操作符规定操作数和结果关系。
* 局部推导只依赖附近表达式和声明，成本低、诊断稳定；跨函数或跨模块的全局推导能力更强，但约束图和错误传播范围更大。
* 上下文类型把信息从目标位置向表达式内部传播，例如赋值目标、函数参数位置和返回位置可以帮助推导匿名函数参数或字面量类型。
* 约束求解的核心对象是类型变量、类型关系和统一；统一把两个类型表达式合并，并把结果继续传播到整个约束图。
* 泛型绑定会先得到最一般类型方案，再在每个使用点实例化成具体类型关系。
* occurs check 用来阻止普通类型系统把类型变量统一成包含自身的无限类型，除非语言显式支持递归类型。
* 推导失败常见于信息不足、约束冲突、候选不唯一和泛型参数缺少证据；诊断应尽量回溯到最小冲突来源。
* 求解后的类型事实需要写回 typed AST、HIR 或其它语义表示，供重载选择、泛型实例化、IR lowering 和后续分析复用。

关键路径
--------

``完成名字绑定的 AST → 为缺失类型创建类型变量 → 从声明/字面量/操作符/调用/上下文生成约束 → 合并约束 → 统一与求解 → 检查 occurs/冲突/歧义 → 写回具体类型或泛型类型方案 → 生成诊断或带类型表示``。

调用点应先实例化被调用对象的泛型类型方案，再把每个实参类型与对应形参建立约束，求解后得到调用结果类型。若外层还有目标类型，则继续把调用结果与目标类型统一。

概念辨析
--------

* **类型推导 vs 类型检查**：推导负责补齐未知类型，检查负责验证最终类型关系是否符合语言规则；两者通常交织执行。
* **局部推导 vs 全局推导**：区别在于类型事实传播范围，而不是推导算法是否“智能”。
* **类型变量 vs 泛型类型参数**：类型变量是求解器中的未知项；泛型参数是程序声明中的类型抽象，求解后可能形成可复用类型方案。
* **统一 vs 类型相等文本比较**：统一会递归处理函数、列表、元组等类型结构，并产生新的变量绑定关系。
* **信息不足 vs 约束冲突**：前者存在多个可能解或没有足够证据，后者是同一类型变量被要求同时满足不兼容类型。
* **上下文类型 vs 自底向上推导**：前者从目标位置向内传递期待类型，后者从表达式自身向外产生类型事实。

本章结论
--------

类型推导本质上是约束求解。稳定的阅读和排查顺序是：先找未知类型变量，再列出每条语法和调用规则产生的约束，随后观察统一怎样传播事实，最后判断失败属于证据不足、冲突、歧义还是泛型实例化缺失。

第065章：Background Process Reclamation
======================================

核心知识点
----------

* 后台进程回收的目的，是把有限内存、CPU、电量和热预算优先交给当前用户可见任务，同时把后台进程视为可丢弃的性能缓存。
* App 退到后台后，系统会降低进程重要性；资源压力低时保留进程以加速返回，压力高时终止低优先级执行容器。
* 系统回收的是进程和内存，不是用户任务本身。用户任务能否延续，取决于 App 是否把草稿、导航、未提交操作和恢复入口保存到进程外。
* Android 通过组件状态、进程重要性、``oom_score_adj`` 等信息和 ``lmkd`` 的内存压力判断完成回收；cached process 是主要候选。
* Apple 中 suspended App 仍占用内存但不执行普通代码，系统可在内存压力下直接终止；具体 Jetsam 排序属于平台内部策略。
* Foreground service、长期音频、导航定位等系统认可任务可以提高后台进程保护等级，但不构成永久存活保证。
* 大内存缓存会同时提高短期恢复速度和长期被回收概率，App 必须在缓存收益与系统驻留成本之间取舍。
* 可靠后台架构应把关键操作写入持久化队列，并保证进程被杀后可以重新调度或幂等恢复。

关键路径
--------

用户离开 App
→ Activity / Scene 不再可见
→ Framework 降低进程重要性
→ 系统评估前台任务、后台任务语义与内存压力
→ 压力低：保留 cached / suspended process 作为恢复缓存
→ 压力高：选择低优先级进程
→ 终止进程并释放匿名内存、缓存和运行时对象
→ 系统清理相关进程记录与 IPC 关系
→ 用户再次进入 App
→ 系统重新创建进程
→ App 从 saved state、数据库、文件和任务记录恢复用户工作。

概念辨析
--------

``Process retention`` 与 ``State durability``：保留进程只是性能优化；持久化状态才是用户任务跨回收的可靠基础。

``Cached process`` 与 ``Background task``：cached process 没有强执行价值；后台任务只有进入系统认可的调度入口才具备继续运行的语义。

``LMKD / Jetsam`` 与 ``Lifecycle``：回收执行发生在低层，但目标优先级主要来自高层生命周期和任务重要性。

``Large cache`` 与 ``Fast resume``：大缓存可能加快短期恢复，同时增加内存压力和被系统回收的风险。

本章结论
--------

后台进程是移动 OS 可主动回收的缓存资源。App 必须假设后台进程随时可能消失，把用户任务状态和可靠后台工作从进程内存中分离出来，才能同时适应 Android 的 cached process 回收和 Apple 的 suspended App 终止。

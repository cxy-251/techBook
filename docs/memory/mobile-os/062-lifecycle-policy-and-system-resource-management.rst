第062章：Lifecycle Policy and System Resource Management
========================================================

核心知识点
----------

* Lifecycle Policy 是系统根据 App 可见性、用户意图、授权状态和资源压力，对 CPU、内存、网络、定位、音频等资源实施分级治理的策略集合。
* 生命周期状态不会对整个 App 一刀切；不同资源有不同后台规则。导航可继续定位和播报，普通 UI 刷新和任意轮询通常会被停止或延后。
* Foreground priority 保护用户正在感知的任务，包括输入、动画、音视频、导航、通话和其它实时交互。
* Background work 应通过 WorkManager、JobScheduler、BackgroundTasks、后台传输、push、alarm 等平台入口表达，让系统拥有调度权。
* 内存保留只是性能优化；系统可以依据进程重要性和内存压力回收后台执行容器。
* 生命周期回调必须与状态持久化结合。关键业务状态不能等到“即将终止”才保存，因为进程可能没有最后清理机会。
* 系统资源策略同时受电池、网络、温控、隐私和用户设置影响，因此“有权限”不等于“当前一定能持续使用资源”。
* 移动 App 架构天然需要任务拆分、幂等重试、状态持久化和可恢复设计。

关键路径
--------

用户发起任务
→ Framework 将任务表达为前台交互、持续用户任务或可延迟后台工作
→ System Service 记录调用者、生命周期与任务类型
→ 策略层检查权限、前后台状态、电量、网络、温度和内存压力
→ 用户可见任务获得受保护资源窗口
→ 可延迟任务进入系统调度队列
→ 不再有执行理由的进程进入缓存或回收候选
→ 条件满足时系统重新唤醒后台任务
→ 进程被回收后由持久化状态和幂等任务记录完成恢复。

概念辨析
--------

``Lifecycle state`` 与 ``Resource availability``：生命周期只提供重要输入；资源是否可用还取决于任务语义、权限、电源、网络和系统策略。

``Background thread`` 与 ``Background task``：线程只是进程内执行对象；只有平台认可的后台任务入口才能让系统在 App 离开前台后继续调度工作。

``Memory retained`` 与 ``State persisted``：后台进程仍在内存中只代表暂时缓存；持久化状态才具备跨进程死亡的恢复能力。

``Foreground service / background mode`` 与 ``Permanent keep-alive``：前者是特定用户可见任务的受控例外，不是让 App 永久常驻的通用机制。

本章结论
--------

生命周期策略的本质是把用户价值转换成资源预算。App 应把实时用户任务、可延迟后台任务和可恢复状态分开设计，让系统服务负责资源调度，让持久化层负责跨进程连续性。

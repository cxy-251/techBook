The Web as a Standardized, Multi-Vendor Platform
=================================================

核心知识点
----------

* Web 是由标准契约、多个浏览器实现、服务器、网络协议、测试体系和历史内容共同维持的多厂商平台，不等于某个浏览器或框架。
* 标准规定对象、状态、算法与错误语义；浏览器实现决定当前真实行为；跨浏览器测试和兼容性数据负责检验两者是否收敛。
* 多厂商压力使新能力必须同时考虑实现意愿、互操作性、安全、隐私、设备资源与兼容成本。
* Web 必须长期保存既有内容和 URL 的可访问性，因此旧行为很难被直接删除，平台演化天然携带兼容负担。
* Framework 是平台契约上的包装层。判断框架能力时，应先还原其落点：browser、server、edge、build time、HTTP、cache、storage 或 permission boundary。
* 一个能力进入生产路径的证据至少包括：规范语义明确、目标浏览器实现可用、跨实现行为足够一致、失败路径可恢复。

关键路径
--------

核心阅读路径是：

``User Intent → Page Code → Web Platform Contract → Browser Implementation → Runtime Behavior → User-visible Result``

以一次结账请求为例：

``URL navigation → HTML document → DOM event → ECMAScript callback → Fetch → HTTP → server session → response → DOM update``

定位新平台能力时按以下顺序：

``能力对象 → 标准契约 → 浏览器支持 → 安全/权限条件 → 失败与 fallback → 框架封装``

概念辨析
--------

* **标准 vs 实现**：标准说明“应该怎样”；浏览器实现说明“现在实际上怎样”。生产判断必须同时看两者。
* **平台能力 vs 框架能力**：框架可以改变 API 形状和代码组织方式，不能改变 HTTP、DOM、浏览器安全模型等底层契约。
* **规范存在 vs 可生产使用**：有规范不代表已经跨浏览器稳定；还要看实现、测试、兼容数据和目标用户环境。
* **兼容历史 vs 技术落后**：保留历史行为是开放 Web 的平台约束，它换取旧内容持续可访问。
* **多厂商平台 vs 单一运行时**：Web 的架构决策必须容纳多个独立实现，因此互操作性本身就是系统设计条件。

本章结论
--------

现代 Web 的稳定基础不是某个框架，而是标准化契约在多个独立实现中的长期收敛。分析任何 Web 行为时，应先确定它依赖哪个平台对象和标准边界，再检查目标浏览器的真实实现、兼容证据和恢复路径；框架只应作为这些边界上的组织与优化工具。

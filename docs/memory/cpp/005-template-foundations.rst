第005章：Template Foundations
=============================

核心知识点
----------

模板定义描述一组潜在实体，具体模板实参进入后才形成特化。``vector<int>``、``vector<string>`` 是同一个类模板的不同特化类型；函数模板调用则经历名字查找、模板参数推导/替换、重载决议和需要时的实例化。

类型模板参数决定类型维度；非类型模板参数把值放入类型身份，例如 ``array<int, 4>`` 与 ``array<int, 8>`` 是不同类型。非类型参数让长度、extent 等信息在编译期传播。

实例化具有延迟性。类模板形成某个特化，不代表所有成员函数体都立即实例化；依赖模板参数的成员通常在真正使用时才暴露约束和错误。这是 STL 模板报错常沿调用栈延迟出现的根源。

模板参数推导依据函数形参模式和调用实参进行匹配。推导阶段要求同一个模板参数得到一致结果；普通隐式转换通常发生在模板实参已经确定之后，而不是用来“帮助”冲突的推导结果。

可变参数模板通过参数包表达任意数量的类型和值。``Args&&...`` 配合 ``std::forward<Args>(args)...`` 是 emplace 家族保留参数类型和值类别的核心机制。

全特化为一组完整模板实参提供专门实现；类模板/变量模板可以偏特化；函数模板通常通过重载、约束或 tag dispatch 表达不同实现路径。

依赖名查找具有两阶段特征。模板定义阶段可确定的非依赖名字先查找；依赖模板参数的名字需要等实例化时结合具体实参继续解析。``typename``、``template`` 关键字用于消除某些依赖名语法歧义。

关键路径
--------

函数模板调用的主路径是：

``查找模板名 → 从实参推导模板参数/读取显式参数 → 替换模板参数 → 形成候选特化 → 约束/SFINAE/可行性检查 → 重载决议 → 实例化所需函数体 → 生成具体代码``。

类模板的主路径是：

``模板定义 → 给出 T/N 等实参 → 形成具体类型特化 → 当前上下文若需要完整类型则实例化必要布局 → 某成员真正被使用时实例化对应定义``。

完美转发的模板路径是：

``调用实参 value category → 推导 Args → forwarding reference 绑定 → 形参名在函数体中是 lvalue → forward<Args> 恢复原类别 → 目标构造函数/重载接收``。

STL traits 的典型路径是：

``泛型算法得到类型 T → 查询 trait/concept → 编译期得到能力或属性 → 选择实现/拒绝不满足约束的调用 → 生成针对 T 的具体路径``。

因此阅读 STL 模板源码时先找模板参数，再找 traits/concept，再看分派方式，最后检查实例化点与错误出现在哪一层。

概念辨析
--------

``模板`` 不等于一个统一的运行时对象或函数。模板主要是编译期生成规则；真正参与对象布局和机器代码生成的是具体特化。

``模板参数推导`` 不等于普通隐式转换。若两个函数实参分别推导出 ``T=int`` 与 ``T=double``，推导会冲突；显式固定 ``T=double`` 后，普通参数转换才可能处理 ``int`` 到 ``double``。

``T&&`` 不总是普通右值引用。模板推导语境中的 forwarding reference 会根据调用实参折叠成左值引用或右值引用，并借助 ``std::forward`` 保留原 value category。

``特化`` 与 ``重载`` 不同。特化是在模板家族内部为实参模式选择定义；重载是在多个函数候选之间做重载决议。函数模板没有类模板那样的偏特化机制。

``constexpr`` 不代表函数一定在编译期执行。它表示满足常量表达式条件时可以参与编译期求值；相同函数也可以在运行时调用。

``inline`` 的核心工程边界不是“保证内联优化”，而是支持实体在多个翻译单元中的定义规则；模板和许多 constexpr 实体因此适合放在头文件中。

本章结论
--------

STL 的泛型能力建立在“模板参数 → 推导/替换 → 依赖名查找 → traits/约束 → 实例化 → 具体代码”这条编译期路径上。阅读模板源码时不要从最终长错误信息倒推；先定位当前是定义阶段、推导阶段、替换阶段、重载阶段还是成员实例化阶段，问题通常会迅速收敛。

第047章：Constexpr STL
======================

核心知识点
----------

* ``constexpr STL`` 表示标准库对象和算法能够进入常量求值；前提是语言规则、标准库接口、元素操作和调用上下文同时允许编译期执行。
* ``constexpr`` 函数只是“可以”在编译期执行；只有结果进入 ``constexpr`` 变量、``static_assert``、模板实参等常量表达式上下文时，调用才被强制常量求值。``consteval`` 则要求每次调用都在编译期完成。
* ``std::array`` 等固定存储对象天然适合长期保存编译期结果；``std::vector``、``std::string`` 等动态容器更适合作为常量求值内部的临时工作区。
* C++20 允许常量求值期间进行受控动态分配，但动态存储必须在同一次常量求值结束前释放；因此通常不能把持有该动态存储的 ``vector`` 直接保存为长期 ``constexpr`` 对象。
* ``constexpr`` algorithm 仍保持原有算法契约和复杂度，例如 ``sort`` 仍要求随机访问和可排序关系，``binary_search`` 仍要求输入区间已经有序。
* 元素类型的构造、移动、比较、赋值和析构路径也必须能进入常量求值；自定义 allocator 或运行期资源会成为额外边界。
* 编译期执行不会消除成本，只是把工作转移到构建阶段。大规模排序、搜索和表生成会增加编译时间与常量求值资源消耗。
* ``static_assert`` 配合 STL 算法适合把排序、去重、范围合法性和协议表一致性变成构建期约束。
* 标准版本不能只看编译参数；``__cpp_lib_constexpr_vector``、``__cpp_lib_constexpr_algorithms`` 等 feature-test macro 更能反映实际标准库能力。

关键路径
--------

1. 先确认目标编译器和标准库版本，并检查对应 feature-test macro。
2. 确认容器成员函数、iterator 操作、算法和 callable 都具备 ``constexpr`` 支持。
3. 判断调用点是否真正要求常量表达式；需要强制时使用 ``constexpr`` 对象、``static_assert`` 或 ``consteval`` 入口。
4. 检查元素类型的构造、移动、比较、赋值和析构是否都能在常量求值中执行。
5. 若使用 ``vector`` / ``string`` 等动态容器，把它们限制在同一次常量求值内部，并保证动态存储在结束前释放。
6. 将最终结果转成 ``array``、聚合对象、tuple 或其他固定存储形式，再作为长期编译期常量保存。
7. 最后评估编译时间；规模大或输入本质上来自运行期的数据应留在运行期处理。

概念辨析
--------

* **constexpr 函数与常量求值**：前者提供资格，后者由调用上下文决定是否真的发生在编译期。
* **constexpr 与 consteval**：``constexpr`` 可编译期也可运行期；``consteval`` 调用必须形成常量表达式。
* **固定容器与动态容器**：``array`` 的数据属于对象自身；``vector`` 的元素通常依赖动态存储，长期编译期保存受到更严格限制。
* **编译期算法与运行期算法**：算法契约和复杂度不变，只是执行阶段不同。
* **动态分配允许与动态所有权持久化**：C++20 允许常量求值中的瞬时分配，不代表任意动态存储都能逃逸为长期 constexpr 状态。
* **标准模式与库实现能力**：启用 C++20/23 只给出语言和标准目标，实际可用接口仍应通过标准库版本和 feature-test macro 验证。

本章结论
--------

Constexpr STL 的判断顺序是“版本能力 -> 调用上下文 -> 元素与算法资格 -> 动态存储闭合 -> 输出形态 -> 编译成本”。最稳定的模式是用动态容器和算法作为编译期临时工作区，把最终结果固化到固定存储对象中，再用 ``static_assert`` 或常量表消费结果。

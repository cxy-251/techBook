第057章：Container Selection Principles
======================================

核心知识点
----------

* 容器选型先看工作负载，不先看容器名字：顺序扫描、随机访问、尾部追加、双端流动、中间修改、按 key 精确查找、范围查询、稳定地址是不同问题。
* ``vector`` 是批量拥有、顺序扫描、随机访问和尾部增长的默认强候选；扩容会搬迁元素，外部长期保存元素地址时要特别谨慎。
* ``deque`` 适合双端增长并保留随机访问；``list`` 适合已知位置附近频繁插入删除且重视 iterator/reference 稳定性；``array`` 适合容量属于类型契约的固定大小对象。
* ``unordered_map/set`` 适合精确键查找；``map/set`` 适合有序遍历、lower/upper_bound、范围查询和邻近键语义。
* ``stack``、``queue``、``priority_queue`` 的价值是主动收窄接口，把允许的访问顺序写进类型，而不是获得一种新的底层存储。
* ``string_view``、``span`` 和 ranges view 是非拥有观察层；选择它们前必须确认源对象生命周期、连续性和修改失效规则。
* 一个容器不必同时承担所有需求。工程上常用“主体存储 + 辅助索引”，例如 ``vector<Event>`` 负责拥有和扫描，``unordered_map<id,index>`` 负责精确查询，``map<time,index>`` 负责范围查询。
* 主存储可能搬迁时，辅助结构保存 index、id 或稳定句柄通常比保存 ``T*`` 更容易维护。

关键路径
--------

业务需求 → 列出主操作及频率 → 判断是否要求顺序/范围语义 → 判断是否要求连续存储或稳定地址 → 判断增长发生在末尾、两端还是中间 → 判断是否需要 key lookup → 选择主体容器 → 必要时增加辅助索引 → 校验失效规则与测量结果。

典型组合是：``vector`` 保存实体，``unordered_map`` 保存 id 到下标，``map`` 保存有序时间到下标，``deque/queue`` 保存待处理下标，``priority_queue`` 保存 deadline。每个结构只负责自己擅长的访问模式。

概念辨析
--------

* **容器类别 vs 业务语义**：sequence/associative/unordered 只是分类入口；真正决定选型的是操作比例和稳定性要求。
* **地址稳定 vs 下标稳定**：``vector`` 扩容会改变地址，但只追加不做中间 erase 时，既有元素下标仍可保持业务意义。
* **ordered vs unordered**：有序容器交付顺序、范围和邻近关系；哈希容器交付平均快速精确查询，不能自然替代范围语义。
* **拥有容器 vs view**：容器管理元素生命周期；view 只描述可见范围或转换规则，不能替代拥有者。
* **一个万能容器 vs 多结构协作**：强行让一个结构承担扫描、查询、排序和队列语义通常会牺牲主路径；辅助索引是常见工程解法。

本章结论
--------

容器选型的稳定方法是把业务访问模式拆开：先确定谁拥有数据，再确定主遍历方式、增长方式、键查询方式和稳定性要求。默认从简单连续结构出发，只有明确证据证明其它语义更重要时，再选择分段、节点、有序或哈希结构。

第046章：PMR
============

核心知识点
----------

* PMR（Polymorphic Memory Resource）把 STL 的内存策略从 allocator 模板类型转成运行时 ``memory_resource`` 对象；``std::pmr::vector<T>`` 等容器的静态类型不因资源实现不同而改变。
* ``std::pmr::polymorphic_allocator<T>`` 持有 ``memory_resource*``，容器通过 allocator 请求原始存储，资源对象决定内存来自本地缓冲、池、上游资源还是普通 ``new/delete``。
* 容器负责元素构造、移动和析构，``memory_resource`` 负责原始内存分配与回收；对象生命周期和存储生命周期必须分开判断。
* ``monotonic_buffer_resource`` 适合阶段性批量构建：分配持续向前推进，单次 deallocate 通常不真正释放，最终由 ``release()`` 或资源析构统一回收。
* ``unsynchronized_pool_resource`` / ``synchronized_pool_resource`` 适合大小集中且分配释放交错的对象；前者无共享线程安全开销，后者用于同一资源被多线程共同访问的场景。
* PMR 容器和嵌套 PMR 对象必须明确资源来源。容器类型相同并不意味着资源相同，应通过 ``get_allocator().resource()`` 追踪运行时资源关系。
* 资源对象必须比所有依赖它的容器及元素活得更久；资源先销毁会让后续扩容、清空、析构或赋值访问悬垂资源指针。
* PMR 的拷贝、移动、交换不能只按普通容器理解，还要检查 allocator/resource 传播边界，尤其是跨函数、模块或线程返回对象时。
* 默认资源是全局运行时配置入口；局部性能设计更适合显式传递资源，使资源生命周期和作用范围可见。

关键路径
--------

1. 找到 ``memory_resource`` 的创建位置和拥有者，确认它的生命周期边界。
2. 沿 ``pmr container -> polymorphic_allocator -> memory_resource`` 追踪每次分配实际进入哪个资源。
3. 对嵌套 ``pmr::vector<pmr::string>`` 等结构，继续检查元素内部是否也绑定期望资源。
4. 对阶段性一次构建、整体销毁的工作区优先考虑 ``monotonic_buffer_resource``，并保证对象先析构、再 ``release()``。
5. 对尺寸集中的频繁分配/归还场景考虑 pool resource，并根据资源是否共享选择同步或非同步版本。
6. 在拷贝、移动、交换和函数返回处检查源资源与目标资源是否一致，以及目标资源是否继续存活。
7. 最后再根据分配次数、大小分布、碎片、锁和峰值内存决定是否值得采用 PMR。

概念辨析
--------

* **allocator 与 memory_resource**：allocator 是容器使用的分配接口对象；PMR allocator 内部再把请求转发给运行时 ``memory_resource``。
* **元素生命周期与存储生命周期**：元素析构负责结束对象生命；资源回收只处理原始存储，两者不能用 ``release()`` 相互替代。
* **monotonic 与 pool**：前者用统一阶段释放换取短分配路径；后者维护可复用空闲块，适合局部释放后再次分配。
* **unsynchronized 与 synchronized pool**：区别在同一资源对象的并发访问保证，不在容器本身是否会跨线程。
* **PMR 类型一致与资源一致**：两个 ``pmr::vector<T>`` 可以是完全相同的 C++ 类型，却绑定不同运行时资源。
* **默认资源与显式资源**：默认资源提供全局入口；显式资源更利于局部生命周期、性能和跨模块契约审查。

本章结论
--------

PMR 的核心不是“更快的 allocator”，而是把内存策略变成运行时可注入资源。分析顺序应固定为“对象阶段 -> 分配/释放模式 -> 资源类型 -> 资源生命周期 -> 传播边界”。性能收益只有在资源模型与对象生命周期匹配时才成立；资源寿命和跨资源移动、复制、交换是更优先的正确性条件。

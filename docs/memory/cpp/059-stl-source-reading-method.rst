第059章：STL Source Reading Method
=================================

核心知识点
----------

* 读 STL 源码要把标准承诺和实现手段分开。标准规定接口语义、复杂度、异常保证与失效规则；libstdc++、libc++、MSVC STL 只是在不同目录、命名和 ABI 约束下实现这些要求。
* 源码阅读从用户可见调用进入：容器成员函数、算法、iterator、allocator traits、iterator traits 是稳定入口；不要从整个头文件顶端顺序阅读。
* 先固定当前具体类型和负载，再把模板参数替换成实际角色，可显著降低 ``_Tp``、``_Alloc``、``_Iter``、宏和 traits 带来的噪声。
* traits 通常负责能力查询和接口适配；真正改变对象状态的是 allocate/construct/move/destroy/deallocate、指针重连、bucket 重建、iterator 推进和 comparator 调用。
* 读容器修改操作时先找提交点：容量是否足够、何时申请新存储、构造成功数量如何记录、失败如何回滚、最后何时替换容器状态。
* 读算法时先恢复半开区间不变量，再看 iterator 能力、谓词/比较器调用和区间收缩方式；helper 名称不是核心，状态变化才是核心。
* 实现宏应按用途归类：constexpr/标准版本、调试 iterator、sanitizer、ABI/可见性、平台属性。核心路径未读通前可先折叠非状态性宏。
* 最终要画出短调用链，并把源码观察转成工程结论：复杂度、分配次数、失效范围、异常安全和类型约束。

关键路径
--------

公开 API → 查标准语义 → 定位当前实现入口 → 固定实际模板实参 → 找容器/算法核心状态 → 只跟踪改变状态的 helper → 必要时展开 allocator/iterator traits → 标记提交点与失败路径 → 回到调用点总结复杂度、失效和生命周期。

例如 ``vector::push_back`` 的核心链通常可压成：检查 ``end != cap`` → 有空间则在尾部 construct 并推进 end；无空间则 allocate 新缓冲 → 迁移旧元素 → 构造新元素 → 回滚或提交 → destroy/deallocate 旧存储。

概念辨析
--------

* **标准接口 vs 内部符号**：``std::vector`` 的语义可迁移；``_M_*``、``__*``、``_*`` 等内部名字只属于某个实现版本。
* **traits 层 vs 状态层**：traits 告诉实现“类型能做什么”；容器指针、节点、bucket、对象生命周期才是运行时状态。
* **模板噪声 vs 主路径**：泛型分支为了覆盖所有类型存在；当前调用只走其中很少一部分，应先具体化再阅读。
* **函数调用链 vs 文件调用链**：阅读目标不是把 include 文件全部展开，而是追踪一个接口现象到最终状态变化。
* **源码事实 vs 工程结论**：看到增长策略或 helper 只是实现事实；需要继续推导它对分配、失效、异常和性能意味着什么。

本章结论
--------

STL 源码阅读应始终以“当前调用改变了什么状态”为中心。先用标准语义确定目标，再在实际实现中定位最短执行路径，过滤模板和宏噪声，最后把调用链压缩成对象、内存、iterator 与算法的不变量。

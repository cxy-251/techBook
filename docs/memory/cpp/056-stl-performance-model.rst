第056章：STL Performance Model
=============================

核心知识点
----------

* STL 性能判断不能停在大 O；还要同时看内存布局、cache locality、分配次数、对象迁移、分支行为和 iterator/reference/pointer 失效。
* ``vector`` 的连续存储适合批量扫描，扩容成本集中在重新分配与元素迁移；``list`` 的局部插入删除稳定，但节点跳转、独立分配和 cache miss 成本高。
* ``deque`` 是分段连续存储，双端操作稳定且支持随机访问；扫描局部性通常介于 ``vector`` 与节点容器之间。
* ``map/set`` 的对数查找不代表机器时间一定优于排序后的 ``vector + lower_bound``；节点跳转、比较次数和缓存行为必须一起测量。
* ``unordered_*`` 的平均常数复杂度依赖哈希分布、bucket 数量和 load factor；rehash 会带来结构重建和 iterator 失效。
* ``reserve``、合理增长策略和 ``noexcept`` move 能显著影响 ``vector`` 的迁移成本；元素内部资源如 ``string`` 还可能引入额外分配。
* 性能优化应以真实工作负载为单位：构建、查询、扫描、更新、清理要分阶段测量，而不是只比较容器 API 的理论复杂度。

关键路径
--------

业务操作 → 确定主访问模式 → 查询标准复杂度与失效规则 → 展开常见存储形状 → 统计分配/迁移/比较/指针跳转 → 判断 cache 与分支行为 → benchmark / profiler 验证 → 再决定容器或数据布局。

对追加后反复扫描的负载，常见优先路径是 ``vector``；若还需按 key 查询，可让连续主存储负责扫描，再建立 ``unordered_map<key, index>`` 等辅助索引。索引保存下标或稳定句柄通常比保存元素地址更能承受 ``vector`` 扩容。

概念辨析
--------

* **复杂度 vs 实际时间**：复杂度描述规模增长阶；cache miss、分配器、对象大小和分支预测决定大量常数成本。
* **连续存储 vs 节点稳定性**：连续布局提升扫描局部性；节点布局换取局部插入删除和地址稳定，二者不是同一优化目标。
* **move vs 零成本迁移**：move 只是调用移动构造/赋值；其真实成本由元素类型决定，且非 ``noexcept`` move 可能让容器选择 copy 以维持异常保证。
* **平均 O(1) vs 固定 O(1)**：哈希查找是平均常数，不等于所有输入、所有负载因子下固定成本。
* **benchmark vs 直觉**：源码和复杂度用于建立假设，最终工程选择要由真实数据规模、访问比例和硬件计数器验证。

本章结论
--------

STL 性能模型的稳定读法是：先看业务访问模式，再看容器布局和对象生命周期，再追踪分配、迁移、失效、cache 与分支，最后用测量闭环。容器没有脱离工作负载的绝对快慢。

学习内容架构
============

``techBook`` 将技术学习拆成知识范围、路径、学习单元、事实证据、评估和状态六类内容。它们都服务于直接阅读，不依赖构建系统。

知识范围
--------

``aiBook`` 的 Roadmap、Roadmap 配套规范和文章生成控制文件记录用户希望获得的知识。它们决定需要覆盖什么，不直接决定章节数量、顺序和篇幅。

旧 ``aiBook/docs`` 是旧生成流程的结果，只用于分析过度扩充、前置缺失和教学失败，不作为新内容的事实来源。

学习路径
--------

track 根据 Roadmap 知识库存定义目标读者、入口能力、最终能力、阶段顺序和范围。

Roadmap 知识项可以根据学习依赖被合并、拆分、重排、延后或明确排除。每项变化都需要留下覆盖记录，不能静默丢失用户真正想学的知识。

学习单元
--------

unit 负责一次明确的能力变化。读者需要经历预测、观察、逐步推理、条件变化、误解修正和迁移任务。

每个 unit 需要说明它覆盖哪个 Roadmap 知识项，以及技术结论来自哪些一手资料或真实现象。

事实证据
--------

技术事实重新来自：

* 官方文档、标准和规范；
* 固定版本源码；
* 示例代码与实际输出；
* 编译错误；
* 请求、日志或进程状态；
* 图示、界面现象或 trace。

源码级内容需要标明仓库、release、commit、平台和工具链。实际输出需要标明验证环境和日期；未执行内容必须明确标为预期结果。

Roadmap 只能证明“需要学习这个知识”，不能证明技术结论正确。

评估
----

评估不只检查术语记忆。问题必须来自 unit 中的现象，答案必须给出推理和错误模型分析，最终任务检查读者能否把理解迁移到变化场景。

状态
----

少量 TOML 记录：

* Roadmap 和生成控制文件路径；
* 知识项的待设计、合并、覆盖、延后或排除状态；
* 学习路径和 unit 的当前进度；
* 事实来源、验证环境和实际阅读反馈。

状态文件负责跨对话接续，不替代 RST 内容，也不能把“文件已经写完”直接等同于“读者已经学会”。

直接阅读
--------

面向读者的内容位于 ``docs/tracks/``。文件使用普通 RST 相对链接互相连接，不使用 Sphinx、toctree、自动检查、HTML 构建或发布系统。

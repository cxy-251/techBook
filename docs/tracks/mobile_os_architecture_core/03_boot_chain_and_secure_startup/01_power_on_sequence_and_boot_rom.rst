========================================================================
Chapter 13: 上电时序与硬件信任根：PMIC 供电、不可变 Boot ROM 与硬件熔丝
========================================================================

.. note:: 前置背景与认知承接
   第一模块系统解构了移动 OS 的六层调用模型与系统边界，第二模块全面夯实了 SoC 芯片级异构拓扑、大小核调度、TBDR 渲染、ISP 图像管道、NPU 算力与整机供电存储等全部物理底座。从本章开始，全书进入第三模块——引导链路与安全启动（Boot Chain）。一部智能手机在用户按下电源键的短短数百毫秒内，必须从无电荷无状态的“物理死寂”状态，经由严格的电气上电时序、硬件级安全验证与多级引导加载器，最终唤醒操作系统内核。本章将系统解构冷启动第一微秒的 PMIC 电源时序、CPU 复位向量（Reset Vector）捕获、只读不可变 Boot ROM（PBL - Primary Boot Loader）执行微架构、片上一次性可编程硬件熔丝（eFuse / OTP）公钥指纹校验，以及建立全链路不可篡改硬件信任根（Root of Trust - RoT）的物理机理。

------------------------------------------------------------------------
13.1 冷上电电气时序与硬件复位向量 (Reset Vector)
------------------------------------------------------------------------

当智能手机处于关机断电状态时，SoC 芯片内部的数十亿晶体管处于零电压逻辑无序状态。冷启动的起点是由物理按键事件触发的毫秒级精确电气时序：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     冷启动第一毫秒: PMIC 硬件上电时序状态机              |
   +-------------------------------------------------------------------------+

   [ 用户长按 Power 键 (产生 > 50ms 硬件接地低电平信号) ]
        |
        v
   [ 主 PMIC 芯片捕获 PWRKEY 中断，启动内部硬件时序发生器 (Sequencer) ]
        |
        +---> 1. 启动常驻供电域 (VDD_AON / RTC: 0.5V) -> 唤醒 PMIC 内部微控制器
        |        (延时等待 100 微秒，确保电压轨纹波稳定)
        +---> 2. 启动内存供电域 (VDD2_LPDDR5: 0.9V, VDDQ: 0.5V)
        |        (延时等待 200 微秒)
        +---> 3. 启动 SoC 逻辑与 CPU 核心电压轨 (VDD_SOC: 0.75V, VDD_CPU_LITTLE: 0.65V)
        |        (等待所有电压轨输出 Power-Good 硬件拉高信号)
        v
   [ 激活外部 38.4MHz 温补晶体振荡器 (TCXO) -> SoC 内部锁相环 (PLL) 锁定倍频 ]
        |
        v (电气环境完全就绪)
   [ PMIC 释放硬件复位引脚 (Reset Deassertion: SoC_RESET_N 从低电平拉升至高电平) ]

复位向量 (Reset Vector) 硬件跳转
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 `SoC_RESET_N` 引脚被释放的一瞬间：
1. CPU 硬件逻辑解除冻结，硬件仲裁器指定引导主核心（Boot CPU，通常为 Little Cluster 中的 Core 0）；
2. 引导核心内部的**程序计数器（Program Counter - PC 寄存器）**被硬件逻辑强行硬编码指向预置的**复位向量物理地址**（例如 ARMv8/ARMv9 架构下的 `0x0000_0000_0000_0000` 或 SoC 内部映射地址 `0x0010_0000`）；
3. CPU 在该地址捕获第一条执行机器指令，正式拉开操作系统的生命序幕。

------------------------------------------------------------------------
13.2 不可变 Boot ROM (Primary Boot Loader - PBL) 执行微架构
------------------------------------------------------------------------

复位向量所指向的物理存储介质，是直接固化在 SoC 硅片内部的 **Boot ROM（又称 Primary Boot Loader - PBL，或 SecureROM）**。

Boot ROM 的物理不可变性 (Immutability)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **金属掩膜光刻 (Mask ROM)**：Boot ROM 并非闪存颗粒，而是在芯片制造（Fabrication）阶段通过光刻掩膜直接烧结在晶圆金属层中的硬件电路；
- **绝对的只读防线**：出厂后无论是操作系统、内核漏洞、物理拆机还是高压电击，**任何人都无法修改或覆盖 Boot ROM 中的单比特代码**。它是整个设备安全防线的物理底座。

片上 SRAM (Internal SRAM / OCIM) 的沙箱环境
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Boot ROM 执行阶段，外部物理 LPDDR5X 内存芯片由于尚未配置内存控制器时钟、驱动强度与阻抗校准（ZQ Calibration），处于**完全不可用状态**。

Boot ROM 必须完全依赖集成在 SoC 片上的微小 **内部 SRAM（On-Chip SRAM / OCIM，通常仅 256KB ~ 512KB）** 作为其执行栈（Stack）和数据堆（Heap），构建出一个完全自给自足的最小执行沙箱。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       Boot ROM (PBL) 核心执行任务流                      |
   +-------------------------------------------------------------------------+

   [ 1. 最小硬件环境初始化 ]
   * 初始化 ARM 异常向量表 (VBAR_EL3)
   * 关闭看门狗定时器 (Watchdog)，配置 L1 指令/数据 Cache
   ---------------------------------------------------------------------------
   [ 2. 启动模式判定 (Boot Strapping) ]
   * 读取硬件引导引脚 (Boot Pins) 状态
   * 判定目标启动介质 (UFS 4.0 闪存 vs USB 紧急下载模式 EDL/DFU)
   ---------------------------------------------------------------------------
   [ 3. 初始化 UFS 存储控制器与 DMA 引擎 ]
   * 驱动 UFS 物理层 (M-PHY) 与 UniPro 链路层，建立基础读取通道
   ---------------------------------------------------------------------------
   [ 4. 镜像搬运与硬件验签 (Secure Boot Verification) ]
   * 从 UFS 固化分区读取二级引导器 (SBL / XBL / iBoot Stage 1) 到片上 SRAM
   * 调用片上硬件加密引擎比对公钥哈希并验证数字签名
   ---------------------------------------------------------------------------
   [ 5. 移交执行权 (Jump to SBL) ]
   * 验签通过后，PC 指针跳转至片上 SRAM 中的 SBL 入口点执行

13.3 硬件信任根 (Root of Trust - RoT) 与 eFuse 熔丝阵列
------------------------------------------------------------------------

如果用于验证后续固件合法性的公钥是存储在闪存文件系统中的，黑客可以通过修改闪存中的公钥来实现“自签恶意固件”的非法刷机。为了构筑不可篡改的**硬件信任根（Root of Trust - RoT）**，现代移动芯片引入了 **一次性可编程电熔丝（eFuse / OTP Memory）** 阵列。

eFuse (Electrical Fuse) 物理熔断机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **物理单向性**：每个 eFuse 比特出厂时默认状态为 `0`。在产线阶段，通过向目标熔丝施加特定的编程高电压（如 1.8V）与大电流，将微观金属引线永久汽化物理烧断，该位状态永久锁定为 `1`；
- **物理不可逆性**：一旦熔断，任何软件指令或物理手段均无法将 `1` 恢复为 `0`。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  SoC 内部 eFuse 阵列与硬件信任根绑定拓扑                |
   +-------------------------------------------------------------------------+

   [ 手机厂商安全制造产线 (Secure Manufacturing Factory) ]
        |
        | 1. 厂商生成非对称根密钥对: (Root Private Key 私钥 / Root Public Key 公钥)
        | 2. 计算根公钥哈希: OEM_PK_HASH = SHA-256(Root_Public_Key)
        v
   [ SoC 片上 eFuse 硬件熔丝存储区 (OTP - One-Time Programmable) ]
   +-------------------------------------------------------------------------+
   | 寄存器 0x01: OEM_PK_HASH (256-bit 根公钥指纹, 永久物理烧断!)           |
   | 寄存器 0x02: ANTI_ROLLBACK_VERSION (防降级版本计数器)                   |
   | 寄存器 0x03: JTAG_DISABLE_FUSE (硬件 JTAG 调试接口物理熔断锁死位)       |
   | 寄存器 0x04: SEC_BOOT_ENABLE (安全启动主使能位: 1 = 强制验签)           |
   +-------------------------------------------------------------------------+
        |
        v (硬件只读总线直接连接至片上加密引擎)
   [ 硬件公钥比对电路与安全密码协处理器 (SPU / Secure Enclave) ]

13.4 PBL 对 SBL (Secondary Boot Loader) 的严格验签状态机
------------------------------------------------------------------------

Boot ROM 加载第二阶段引导程序（在高通平台称为 XBL - eXtensible Boot Loader，在苹果平台称为 LLB / iBoot Stage 1）时，必须执行严密的数学密码学验签流水线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PBL 对 SBL 镜像逐级验签数学状态机                   |
   +-------------------------------------------------------------------------+

   [ 从 UFS 闪存读取 SBL 签名镜像文件 (Signed Image Container) ]
   +-------------------------------------------------------------------------+
   | 1. 证书链 (Certificate Chain): 包含 Root CA 证书与签署 SBL 的 OEM 证书  |
   | 2. 数字签名 (Signature): 厂商私钥对 SBL 载荷哈希的加密签名              |
   | 3. SBL 原始二进制机器码 (Binary Payload)                                 |
   +-------------------------------------------------------------------------+
        |
        v
   [ 步骤 1: 根公钥指纹硬件强校验 (Root Public Key Authentication) ]
   * PBL 提取证书链中的 Root Public Key
   * 计算 Hash_calc = SHA-256(Root_Public_Key)
   * 硬件比较: Hash_calc 是否与 eFuse 中的 OEM_PK_HASH 绝对相等?
        |
        +-- [ 否: 硬件公钥被篡改! ] ------------> [ 强制熔断停机 / 触发紧急恢复模式 ]
        |
        v [ 是: 确认公钥归属官方厂商! ]
   [ 步骤 2: 证书链有效性校验 (Certificate Chain Validation) ]
   * 使用 Root Public Key 验证 OEM 证书的签名有效性与授权范围
        |
        v
   [ 步骤 3: 二进制载荷完整性与签名校验 (Payload Integrity Check) ]
   * 使用 OEM Public Key 解密数字签名，得到期望哈希值 Expected_Hash
   * 硬件加密加速器计算片上 SRAM 中 SBL 实际二进制哈希: Actual_Hash = SHA-256(SBL_Code)
   * 硬件比较: Actual_Hash == Expected_Hash ?
        |
        +-- [ 否: 二进制代码被恶意修改! ] ------> [ 强制停机拒绝执行! ]
        |
        v [ 是: 证明 SBL 代码 100% 官方正版且未被篡改! ]
   [ 步骤 4: 防回滚版本检查 (Anti-Rollback Check) ]
   * 读取 SBL 头部的软件版本号 Version_SBL
   * 检查是否满足: Version_SBL >= eFuse.ANTI_ROLLBACK_VERSION
        |
        v [ 通过所有校验 ]
   [ 步骤 5: 控制权交接 ] -> CPU 跳转至 SRAM 中执行 SBL 第一条指令!

13.5 紧急恢复模式 (EDL / DFU) 与防刷机后门攻防
------------------------------------------------------------------------

当设备由于意外断电导致 UFS 分区损坏，或者安全启动验签失败时，系统绝不会陷入物理死锁，而是自动回退至**紧急下载模式**。

Qualcomm EDL (9008) 与 Apple DFU 模式微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   紧急下载模式 (EDL / DFU) 硬件回退拓扑                 |
   +-------------------------------------------------------------------------+

   [ SBL 验签失败 / UFS 通信超时 / 物理 TestPoint 测试点接地 ]
        |
        v
   [ Boot ROM 放弃从 UFS 闪存读取，转而初始化 SoC 片上 USB 2.0 PHY 控制器 ]
        |
        v
   [ 手机通过 USB 接口枚举为专用维护设备: ]
        * 高通平台: "Qualcomm HS-USB QDLoader 9008" (EDL 模式)
        * 苹果平台: "Apple Mobile Device (DFU Mode)" (DFU 模式)
        |
        v
   [ 接收外部刷机工具 (QFIL / iTunes / Configurator) 下发协议数据包 ]

紧急下载模式下的硬件安全闸门
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

许多人误以为进入了底层 EDL/DFU 模式就可以任意刷写自制操作系统（Custom ROM）。在现代安全芯片设计中，**Boot ROM 在紧急模式下依然具备严苛的安全闸门**：

1. **协议加载器强验签 (Programmer Verification)**：外部工具必须首先向手机上传一个微小的引导程序（Qualcomm Firehose Programmer / Apple iBSS）。**Boot ROM 会对该引导程序进行完全相同强度的 eFuse 公钥签名校验**，任何未由厂商官方私钥签署的 Programmer 都会被 Boot ROM 直接丢弃；
2. **鉴权挑战响应机制 (Auth Challenge-Response)**：部分高端旗舰手机在 EDL 模式下，Boot ROM 还会要求刷机端提供经由厂商云端服务器实时签发的临时授权 Token（带有随机数 Nonce），彻底阻断了利用维修漏洞非法窃取用户加密数据的黑客行径。

13.6 双平台硬件信任根与第一阶段引导对比
------------------------------------------------------------------------

.. list-table:: Android 旗舰平台与 Apple 硬件信任根体系对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 维度
     - Android 平台 (以高通骁龙为例)
     - Apple 平台 (A 系列 / M 系列芯片)
   * - **硬件信任根载体**
     - SoC 内部 eFuse 阵列 (`OEM_PK_HASH`)
     - 芯片内部封装只读熔丝与 Secure Enclave 硬件
   * - **第一阶段引导 (L1)**
     - **PBL (Primary Boot Loader)**，刻蚀在 Boot ROM
     - **SecureROM**，刻蚀在 SoC 内部 ROM 掩膜
   * - **执行内存环境**
     - 片上内部 SRAM (OCIM / 256KB~512KB)
     - 片上安全 SRAM (Secure On-Chip SRAM)
   * - **第二阶段引导 (L2)**
     - **XBL (eXtensible Boot Loader)**
     - **LLB (Low-Level Bootloader)** / iBoot Stage 1
   * - **硬件调试防护**
     - 产线烧断 JTAG eFuse 熔丝，彻底物理断开引脚
     - 专用硬件 SecureROM 禁用调试寄存器与序列线
   * - **紧急恢复模式**
     - **EDL 模式 (9008)**，受 Firehose 签名保护
     - **DFU 模式 (Device Firmware Upgrade)**，受 SHSH2 签名保护

========================================================================
Chapter 14: 逐级验签与系统完整性校验：Chain of Trust、AVB 签名链、vbmeta 与 dm-verity
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了冷启动第一毫秒内的 PMIC 电气时序、不可变 Boot ROM（PBL）微架构与 eFuse 硬件信任根（Root of Trust - RoT）。然而，随着引导加载程序从微小的片上 SRAM 迁移至数百兆字节的复杂 Linux / XNU 内核及数吉字节（GB）的只读系统镜像，逐字节全量加载验签的耗时将导致开机时间呈灾难性爆炸。为了兼顾密码学防篡改强度与秒级开机性能，现代移动 OS 构筑了多级信任链（Chain of Trust）、Android 验证启动（AVB 2.0）、vbmeta 描述符网络，以及基于 Linux 块设备层的 dm-verity 实时透明哈希树校验。本章将系统剖析整机签名信任链的逐级传递、AVB 核心数据结构、dm-verity 默克尔树（Merkle Tree）按需校验算法，以及 Apple Secure Boot / Local Boot Policies 的对等实现与防回滚保护机制。

------------------------------------------------------------------------
14.1 信任链传递机制 (Chain of Trust) 与逐级验证范式
------------------------------------------------------------------------

安全启动的核心公理是**信任的单向不可逆传递**：在引导流水线中，下一阶段的代码或系统镜像在获得 CPU 控制权之前，必须且只能由已经通过验证的前一阶段代码完成密码学签名与完整性校验。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       移动操作系统完整信任链逐级传递模型                |
   +-------------------------------------------------------------------------+

   [ 阶段 0: 硬件信任根 (Root of Trust - 硅片不可变) ]
   * SoC 片上 eFuse (根公钥指纹 OEM_PK_HASH) -> 校验 Boot ROM 初始公钥
        |
        v (在片上 SRAM 中验证)
   [ 阶段 1: 第一级/第二级引导程序 (PBL -> XBL / iBoot Stage 1) ]
   * 初始化 DDR 内存控制器与安全环境 (ARM TrustZone / Secure Enclave)
        |
        v (在外部 DRAM 中验证)
   [ 阶段 2: 应用程序引导加载器 (ABOOT / Little Kernel / iBoot Stage 2) ]
   * 解析 Android Verified Boot (AVB) vbmeta 结构 / Apple IMG4 容器
        |
        v (加载内核与设备树)
   [ 阶段 3: 操作系统内核与初始内存盘 (Kernel + initramfs / boot.img) ]
   * 校验内核镜像哈希，向内核传递 dm-verity 根哈希命令行参数
        |
        v (驱动加载与文件系统挂载)
   [ 阶段 4: 块设备级实时完整性校验 (dm-verity / Signed System Volume) ]
   * 驱动对 /system, /vendor, /product 只读分区进行透明 4KB 块按需校验
        |
        v (启动用户空间)
   [ 阶段 5: 用户态系统初始化 (Android init / Apple launchd) ]

- **断链防御机制**：若链条中任意一级的哈希比对失败或签名不匹配，当前引导程序**绝对禁止跳转执行下一阶段**，而是立即切断引导流并回退至安全恢复或刷机模式，确保恶意篡改的代码绝无机会在特权模式下运行。

14.2 Android Verified Boot (AVB 2.0) 架构与 vbmeta 描述符体系
------------------------------------------------------------------------

在早期的 Android 验证启动（AVB 1.0）中，签名信息被粗暴地硬编码附加在每个分区的尾部，导致分区更新复杂且难以支持模块化解耦。Google 从 Android 8.0 开始全面确立了 **AVB 2.0（Android Verified Boot 2.0）** 标准。

vbmeta 分区物理数据结构解构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

AVB 2.0 引入了专用的独立元数据镜像——`vbmeta.img`（Verified Boot Metadata），其物理二进制布局高度结构化：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       vbmeta 二进制镜像标准物理拓扑                     |
   +-------------------------------------------------------------------------+

   +-------------------------------------------------------------------------+
   | 1. Magic 幻数: "AVB0" (0x41564230, 4 字节)                              |
   | 2. 版本号与总体长度 (Header Block: 256 字节)                            |
   +-------------------------------------------------------------------------+
   | 3. 认证数据块 (Authentication Block):                                   |
   |    * 签名算法枚举 (如 SHA256_RSA4096 / SHA512_RSA4096)                   |
   |    * OEM 官方公钥二进制字节 (OEM Public Key)                            |
   |    * 针对整个 Auxiliary Block 数据的数字签名 (Digital Signature)        |
   +-------------------------------------------------------------------------+
   | 4. 辅助数据块 (Auxiliary Block - 包含核心验证描述符列表):               |
   |    * [描述符 A: Hash Descriptor] -> 校验 boot / recovery / dtbo 完整镜像 |
   |    * [描述符 B: Hashtree Descriptor] -> 校验 system / vendor dm-verity 树|
   |    * [描述符 C: Chain Partition Descriptor] -> 链接子 vbmeta_system 分区 |
   +-------------------------------------------------------------------------+

链式分区描述符 (Chain Partition Descriptors) 的解耦机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了支持 Project Treble 下系统分区（Google GSI）与厂商驱动分区（Vendor）的独立 OTA 更新，AVB 支持**分层链式委托**：
主 `vbmeta` 分区内部可以包含一个指向 `vbmeta_system` 的链式描述符，其中声明了允许签署系统分区的独立公钥哈希。引导加载器在验证主 `vbmeta` 后，使用该指定公钥继续递归验证 `vbmeta_system`，实现了跨厂商团队的安全解耦。

14.3 dm-verity 实时透明哈希树 (Merkle Tree) 块级校验微架构
------------------------------------------------------------------------

现代智能手机的 `system.img`、`vendor.img` 与 `product.img` 体积高达 4GB ~ 8GB。如果在开机阶段将整个 8GB 镜像全量读入内存并计算 SHA-256 哈希，开机耗时将长达数十秒，这在工业级产品中是绝对不可接受的。

Linux 内核引入了 **dm-verity（Device Mapper Verity）** 目标驱动，基于**默克尔哈希树（Merkle Tree）**实现了运行时毫秒级按需透明校验。

默克尔哈希树的物理构建模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  dm-verity 默克尔哈希树 (Merkle Tree) 构建拓扑          |
   +-------------------------------------------------------------------------+

   [ vbmeta 中经数字签名的 Root Hash (32 字节, 绝对可信基准) ]
                                |
                                v
               +----------------+----------------+
               | Level 2 Hash 0 | Level 2 Hash 1 | ... (顶级 Hash 节点块: 4KB)
               +----------------+----------------+
                 /            \
       +--------+--------+    +--------+--------+
       | Level 1 Hash 0  |    | Level 1 Hash 1  | ... (一级 Hash 节点块: 4KB)
       +--------+--------+    +--------+--------+
         /            \
   +----+---+      +----+---+
   | Data 0 |      | Data 1 | ... (底层物理数据块: 4KB Data Blocks in system.img)
   +--------+      +--------+

1. **分块哈希**：将整个底层数据分区以 **4KB 页面（Data Block）** 为单位均匀切分；
2. **多级聚合**：每个 4KB 数据块生成一个 32 字节的 SHA-256 哈希。一个 4KB 的 Hash 节点块恰好可以容纳 $4096 \div 32 = 128$ 个子节点哈希；
3. **收敛至根**：递归向上计算，直至最后聚合为一个唯一的 32 字节 **Root Hash（根哈希）**。根哈希直接固化在经数字签名的 `vbmeta` 的 `Hashtree Descriptor` 中。

运行时按需拦截与零延迟校验流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在操作系统运行期间，dm-verity 挂载为只读虚拟块设备（`/dev/block/dm-0`）：

.. code-block:: text

   [ 用户态进程调用 read() 读取 /system/bin/app_process64 (对应物理 Data Block #42) ]
        |
        v
   [ Linux 内核 VFS -> 页面缓存缺失 (Page Cache Miss) ]
        |
        v
   [ dm-verity 驱动在 I/O 提交点进行透明拦截 ]
        |
        +---> 1. 从 UFS 闪存读取原始 Data Block #42 (4KB 数据)
        +---> 2. 从 UFS 闪存读取对应的 Level 1 Hash 块
        +---> 3. 硬件加密加速器计算: SHA-256(Data Block #42)
        +---> 4. 比对计算哈希是否等于 Level 1 节点中存储的期望哈希
        |        (若上一级 Hash 块未在内存中，递归比对至内存中已校验的 Root Hash)
        v
   [ 校验判定结果: ]
        |
        +-- [ 校验通过: 耗时 < 10 微秒 ] ---> 填充 Page Cache，数据透明返回用户态！
        |
        +-- [ 校验失败: 发现单比特篡改! ] --> 拒绝返回数据！返回 EIO 错误！
                                              触发全局安全事件 (Kernel Panic / 重启修复)

14.4 防版本回滚保护 (Anti-Rollback Protection) 与安全版本计数器
------------------------------------------------------------------------

降级攻击 (Rollback Attack) 的物理威胁
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

如果攻击者截获了一个历史上由厂商官方合法签名的旧版本系统固件（该旧固件包含已知的重大内核提权漏洞），攻击者可以将手机强制刷入该旧固件。由于旧固件的官方签名完全合法有效，常规的安全启动验签会判定通过，从而使设备重新暴露于已知漏洞之下。

防回滚索引 (Rollback Index) 与硬件计数器联动
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了封死降级攻击通道，现代移动设备建立了**硬件级单向防回滚约束**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     防回滚版本比对与硬件计数器单向递增                  |
   +-------------------------------------------------------------------------+

   [ 固件镜像头中声明的防回滚索引: Rollback_Index_Image ]
                                vs
   [ 安全芯片 / eFuse / RPMB 中保存的硬件防回滚计数器: Rollback_Index_Hardware ]

   比对判定法则:
   * 若 Rollback_Index_Image >= Rollback_Index_Hardware:
     -> 允许启动！
     -> 若 Rollback_Index_Image > Rollback_Index_Hardware (发生了系统安全升级):
        在系统成功启动并确认正常后，安全服务通过 TEE 驱动在 RPMB 分区中单向递增硬件计数器！
   * 若 Rollback_Index_Image < Rollback_Index_Hardware (检测到非法降级刷机!):
     -> 拒绝启动！屏幕显示安全违规并停机！

14.5 Apple Secure Boot 与签名系统宗卷 (SSV - Signed System Volume)
------------------------------------------------------------------------

在 Apple 平台（iOS / iPadOS / macOS）中，苹果采用了与 Android AVB 异曲同工但深度软硬件垂直整合的安全启动架构：

.. list-table:: Apple 安全启动各阶段与验证载体矩阵
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 启动阶段
     - 载荷格式与容器
     - 校验执行实体
     - 关键安全约束
   * - **SecureROM**
     - 固化在片上 ROM
     - 硬件电路直接执行
     - 验证 LLB / iBoot Stage 1 的苹果根公钥签名
   * - **iBoot 阶段**
     - IMG4 加密容器
     - Secure Enclave (SEP)
     - 校验 ECID 专属绑定、Nonce 随机数（杜绝重放）与 SEP 固件
   * - **XNU 内核加载**
     - Mach-O Kernel 镜像
     - iBoot 引导加载器
     - 验证内核签名、DeviceTree 与启动参数（boot-args）
   * - **文件系统挂载**
     - **签名系统宗卷 (SSV)**
     - XNU APFS 驱动
     - 验证 APFS B-Tree 根哈希，封锁任何对 `/System` 的写入修改

签名系统宗卷 (Signed System Volume - SSV)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Apple 在现代系统中引入了 **SSV（Signed System Volume）** 技术：系统启动时，操作系统直接从不可变的只读快照（APFS Snapshot）启动。整个快照的所有目录树结构、元数据与文件内容被压缩计算为一个唯一的 SHA-256 根哈希，并在内核引导阶段由 Apple 签名证书强校验。在 macOS/iOS 运行时，任何对系统目录的修改都会破坏哈希树，导致下次引导彻底失败。

14.6 双平台安全启动与完整性校验机制全景对比
------------------------------------------------------------------------

.. list-table:: Android AVB 2.0 与 Apple Secure Boot 核心技术对照
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 比较维度
     - Android 平台 (AVB 2.0 + dm-verity)
     - Apple 平台 (Secure Boot + SSV)
   * - **信任链锚点**
     - SoC 片上 eFuse 中的 `OEM_PK_HASH`
     - SecureROM 中的苹果根公钥与 Secure Enclave
   * - **元数据存储**
     - 独立的 `vbmeta` 分区（支持链式子描述符）
     - IMG4 结构化容器（包含 Manifest 清单）
   * - **块级只读校验**
     - **Linux dm-verity**（按需 4KB 默克尔树校验）
     - **APFS Signed System Volume**（基于 APFS 快照树）
   * - **防降级回滚**
     - eFuse 熔丝位 + eMMC/UFS RPMB 安全回滚计数器
     - Secure Enclave 签名服务 + SHSH2 云端随机数票据
   * - **设备专属绑定**
     - 支持 Bootloader 解锁（切换至黄色/橙色安全状态）
     - 强绑定单一设备的物理 `ECID` 唯一芯片序列号

小结与下章导读
------------------------------------------------------------------------

本章从密码学与系统微架构出发，系统解构了多级信任链的单向传递模型、Android AVB 2.0 vbmeta 描述符网络、Linux 内核 dm-verity 实时按需块级校验算法、防版本回滚保护机制，以及 Apple Secure Boot 与 SSV 签名系统宗卷的实现。

在安全启动机制确保了底层内核与分区数据的绝对纯净后，操作系统必须面临实际的固件升级与分区管理——下一章我们将聚焦于**手机存储分区拓扑与更新：A/B 无缝 OTA 槽位切换、Recovery 修复模式与防版本回滚保护**，深入剖析双槽位镜像切换、动态分区（Dynamic Partitions）与后台静默更新的底层实现。

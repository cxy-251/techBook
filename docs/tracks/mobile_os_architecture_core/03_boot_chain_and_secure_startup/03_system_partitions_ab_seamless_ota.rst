========================================================================
Chapter 15: 手机存储分区拓扑与更新：A/B 无缝 OTA、动态分区与回滚保护
========================================================================

.. note:: 前置背景与认知承接
   前一章深入解构了 AVB 2.0 签名链、vbmeta 描述符网络与 dm-verity 默克尔树实时校验机制。然而，移动终端在漫长的生命周期中必须持续接收操作系统的安全补丁与大版本功能升级。早期的“非 A/B（Non-A/B）传统 Recovery 刷机模式”需要设备重启至独立极简系统，在黑屏进度条下执行耗时数十分钟的就地覆写（In-place update），一旦中途发生断电或写损坏将直接导致设备变砖（Bricked）。现代移动操作系统（Android A/B 与 Apple APFS 快照更新）全面重构了存储分区拓扑，引入了 A/B 双槽位（Seamless A/B Update）、动态分区（Dynamic Partitions / super 分区）与虚拟 A/B（Virtual A/B / COW 快照写时复制）机制。本章将系统解构现代手机存储分区拓扑、Boot Control HAL 槽位状态机、无缝静默更新流水线、虚拟 A/B 快照合并机制，以及引导失败时的自动降级回滚与 Recovery 容灾体系。

------------------------------------------------------------------------
15.1 现代智能手机存储分区拓扑演进
------------------------------------------------------------------------

在移动操作系统发展初期，闪存存储被机械地硬划分为固定大小的物理分区（如 `/boot`, `/system`, `/vendor`, `/userdata`, `/cache`, `/recovery`）。随着 Project Treble 的推进与系统镜像模块化解耦，现代移动设备的存储拓扑发生了深刻重构：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 现代智能手机 UFS / eMMC 物理闪存分层拓扑                |
   +-------------------------------------------------------------------------+

   [ 硬件与固件静态分区 (不可动态调整, 厂商烧录) ]
   +---------------+---------------+---------------+---------------+
   | xbl / sbl     | tz / trustzone| hyp / abl     | modem / dsp   | ...
   +---------------+---------------+---------------+---------------+

   [ 引导链静态槽位分区 (真实物理双槽位: _a / _b) ]
   +---------------+---------------+---------------+---------------+
   | boot_a / _b   | init_boot_a/_b| dtbo_a / _b   | vendor_boot_a | vbmeta_a / _b
   | (通用内核GKI) | (通用ramdisk) | (设备树叠加)  | (厂商驱动boot)| (根安全签名)
   +---------------+---------------+---------------+---------------+

   [ 动态逻辑分区卷 (super 物理大分区, 由 Device Mapper 动态划分) ]
   +---------------------------------------------------------------+
   | super 分区 (例如 8GB ~ 12GB 连续物理块)                        |
   |  +----------------+----------------+----------------+         |
   |  | system_a / _b  | vendor_a / _b  | product_a / _b | ...     |
   |  | (Android核心)  | (SoC厂商HAL)   | (OEM定制特性)  |         |
   |  +----------------+----------------+----------------+         |
   +---------------------------------------------------------------+

   [ 用户数据与持久化持久状态分区 (全局单实例, 不分槽位) ]
   +---------------+---------------+---------------+---------------+
   | metadata      | misc          | persist       | userdata      |
   | (加密/回滚元) | (Bootloader传参)| (出厂校准参数)| (FBE 加密数据)|
   +---------------+---------------+---------------+---------------+

.. list-table:: 现代移动操作系统关键分区功能与挂载属性矩阵
   :widths: 18 20 22 40
   :header-rows: 1
   :class: tight-table

   * - 分区标识
     - 槽位属性
     - 挂载点与读写
     - 核心功能与镜像内容
   * - **`boot` / `init_boot`**
     - A/B 双槽位
     - 内核加载点（只读）
     - 包含通用 Linux 内核（GKI - Generic Kernel Image）与第一阶段 Ramdisk
   * - **`vendor_boot`**
     - A/B 双槽位
     - 内核加载点（只读）
     - 存放 SoC 芯片厂商专属的核心内核驱动模块（`.ko`）与厂商 Ramdisk
   * - **`vbmeta`**
     - A/B 双槽位
     - 引导期解析（只读）
     - 存放 AVB 2.0 核心签名、描述符网络与各分区的根哈希（Root Hash）
   * - **`super` (动态分区)**
     - 内部逻辑 A/B
     - 块设备容器
     - 容纳 `system`、`vendor`、`product`、`system_ext`、`odm` 等动态逻辑卷
   * - **`metadata`**
     - 单实例（无 A/B）
     - `/metadata` (读写)
     - 存放文件级加密（FBE）密钥元数据与 Virtual A/B 快照状态机描述符
   * - **`userdata`**
     - 单实例（无 A/B）
     - `/data` (ext4/f2fs)
     - 存放全量用户数据、应用安装包（`/data/app`）与加密运行沙箱

15.2 传统 Non-A/B Recovery 升级模式及其物理缺陷
------------------------------------------------------------------------

在早期的 Non-A/B 传统架构中，系统更新完全依赖独立的 **Recovery 系统** 进行就地覆写：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     传统 Non-A/B Recovery 模式升级全流程                |
   +-------------------------------------------------------------------------+

   [ 1. Android 正常系统运行中 ]
        |
        +---> 下载 OTA 全量/差分包 (例如 update.zip) 保存至 `/cache` 分区
        +---> 向 `/misc` 或 `/cache/recovery/command` 写入指令: "--update_package=..."
        +---> 调用 PowerManager 重启进入 Recovery 模式
        |
   [ 2. 设备关机重启 -> Bootloader 检测到 Boot into Recovery 标志 ]
        |
        v
   [ 3. 加载 recovery 分区中的极简微内核与 Recovery 守护进程 ]
        |  * 此时主 Android 系统完全停止运行！手机黑屏并展示刷机齿轮/进度条！
        |  * 用户完全无法使用手机进行通话、求救或常规操作 (停机时间 15 ~ 45 分钟)
        v
   [ 4. Recovery 进程开始就地覆写 (In-Place Overwrite) 物理 /system 分区 ]
        |
        +-- [ 场景 A: 升级中途电池耗尽 / 用户强行拔电 / UFS 发生局部物理坏块 ]
        |        |
        |        v
        |   [/system 物理分区处于半新半旧的损坏状态！无法启动！设备永久变砖！]
        |
        +-- [ 场景 B: 写入完成，清除 command 标志，重启进入新系统 ]

传统 Non-A/B 模式的三大致命缺陷
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **零容错性与变砖风险**：由于是对运行分区进行直接覆写，一旦写入过程中断或新固件存在致命启动崩溃（Bootloop），设备将无法回退，只能通过售后线刷救砖；
2. **极长的停机时间（Downtime）**：解压、校验、格式化与写入的全过程全部在 Recovery 模式下同步执行，用户被迫等待数十分钟；
3. **巨大的存储空间浪费**：设备必须额外划分一个 1GB~2GB 的 `/cache` 物理分区专门用于暂存 OTA 镜像，而在日常使用中该空间几乎完全闲置。

15.3 A/B 无缝更新 (Seamless Updates) 与槽位状态机
------------------------------------------------------------------------

为了彻底消除刷机变砖风险与用户停机时间，Android 7.0 引入了 **A/B 无缝更新机制（A/B Seamless Updates）**。

A/B 槽位三元状态与 Boot Control HAL 接口
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 A/B 架构下，所有与操作系统引导相关的核心分区均存在成对的槽位（Slot A 与 Slot B）。Bootloader 与底层固件通过 **Boot Control HAL** 维护每个槽位的状态三元组：

.. code-block:: text

   struct SlotMetadata {
       bool is_active;        // 当前是否为目标活动引导槽位
       bool is_successful;    // 该槽位是否已成功引导并被系统标记确认
       uint8_t tries_remaining; // 剩余允许尝试引导的计数值 (初始通常设为 7 或 3)
   };

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     A/B 槽位切换与容灾状态机流转拓扑                    |
   +-------------------------------------------------------------------------+

   [ 状态 1: 当前系统稳定运行在 Slot A (Slot A: active=1, successful=1, tries=0) ]
        |
        v (1. 后台静默升级: update_engine 在用户玩手机时，直接将新系统流式写入 Slot B)
   [ 状态 2: 写入完成，调用 markBootSuccessful(A), setActiveBootSlot(B) ]
        |  * Slot B 元数据更新为: active=1, successful=0, tries_remaining=7
        v
   [ 2. 用户仅需正常重启手机 (Reboot) ]
        |
        v
   [ 状态 3: Bootloader 尝试从 Slot B 引导 ]
        |  * Bootloader 读取 Slot B: 发现 active=1 且 tries_remaining > 0
        |  * 将 Slot B 的 tries_remaining 递减为 6，并跳转执行 Slot B 内核与系统
        |
        +---> [ 分支 3.1: Slot B 成功启动并进入 Android 用户态 ]
        |          |
        |          v
        |     [ 系统服务 update_engine 确认网络、服务均正常，调用 markBootSuccessful(B) ]
        |     * Slot B 转为: active=1, successful=1, tries_remaining=0
        |     * 升级圆满完成！Slot A 降级为备用槽位。
        |
        +---> [ 分支 3.2: Slot B 发生 Kernel Panic / Framework 连续崩溃 (Bootloop) ]
                   |
                   v
              [ 手机看门狗触发重启，Bootloader 再次尝试 Slot B (tries=5, 4, 3, 2, 1) ]
                   | (当 tries_remaining 归 0 且 successful 仍为 0 时)
                   v
              [ 触发自动故障回滚 (Rollback)！Bootloader 自动切回 Slot A 引导！]
              * 手机毫秒级恢复至原旧系统，用户数据完好无损，完全无感！

15.4 动态分区 (Dynamic Partitions) 与 Super 分区卷管理
------------------------------------------------------------------------

A/B 分区虽然解决了安全与可用性问题，但也带来了物理闪存空间的剧烈膨胀：如果 `system` (3.5GB)、`vendor` (1.5GB)、`product` (2.5GB) 均硬划分双份，仅只读系统分区就需要独占近 15GB 的物理闪存。

Android 10 引入了**动态分区（Dynamic Partitions）**架构，通过 Linux 内核的 **Device Mapper（dm-linear）** 驱动将多个零散的只读分区聚合为一个单一的 `super` 物理块设备：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     动态分区 super 卷管理与 dm-linear 映射              |
   +-------------------------------------------------------------------------+

   [ 物理闪存中的单一物理分区: /dev/block/by-name/super (大小: 9.0 GB) ]
   +-------------------------------------------------------------------------+
   | LpMetadata (分区元数据表): 记录各逻辑分区的 Extent 物理偏移与扇区长度   |
   +-------------------------------------------------------------------------+
   | Extent 0..N (连续/离散的数据块池)                                       |
   | [ system_a 占用 3.1GB ] [ vendor_a 占用 1.2GB ] [ product_a 占用 2.0GB ] |
   | [ 空闲碎片空间: 2.7GB - 可由未来任意子分区按需动态伸缩分配! ]            |
   +-------------------------------------------------------------------------+
        |
        v (在 init 第一阶段解析 LpMetadata 并创建虚拟块设备)
   +---> /dev/block/mapper/system_a   (挂载至 /system)
   +---> /dev/block/mapper/vendor_a   (挂载至 /vendor)
   +---> /dev/block/mapper/product_a  (挂载至 /product)

- **动态尺寸伸缩**：在发布 OTA 更新时，若 `system` 分区体积增加了 500MB，而 `vendor` 缩减了 200MB，OTA 生成工具只需调整 `LpMetadata` 中的逻辑块映射，无需修改手机底层的物理分区表（GPT / MBR），彻底消除了“系统分区爆满而无法升级”的历史包袱。

15.5 虚拟 A/B (Virtual A/B) 与写时复制 (COW Snapshot) 空间优化
------------------------------------------------------------------------

纯 A/B 分区要求 `super` 分区内必须同时容纳 Slot A 与 Slot B 的全量逻辑卷，依然消耗了近一倍的静态空间。Android 11 推出了**虚拟 A/B（Virtual A/B / VAB）** 技术，实现了**接近零额外空间开销的无缝更新**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Virtual A/B 写时复制 (COW) 升级与合并架构           |
   +-------------------------------------------------------------------------+

   [ 阶段 1: 系统运行在 Slot A 时接收 OTA 更新 ]
   * 引导分区 (boot, vendor_boot, vbmeta) 保持真实物理 A/B 双槽位 (< 200MB);
   * 逻辑分区 (system, vendor) 物理上仅保留 Slot A 的单一基准镜像!
   * 在 /data 剩余空间中动态创建极小的写时复制差分文件: COW (Copy-On-Write) Images:

   +-------------------------------------------------------------------------+
   | 物理 super 分区 (仅存放系统 Slot A 基础数据)                            |
   +-------------------------------------------------------------------------+
        ^
        | (读取未修改的基础块)
   [ dm-snapshot / dm-user 虚拟合成设备 (/dev/block/mapper/system_b) ]
        | (读取本次 OTA 修改的全新块)
        v
   [ 临时写入 /data/gsi/ota/system_b-cow-img (仅消耗增量差分体积, ~800MB) ]

   ---------------------------------------------------------------------------
   [ 阶段 2: 槽位激活并重启至 Slot B ]
   * Bootloader 加载 boot_b 内核与 ramdisk;
   * init 阶段挂载基于 dm-snapshot 组合而成的虚拟 system_b (Base + COW);
   * 系统成功进入桌面，用户立即可用！

   ---------------------------------------------------------------------------
   [ 阶段 3: 后台无感快照合并 (Snapshot Merge Phase) ]
   * 后台守护进程 (snapshotctl / update_engine) 启动合并流水线:
     将 /data 中 COW 增量块静默写回物理 super 分区中的对应扇区;
   * 合并完成后，自动删除 /data 下的临时 COW 文件，彻底释放空间！

15.6 Apple APFS 卷组 (Volume Group) 与只读快照封印更新
------------------------------------------------------------------------

在 Apple 生态（iOS / iPadOS / macOS）中，苹果利用 **APFS（Apple File System）** 的高级文件系统特性实现了机制等价且极其优雅的密封无缝更新：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   Apple APFS 卷组 (Volume Group) 架构拓扑               |
   +-------------------------------------------------------------------------+

   [ APFS 容器 (Container) - 共享整块物理闪存空间 (Space Sharing) ]
        |
        +---> [ 1. 只读系统卷 (System Volume: com.apple.os.update-XXXX) ]
        |        * 根目录树被挂载为严格不可变的只读 APFS 快照 (Signed Snapshot);
        |        * 快照根哈希由 Apple 官方在引导阶段强校验 (SSV 机制);
        |        * 系统更新时，后台直接在 APFS 容器内创建新系统卷并写入数据;
        |
        +---> [ 2. 可读写数据卷 (Data Volume: Macintosh HD - Data / /private/var) ]
                 * 存放所有用户应用、照片、缓存与可变数据;
                 * 通过“合成纽带（firmlinks）”双向透明桥接至系统卷（如 `/Users` -> `/System/Volumes/Data/Users`）;
                 * 升级或回滚系统卷时，数据卷完全保持独立不被破坏！

========================================================================
Chapter 26: 音频与多媒体 HAL 架构：AudioFlinger、ALSA 与低时延通路
========================================================================

.. note:: 前置背景与认知承接
   在上一章（Chapter 25）中，我们解构了传感器子系统在低采样率、常驻低功耗场景下的 IIO 驱动、Sensor Hub 协处理器与 Fast Message Queue 架构。与传感器数据主要面向事件捕获不同，移动多媒体子系统中的音频链路对**连续高吞吐实时性、确定性时钟抖动以及极低端到端时延**有着近乎苛刻的要求。音频数据是以微秒级时间片流式传输的脉冲编码调制（PCM）样本，在音乐播放、语音通话、游戏音效以及实时录音等场景下，任何微小的缓冲区断流（Underflow）或溢出（Overflow）都会直接表现为用户可闻的爆音、破音或卡顿。本章将深入剖析移动音频系统的垂直架构：从底层物理 CODEC 编解码器与 Linux ALSA/TinyALSA 内核驱动，到 Android 音频执行引擎（AudioFlinger）与策略中枢（AudioPolicyService），再到现代 Stable AIDL Audio HAL、FastMixer 实时混音以及 AAudio/Oboe 独占 MMAP 低时延硬件直流通路。

26.1 移动音频硬件拓扑与物理通路
------------------------------------------------------------------------

音频硬件组成与总线连接
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动设备上的音频子系统由数字处理核心、物理传输总线与模拟信号链组成：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  现代移动 SoC 音频硬件拓扑与数据通路                    |
   +-------------------------------------------------------------------------+

   [ 主应用处理器 (SoC / AP) ]               [ 专用音频 DSP (Audio DSP / ADSP) ]
   +-------------------------+               +---------------------------------+
   | CPU (AudioFlinger / HAL)|               | 运行实时音频固件 (RTOS)         |
   | - 软件混音、音效处理    |               | - 硬件解码 (Offload MP3/AAC)    |
   | - 策略路由与时序控制    |               | - 语音唤醒 (Hotword / VUI)      |
   +-------------------------+               | - 硬件回声消除与降噪 (AEC/NS)   |
                |                                    |
                | AXI / DMA 共享物理内存             |
                +-----------------+------------------+
                                  |
                                  | I2S / TDM / SoundWire 数字音频总线
                                  v
   +-------------------------------------------------------------------------+
   | 独立音频编解码器芯片 (Audio CODEC / PMIC Audio Subsystem)               |
   |                                                                         |
   | +---------------------------------------------------------------------+ |
   | | 数模转换器 (DAC - Digital to Analog Converter) -> 重建平滑模拟波形  | |
   | +---------------------------------------------------------------------+ |
   | | 模数转换器 (ADC - Analog to Digital Converter) -> 麦克风模拟信号量化| |
   | +---------------------------------------------------------------------+ |
   | | 片上混音矩阵 (Analog/Digital Mixer) 与 增益放大器 (PGA / Volume)    | |
   | +---------------------------------------------------------------------+ |
   +-------------------------------------------------------------------------+
            |                                         ^
            | 模拟输出                                | 模拟输入
            v                                         |
   +-----------------------+                 +-----------------------+
   | 智能功放 (Smart PA)   |                 | 麦克风阵列 (MIC Array)|
   | - 电流电压实时感知 (IV|                 | - 主麦克风 (话筒底部) |
   |   Sensing) 防烧喇叭   |                 | - 降噪副麦 (机身顶部) |
   | - 升压电路 (Boost D类)|                 | - 相机麦克风 (背面)   |
   +-----------------------+                 +-----------------------+
            |
            v
   [ 扬声器 (Speaker) / 听筒 (Receiver) / 3.5mm 耳机 / Type-C 数字耳机 ]

- **I2S（Inter-IC Sound）总线**：数字音频传输的工业标准三线总线，包含连续时钟线（SCK / BCLK）、左右声道字选择线（WS / LRCK）以及串行数据线（SDATA）；
- **TDM（Time Division Multiplexed）**：时分复用总线，在单条物理数据线上划分多个连续时隙（Time Slots），支持 4 / 8 / 16 声道麦克风阵列与多扬声器数据并发；
- **SoundWire**：MIPI 组织制定的新一代统一数字音频总线，双线制（Clock / Data）支持多设备级联、动态唤醒与控制/数据流混合传输；
- **Smart PA（智能功率放大器）**：移动扬声器体积极小，Smart PA 内置升压电路（Boost Converter）将电池电压（3.8V）升至 10V~12V 以输出大音量，并通过实时电流/电压反馈（IV Sensing）算法计算音圈温度与振膜位移，动态限制输出幅度以防止扬声器物理损坏。

音频通路物理属性与采样参数
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

音频 PCM 数据的核心物理特征由三项指标严格决定：

.. list-table:: 移动音频核心物理参数与典型配置
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 物理参数
     - 基础定义
     - 典型取值
     - 物理影响与工程考量
   * - **采样率 (Sample Rate)**
     - 每秒对模拟信号进行采样的次数 ($f_s$)
     - 44.1 kHz (CD标准), 48 kHz (Android标准), 96/192 kHz (Hi-Res)
     - 决定奈奎斯特截止频率 ($f_{\max} = f_s / 2$)；48 kHz 是移动 SoC 硬件标准时钟基准
   * - **量化位深 (Bit Depth)**
     - 每个采样点的数据量化精度
     - 16-bit (整数), 24-bit (高动态), 32-bit (浮点计算)
     - 决定理论信噪比 ($SNR \approx 6.02 	imes N + 1.76 	ext{ dB}$)，16-bit 为 98 dB，24-bit 达 144 dB
   * - **声道数 (Channels)**
     - 独立空间声轨数量
     - 单声道 (Mono), 双声道立体声 (Stereo), 5.1/7.1 空间音频
     - 决定单帧（Frame）数据尺寸：$	ext{FrameSize} = 	ext{Channels} 	imes (	ext{BitDepth} / 8)$

26.2 Linux ALSA 与 TinyALSA 内核音频子系统
------------------------------------------------------------------------

ALSA 体系与 DAPM 动态电源管理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Linux 内核采用 **ALSA（Advanced Linux Sound Architecture）** 管理底层音频设备。ALSA 在移动嵌入式场景下抽象为 **ASoC（ALSA System on Chip）** 架构，将声卡划分为三个解耦模块：

1. **Codec 驱动**：定义物理编解码芯片上的 DAC、ADC、混音器与增益调节逻辑；
2. **Platform 驱动**：定义 SoC 片上数字音频接口（DAI）与 DMA 传输控制器驱动；
3. **Machine 驱动**：作为粘合层，将特定电路板上的 Codec 与 Platform DAI 端口进行时钟与引脚绑定。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       ALSA SoC (ASoC) 驱动架构模型                      |
   +-------------------------------------------------------------------------+

   [ Machine 驱动 (板级绑定层 / Device Tree) ]
   +-------------------------------------------------------------------------+
   | - 绑定 DAI Link (例如: SoC I2S0 <---> Realtek ALC5686 Codec)            |
   | - 注册声卡实体: snd_soc_register_card()                                 |
   +-------------------------------------------------------------------------+
         |                                                 |
         v                                                 v
   [ Platform 驱动 (SoC 数字音频控制器) ]       [ Codec 驱动 (编解码器芯片) ]
   +------------------------------------+       +----------------------------+
   | - DMA 引擎驱动 (snd_soc_platform)  |       | - 寄存器表与音量 Controls  |
   | - CPU DAI 驱动 (I2S / PCM / TDM)   |       | - Codec DAI 驱动           |
   | - 物理中断与 DMA 环形缓冲区管理    |       | - DAPM 音频电源路径拓扑    |
   +------------------------------------+       +----------------------------+

**DAPM（Dynamic Audio Power Management）** 是 ASoC 针对移动设备的能耗治理核心：
- DAPM 将声卡内部的每一个模拟组件（DAC、ADC、PGA、Mixer、耳机放大器）抽象为一个 **DAPM Widget（微型电源部件）**；
- 组件之间通过 **DAPM Route（音频路径路线图）** 逻辑相连；
- 只有当一条从音频源（如 PCM Playback）到目标物理输出端点（如 Headphone Jack）的完整通路被激活时，DAPM 才会自动给该路径上的相关硬件寄存器上电，其余未使用的模拟电路则保持彻底断电，从而将音频待机漏电降至最低。

ALSA PCM 环形缓冲区微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在内核空间，ALSA 为 PCM 数据流维护一块连续的 DMA 环形缓冲区（Ring Buffer）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   ALSA PCM 环形缓冲区 (DMA Ring Buffer) 拓扑            |
   +-------------------------------------------------------------------------+

   DMA 物理内存缓冲区 (Buffer Size = 4 * Period Size)
   +--------------------+--------------------+--------------------+--------------------+
   |  Period 0 (帧片段) |  Period 1 (帧片段) |  Period 2 (帧片段) |  Period 3 (帧片段) |
   +--------------------+--------------------+--------------------+--------------------+
   0                    1                    2                    3                    4
   ^                                         ^                                         ^
   | hw_ptr (硬件 DMA 读取指针)              | appl_ptr (用户态写入指针)               | 环形回卷边界

- **Period（硬件中断周期）**：DMA 控制器每传输完一个 Period 的数据，就会触发一次硬件中断（Hardware IRQ），通知内核与用户态推进指针；
- **Buffer Size（总缓冲区尺寸）**：整个环形缓冲的总容量，必须是 Period Size 的整数倍（通常为 2 ~ 4 个 Period）；
- **`hw_ptr`**：硬件 DMA 控制器当前正在向 DAC 传输数据的物理指针（由硬件中断单向推移）；
- **`appl_ptr`**：用户态音频服务（如 AudioFlinger / TinyALSA）当前已写入 PCM 样本的应用指针；
- **XRun 状态（Underflow / Overflow）**：
  - **Underrun（下溢/欠载）**：用户态写入过慢，`hw_ptr` 追上 `appl_ptr`，DMA 读到无效数据，硬件产生杂音或静音；
  - **Overrun（上溢/过载）**：录音场景下用户态读取过慢，`hw_ptr` 覆盖了尚未被应用读取的有效样本，导致丢帧。

为什么移动端使用 TinyALSA 替代 ALSA-lib？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

标准 Linux 桌面发行版使用体积庞大、依赖 glibc 的 `alsa-lib`。Android 彻底剔除了 `alsa-lib`，开发了轻量级的 **TinyALSA**：

.. list-table:: TinyALSA vs 传统 ALSA-lib 对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 对比维度
     - 传统桌面 ALSA-lib
     - Android TinyALSA
   * - **代码体积与依赖**
     - 庞大，依赖复杂配置文件与动态插件系统（几十 MB）
     - 仅包含 2 个核心 C 文件（`pcm.c`, `mixer.c`），编译体积数十 KB
   * - **内核交互方式**
     - 封装多层复杂抽象，调用开销大
     - 直接通过 `ioctl()` 读写 `/dev/snd/pcmC0D0p` 与 `/dev/snd/controlC0`
   * - **混音与格式转换**
     - 包含用户态软件混音（dmix）与重采样插件
     - 零多余插件，仅提供原始数据读写，混音由 AudioFlinger 统一接管
   * - **实时性与确定性**
     - 包含锁与动态内存分配，时延抖动不可控
     - 极精简代码路径，内存静态分配，无死锁隐患

TinyALSA 核心 API 代码范式：

.. code-block:: c

   #include <tinyalsa/pcm.h>
   #include <tinyalsa/mixer.h>

   struct pcm_config config = {
       .channels = 2,
       .rate = 48000,
       .period_size = 240,     /* 单个周期 240 帧 (5ms) */
       .period_count = 4,      /* 总共 4 个周期，总缓冲 20ms */
       .format = PCM_FORMAT_S16_LE,
       .start_threshold = 240,
       .stop_threshold = 0,
   };

   /* 打开声卡 0、设备 0 的放音通路 (PCM_OUT) */
   struct pcm *pcm = pcm_open(0, 0, PCM_OUT, &config);
   if (!pcm_is_ready(pcm)) {
       /* 错误处理: pcm_get_error(pcm) */
   }

   /* 写入 PCM 帧数据 (直接陷入内核 ALSA 驱动) */
   pcm_write(pcm, audio_buffer, buffer_bytes);

   /* 关闭并释放设备 */
   pcm_close(pcm);

26.3 Android 音频中枢：AudioFlinger 与 AudioPolicyService
------------------------------------------------------------------------

策略与执行解耦架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Android 音频服务系统由运行在 `audioserver` 守护进程（独立用户态 UID `audioserver`）中的两大核心引擎构成：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                Android AudioServer 核心双引擎架构拓扑                   |
   +-------------------------------------------------------------------------+

   [ 客户端应用进程 (App Process) ]
   +-------------------------------------------------------------------------+
   | MediaPlayer / AudioTrack / ExoPlayer / Oboe                             |
   +-------------------------------------------------------------------------+
          |                                                   |
          | Binder RPC (控制命令 / 路由请求)                  | Binder RPC (音频数据流)
          v                                                   v
   +===================================+   +=================================+
   | AudioPolicyService (控制与策略中枢)|   | AudioFlinger (音频执行与混音引擎)|
   |                                   |   |                                 |
   | - 设备拓扑发现与动态路由          |   | - 线程模型 (PlaybackThread)     |
   | - 音量曲线换算 (Volume Curves)    |   | - 软件多流混音器 (AudioMixer)   |
   | - 音频焦点仲裁 (Audio Focus)      |   | - 音效处理链 (AudioEffect Chain)|
   | - 策略配置解析 (audio_policy.xml) |   | - 共享内存代理 (ClientProxy)    |
   +===================================+   +=================================+
                      |                                       |
                      | 路由决策通知 (openOutputStream)       |
                      +--------------------------------------->
                                                              |
                                                              v
   +-------------------------------------------------------------------------+
   | Audio HAL 驱动层 (Stable AIDL: IModule / IStreamOut)                    |
   +-------------------------------------------------------------------------+

1. **AudioPolicyService（决策层）**：
   - 监听物理外设插拔事件（如耳机插入、蓝牙 A2DP 连接、HDMI 连接）；
   - 根据音频属性（`AudioAttributes`: `USAGE_MEDIA`, `USAGE_VOICE_COMMUNICATION`）决定音频应该路由到哪个物理输出端口；
   - 维护音量曲线表（Volume Curves），将上层 0~15 级音量平滑映射为硬件分贝值（dB）。
2. **AudioFlinger（执行层）**：
   - 作为音频硬件在用户态的直接管理者；
   - 为每个物理输出流创建专用的工作线程（`PlaybackThread`）；
   - 负责将多个应用发送过来的不同采样率、不同声道数的 PCM 数据进行重采样（Resample）、格式转换、音量增益调节以及多路混音。

AudioFlinger 核心线程模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

AudioFlinger 内部针对不同的音频场景设计了专门的线程子类：

.. list-table:: AudioFlinger PlaybackThread 核心子类与工作机制
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 线程类型
     - 调度策略与优先级
     - 适用音频场景
     - 核心机制与特征
   * - **MixerThread**
     - `SCHED_OTHER` / `SCHED_FIFO`
     - 普通应用媒体播放、系统提示音
     - 使用 `AudioMixer` 软件混音器，周期较长（通常 20ms），容忍少量调度抖动
   * - **FastMixer (FastThread)**
     - `SCHED_FIFO` (实时优先级 2/3)
     - 游戏音效、实时乐器演奏、VR
     - 专用小周期硬件 Buffer（如 4ms / 192 帧），使用非阻塞状态机与无锁队列
   * - **DirectOutputThread**
     - `SCHED_OTHER`
     - 高解析度音频 (Hi-Res PCM)、多声道 DDP
     - **不执行任何软件混音**，将特定格式 PCM 直通送往支持该格式的硬件 DAC
   * - **OffloadThread**
     - `SCHED_OTHER`
     - 纯音频音乐播放 (MP3/AAC 熄屏播放)
     - 压缩音频原码直接送往硬件 DSP，CPU 写入大块数据后进入长时间挂起休眠
   * - **RecordThread**
     - `SCHED_FIFO`
     - 麦克风录音、语音通话上行
     - 从硬件获取音频流，通过 `AudioResampler` 转换后分发给多个录音客户端

AudioTrack 共享内存无锁传输拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了避免每个音频采样包都通过 Binder 驱动引发内存拷贝与上下文切换，`AudioTrack` 与 `AudioFlinger` 之间使用 **共享内存（Shared Memory / ashmem / memfd）** 配合原子代理状态机进行通信：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                AudioTrack 跨进程共享内存与无锁状态机拓扑                |
   +-------------------------------------------------------------------------+

   [ 客户端进程 (App: AudioTrack) ]            [ AudioServer (AudioFlinger) ]
   +------------------------------+            +----------------------------+
   | ClientProxy (客户端代理)     |            | AudioTrackServerProxy      |
   +------------------------------+            +----------------------------+
                 |                                           |
                 | (用户态内存映射, 无系统调用开销)          |
                 v                                           v
   +=========================================================================+
   | 共享内存块 (Shared Memory Buffer: 由 IAudioFlinger 创建并传递 FD)       |
   |                                                                         |
   | +---------------------------------------------------------------------+ |
   | | audio_track_cblk_t 控制块 (Control Block: 包含原子环形头)           | |
   | | - mServer (服务端已消费位置)      - mUser (客户端已生产位置)        | |
   | | - mFlags (状态标志)               - mVolumeHandler (动态音量参数)   | |
   | +---------------------------------------------------------------------+ |
   | | 原始 PCM 环形音频数据区 (Circular Audio Buffer: PCM Samples)        | |
   | | [ Frame 0 ] [ Frame 1 ] [ Frame 2 ] ... [ Frame N-1 ]              | |
   | +---------------------------------------------------------------------+ |
   | | Futex 同步唤醒字 (Futex Word: 供缓冲区满/空时挂起与唤醒)            | |
   | +---------------------------------------------------------------------+ |
   +=========================================================================+

- **`audio_track_cblk_t`**：驻留在共享内存头部的控制结构体；
- **无锁位置推进**：客户端调用 `AudioTrack.write()` 时，`ClientProxy` 计算可用空闲空间，向环形数据区拷贝 PCM 样本，并原子递增 `mUser` 指针；`MixerThread` 混音循环中，`AudioTrackServerProxy` 读取样本并原子递增 `mServer` 指针；
- **Futex 唤醒退化机制**：仅当共享内存环形缓冲区写满（Buffer Full，应用需等待）或读空（Buffer Empty，服务端挂起）时，双方才会触发内核 `futex()` 系统调用进行休眠与唤醒。

26.4 现代 Audio AIDL HAL 微架构与 DSP 硬件卸载
------------------------------------------------------------------------

Audio HAL 演进历程
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. list-table:: Android Audio HAL 架构演进全景
   :widths: 18 22 30 30
   :header-rows: 1
   :class: tight-table

   * - 架构代际
     - 接口定义形式
     - 运行模型
     - 核心优缺点
   * - **Legacy HAL**
     - `audio.h` (C 语言函数指针)
     - 加载进 `audioserver` 进程空间 (`dlopen`)
     - 零 IPC 开销，但 Vendor 代码崩溃将直接拖垮整个系统音频服务
   * - **HIDL HAL**
     - `android.hardware.audio@7.0`
     - 独立 Vendor 进程 (`android.hardware.audio-service`)
     - 实现 Binder 跨进程隔离，但接口繁复，对象生命周期难以精准控制
   * - **Stable AIDL**
     - `android.hardware.audio.core-V1` (Android 14+)
     - 统一 Stable AIDL 接口契约
     - 消除结构体冗余，强类型版本化，原生支持 AIDL Fast Message Queue

Stable AIDL Audio HAL 核心契约
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代 Audio HAL 的核心接口定义如下：

.. code-block:: java

   package android.hardware.audio.core;

   interface IModule {
       // 1. 设置声卡主时钟与连接配置
       void setMasterMute(boolean mute);
       void setMasterVolume(float volume);

       // 2. 打开输出音频流 (PCM 放音 / 硬件直通 / Offload)
       IStreamOut openOutputStream(in StreamDescriptor desc, in AudioPortConfig mixPortConfig);

       // 3. 打开输入音频流 (麦克风录音 / 通话回采)
       IStreamIn openInputStream(in StreamDescriptor desc, in AudioPortConfig mixPortConfig);

       // 4. 获取支持的物理设备端口与路由连接能力

Audio Offload (硬件 DSP 卸载) 节能微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统的 PCM 播放模式下，CPU 必须每隔 5ms~20ms 唤醒一次以向 Audio HAL 投递 PCM 数据，这使得 CPU 无法进入深度低功耗状态（C-States）。

**Audio Offload（音频硬件卸载）** 彻底改变了这一能耗路径：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Audio Offload 硬件卸载数据流拓扑                    |
   +-------------------------------------------------------------------------+

   [ 音乐播放器应用 (Music App) ]
   +-------------------------------------------------------------------------+
   | 播放 MP3 / AAC 音频文件 (以大块压缩数据写入, 例如一次写入 512KB)        |
   +-------------------------------------------------------------------------+
                                      |
                                      v (直接传递压缩数据, 绕过 AudioMixer 软件重采样)
   [ AudioFlinger: OffloadThread ]
   +-------------------------------------------------------------------------+
   | 1. 将大块压缩音频写入 Audio HAL Offload 驱动;                           |
   | 2. 设置长周期硬件定时器;                                                |
   | 3. 主 CPU (AP) 彻底进入 Suspend 深度休眠模式 (功耗降至 ~3mA)            |
   +-------------------------------------------------------------------------+
                                      |
                                      v DMA 传输至片上共享 SRAM
   [ 专用音频 DSP (Low-Power Audio Subsystem / Hexagon ADSP) ]
   +-------------------------------------------------------------------------+
   | - 运行硬件 MP3/AAC 解码器固件;                                          |
   | - 运行硬件音效算法 (EQ / Bass Boost);                                   |
   | - 直接驱动硬件 DAC 进行播放;                                            |

26.5 低时延音频链路：FastMixer、AAudio 与 Oboe
------------------------------------------------------------------------

传统音频链路的时延成因剖析
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

标准 Android 音频输出时延通常高达 **80 ms ~ 150 ms**，其物理开销分布如下：

1. **应用层缓冲（10 ms ~ 30 ms）**：Java 垃圾回收与线程调度抖动迫使应用预留较大 Buffer；
2. **AudioTrack JNI 桥接与 ClientProxy 写入（5 ms）**；
3. **AudioFlinger MixerThread 周期（20 ms ~ 40 ms）**：标准混音线程的周期性调度间隔；
4. **AudioMixer 软件混音与音效处理（5 ms ~ 10 ms）**；
5. **HAL 驱动缓冲区与 ALSA DMA Ring Buffer（20 ms ~ 40 ms）**；
6. **硬件 DAC 转换与模拟输出延迟（2 ms ~ 5 ms）**。

FastMixer 实时混音微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了将延迟压缩至 **10 ms ~ 20 ms** 黄金标准，AudioFlinger 引入了 **FastMixer**：

- **`SCHED_FIFO` 实时调度**：FastMixer 线程被配置为 Linux 实时调度策略（`SCHED_FIFO`，静态优先级高于所有普通 UI 和后台线程），保证在每个周期到达时无条件抢占 CPU；
- **StateQueue 非阻塞状态机**：普通 `MixerThread` 与 `FastMixer` 之间通过无锁 `StateQueue` 传递控制命令，**FastMixer 线程执行循环中严禁调用任何可能引发阻塞的系统调用（无 Mutex 锁、无内存分配 malloc、无 Binder 调用、无文件 I/O）**；
- **小周期硬件 Burst Size**：直接匹配底层 ALSA 驱动的单个 Period 尺寸（通常为 192 帧 / 4ms），每个周期精准处理 192 帧数据并立即送入硬件。

AAudio 与 Oboe：MMAP 硬件直连模式
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

针对极端专业的音频场景（如实时音频合成器、DJ 打碟、游戏低时延监听），Google 引入了原生 C API **AAudio**（C++ 封装层为 **Oboe**）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              AAudio MMAP 独占模式 (Direct Hardware Path)                |
   +-------------------------------------------------------------------------+

   [ 客户端应用进程 (Pro-Audio / Game Engine) ]
   +-------------------------------------------------------------------------+
   | Oboe / AAudio C++ 引擎 (AAUDIO_PERFORMANCE_MODE_LOW_LATENCY)            |
   | - 直接通过 MMAP 指针向共享硬件缓冲区写入 PCM 样本                       |
   +-------------------------------------------------------------------------+
                                      |
                                      | (完全旁路 AudioServer / AudioFlinger / 混音器)
                                      v
   +=========================================================================+
   | ALSA 内核 PCM DMA 缓冲区 (Kernel DMA Memory Map)                        |
   |                                                                         |
   | - 客户端进程直接获得 ALSA DMA 物理缓冲区的用户态虚拟地址映射 (mmap)     |
   | - 写入的数据由硬件 DMA 引擎直接读取并送入 DAC 转换                      |
   +=========================================================================+
                                      |
                                      v
                             [ 硬件 DAC -> 扬声器 ]

- **MMAP Shared 模式**：多个低时延应用共享一个紧凑的底层 ALSA 缓冲区；
- **MMAP Exclusive（独占模式）**：单个应用独占整个硬件 ALSA DMA 缓冲区，数据传输完全绕过整个 Android 软件框架层，直接实现 **< 10ms 端到端输出时延**。

小结与下章导读
------------------------------------------------------------------------

本章系统剖析了移动操作系统音频与多媒体子系统的端到端微架构：从多通道 I2S/TDM 总线与 Codec/Smart-PA 模拟信号链，到 Linux ALSA SoC 架构的 DAPM 动态电源管理与 TinyALSA 极简内核交互；从 Android `audioserver` 中 AudioPolicy 策略路由与 AudioFlinger 多线程混音引擎的解耦拓扑，到 Stable AIDL Audio HAL 与 Audio Offload 硬件节能卸载机制；最后深入推导了 FastMixer 实时无锁混音与 AAudio/Oboe 硬件 MMAP 独占直连带来的极致低时延物理实现。

========================================================================
Chapter 9: GPU 移动渲染与硬件合成输出：TBDR、BufferQueue 与 HWC
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了 ARM DynamIQ 共享 DSU 拓扑、Linux EAS 调度器容量模型、Schedutil 动态调频数学模型与触控交互前台提速（Interactive Boost）。在智能手机全栈运行链路中，应用界面的视觉呈现是由 GPU 图形渲染引擎与专用显示合成硬件协同完成的。移动终端由于受到严苛的 LPDDR 带宽与功耗约束，无法采用桌面 GPU 的立即模式渲染（IMR），而是全面拥抱贴片延迟渲染（TBDR）。本章将系统剖析移动 GPU 贴片延迟渲染微架构（Tile Buffer & Hidden Surface Removal）、Android 核心图层数据流管道（Surface / BufferQueue 三缓冲队列）、同步围栏（Sync Fence）机制，以及专用硬件合成器（Hardware Composer - HWC）的多图层零拷贝叠加与 DPU 扫描输出。

------------------------------------------------------------------------
9.1 桌面 IMR vs 移动 TBDR (Tile-Based Deferred Rendering) 架构
------------------------------------------------------------------------

图形渲染的物理本质，是将三维多边形或二维矢量图形转换为屏幕像素网格的颜色值。桌面独立显卡与移动 SoC 在硬件微架构上走向了两条截然不同的技术路线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             桌面 IMR (立即模式) vs 移动 TBDR (贴片延迟渲染) 架构对比    |
   +-------------------------------------------------------------------------+

   [ 桌面 GPU: 立即模式渲染 (Immediate Mode Rendering - IMR) ]
   [ DrawCall 提交 ]
        |
        v
   [ 顶点着色 (VS) ] -> [ 立即光栅化 (Rasterize) ] -> [ 像素着色 (PS) ] -> [ 写入外部 VRAM ]
   * 物理缺陷: 每次着色与深度测试频繁读写外部高功耗显存，发热高达数十瓦，移动端绝对无法承受！

   [ 移动 GPU: 贴片延迟渲染 (Tile-Based Deferred Rendering - TBDR) ]
   [ 阶段 1: 几何分块 (Binning Pass) ]
   [ 顶点着色 (VS) ] -> [ 屏幕划分为 16x16 像素 Tiles ] -> [ 构建每个 Tile 的图元列表 (Bin List) ]
        | (几何处理完毕，进入第二阶段)
        v
   [ 阶段 2: 贴片光栅化与延迟着色 (Tiling & Shading Pass) ]
   逐个将 Tile 加载至 GPU 片上极速 SRAM (Tile Memory, 延迟仅 1ns, 功耗极低!):
        |
        +---> 1. 硬件隐式表面剔除 (Hidden Surface Removal - HSR / Forward Pixel Kill)
        |        * 在片上深度缓冲区完成全部图元深度排序，仅对最终可见像素执行 1 次着色！
        +---> 2. 执行像素着色器 (PS)
        +---> 3. Tile 渲染完毕后，单次批量写回外部 LPDDR5X 显存 (End-of-Tile Writeback)

.. list-table:: 桌面 IMR 与移动 TBDR 渲染架构核心微架构对比
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 架构维度
     - 桌面 IMR 架构
     - 移动 TBDR 架构
     - 移动系统能效收益
   * - **显存读写位置**
     - 外部独立显存 (VRAM)
     - **GPU 片上高带宽 SRAM (Tile Buffer)**
     - 减少 80% 以上的高功耗 DRAM 总线访存
   * - **Overdraw (过绘制) 处理**
     - 依赖 Early-Z，非严格排序时无效着色高
     - **硬件级 HSR / FPK 严格剔除不可见表面**
     - 无论应用层渲染顺序如何，着色计算量降至最低
   * - **Alpha Test / Discard**
     - 硬件无额外惩罚
     - 会打断 HSR 预排序，迫使 Tile 回退为常规模式
     - 移动端开发必须严格限制 `discard` 指令使用
   * - **代表硬件**
     - NVIDIA RTX, AMD Radeon 桌面卡
     - **Apple GPU, Qualcomm Adreno, ARM Immortalis**
     - 支撑手机以 < 3W 功耗实现高画质 120Hz 渲染

9.2 Gralloc 显存分配器与 DMA-BUF 零拷贝流转
------------------------------------------------------------------------

在移动操作系统中，相机的原始视频帧（ISP 采集）、硬件解码器输出（MediaCodec）、应用界面的 OpenGL/Vulkan 绘制（App RenderThread）以及负责最终合成的系统服务（SurfaceFlinger），运行在完全隔离的独立进程中。

为了避免在进程间复制数兆字节的高清图像数据，移动内核引入了**基于 DMA-BUF 的图形内存中介机制**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 Gralloc 驱动与 DMA-BUF 跨进程零拷贝流转架构             |
   +-------------------------------------------------------------------------+

   [ 应用进程 (App RenderThread) ]              [ 厂商 Gralloc HAL 驱动 (/dev/ion 或 /dev/dma_heap) ]
        |                                                              |
        +--- 1. 调用 AHardwareBuffer_allocate() / gralloc.allocate() ->+
                                                                       |
        +<-- 2. 导出标准 Linux 文件描述符 (dma_buf fd) <---------------+
        |
   [ 3. 通过 Binder IPC 将 dma_buf fd 传递给系统服务 ]
        |
        v
   [ 接收端进程 (SurfaceFlinger / HWComposer) ]
        |
        +---> 4. 内核 mmap(fd) 将同一组物理内存直接映射至当前进程虚拟地址空间！
        * 物理效果: 零数据拷贝！GPU、ISP、DPU 全部通过硬件 DMA 直接读写同一块物理内存颗粒！

硬件无损压缩格式协商 (AFBC / UBWC)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Gralloc 在分配显存时，还会自动协商厂商专有的硬件压缩标志（如 ARM AFBC - Arm Frame Buffer Compression，高通 UBWC - Universal Bandwidth Compression）。显存数据在 GPU 写入时被硬件实时压缩，DPU 扫描显示时硬件直接解压，使得整机显存总线带宽进一步削减 50%。

9.3 Surface 与 BufferQueue 三缓冲 (Triple Buffering) 状态机
------------------------------------------------------------------------

Android 图形子系统的核心数据流管道由 **BufferQueue** 驱动，其本质是一个高并发无锁的生产者-消费者（Producer-Consumer）循环队列。

BufferQueue 四状态生命周期状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       BufferQueue 四状态流转状态机                      |
   +-------------------------------------------------------------------------+

                 +-----------------------------------------+
                 |                                         | releaseBuffer()
                 v                                         | (消费者消费完毕)
             [ FREE: 空闲槽位 ]                            |
                 |                                         |
                 | dequeueBuffer() (生产者申请绘制槽位)    |
                 v                                         |
             [ DEQUEUED: 正在由 GPU / CPU 绘制渲染 ]       |
                 |                                         |
                 | queueBuffer() (生产者绘制完毕入队)      |
                 v                                         |
             [ QUEUED: 就绪就绪队列中，等待合成 ]          |
                 |                                         |
                 | acquireBuffer() (SurfaceFlinger 获取合成)|
                 v                                         |
             [ ACQUIRED: 正在由 HWC / DPU 硬件扫描输出 ] --+

双缓冲 (Double Buffering) vs 三缓冲 (Triple Buffering) 流水线对齐
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **双缓冲的缺陷（Jank 级联）**：若系统仅分配 2 个 Buffer（前台显示 Buffer 0，后台绘制 Buffer 1）。当应用因偶发计算复杂度导致第 $N$ 帧在 VSYNC 信号到来时未绘制完成，Buffer 0 必须继续显示，导致第 $N$ 帧掉帧；由于此时 Buffer 1 仍被占用且 Buffer 0 仍在扫描，应用主线程**在接下来的整个 VSYNC 周期内被强制挂起阻塞**，导致后续连续多帧发生雪崩式卡顿。
- **三缓冲机制（Triple Buffering）**：通过引入第 3 个 Buffer，当 Buffer 0 正在显示且 Buffer 1 发生绘制超时时，应用可以直接申请 Buffer 2 **立即开始下一帧的计算**，最大程度利用 CPU/GPU 算力平滑偶发卡顿，将掉帧概率压制至极限。

9.4 显式同步机制：Sync Fence 与 Timeline Semaphore
------------------------------------------------------------------------

在跨进程高并发图形流水线中，CPU 不能通过阻塞等待（如 `glFinish()`）来确认 GPU 绘制完成，否则会导致 CPU 占用率飙升与严重的流水线气泡。现代移动 OS 全面采用**显式同步围栏（Explicit Sync Fence）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   显式同步 Sync Fence 全链路无阻塞流水线                |
   +-------------------------------------------------------------------------+

   [ 应用 RenderThread (GPU 生产者) ]
        |
        +---> 向 GPU 提交绘图指令 (非阻塞立即返回!)
        +---> 创建 acquire_fence (表示 GPU 正在绘制)
        +---> 调用 queueBuffer(slot, acquire_fence) 将 Buffer 传递给 SurfaceFlinger
        |
   [ 系统合成器 SurfaceFlinger (消费/中继端) ]
        |
        +---> 接收到 Buffer 与未触发的 acquire_fence (CPU 完全不等待!)
        +---> 将 Buffer 与 acquire_fence 打包直接下发给硬件合成驱动 HWC
        |
   [ 硬件合成器 HWC / DPU (显示端) ]
        |
        +---> 硬件监听: 当 GPU 完成最后一条像素写入时，硬件瞬间触发 acquire_fence 信号!
        +---> DPU 硬件零延迟启动物理扫描输出!
        +---> DPU 扫描完成后触发 release_fence 信号，通知应用槽位已可安全重写。

9.5 硬件合成器 (Hardware Composer - HWC) 与 DPU 扫描输出
------------------------------------------------------------------------

现代智能手机屏幕上通常同时并存多个图层（Layers）：系统状态栏、导航栏、壁纸、浮动窗口、视频播放器图层以及应用主体视图。

GPU 合成 (GLES Composition) 的昂贵代价
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

早期 Android 使用 GPU（OpenGL ES）将所有图层逐层绘制到一个统一的全屏 FrameBuffer 中。在 120Hz 刷新率下，GPU 每秒需要额外执行 120 次多图层混合光栅化，消耗数十毫秒算力与数 GB/s 显存带宽，导致整机发热剧烈。

专用显示处理器 (DPU) 与 HWC 硬件合成微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代移动 SoC 内部集成了专用的**显示处理单元（Display Processing Unit - DPU）**。**硬件合成器（Hardware Composer - HWC HAL）** 是连接 SurfaceFlinger 与 DPU 硬件的控制中枢：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     HWC 两阶段图层合成协商状态机                        |
   +-------------------------------------------------------------------------+

   [ SurfaceFlinger 收集系统当前所有可见图层 (Layers) ]
        |
        v
   [ 1. 准备阶段 (Prepare / ValidateDisplay) ]
        |  * SurfaceFlinger 将所有图层的位置、尺寸、透明度与 Transform 提交给 HWC HAL;
        |  * HWC 查询 DPU 硬件能力 (例如 DPU 拥有 6 个独立的硬件 Overlay 混音管道);
        |  * HWC 对每个图层判定合成模式:
        |     +-> 支持的图层标记为: HWC_OVERLAY (由 DPU 硬件直出!)
        |     +-> 复杂的特殊混合图层标记为: HWC_FRAMEBUFFER (回退至 GPU 预合成)
        v
   [ 2. 呈现阶段 (Present / SetDisplay) ]
        |  * DPU 硬件在读取显存的瞬间，直接通过片上混音电路完成图层叠加与缩放，
        |    通过 MIPI DSI 接口直接驱动物理 OLED 屏幕点阵刷新!
        * 收益: 彻底释放 GPU 算力！GPU 功耗与显存回写开销完全归零！

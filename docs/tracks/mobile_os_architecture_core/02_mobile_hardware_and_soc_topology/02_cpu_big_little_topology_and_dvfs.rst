========================================================================
Chapter 8: CPU 大小核异构拓扑与动态调频：EAS、DVFS 与前台加速
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了移动 SoC 芯片级异构拓扑、片上网络（NoC）互连总线与 UMA 统一内存架构。在众多片上算力单元中，CPU 集群依然是通用操作系统指令执行与逻辑决策的中枢。智能手机无法像桌面 PC 那样维持对称多处理（SMP）的高频运转，必须依托非对称大小核架构实现能耗与性能的极致平衡。本章将深入 ARM DynamIQ 共享 DSU 拓扑、Linux 能效感知调度（EAS）算法模型、CPUFreq / Schedutil 动态电压频率调整（DVFS）数学状态机，以及触控交互时 UI 线程的前台瞬时提速（Interactive Boost）机制。

------------------------------------------------------------------------
8.1 ARM 大小核拓扑演进：从 big.LITTLE 双丛集到 DynamIQ 共享 DSU
------------------------------------------------------------------------

在移动处理器的微架构演进史上，多核拓扑经历了从“物理双丛集”到“单丛集全融合”的深刻重构：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             传统 big.LITTLE 双丛集 vs 现代 DynamIQ 共享 DSU 架构对比    |
   +-------------------------------------------------------------------------+

   [ 早期 big.LITTLE (CCI 双丛集外部互连) ]
   +-----------------------------+       +-----------------------------+
   | Cluster 0: 大核群 (Cortex-A73) |       | Cluster 1: 小核群 (Cortex-A53) |
   | [Core 0] [Core 1] (共用 L2)  |       | [Core 2] [Core 3] (共用 L2)  |
   +--------------+--------------+       +--------------+--------------+
                  |                                     |
                  +-----> [ 外部 CCI-400 互连总线 ] <----+
   * 缺陷: 跨丛集线程迁移需经外部总线同步 L2 缓存，延迟高达 20~50 微秒！

   [ 现代 DynamIQ 架构 (单复合体共享 DSU) ]
   +-------------------------------------------------------------------------+
   | DynamIQ 共享单元 (DSU - DynamIQ Shared Unit)                           |
   |                                                                         |
   |  [ 超大核: Cortex-X4 ] [ 性能大核: 4x Cortex-A720 ] [ 能效小核: 3x A520 ] |
   |        |                       |                         |              |
   |  (独立私有 L2 1MB)       (独立私有 L2 512KB)       (独立私有 L2 256KB)  |
   |        |                       |                         |              |
   |  +-----+-----------------------+-------------------------+-----------+  |
   |  |           全核心共享内部三级缓存 (Shared L3 Cache 8MB)            |  |
   |  |                  + 硬件侦听过滤器 (Snoop Filter)                  |  |
   |  +-------------------------------------------------------------------+  |
   +-------------------------------------------------------------------------+
   * 收益: 核间迁移直接在片上 L3 缓存完成，延迟骤降至 < 1 微秒；支持单核异步调频！

   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 核心分类
     - 代表微架构

   * - **超大核 (Prime / Cortex-X)**
     - Cortex-X4 / Apple Everest

     - Cortex-A520

8.2 能效感知调度器 (EAS) 容量模型与负载追踪
------------------------------------------------------------------------

在异构多核系统中，传统的 Linux CFS 完全公平调度器无法感知不同物理核心的算力差异与功耗模型。移动操作系统全面引入了**能效感知调度（Energy-Aware Scheduling - EAS）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     EAS 调度器唤醒放置核心决策状态机                    |
   +-------------------------------------------------------------------------+

   [ 任务唤醒 (Task Wakeup) ]
        |
        v
   [ 1. 读取任务 WALT / PELT 历史负载估计值 Task_util ]
        |
        v
   [ 2. 候选核心过滤 (Capacity Margin Check) ]
        |  * 若 Task_util > 核心容量 * 80%，过滤掉小核 (防止算力不足导致卡顿)
        v
   [ 3. 能耗增量评估 (Energy Model Evaluation) ]
        |  * 模拟将任务放置在小核: 估算整机能耗增量 Delta_E_little
        |  * 模拟将任务放置在大核: 估算整机能耗增量 Delta_E_big
        |  * 模拟将任务放置在超大核: 估算整机能耗增量 Delta_E_prime
        v
   [ 4. 挑选 Delta_E 最小且满足截止时间预算的物理核心放置任务 ]

PELT (周期性实体负载追踪) vs WALT (窗口辅助负载追踪)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **PELT (Per-Entity Load Tracking - 原生 Linux 方案)**：
  对任务的 CPU 占用进行指数加权移动平均（EWMA，半衰期 32ms）。其数学曲线极其平滑，但在面对触控滑屏等突发高负载时，需要经历数十毫秒的“爬坡期”，极易引发首帧掉帧。
- **WALT (Window-Assisted Load Tracking - 移动平台定制方案)**：
  将时间划分为固定窗口（如与屏幕刷新率对齐的 16.6ms 或 20ms）。调度器直接取上一个窗口内任务的**实际执行时间峰值**作为当前负载预估，对突发任务实现单周期即时捕获，快速拉升算力。

8.3 动态电压与频率调整 (DVFS) 与 Schedutil 调速器
------------------------------------------------------------------------

**动态电压与频率调整（Dynamic Voltage and Frequency Scaling - DVFS）** 构成了 CPU 功耗控制的硬件调节旋钮。

OPP 操作性能点表与 Schedutil 数学公式
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

芯片出厂时，固件内固化了每个核心集群的**操作性能点表（Operating Performance Points - OPP）**，每个频点绑定了安全工作所需的最低供电电压：

.. math::

   	ext{OPP Table} = \Big\{ (f_1, V_1), \; (f_2, V_2), \; \dots, \; (f_n, V_n) \Big\}

Linux 内核中的 **Schedutil 调速器** 直接依据调度器的负载追踪值实时解算目标频点：

.. math::

   f_{	ext{target}} = 1.25 	imes f_{\max} 	imes \frac{	ext{CPU Load}}{	ext{CPU Capacity}}

- 因子 $1.25$ 预留了 25% 的算力冗余（Headroom），确保任务负载突增时不发生执行阻塞。

硬件自主 P-State 控制 (Hardware Controlled P-States - HWP)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代高端移动芯片（如 Apple Silicon 与最新 ARM 核心）引入了硬件级自主调频电路。操作系统仅需下发高层性能诉求（Energy vs Performance Preference），芯片内部的微控制器以 **1ms 以下的极高频次** 硬件自主微调电压与主频，消除了内核软件上下文切换开销。

8.4 触控交互前台提速 (Interactive Boost) 与 UI 线程绑定
------------------------------------------------------------------------

移动操作系统的核心设计准则是“**交互响应优先级绝对高于后台能效**”。当用户手指触摸屏幕的瞬间，系统启动全链路硬件提速：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  触控交互全链路前台瞬时提速时序拓扑                     |
   +-------------------------------------------------------------------------+

   [ 触摸屏硬件中断 (Touch IRQ - 240Hz/360Hz 采样) ]
        |
        v
   [ 内核 Input 子系统 -> Android InputReader / InputDispatcher ]
        |
        v
   [ 触发 CPU Performance Boost (Perfetto Hint / PowerHAL) ]
        |  * 强行解除当前 EAS 能耗约束；
        |  * 在 1 个调度周期内将 CPU 大核/超大核频率强制拉满至最高 OPP 点！
        v
   [ 前台交互线程保障 (Cgroups 拓扑调度) ]
        |
        +---> [ 前台 UI 主线程 (main) & RenderThread ]: 绑定在 top-app cgroup (大核运行)
        |
        +---> [ 后台同步线程 (JobScheduler Worker) ]: 压制在 background cgroup (小核限制)

- **提速脉冲 (Boost Pulse)**：瞬时满频通常维持 100ms ~ 200ms。该策略充分利用了 CMOS 芯片的热容延迟（Thermal Inertia）——在芯片温度尚未明显升高的极短时间内释放极限算力完成首屏渲染，随后迅速回退至平稳频点。

8.5 热约束下的多级协同降频 (Thermal Throttling Coordination)
------------------------------------------------------------------------

当设备由于长时间高负载运行导致机身表面温度逼近安全红线（$43^\circ	ext{C} \sim 45^\circ	ext{C}$）时，系统启动**多级协同温控降频策略**：

.. list-table:: 热约束下 CPU 核心协同降频阶段矩阵
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 控温降频阶段
     - 硬件与内核调度层动作
     - 上层用户体验保护
   * - 阶段 1: 频点封顶
(Frequency Capping)
     - 将 CPU 超大核最高频点限制在额定值的 70%（如 3.4GHz 封顶在 2.4GHz）
     - 维持 120Hz/90Hz 刷新率，基本无感知
   * - 阶段 2: 核心热拔插
(Core Offlining)
     - 彻底切断超大核供电轨（Offline），将前台 UI 线程回退至性能大核运行
     - 系统将屏幕刷新率降级至 60Hz，保证界面稳定
   * - 阶段 3: 激进任务下迁
(Forced Demotion)
     - 强制限制大核主频，将非核心前台任务全量压入能效小核运行
     - 限制游戏后台帧率，优先保证电话与紧急通信能力

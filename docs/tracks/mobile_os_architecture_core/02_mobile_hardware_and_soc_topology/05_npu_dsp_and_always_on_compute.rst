11.1 端侧张量计算物理本质：为什么 CPU/GPU 无法满足 AI 能效比？
------------------------------------------------------------------------

深度学习模型（如 CNN 卷积、Transformer 自注意力机制矩阵乘法）的核心数学本质是高密度的**通用矩阵乘加运算（GEMM - General Matrix Multiply）**：

.. math::

   \mathbf{C} = \alpha (\mathbf{A} 	imes \mathbf{B}) + \beta \mathbf{C}

张量计算具有极高的算术强度（Arithmetic Intensity = $\frac{	ext{FLOPs}}{	ext{Byte}}$）与极规整的并行数据流。但在移动终端严格的电池供电约束下，传统通用处理器的微架构暴露出严重的物理短板：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             CPU / GPU / NPU 执行张量乘加运算的硬件能耗分布对比          |
   +-------------------------------------------------------------------------+

   [ 通用 CPU (耗电主要在指令控制) ]
   +-------------------------------------------------------------+
   | 指令译码 (30%) | 乱序发射与分支预测 (35%) | 寄存器读写 (20%) | ALU 计算 (15%) |
   +-------------------------------------------------------------+
   * 能效比: 1 ~ 3 TOPS/W (绝大多数电能浪费在指令流控制与分支预测电路上)

   [ 图形 GPU (耗电主要在通用着色开销) ]
   +-------------------------------------------------------------+
   | SIMT 线程调度 (20%) | 显存纹理缓存 (30%) | 向量寄存器 (25%) | 算术乘加 (25%) |
   +-------------------------------------------------------------+
   * 能效比: 8 ~ 15 TOPS/W (为可编程图形流水线设计，定点矩阵能效依然次优)

   [ 专用 NPU / 张量引擎 (极致纯算力密集) ]
   +-------------------------------------------------------------+
   | 极简控制流 (2%) | 片上紧耦合 SRAM (18%) | 密集脉动乘加阵列 (80%!)  |
   +-------------------------------------------------------------+
   * 能效比: 30 ~ 50 TOPS/W! (90% 晶体管直接化为乘加器，片上数据高度复用)

.. list-table:: 移动计算单元张量推理特征对比矩阵
   :widths: 18 20 20 22 20
   :header-rows: 1
   :class: tight-table

   * - 处理器类型
     - 核心计算微架构
     - 原生数据类型
     - 编程与调度模型
     - 典型能效比区间
   * - **应用 CPU**
     - 超标量乱序多发射 + NEON
     - FP32, FP16, INT8
     - 通用 C/C++ 线程，OS 内核调度
     - 1 ~ 3 TOPS/W
   * - **移动 GPU**
     - TBDR SIMT 向量流水线
     - FP32, FP16, INT8
     - OpenCL / Vulkan Compute / Metal
     - 8 ~ 15 TOPS/W
   * - **专用 DSP**
     - VLIW 超长指令字 + 向量拓展
     - INT8, INT16, FP16
     - 专用微内核 RTOS + RPC 驱动
     - 15 ~ 25 TOPS/W
   * - **神经处理单元 (NPU)**
     - **二维脉动阵列 (Systolic Array)**
     - **INT8, INT4, FP16, Microscaling**
     - **硬件指令图引擎 (Graph Engine)**
     - **30 ~ 50 TOPS/W**

11.2 NPU 脉动阵列 (Systolic Array) 与低比特量化微架构
------------------------------------------------------------------------

脉动阵列 (Systolic Array) 数据流拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动 NPU（如 Apple Neural Engine - ANE、高通 Hexagon NPU）普遍采用**脉动阵列**拓扑。其设计灵感源于人体血液循环：数据以固定的时钟节拍在二维网格化的处理单元（Processing Element - PE）阵列中沿行与列有节奏地流动与计算。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    2D 脉动阵列 (Weight-Stationary) 硬件流拓扑           |
   +-------------------------------------------------------------------------+

              特征图输入流 Input Data (逐拍移位输入)
                 |         |         |
                 v         v         v
        +--------+---------+---------+--------+
        | PE(0,0) -> PE(0,1) -> PE(0,2) ...   |   * 权重静态驻留 (Weight Stationary):
        +--------+---------+---------+--------+     神经网络权重预先载入各 PE 内部寄存器
        | PE(1,0) -> PE(1,1) -> PE(1,2) ...   |   * 特征图在横向与纵向 PE 间直接传递
        +--------+---------+---------+--------+   * 局部累加结果直接在片上完成融合
        | PE(2,0) -> PE(2,1) -> PE(2,2) ...   |   * 彻底避免了频繁读取外部 DRAM 的巨大能耗!
        +--------+---------+---------+--------+
                 |         |         |
                 v         v         v
              矩阵输出结果流 Output Accumulator

低比特量化 (INT8 / INT4) 与稀疏化加速
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **线性非对称量化数学映射**：
   将 32 位浮点数 $x \in [\alpha, \beta]$ 线性压缩为 8 位定点整数 $q \in [-128, 127]$：

   .. math::

      q = 	ext{round}\left( \frac{x}{S} \right) + Z, \quad S = \frac{\beta - \alpha}{q_{\max} - q_{\min}}

   - 8 位乘加器（INT8 MAC）的硅片面积仅为 32 位浮点乘加器（FP32 MAC）的 **15%**，功耗仅为 **10%**；
   - 模型权重体积直接削减 75%，大幅释放系统 DRAM 显存带宽。
2. **结构化稀疏计算 (2:4 Structured Sparsity)**：
   硬件要求在每连续 4 个权重值中必须有 2 个为零值。NPU 硬件解码器跳过零值乘法，仅用一半的时钟周期完成矩阵乘法，算力吞吐瞬间翻倍！

11.3 常驻感知岛 (Sensor Hub) 与微安级唤醒拓扑
------------------------------------------------------------------------

在智能手机日常使用中，计步、抬腕亮屏、睡眠监测与语音唤醒词监听需要 **24 小时不间断运行**。若由主 CPU 维持唤醒执行这些简单算法，手机电池将在 5 小时内耗尽。

常驻感知岛 (Always-On Island - AON) 硬件拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动 SoC 开辟了物理电气完全隔离的**常驻供电岛（AON Domain）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Sensor Hub 常驻感知与阶梯式唤醒拓扑                 |
   +-------------------------------------------------------------------------+

   [ 主应用处理器 (AP Cluster - CPU/GPU) ] -> [ 深度睡眠休眠态 (Power-Gated, 功耗 0 mW) ]
          ^
          | (仅当检测到有效事件时，发出 Wakeup IRQ 硬件中断拉起主 AP)
          |
   [ 常驻感知岛 (AON Domain - 独立 0.5V 电压轨, 功耗 < 2mW) ]
   +-------------------------------------------------------------------------+
   | 专用低功耗协处理器: ARM Cortex-M33 / RISC-V (运行频率 24MHz ~ 100MHz)    |
   | 片上私有超低漏电 SRAM: 128KB ~ 512KB (运行 CHRE 轻量化算法)              |
   | 硬件传感器控制器 (I3C / SPI FIFO 硬件直通引擎)                          |
   +-------------------------------------------------------------------------+
          ^                 ^                  ^                 ^
          | (I3C 总线)       | (SPI 总线)        | (PDM 接口)      | (I2C 总线)
   [ 3轴加速度计 ]     [ 陀螺仪传感器 ]   [ 超低功耗麦克风 ]  [ 距离/环境光传感器 ]
   (计步/跌倒检测)     (抬腕亮屏姿态)     (本地唤醒词监听)    (口袋防误触检测)

Android 上下文感知中枢运行时 (CHRE)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Android 制定了 **Context Hub Runtime Environment (CHRE)** 规范：
- 厂商在 Sensor Hub 的微型 RTOS 上部署轻量化的 C/C++ 微应用（**Nanoapps**）；
- Nanoapp 持续处理传感器 FIFO 队列数据，执行卡尔曼滤波、步态识别与音频梅尔倒谱分析；
- **唤醒过滤率 > 99.9%**：只有当 Nanoapp 判定用户确实执行了抬腕动作或喊出了唤醒词，才会拉升主 SoC 的供电轨并产生唤醒中断，实现极致的待机续航。

11.4 驱动层异构数据管道：DMA-BUF 与 FastRPC 零拷贝交换
------------------------------------------------------------------------

当应用在 CPU 端发起 AI 推理请求时，若将相机 YUV 帧或大模型权重在 CPU、DSP 与 NPU 之间进行内存拷贝，将严重劣化吞吐并导致 CPU 满载。移动系统依托 **DMA-BUF 与 FastRPC** 构建了跨硬件域的零拷贝管道：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |               Linux DMA-BUF 与 FastRPC 跨域零拷贝数据交互架构           |
   +-------------------------------------------------------------------------+

   [ 用户态应用 (App Client) ]
        |
        v (1. 申请输入/输出张量内存)
   [ Linux 内核 DMA-BUF 驱动 ] -> 分配物理连续/离散显存页框 (dma_buf_fd)
        |
        v (2. 调用 FastRPC ioctl 发起远程过程调用)
   [ FastRPC 驱动 (drivers/soc/qcom/fastrpc.c) ]
        |  * 将 dma_buf_fd 转换为硬件物理页描述符表 (Scatter-Gather List)
        |  * 通过片上共享内存 (SMEM) 发送 IPC 命令给 DSP/NPU
        v
   [ 片上安全桥接与 SMMU 硬件页表映射 ]
        |  * NPU 硬件的 System MMU 直接将该物理内存映射入自身的执行虚拟空间
        v
   [ NPU / DSP 专用硬件加速器 ]
        |  * 直接从该物理显存并发读取图像帧并执行脉动矩阵计算!
        |  * 计算结果原地写回 DMA-BUF 关联的输出缓冲区!
        v (3. 硬件中断通知完成)
   [ App 直接读取输出张量内存 (全链路零 CPU 内存拷贝!) ]

11.5 系统级 AI 运行时调度：Android NNAPI 与 Apple CoreML
------------------------------------------------------------------------

为什么移动操作系统必须提供系统级的 AI 运行时代理，而严禁应用直连 NPU 驱动？

1. **驱动崩溃隔离**：第三方模型结构异常若直接输入专有驱动可能导致硬件挂死，中介运行时负责模型图合法性校验；
2. **多进程异构算力仲裁**：当相机实时人脸追踪（前台高优先级）与相册后台分类（后台低优先级）并发竞争 NPU 时，系统服务负责执行硬件时间片调度；
3. **自适应算子降级 (Fallback)**：若 NPU 硬件不支持某些罕见算子（如特定非线性激活函数），运行时自动将该子图透明拆分并降级至 GPU 或 CPU 执行。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 系统级 AI 运行时架构分层与算子分发拓扑                  |
   +-------------------------------------------------------------------------+

   [ 应用程序层 (TensorFlow Lite / PyTorch Mobile / ONNX Runtime) ]
        |
        v (标准化 API 调用)
   [ 操作系统 AI 统一中间层: Android NNAPI / Android AICore / Apple CoreML ]
        |  * 神经网络计算图编译与优化 (Graph Compilation)
        |  * 算子融合 (Operator Fusion: Conv + BatchNorm + ReLU -> 单指令)
        |  * 异构算子自动切分 (Sub-graph Partitioning)
        |
        +-----------------------+-----------------------+
        | (标准卷积算子)         | (高维矩阵乘法)        | (特殊自定义算子)
        v                       v                       v
   [ NPU HAL3 驱动 ]      [ GPU OpenCL/Metal ]     [ CPU NEON 内核 ]
   (极致能效推理: 90%)     (浮点矩阵辅助: 8%)       (兜底通用计算: 2%)

========================================================================
Chapter 20: 中断处理、下半部机制与移动驱动交互
========================================================================

.. note:: 前置背景与认知承接
   在前两章中，我们解构了移动操作系统在 CPU 算力调度（EAS、WALT）与统一内存治理（ZRAM、Ashmem、LMKD、Jetsam）上的底层机制。然而，移动操作系统的核心本质是一个**由外设异步事件强力驱动的实时交互系统**。从 120Hz/240Hz 触控屏幕的电容扫描、4K@60fps 相机传感器（CMOS）的帧同步脉冲，到 5G 基带的数据包到达，所有的外部物理世界交互均以**硬件中断（Hardware Interrupt）**为唯一起点。智能手机对低延迟与极致功耗的双重苛求，使得移动内核的中断子系统与设备驱动模型必须在微秒级响应、核间功耗迁移与硬件 DMA 零拷贝之间取得严密平衡。本章将深入内核底层的硬件中断处理链条：从 ARM GIC 中断控制器路由，到硬中断（HardIRQ）执行约束与下半部（Softirq、Workqueue、Threaded IRQ）演化，再到 DMA/IOMMU 内存总线直通，并以 240Hz 触控屏中断全链路穿透剖析移动端驱动的交互本质。

------------------------------------------------------------------------
20.1 移动硬件中断拓扑与 ARM GIC 路由架构
------------------------------------------------------------------------

在现代多核移动 SoC（如高通 Snapdragon、联发科 Dimensity、Apple Silicon）中，所有外设的物理引脚电平跳变均由专用的硬件中断控制器统一仲裁与分发。ARM 架构的工业级标准即为 **GIC（Generic Interrupt Controller，主流为 GIC-v3 / GIC-v4）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    ARM GIC-v3/v4 移动 SoC 中断路由拓扑                   |
   +-------------------------------------------------------------------------+

   [ 外设中断源 (Peripheral Interrupt Sources) ]
        |--- 触控屏 (Touch IC) / 物理按键 / 电源键 (GPIO -> SPI)
        |--- 相机传感器 (ISP / MIPI CSI-2 SOF/EOF -> SPI)
        |--- 5G 基带 (Modem PCIe/IPC -> SPI / LPI)
        |--- UFS 闪存控制器 / USB 3.2 控制器 (DMA EOT -> SPI)
        |
        v
   +-------------------------------------------------------------------------+
   |             Distributor (GICD) 全局中断分发器 (SoC 级)                  |
   |   * 集中管理全局中断号 (SPI, INTID 32~1019)                             |
   |   * 中断优先级仲裁 (0~255) / 中断使能与状态机 (Inactive/Pending/Active) |
   |   * 路由决策: 将 SPI 导向特定 CPU Core 的 Redistributor                 |

   +-----------------------------+         +-----------------------------+
        |                                       |
        v                                       v
   +-----------------------------+         +-----------------------------+
   | CPU Interface (ICC - Core 0)|         | CPU Interface (ICC - Core 1)|

   | * EOI / IAR 寄存器硬件握手  |         | * EOI / IAR 寄存器硬件握手  |

        | (触发 ARM64 IRQ 异常)                 | (触发 ARM64 IRQ 异常)

硬件中断分类与中断号（INTID）空间
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

ARM GIC 将中断划分为四种截然不同的物理形态：

.. list-table:: ARM GIC 中断物理分类与特征矩阵
   :widths: 15 15 25 45
   :header-rows: 1
   :class: tight-table

   * - 中断类别
     - INTID 范围
     - 作用范围与目标
     - 典型移动端应用场景与硬件源
   * - **SGI (Software Generated Interrupt)**
     - 0 ~ 15
     - 核间中断（IPI - Inter-Processor Interrupt）
     - **SMP 核间通信**：调度器跨核负载均衡（`SMP_CALL_FUNCTION`）、TLB 远程刷新、CPU 热拔插唤醒。
   * - **PPI (Private Peripheral Interrupt)**
     - 16 ~ 31
     - 单 CPU 核心私有独占
     - **本地定时器（Generic Timer）**：驱动 Tickless 调度周期；性能监控单元（PMU 溢出中断）。
   * - **SPI (Shared Peripheral Interrupt)**
     - 32 ~ 1019
     - 共享外设中断，由 GICD 路由至任一可用核心
     - **主要移动外设**：触控屏（Touch IC）、I2C/SPI 总线控制器、UFS 存储读写完成、相机 ISP 帧结束。
   * - **LPI (Locality-specific Peripheral Interrupt)**
     - 8192+
     - 基于内存消息的中断（MSI / MSI-X），无固定连线
     - **高速总线设备**：5G 基带 PCIe 报文到达、Wi-Fi 7 / NVMe 高速并发队列。

中断状态机与硬件握手协议
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

GIC 硬件内部维护着严格的四状态跃迁模型：
1. **Inactive（未激活）**：当前无外设信号触发；
2. **Pending（待决）**：外设拉低/拉高中断引脚，GIC 已感知信号，但 CPU 尚未响应（可能当前 CPU 处于关中断状态或正在执行更高优先级中断）；
3. **Active（激活执行中）**：CPU 执行 `mrs x0, ICC_IAR1_EL1` 读取中断确认寄存器（IAR - Interrupt Acknowledge Register），硬件自动原子化返回当前最高优先级的 INTID，并将状态置为 Active；
4. **Active and Pending（并发待决）**：当前中断处理尚未结束，同一外设再次发出新的中断脉冲。

当内核处理完毕后，必须向 `ICC_EOIR1_EL1`（End of Interrupt Register）写入当前 INTID，完成硬件应答（EOI），GIC 方允许该中断源产生后续信号。

IRQ 亲和性（IRQ Affinity）与功耗协同
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在移动平台上，中断不能随意发送给任意 CPU 核心：
- **避免唤醒深度休眠核心**：若某个 CPU 丛集（Cluster）处于深度的 `C-State`（电源门控断电），向其路由中断需要消耗数十微秒与巨大瞬时电流完成上电唤醒。GIC 路由策略优先将 SPI 中断绑定至当前处于活跃状态的轻量级能效核（Little Core）；
- **动态迁移（Dynamic IRQ Balancing）**：在相机录像或大文件读写等高吞吐场景下，内核 `irqbalance` 机制将 ISP 或 UFS 的中断亲和性动态绑定至具有更高内存带宽的高性能大核（Big Core），以避免单核处理饱和引起丢包。

20.2 上半部硬中断 (HardIRQ) 与执行约束
------------------------------------------------------------------------

当 ARM64 CPU 响应 IRQ 异常时，硬件自动保存当前 `PSTATE` 到 `SPSR_EL1`，将返回地址存入 `ELR_EL1`，并将 `PSTATE.I` 位置 1（**强制关闭当前 CPU 的本地中断响应**），随后跳转至异常向量表（Vector Table）的 `el1_irq` 入口。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    Linux 内核硬中断 (HardIRQ) 执行约束                  |
   +-------------------------------------------------------------------------+

   [ 硬件引脚触发 ] ---> [ ARM64 异常向量 el1_irq ]
                                 |
                                 v
   +-------------------------------------------------------------------------+
   |               硬中断上下文 (Atomic Context / 关本地中断)                 |
   |                                                                         |
   |   [ 允许的操作 (Allowed) ]              [ 严禁的操作 (Strictly FORBIDDEN) ]|
   |   * 读取硬件状态寄存器 (I/O MMIO)        * 严禁睡眠 / 调度: schedule()      |
   |   * ACK/EOI 硬件中断线应答               * 严禁互斥锁: mutex_lock()         |
   |   * 抓取数据放入环形队列 (RingBuffer)    * 严禁大内存分配: kmalloc(GFP_KERNEL)|
   |   * 标记并激活下半部 (raise_softirq)     * 严禁用户态拷贝: copy_to_user()   |
   |   * 释放自旋锁: spin_unlock()            * 严禁执行耗时循环 (>10 微秒)     |
   +-------------------------------------------------------------------------+
                                 |
                                 v (执行完毕快速退出)
   [ 开启本地中断，将重度数据处理与系统调度推迟至下半部 (Bottom Half) ]

硬中断上下文的物理禁区
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

处于硬中断上下文中的代码必须严格遵守以下物理铁律：

1. **绝对禁止引起睡眠或进程调度**：
   - 中断没有独立的进程实体（没有独立的 `task_struct` 调度上下文，仅借用被中断进程的内核栈或独立中断栈 `irq_stack`）；
   - 如果在硬中断中调用可能引起睡眠的函数（如 `mutex_lock()`、`msleep()`、信号量 `down()`），调度器试图执行上下文切换（`schedule()`）时，将无法保存和恢复中断现场，直接引发内核崩溃（Kernel Panic: *Aiee, killing interrupt handler!*）。
2. **禁止访问用户空间虚拟地址**：
   - 调用 `copy_to_user()` 或 `copy_from_user()` 极易触发缺页异常（Page Fault）；而缺页异常需要从闪存读入数据（I/O 睡眠等待），在中断上下文中这是致命错误。
3. **极短执行时间预算（$<10\mu	ext{s}$）**：
   - 硬中断执行期间，当前 CPU 的所有同级或低级中断全被屏蔽。如果硬中断执行耗时超过数十微秒，将导致高频音频采集溢出（Audio Glitch）、触控扫描跳帧以及高精度硬件定时器严重漂移。

因此，硬中断（上半部）的唯一使命是：**快速与硬件完成握手、读取状态码、抢救关键硬件数据寄存器，然后立即唤醒下半部（Bottom Half），最后退回正常执行流**。

20.3 下半部机制演进：Softirq、Tasklet、Workqueue 与 Threaded IRQ
------------------------------------------------------------------------

为了在开放中断响应（保证系统低延迟）的同时处理繁重的数据解析与业务分发，Linux 内核历经了数十年的下半部架构演进。

.. list-table:: 移动内核四种下半部机制技术指标与适用场景对比
   :widths: 15 15 15 20 35
   :header-rows: 1
   :class: tight-table

   * - 机制名称
     - 执行上下文
     - 是否允许睡眠
     - 多核并发能力
     - 典型应用场景与移动端选型
   * - **Softirq (软中断)**
     - 中断下半部上下文
     - **严禁睡眠**
     - 同一软中断可在多个 CPU 上**完全并发**
     - **仅限内核核心子系统**：网络报文收发（`NET_RX/TX`）、高精度定时器（`TIMER`）、RCU 回调、块设备（`BLOCK`）。
   * - **Tasklet**
     - 基于 Softirq 构建
     - **严禁睡眠**
     - 同一 Tasklet 实例**不可跨核并发**（严格串行）
     - 传统轻量级外设驱动（现代移动端驱动已逐渐淘汰）。
   * - **Workqueue (工作队列)**
     - 进程上下文 (`kworker`)
     - **允许自由睡眠**
     - 由 CMWQ 线程池在多个 CPU 上并发调度
     - 异步 I/O 回写、设备电源状态切换、固件加载、后台内存整理。
   * - **Threaded IRQ (线程化中断)**
     - **独立内核线程** (`irq/xx`)
     - **允许自由睡眠**
     - 具有独立 `task_struct`，受 EAS 调度器完整治理
     - **现代移动驱动标配**：触控屏（Touch IC）、传感器中枢（Sensor Hub）、相机 ISP、音频编解码器。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             现代移动驱动的标配架构：Threaded IRQ (线程化中断)           |
   +-------------------------------------------------------------------------+

   [ 硬件引脚触发 ]
        |
        v
   +-------------------------------------------------------------------------+
   | [ 上半部 HardIRQ: quick_check_handler() ] (耗时 < 2 微秒)               |
   | * 读取中断状态寄存器，确认是否为本设备产生的中断                        |
   | * 掩蔽外设中断线 (Disable IRQ Line at Controller)                       |
   | * 返回 IRQ_WAKE_THREAD;                                                 |
   +-------------------------------------------------------------------------+
        |
        v (内核唤醒专用实时内核线程)
   +-------------------------------------------------------------------------+
   | [ 下半部 Thread: threaded_handler() ] (线程名称: "irq/42-touch")        |
   | * 拥有独立 task_struct，运行于 SCHED_FIFO 实时调度类                    |
   | * 允许通过 I2C / SPI 总线读取多字节数据 (允许持有 mutex，允许阻塞 I/O)  |
   | * 将数据封装为 input_event 上报给 Linux Input 子系统                    |
   | * 处理完毕，解除外设中断线掩蔽 (Re-enable IRQ Line)                    |
   +-------------------------------------------------------------------------+

为什么移动平台全面拥抱 Threaded IRQ？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统设计中，驱动开发者往往在上半部中调用 `schedule_work()` 将任务推给共享工作队列。这种方式在智能手机上存在致命缺陷：
1. **优先级不可见与调度倒置**：通用 Workqueue 线程池（`kworker`）默认运行于普通 `SCHED_OTHER` 时间片轮转调度类。在 CPU 重载时，关键的触控中断工作可能排在后台文件下载之后，造成数百毫秒的严重触控卡顿；
2. **EAS 能效调度器可感知（EAS-Aware）**：
   - Threaded IRQ 通过 `request_threaded_irq()` 注册，为每个中断分配一个专属的内核线程（如 `irq/124-goodix_ts`）；
   - 该线程拥有独立的 PID 与调度属性，可被系统设置为实时优先级（`SCHED_FIFO`，优先级 98）；
   - Android 系统可利用 Linux Cgroups 将前台触控中断线程直接打入 `top-app` cpuset，绑定至最高频大核执行，实现从手指触控到线程响应小于 **1 毫秒** 的极致吞吐。

20.4 DMA 控制器与内存总线直通体系
------------------------------------------------------------------------

对于相机传感器（每秒 30~60 帧 5000 万像素 RAW 数据，吞吐量超 2GB/s）或 5G 调制解调器（Gbps 级高速报文），如果依赖 CPU 执行寄存器读取并将数据写入内存（PIO - Programmed I/O），CPU 将被 100% 占满且系统严重过热。移动平台必须采用 **DMA（Direct Memory Access）** 硬件总线主控直通。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 移动 SoC 中的 DMA 与 SMMU 统一内存访问拓扑              |
   +-------------------------------------------------------------------------+

   [ 外设硬件控制器 (如 相机 ISP / UFS 存储控制器) ]
        |
        | (硬件发起 DMA 写请求: 目标为 IOVA 虚拟地址)
        v
   +-------------------------------------------------------------------------+
   |          System MMU (ARM SMMU-v3 / IOMMU 设备虚拟内存管理单元)          |
   |   * 将连续的 IOVA (0x80000000) 翻译为离散的物理页框 PFN (DRAM Pages)    |
   |   * 硬件级内存保护: 隔离外设访问越界，防止恶意设备 DMA 攻击            |
   +-------------------------------------------------------------------------+
        |
        v (AXI 高速总线直通写入)
   +-------------------------------------------------------------------------+
   |                  物理 LPDDR 内存 (Physical DRAM Pages)                  |
   |   [ Page A (0x1000) ]  <-- (DMA 直接写入图像数据，完全无需 CPU 介入!)    |
   |   [ Page B (0x4000) ]  <-- (Scatter-Gather 离散链表聚合)                |
   |   [ Page C (0x9000) ]                                                   |
   +-------------------------------------------------------------------------+
        ^
        | (DMA 传输完成产生中断通知 CPU -> CPU 读取内存前必须执行 Cache Invalidate)
   [ CPU Cache 缓存一致性维护点 ]

一致性 DMA 与流式 DMA 映射
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动内核驱动必须根据数据访问模式选择正确的 DMA 内存映射范式：

1. **一致性 DMA 映射（Coherent DMA: `dma_alloc_coherent`）**：
   - 物理内存分配时直接在页表中关闭 CPU Cache（标记为 Uncached / Write-Through）；
   - **特性**：CPU 与外设随时读写该内存，数据天然一致，无需任何显式同步；
   - **缺点**：由于绕过了 CPU 高速缓存，CPU 读写性能极低；通常仅用于外设命令描述符环（Ring Buffer Descriptors）。
2. **流式 DMA 映射（Streaming DMA: `dma_map_single` / `dma_map_sg`）**：
   - 用于真实的大体积数据传输（如网络包、相机帧、视频流），内存页面保留正常的 CPU Cache 特性；
   - **严格的缓存生命周期同步（Cache Invalidation & Clean）**：
     - **Device to CPU（外设写入内存）**：DMA 启动前，CPU 必须执行 `DMA_FROM_DEVICE` 映射，内核对目标内存区间执行 **`Cache Invalidate`**（将 CPU L1/L2 Cache 中对应的 Cacheline 标记为无效）。当外设写入 DRAM 完毕后，CPU 首次读取时强制穿透到 DRAM 加载最新数据，防止读取到 CPU 缓存中的陈旧过时数据；
     - **CPU to Device（外设读取内存）**：CPU 准备好数据后，必须执行 `DMA_TO_DEVICE` 同步，内核执行 **`Cache Clean/Flush`**（强制将 L1/L2 缓存中的脏数据同步刷入物理 DRAM），确保外设 DMA 读取到 CPU 刚才计算的真实结果。

分散/聚集 DMA (Scatter-Gather DMA) 与 IOMMU 协同
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在虚拟内存系统运行一段时间后，物理内存高度碎片化，极难分配到几十兆连续的物理页框。
- **Scatter-Gather DMA**：驱动将离散的物理页框组织为链表数组（`struct scatterlist sg[]`），硬件 DMA 控制器自动按链表连续搬运；
- **ARM SMMU（System MMU）**：现代移动 SoC 在外设与总线之间增加了硬件 SMMU，驱动只需配置 SMMU 页表，即可将离散的物理页框虚拟化为外设视角下单调连续的 **IOVA（I/O Virtual Address）**，实现跨硬件模块（如 ISP 直接向 GPU 显存注水）的零拷贝流转。

20.5 典型移动驱动全链路穿透剖析：以 240Hz 触控屏中断为例
------------------------------------------------------------------------

为了将中断、下半部、总线驱动与上层系统连接成闭环，我们完整追踪一次用户手指触摸屏幕（240Hz Touch Sampling）引发的系统全链路穿透时序。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                240Hz 触控屏硬件中断到 Android App 全链路穿透时序         |
   +-------------------------------------------------------------------------+

   [ 物理触摸发生 (t = 0.00 ms) ]
        |
        v
   [ 1. 触摸屏控制器 (Touch IC / 固件) ]
        | * 驱动自容/互容电容矩阵扫描，硬件解算接触点物理坐标 (X=540, Y=1120)
        | * 拉低 SoC GPIO 引脚电平 (产生下降沿中断脉冲)
        v (硬件连线)
   [ 2. ARM GIC 中断控制器 (GIC-v3) ]
        | * 捕获硬件 SPI 中断线信号，将 INTID 142 置为 Pending
        | * 触发 CPU Core 0 的 el1_irq 硬件异常 (耗时 < 0.1ms)
        v
   [ 3. Linux 内核驱动上半部: touch_hard_irq() ]
        | * 执行 ICC_IAR1_EL1 确认中断，关闭本地 GPIO 中断线
        | * 返回 IRQ_WAKE_THREAD 唤醒线程化中断 (耗时 ~2 微秒)
        v
   [ 4. 线程化中断处理线程: irq/142-touch_ts (SCHED_FIFO / top-app) ]
        | * 发起 I2C/SPI 总线 DMA 传输，读取 64 字节触控报文
        | * 解析多点触控协议: input_mt_report_slot_state(), input_report_abs()
        | * 调用 input_sync() 写入 Linux Input 子系统环形队列 (evdev)
        v (内核向用户态暴露: /dev/input/event3)
   [ 5. Android InputReader 线程 (位于 system_server 进程) ]
        | * epoll_wait() 被 VFS 数据就绪事件唤醒，读取 struct input_event
        | * 将原始坐标转换为 MultiTouch 运动事件 (MotionEvent.ACTION_MOVE)
        v (进程内无锁环形队列)
   [ 6. Android InputDispatcher 调度线程 ]
        | * 查找当前焦点窗口 (Focus Window)，确定目标应用进程
        | * 通过 Unix Domain Socket (InputChannel) 将事件跨进程写入 App 的 socket
        v (跨进程通信 / Socket FD 数据就绪)
   [ 7. 应用主线程 (UI Thread / Activity Looper) ]
        | * Native Looper 被 epoll_wait 唤醒，通过 JNI 回调 View.dispatchTouchEvent()
        | * 触发应用业务逻辑与 UI 重绘流水线 (t = 1.8~3.5 ms 瞬间完成响应!)

多点触控协议（Multi-Touch Protocol Type B）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Linux 内核中，触控驱动采用 Type B 协议（Slot 槽位模型）以极低带宽上报多指触摸：
- 每个物理手指绑定一个恒定的 `Slot ID`；
- 当手指移动时，驱动仅上报发生变化的坐标轴（如 `ABS_MT_POSITION_X`），未发生变化的手指无需重复发送；
- 最终通过 `SYN_REPORT`（`input_sync`）单周期提交一次原子帧，杜绝了多指数据交错与撕裂。

20.6 Apple Darwin/XNU 内核中断与 IOKit 驱动模型对比
------------------------------------------------------------------------

在 Apple iOS / macOS 体系中，XNU 混合内核与 IOKit 驱动框架采用了与 Linux 截然不同的面向对象（Object-Oriented）设计哲学。

.. list-table:: Linux 内核驱动与 Apple IOKit 驱动框架架构对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 对比维度
     - Linux 驱动架构 (Android)
     - Apple IOKit 驱动架构 (iOS / macOS)
   * - **核心设计范式**
     - C 语言结构体 + 函数指针虚表（`file_operations`, `driver`）
     - **C++ 面向对象驱动树**（基于 `OSObject` / `IOService` 继承体系）
   * - **中断分发机制**
     - HardIRQ + Softirq / Workqueue / **Threaded IRQ**
     - **`IOInterruptEventSource` + `IOWorkLoop` 单线程门禁**
   * - **并发与锁模型**
     - 复杂的自旋锁（`spinlock_t`）、互斥锁（`mutex`）与 RCU
     - **WorkLoop 序列化单线程模型**（天然免锁，彻底杜绝并发死锁）
   * - **设备匹配模型**
     - 设备树（Device Tree - `.dts`）与 ACPI
     - **I/O Registry 注册表**（动态匹配驱动 Persona 与匹配属性）
   * - **现代演进方向**
     - Android Project Treble Binderized HAL + AIDL
     - **Apple DriverKit (DEXT)**：驱动完全迁移至用户空间沙箱运行

IOKit IOWorkLoop：消除锁竞争的单线程循环
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统 Linux 驱动开发中最常见的系统死锁与竞态发生在中断处理函数与普通进程上下文之间。Apple IOKit 提出了一套极具特色的解决方案——**`IOWorkLoop`（工作循环）**：
- 每个驱动服务绑定一个专用的 `IOWorkLoop` 内核线程；
- 中断事件通过 `IOInterruptEventSource` 注入 WorkLoop 队列；
- 定时器、DMA 完成事件与应用控制请求全部被封装为事件源（`IOEventSource`）；
- `IOWorkLoop` 线程按序单线程串行分发所有事件。驱动开发者在方法内部**几乎不需要手动加减互斥锁**，从根源上消除了驱动层的死锁风险与锁争用导致的流水线气泡。

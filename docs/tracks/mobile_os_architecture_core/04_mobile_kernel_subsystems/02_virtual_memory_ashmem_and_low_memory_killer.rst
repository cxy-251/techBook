========================================================================
Chapter 19: 虚拟内存与物理内存治理：ZRAM 压缩、Ashmem 匿名共享、LMKD 与 iOS Jetsam 回收机制
========================================================================

.. note:: 前置背景与认知承接
   在前一章中，我们深入剖析了 Linux 能效感知调度器（EAS）、WALT 负载追踪以及针对前台 UI 交互的算力提速机制。然而，在移动操作系统中，计算能力的调度必须依托于稳定、充裕且低延迟的内存子系统支持。智能手机面临着独特的物理硬件制约：**统一内存架构（UMA）下 CPU、GPU、NPU 与 ISP 共同争用 4GB~16GB 的有限 LPDDR 物理内存，且缺乏传统桌面计算机近乎无限的磁盘交换空间（Swap Partition）**。本章将深入内核虚拟内存与物理页管理的最底层，全面解构移动平台内存分级治理体系：从页表映射与内存分类，到 ZRAM 内存压缩块设备、Ashmem/memfd 跨进程匿名共享，再到 Android 用户态 LMKD 与 Apple XNU Jetsam 杀进程回收策略的微架构实现。

19.1 移动内存管理的物理约束与双层拓扑
------------------------------------------------------------------------

在服务器或桌面操作系统中，当物理内存耗尽时，系统通常会将不活跃的匿名页面换出到外部高速 NVMe SSD 上的 Swap 分区。但在移动设备上，这种策略面临着严苛的物理限制：

1. **闪存擦写寿命（TBW）硬约束**：智能手机使用的 UFS / eMMC 闪存芯片擦写寿命有限，频繁的高吞吐换页写入会在 1~2 年内迅速耗尽存储介质寿命。
2. **I/O 延迟与功耗尖峰**：闪存读写延迟（数十微秒至毫秒级）远高于 DRAM（数十纳秒），且高频 I/O 触发的主控供电会打破整机的能耗预算，直接导致前台 UI 掉帧。
3. **异构硬件统一内存争用（UMA Contention）**：移动 SoC 没有独立的独立显存（VRAM），4K 相机 RAW 预览流（ISP）、3D 渲染图层（GPU）、神经网络权重（NPU）以及操作系统内核与应用堆（CPU）全部从同一块物理 LPDDR 芯片中划分页框。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  移动操作系统虚拟内存向物理页框映射拓扑                 |
   +-------------------------------------------------------------------------+

   [ 应用进程虚拟地址空间 (48-bit Virtual Address Space) ]
        |
        |--- 用户空间: 0x0000000000000000 ~ 0x00007FFFFFFFFFFF (128 TB)
        |       * 代码段 (RX) / 数据段 (RW) / 匿名堆 (Heap) / 线程栈 (Stack)
        |       * 文件内存映射 (mmap: APK, so, 数据库, 资源)
        |       * 图形与共享内存 (Gralloc / Ashmem / DMA-BUF)
        |
        v [ 硬件 MMU 多级页表翻译: PGD -> PUD -> PMD -> PTE ]
   +-------------------------------------------------------------------------+
   |                物理内存管理池 (Physical Page Frames - DRAM)             |
   +-------------------------------------------------------------------------+
        |
        |---> [ 1. 干净文件页 (Clean Page Cache) ] --> 随时可直接丢弃释放
        |---> [ 2. 脏文件页 (Dirty Page Cache) ] ----> 须写回闪存后方可释放
        |---> [ 3. 匿名内存页 (Anonymous Pages) ] ---> 堆/栈数据，须压缩进 ZRAM
        |---> [ 4. 内核与驱动不可移动页 (Pinned) ] --> Slab/DMA/CMA，绝对锁定
        +---> [ 5. 共享硬件缓冲区 (DMA-BUF) ] ------> GPU/ISP 直通，按引用释放

多级页表与缺页异常（Demand Paging）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

ARM64 架构下，Linux 内核与 Apple XNU 均采用 4 级页表分页机制（以 4KB 页面为例，包含 PGD 全局目录、PUD 上级目录、PMD 中间目录与 PTE 页表项）。

当应用程序通过 `malloc()` 或 `mmap()` 申请 100MB 内存时，内核仅仅是在进程的虚拟内存红黑树（`vm_area_struct`）中分配了一段虚拟地址区间，**并没有实际消耗任何物理 DRAM 页框**。只有当 CPU 首次执行指令读取或写入该虚拟地址时，硬件 MMU 触发**缺页异常（Page Fault）**，内核捕获异常后执行真实分配：
- **次要缺页（Minor Page Fault）**：所需数据已在内存中（例如命中 Page Cache 或分配新的零填充全零匿名页），内核直接将物理页框物理地址（PFN）填入 PTE 页表项并刷新 TLB，耗时通常 $<1\mu	ext{s}$；
- **主要缺页（Major Page Fault）**：所需数据不在内存中，必须从 UFS 闪存读取代码段或从 ZRAM 压缩区解压数据，线程被强制置入睡眠等待 I/O 完成，耗时通常为数十微秒至数毫秒。

内存类型分类与回收代价
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动操作系统将物理内存中的页面细分为不同的资源池，不同池具有截然不同的回收成本与生命周期：

.. list-table:: 移动操作系统核心物理内存分类与回收代价矩阵
   :widths: 18 22 25 35
   :header-rows: 1
   :class: tight-table

   * - 内存类别
     - 典型分配来源
     - 内核回收途径
     - 回收引发的性能与体验代价
   * - **干净文件页 (Clean Page Cache)**
     - APK 代码段、.so 动态库只读段、静态资源文件
     - 直接从页表中解除映射并丢弃（Eviction）
     - **极低**：下次访问仅需触发 Major Fault 重新从闪存读入；但过多丢弃会导致应用启动变慢。
   * - **脏文件页 (Dirty Page Cache)**
     - SQLite 数据库修改页、应用写入的私有文件
     - 必须由内核回写线程（`kworker/flush`）同步刷入闪存后丢弃
     - **中等**：受闪存 I/O 队列深度与带宽限制，若 I/O 阻塞会拖慢整机响应。
   * - **匿名内存 (Anonymous Pages)**
     - ART 虚拟机 Java 堆、Native C/C++ 堆、线程栈
     - 无法直接丢弃；必须通过 CPU 压缩写入 ZRAM，或直接终止进程
     - **高**：消耗 CPU 算力进行实时压缩/解压；若内存持续枯竭则导致应用进程被强制杀死。
   * - **共享图形/硬件 Buffer**
     - Gralloc / `dma-buf` 显存、Camera RAW 缓冲区
     - 由硬件驱动引用计数管理；只有所有持有者均关闭 FD 时释放
     - **极高**：若强行释放会导致渲染花屏、相机管道崩溃或桌面合成器（SurfaceFlinger）重置。
   * - **内核固定内存 (Pinned Memory)**
     - Slab 分配器（inode, dentry, task_struct）、中断栈
     - 内核 Shrinker 机制按需收缩；核心结构体常驻
     - **不可回收**：属于内核运行骨干，过度膨胀会引发系统级崩溃。

19.2 ZRAM 内存压缩子系统与动态交换拓扑
------------------------------------------------------------------------

为了在不损害闪存寿命的前提下扩展可用内存，现代 Android 与移动 Linux 平台普遍引入了 **ZRAM**（RAM-based Compressed Swap Device）子系统。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                      ZRAM 内存压缩换页与回写拓扑架构                    |
   +-------------------------------------------------------------------------+

   [ 物理 DRAM 空间划分 ]
   +-------------------------------------------------------------------------+
   | 普通可用内存区 (Normal RAM Pool)      | ZRAM 压缩存储池 (zsmalloc)      |
   |                                       |                                 |
   | [ 匿名页 1 (4KB) ] --(压缩: LZO/LZ4)-> | [ 压缩块 (1.2KB) ] (压缩比 ~3:1)|
   | [ 匿名页 2 (4KB) ]                   | [ 压缩块 (1.4KB) ]              |
   | [ 匿名页 3 (4KB) ]                   | [ 压缩块 (0.9KB) ]              |
   |                                       |                                 |
   +-------------------------------------------------------------------------+
        |                                       |
        | (内存极度紧张时)                       | (ZRAM 填满且无法压缩时)
        v                                       v
   [ 触发 kswapd 内核换页 ]             [ ZRAM Writeback: 写入闪存冷交换区 ]

ZRAM 工作原理与数据流
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

ZRAM 在 Linux 内核中注册为一个虚拟块设备（如 `/dev/block/zram0`），并将其挂载为系统的最高优先级 Swap 分区：

1. **换出（Swap Out / Page Compress）**：
   - 当内核内存水位线下降触发 `kswapd` 守护进程时，内核内存扫描器（LRU 链表）识别出长时间未访问的非活跃匿名页（Inactive Anonymous Page）；
   - 内核调用高效流式压缩算法（如 **LZO-RLE** 或 **LZ4**），将原本占用 4096 字节的物理页压缩为平均 1.0KB~1.5KB 的紧凑二进制数据块；
   - 压缩后的数据块被存入专门针对内存碎片优化的专用内存分配器 **`zsmalloc`** 存储池中；
   - 原始 4KB 物理页被立即释放归还给系统空闲池，PTE 页表项被标记为 Swap Entry（记录 ZRAM 设备号与块槽位索引）。
2. **换入（Swap In / Page Decompress）**：
   - 当后台应用被重新唤醒切换到前台，CPU 访问该页面触发 Swap Page Fault；
   - 内核根据 PTE 中的 Swap Entry 索引定位到 ZRAM 中的压缩块，调用解压引擎将其还原为原始 4KB 页面并映射回进程地址空间；
   - ZRAM 存储池中的压缩副本被释放。

压缩算法选型与开销权衡
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动平台对 ZRAM 压缩算法的选择有着严苛的吞吐与能效考量：

.. list-table:: 移动端主流 ZRAM 压缩算法性能指标实测对照
   :widths: 15 25 25 35
   :header-rows: 1
   :class: tight-table

   * - 算法名称
     - 典型压缩比 (4KB 原始页)
     - 压缩 / 解压吞吐性能
     - 适用场景与工程特性
   * - **LZO-RLE**
     - ~2.8 : 1 (约 1.4 KB)
     - 压缩 ~800 MB/s / 解压 ~1.5 GB/s
     - **Android 默认标配**：针对内存中连续全零字节进行了专用 RLE 加速，极低 CPU 负载。
   * - **LZ4**
     - ~2.5 : 1 (约 1.6 KB)
     - 压缩 ~750 MB/s / **解压 ~3.5 GB/s**
     - **解压性能极强**：适合对前台切回响应速度要求极高的高端旗舰机型。
   * - **ZSTD**
     - **~3.5 : 1 (约 1.1 KB)**
     - 压缩 ~250 MB/s / 解压 ~1.0 GB/s
     - **极限压缩比**：适合 2GB~4GB 极低内存入门级设备（Android Go）。

19.3 匿名共享内存机制：从 Ashmem 到现代 memfd 与 dma-buf
------------------------------------------------------------------------

在移动操作系统多进程沙箱隔离模型下，跨进程传输大体积数据（如相机 4K 图像、跨进程 Bitmap、Surface 图层元数据）如果采用常规 Binder 复制，会导致极其严重的 CPU 拷贝开销与内存暴涨。为此，操作系统必须提供**零拷贝（Zero-Copy）的高性能共享内存底座**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             Ashmem / memfd 跨进程共享内存生命周期与引用模型             |
   +-------------------------------------------------------------------------+

   [ 进程 A (生产者 / CameraService) ]       [ 进程 B (消费者 / UI App) ]
        |                                          |
        | 1. fd = memfd_create("shared_buf")       |
        | 2. ftruncate(fd, 8MB)                    |
        | 3. addr_A = mmap(fd, 8MB, PROT_WRITE)    |
        |    (向 addr_A 写入图像帧数据)            |
        |                                          |
        | 4. 通过 Binder IPC 发送 fd ------------->| 5. 收到 dup 后的 fd_B
        |                                          | 6. addr_B = mmap(fd_B, PROT_READ)
        |                                          |    (直接读取同一块物理内存!)
        v                                          v
   +-------------------------------------------------------------------------+
   |            内核物理页框池 (同一组物理 DRAM 页面，无任何内存拷贝)        |
   +-------------------------------------------------------------------------+

Android Ashmem（已废弃）与 Pin / Unpin 机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

早期 Android 设计了专用的内核驱动 **Ashmem（Anonymous Shared Memory）**：
- **ioctl 控制接口**：通过打开 `/dev/ashmem` 设备节点，使用 `ASHMEM_SET_SIZE` 设置共享内存尺寸，使用 `ASHMEM_SET_PROT_MASK` 限制内存保护位。
- **页面锁定状态机（Pin / Unpin）**：
  - 进程可以通过 `ASHMEM_UNPIN` 将某段内存标记为“可丢弃”；
  - 当内核遭遇内存压力时，内存管理器可直接回收处于 Unpinned 状态的物理页，而无需通知持有者；
  - 进程再次访问前执行 `ASHMEM_PIN`，若内核返回 `ASHMEM_IS_PURGED`，应用可知晓该内存已被清空，须重新计算或填充数据。

现代架构收敛：`memfd_create` 与 `dma-buf`
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

由于 Ashmem 属于 Android 专用 Out-of-tree 内核驱动，难以被上游 Linux 内核社区合并，且存在复杂的锁竞争问题，现代 Android（Android 10+ / Linux 5.x+）已全面完成架构迁移：

1. **通用匿名内存 `memfd_create()`**：
   - 完全采用 Linux 主线标准系统调用 `int memfd_create(const char *name, unsigned int flags)`；
   - 创建一个匿名临时文件描述符，支持 Linux 标准的文件密封机制（File Sealing，如 `F_SEAL_SHRINK`, `F_SEAL_GROW`, `F_SEAL_WRITE`），防止恶意接收方篡改共享内存大小或破坏只读缓冲区。
2. **硬件多媒体共享底座 `dma-buf`**：
   - 针对 GPU、ISP、VPU 等硬件驱动间的高吞吐流式数据，全面采用 Linux 内核标准子系统 **`dma-buf`**；
   - 配合跨进程 Binder 传递文件描述符，实现了应用渲染、合成器（SurfaceFlinger）与显示硬件控制器（HWC）之间全链路的绝对零拷贝。

19.4 Android Low Memory Killer (LMKD) 架构与回收策略
------------------------------------------------------------------------

当文件页回收和 ZRAM 压缩均已达到物理极限，系统仍无法满足新进程或前台硬件的物理内存分配需求时，操作系统必须执行最后的防御机制：**按优先级终止（Kill）低价值后台进程**。

早期内核态 LMK 的缺陷与用户态 LMKD 演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在早期 Android 版本中，低内存杀进程逻辑硬编码在 Linux 内核驱动 `drivers/staging/android/lowmemorykiller.c` 中。这种内核态实现存在严重缺陷：
- 内核在直接回收路径中阻塞式遍历所有进程的 `task_struct` 并发送 `SIGKILL`，导致内核调度器产生巨大的锁争用和调度气泡（Scheduling Bubbles）；
- 内核无法深度感知上层 Framework 复杂的进程状态、组件生命周期以及用户当前的真实意图。

因此，现代 Android 全面转向由用户态守护进程 **`lmkd`（Low Memory Killer Daemon）** 统一主导。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    现代 Android LMKD 用户态治理架构                     |
   +-------------------------------------------------------------------------+

   [ 内核事件层 (Kernel Signals) ]
        |
        |--- 1. PSI (Pressure Stall Information): /proc/pressure/memory
        |--- 2. cgroup v2 内存事件: memory.pressure / memory.high
        |--- 3. 内存颠簸度量 (Thrashing Detection: refault_rate / swap_rate)
        |
        v [ epoll 异步事件捕获机制 ]
   +-------------------------------------------------------------------------+
   |                   用户态 lmkd 守护进程决策中枢                          |
   +-------------------------------------------------------------------------+
        |
        | 结合 AOSP Framework (ActivityManagerService) 动态维护的:
        | * oom_score_adj 优先级表 (-1000 ~ +1000)
        | * 进程驻留物理内存大小 (RSS / PSS)
        |
        v [ 决策: 选取当前最不重要且能释放最多物理页的进程 ]
   [ 执行终止: cgroup.kill / pidfd_send_signal(SIGKILL) ] ---> 瞬间回收数十MB物理页!

PSI (Pressure Stall Information) 驱动的精确度量
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代 `lmkd` 彻底废弃了传统的固定剩余内存水位线（Minfree Watermarks）判定法，转而采用 Linux 内核的 **PSI（Pressure Stall Information）** 机制。

PSI 实时监控 CPU 线程因等待内存分配/换页而被阻塞挂起的时间比例：
- **`some` 压力指标**：代表系统中至少有一个 CPU 线程因为内存短缺（如 Major Fault 或直接内存回收 Direct Reclaim）而处于挂起等待状态的时间占比；
- **`full` 压力指标**：代表系统中**所有**处于就绪态的 CPU 线程全部因为等待内存 I/O 而无法执行（CPU 出现绝对空转），此时系统已发生严重的“内存颠簸（Thrashing）”。

`lmkd` 在 `/proc/pressure/memory` 上注册三个档位的 `epoll` 触发阈值：

.. list-table:: LMKD 基于 PSI 的三级响应策略与动作模型
   :widths: 18 25 25 32
   :header-rows: 1
   :class: tight-table

   * - 压力等级 (Level)
     - PSI 触发条件阈值
     - 涉及进程评分区间
     - lmkd 执行的具体回收动作
   * - **Low Pressure**
     - `some 10ms` in 1000ms
     - `oom_score_adj >= 900`
     - 清理最不重要的空闲缓存进程（Cached Apps），释放零散物理页。
   * - **Medium Pressure**
     - `some 30ms` in 1000ms
     - `oom_score_adj >= 700`
     - 终止后台无感知服务进程、历史任务栈底部的 Activity 进程。
   * - **Critical Pressure**
     - `full 50ms` in 1000ms
     - `oom_score_adj >= 200`
     - 紧急终止一切非前台可见进程（包括后台音频服务），全力挽救前台 UI 与内核稳定性。

进程优先级评分：`oom_score_adj`
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Android Framework（`ActivityManagerService`）根据进程的组件状态实时动态计算并向 `/proc/[pid]/oom_score_adj` 写入一个介于 **`-1000` 到 `+1000`** 之间的整数：

.. code-block:: text

   [-1000] --------------------------------------------------------> [+1000]
   绝对安全 (永不查杀)                                              首要查杀目标

   [-1000] NATIVE / SYSTEM     : init, zygote, system_server, surfaceflinger
   [-900]  PERSISTENT_PROC     : 电话核心进程 (Telephony), 蓝牙中枢
   [0]     FOREGROUND_APP      : 用户当前正在交互的前台焦点 App
   [100]   VISIBLE_APP         : 可见但无焦点 (如画中画浮窗、分屏 App)
   [200]   PERCEPTIBLE_APP     : 正在后台播放音乐、导航的 App
   [500]   SERVICE_APP         : 后台正在执行下载或同步的服务进程
   [700]   PREVIOUS_APP        : 刚才刚刚切到后台的上一个 App (优先保留防重开)
   [900~]  CACHED_APP_LIST     : 处于后台没有任何任务运行的纯缓存进程

19.5 Apple XNU 内存治理体系：memorystatus 与 Jetsam 回收机制
------------------------------------------------------------------------

在 Apple iOS / iPadOS 体系中，XNU 混合内核采用了一套与 Android 理念相似但实现更为强硬激进的内存治理子系统——**`memorystatus`（通常统称为 Jetsam）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    Apple XNU Jetsam 内存强制回收机制                    |
   +-------------------------------------------------------------------------+

   [ 内存消耗实时监控: vm_map / 物理页常驻集合 (Resident Memory) ]
        |
        +---> [ 单进程硬性限额检查: per-process dirty limit ]
        |        |
        |        +--> (单应用超出限额) ---> 触发 EXCEPTION_FLAG_RESOURCE 立即强杀!
        |
        +---> [ 系统全局内存压力水位线: memorystatus_available_pages ]
                 |
                 +--> (全局内存枯竭) ---> 按 Jetsam Priority 优先级链表从低到高强杀

Jetsam 核心工作机制与设计哲学
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **绝对严格的单进程物理内存上限（Per-Process Memory Limits）**：
   - 与 Android 允许前台应用动态吞噬大量内存直到全局告警不同，iOS 为不同设备形态和不同类型进程（App、Widget、App Extension、后台任务）预设了**不可逾越的物理常驻脏页硬性限额（Dirty Limit）**；
   - 例如在 6GB 物理内存的 iPhone 上，一个普通前台 App 可能被严格限制使用最多 2.8GB 内存。一旦其物理脏页（Dirty Pages）触及阈值，XNU 内核的 `memorystatus_jettison_task()` 函数会立即向该进程发送 `SIGKILL`，产生带有 `EXC_RESOURCE (RESOURCE_TYPE_MEMORY)` 的 Jetsam 诊断日志。
2. **Jetsam 优先级带（Jetsam Priority Bands）**：
   - XNU 内核维护了一组双向进程链表，进程根据系统角色处于不同的优先级区间：
     - `JETSAM_PRIORITY_IDLE` (0)：最底层的后台空闲缓存进程；
     - `JETSAM_PRIORITY_BACKGROUND` (3)：受限后台运行进程；
     - `JETSAM_PRIORITY_UI_SUPPORT` (8)：系统键盘、输入法服务；
     - `JETSAM_PRIORITY_FOREGROUND` (10)：前台焦点 App；
     - `JETSAM_PRIORITY_CRITICAL` (19)：`launchd`、`SpringBoard` 等关键系统守护进程。
3. **全局内存压力驱动的淘汰（System-Wide Pressure Jettisoning）**：
   - 当系统可用物理页跌破紧急水位线（`memorystatus_available_pages <= memorystatus_emergency_pages`），内核从 `JETSAM_PRIORITY_IDLE` 链表头部开始，快速遍历并强杀整个进程，直到系统可用页恢复至安全水位以上。

19.6 跨平台技术矩阵：Android LMKD vs Apple XNU Jetsam
------------------------------------------------------------------------

.. list-table:: Android (Linux) 与 Apple (XNU) 移动内存治理机制全景对比
   :widths: 18 41 41
   :header-rows: 1
   :class: tight-table

   * - 治理维度
     - Android 体系 (Linux + LMKD)
     - Apple iOS 体系 (XNU + Jetsam)
   * - **决策执行主体**
     - **用户态守护进程** `lmkd`，结合内核 PSI 与 cgroup v2
     - **XNU 内核空间** `memorystatus` 子系统直接执行
   * - **内存压缩技术**
     - **ZRAM 块设备**（结合 LZO-RLE / LZ4 压缩 swap 空间）
     - **XNU Compressed Memory**（内核虚拟内存子系统原生压缩）
   * - **跨进程共享内存**
     - `memfd_create()` 与 `dma-buf`（早期为 Ashmem）
     - Mach VM 共享内存（`mach_make_memory_entry`）与 IOSurface
   * - **单进程内存限额**
     - **弹性软约束**：主要由全局可用内存决定，单应用可使用较大内存
     - **硬性配额红线**：每个 App 拥有出厂级严格物理脏页上限，越界秒杀
   * - **压力感知指标**
     - **PSI 阻塞停顿时间**（`some` / `full` stall 时间占比）
     - **物理剩余页框水位线**（Available Pages Watermark）
   * - **进程终止机制**
     - 通过 `cgroup.kill` 或发送 `SIGKILL` 终止进程树
     - 内核直接调用 `task_terminate()` 并生成 Jetsam Report
   * - **开发者诊断工具**
     - `dumpsys meminfo`、Perfetto Trace、`am kill` 日志
     - Xcode Organizer、MetricKit、`.ips` 格式 Jetsam 事件报告

本章系统解构了移动操作系统在有限 LPDDR 硬件约束下的内存分层治理机制：从虚拟内存多级页表映射与按需缺页分配，到 ZRAM 内存压缩块设备的算法选型与换页机制；从基于文件描述符的 Ashmem/memfd/`dma-buf` 零拷贝共享底座，到 Android 用户态 LMKD 基于 PSI 指标的阶梯式杀进程策略，以及 Apple XNU 基于物理脏页限额与 Jetsam 优先级的强管控体系。

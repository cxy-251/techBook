18.1 移动内核调度的物理约束与根本矛盾
------------------------------------------------------------------------

在服务器与传统桌面计算环境中，操作系统调度器（如 Linux CFS - 完全公平调度器 / EEVDF - 尽早截止时间优先虚拟运行时调度器）的核心设计目标是**吞吐量最大化**与**算力绝对公平分配**，因为服务器具备持续插电的供电环境与主动风扇散热。

智能手机的物理现实彻底颠覆了这一假设：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     智能手机调度的三大物理极限与矛盾矩阵                |
   +-------------------------------------------------------------------------+

   [ 物理极限 1: 电量预算硬约束 (Battery Budget) ]
   * 锂电池容量固定 (约 15~20 Wh)，整机待机电流必须压制在 < 10mA；
   * CPU 全核满载功耗可高达 10W~15W (若持续满载，电池将在 1.5 小时内耗尽)!

   [ 物理极限 2: 紧凑热包络 (Thermal Envelope) ]
   * 手机采用纯被动金属中框散热，机身持续散热极限仅为 3.5W ~ 5.0W；
   * 结温超过 45°C 触发人体防烫伤保护，内核必须在数十毫秒内阶梯式降频降温。

   [ 物理极限 3: 前台交互零卡顿确定性 (Zero-Jank Determinism) ]
   * 120Hz 刷新率要求 UI 线程从接收触摸事件到提交图层渲染必须在 8.33ms 内完成；
   * 调度延迟 (Scheduling Latency) 超过 2ms 就会直接引发丢帧 (Jank) 与手感粘滞。

动态功耗超线性模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

根据 CMOS 芯片数字电路物理功耗方程：

.. math::

   P = \alpha \cdot C \cdot V^2 \cdot f + I_{	ext{leak}} \cdot V

其中 $\alpha$ 为活动因子，$C$ 为负载电容，$V$ 为供电电压，$f$ 为工作频率。由于半导体物理特性中工作频率与驱动电压近似正比关系（$V \propto f$），因此动态功耗与频率呈现**立方级超线性增长**：

.. math::

   P_{	ext{dynamic}} \propto f^3

这意味着：将 CPU 频率提升 2 倍，算力吞吐提升 2 倍，但动态能耗开销将激增至 **8 倍**！因此，移动内核调度器绝不能简单采用“有任务就无脑拉满最高频”的暴力策略，必须在**能耗曲线的拐点处寻找全局能耗最小化解**。

18.2 EAS 能效感知调度器：容量模型与能耗模型
------------------------------------------------------------------------

为了在异构多核架构（ARM DynamIQ：超大核 Cortex-X、性能大核 Cortex-A7xx、高能效小核 Cortex-A5xx）上实现能效最优调度，Linux 内核引入了 **EAS（Energy Aware Scheduling）** 体系。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    EAS 调度器架构与三大支撑子系统拓扑                   |
   +-------------------------------------------------------------------------+

   [ 1. 核心容量模型 (CPU Capacity Model) ]
        |  * 标准化归一算力: 超大核 (1024) / 大核 (700) / 小核 (350)
        v
   [ 2. 负载追踪引擎 (PELT / WALT) ] --------> [ 实时计算任务所需算力 Util ]
        |                                              |
        v                                              v
   [ 3. 能耗模型 (Energy Model - EM) ] <---------------+
        |  * 存储各性能域 (Performance Domain) 在各 OPP 频点下的功耗表 (mW)
        |  * 评估算法: 遍历候选核心，计算任务放置后的整机能耗增量 Delta Energy
        v
   [ 4. 最佳核心放置决策 (select_task_rq_fair) ] ---> 将任务分发至最佳 CPU 核心

CPU 容量标准化归一模型 (Capacity Margin)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

EAS 将系统中性能最强的 CPU 核心在其最高物理频率下的算力定义为基准常数 **1024**。其余核心及不同工作频点下的算力均通过缩放比例归一化表示：

.. list-table:: 现代旗舰 SoC 三丛集 CPU 核心容量与能耗参数矩阵
   :widths: 18 18 20 22 22
   :header-rows: 1
   :class: tight-table

   * - 核心丛集 (Cluster)
     - 物理微架构
     - 峰值工作频率
     - 归一化最大容量 (Capacity)
     - 峰值功耗 / 典型能效
   * - **超大核 (Prime)**
     - Cortex-X4 (1 核)
     - 3.4 GHz
     - **1024 (100%)**
     - ~4500 mW (算力爆发，能效比低)
   * - **性能大核 (Big)**
     - Cortex-A720 (5 核)
     - 2.8 GHz
     - **720 (70.3%)**
     - ~1800 mW (主干算力，高吞吐)
   * - **能效小核 (Little)**
     - Cortex-A520 (2 核)
     - 2.0 GHz
     - **360 (35.1%)**
     - ~350 mW (常驻待机，能效极高)

能耗增量评估算法 ($\Delta 	ext{Energy}$)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个处于休眠状态的任务被唤醒时（如 App 收到网络数据包或定时器到期），EAS 调度器在 `select_task_rq_fair()` 中执行能耗预估：

1. **确定算力匹配候选集**：
   若任务当前预估利用率 $	ext{Util}_{	ext{task}} = 200$，小核最大容量为 360，则小核完全有能力在不拉满频率的情况下承载该任务，小核与大核均进入候选集；若 $	ext{Util}_{	ext{task}} = 600$，小核即使拉至最高频也无法按时完成，直接将小核剔除出候选集，仅保留大核与超大核。
2. **计算能耗增量**：
   对于候选集中的每个 CPU 核心 $C_i$，模拟将该任务加入其运行队列后，所在性能域所需提升的 DVFS 目标频点与功耗：

   .. math::

      \Delta 	ext{Energy}(C_i) = E_{	ext{after}}(C_i) - E_{	ext{before}}(C_i)

3. **放置决策**：调度器最终将任务唤醒放置在 $\Delta 	ext{Energy}$ 最小的 CPU 核心上，实现毫秒级动态能效最优收敛。

18.3 负载追踪机制：Linux 原生 PELT vs 移动端 WALT
------------------------------------------------------------------------

EAS 能够做出精准选核的前提，是调度器必须对每个任务所消耗的 CPU 算力（Task Utilization）具备实时、准确的度量。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                PELT (指数衰减) vs WALT (滑动窗口) 负载响应曲线对比      |
   +-------------------------------------------------------------------------+

   [ 场景: 触控滑动发生，UI 线程瞬间满载 (100% 突发算力需求) ]

   算力利用率
   100% |                                      +---------------- (WALT: 1 周期直达!)
        |                                     /|
        |                  PELT 缓慢上升曲线 / |
        |                 ................../  |
        |              ../                     |
    50% |           ../                        |
        |        ../                           |
        |     ../                              |
        |  ../                                 |
     0% +---+-------+-------+-------+-------+--+------------------------> 时间 (ms)
            0       32ms    64ms    96ms   128ms

.. list-table:: PELT 与 WALT 负载追踪算法微架构深度对比
   :widths: 18 41 41
   :header-rows: 1
   :class: tight-table

   * - 算法维度
     - Linux 原生 PELT (Per-Entity Load Tracking)
     - 移动定制 WALT (Window-Assisted Load Tracking)
   * - **数学模型**
     - 基于 32ms 半衰期的几何级数指数衰减加权积分
     - 基于固定滑动时间窗口（如 16ms 或 20ms）的直方图统计
   * - **突发负载响应**
     - **极慢**：从 0 上升至 90% 负载需要 **100ms~150ms**（约 5~8 个 32ms 周期）
     - **瞬时**：在当前窗口结束或检测到突发满载时，**1 个窗口（16ms）即可冲顶**
   * - **空闲衰减速度**
     - 同样经历 32ms 半衰期缓慢回落，释放 CPU 滞后
     - 窗口内若无运行立即清零，功耗释放极快
   * - **移动端优劣势**
     - 适合服务器吞吐；但在手机上导致滑动前几帧严重掉帧
     - **高通/联发科旗舰机标配**；完美适配 60Hz/120Hz 帧周期

uclamp (Utilization Clamping)：用户态对内核调度的意图注入
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了消除内核算法对应用意图推断的滞后性，Linux 内核引入了 **`uclamp`** 机制（通过 `sched_setattr` 或 cgroup 设置）：
- **`uclamp.min`（最低算力钳位）**：前台渲染线程处于交互状态时，Android Framework 将其 `uclamp.min` 设置为 512，强制通知 EAS：“该线程即使当前负载很小，选核与调频时也必须按至少 512 算力配置，直接调用大核并拉升频率！”
- **`uclamp.max`（最高算力封顶）**：后台同步任务或日志上报线程被设置 `uclamp.max = 120`，强制禁止其抢占高频与大核，物理封杀后台耗电。

18.4 前台响应保障机制：cgroup 拓扑、调度组与交互提速
------------------------------------------------------------------------

Android 在内核基础调度器之上，构筑了一套严密的分级控制体系：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  Android cgroup 分组拓扑与 CPU 核心分配矩阵             |
   +-------------------------------------------------------------------------+

   [ 用户操作事件 (Touch / Gesture) ]
        |
        v
   [ 1. top-app (前台焦点 App 主线程、RenderThread、SurfaceFlinger) ]
        |  * CPU 亲和性: 绑定大核 (Cortex-A720) 与超大核 (Cortex-X4)
        |  * CPU 权重 (cpu.shares): 1024 (最高调度优先级)
        |  * uclamp.min: 512 (强制高频)
        v
   [ 2. foreground (可见前台后台服务、播放中音频) ]
        |  * CPU 亲和性: 允许使用小核与大核
        |  * CPU 权重: 512
        v
   [ 3. background / restricted (不可见后台任务、预加载) ]
        |  * CPU 亲和性: 严格限制仅使用小核集群 (Cortex-A520)
        |  * CPU 权重: 50 (极度压制)
        |  * uclamp.max: 100 (物理禁止升频)
        v
   [ 4. cached / frozen (缓存冻结进程) ]
        |  * 利用 cgroup v2 freezer 挂起，完全剥夺 CPU 调度权 (0% CPU 占用)

触控交互提速 (Touch Boost) 与 PowerHAL 联动
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当用户手指首次触碰屏幕（Touch Down）的瞬间：
1. **中断捕获**：触摸屏控制器上报硬件中断，内核 `evdev` 产生输入事件；
2. **PowerHAL 性能提示**：Android `InputReader` 识别到交互行为，立即向厂商 `PowerHAL`（HIDL/AIDL）发送 `INTERACTION` 脉冲提示；
3. **硬件级瞬时升频**：内核在 **< 1ms** 内将 CPU 大核频点拉升至高频（如 2.2GHz），为接下来的视图层级遍历（View Hierarchy Measure / Layout）与首帧渲染注入瞬时爆发算力；
4. **脉冲衰减**：提速脉冲通常维持 100ms~150ms，随交互稳定后平滑交还给 EAS 自适应调速器控制，兼顾跟手度与续航。

18.5 优先级反转 (Priority Inversion) 与内核同步锁继承
------------------------------------------------------------------------

在高度并发的移动操作系统中，最致命的卡顿并非来自 CPU 算力不足，而是来自**隐蔽的锁争用（Lock Contention）引发的优先级反转**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                      典型优先级反转与优先级继承 (PI) 消除机制           |
   +-------------------------------------------------------------------------+

   [ 发生致命反转 (无 PI 保护) ]
   1. 低优先级后台工作线程 L 持有共享互斥锁 Lock_A;
   2. 高优先级 UI 主线程 H 唤醒，尝试获取 Lock_A，被迫挂起阻塞 (Blocked);
   3. 中优先级后台日志线程 M 唤醒 (无需锁)，由于其优先级高于 L，调度器持续让 M 运行;
   4. 结果: L 无法获得 CPU 释放锁，导致最高优先级的 UI 线程 H 被中等优先级的 M 无限期卡死 -> 触发 ANR 掉帧崩溃!

   [ 内核优先级继承 (Priority Inheritance - rt_mutex / futex) 消除反转 ]
   * 当 UI 主线程 H 阻塞在 Lock_A 时，内核检测到持有者为低优先级线程 L;
   * 内核瞬间将 L 的调度优先级临时提升至与 H 完全相同 (Top-App 级别);
   * L 迅速获得 CPU 调度执行并释放 Lock_A;
   * L 释放锁后优先级恢复原状，UI 主线程 H 立即夺回锁并继续渲染，掉帧被消弭于无形!

- **Binder 线程优先级继承**：当前台 App 通过 Binder 同步调用 `system_server` 中的系统服务时，Binder 驱动会自动将发起端线程的优先级、cgroup 与 uclamp 属性透传并注入到 `system_server` 的接收工作线程上，确保跨进程请求不会因服务端排队降级而延迟。

18.6 跨平台对照：Linux EAS + cgroup vs Apple XNU QoS 调度

Chapter 22: 内核安全边界与攻击面收敛：DAC、MAC 与系统调用过滤
========================================================================

.. note:: 前置背景与认知承接
   在前一章中，我们解构了移动硬件电源管理的完整闭环：从毫秒级空闲时的 Tickless Idle (NO_HZ) 动态停跳与 CPUIdle C-State 硬件能级跃迁，到设备级 Runtime PM 拓扑，再到整机挂起 System Suspend 与 Android Doze 策略。然而，移动操作系统的运行环境本质上是一个**零信任的多敌意域（Zero-Trust Multi-Adversary Environment）**：在同一台设备上，用户安装的成百上千个不受信任的第三方应用，与底层高度敏感的生物识别凭据、移动支付私钥、通讯录、麦克风及位置信息物理共存。内核（Kernel / EL1）处于用户态应用程序（EL0）与底层安全世界 / 硬件信任根（EL3 / Secure Enclave）之间的最关键隔离咽喉。本章作为 Part 4 移动内核机制的收官之作，将深入体系结构与内核源码底层，全面剖析移动内核如何通过**硬件特权级约束、重构的 POSIX DAC 独立沙箱、SELinux 强制访问控制 (MAC)、seccomp-bpf 系统调用过滤**以及**内核运行时自防御 (Kernel Self-Protection)** 构筑起多层次纵深防御安全边界。

22.1 硬件特权级与硬件安全原语：ARM64 异常级别与 MMU 隔离
------------------------------------------------------------------------

操作系统内核的一切安全防御逻辑，其终极效力全部建立在硬件体系结构提供的**物理特权级硬隔离（Hardware Privilege Isolation）**之上。在 ARMv8/ARMv9 架构中，处理器在物理上被划分为四个非对称的异常级别（Exception Levels: EL0 ~ EL3）以及安全世界与非安全世界的双重虚拟化拓扑。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              ARM64 硬件异常级别与安全执行环境 (TrustZone) 拓扑          |
   +-------------------------------------------------------------------------+

            [ 非安全世界 (Normal World / Rich OS) ]    [ 安全世界 (Secure World / TEE) ]
   EL0      +------------------------------------+    +--------------------------------+
   (用户态) | 普通应用程序 (Android Apps / Web)  |    | 安全可信应用 (Trustlets / TA)  |
            +------------------------------------+    +--------------------------------+
                              |                                       |
                              | svc (系统调用异常)                    | svc (安全系统调用)
                              v                                       v
   EL1      +------------------------------------+    +--------------------------------+
   (内核态) | 移动操作系统内核 (Linux / XNU 内核)|    | 安全可信操作系统 (Trusty OS)   |
            +------------------------------------+    +--------------------------------+
                              |                                       |
                              | hvc (Hypervisor 调用)                 |
                              v                                       |
   EL2      +------------------------------------+                    |
   (虚拟化) | 虚拟机监视器 (KVM / Hypervisor)    |                    |
            +------------------------------------+                    |
                              \                                      /
                               \                                    / smc (Secure Monitor Call)
                                v                                  v
   EL3      +--------------------------------------------------------------------------+
   (固件层) | 芯片级安全监视器 (ARM Trusted Firmware / ATF / 硬件唯一根密钥 RoT)       |
            +--------------------------------------------------------------------------+

MMU 硬件页表权限位与防提权保护
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

内存管理单元（MMU）通过多级页表转换条目中的物理控制位，在硬件流水线中严格执行权限校验：

1. **AP[2:1] (Access Permissions) 访问控制位**：
   - `00`：仅 EL1 特权级可读写，EL0 用户态访问直接触发硬件级别 Data Abort 异常；
   - `01`：EL1/EL0 均可读写；
   - `10`：仅 EL1 可读（内核只读代码段与常量段）；
   - `11`：EL1/EL0 均只读。
2. **PXN (Privileged Execute-Never) 与 UXN (User Execute-Never)**：
   - **`UXN`**：标记为用户态不可执行（如用户数据堆、栈内存），直接在硬件层面免疫经典的栈溢出代码注入执行（DEP / W^X）；
   - **`PXN`**：标记为特权级不可执行。即使攻击者在用户空间注入了包含提权机器码的内存页，一旦内核被攻击劫持（如篡改函数指针）试图跳转至用户空间执行该代码（典型的 `ret2usr` 攻击），CPU 硬件指令预取单元在发现当前处于 EL1 且执行页被标记为 PXN 时，立即触发 Instruction Abort 致命异常，瞬间熔断攻击链。

ARM 硬件硬件安全扩展：PAN、PAC 与 BTI
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了进一步压缩内核态下的受攻击面，现代移动 SoC（如高通 Snapdragon 8 Gen 系列、联发科天玑 9000 系列及 Apple A/M 系列芯片）全面集成了硬件级安全扩展指令集：

.. list-table:: ARM64 现代硬件安全原语与攻击防御矩阵
   :widths: 15 25 35 25
   :header-rows: 1
   :class: tight-table

   * - 硬件原语
     - 架构扩展标准
     - 硬件微架构机制
     - 防御的核心攻击手法
   * - **PAN**
     - ARMv8.1-A (Privileged Access Never)
     - 当 CPU 处于 EL1 内核态时，硬件**完全阻断对任何 EL0 用户态虚拟地址的直接读写**，仅允许通过专用的 `copy_from_user` / `copy_to_user` 校验指令访问。
     - 杜绝内核代码逻辑漏洞被诱骗直接解引用恶意伪造的用户空间数据指针。
   * - **PAC**
     - ARMv8.3-A (Pointer Authentication)
     - 利用 64 位虚拟地址未使用的顶部 16 位，结合硬件私有密钥（Key）、上下文（SP/Modifier）与 SHA/QARMA 算法生成 16 位密码学签名（PAC Code）注入指针；使用前硬件必须执行 `AUT` 指令验签。
     - 彻底瓦解通过篡改函数返回地址或虚函数表（vtable）指针实施的 **ROP (面向返回编程)** 与 **JOP (面向跳转编程)** 攻击。
   * - **BTI**
     - ARMv8.5-A (Branch Target Identification)
     - 标记合法跳转目标。间接跳转指令（`BR`/`BLR`）的目标地址必须是显式的 `BTI` 硬件标记指令，否则硬件自动抛出异常。
     - 阻断攻击者利用内核代码段内的任意片段（Gadgets）拼凑恶意执行流。
   * - **MTE**
     - ARMv8.5-A (Memory Tagging Extension)
     - 硬件给物理内存的每 16 字节分配一个 4 位的物理标签（Physical Tag），并给指针的高 4 位打上逻辑标签（Logical Tag）；CPU 访存时硬件单周期比对双标签。
     - 硬件单周期秒级捕获 **Use-After-Free (UAF)** 与 **堆缓冲区越界写（Heap Out-of-Bounds）** 内存越界漏洞。

22.2 POSIX 自主访问控制 (DAC) 在移动系统中的特殊重构
------------------------------------------------------------------------

传统的 Unix/Linux 操作系统是为**多用户共享服务器（Multi-user Multi-human）**设计的：系统允许多个真实的人类用户登录，通过统一的 `root` 用户管理全局系统，每个用户拥有私有的 `/home/username` 目录，文件通过 `rwxrwxrwx` 权限位区分为所有者（Owner）、所属组（Group）与其他用户（Other）。

然而在智能手机场景下，整台物理设备通常仅服务于**单一的人类机主**，但机主会安装数百个由不同开发者编写的第三方应用程序。如果继续沿用传统桌面操作系统的模型（所有应用程序均继承当前登录机主的单一 UID 运行），那么任何一个恶意应用都可以肆意读取微信的聊天数据库或相册照片。

移动操作系统对 Linux 原生 POSIX DAC 体系进行了**颠覆性的范式重构：Single-Human, Multi-App Sandbox（单机主，单应用单独立 UID 模型）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |       传统服务器 Linux DAC 拓扑 vs 移动 Android/iOS 沙箱 DAC 拓扑       |
   +-------------------------------------------------------------------------+

   [ 1. 传统 Linux 服务器多用户模型 ]
   人类用户 Alice (UID 1000) ---> 运行 bash, vim, firefox (全部继承 UID 1000)
   人类用户 Bob   (UID 1001) ---> 运行 bash, gcc, python  (全部继承 UID 1001)
   安全边界: Alice 的进程无法读写 Bob 的 /home/bob/，但 Alice 的所有进程间毫无防御!

   [ 2. 移动操作系统单应用独立 UID 沙箱模型 (Android App-per-UID) ]
   人类机主 (唯一所有者: User 0)
     ├── 应用 A: 微信       (系统分配独立虚拟 UID: 10123 / u0_a123)
     │     └── 私有数据目录: /data/user/0/com.tencent.mm/ [权限: rwx------, Owner: 10123]
     ├── 应用 B: 恶意手电筒 (系统分配独立虚拟 UID: 10188 / u0_a188)
     │     └── 私有数据目录: /data/user/0/com.flashlight/ [权限: rwx------, Owner: 10188]
     └── 应用 C: 手机银行   (系统分配独立虚拟 UID: 10205 / u0_a205)
           └── 私有数据目录: /data/user/0/com.bank/       [权限: rwx------, Owner: 10205]

   安全隔离: 应用 B 即使注入恶意代码，在内核文件系统 DAC 检查时，由于 UID 10188 != 10205，
             内核 VFS 直接在底层拒绝 open() 调用，返回 EACCES (Permission Denied)!

Android 虚拟 UID 计算体系与 Linux `struct cred`
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Android 将 32 位的 Linux UID 进行了空间划分，完美支持多用户空间（Multi-user）与工作资料（Work Profile）：

$$	ext{Linux UID} = 	ext{User ID} 	imes 100000 + 	ext{App ID}$$

例如：主用户（User 0）下安装的某个 AppID 为 `10123` 的应用，其 Linux UID 为 `10123`（字符串标识 `u0_a123`）；若在工作分身空间（User 10）中运行该应用，其 Linux UID 变为 $10 	imes 100000 + 10123 = 1010123$（`u10_a123`），从内核层面实现了工作数据与个人数据的物理隔离。

在 Linux 内核内部，每个进程控制块 `task_struct` 均绑定唯一的安全凭证结构体 `struct cred`：

.. code-block:: c

   struct cred {
       atomic_t        usage;
       kuid_t          uid;            /* 真实用户 ID (Real UID: 10123) */
       kgid_t          gid;            /* 真实组 ID (Real GID: 10123) */
       kuid_t          euid;           /* 有效用户 ID (Effective UID，用于权限检查) */
       kgid_t          egid;           /* 有效组 ID */
       kuid_t          fsuid;          /* 文件系统访问 UID (VFS 权限检查依据) */
       kgid_t          fsgid;          /* 文件系统访问 GID */
       struct group_info *group_info;  /* 附加组 ID 列表 (Supplementary GIDs) */
       kernel_cap_t    cap_inheritable;/* POSIX Capabilities 权能集 */
       kernel_cap_t    cap_permitted;
       kernel_cap_t    cap_effective;
       void            *security;      /* 指向 LSM (SELinux) 安全上下文标签指针 */
   };

Android 早期权限机制正是通过附加组（`group_info`）实现的：当应用被授予网络权限时，`Zygote` 进程在 `fork` 应用程序后向其 `struct cred` 的 `group_info` 中注入 `AID_INET`（GID 3003）。当进程尝试调用 `socket(AF_INET, SOCK_STREAM, 0)` 时，内核网络子系统直接检查当前进程是否包含 GID 3003，无此 GID 则直接抛出 `EPERM`。

DAC 的致命结构缺陷：为什么必须引入 MAC？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

尽管 App-per-UID 模型构筑了第一道坚实防线，但传统 DAC 存在两大不可克服的结构性致命缺陷：
1. **超级用户 Root (UID 0) 的特权无上性**：在 DAC 模型中，UID 0 拥有无视一切权限位的“特权通行证”。一旦系统的某个底层守护进程（如 `vold`、`rild` 或 `installd`）因内存漏洞被攻击者提权劫持，攻击者将直接获得 UID 0，随后便可肆意读取全盘数据并刷入恶意驱动；
2. **所有者自主转让失控**：文件所有者可以自行通过 `chmod 777` 降低安全性，恶意软件可利用配置疏漏诱骗其他进程开放权限。

因此，现代移动操作系统必须在 DAC 之上建立更为严格的**强制访问控制（Mandatory Access Control - MAC）**防线。

22.3 强制访问控制 (MAC)：SELinux 深度微架构与 Type Enforcement
------------------------------------------------------------------------

与 DAC“以所有者为中心、支持自主赋权”不同，**MAC（强制访问控制）的核心准则是 Default-Deny（默认彻底拒绝）**：系统中的任何主体（Subject，如进程）对任何客体（Object，如文件、Socket、IPC Binder、设备节点）的访问，必须在预先编译烧录于系统镜像中的安全策略规则库中**显式声明并允许**，否则一律被内核强制阻断；**即便是拥有 UID 0 的 Root 进程，在 MAC 面前也如同普通受限进程，受到极其严苛的规则铁笼约束。**

Android 从 4.4 引入、并在 5.0+ 全面强制启用了基于 Linux Security Modules (LSM) 框架的 **SELinux（Security-Enhanced Linux）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                Linux 内核 LSM 框架与 SELinux 决策微架构                 |
   +-------------------------------------------------------------------------+

   用户空间进程 (Subject: untrusted_app)
        |
        | 系统调用 (如 open(\"/dev/binder\", O_RDWR))
        v
   +-------------------------------------------------------------------------+
   | Linux 内核 VFS / 系统调用入口                                           |
   |   1. 执行基础合法性检查                                                 |
   |   2. 执行传统 POSIX DAC 权限检查 (UID/GID 是否匹配) -> 检查通过!        |
   |   3. 触发 LSM 安全钩子 (LSM Hook: security_file_open())                 |
   +-------------------------------------------------------------------------+
        |
        v
   +-------------------------------------------------------------------------+
   | SELinux 安全子系统 (security/selinux/)                                  |
   |                                                                         |
   |   +-----------------------------------------------------------------+   |
   |   | 访问向量缓存 (Access Vector Cache - AVC)                        |   |
   |   |   * 快速哈希查找: <scontext, tcontext, tclass>                  |   |
   |   +-----------------------------------------------------------------+   |
   |        |                                       ^                        |
   |        | (AVC 未命中 / Miss)                   | (更新缓存条目)         |
   |        v                                       |                        |
   |   +-----------------------------------------------------------------+   |
   |   | 安全策略引擎 (Security Server / Policy Engine)                  |   |
   |   |   * 遍历系统只读策略规则库 (编译自 .te 文件的 SELinux Policy)   |   |
   |   |   * 判定: allow untrusted_app binder_device:chr_file { rw };?   |   |
   |   +-----------------------------------------------------------------+   |
   |        |                                                                |
   |        +-----> 判定结果: [ 允许 (ALLOW) ] -> 继续内核后续 I/O 逻辑      |
   |        |                                                                |
   |        +-----> 判定结果: [ 拒绝 (DENY)  ] -> 打印 avc: denied 日志,     |
   |                                              直接返回 -EACCES 拦截!     |
   +-------------------------------------------------------------------------+

SELinux 安全上下文与 Type Enforcement (TE) 规则模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

SELinux 为内核中的每个进程和每个客体绑定一个标准的字符串安全标签（Security Context），格式为：

$$	ext{User} : 	ext{Role} : 	ext{Type} : 	ext{MLS\_Level}$$

在移动端 Android 中，最关键的核心是 **Type（类型）**，在进程主体上被称为 **Domain（安全域）**，在资源客体上被称为 **Type（类型）**。

.. code-block:: text

   进程主体 (Subject):   u:r:untrusted_app:s0:c512,c768  (第三方应用程序域)
   设备客体 (Object):    u:object_r:camera_device:s0     (相机硬件字符设备节点 /dev/video0)
   服务客体 (Object):    u:object_r:cameraserver_service (Camera 系统服务 Binder 接口)

SELinux 策略文件（`.te`）使用严格的领域特异性语言进行编写：

.. code-block:: text

   # 1. 允许普通第三方应用与系统服务通信 (通过 ServiceManager 查找服务)
   allow untrusted_app cameraserver_service:service_manager find;

   # 2. 允许普通第三方应用通过 Binder IPC 与 cameraserver 进程通信
   allow untrusted_app cameraserver:binder { call transfer };

   # 3. 允许 cameraserver 守护进程直接读写物理相机字符设备
   allow cameraserver camera_device:chr_file { read write ioctl open };

   # 4. 关键安全边界: neverallow 静态强断言 (编译期由 checkpolicy 强制验证)
   # 严禁任何普通应用程序域 (appdomain) 直接打开相机原始字符设备 (必须通过 cameraserver 代理!)
   neverallow appdomain camera_device:chr_file { read write open ioctl };

`neverallow` 规则在 AOSP 编译阶段由安全工具链进行全局形式化验证，任何厂商 ROM 或第三方代码若试图添加绕过系统服务直接访问底层硬件的 `allow` 规则，编译将直接报错中止，从源头杜绝了架构设计上的安全越界。

访问向量缓存 (AVC - Access Vector Cache) 高性能微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

内核每次执行系统调用都需要经过 LSM 钩子检查。如果每次检查都要去解析庞大的 SELinux 策略规则树，将导致系统性能暴跌。
SELinux 在内核中设计了高效的 **AVC（Access Vector Cache）**：
- 以 `(Source SID, Target SID, Target Class)` 作为 64 位复合键（Key）组织全局哈希表；
- 绝大多数高频访问（如 VFS 读写、内存映射、Binder 通信）的 AVC 缓存命中率高达 **99.9%**；
- 单次 MAC 校验仅消耗数个 CPU 时钟周期（单次内存比对与位掩码与操作），将安全检查带来的性能开销压制在 0.5% 以内。

Apple iOS / XNU 中的 Seatbelt (Sandbox.kext) 架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Apple 体系中，XNU 内核基于 FreeBSD 的 **MACF（Mandatory Access Control Framework）** 实现了专有的 **Seatbelt（`sandbox.kext`）** 机制：
- 策略由 Scheme 语言编写的 `.sb` 策略文件定义；
- 在编译阶段被编译为极其紧凑的二叉决策树字节码（Compiled Sandbox Profile）；
- 应用启动时，`launchd` 通过 `sandbox_init_with_parameters()` 系统调用将字节码载入 XNU 内核，将其绑定至当前 Mach `task_t` 的安全槽位中；
- 任何越界的文件访问或 IPC 端口查找直接在 Mach 消息派发层与 BSD VFS 边界被内核静默抛弃。

------------------------------------------------------------------------
22.4 系统调用攻击面收敛：seccomp-bpf 过滤与系统调用沙箱
------------------------------------------------------------------------

即便拥有 DAC 和 MAC，内核本身依然存在巨大的安全漏洞隐患。Linux 内核拥有超过 **450 个系统调用**，而一个常规的移动应用程序在生命周期中只需要使用其中的 **60 ~ 80 个核心系统调用**（如 `read`, `write`, `epoll_wait`, `ioctl` 等）。

那些应用程序几乎从不使用的高危系统调用（例如用于内核热补丁加载的 `kexec_load`、用于进程调试注胶的 `ptrace`、用于命名空间切换的 `setns`、性能剖析接口 `perf_event_open` 以及复杂的 `keyctl` 密钥子系统），往往由于逻辑极其复杂而成为内核 0-day 本地提权漏洞的**重灾区**。

为了将内核的受攻击面压缩至物理极限，移动操作系统全面部署了 **seccomp-bpf（Secure Computing with Berkeley Packet Filter）** 机制。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             seccomp-bpf 在应用启动阶段的下发与内核过滤时序              |
   +-------------------------------------------------------------------------+

   [ Zygote 根孵化进程 (拥有特权) ]
        |
        | 1. fork() 孵化出子进程 (新的 Application Process)
        v
   [ 子进程处于受信任初始化窗口 (App Specialize Phase) ]
        |
        | 2. 设置 PR_SET_NO_NEW_PRIVS 标志位 (永久封死未来通过 setuid/cap 提权的可能性)
        |    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
        |
        | 3. 将预编译好的 BPF 字节码注入内核 seccomp 引擎
        |    prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &bpf_program);
        |
        | 4. 切换为不受信任的应用 UID (如 setresuid(10123, 10123, 10123))
        | 5. 加载第三方 APK 代码并移交控制权
        v
   [ 第三方恶意代码执行 (EL0 处于完全封锁状态) ]
        |
        | 尝试发起恶意系统调用 (如 ptrace(PTRACE_TRACEME, ...) 试图劫持其他进程)
        v
   +-------------------------------------------------------------------------+
   | 内核系统调用入口 (ARM64 el0_svc 向量)                                   |
   |                                                                         |
   |   * 截获系统调用号 __NR_ptrace                                          |
   |   * 内核 BPF 解释器执行 seccomp 规则程序                                |
   |   * 判定: __NR_ptrace 命中黑名单 / 未在白名单中!                        |
   |   * 触发动作: 返回 SECCOMP_RET_TRAP / SECCOMP_RET_KILL_PROCESS          |
   |                                                                         |
   |   * 物理后果: 内核向当前进程投掷 SIGSYS 信号，瞬间将恶意进程强行击毙!   |

seccomp-bpf 过滤指令集与决策返回值
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

seccomp 策略以经典 BPF（cBPF）指令集的形式组织成微型有限状态机：

.. code-block:: c

   /* 传递给内核 seccomp BPF 程序的上下文数据结构 */
   struct seccomp_data {
       int   nr;                    /* 触发的系统调用号 (__NR_openat, __NR_read 等) */
       __u32 arch;                  /* 目标架构标识 (AUDIT_ARCH_AARCH64，防止 32位/64位 ABI 混淆) */
       __u64 instruction_pointer;   /* 触发系统调用时的 PC 寄存器地址 */
       __u64 args[6];               /* 系统调用的 6 个 64 位入参 (arg0 ~ arg5) */
   };

BPF 程序执行完毕后，向内核返回一个 32 位的决策状态码：

.. list-table:: seccomp-bpf 内核决策动作矩阵
   :widths: 25 35 40
   :header-rows: 1
   :class: tight-table

   * - 返回状态码
     - 内核执行行为
     - 适用场景与安全意义
   * - **`SECCOMP_RET_ALLOW`**
     - 放行。系统调用正常进入内核分配执行。
     - 命中白名单的安全系统调用（如 `read`, `write`, `gettimeofday`）。
   * - **`SECCOMP_RET_ERRNO`**
     - 静默拦截。内核不执行系统调用，直接给用户态返回指定的错误码（如 `EPERM` 或 `ENOSYS`）。
     - 伪装系统调用不存在，避免应用程序崩溃，同时彻底阻断恶意探测。
   * - **`SECCOMP_RET_KILL_PROCESS`**
     - 立即处决。内核立即终止该进程所属的整个线程组，不给执行任何退出清理代码的机会。
     - 捕获到明确的恶意越权调用（如尝试直接调用 `reboot` 或 `mount`）。
   * - **`SECCOMP_RET_TRAP`**
     - 发送 `SIGSYS` 信号给进程自身。
     - 用于系统级安全审计、Crash 崩溃转储分析。

通过 seccomp-bpf，Android 将应用能触达的系统调用数量砍掉了 **80% 以上**，即使内核的某些冷门网络协议或文件系统驱动中存在未公开的严重漏洞，只要该系统调用在应用沙箱的 seccomp 规则中被剔除，攻击者便**在物理上失去了向内核发送恶意攻击载荷的入口**。

22.5 内核自防御技术与运行时内存加固 (Kernel Self-Protection)
------------------------------------------------------------------------

除了在边界上进行收敛，现代移动内核在自身二进制镜像和运行时内存组织中集成了深度的**内核自防御技术（Kernel Self-Protection Project - KSPP）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              移动操作系统内核全景自防御技术栈 (KSPP)                    |
   +-------------------------------------------------------------------------+

   [ 1. 编译期与二进制加固 ]
     ├── Clang Forward-edge CFI  : 间接函数指针签名校验，防止篡改内核 ops 虚表
     ├── Clang Shadow Call Stack : 专用 x18 寄存器独立隔离返回地址，硬件免疫 ROP
     └── Initify / __ro_after_init: 初始化完成后将核心配置数据结构强制 remap 为只读

   [ 2. 地址空间与随机化防御 ]
     ├── KASLR (内核地址随机化) : 引导阶段根据硬件随机数 (TRNG) 随机偏移内核基址
     └── KPTI (内核页表隔离)    : 彻底拆分用户态与内核态 PGD 页表，物理防御 Meltdown 侧信道

   [ 3. 内存动态防护与堆加固 ]
     ├── SLAB / SLUB Freelist 混淆与硬件 Canary 保护
     ├── ARMv8.5-A MTE 硬件内存着色 (单周期捕获堆 Use-After-Free 漏洞)
     └── W^X (Write XOR Execute) : 内核内存页严禁同时具备可写与可执行属性

Shadow Call Stack (SCS) 硬件影子调用栈原理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统的栈帧结构中，函数的局部变量与返回地址（Return Address / LR 寄存器）保存在同一个内核栈中。一旦内核发生栈缓冲区溢出漏洞，攻击者可直接覆盖栈上的返回地址，控制内核代码执行流。

Android 内核在 AArch64 上全面启用了 **Shadow Call Stack（SCS / 影子调用栈）**：
- 为每个内核线程分配一个专有的影子栈内存页，该页面绝不存储任何局部变量；
- ARM64 的平台保留寄存器 **`x18`** 被专门用作影子栈指针（SCS Pointer）；
- 函数入口处（Prologue）：硬件指令将 `LR`（返回地址）同时压入常规内核栈与 `x18` 指向的影子栈；
- 函数出口处（Epilogue）：内核**强制从 `x18` 影子栈加载返回地址并执行跳转**，完全忽略常规栈上的返回地址。即使常规栈被攻击者溢出覆盖得面目全非，内核依然能绝对安全地返回到正确的调用点，使得栈溢出 ROP 攻击在物理上彻底失效。

22.6 移动内核纵深防御体系总结与矩阵对比
------------------------------------------------------------------------

移动操作系统的安全性绝非依赖单一组件，而是通过多层异构机制构建的**纵深防御体系（Defense-in-Depth）**。攻击者想要完整攻破一台现代移动终端，必须连续突破五道物理与逻辑防线：

.. list-table:: 移动内核五层纵深防御体系矩阵
   :widths: 15 20 25 25 15
   :header-rows: 1
   :class: tight-table

   * - 防御层级
     - 核心代表技术
     - 裁决与执行位置
     - 核心防护目标
     - 突破难度
   * - **硬件特权层**
     - ARM EL0~EL3, MMU AP/PXN, PAN, PAC
     - CPU 流水线 / 硬件 MMU 转换逻辑
     - 强制特权指令隔离，防止跨越特权级直接执行/读写特权内存。
     - 极高（需硬件架构漏洞或物理探针）
   * - **系统调用过滤层**
     - seccomp-bpf, `PR_SET_NO_NEW_PRIVS`
     - 内核系统调用总入口 (`el0_svc`)
     - 剔除 80% 未使用的高危系统调用，极度收敛内核受攻击面。
     - 很高（无可用入口）
   * - **强制访问控制 (MAC)**
     - SELinux (Android) / Seatbelt (iOS)
     - 内核 LSM 安全钩子 (`security_*`)
     - 终结 Root 特权，对所有进程、文件、IPC 执行默认拒绝策略。
     - 很高（需找到未覆盖策略或 AVC 绕过）
   * - **自主访问控制 (DAC)**
     - App-per-UID, POSIX 权限, `struct cred`
     - 内核 VFS 文件系统 / 进程子系统
     - 隔离不同第三方应用私有数据目录与基本系统资源。
     - 中等（提权可绕过）
   * - **内核自防御层 (KSPP)**
     - KASLR, Shadow Call Stack, CFI, MTE
     - 编译器插桩 / 内核内存管理子系统
     - 即使内核存在代码漏洞，也使内存破坏型 Exploit 无法稳定构建。
     - 极高（组合防御）

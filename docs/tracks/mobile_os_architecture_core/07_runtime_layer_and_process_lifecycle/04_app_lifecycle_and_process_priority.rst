Chapter 36: 应用前后台生命周期与进程优先级状态机

.. note:: 前置背景与认知承接
   在上一章（Chapter 35: Zygote 预加载与写时复制进程孵化加速）中，我们详细剖析了 Android 系统如何利用 Zygote 进程的原型镜像，通过纯单线程环境下的 ``fork()`` 与内存管理单元（MMU）写时复制（COW）机制，在百毫秒内完成应用进程的裂变与安全沙箱专门化。

   当进程被成功孵化并建立 ``ActivityThread`` 消息循环后，系统面临的资源治理挑战才刚刚开始：**在多任务并发的移动设备中，物理内存、CPU 调度周期与电池电量均受到严苛约束，操作系统如何对数十个存活的应用进程实施动态调度与分级治理？**

   传统桌面操作系统将进程视为自由驻留的平权实体，进程只要未主动退出便可一直分配时间片并驻留内存。移动操作系统彻底推翻了这一假设，将应用进程降级为受控的“易失性计算容器”，把用户意图、组件活跃度与系统可用资源映射为动态变化的优先级状态机。本章我们将深入 Android 与 iOS 的进程控制中枢，解构从前台交互到后台回收的完整生命周期，剖析 Android ``oom_score_adj`` 二十一级评分体系与组件优先级继承算法，解析基于 Linux PSI（Pressure Stall Information）的用户态 LMKD 回收引擎，探讨 Apple 基于 XNU ``memorystatus`` 与 Jetsam 的内存水位截杀机制，并确立应对进程非正常死亡的工业级状态保存与恢复模型。

36.1 移动进程生命周期的物理本质：从自由驻留到受控资源实体
------------------------------------------------------------------------

桌面开放模型与移动受控治理模型的物理分水岭
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

桌面操作系统（Linux、macOS、Windows）在设计之初假定设备接驳连续交流电源、拥有虚拟内存交换分区（Swap Disk），并且拥有数十吉字节的物理内存。在这一模型下：
- 进程拥有长周期的驻留权，后台程序可以无约束创建线程池、轮询硬件接口并保持内存驻留；
- 内核的 OOM Killer 仅作为极端灾难状态下的自保手段，非必要绝不轻易终止正常进程。

移动终端的物理约束彻底破坏了上述前提：
1. **电池能量预算受限**：锂电池能量密度存在物理天花板，任何未受管制的后台后台轮询与无序唤醒都会直接导致待机续航崩塌；
2. **被动散热热包络极低**：手机 SoC 缺乏主动风扇散热，持续功耗超过 4W~7W 即会迅速触发芯片结温保护，导致 CPU/GPU 强制降频；
3. **无磁盘 Swap 分区**：移动闪存（UFS/NVMe）存在严格的写入寿命（P/E Cycles）限制，高频写入 Swap 分区会导致闪存坏块剧增；同时移动闪存随机写入延迟远高于 DRAM，无法承受桌面级的页面换出抖动（Thrashing）。

因此，移动操作系统确立了根本性的资源治理公理：**进程仅是承载组件运行的临时容器，系统拥有随时剥夺进程调度资格并回收其地址空间的绝对控制权。进程的生死必须严格挂钩于当前用户可见价值与系统资源水位。**

进程状态分类矩阵与系统行为
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动系统将应用进程划分为五类核心生命周期状态，每个状态对应明确的 CPU 调度配额、物理内存保留级别与网络/传感器访问权限：

.. list-table:: 移动应用进程核心生命周期状态与资源供给矩阵
   :widths: 15 25 30 30
   :header-rows: 1
   :class: tight-table

   * - 状态标识
     - 物理判定条件
     - 调度器配额与 cgroup 划分
     - 内存保留与回收风险
   * - **Foreground**
       (前台活跃)
     - 拥有直接面向用户的焦点窗口，正在响应触控输入，或正在执行生命周期回调。
     - 绑定 ``top-app`` cgroup，分配最高 CPU 容量配额，允许独占全部大核与超大核。
     - 最高级别物理内存保障，禁止被系统回收器回收。
   * - **Visible**
       (前台可见)
     - UI 部分可见但失去输入焦点（如被权限弹窗遮挡、分屏模式非活动区、画中画小窗）。
     - 归入 ``foreground`` cgroup，分配充足时间片，保证 60/120 FPS 渲染流畅度。
     - 享有仅次于前台的内存保留权，仅在系统极端内存耗尽时受波及。
   * - **Service/Perceptible**
       (用户可感知后台)
     - 无可见界面，但持有正在运行的授权前台服务（如后台音乐播放、实时步进导航）。
     - 归入系统特定前台服务调度组，施加 CPU 峰值上限约束以防发热。
     - 优先保留，但若自身发生严重内存泄漏将面临定向清除。
   * - **Background**
       (受限后台工作)
     - 界面完全脱离屏幕，正在执行系统批准的有限短时后台任务（如 WorkManager 同步）。
     - 压制至 ``background`` / ``restricted`` cgroup，严格限制并发核心数量与频点。
     - 处于回收候选边缘，系统资源告警时优先缩减其执行配额。
   * - **Cached / Suspended**
       (挂起/缓存驻留)
     - 无任何活动组件运行，代码执行被挂起（iOS Suspended / Android 进程冻结器 cgroup v2 freezer）。
     - **分配 0% CPU 时间片**，所有用户态线程被内核强行暂停运行。
     - **纯粹作为启动加速缓存保留**，在系统出现任何轻微内存压力时首当其冲被按序清除。

36.2 Android 进程重要性分层与 oom_score_adj 状态机
------------------------------------------------------------------------

ProcessRecord 与重要性评分体系
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Android 系统的服务治理中枢（``system_server``）内部，``ActivityTaskManagerService``（ATMS）与 ``ActivityManagerService``（AMS）通过 ``ProcessList`` 深度维护着全系统每一个运行中进程的抽象元数据对象——``ProcessRecord``。

为了让 Linux 内核及底层的低内存管理程序获知各进程的相对重要程度，Android 引入了从 **-1000 到 +1000** 的离散数值矩阵——**``oom_score_adj``**。数值越小，代表进程越重要；数值越大，代表进程优先级越低，越容易被系统回收：

.. list-table:: Android 进程重要性梯队与 oom_score_adj 映射基准
   :widths: 18 20 18 44
   :header-rows: 1
   :class: tight-table

   * - 优先级梯队标识
     - oom_score_adj 常量
     - 典型分值范围
     - 处于该梯队的典型组件与系统状态
   * - **SYSTEM_ADJ**
     - SYSTEM_ADJ
     - -900
     - ``system_server`` 核心守护进程，持有全系统核心服务。
   * - **PERSISTENT_PROC**
     - PERSISTENT_PROC_ADJ
     - -800
     - 系统常驻应用（如 Telephony 电话服务、蓝牙底层服务）。
   * - **PERSISTENT_SERVICE**
     - PERSISTENT_SERVICE_ADJ
     - -700
     - 承载关键系统组件并被标记为 persistent 的子进程。
   * - **TOP_APP**
     - FOREGROUND_APP_ADJ
     - 0
     - **当前获得焦点、用户正在直接触控交互的前台顶层应用**。
   * - **BOUND_TOP**
     - BOUND_TOP_APP_ADJ
     - 50
     - 接受 TOP 应用显式高优先级绑定的外部服务进程。
   * - **FOREGROUND_SERVICE**
     - PERCEPTIBLE_APP_ADJ
     - 50 ~ 100
     - 声明有可见通知的前台服务（如后台网易云音乐播放、高德导航）。
   * - **VISIBLE_APP**
     - VISIBLE_APP_ADJ
     - 100
     - 界面可见但失去焦点的 Activity（如被对话框遮挡的底层页面）。
   * - **PERCEPTIBLE_APP**
     - PERCEPTIBLE_LOW_APP_ADJ
     - 200 ~ 250
     - 用户仍可感知的组件（如悬浮窗、处于活跃状态的输入法 IME）。
   * - **BACKUP_APP**
     - BACKUP_APP_ADJ
     - 300
     - 正在执行本地或云端数据备份任务的应用进程。
   * - **HEAVY_WEIGHT**
     - HEAVY_WEIGHT_APP_ADJ
     - 400
     - 在 Manifest 中声明为重度运行、尽量避免杀死的特权进程。
   * - **SERVICE_APP**
     - SERVICE_ADJ
     - 500
     - 启动了普通后台 Service 超过 30 分钟的后台服务进程。
   * - **HOME_APP**
     - HOME_APP_ADJ
     - 600
     - 桌面启动器（Launcher）进程，受系统特殊保护以确保退回桌面流畅。
   * - **PREVIOUS_APP**
     - PREVIOUS_APP_ADJ
     - 700
     - 用户上一个刚刚切走的应用（便于在两个应用之间快速来回切换）。
   * - **SERVICE_B**
     - SERVICE_B_ADJ
     - 800
     - 运行时间过长的普通后台服务，降级进入低优先级回收保护区。
   * - **CACHED_APP**
     - CACHED_APP_MIN_ADJ ~ CACHED_APP_MAX_ADJ
     - 900 ~ 999
     - **无任何活动组件的后台缓存进程**，按最近使用时间（LRU）升序分布。

动态权重仲裁算法：``computeOomAdjLSP()``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

系统并非静态固化上述分值，每当系统内发生特定事件（如用户点击返回桌面、启动新 Activity、服务绑定、广播派发或定时器触发），AMS 都会遍历任务拓扑，执行核心动态决策函数 ``OomAdjuster.computeOomAdjLSP()``：

.. code-block:: text

   事件输入 (Activity 状态切换 / Service 绑定 / 广播开始与结束)
     |
     v
   OomAdjuster.updateOomAdjLSP()
     |
     +--> 遍历 ProcessRecord 列表，执行 computeOomAdjLSP():
           |
           +-- 1. 扫描进程内所有 Activity 状态:
           |      - 若包含 RESUMED 状态 -> 设为 FOREGROUND_APP_ADJ (0)
           |      - 若包含 PAUSING / PAUSED / STOPPING 状态 -> 设为 VISIBLE_APP_ADJ (100)
           |
           +-- 2. 扫描进程内所有 Service 状态:
           |      - 检查是否调用 startForeground() 并持有有效通知 -> 提权至 50
           |      - 检查是否正处于生命周期执行中 (onCreate/onStartCommand) -> 提权至 0
           |
           +-- 3. 扫描进程内 BroadcastReceiver 状态:
           |      - 若正在主线程执行 onReceive() -> 临时提权至 FOREGROUND_APP_ADJ (0)
           |
           +-- 4. 依赖传导遍历 (Dependency Propagation):
           |      - 遍历所有与当前进程建立连接的 ServiceConnection 与 ContentProviderConnection
           |      - 依据绑定 Flags (如 BIND_ABOVE_CLIENT, BIND_IMPORTANT) 提升服务提供方 Adj
           |
           v
   应用最新计算结果:
     - 将最终 oom_score_adj 写入 Linux 内核节点: /proc/[PID]/oom_score_adj
     - 调整进程对应的 cgroup 分组 (如移动至 /sys/fs/cgroup/uid_10185/pid_1234/cgroup.procs)
     - 同步通知用户态 lmkd 守护进程更新其内部红黑树索引

组件依赖与优先级提升传递 (Priority Inheritance)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在微服务化与组件化架构中，客户端进程与服务端进程之间常存在强依赖关系。若一个处于后台的进程（``oom_score_adj = 900``）为前台正处于交互状态的应用（``oom_score_adj = 0``）提供关键远程数据，如果系统单纯依据后台进程自身的属性对其执行回收，将导致前台应用因跨进程通信中断而发生崩溃。

Android 建立了严密的优先级提升传导机制：

.. code-block:: text

   +--------------------------+                +--------------------------+
   |   前台输入法 / 购物 App   |                |     后台支付服务进程      |
   | (Process A, Adj = 0)     |                | (Process B, 原始 Adj = 800)|
   +--------------------------+                +--------------------------+
                |                                           |
                |  Context.bindService(..., BIND_AUTO_CREATE |
                |                           BIND_IMPORTANT) |
                +==========================================>|
                                                            |
                     [AMS 计算依赖传递链]                    |
                     Process B 动态继承 Process A 的重要性    |
                     Process B 的 oom_score_adj 被强制提权至 50
                                                            v
                                               +--------------------------+
                                               | 提升后受系统保护, 豁免回收 |
                                               +--------------------------+

- **`BIND_AUTO_CREATE`**：当客户端与服务建立连接时，若服务未运行则自动启动，服务重要性跟随客户端提升；
- **`BIND_IMPORTANT`**：将服务端提升至与客户端完全同级的可见性保障；
- **`BIND_NOT_FOREGROUND`**：压制提权效果，禁止服务端提升至最高前台级别；
- **`BIND_WAIVE_PRIORITY`**：明确放弃影响服务端的优先级，服务端维持其自身既有 Adj 运行。

36.3 内存压力检测与回收执行中枢：Linux LMKD 与 PSI 事件机制
------------------------------------------------------------------------

从内核态 LowMemoryKiller 到用户态 LMKD 的演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在早期 Android 版本中，低内存回收逻辑由 Linux 内核驱动模块 ``lowmemorykiller.ko``（In-kernel LMK）硬编码实现。内核维护了一张固定的阈值对照表：

.. code-block:: text

   /sys/module/lowmemorykiller/parameters/minfree   (空闲页框阈值数组)
   /sys/module/lowmemorykiller/parameters/adj       (对应的 oom_score_adj 阈值数组)

当系统空闲页框跌破某档阈值时，内核直接遍历进程链表，找出首个满足条件的大内存进程，向其投递 ``SIGKILL`` 信号。

这种早期设计存在三大不可调和的工程缺陷：
1. **策略固化于内核态**：Linux 上游社区始终拒绝接纳 LMK 进入主线内核，认为内存回收策略属于用户态职责；
2. **判断维度单一且滞后**：仅以“空闲物理内存页面数量（Free Pages）”作为触发判断，无法感知匿名页与文件缓存页的周转率，更无法获知系统是否已发生严重的 I/O 等待与内存分配阻塞；
3. **无法与现代 cgroup v2 深度协同**：难以实现基于 cgroup 的整组进程冻结与多维度压力控制。

自 Android 9 (Pie) 起，Google 全面引入用户态守护进程 **``lmkd`` (Low Memory Killer Daemon)**，并在后续版本中彻底废除内核驱动，将回收中枢迁移至用户空间。

PSI (Pressure Stall Information) 阻塞监测微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代移动系统感知内存紧缺的最核心依据不再是剩余内存绝对值，而是 **内核 PSI（Pressure Stall Information）机制**。

PSI 实时监测 CPU、内存与 I/O 资源因为供需失衡而导致任务被强制阻塞挂起的时间比例（文件节点位于 ``/proc/pressure/memory``）：
- **``some`` 指标**：至少有一个任务因为等待内存分配（如执行物理页回收、匿名页写出到 ZRAM）而发生停顿的时间占比；
- **``full`` 指标**：**系统中所有非空闲任务同时因为内存短缺而全部停顿**的时间占比。此时 CPU 算力被彻底闲置，系统发生死锁级卡顿。

.. code-block:: text

   lmkd 初始化监听流程:
     1. 打开 /proc/pressure/memory
     2. 配置触发阈值 (例如: 200ms 内 full 阻塞超过 50ms)
     3. 注册 epoll_ctl(epollfd, EPOLL_CTL_ADD, psi_fd, ...)
     4. lmkd 线程安全阻塞于 epoll_wait()
            |
            v  [系统发生严重内存争用，内核触发 PSI 阈值中断]
     5. epoll_wait() 瞬间唤醒 lmkd 守护线程
     6. lmkd 启动分级回收裁决状态机

LMKD 进程回收决策流程
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 LMKD 被 PSI 唤醒后，其内部执行极其高效的内存扫描与杀死裁决：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       LMKD 用户态内存回收决策流程图                       |
   +-------------------------------------------------------------------------+
   epoll 触发 PSI 压力事件 (Medium / Critical)
     |
     v
   1. 检查各 oom_score_adj 槽位中的候选进程 (从 999 向下逐级扫描)
     |
     v
   2. 评估进程物理内存特征 (读取 /proc/[PID]/statm 获取 RSS 与 VSS):
     |  - 计算该进程释放后能够返还的物理内存总量 (估算 USS)
     |  - 检查该进程最近是否处于活跃状态 (活跃访问保护)
     |
     v
   3. 判定当前压力级别:
     |-- [Medium 压力]:
     |     - 仅在 oom_score_adj >= 900 (CACHED 梯队) 中按 LRU 顺序杀死单一进程
     |     - 观察内存恢复状态，避免过度杀伤
     |
     +-- [Critical 压力 (系统濒临崩溃)]:
           - 跨越 CACHED 梯队，直接深入 SERVICE_ADJ (500) 甚至 PERCEPTIBLE_ADJ (200)
           - 优先选择驻留内存（RSS）最大的贪婪进程实施精确斩首
           - 调用 kill(pid, SIGKILL) 强行注销进程
     |
     v
   4. 进程消亡通知:
     - 内核回收进程全部页表与物理页框，释放匿名内存
     - 产生 SIGCHLD 信号通知父进程 Zygote
     - Zygote 清除内部子进程记录
     - AMS 捕获进程死亡事件，清理 ProcessRecord 并将对应 Activity 标记为待重建

36.4 Apple 进程治理与 Jetsam 回收机制

UIKit / SwiftUI 应用状态机转换拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Apple iOS 平台的公开生命周期模型紧密围绕用户界面会话（``UIScene``）与全局应用状态（``UIApplication.State``）展开：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Apple iOS 核心生命周期状态迁移图                     |
   +-------------------------------------------------------------------------+
   用户点击图标
     |
     v
   [Not Running] (未运行状态)
     |
     +--> [Inactive] (前台非活动态: 正在启动 / 系统电话呼入 / 控制中心展开)
           |
           +--> [Active] (前台活跃态: 拥有完整事件响应循环与 120Hz 渲染权)
                 |
                 | (用户上滑退回桌面)
                 v
           [Inactive] (转场动画执行中)
                 |
                 v
           [Background] (后台运行态: 获得约 5~30 秒短时执行窗口完成收尾)
                 |
                 +-- [申请 Background Task / 声明特定 Background Modes] --> 继续受控工作
                 |
                 | (后台窗口耗尽且无特许模式)
                 v

XNU 内核 memorystatus 与 Jetsam 优先级机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 iOS 底层，进程生命周期与内存回收不是由独立用户态守护进程执行，而是由 **XNU 内核内部的 ``memorystatus`` 子系统（常统称为 Jetsam）** 原生管理。

与 Android 类似，XNU 为系统中运行的所有 Mach 任务（Tasks）维护着多级离散的 Jetsam 优先级队列（Jetsam Bands）：

.. list-table:: Apple XNU 内核 memorystatus 核心优先级队列分段
   :widths: 20 20 60
   :header-rows: 1
   :class: tight-table

   * - Jetsam 优先级分段
     - 优先级数值 (Band)
     - 包含的系统服务与应用实体
   * - **JETSAM_PRIORITY_IDLE**
     - 0
     - **处于 Suspended 状态的所有普通第三方应用**，回收流水线首要清除目标。
   * - **JETSAM_PRIORITY_BACKGROUND**
     - 20
     - 正在后台运行受控音频、后台定位或推送同步任务的应用。
   * - **JETSAM_PRIORITY_MAIL**
     - 40
     - 专用于系统邮件后台轮询等特定预置服务的保护通道。
   * - **JETSAM_PRIORITY_FOREGROUND_SUPPORT**
     - 80
     - 为前台活跃应用提供底层支撑的附属服务（如部分渲染扩展、输入支持）。
   * - **JETSAM_PRIORITY_FOREGROUND**
     - 100
     - **当前处于前台活跃状态的应用（Active App）**。
   * - **JETSAM_PRIORITY_SYSTEM**
     - 200+
     - 核心系统级守护进程（如 ``launchd``, ``SpringBoard``, ``backboardd``）。

单进程物理内存高水位线 (Footprint Limit) 惩罚
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

iOS 与 Android 在内存治理策略上存在一个重大差异：**iOS 为每个设备型号与应用类型设定了极其严苛的单进程物理内存配额上限（Per-Process Memory Footprint Limit）**。

- 在拥有 6GB 物理内存的 iPhone 机型上，普通前台应用的物理内存上限通常被限制在 2.5GB~3GB 左右；
- 后台扩展程序（App Extensions，如 Widget 或输入法扩展）的上限甚至低至 30MB~120MB；
- XNU 监控的是该进程实际占用的 **Dirty Pages（脏物理页）与 Compressed Pages（压缩页）** 之和（通过内核 ``task_info`` 读取）；
- **越线即死机制**：一旦前台或后台应用的内存 Footprint 突破了该上限，无论当前系统整机还剩多少空闲内存，XNU 的 Jetsam 机制将**在微秒级时间内直接向其发送 ``SIGKILL`` 信号予以击杀**，并在系统崩溃日志中生成专属的 ``EXC_RESOURCE -> WAKEUPS / MEMORY`` 报告。

36.5 进程死亡与状态恢复架构 (State Restoration)
------------------------------------------------------------------------

进程非正常死亡是移动系统的执行常态
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在移动应用开发与架构设计中，最大的反模式是将桌面系统的思维代入移动端，误以为每个进程退出前都一定会走完完整的清理回调（如 Android 的 ``Activity.onDestroy()`` 或 iOS 的 ``applicationWillTerminate:``）。

移动系统的物理现实是：**当应用进入 Cached 或 Suspended 状态后，系统为了释放内存所执行的回收是底层的 ``kill(PID, SIGKILL)`` 系统调用**。该信号由内核强制执行，**用户态进程没有任何机会拦截该信号，也不会有任何一行析构代码获得执行机会**。

因此，进程死亡不是“异常故障”，而是移动系统的“正常输入”。优秀的移动架构必须将进程死亡与就地状态恢复设计为核心支撑支柱。

状态分层与边界隔离拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了在进程被物理销毁后依然能够向用户呈现无缝连贯的使用体验，系统中的状态必须执行四层解耦：

.. list-table:: 移动应用状态多级持久化与恢复模型
   :widths: 18 27 25 30
   :header-rows: 1
   :class: tight-table

   * - 状态层级
     - 涵盖的数据实体
     - 生命周期与驻留介质
     - 跨进程死亡恢复方案
   * - **UI 瞬态**
       (Transient UI State)
     - 滚动列表偏移量、输入框未提交文本、当前选中 Tab 索引。
     - 随 Activity/View 实例存活，驻留于内存堆中。
     - 依赖系统托管的 SavedState 框架（Android ``onSaveInstanceState`` / iOS Scene Restoration）。
   * - **导航会话态**
       (Navigation State)
     - 页面回退栈结构、跨模块路由参数、页面间数据传递。
     - 随当前 Task/Scene 存活，受系统框架层控制。
     - 序列化为轻量路由 URI 或结构化参数，交由系统框架在进程重启时回放重建。
   * - **领域数据态**
       (Domain State)
     - 购物车清单、已编辑的文章草稿、本地配置参数。
     - 跨越进程生命周期，独立于 UI 结构。
     - **即时落盘存储**（SQLite / Room / CoreData / DataStore），严禁仅保留于单例或内存。
   * - **远端异步态**
       (Remote Task State)
     - 正在进行的大文件断点续传、未提交的网络请求队列。
     - 受网络连接与服务端会话约束。
     - 依托持久化作业队列（WorkManager / Background URLSession）由系统服务接管调度。

Android SavedState 机制与 Binder 1MB 物理缓冲区限制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Android 提供了基于 ``onSaveInstanceState(Bundle)`` 的界面轻量恢复机制。然而，这一机制背后隐藏着一个高频引发线上崩溃的硬件与系统边界限制：**Binder 驱动事务缓冲区上限**。

1. **机制流转原理**：当 Activity 离开前台时，Framework 会调用各层 View 的 ``onSaveInstanceState()``，将数据序列化打包为一个 ``Bundle``。该 ``Bundle`` 随后通过 Binder IPC **跨进程发送给 ``system_server`` 由 AMS/ATMS 统一替应用保存在系统内存中**；
2. **物理缓冲区瓶颈**：每一个通过 ``mmap()`` 接入 Binder 驱动的进程，内核仅为其分配了 **1MB（实际为 1024KB - 8KB = 1016KB）的异步共享内存空间**；
3. **TransactionTooLargeException 根因**：该 1MB 缓冲区被当前进程内**所有正在并发执行的 Binder 通信交易所共享**。若应用误将大尺寸 Bitmap、数百条序列化模型对象列表塞入 ``Bundle``，单次传输体积一旦超过缓冲区安全边界（通常超过 500KB 即面临极高风险），内核 Binder 驱动将直接返回错误码，抛出臭名昭著的 ``TransactionTooLargeException`` 运行时崩溃。

.. code-block:: text

   【反模式：违背物理边界】
   UI State Bundle -----------------------------------------> Binder IPC 跨进程传输 (超限崩溃!)
      - 序列化整部书籍章节数据 (800KB)                         (上限 1MB 共享空间击穿:
      - 携带原始高分辨率位图                                   android.os.TransactionTooLargeException)

   【最佳实践：键值指针化 (Key-Pointer Pattern)】
   1. 大体积业务事实 (草稿正文) --------> 写入本地轻量数据库 (Room/SQLite) 生成主键 UUID: "draft_9527"
   2. UI State Bundle 仅携带轻量指针 ---> 通过 Binder 传输 (体积 < 1KB, 绝对安全)
      - Bundle.putString("draft_id", "draft_9527")
      - Bundle.putInt("scroll_offset", 1420)
   3. 进程重启后:
      - 依据 "draft_id" 从本地数据库异步拉取大文本
      - 依据 "scroll_offset" 恢复视图滚动位置

本章系统解构了移动操作系统进程生命周期与资源治理优先级的底层实现逻辑：
- 剖析了移动硬件受限于电池功耗、热包络与闪存寿命，将应用进程降级为受控瞬态容器的架构必然性；
- 深入解剖了 Android 基于 ``oom_score_adj``（-1000 至 +1000）的二十一级细粒度优先级状态机，推导了 ``OomAdjuster`` 的动态评分机制与基于 Service/Provider 依赖关系的优先级继承传递算法；

- 探讨了 Apple iOS 基于 XNU 内核 ``memorystatus`` 与 Jetsam 机制的离散优先级设计，剖析了单进程物理内存 Footprint 上限的强制截杀模型；
- 确立了移动系统“进程必死”的核心设计准则，建立了基于 UI 瞬态、导航态与持久领域态的分层恢复架构，揭示了 Binder 1MB 事务缓冲区引发 ``TransactionTooLargeException`` 的底层机理与键值指针化设计规范。

然而，在移动操作系统的另一极——Apple iOS 平台，其应用运行并不依赖类似 ART 的托管虚拟机与垃圾收集器，而是依托纯粹的机器码编译与静态原生运行时体系。在下一章 **Chapter 37: Apple 原生运行时：Mach-O 格式、dyld 4 共享缓存与 ARC 内存模型 (05_apple_dyld_and_arc.rst)** 中，我们将转向 Apple 平台的底层技术核心，深度解析 ARM64 架构下 Mach-O 二进制文件格式、dyld 4 动态链接器的高性能共享缓存与符号绑定微架构，以及自动引用计数（ARC）在编译期与运行期的硬件协同实现。

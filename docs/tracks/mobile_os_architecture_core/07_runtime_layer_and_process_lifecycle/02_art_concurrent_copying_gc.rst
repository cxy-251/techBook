========================================================================
Chapter 34: ART 并发垃圾回收 (CC-GC) 与停顿时间控制
========================================================================

.. note:: 前置背景与认知承接
   在上一章（Chapter 33: Android 运行时微架构：DEX、解释器、JIT 与 AOT）中，我们解构了托管代码从紧凑的 DEX 格式加载到内存，经由 nterp 纯汇编解释器、JIT 异步编译到 AOT 本地机器码的执行引擎闭环。

   然而，无论代码是以解释器还是本地机器码运行，Java/Kotlin 对象的分配与生命周期均受管于运行时堆（Managed Heap）。在 60Hz/120Hz 移动人机交互场景下，每帧的计算预算被硬性压缩至 16.6ms 乃至 8.3ms。如果在用户交互、列表滑动或复杂动画渲染期间，垃圾收集器（Garbage Collector, GC）引发数十毫秒的全系统线程暂停（Stop-The-World, STW），就会直接造成丢帧、触控迟滞与严重卡顿。

   为了在彻底消除物理内存碎片的同时将 STW 停顿时间压制在亚毫秒（Sub-millisecond）级，Android 8.0 起全面引入了 **并发拷贝垃圾回收器（Concurrent Copying Garbage Collector, 简称 CC-GC）**。本章我们将深入 ART 的内存堆微架构，解剖 RegionSpace 的物理空间布局与 TLAB 无锁分配、Baker 风格读屏障（Baker-style Read Barrier）的硬件级实现、并发三色标记与对象疏散（Evacuation）算法，以及移动端 UI 停顿控制与内存抖动的物理排查链路。

34.1 移动垃圾回收的演进困境与停顿时间物理挑战
------------------------------------------------------------------------

从 Dalvik 到 ART 早期收集器的演进轨迹
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动设备的物理硬件特性对垃圾回收机制构成了极其严苛的约束：
1. **物理内存预算有限**：缺少桌面系统的离线大内存与高速虚拟内存 Swap 分区，ZRAM 压缩依赖 CPU 计算；
2. **电池能效与发热包络**：GC 线程若长时间占满高能效 CPU 大核，会迅速引发芯片过热降频；
3. **极低帧延迟容忍度**：UI 线程与 RenderThread 的任何毫秒级阻塞都会直接转化为用户肉眼可见的掉帧（Jank）。

回顾 Android 运行时垃圾回收器的演化历程，每一次重大架构革新本质上都是在**停顿时间（Pause Time）**、**吞吐量（Throughput）**与**内存碎片（Fragmentation）**之间进行的工程决断：

.. list-table:: Android 运行时垃圾回收器历史架构演进对比
   :widths: 15 20 25 20 20
   :header-rows: 1
   :class: tight-table

   * - 收集器代际
     - 核心回收算法
     - 典型 STW 停顿时间
     - 内存碎片整理能力
     - 物理开销与瓶颈
   * - **Dalvik GC**
       (Android 2.x~4.4)
     - 标记-清除
       (Mark-Sweep)
     - 10ms ~ 50ms+
       (两次长时间 STW)
     - 无整理能力
       (严重内存碎片化)
     - 停顿直接打穿帧预算；内存碎片导致即使总空闲内存充裕也因无法找到连续页而抛出 OOM。
   * - **ART CMS**
       (Android 5.0~7.x)
     - 并发标记-清除
       (Concurrent Mark-Sweep)
     - 1ms ~ 5ms
       (微秒级 Root 枚举)
     - 无整理能力
       (仅在切入后台时转为同质空间压缩)
     - 并发标记大幅削减 STW，但碎片问题依然存在；长时间运行后堆空间离散，分配大对象成本高昂。
   * - **ART Semi-Space**
       (Android 早期实验)
     - 半空间拷贝
       (Semi-Space Copying)
     - 10ms ~ 30ms
       (拷贝过程全量 STW)
     - 绝对紧凑整理
       (零内存碎片)
     - 堆内存空间利用率减半（仅能使用 50% 内存，另一半作为 To-Space 备用）；拷贝时必须暂停所有业务线程。
   * - **ART CC-GC**
       (Android 8.0 至今标准)
     - **并发拷贝与区域化整理**
       (Concurrent Copying)
     - **< 0.5ms (通常 50~200μs)**
       (仅初始标记与最终切换)
     - **强力紧凑整理**
       (彻底消除内存碎片)
     - 依赖编译器内联读屏障（Read Barrier）拦截对象解引用；以极小的 CPU 读开销换取完全并发的对象搬移。

Stop-The-World (STW) 的硬件与系统级破坏力
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统的标记-清除或非并发拷贝算法中，STW 机制通过在所有编译生成的代码边界插入安全点（Safepoint/Checkpoint）轮询指令实现。当 GC 发起 STW 请求时：
- 所有运行托管代码的线程在下一个 Safepoint 被操作系统互斥锁挂起（Futex Sleep）；
- UI 线程正在执行的测量、布局（Layout）或绘制（Draw）指令被迫中断；
- 硬件显示子系统的 VSYNC 垂直同步信号到达时，RenderThread 无法从阻塞的 BufferQueue 提交新的图像帧，显示控制器只能重复扫描上一帧画面，硬件层面表现为严重的掉帧中断；
- 移动系统的交互流畅性要求将 STW 时间控制在亚毫秒（Sub-millisecond）级别，甚至让核心标记与对象搬移过程完全在后台并发完成。

34.2 ART 堆内存微架构：RegionSpace 与内存空间拓扑
------------------------------------------------------------------------

多 Space 复合堆架构全景
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ART 虚拟机内部（`art/runtime/gc/heap.h`），堆内存并非一块均匀扁平的虚拟地址段，而是由多个具备不同生命周期策略、内存对齐规则与分配特性的专属子空间（Space）逻辑复合而成：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     ART Managed Heap 物理虚拟地址空间拓扑                |
   +-------------------------------------------------------------------------+
   | Image Space (Boot Image /system/framework/boot.art)                     |
   |   - 只读共享内存映射 (mmap PROT_READ MAP_SHARED)                         |
   |   - 跨所有应用进程零拷贝共享，零 GC 开销，完全不可变                       |
   +-------------------------------------------------------------------------+
   | Zygote Space (Zygote 进程预加载的系统类与核心单例对象)                    |
   |   - 写入时复制 (Copy-On-Write)，只读段跨进程复用，脏页局部私有化           |
   +-------------------------------------------------------------------------+
   | Non-Moving Space (不可移动对象空间)                                      |
   |   - 存储 Class 原型对象、JNI 全局引用、本地线程映射结构等内部关键元数据     |
   |   - GC 过程中绝不改变物理内存地址，避免破坏底层 Native 指针引用           |
   +-------------------------------------------------------------------------+
   | Large Object Space (LOS 大对象空间 - 离散页分配器)                       |
   |   - 专门容纳体积大于 12KB 的连续大对象 (如 Bitmap 像素字节数组)          |
   |   - 采用独立系统页分配管理，回收时直接释放虚拟页，避免在主堆上搬运高昂数据  |
   +-------------------------------------------------------------------------+
   | RegionSpace (区域化主堆 - CC-GC 核心运作空间)                            |
   |   - 由数千个大小相等的固定 Region 构成 (默认单 Region 容量 1MB 或 2MB)     |
   |   - 承担绝大多数 Java/Kotlin 对象的极速分配、并发标记与移动疏散压缩       |
   +-------------------------------------------------------------------------+

RegionSpace 物理拓扑与状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

RegionSpace（`art/runtime/gc/space/region_space.h`）将一片连续的高达数百兆字节的虚拟内存空间均匀切割为固定大小的 **Region**。每个 Region 拥有独立的状态标记与指针边界：

.. code-block:: text

   Region 内部物理结构:
   +-----------------------+----------------------------------+--------------+
   | 已分配对象数据区       | TLAB 当前分配游标                | 未使用空闲空间|
   | (Live / Dead Objects) | (Allocating: begin_ -> top_)     | (top_ -> end)|
   +-----------------------+----------------------------------+--------------+
   ^ begin_                                                   ^ end_
                           ^ top_ (Bump Pointer)

在 CC-GC 的生命周期中，每个 Region 在状态机驱动下动态流转：

.. list-table:: RegionSpace 中 Region 的核心状态及其生命周期语义
   :widths: 22 25 53
   :header-rows: 1
   :class: tight-table

   * - Region 状态定义
     - 物理角色定义
     - 在当前 GC 轮次中的物理操作行为
   * - `kRegionFree`
     - 完全未分配的空闲区域
     - 尚未分配物理页或已被回收；当需要新空间时被唤醒分配。
   * - `kRegionInToSpace`
     - **To-Space (活动/目标区)**
     - 当前正在接收新分配对象的区域，或作为存活对象被拷贝移动过来的目的地。
   * - `kRegionFromSpace`
     - **From-Space (回收源区)**
     - 存有上一轮次遗留对象的区域。本轮 GC 需要对其进行扫描，将存活对象疏散搬移出去。
   * - `kRegionUnevacFromSpace`
     - **不疏散源区**
     - 属于 From-Space 但被策略判定为无需物理搬移的区域（如大对象集中区），仅就地并发标记其存活对象。
   * - `kRegionLargeTail`
     - 连续大对象尾部
     - 当对象体积超过单个 Region 容量时，连续跨越多个 Region，后续 Region 标记为 Tail。

TLAB 线程本地分配缓冲区与无锁碰撞指针分配
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在多线程高并发创建对象的场景下（如主线程解析 JSON 的同时后台线程解码网络图片），若所有线程共用一把全局互斥锁在堆上寻找空闲槽位，锁争用（Lock Contention）将导致严重的 CPU 调度上下文切换。

RegionSpace 采用了 **TLAB (Thread-Local Allocation Buffer)** 架构：
1. 每个 Java 线程绑定一个私有的 `ThreadLocalAllocationBuffer`；
2. 当线程需要分配对象时，首先在绑定的私有 TLAB 内部执行 **碰撞指针分配 (Bump-Pointer Allocation)**：
   - 读取本地指针 `top_` 与边界指针 `end_`；
   - 计算新对象所需对齐字节数（8 字节对齐）；
   - 若 `top_ + size <= end_`，直接将 `top_` 前移并返回起始地址，**整个分配路径仅需 3 条汇编指令，无任何锁操作与系统调用**；
3. 当私有 TLAB 空间耗尽时，线程才进入慢速路径（Slow Path），加锁从全局 `kRegionInToSpace` 列表中申请一个新的 Region 或新的 TLAB 块。

34.3 并发拷贝 (Concurrent Copying) 算法全景与三色标记
------------------------------------------------------------------------

三色标记模型在移动并发拷贝中的演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统的垃圾回收采用图论遍历，将对象图划分为三色集合：
- **白色 (White)**：尚未被访问的对象。在标记阶段结束时，白色对象即为不可达的垃圾；
- **灰色 (Gray)**：已经被 GC 访问并确认存活，但其引用的子字段对象尚未完全遍历的对象；
- **黑色 (Black)**：已经被 GC 访问并确认存活，且其所有字段引用均已压入遍历队列或完成扫描的对象。

在并发标记与拷贝（Concurrent Copying）模式下，三色标记不仅标记存活状态，还直接驱动对象的**物理内存迁移**：当一个对象由白色变为灰色时，其物理实体即刻被**拷贝到 To-Space**。

CC-GC 执行时序四阶段闭环
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

CC-GC 的单次完整垃圾收集历经四个紧密咬合的阶段：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       ART CC-GC 核心执行阶段时序图                       |
   +-------------------------------------------------------------------------+

   [ 阶段 1: 初始标记 (Initial Mark) - 极短 STW (< 0.2ms) ]
   1. 挂起所有托管线程 (Thread Suspend Checkpoint)
   2. 空间角色原子反转: 现有的已分配 Regions 标记为 From-Space
   3. 选定全新的空白 Regions 标记为 To-Space
   4. 枚举根集 (GC Roots: 线程栈寄存器、JNI 引用、静态根)
   5. 将 GC Roots 直接引用的对象拷贝至 To-Space，或压入 Gray 队列
   6. 恢复所有应用线程运行 (Resume All Threads)
         |
         v
   [ 阶段 2: 并发标记与拷贝 (Concurrent Copying) - 应用与 GC 完全并发运行 ]
   1. GC 后台守护线程从 Gray 队列不断取出对象
   2. 遍历其成员引用字段:
      - 若引用指向 From-Space 对象:
        -> 在 To-Space 分配新内存并 memcpy 复制对象
        -> 在旧对象原头部留下转发指针 (Forwarding Pointer)
        -> 将字段指针修正为指向 To-Space 新地址
   3. 【关键并发控制】若应用 UI 线程并发访问尚未被 GC 处理的 From-Space 引用:
      -> 硬件内联读屏障 (Baker Read Barrier) 瞬间拦截
      -> 抢在业务代码使用前完成对象拷贝与指针修正
         |
         v
   [ 阶段 3: 最终标记与处理 (Flip Thread Roots) - 微秒级 STW / 弱引用处理 ]
   1. 再次微暂停，处理未决引用与弱引用/软引用/Cleaner 链表
   2. 确保全系统所有线程栈及寄存器不再包含任何 From-Space 指针
   3. 切换标记位，进入清理态
         |
         v
   [ 阶段 4: 并发清理与空间回收 (Reclaim Phase) - 并发执行，零停顿 ]
   1. 原 From-Space 区域内所有存活对象已全部迁空
   2. 无需逐个遍历死对象，整片 Region 瞬间批量重置为 kRegionFree
   3. 向内核调用 madvise(..., MADV_DONTNEED) 释放物理页框，归还系统物理内存

从空间 (From-Space) 到目标空间 (To-Space) 的对象疏散
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了理解对象疏散的物理细节，观察一个典型对象 `A` 被拷贝前后的内存结构变化：

.. code-block:: text

   拷贝前:
   From-Space 内存区 (即将作废)               To-Space 内存区 (长期存活)
   +----------------------------+             +----------------------------+
   | Object A [LockWord | Class]|             | (空闲空间)                  |
   | field_1: 0x1234            |             |                            |
   +----------------------------+             +----------------------------+

   拷贝后并在原头部写入转发指针:
   From-Space 内存区                          To-Space 内存区
   +----------------------------+             +----------------------------+
   | [Forwarding Pointer: 0x8000]             | Object A' (副本)           |
   | field_1: 0x1234            |             | [LockWord | Class]         |
   +----------------------------+             | field_1: 0x1234            |
                  |                           +----------------------------+
                  +----------------------------------------^ (新地址 0x8000)

在旧对象头部写入的**转发指针（Forwarding Pointer）**是保障并发一致性的关键。一旦某个线程通过 CAS 操作成功写入转发指针，后续任何其他并发线程读取该旧对象时，只要读到转发标记，就会直接获取对应 To-Space 新对象的物理地址，避免了重复拷贝与数据分裂。

34.4 硬件加速的 Baker 读屏障 (Baker Read Barrier) 微架构
------------------------------------------------------------------------

为什么并发拷贝必须依赖读屏障？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在并发标记-清除（CMS）算法中，对象位置保持固定，仅需写屏障（Write Barrier）记录应用线程并发修改的引用字段即可。但在**并发拷贝（Concurrent Copying）**中，对象在内存中的物理地址时刻在发生迁移：
- 如果没有机制进行拦截，应用 UI 线程可能持有一个指向 From-Space 旧对象的过时指针；
- 当 UI 线程修改了该旧对象的字段，而 GC 线程随后却将未更新的数据拷贝到了 To-Space 并最终丢弃旧空间，就会发生致命的**写丢失（Write Loss）与内存脑裂（Split-Brain）**。

因此，并发拷贝必须维护 **To-Space 不变式 (To-Space Invariant)**：
**在任何时刻，应用线程能够读取或操作的对象指针，必须绝对指向 To-Space**。为了在硬件层面捍卫这一不变式，必须对每一次对象引用的加载进行拦截，这就是读屏障。

Baker 风格读屏障的设计智慧：LockWord 复用
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统读屏障（如 Brooks 风格）为每个对象头额外分配一个指针大小的转发空间，这在堆内存达到数千万个小对象时会导致严峻的内存膨胀（额外消耗 10%~20% 内存空间）。

ART 实现了高度紧凑的 **Baker 风格读屏障（Baker-style Read Barrier）**。它没有增加任何额外的对象头开销，而是巧妙利用了 Java 对象原生对象头部的 **`LockWord`（锁字，32 位）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     ART 统一对象头 LockWord 位域拓扑                     |
   +-------------------------------------------------------------------------+
   | Bit 31 ~ 30 : 锁状态标识位 (Lock State: FatLock, ThinLock, HashCode)    |
   | Bit 29      : kReadBarrierState (GC 读屏障状态位: 0=Gray, 1=Non-Gray)   |
   | Bit 28 ~ 0  : 线程 ID、哈希码或监视器锁 Monitor 索引                    |
   +-------------------------------------------------------------------------+

通过在 LockWord 中分配独立的标记位 `kReadBarrierState`：
- 当对象已经处于 To-Space 且不是未扫描的灰色状态时，该位被置为特定标记；
- 读屏障通过测试该位，能够以最快速度判定引用是否安全，无需遍历任何全局哈希表或外部元数据。

ARM64 指令级快速路径 (Fast Path) 与慢速路径 (Slow Path)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在现代 Android 旗舰设备的 64 位 ARMv8-A/ARMv9 处理器上，ART JIT 与 dex2oat 编译器在生成访问对象字段的代码时，会将读屏障编译为极短的内联机器指令流：

.. code-block:: arm64

   // 读取对象字段操作: obj.field (obj 存放在 x0, 字段偏移量 #32)
   // 1. 正常加载字段引用至 x1
   ldr   w1, [x0, #32]

   // ----------------- Baker Read Barrier Fast Path -----------------
   // 2. 加载目标引用对象 (x1) 内部的 LockWord (对象头偏移 0)
   ldr   w2, [x1, #0]
   // 3. 测试 LockWord 中的第 29 位 (kReadBarrierState)
   //    若已经是合法 To-Space/非灰色状态，直接跳转到继续执行，穿透开销仅 1~2 周期
   tbnz  w2, #29, .Lfast_path_done

   // ----------------- Baker Read Barrier Slow Path -----------------
   // 4. 罕见分支: 命中未被搬移的 From-Space 对象，跳转至 C++ 汇编桩函数
   bl    art_read_barrier_slow_path
   .Lfast_path_done:
   // 继续执行业务逻辑...

慢速路径（Slow Path）的处理逻辑极其严密：
1. 保存当前 CPU 寄存器上下文；
2. 检查该对象是否已经包含转发指针：
   - 若已有转发指针，说明已被 GC 线程拷贝完毕，直接返回该新地址；
   - 若尚未拷贝，调用线程自身**就地执行并发拷贝**：在 To-Space 分配内存、拷贝数据、CAS 回填转发指针，并将对象置为 Gray；
3. 将修复后的 To-Space 引用写入调用方寄存器，恢复寄存器上下文并平滑返回。

这种架构设计保证了 **99.9% 以上的对象读取直接命中快速路径（Fast Path）**，平均仅增加 1~2 个 CPU 时钟周期与微量指令缓存（I-Cache）占用，将全系统读屏障的物理性能开销压制在 2%~4% 的极低能耗区间内。

34.5 垃圾回收触发决策体系与内存压力反馈
------------------------------------------------------------------------

GC 触发类型与系统状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

ART 内部定义了完备的垃圾回收触发因果类型（`art/runtime/gc/gc_cause.h`）：

.. list-table:: ART 常见垃圾回收触发类型及其系统级因果链
   :widths: 22 25 53
   :header-rows: 1
   :class: tight-table

   * - GC 触发因果类型
     - 触发物理条件
     - 系统级行为与影响
   * - **`kGcCauseForAlloc`**
     - 线程在 TLAB 或堆上分配对象时，连续无法获取新 Region。
     - **阻塞式被动分配停顿（Alloc Stall）**：当前分配线程被强制休眠等待 GC 释放可用内存，极易引发 UI 丢帧。
   * - **`kGcCauseBackground`**
     - 堆内存占用达到动态调整的软上限阈值（Target Utilization）。
     - **非阻塞主动并发回收**：在后台线程默默启动，完全不影响前台 UI 交互与渲染。
   * - **`kGcCauseExplicit`**
     - 应用程序显式调用 `System.gc()`。
     - 触发全量阻塞式收集；在移动生产环境中属于反模式，会强行打断能效调速与后台睡眠。
   * - **`kGcCauseTrim`**
     - 系统广播低内存警告或应用进入后台。
     - 触发物理页修剪，调用 Linux 内核 `MADV_DONTNEED` 清退未使用的物理页，最大化 ZRAM 压缩效率。

堆目标利用率 (Target Utilization) 与自适应边界推导
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了避免频繁触发 GC，同时防止无节制占用系统物理内存，ART 引入了基于目标利用率的自适应调节算法：
- 堆利用率定义为：$U = \frac{	ext{LiveBytes}}{	ext{HeapSize}}$，系统默认目标利用率通常配置为 $U_{	ext{target}} = 0.75$（75%）；
- 每次垃圾回收完成并完成清理后，收集器统计当前实际存活的字节数 $	ext{LiveBytes}$；
- 动态推导下一次后台 GC 启动的内存触发水位：

.. math::

   	ext{NextGcThreshold} = \min\left( \frac{	ext{LiveBytes}}{U_{	ext{target}}}, 	ext{HeapMaxLimit} \right)

若应用短时间内大量释放对象，$	ext{LiveBytes}$ 骤降，$	ext{NextGcThreshold}$ 随之收紧，降低内存物理驻留（RSS）；若应用内存保持增长，阈值平滑上移，延迟下次 GC 介入时机，保证批处理计算吞吐量。

弱引用、软引用与 Finalizer 异步清理流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

除了常规强引用，ART CC-GC 还负责四类特殊引用对象的生命周期状态机推进：
1. **SoftReference（软引用）**：在系统物理内存充足时不回收；当系统逼近最大堆上限或收到内核低内存通知时，作为第一批牺牲者强制回收；
2. **WeakReference（弱引用）**：一旦在单次 GC 遍历中判定其引用的目标对象无任何强引用路径，立即切断其指针并压入 `ReferenceQueue`；
3. **Cleaner / PhantomReference（虚引用）**：广泛用于 Android 底层 Native 资源（如 `HardwareBuffer`、`Canvas`、`SkBitmap`）的自动生命周期绑定。
4. **Finalizer 机制的隐患**：拥有 `finalize()` 方法的对象在回收时不能被直接释放，必须被转移至系统级 `FinalizerDaemon` 队列等待单独线程执行。若应用主线程或后台任务繁重导致 Finalizer 线程饥饿，积压的废弃对象将霸占物理内存，最终引发 `TimeoutException` 致命崩溃。

------------------------------------------------------------------------
34.6 移动交互丢帧因果诊断：内存抖动与 Allocation Stall
------------------------------------------------------------------------

为什么 STW 压至亚毫秒，应用依然会因 GC 发生严重丢帧？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

许多移动开发者存在认知误区，认为只要 GC 的 STW 时间小于 1ms，垃圾回收就绝不可能导致 16.6ms 交互掉帧。然而，在真实的高负载生产环境中，由垃圾回收引起的掉帧往往来自于另外两条致命的隐蔽路径：**Allocation Stall（分配阻塞）** 与 **CPU 大核算力争用（CPU Contention）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                高频内存抖动引发 UI 掉帧的物理因果链                      |
   +-------------------------------------------------------------------------+

   UI 主线程 / 渲染线程:
   每一帧在 onDraw() 或列表绑定中以 >200MB/s 的极高速率疯狂创建短期临时对象
   (如 String 拼接、大量 Model 转换、Lambda 闭包、临时 Rect)
       |
       v
   TLAB 空间数毫秒内瞬间耗尽!
       |
       v
   RegionSpace 中无空闲 kRegionFree 可用!
       |
       v
   【致命路径 1: Allocation Stall】
   UI 线程调用 AllocObject() 失败，进入内核 Futex 等待，线程被强制挂起!
       |
       +<--------------------+ (等待后台 GC 线程腾出内存)
       |                     |
       v                     |
   【致命路径 2: CPU Contention】
   后台 GC 守护线程并发启动，为尽快完成疏散，拉满 CPU 算力，抢占大核集群!
       |
       v
   RenderThread 无法获取足够的 CPU 时钟周期完成当前帧的 GPU 命令录制
       |
       v
   VSYNC 信号到达 -> BufferQueue 发生 Underrun -> 用户肉眼可见画面跳帧 (Jank)!

Perfetto 系统级 Trace 证据链定位与分析
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

使用 Perfetto 抓取系统级 Trace，定位 GC 性能问题应锁定以下四类关键证据点：

.. list-table:: 垃圾回收性能诊断关键 Trace 证据点与判定标准
   :widths: 22 28 50
   :header-rows: 1
   :class: tight-table

   * - Trace 事件名称
     - 出现的线程 / 上下文
     - 物理微架构指示意义与性能红线
   * - `art::gc::ConcurrentCopying`
     - `HeapTaskDaemon` (后台 GC 线程)
     - 表示 CC-GC 正在并发执行。若其持续时间超过 50ms 且跨越多个 VSYNC 周期，说明存活对象量大或堆压力极高。
   * - `AllocStall`
     - **`main` / `RenderThread` (UI/渲染线程)**
     - **严重丢帧第一元凶**！表示 UI 关键线程因堆空间耗尽被迫挂起等待。该切片耗时超过 5ms 必然直接导致当前帧丢弃。
   * - `FlipOtherThreads`
     - 主控 GC 线程 (STW Checkpoint)
     - 记录初始标记或最终切换阶段暂停业务线程的实际 STW 耗时，健康基准应维持在 100μs ~ 300μs 以内。
   * - `Heap Allocation Rate`
     - 全进程内存分配统计
     - 单位时间内的对象分配速率。若列表滑动期间分配速率飙升至 50MB/s ~ 100MB/s 以上，判定为严重的内存抖动（Memory Churn）。

工业级内存抖动治理模式
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

消灭 Allocation Stall 与 GC 争用的核心不在于调优虚拟机参数，而在于从代码层面切断高频对象分配链：
1. **消除高频绘图路径中的内存分配**：严禁在 `View.onDraw()`、Compose 的高频重组代码块或列表 `onBindViewHolder` 中创建 `Paint`、`Path`、`String`、格式化工具或临时数据包装类；
2. **对象池（Object Pool）与缓冲复用**：针对高频创建且生命周期极其短暂的对象（如事件分发中的 `MotionEvent`、几何计算中的 `Matrix`），使用线程安全的池化复用机制；
3. **结构体扁平化与基本类型特化**：使用原始基本类型数组（如 `int[]`、`long[]`）替代强包装的集合对象（如 `ArrayList<Integer>`），彻底消灭包装箱（Autoboxing）带来的数十倍小对象内存分配；
4. **Bitmap 物理显存复用**：配置 `BitmapFactory.Options.inBitmap` 复用已分配的物理页框，避免频繁触发 Large Object Space 的内核级页表分配与清退。

本章系统解构了 Android 运行时垃圾回收体系与并发拷贝（CC-GC）的底层微架构：
- 剖析了移动操作系统在物理内存、电池能效与交互延迟严苛约束下的 GC 演进历程，指出了传统 STW 机制对 60Hz/120Hz 渲染流水线的破坏力；

- 详细推导了并发拷贝算法的四阶段时序闭环、三色标记与对象物理疏散过程中的转发指针机制；
- 系统揭密了基于对象头 `LockWord` 状态位复用的 Baker 风格读屏障，剖析了 ARM64 汇编指令级快速路径拦截与慢速路径安全回退的实现细节；
- 建立了基于目标利用率的自适应堆调整决策模型与多级引用清理流水线；
- 深入剖析了 Allocation Stall 与 CPU 争用引发交互丢帧的底层微架构成因，建立了基于 Perfetto Trace 的工业级证据链排查模型。

在掌握了单个应用进程内部托管运行时的执行引擎与内存回收机制之后，我们必须将视野转向移动操作系统的另一个根本性基础设施：**这些应用进程究竟从何而来？**

在桌面操作系统中，创建新进程通常通过直接 `fork()` 紧接着 `execve()` 载入全新可执行文件，并从零开始重新初始化运行时与类库，这种冷启动方式在移动设备上会耗费数秒甚至更长时间。为了让成千上万的移动应用以百毫秒级的极致速度瞬间启动，Android 构筑了一套基于**原型预加载与写时复制（Copy-On-Write）**的独创性进程孵化体系。

在下一章 **Chapter 35: Zygote 预加载与写时复制 (COW) 进程孵化加速** 中，我们将深入 Android 进程起源中枢，解构 Zygote 进程的孵化拓扑、核心类库与资源的预加载机制、Linux 内核写时复制（COW）物理页表共享，以及 App 进程启动全链路的极速蜕变。

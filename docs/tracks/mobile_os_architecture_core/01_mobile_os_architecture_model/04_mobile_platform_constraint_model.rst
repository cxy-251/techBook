Chapter 4: 移动平台约束模型：电量预算、热包络与后台唤醒控制
========================================================================

.. note:: 前置背景与认知承接
   前三章系统解构了移动操作系统的六层垂直架构链条与系统服务控制面的中介代理机制。然而，所有这些软件抽象的运行，均被严格框定在移动设备极其严苛的物理运行环境之中。本章将深入移动操作系统的物理约束模型——系统解构静态待机与动态运行下的电量预算分配、芯片级热包络（Thermal Envelope）与 DVFS 阶梯式温控状态机、基于独立 Sensor Hub 的低功耗常驻感知，以及对齐批处理（JobScheduler/BGTask）与 Doze 深度休眠的后台唤醒压制体系。

4.1 电量预算模型 (Battery Budget) 与能耗物理量化
------------------------------------------------------------------------

智能手机所搭载的锂离子/锂聚合物电池，其工作电压区间通常为 $3.7	ext{V} \sim 4.45	ext{V}$，总能量容量在 $11	ext{Wh} \sim 19	ext{Wh}$（对应 $3000	ext{mAh} \sim 5000	ext{mAh}$）。操作系统的功耗管理目标，是确保整机在全天候 24 小时混合使用周期内始终维持受控的电量消耗曲线。

.. list-table:: 智能手机各核心硬件模块物理电流与功耗基准矩阵
   :widths: 18 20 22 40
   :header-rows: 1
   :class: tight-table

   * - 硬件子系统
     - 典型工作电流 (3.8V 基准)
     - 瞬时功耗 (mW)
     - 系统级功耗治理策略
   * - 整机深度休眠 (Deep Sleep)
     - 3 ~ 10 mA
     - 11 ~ 38 mW
     - 切断 CPU 大核与外设供电，仅保留 PMIC、RTC 与基带监听
   * - 独立低功耗 Sensor Hub
     - 0.5 ~ 2 mA
     - 2 ~ 8 mW
     - 主 CPU 休眠，协处理器以微安级电流常驻采样加速度计
   * - OLED 显示面板 (50% APL)
     - 150 ~ 400 mA
     - 570 ~ 1520 mW
     - 动态刷新率调节 (LTPO 1Hz~120Hz)、深色模式降低发光像素
   * - CPU 大能效核群 (Heavy Load)
     - 800 ~ 2000 mA
     - 3000 ~ 7600 mW
     - EAS 调度限制、突发任务完成后立刻回退低功耗 P-State
   * - 5G 射频与基带 (Full Tx/Rx)
     - 600 ~ 1200 mA
     - 2280 ~ 4560 mW
     - 智能 5G 切换 (Smart 5G)、网络请求批量合并唤醒
   * - 4K/60fps 录像 ISP + CMOS
     - 900 ~ 1600 mA
     - 3420 ~ 6080 mW
     - 内存零拷贝 DMA 传输、硬件编码器直接旁路

4.2 动态功耗与静态漏电：能效感知调度 (EAS) 的物理根基
------------------------------------------------------------------------

CMOS 数字集成电路的物理总功耗由动态翻转功耗（Dynamic Power）与静态漏电功耗（Static Leakage Power）共同构成：

.. math::

   P_{	ext{total}} = P_{	ext{dynamic}} + P_{	ext{static}} = \alpha \cdot C \cdot V^2 \cdot f + I_{	ext{leak}} \cdot V

- $\alpha$：晶体管时钟翻转率；$C$：负载电容；$V$：供电电压；$f$：时钟工作频率；$I_{	ext{leak}}$：半导体静态漏电流。

由于芯片工作电压 $V$ 随着工作频率 $f$ 近似呈线性增长（$V \propto f$），因此**动态功耗与工作频率呈现立方的超线性增长关系**（$P_{	ext{dynamic}} \propto f^3$）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                CPU 核心工作频率与功耗非线性增长曲线                     |
   +-------------------------------------------------------------------------+
   功耗 P (mW)
       ^
  6000 |                                                 /================= [超大核 3.2GHz: 极高功耗]
       |                                                /
  3000 |                                       +-------+ (大核 2.4GHz: 平衡区)
       |                                      /
   500 |             +-----------------------+ (小核 1.5GHz: 高能效甜点区)
       |            /
       +-----------+------------------------------------------------------>
       0          1.0                       2.0                 3.0         频率 f (GHz)

大小核异构拓扑 (big.LITTLE / DynamIQ) 与 EAS
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **物理事实**：在一个高能效小核（如 Cortex-A520）上以 1.2 GHz 运行后台任务，其消耗的电量仅为在超大核（如 Cortex-X4）上运行相同任务的 **10% ~ 20%**。
- **能效感知调度 (Energy-Aware Scheduling - EAS)**：Linux 内核在调度线程时，结合预置的芯片能耗模型表（Energy Model），计算将该任务分别放置在小核、大核或超大核上的整机能耗增量 $\Delta E$。在满足前台交互延迟的前提下，优先挑选能耗增量最小的核心。

4.3 热包络 (Thermal Envelope) 与芯片级温控降级状态机
------------------------------------------------------------------------

手机受限于手持体积与无风扇被动散热（Passive Cooling）条件，其持续稳态散热能力（TDP）仅为 **3.5W ~ 5.5W**。当全芯片瞬时功耗持续超过 8W 时，热量将在机身内部迅速累积。

为了防止机身表面温度超过 $45^\circ	ext{C}$ 灼伤用户，操作系统内的温控守护进程（Thermal Daemon）持续监听分布在 CPU 集群、GPU、基带射频与电池附近的物理热敏电阻（NTC Thermistors），并执行阶梯式降级状态机：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     移动操作系统 Thermal Daemon 温控状态机              |
   +-------------------------------------------------------------------------+

   [ Level 0: 正常温区 (< 38°C) ]
        * 系统无任何约束，允许 CPU/GPU 触发短时 Turbo 峰值主频
        |
        v (结温升高)
   [ Level 1: 预警温区 (38°C ~ 41°C) ]
        * DVFS 封顶：限制 CPU 超大核最高频点，关闭 GPU 峰值频率
        |
        v
   [ Level 2: 控温温区 (41°C ~ 43°C) ]
        * 屏幕显示抑制：全局峰值亮度压低 25%，强制将 120Hz 高刷切回 60Hz
        * 降低前台游戏渲染分辨率 (动态分辨率缩放 DRS)
        |
        v
   [ Level 3: 严苛保护温区 (43°C ~ 45°C) ]
        * 外设能力剥离：禁用后置闪光灯，强行中断 4K 60fps 录像
        * 电池充电限流：快充功率由 100W 强制降级至 10W~15W 以减缓发热
        |
        v
   [ Level 4: 紧急临界温区 (> 45°C) ]
        * 强杀高耗电后台应用，弹出全屏系统高温告警，必要时内核触发关机

4.4 后台唤醒控制与批处理对齐机制 (WakeLocks, Doze & BGTask)
------------------------------------------------------------------------

在移动操作系统中，最致命的电量消耗并非来自前台正常使用，而是来自**后台应用的频繁无序唤醒（Wakeup Storm）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 无序唤醒风暴 vs 对齐批处理深度休眠对比                  |
   +-------------------------------------------------------------------------+

   [ 传统无序唤醒模式: CPU 频繁被拉出休眠，待机功耗极高 ]
   App A 心跳:  --[Wake]-----------------[Wake]-----------------[Wake]----
   App B 同步:  -------[Wake]-----------------[Wake]----------------------
   App C 上报:  -------------[Wake]-----------------[Wake]----------------
   CPU 供电轨:  |=== ON ===|== ON ==|=== ON ===|== ON ==|=== ON ===|== ON ==| (静态漏电 100mA+)

   [ 现代系统级 Doze & 对齐批处理模式: 绝大部分时间处于深度休眠 ]
   全部后台任务: ----------------------[ 集中批量执行窗口 (Maintenance Window) ]
   CPU 供电轨:  |--- 深度休眠 (<10mA) -------------------|=== 唤醒 10秒 ===|

Doze 深度休眠两阶段机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **浅度休眠 (Light Doze)**：用户灭屏且未连接电源时即时触发。系统阻断所有应用的常规网络访问，推迟后台同步作业，但允许前台音乐播放与闹钟定时器。
2. **深度休眠 (Deep Doze)**：设备处于静止状态（由低功耗运动传感器判定）数十分钟后进入。系统完全切断网络连接、忽略常规 WakeLock 唤醒锁，并停止所有 AlarmManager 定时器，仅在周期性的极窄维护窗口（Maintenance Window）中统一释放一次。

4.5 常驻低功耗传感器与独立 Sensor Hub 架构
------------------------------------------------------------------------

为了实现 24 小时连续计步、摔倒检测与抬腕亮屏功能，移动平台在物理硬件层面实现了计算解耦：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  主 SoC 深度休眠与 Sensor Hub 协处理器拓扑              |
   +-------------------------------------------------------------------------+

   [ 物理传感器外设: 加速度计 / 陀螺仪 / 距离感应器 ]
        |
        | I2C / SPI 低速串行总线
        v
   [ 独立微控制器: Sensor Hub (如 ARM Cortex-M4 / 微安级功耗) ]
        |  * 运行精简实时操作系统 (RTOS)，内部开辟硬件 FIFO 环形缓冲区
        |  * 持续以 50Hz 采样并执行硬件级步数识别 / 抬腕手势算法
        |
        +---> [ 未识别到触发事件 ] -> 仅将数据累加至本地寄存器，主 CPU 继续休眠
        |
        +---> [ 识别到抬腕亮屏或跌倒手势 ]
                 |
                 | 触发专用硬件中断引脚 (Wakeup IRQ Line)
                 v
   [ 唤醒主 Application Processor (主 CPU) ] -> 恢复 SurfaceFlinger 点亮屏幕

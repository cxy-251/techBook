Chapter 6: 双平台架构映射：Android 基于 Linux 与 Apple 基于 Darwin/XNU

6.1 双平台宏观分层架构映射矩阵
------------------------------------------------------------------------

尽管 Android 与 iOS 的上层开发语言与 API 风格迥异，但两者在垂直架构分层上呈现出高度一致的对称映射关系：

.. list-table:: Android (AOSP) 与 Apple (iOS/Darwin) 六层架构技术映射全景
   :widths: 15 20 32 33
   :header-rows: 1
   :class: tight-table

   * - 垂直分层
     - 系统层级职责
     - Android (基于 Linux 生态)
     - Apple (基于 Darwin/XNU 生态)
   * - 6. 应用层
     - 终端用户界面与交互
     - 独立 APK / AAB 沙箱进程 (Java/Kotlin/Flutter)
     - 独立 IPA 沙箱容器进程 (Swift/Objective-C)
   * - 5. 框架层
     - 系统能力 SDK 与 API
     - Android Framework (Java SDK: Activity, Location)
     - Cocoa Touch (UIKit, SwiftUI, CoreLocation)
   * - 4. 服务层
     - 全局状态持有与多租户仲裁
     - `system_server` (AMS, WMS) + Native Daemons
     - `launchd` 服务树 + System Daemons (`SpringBoard`)
   * - 3. 驱动/HAL
     - 屏蔽硬件私有协议
     - Project Treble AIDL/HIDL HAL + Gralloc
     - IOKit C++ 类库 + DriverKit 用户态扩展 (DEXT)
   * - 2. 内核层
     - 资源虚拟化与特权调度
     - **Linux 宏内核** (EAS 调度, Ashmem, Binder)
     - **Darwin/XNU 混合微内核** (Mach, BSD, IOKit)
   * - 1. 物理硬件
     - 硅片与异构计算单元
     - 开放多厂商 SoC (Snapdragon, Dimensity, Tensor)
     - 自研垂直整合 SoC (Apple A-Series / M-Series)

6.2 内核架构与调度哲学：Linux 宏内核 vs XNU 混合微内核
------------------------------------------------------------------------

内核架构的选择深刻影响了操作系统的实时性、内存占用与跨芯片移植成本：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                Android Linux 宏内核 vs Apple XNU 混合微内核             |
   +-------------------------------------------------------------------------+

   [ Android: Linux 宏内核体系 ]
   +-------------------------------------------------------------------------+
   |  VFS 虚拟文件系统 | 网络协议栈 | EAS 能效感知调度 | Binder 驱动 | 驱动程序  |
   |                                                                         |
   |              统一运行在最高特权空间 (Kernel Mode / EL1)                 |
   +-------------------------------------------------------------------------+

   [ Apple: Darwin/XNU 混合微内核体系 ]
   +-------------------------------------------------------------------------+
   | BSD 层: POSIX API, 进程模型, 用户凭证, kqueue, BSD Sockets             |
   +-------------------------------------------------------------------------+
   | Mach 微内核层: 线程抽象, Mach Message 消息总线, 虚拟内存 (vm_map), IPC |
   +-------------------------------------------------------------------------+
   | IOKit / DriverKit: 面向对象硬件驱动框架                                 |
   +-------------------------------------------------------------------------+

Linux EAS 调度 vs Apple QoS 服务质量模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Android Linux (EAS 能效调度)**：基于能耗模型表（Energy Model）与 WALT 负载追踪，追求在满足帧率预算下的整机功耗最小化，适合适配不同制程的大中小异构核心。
- **Apple XNU (QoS 服务质量等级)**：定义了严格的线程级 QoS 等级（`UserInteractive`、`UserInitiated`、`Utility`、`Background`）。当主线程（UI 交互）发起任务时，内核强制执行**优先级继承（Priority Inversion Avoidance）**，确保交互响应的绝对优先。

6.3 IPC 通信中枢：Android Binder vs Apple Mach Port / XPC
------------------------------------------------------------------------

跨进程通信机制构成了移动操作系统的“服务骨干网络”：

.. list-table:: Android Binder 与 Apple Mach Port / XPC 通信微架构对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 架构维度
     - Android Binder IPC
     - Apple Mach Port / XPC
   * - 通信端点抽象
     - 基于 Binder 驱动节点 (`/dev/binder`) 与句柄引用
     - 基于 Mach Port 端口权标 (`mach_port_t` Send/Receive Right)
   * - 内存搬运机制
     - **一次拷贝 (One-Copy)**：通过 `mmap` 将数据从发送方用户态直接拷入接收方内核映射区
     - **消息传递 (Message Passing)**：小消息内联拷贝；大消息通过虚拟内存重映射 (OOB Memory Descriptor)
   * - 线程池与并发
     - 驱动层为每个服务进程动态维护 16 个以上的 Binder 工作线程池
     - 基于 Grand Central Dispatch (GCD) 异步队列实现事件驱动的无锁并发
   * - 调用语义
     - 以同步阻塞 RPC 为主，支持 AIDL 接口强类型约束
     - 以异步消息投递与闭包回调为主，支持 XPC Dictionary 动态类型

6.4 运行时与内存模型：ART 虚拟机 vs dyld + ARC 静态原生
------------------------------------------------------------------------

应用代码的编译与执行模式，是两大阵营差异最显著的技术分水岭：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                Android ART 运行时 vs Apple 原生编译执行流水线           |
   +-------------------------------------------------------------------------+

   [ Android: ART 动态虚拟机管线 ]
   Java/Kotlin 源码 ---> 编译为 DEX 字节码 ---> Zygote 孵化进程
                              |
                              +---> 首次运行: 解释器 (Interpreter) 极速启动
                              +---> 热点代码: JIT 动态即时编译为机器码
                              +---> 闲时充电: AOT 后台 Profile 编译为机器码 (.oat)
                              +---> 运行时: 并发标记清除/移动 GC 回收内存

   [ Apple: 静态编译 + dyld 链接管线 ]
   Swift/Obj-C 源码 ---> LLVM 前端编译 ---> 静态链接为 ARM64 Mach-O 本地机器码
                              |
                              +---> 启动: dyld 共享缓存 (dyld shared cache) 零重定位
                              +---> 内存管理: 编译器注入 retain/release 自动引用计数 (ARC)
                              +---> 运行时: 零 GC 停顿，内存峰值受限且确定性极高

- **Android 的哲学**：跨硬件设备兼容性优先。通过 DEX 虚拟机抹平不同 SoC 芯片的指令集差异，借助 JIT/AOT 混合编译平衡安装速度与运行性能。
- **Apple 的哲学**：极致单机运行效率与低内存确定性优先。直接面向自研 ARM 芯片静态编译，消除虚拟机层与运行时 GC 停顿，使得 4GB~6GB 内存设备能够获得媲美 Android 12GB~16GB 设备的流畅度。

6.5 安全防护体系：Android UID + SELinux vs Apple Code Signing + Sandbox
------------------------------------------------------------------------

.. list-table:: 双平台安全防护与权限体系全景对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 安全防线维度
     - Android 安全栈 (AOSP)
     - Apple 安全栈 (iOS/Darwin)
   * - 进程主体身份
     - Linux 用户 ID (UID，如 `u0_a185`)
     - Bundle Identifier + Team ID + Code Directory Hash (cdhash)
   * - 强制访问控制 (MAC)
     - **SELinux**：针对 App、HAL、Native 服务配置细粒度 Type Enforcement 策略
     - **Seatbelt / Apple Sandbox**：基于 SBPL 策略语言的内核扩展隔离
   * - 代码完整性保护
     - 安装期 APK 验签；运行时允许动态加载 DEX（受到限制）
     - **严格强制代码签名**：内核强制实施 $W\oplus X$（不可同时可写可执行），禁止执行未签名代码
   * - 硬件安全隔离区
     - ARM TrustZone / Keymaster / KeyMint / StrongBox
     - 独立硬件协处理器 **Secure Enclave Processor (SEP)**

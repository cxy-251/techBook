========================================================================
Chapter 3: 硬件能力中介化与系统控制面
========================================================================

.. note:: 前置背景与认知承接
   第二章解构了移动操作系统自底向上的六层垂直调用链路。在这一链条中，系统服务中介层构成了整个操作系统的控制平面（Control Plane）。本章将深入解构系统服务如何作为物理硬件的唯一代理，仲裁多应用对独占与共享硬件的竞争冲突，在 IPC 边界执行不可绕过的权威安全校验，并通过进程看门狗（Watchdog）与状态自愈机制控制故障的物理爆炸半径。

------------------------------------------------------------------------
3.1 硬件能力的物理属性分类：独占型 vs 共享型 vs 虚拟化资源
------------------------------------------------------------------------

在移动终端有限的物理空间内，SoC 与外设硬件在多应用并发访问时的物理行为存在根本差异。系统服务控制面的首要任务，是依据硬件的物理属性实施分级资源抽象与调度：

.. list-table:: 移动设备硬件资源分类与多租户仲裁模型
   :widths: 18 22 30 30
   :header-rows: 1
   :class: tight-table

   * - 资源分类
     - 典型物理外设
     - 多租户竞争冲突形态
     - 系统控制面仲裁策略
   * - 独占型物理硬件 (Exclusive Hardware)
     - 相机 CMOS 传感器、基带蜂窝语音通话、NFC 控制器
     - 物理上仅支持单一数据流配置，多应用并发打开导致硬件死锁
     - 基于前台焦点与进程优先级的**抢占式驱逐** (Preemptive Eviction)
   * - 分时/空间共享硬件 (Multiplexed Hardware)
     - 音频 DAC/DSP、GNSS 芯片、IMU 惯性传感器 (加速度计/陀螺仪)
     - 多个应用同时请求不同采样率、不同音量与输出流
     - **聚合与降采样** (Aggregation & Downsampling) 及音频焦点状态机
   * - 全虚拟化资源 (Virtual Resources)
     - GPU 计算核心、物理内存页框、网络套接字 (Sockets)
     - 显存空间争用、带宽饱和、CPU 时间片竞争
     - 硬件上下文切换 (Context Switch)、页表隔离与 QoS 权重分配

3.2 独占设备仲裁机制：以 CameraService 抢占与状态机为例
------------------------------------------------------------------------

相机子系统是独占型物理硬件的典型代表。CMOS 传感器输出的 MIPI CSI-2 物理差分信号线，直接硬连线至 SoC 内部的专用图像信号处理器（ISP）。当多个应用程序（如前台拍照应用与后台视频通话应用）并发尝试打开相机时，系统服务必须执行严格的仲裁流水线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  CameraService 独占式客户端抢占状态机                   |
   +-------------------------------------------------------------------------+

   [ 应用 A: 后台扫码服务 (持有 Camera 0 句柄, UID: 10120) ]
        |
        | 正常流式拉取预览帧数据
        v
   [ 硬件状态: Camera 0 ISP 流水线被应用 A 独占锁定 ]
        ^
        | (用户在桌面点击启动应用 B: 前台系统相机, UID: 10005)
        |
   [ 应用 B 调用 connectDevice("0", clientCallback) ]
        |
        v
   [ CameraService 仲裁控制器 (Authoritative Arbiter) ]
        |
        | 1. 查询应用 A 与应用 B 的前台可见性与 oom_score_adj 评分
        | 2. 判定: 应用 B 为前台 Top Activity，优先级高于应用 A
        | 3. 触发抢占逻辑 (Eviction):
        |    -> 向应用 A 发送 ICameraDeviceCallbacks.onDeviceDisconnected()
        |    -> 强行关闭应用 A 在 HAL 层的 Camera3Device 物理会话
        v
   [ HAL 硬件管道释放完毕 (Stream Drain) ]
        |
        | 4. 将物理传感器控制权重新配置并绑定至应用 B
        v
   [ 应用 B 成功获取硬件控制权并启动 ISP 流水线 ]

抢占机制确保了前台与用户直接交互的应用永远具备最高硬件使用权，防止后台恶意应用或异常挂起进程永久占用物理硬件。

3.3 共享设备的多租户聚合与焦点管理
------------------------------------------------------------------------

对于支持多路并发的物理硬件，系统服务通过数学聚合与软件状态机，向应用层暴露虚拟化的独立接口。

音频焦点状态机 (Audio Focus Protocol)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动设备通常只有一个物理扬声器或一套蓝牙音频通路。当音乐播放器正在播放时，若导航应用发起语音播报，或电话呼入，系统并非简单粗暴地断开连接，而是通过音频焦点（Audio Focus）状态机进行协调：

- **完全焦点获取 (`AUDIOFOCUS_GAIN`)**：主播放器独占主声道播放；
- **瞬时焦点失去 (`AUDIOFOCUS_LOSS_TRANSIENT`)**：电话呼入时，暂停音乐播放，通话结束后自动恢复；
- **瞬时降音量 (`AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK`)**：导航播报时，底层音频混音器（Audio Mixer）自动将背景音乐音量压低 80%（Ducking），播报完毕后无缝还原。

3.4 权威权限执行点 (Authoritative Security Enforcement Point)
------------------------------------------------------------------------

在移动操作系统安全模型中，**客户端应用进程被视为完全不可信环境**。应用可以被逆向、篡改或通过动态注入修改内存。因此，所有安全判定必须在系统服务内部闭环：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 Binder 内核级凭证提取与权威权限执行点                   |
   +-------------------------------------------------------------------------+

   [ 不可信应用进程 (App Process) ]
        |  * (本地伪造身份或绕过 Java 检查毫无意义)
        |  * 发起跨进程 IPC 调用
        v
   [ Linux Binder 内核驱动 ]
        |  * 驱动层依据发送方套接字/Task 实体，在数据包头上盖上内核公章:
        |    -> sender_euid = 10185 (Calling UID)
        |    -> sender_pid  = 3412  (Calling PID)
        v
   [ 系统服务特权进程 (system_server / LocationManagerService) ]
        |
        | 1. 调用 Binder.getCallingUid() 提取不可篡改的 UID
        | 2. 查询 AppOps 运行时动态权限数据库 (PermissionController)
        | 3. 校验调用方 UID 是否被授予 ACCESS_FINE_LOCATION
        |
        +---> [ 权限已授予 ] -> 正常下发硬件并返回坐标
        |
        +---> [ 权限已撤销 / 单次授权超时 ] -> 立即抛出 SecurityException 或静默阻断

3.5 服务隔离、看门狗监控与故障爆炸半径控制
------------------------------------------------------------------------

系统服务自身运行在用户态，其内部可能包含成千上万行复杂的业务逻辑与第三方厂商扩展代码。为了防止单个硬件驱动崩溃拖垮整个操作系统，现代移动系统实施了细粒度的进程隔离与看门狗监控：

1. **进程解耦与服务拆分 (Treble Architecture)**：
   - 传统的单体架构将所有服务打包进单一进程，一个音视频驱动崩溃将导致整个系统死亡。
   - 现代架构将核心服务拆分为相互独立的独立守护进程：`cameraserver`、`audioserver`、`surfaceflinger`、`system_server`。
2. **死亡通知与连接自愈 (DeathRecipient)**：
   - 当底层 `cameraserver` 因硬件异常发生段错误退出时，`system_server` 与应用层通过注册的 `linkToDeath` 立即收到异步死亡通知。
   - 系统管理进程（`init` / `launchd`）在 100ms 内重启该守护进程，应用层捕获错误后可重置相机管道，无需重启整机。
3. **系统级软件看门狗 (System Watchdog)**：
   - `system_server` 内部运行一个高优先级的 Watchdog 监控线程，定期向 ActivityManager、PowerManager 等核心服务的消息队列发送心跳乒乓包（Ping-Pong）。
   - 若某服务因死锁或 IPC 阻塞在 30 秒内未响应心跳，Watchdog 强行收集当前所有线程的调用栈（Traces），并向内核发送 `SIGABRT` 信号触发软重启自愈。

========================================================================
Chapter 1: 移动与桌面系统共同基础与移动特定约束模型
========================================================================

.. note:: 前置背景与认知锚点
   本章作为全书开篇，确立移动操作系统的系统级世界观。通过解构移动 OS 与传统桌面 OS 的共性内核抽象底座与本质约束差异，剖析受控资源治理模型（Controlled Resource Governance）、前后台进程状态机与全系统五大物理约束矩阵，为后续深入硬件拓扑、内核调度、系统服务与安全沙箱建立坚实的架构认知基石。

------------------------------------------------------------------------
1.1 操作系统共同基础：进程、内存、文件、网络、设备与安全
------------------------------------------------------------------------

从计算机体系结构的经典分层模型审视，现代移动操作系统（如基于 Linux 内核的 Android 与基于 Darwin/XNU 内核的 iOS）与传统桌面/服务器操作系统（如 Linux 发行版、Windows、macOS）共享完全一致的基础内核抽象原语。操作系统的根本使命始终是管理物理硬件资源，并向用户空间程序提供一致、安全、受控的虚拟化接口。

.. list-table:: 移动与桌面操作系统共享的基础系统抽象原语
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 核心抽象原语
     - 内核物理管理实体
     - 向用户空间暴露的标准接口
   * - 进程与执行线程 (Process / Thread)
     - CPU 时钟时序分配、寄存器状态上下文、内核调度队列 (`task_struct` / `task_t`)
     - POSIX 系统调用 (`fork`, `execve`, `pthread_create`)、进程描述符 (PID)
   * - 虚拟地址空间 (Virtual Memory)
     - MMU 多级页表、物理页框分配器 (`Page Allocator`)、缺页异常处理 (`Page Fault`)
     - 虚拟内存映射 (`mmap`, `brk`, `munmap`)、用户/内核空间隔离
   * - 虚拟文件系统 (VFS)
     - 磁盘块设备驱动、Inode 节点树、目录项缓存 (`Dentry Cache`)、日志文件系统
     - 文件描述符 (`open`, `read`, `write`, `close`)、路径命名空间
   * - 网络通信栈 (Network Stack)
     - 网卡 DMA 环形缓冲区、网络协议栈状态机 (`TCP/IP`, `UDP`, `Routing Table`)
     - 套接字句柄 (`socket`, `bind`, `connect`, `epoll` / `kqueue`)
   * - 设备抽象与驱动 (Device Drivers)
     - 中断处理底半部、总线控制器 (`PCIe`, `USB`, `I2C`, `SPI`)、设备树 (`Device Tree`)
     - 设备文件节点 (`/dev/*`)、IO 控制接口 (`ioctl`)、Mach Messages
   * - 安全凭证与隔离 (Security Credentials)
     - 用户标识 (`UID/GID`)、安全标签 (`SELinux Context` / `Sandbox Profile`)
     - 访问控制矩阵 (`DAC / MAC`)、系统调用截获点 (`ptrace`, `seccomp`)

这一底层抽象的同构性解释了为何 Android 能够直接复用 Linux 内核的内存管理、进程调度与网络协议栈，而 iOS 能够直接沿用 macOS 核心的 XNU（Mach 微内核与 BSD 层的混合架构）。无论是处理高并发网络请求的服务器进程，还是响应触摸滑动的移动应用进程，其在内核层面的物理执行本质均由 CPU 时间片分配、页表映射与系统调用陷入所驱动。

1.2 桌面系统的开放资源模型与多任务范式
------------------------------------------------------------------------

传统桌面操作系统（Desktop OS）的架构设计孕育于“工作站与个人计算”时代，其核心设计假设建立在一组高度宽松的物理与使用边界之上：

1. **持续稳定的能源供给**：设备通常直接连接交流电源电网，或配备大容量电池（50~100 Wh）。内核调度器优先追求吞吐量与单任务响应速度，无需以微安（$\mu A$）为单位精细计量瞬时能耗。
2. **充裕的主动散热环境**：配备大尺寸散热鳍片与主动散热风扇，热设计功耗（TDP）普遍在 15W 至 250W 以上，系统极少因为轻度负载而触发激进的硬件降频（Thermal Throttling）。
3. **开放式资源所有权**：
   - 应用进程在获取普通用户权限后，可自由遍历并读写绝大部分用户主目录文件。
   - 允许任意第三方应用创建持久驻留的后台守护进程（Background Daemons），持续消耗 CPU 与网络带宽。
   - 支持多任务多窗口自由重叠并发运行，所有前后台进程拥有对等的硬件访问权利。
4. **去中心化的软件分发与信任体系**：用户拥有系统最高控制权（Administrator / root），可自由执行未经验证的二进制可执行文件，内核默认信任用户直接拉起的应用程序。

1.3 移动系统的受控资源治理模型 (Controlled Resource Governance)
------------------------------------------------------------------------

将计算设备缩减至随身携带的手机形态后，桌面操作系统的开放模型遭遇了不可逾越的物理现实阻碍。智能手机面临着极致严苛的物理与使用约束：

- **有限的电池电量**：整机电池容量仅为 10~20 Wh（3000~5000 mAh），必须支撑全天候 16~24 小时的混合使用。
- **被动散热极限**：手机受限于体积、重量与手持舒适度，无法内置主动风扇，芯片瞬时功耗若持续超过 4W~7W，机身表面温度将迅速突破安全阈值（45°C）。
- **高隐私敏感度**：设备集成了高精度 GPS、双向麦克风、超高清摄像头、生物识别传感器（指纹/人脸）以及全量通讯录与相册，物理上全天候随身携带。
- **不可预测的网络波动**：设备频繁在 5G 强网、弱网、基站切换、Wi-Fi 漫游与完全无网状态之间跳转。

为了在上述物理极限下保障系统的全天候可用性，移动操作系统确立了**受控资源治理模型（Controlled Resource Governance）**。其核心哲学是：**系统全面收回应用程序对底层硬件的直接支配权，所有硬件能力必须经过系统服务中介化代理、运行时动态授权与严格的生命周期配额管理。**

.. list-table:: 桌面操作系统与移动操作系统设计哲学对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 系统治理维度
     - 传统桌面系统 (开放自治模型)
     - 现代移动系统 (受控资源治理模型)
   * - 资源访问范式
     - 应用直接调用系统调用或操作设备节点
     - 应用通过系统服务（System Service）代理访问硬件
   * - 后台执行策略
     - 允许无限制后台常驻与长连接轮询
     - 严格冻结挂起（Suspend），后台任务必须对齐批处理
   * - 文件系统可见性
     - 全局命名空间开放，自由访问公共目录
     - 强制独立沙箱（Sandbox），访问共享文件需显式 Picker
   * - 权限控制机制
     - 安装期一次性粗粒度授权，默认开放度高
     - 运行时精细化动态授权，随时可撤销与降级（AppOps/TCC）
   * - 进程生命周期
     - 进程存活由用户或进程自身主动决定
     - 进程生命周期由系统完全托管，内存紧张时随时强杀（LMK/Jetsam）
   * - 应用分发体系
     - 自由下载可执行文件，本地无约束安装
     - 集中化签名验签、受控能力声明（Entitlements）与商店分发

1.4 移动平台五大约束矩阵：Power、Thermal、Privacy、Sensor、Connectivity
------------------------------------------------------------------------

在移动操作系统内部，每一次 API 调用、线程唤醒、网络请求与渲染提交，均受到五大核心物理约束的立体交织制约：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       移动平台五大物理约束矩阵体系                       |
   +-------------------------------------------------------------------------+
        |
        +---> 1. 电量预算约束 (Power / Battery Budget)
        |        * 核心指标：整机静态待机功耗 < 10~15 mA
        |        * 系统控制：Tickless Idle、EAS 能效调度、WakeLock 强力压制
        |
        +---> 2. 热包络与温控 (Thermal Envelope)
        |        * 核心指标：机身表面温度 < 42°C~45°C，持续 TDP < 4~6W
        |        * 系统控制：DVFS 阶梯式降频、屏幕亮度主动压低、快充限流
        |
        +---> 3. 隐私与数据隔离 (Privacy & Isolation)
        |        * 核心指标：敏感硬件访问全透明、数据最小化暴露
        |        * 系统控制：状态栏硬件指示器（绿色/黄色原点）、剪贴板访问拦截
        |
        +---> 4. 低功耗传感器常驻 (Sensor Subsystem)
        |        * 核心指标：24 小时计步与抬腕亮屏功耗 < 1% 整机电量
        |        * 系统控制：主 CPU 休眠，交由片上独立 Sensor Hub 协处理器采样
        |
        +---> 5. 复杂无线连接 (Connectivity & Radio Management)
                 * 核心指标：基站射频功耗控制、抗丢包重传、快速漫游
                 * 系统控制：网络请求自动合并批处理（JobScheduler/BGTask）

电量预算 (Power Budget) 的系统级贯彻
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

移动 CPU 在无计算任务时必须立即进入极低功耗的休眠状态（C-State / Sleep Mode）。若某个后台应用每隔 100 毫秒唤醒一次 CPU 执行心跳包检测，将导致整个 SoC 芯片的电源管理集成电路（PMIC）无法切断大核电压轨，待机功耗飙升 5~10 倍。

移动操作系统通过以下机制治理电量：

- **能效感知调度（Energy-Aware Scheduling - EAS）**：在为线程挑选运行核心时，综合权衡核心计算能力与每瓦性能比，尽可能将任务调度至小能效核运行。
- **定时任务对齐与批处理**：系统将来自不同应用的非即时性网络请求与后台作业收集并延迟，在设备接入 Wi-Fi 且充电时集中唤醒基带与无线网卡一次性处理完毕。

热包络 (Thermal Envelope) 与降级阶梯
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当芯片结温（Junction Temperature）升高至临界阈值时，温控守护进程（Thermal Daemon）将触发硬性保护状态机：

1. **第一阶段**：限制 CPU/GPU 动态调频调压（DVFS）的最高主频；
2. **第二阶段**：降低屏幕全局峰值亮度（如从 1000 nits 压制至 500 nits），并将刷新率由 120Hz 强制回退至 60Hz；
3. **第三阶段**：限制相机 4K/60fps 录像时长与后置闪光灯，强行关闭大型 3D 游戏后台缓存；
4. **第四阶段**：限制电池充电输入电流，防止电池内部化学反应叠加发热。

1.5 前后台生命周期与进程阶梯式回收策略
------------------------------------------------------------------------

为了实现前台交互的绝对流畅（60fps / 120fps 零掉帧）与多任务切换的高可用性，移动操作系统彻底重塑了进程生命周期模型。

应用进程五大状态机流转
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     移动应用进程生命周期状态机                          |
   +-------------------------------------------------------------------------+

   [ 1. 前台活跃 (Foreground Active) ]
        |  * 拥有屏幕焦点与顶层可见窗口
        |  * 分配最高 CPU 优先级 (SCHED_FIFO / QoS UserInteractive)
        |  * 独占相机、麦克风等物理硬件访问权
        |
        +---> (用户点击 Home 键或切换至其他应用)
        |
        v
   [ 2. 前台可见但不可交互 (Visible / Paused) ]
        |  * 窗口处于部分遮挡或多任务画中画模式
        |  * 仍保留较高调度权重，但停止高频动画渲染
        |
        +---> (完全移出屏幕视口)
        |
        v
   [ 3. 后台运行状态 (Background Running) ]
        |  * 获得极短的临时执行窗口（Android 为数秒，iOS 为 30 秒）
        |  * 用于完成未竟的持久化存储写入或网络连接断开
        |
        +---> (执行窗口超时且无前台服务授权)
        |
        v
   [ 4. 内存挂起/冻结 (Suspended / Frozen) ]
        |  * 进程地址空间全量保留在物理内存中，但所有线程被内核彻底冻结
        |  * CPU 时间分配归零，不产生任何电量消耗
        |
        +---> (系统发生物理内存不足 Memory Pressure)
        |
        v
   [ 5. 缓存与终止回收 (Cached -> Killed / Terminated) ]
           * 内核或底层内存守护进程直接发送 SIGKILL 信号终止进程
           * 物理页框被全量回收给前台应用，仅在磁盘保留轻量状态快照

内存回收机制对比：Android LMKD vs Apple Jetsam
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

智能手机操作系统通常不配置传统桌面系统的物理磁盘交换分区（Swap Partition），因为高速闪存（UFS / NVMe）的反复擦写会迅速耗尽存储介质物理寿命，且高延迟 I/O 换页会直接导致前台 UI 产生严重卡顿（Jank）。

当物理内存触及水位警戒线时，系统依赖专属的进程回收器：

- **Android LMKD (Low Memory Killer Daemon)**：基于内核进程的 `oom_score_adj`（取值范围 -1000 到 1000）建立评分体系。前台应用评分为 0，后台服务依次上升，最低优先级的 Cached 进程评分高达 900+。内存不足时，LMKD 自底向上遍历并强杀高分进程。
- **Apple Jetsam**：由 Darwin 内核的内存事件机制驱动，为每个进程设定严格的物理内存上限（Memory Footprint Limit）。一旦某后台应用突破预算阈值，或前台应用触发全局内存高水位，Jetsam 立即以原子方式杀死超标或挂起进程。

1.6 安装、签名、沙箱与应用分发信任边界
------------------------------------------------------------------------

在受控资源治理模型下，应用程序的身份确立与权限生效必须在安装前通过多层加密算法与策略文件予以固化：

1. **唯一主体身份（Unique App Identity）**：
   - Android 在应用安装时为其分配系统唯一的 Linux 用户标识（UID，如 `u0_a185`），并挂载独立的 SELinux 进程安全标签（如 `u:r:untrusted_app:s0:c185,c256`）。
   - iOS 依据 Apple 开发者证书生成唯一的 Bundle Identifier 与 Team ID，并注入签名描述文件（Provisioning Profile）。
2. **强制沙箱容器（App Sandboxing）**：
   - 应用程序被内核限制在其私有的文件系统容器目录内部（如 Android 的 `/data/data/<package_name>/` 或 iOS 的 `/var/mobile/Containers/Data/Application/<UUID>/`）。
   - 应用默认无法感知其他应用的存在，亦无法直接读取系统其他目录，所有跨应用数据交换必须通过系统提供的 Picker 或受控 IPC 通道（ContentProvider / App Groups）进行。
3. **受控能力声明与校验（Entitlements & Capabilities）**：
   - 应用程序若需使用推送通知、后台音频播放、钥匙串共享或本地网络访问，必须在签名描述文件（Entitlements Plist / AndroidManifest）中显式声明。系统在安装时校验开发者身份是否被授权使用该项能力。

1.7 用户可见体验背后的系统控制面
------------------------------------------------------------------------

终端用户在使用手机时所感知到的一切性能指标与系统行为，均是移动操作系统底层控制面策略调度的宏观映射：

.. list-table:: 用户可见现象与底层移动操作系统控制面的因果映射
   :widths: 22 38 40
   :header-rows: 1
   :class: tight-table

   * - 用户可见现象
     - 表面技术表现
     - 移动操作系统底层真实控制机制
   * - 界面丢帧卡顿 (Jank)
     - 120Hz 屏幕出现渲染掉帧
     - 主线程执行长任务阻塞事件分发；EAS 将 UI 线程错调至小核；GC 暂停
   * - 应用无响应 (ANR)
     - 弹窗提示“应用未响应”
     - 主线程在 5 秒内未完成 InputEvent 处理；Binder 同步调用跨进程死锁
   * - 异常发热与降频
     - 玩游戏 10 分钟后帧率由 60 骤降至 30
     - 芯片结温触发 Thermal Daemon 保护状态机，DVFS 强制限制 GPU/CPU 顶频
   * - 后台音乐突然中断
     - 切换拍照后正在播放的音乐停播
     - 相机打开占用高达 1.5GB 物理缓冲（RAW Stream），LMKD 强杀后台播放器
   * - 通知延迟送达
     - 锁屏时即时消息未及时弹出
     - 系统进入 Doze 深度休眠模式，基带断开高频唤醒，网络请求被排队对齐
   * - 敏感权限指示器
     - 屏幕右上角常驻绿色原点
     - 底层 CameraService 向系统合成器（SurfaceFlinger）注册硬件活动状态

小结与下章导读
------------------------------------------------------------------------

本章从计算机体系结构出发，建立了移动操作系统受控资源治理模型（Controlled Resource Governance）的核心心智模型，解构了电量、热量、隐私、传感器与无线网络等物理约束对系统架构的决定性影响，并剖析了前后台进程生命周期状态机。

5.2 Boundary 1 & 2: 硬件与厂商驱动边界的演进与解耦
------------------------------------------------------------------------

在移动操作系统早期架构中，厂商驱动与系统框架紧密编译在一起。为了彻底解决 Android 碎片化与系统升级困难，Google 推行了 **Project Treble** 架构革命，重塑了边界 2：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              传统 Passthrough HAL vs 现代 Binderized HAL 演进           |
   +-------------------------------------------------------------------------+

   [ 传统旧架构: Passthrough 动态库直连 (强耦合, 升级极其困难) ]
   system_server (Framework) ---> dlopen("camera.vendor.so") ---> 内核驱动
   * 缺陷: 框架与驱动共享同一进程地址空间，驱动崩溃直接拖死系统；无法独立升级系统分区。

   [ 现代 Treble 架构: Binderized 进程化隔离 (物理分区解耦, GSI 独立升级) ]
   /system 分区: [ system_server ]
                         |
                         | 跨进程 Binder 通信 (基于稳定 AIDL 接口契约)
                         v
   /vendor 分区: [ android.hardware.camera.provider 独立守护进程 ]
                         |
                         v 系统调用 (/dev/video*)
                 [ Linux 内核驱动 ]

- **Vendor Interface (VINTF) 契约**：系统在启动时严格校验 `/system` 与 `/vendor` 分区的兼容性矩阵（Compatibility Matrix），确保系统框架能够向下兼容旧版本的厂商 BSP。
- **Apple DriverKit 创新**：Apple 在 iOS/macOS 体系中推行了类似的机制，将原本运行在 XNU 内核态的 IOKit 驱动逐步迁移至用户态扩展（Driver Extension - DEXT），极大地收缩了内核态的受攻击面。

5.3 Boundary 3: 系统服务中枢边界的权限与状态代理
------------------------------------------------------------------------

系统服务中枢边界是移动操作系统最繁忙的业务中介控制平面：

1. **不可信输入的清洗与防御**：
   - 客户端应用传入的任何参数（如文件路径、内存偏移、Bitmap 尺寸），在穿透 Binder 边界抵达服务层时，必须首先经过严格的数据边界检查与反序列化验证，防止整数溢出或内存越界攻击。
2. **硬件能力的抽象化暴露**：
   - 系统服务对外暴露标准化、高内聚的系统实体（如 `LocationRequest`、`CaptureRequest`），向内则根据设备树与硬件配置，翻译为厂商 HAL 专有的低级操作指令，实现应用代码与底层硬件拓扑的完全解耦。

5.4 Boundary 4: 应用运行时沙箱边界的多层防线
------------------------------------------------------------------------

移动应用沙箱采用“双层强制访问控制”模型构筑坚不可摧的安全边界：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       应用沙箱 DAC + MAC 双层防线拓扑                   |
   +-------------------------------------------------------------------------+

   [ 应用进程操作请求: 尝试读取 /data/data/com.other.app/secret.db ]
        |
        v
   [ 第一道防线: Linux DAC (基于 UID/GID 权限位校验) ]
        |  * 目标文件所有者 UID 为 10185，当前进程 UID 为 10190
        |  * 校验结果: 权限不匹配 (Permission Denied)
        v
   [ 若攻击者利用漏洞完成本地提权 (UID 变为 0 / root) ]
        |
        v
   [ 第二道防线: SELinux MAC (基于 Type Enforcement 强制策略) ]
        |  * 当前进程安全标签: u:r:untrusted_app:s0:c190,c256
        |  * 目标文件安全标签: u:object_r:app_data_file:s0:c185,c256
        |  * 判定: untrusted_app 类别严格禁止跨 MCS Category 访问
        v
   [ 内核强制拦截并产生 avc: denied 审计日志，攻击彻底失败 ]

5.5 跨边界能力流转的性能损耗与零拷贝通道
------------------------------------------------------------------------

当音视频多媒体流、相机连续拍摄或 3D 渲染图层需要高频跨越上述四道边界时，若采用传统的 IPC 内存复制模式，显存与内存总线将瞬间瘫痪。

系统通过**统一显存缓冲区抽象（Graphic Buffer / AHardwareBuffer / IOSurface）**实现零拷贝穿透：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |               基于 dma-buf 句柄的零拷贝跨边界数据流拓扑                 |
   +-------------------------------------------------------------------------+

   1. [ Gralloc / ION 内存分配器 ]: 开辟物理连续的共享内存页框 (DMA Buffer)
        |
        +---> 生成微小的文件描述符句柄: int buffer_fd = 42;
        |
   2. 跨边界流转:
      [ Camera HAL ] --- (传递 fd: 42) ---> [ CameraService ] --- (传递 fd: 42) ---> [ App ]
                                                                                   |
   3. 各边界直接通过 mmap(buffer_fd) 获取用户态虚拟地址映射，实现零拷贝直达！ <----+

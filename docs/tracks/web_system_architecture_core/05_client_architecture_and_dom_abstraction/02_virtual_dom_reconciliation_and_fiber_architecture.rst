================================================================================
Chapter 26: Virtual DOM 协调算法与 React Fiber 架构：双缓存树、可中断增量更新与并发调度微架构
================================================================================

.. note:: 前置背景与认知承接
   在上一章中，我们自底向上解构了 DOM API 在浏览器内核内部的真实系统实现：从 Blink C++ 堆与 V8 托管堆的物理分离，到 V8 包装器对象的双向绑定与 Oilpan 联合垃圾回收；从 7 级穿透调用链到交错读写引发强制同步重排（Layout Thrashing）的物理惩罚（Chapter 25：DOM API 内部实现机制）。我们证明了：跨越语言胶水层直接、无序地操作 C++ 原生 DOM 树不仅耗费大量 CPU 周期，而且极易破坏渲染引擎的批处理优化。

   正是为了解决原生 DOM 操作的高昂成本与命令式 UI 编程的心智负担，现代前端架构演进出了声明式 UI 与 **Virtual DOM（虚拟 DOM）** 抽象层。然而，许多开发者对虚拟 DOM 存在“它比原生 DOM 更快”的技术迷思。事实上，Virtual DOM 在内存中重新生成对象树、计算 Diff 依然消耗显著的 JavaScript 计算资源。早期基于深度优先递归的 Stack Reconciler 更会因为长时间霸占主线程而引发严重的帧率骤降。

   为了彻底解决递归协调不可中断的硬伤，React 团队耗时数年重构了底层内核，推出了以单链表为核心的 **Fiber 架构**。本章将深入剖析 Virtual DOM 的代数本质与经典树编辑距离从 :math:`O(n^3)` 到启发式 :math:`O(n)` 的降维逻辑；详细拆解递归协调器的调用栈瓶颈；系统揭密 Fiber 节点的物理内存拓扑、双缓存树（Double Buffering）机制、时间切片（Time Slicing）协同调度的微架构实现；最后完整推导基于 31 位二进制位掩码的 Lanes 优先级并发模型。

26.1 Virtual DOM 的代数本质与树编辑距离 $O(n^3)$ 到 $O(n)$ 降维
------------------------------------------------------------------------

在纯粹的代数视角下，声明式前端框架将用户界面建模为纯函数映射：

.. math::

   	ext{UI} = f(	ext{State})

当状态 :math:`	ext{State}` 发生变更时，最直观的实现是将整个页面彻底推倒重建。然而，如果每次按键输入都让浏览器清空原有 DOM 并重新解析排版，页面将陷入持续的白屏闪烁，输入焦点与滚动位置亦将彻底丢失。

Virtual DOM 作为不可变内存数据结构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Virtual DOM（虚拟 DOM）的核心思想是在 JavaScript 内存空间中维护一棵轻量级的纯对象树，作为真实 C++ DOM 树的逻辑投影。

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 Virtual DOM 树的内存物理映射关系                                   |
   +---------------------------------------------------------------------------------------------------+

   [JavaScript 虚拟机堆内存 (V8)]                               [Blink 原生 C++ 堆内存]
   
   Virtual DOM (纯 JS 散列对象):                                 真实 DOM (C++ 结构体):
   {                                                             HTMLDivElement {
     type: 'div',                                                  vptr,
     props: {                                                      parent_node_,
       className: 'product-card',                                  first_child_,
       children: [                                                 next_sibling_,
         { type: 'h2', props: { children: 'Keyboard' } },          layout_object_,
         { type: 'span', props: { children: '129' } }              computed_style_,
       ]                                                           ...
     }                                                           }
   }

与一个包含数十个方法虚表、布局关联指针、样式快照与事件监听器映射表的 C++ `blink::Element` 相比，纯 JavaScript 的 VNode 对象仅包含 `type`、`props`、`key` 等极少数必要字段。创建、遍历与销毁一个纯 JS 对象的开销，比在 C++ 堆中分配一个真实 DOM 节点低 1 至 2 个数量级。

经典树编辑距离算法与 $O(n^3)$ 计算黑洞
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

给定两棵树 :math:`T_1` 与 :math:`T_2`，寻找通过最少步骤的“插入节点”、“删除节点”与“修改节点”将 :math:`T_1` 变换为 :math:`T_2` 的问题，在计算机科学中被称为 **树编辑距离问题（Tree Edit Distance）**。

基于动态规划的最优树编辑距离算法（如 Zhang-Shasha 算法或 Klein 算法）的时间复杂度在数学上严格受限于：

.. math::

   O(m 	imes n 	imes \min(d_1, l_1) 	imes \min(d_2, l_2)) \approx O(n^3)

其中 :math:`n` 为树的节点总数，:math:`d` 为树的最大深度，:math:`l` 为树的叶子节点数。

对于一个包含 1,000 个 DOM 节点的常规现代化 Web 应用，如果每次状态变化都执行严格的最小树编辑距离计算：

.. math::

   n = 1,000 \implies n^3 = 10^9 	ext{ 次计算操作}

在现代桌面 CPU 上，:math:`10^9` 次遍历运算需要耗费数百毫秒乃至数秒；在移动终端上，这将直接导致页面永久卡死。因此，直接在生产环境中应用经典树编辑距离算法在物理层面是完全不可行的。

启发式协调算法 (Heuristic Diffing) 的三大先验假设
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了将算法复杂度强行压缩至实际可用的线性复杂度 :math:`O(n)`，React 与各大前端框架引入了基于 Web UI 实际使用特征的 **启发式规则（Heuristic Assumptions）**：

1. **同层级比较假设（Same-Level Reconciliation）**：
   框架假定 Web 页面中的 DOM 节点极少发生跨越父子层级的剧烈搬迁。Diff 算法仅对同层级的兄弟节点进行横向比对。一旦发现某个节点在同层不存在，直接整棵子树销毁，而在新位置整棵子树重新创建，绝不尝试跨越层级去复用子树。
2. **类型不变量假设（Type Invariance）**：
   如果两个同位置虚拟节点的 `type`（如从 `<div>` 变为 `<p>`，或从 `<Header>` 变为 `<Sidebar>`）不同，算法判定其生成的子树结构完全不同，立即触发自上而下的彻底销毁（Unmount），并在相同位置重新构建新类型的整棵子树，不再向下递归深入比对。
3. **节点同一性与键值假设（Identity Preservation via `key`）**：
   开发者为列表中的同级子节点显式提供稳定且唯一的 `key` 属性。框架通过 `key` 识别同一个物理节点在不同渲染周期中的存在，即便其在同层中的相对位置发生了排序、插入或位移。

.. list-table:: 经典树编辑距离算法与 React 启发式 Diff 复杂度对比
   :widths: 20 25 25 30
   :header-rows: 1

   * - 算法模型
     - 时间复杂度
     - 空间复杂度
     - 核心策略与代价
   * - **Zhang-Shasha 算法**
     - :math:`O(n^3)`
     - :math:`O(n^2)`
     - 计算理论绝对最优编辑距离；计算量巨大，不可用于实时交互。
   * - **React 启发式 Diff**
     - :math:`O(n)`
     - :math:`O(n)`
     - 基于 3 大先验假设放弃跨层比对；换取单次线性扫描即可完成更新。

列表同层 Diff 核心状态机与两次遍历机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在处理包含多个同级子节点的集合更新时，React 采用了高效的“两次遍历”状态机算法。为了最大化复用已有 DOM 节点并最小化物理移动，算法维护了一个关键指针 `lastPlacedIndex`：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                React 列表 Diff 与节点移动判定状态机                                 |
   +---------------------------------------------------------------------------------------------------+

   旧节点序列 (Old):  [ A (0),  B (1),  C (2),  D (3) ]
   新节点序列 (New):  [ B,      A,      D,      C      ]

   初始状态: lastPlacedIndex = 0

   步骤 1: 扫描新序列首个节点 B
           在 Old 中找到 B，其旧索引 oldIndex = 1
           判定: oldIndex (1) >= lastPlacedIndex (0) -> 满足单调递增！
           处理: 节点 B 无需移动物理位置。
           更新: lastPlacedIndex = max(0, 1) = 1

   步骤 2: 扫描新序列第二个节点 A
           在 Old 中找到 A，其旧索引 oldIndex = 0
           判定: oldIndex (0) < lastPlacedIndex (1) -> 顺序发生逆转！
           处理: 节点 A 必须在真实 DOM 中向右执行移动操作 (Move to after B)。
           保持: lastPlacedIndex = 1

   步骤 3: 扫描新序列第三个节点 D
           在 Old 中找到 D，其旧索引 oldIndex = 3
           判定: oldIndex (3) >= lastPlacedIndex (1) -> 满足单调递增！
           处理: 节点 D 无需移动。
           更新: lastPlacedIndex = max(1, 3) = 3

   步骤 4: 扫描新序列第四个节点 C
           在 Old 中找到 C，其旧索引 oldIndex = 2
           判定: oldIndex (2) < lastPlacedIndex (3) -> 顺序发生逆转！
           处理: 节点 C 必须在真实 DOM 中向右执行移动操作 (Move to after D)。
           保持: lastPlacedIndex = 3

   最终真实 DOM 变更: 仅移动 A 与 C，B 与 D 原地不动，达成最小化 DOM 操作！

算法的具体流转分为两个阶段：
- **第一阶段（快速单向遍历）**：同时从头开始遍历旧链表与新链表，只要节点类型与 `key` 保持一致，直接原地更新属性复用；一旦遇到第一个不匹配项，第一轮遍历中断；
- **第二阶段（构建 Map 辅助查找）**：将剩余所有未匹配的旧节点放入以 `key`（或索引）为键的散列表 `existingChildren` 中。继续遍历剩余的新节点，通过 `key` 在 Map 中常数时间检索复用。若 `oldIndex < lastPlacedIndex`，说明该节点在旧序列中位于当前已处理节点的前方，现在必须将其物理拔出并向右插入；若 `oldIndex >= lastPlacedIndex`，则更新 `lastPlacedIndex`。剩余未被命中的旧节点被统一标记为删除（Deletion）。

26.2 递归调和器 (Stack Reconciler) 的架构瓶颈与掉帧根源
------------------------------------------------------------------------

在 React 16 之前，协调系统被称为 **Stack Reconciler（栈调和器）**。该架构直接依赖 JavaScript 运行时的本地调用栈（Call Stack）执行自顶向下的深度优先递归比对。

不可中断的递归深度调用栈
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Stack Reconciler 中，父组件渲染子组件的逻辑是同步连贯的：

.. code-block:: javascript

   // Stack Reconciler 递归伪逻辑
   function reconcile(vNode, parentDOM) {
     const dom = updateOrCreateDOM(vNode);
     // 深度优先递归调用自身
     vNode.children.forEach(child => reconcile(child, dom));
     parentDOM.appendChild(dom);
   }

当整棵应用组件树包含上万个节点、嵌套深度达到数十层时，执行栈的调用深度将线性暴增。由于 JavaScript 在浏览器渲染进程中是单线程执行的，**只要递归函数一旦启动，它就必须一口气执行到整棵树的叶子节点返回为止**。

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                 Stack Reconciler 霸占主线程引发掉帧 (Jank) 的时间轴物理剖析                         |
   +---------------------------------------------------------------------------------------------------+

   时间轴 (ms): 0ms               16.6ms             33.2ms             50ms                66.7ms
                |------------------|------------------|------------------|-------------------|
   物理显示刷新: VSYNC 1            VSYNC 2            VSYNC 3            VSYNC 4             VSYNC 5
   
   【Stack Reconciler 执行时序】
   主线程:      |==== Stack Reconciler 递归更新整棵树 (耗时 65ms 连续阻塞) ====| Style | Layout | Paint |
                ^                                                              ^
                用户在此处点击输入框 (Click Input)                              页面在此处才响应输入！
                (输入事件被困在任务队列中无法调度，延迟高达 65ms，产生严重卡顿！)

浏览器主线程的帧预算物理冲突
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于一个标准的 60Hz 刷新率显示屏，留给浏览器渲染一帧的全部时间预算仅有：

.. math::

   T_{	ext{frame}} = \frac{1000 	ext{ ms}}{60} \approx 16.6 	ext{ ms} \quad (	ext{在 120Hz 高刷屏上仅为 } 8.3 	ext{ ms})

在这 16.6 毫秒的微小时间窗口内，主线程不仅要执行业务 JavaScript 逻辑，还必须预留出约 6~10 毫秒用于样式的重算（Recalculate Style）、几何排版（Layout）、图层绘制（Paint）以及与合成器线程（Compositor Thread）同步。

若 Stack Reconciler 的递归遍历耗费了 50 毫秒：
- 主线程将连续跳过 3 个硬件 VSYNC 刷新周期；
- 正在运行的 CSS 关键帧动画、滚动条与视频播放出现剧烈顿挫（Frame Dropping）；
- 用户的触控、点击、键盘输入事件被深埋在浏览器的任务队列中无法出队，直接导致 Google 核心性能指标 **INP (Interaction to Next Paint)** 与 **FID (First Input Delay)** 呈现致命的红色劣化。

这一物理瓶颈宣告了纯递归调用栈在复杂客户端应用中的局限性：**要保障界面绝对流畅，调和过程必须被设计为可以随时暂停、让出主线程，并在稍后无缝恢复的增量计算架构**。

26.3 React Fiber 核心微架构：物理数据结构与双向链表拓扑
------------------------------------------------------------------------

为了彻底摆脱原生 JavaScript 调用栈的束缚，React 将“递归调用栈”在应用层完全重构为一种全新的物理数据结构——**Fiber**。

Fiber 的双重身份：工作单元与节点内存容器
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在微架构层面，一个 Fiber 实例既是组件在特定渲染周期的状态容器，也是调度器执行任务时的最小可分配 **工作单元（Unit of Work）**。

在 Chromium V8 堆中，一个真实的 Fiber 对象（定义于 ReactInternalTypes.js）具有严密的字段拓扑：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                     Fiber 节点的内存核心字段拓扑                                   |
   +---------------------------------------------------------------------------------------------------+

   +---------------------------------------------------------------------------------------------------+
   | 1. 静态节点与实例描述 (Instance Identity):                                                        |
   |    - tag: WorkTag              // 标记节点类型 (0: FunctionComponent, 5: HostComponent 等)         |
   |    - key: null | string        // 唯一 Diff 键值                                                   |
   |    - elementType: any          // React 元素原始类型 (如组件函数或原生 'div' 字符串)              |
   |    - type: any                 // 解析后的真实类型                                                 |
   |    - stateNode: any            // 指向真实物理实体的指针 (真实 DOM 节点或类组件实例)              |
   +---------------------------------------------------------------------------------------------------+
   | 2. 树形拓扑指针 (Structural Pointers / 单链表树):                                                  |
   |    - return: Fiber | null      // 指向父级 Fiber 节点 (模拟调用栈的 return 返回地址)               |
   |    - child: Fiber | null       // 仅指向首个直接子级 Fiber 节点                                    |
   |    - sibling: Fiber | null     // 指向右侧相邻兄弟 Fiber 节点                                      |
   |    - index: number             // 当前节点在同级兄弟中的位置索引                                   |
   +---------------------------------------------------------------------------------------------------+
   | 3. 动态数据与状态缓存 (Dynamic State & Input):                                                     |
   |    - pendingProps: any         // 本轮即将生效的新输入属性 (New Props)                             |
   |    - memoizedProps: any        // 上一轮渲染已生效的旧属性 (Old Props)                             |
   |    - updateQueue: mixed        // 状态更新队列 (保存 setState 产生的更新对象链表)                  |
   |    - memoizedState: any        // 节点自身状态 (在函数组件中指向 Hooks 环状单向链表表头)           |
   |    - dependencies: mixed       // Context 依赖跟踪链表                                             |
   +---------------------------------------------------------------------------------------------------+
   | 4. 调度与副作用标记 (Reconciliation & Side-Effects):                                               |
   |    - flags: Flags              // 自身需要执行的物理副作用掩码 (Placement, Update, ChildDeletion) |
   |    - subtreeFlags: Flags       // 所有子代树中包含的副作用聚合掩码 (用于极速跳过无变更子树)         |
   |    - lanes: Lanes              // 本节点未决更新的 31 位优先级二进制位掩码                         |
   |    - childLanes: Lanes         // 子树中未决更新的优先级掩码集合                                   |
   |    - alternate: Fiber | null   // 指向另一个缓冲树中对应历史节点的镜像指针 (双缓存架构核心)        |
   +---------------------------------------------------------------------------------------------------+

单链表树形拓扑对调用栈的解构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统树结构通常使用 `node.children = [child1, child2, ...]` 的数组存储子节点。这种结构必须依赖递归或内部维护的显式数组栈来回溯父节点。

Fiber 摒弃了数组指针，全面采用 **三指针单链表树（First-Child / Next-Sibling / Return）** 拓扑：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 Fiber 单链表拓扑遍历状态机示意图                                  |
   +---------------------------------------------------------------------------------------------------+

                          +----------------------+
                          |   App (Fiber Node)   |
                          +----------------------+
                                     |
                                     | child
                                     v
                          +----------------------+   sibling    +----------------------+
                          |  Header (Fiber Node) |------------->| Content (Fiber Node) |
                          +----------------------+              +----------------------+
                             |            ^                        |            ^
                       child |            | return           child |            | return
                             v            |                        v            |
                          +----------------------+              +----------------------+
                          |   Logo (Fiber Node)  |              | Article (Fiber Node) |
                          +----------------------+              +----------------------+

这种三指针拓扑使得深度优先遍历可以完全在循环中通过常数级变量实现：
- 向下探索：`workInProgress = workInProgress.child`；
- 横向步进：`workInProgress = workInProgress.sibling`；
- 向上回溯：`workInProgress = workInProgress.return`。

**由于任何时刻遍历的状态仅仅保存在全局唯一的指针变量 `workInProgress` 中，调度器可以在遍历的任意两步之间中断循环、退出执行栈将控制权还给浏览器，并在几十毫秒后根据 `workInProgress` 指向的地址原位继续，完全不受原生调用栈清空的影响！**

工作循环与核心遍历算法：`beginWork` 与 `completeWork`
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Fiber 的单工作单元遍历循环由 `workLoopConcurrent` 驱动，其核心算法包含“向下递进”与“向上归约”两个对称阶段：

.. code-block:: javascript

   // Fiber 并发工作循环核心算法
   function workLoopConcurrent() {
     // 只要存在待处理的工作单元，且当前时间切片未用尽
     while (workInProgress !== null && !shouldYield()) {
       performUnitOfWork(workInProgress);
     }
   }

   function performUnitOfWork(unitOfWork) {
     const current = unitOfWork.alternate;
     
     // 1. 递阶段 (beginWork): 自顶向下计算新状态，生成子 Fiber
     let next = beginWork(current, unitOfWork, renderLanes);
     unitOfWork.memoizedProps = unitOfWork.pendingProps;

     if (next === null) {
       // 无子节点，进入归阶段
       completeUnitOfWork(unitOfWork);
     } else {
       workInProgress = next;
     }
   }

1. **递阶段（`beginWork`）**：
   - 检查节点是否有未决更新（比较 `lanes`）；
   - 如果 props 和 state 未变，直接复用当前节点（Bailout 机制），跳过子树计算；
   - 若必须更新，调用组件函数（FunctionComponent）或提取 `render` 结果，得到新的 React Element 树；
   - 调用 `reconcileChildren`，利用前述的 Diff 算法比对新旧子节点，为子节点创建或复用 Fiber，打上 `Placement`、`Update`、`ChildDeletion` 等副作用标记（`flags`）。
2. **归阶段（`completeWork`）**：
   - 当 `beginWork` 返回 `null`（抵达叶子节点）时进入 `completeWork`；
   - 对于原生 DOM 节点（HostComponent），如果在初次挂载，负责创建真实的 C++ `blink::Element` 实例，并完成属性初始绑定；如果处于更新模式，负责计算属性差异（Diff Props）并打包为更新队列；
   - **冒泡子树标记（Bubble Flags）**：将当前节点子代的 `subtreeFlags` 与 `childLanes` 逐层向上合并至父节点的 `subtreeFlags` 中。这样，父节点无需遍历全部子代，只需检查自身的一位掩码，即可瞬间知晓整棵子树是否包含真实副作用。
   - 检查是否存在后继兄弟节点 `unitOfWork.sibling`。若存在，将工作指针移向兄弟节点重新进入 `beginWork`；若无兄弟节点，回溯至父节点 `unitOfWork.return` 继续执行 `completeWork`，直到返回根节点。

26.4 双缓存 (Double Buffering) 机制与两阶段执行管线
------------------------------------------------------------------------

在计算机图形学中，为了防止正在光栅化绘制的未完成画面被屏幕扫描输出引发画面撕裂（Screen Tearing），显示芯片普遍采用双缓冲（Double Buffering）机制：前缓冲区（Front Buffer）负责向显示器持续输出稳定帧，后缓冲区（Back Buffer）负责在后台全速离屏绘制新一帧。绘制完成后，仅需切换硬件指针，即可完成画面瞬时上屏。

React Fiber 完美借鉴了图形学的双缓存架构：在系统内存中始终同时存在两棵 Fiber 树。

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                               Fiber 双缓存树 (Double Buffering) 内存拓扑                          |
   +---------------------------------------------------------------------------------------------------+

   FiberRootNode (应用全局根节点)
         |
         | current 指针 (切换此指针即可瞬间切换整个屏幕状态)
         v
   +---------------------------------------+          alternate         +---------------------------------------+
   |   current 树 (当前屏幕渲染树)         | <------------------------> | workInProgress 树 (正在构建的离屏树)  |
   +---------------------------------------+                            +---------------------------------------+
   |  HostRootFiber                        |                            |  HostRootFiber                        |
   |    |                                  |                            |    |                                  |
   |    v child                            |                            |    v child                            |
   |  AppFiber (state: { count: 0 })       |                            |  AppFiber (state: { count: 1 })       |
   |    |                                  |                            |    |                                  |
   |    v child                            |                            |    v child                            |
   |  CounterFiber (text: '0')             |                            |  CounterFiber (flags: Update, '1')    |
   +---------------------------------------+                            +---------------------------------------+

Current 树与 WorkInProgress 树的交替镜像
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Current 树**：代表当前已经反映在屏幕上、用户正在交互的真实 UI 拓扑。`FiberRootNode.current` 强引用指向该树的根节点。
- **WorkInProgress (WIP) 树**：当状态发生变更触发新一轮调度时，React 在内存中离屏构建的全新工作树。所有的计算、Diff、组件重新求值均完全在 WIP 树上静默进行。
- **`alternate` 指针与内存池复用**：Current 节点与 WIP 节点之间通过 `alternate` 属性建立双向直接指针关联。在重新渲染时，React 绝非盲目重新实例化所有 Fiber 对象，而是优先从旧节点的 `alternate` 中直接读取已存在的镜像 Fiber 实例，仅覆盖更新其属性。这种设计将频繁触发的大规模 V8 垃圾回收压力消弭于无形。

两阶段执行管线：Render 阶段 vs Commit 阶段
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Fiber 的整个更新管线被在物理层面划分为职责截然不同的两大阶段：

.. list-table:: Fiber 架构两大执行阶段对比矩阵
   :widths: 20 28 26 26
   :header-rows: 1

   * - 阶段名称
     - 执行特征
     - 内部核心动作
     - 核心安全边界
   * - **Render 阶段**
     - **异步、可中断、分片执行**；随时可能因高优任务插入而被废弃重来。
     - 构建 WIP 树、调用函数组件、执行启发式 Diff、标记 `flags`。
     - **绝对禁止包含任何物理副作用！**（不可直接修改 DOM、发起网络请求等）。
   * - **Commit 阶段**
     - **同步、绝对不可中断**；一旦进入必须一口气执行完毕。
     - 遍历副作用标记、真实 DOM 操作（插入/删除/更新）、切换 `current` 指针、执行生命周期与 Hooks。
     - 保证真实 DOM 的状态瞬时一致性，绝不给用户呈现半成品界面。

Commit 阶段的三大细分子阶段
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 Render 阶段在内存中完成整棵 WIP 树的构建后，React 会携带收集了全树副作用标记的根节点，立即同步进入 **Commit 阶段**。Commit 阶段被进一步严密划分为三个微观子阶段：

1. **Before Mutation 阶段（DOM 突变前）**：
   - 触发类组件的 `getSnapshotBeforeUpdate` 生命周期函数；
   - 调度异步的 `useEffect` 清理与创建任务（通过微任务或宏任务登记，并不在此同步执行）。
2. **Mutation 阶段（执行物理 DOM 突变）**：
   - 遍历副作用链，执行真实的 DOM 节点移除（`removeChild`）、插入（`insertBefore` / `appendChild`）与属性赋值更新；
   - 处理组件的 `ref` 解绑（置为 `null`）；
   - **完成指针切换**：在 Mutation 阶段的末尾，执行核心赋值操作：
     
     .. code-block:: javascript

        root.current = finishedWork; // finishedWork 即为本轮构建完的 WIP 树
     
     这一行简单的指针切换，标志着 WIP 树在逻辑上正式登基为新的 Current 树！
3. **Layout 阶段（DOM 突变后布局同步）**：
   - 此时真实 C++ DOM 树已经更新，但浏览器尚未开始绘制（主线程仍在当前 JS 任务中）；
   - **同步执行** `useLayoutEffect` 的销毁与创建回调；
   - 重新绑定最新的 DOM 元素引用至 `ref`；
   - 开发者在此处同步读取 `element.offsetWidth` 或修改滚动条位置，虽然会触发回流，但**不会被用户察觉到任何中间位置的画面跳变**。

26.5 时间切片 (Time Slicing) 与协同调度器 (Scheduler) 微架构
------------------------------------------------------------------------

要实现 Render 阶段的“可中断并发执行”，仅有 Fiber 数据结构是不够的，系统必须配备一个能够与操作系统与浏览器事件循环精密协同的工控中枢——**React Scheduler（独立调度器包）**。

为什么抛弃原生的 `requestIdleCallback`？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

浏览器标准规范中存在原生的 `window.requestIdleCallback()` API，允许脚本在浏览器完成一帧渲染后的空闲期执行后台低优任务。然而，React 架构最终彻底放弃了该原生 API，原因在于其致命的平台缺陷：

1. **极度不可靠的帧触发频率**：当页面在后台运行、或者用户正在高频拖拽窗口时，浏览器的空闲周期调度极其不稳定，甚至会长达数秒完全不分发回调；
2. **刷新率硬编码冲突**：`requestIdleCallback` 默认以 60Hz（约 16.6ms）为时间切片基准，完全无法自适应适配现代移动设备与高刷电竞屏的 90Hz、120Hz 乃至 144Hz 刷新节奏；
3. **平台兼容性黑洞**：WebKit（Safari 浏览器）因对能耗控制的顾虑，长期拒绝实现 `requestIdleCallback`。

基于 `MessageChannel` 宏任务的自研事件循环协同机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代 React Scheduler 采用基于 **`MessageChannel` 宏任务** 的自研调度机制：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                         React Scheduler 时间切片调度环路与浏览器渲染帧协同                         |
   +---------------------------------------------------------------------------------------------------+

     +-----------------------------------------------------------------------------------------------+
     | 浏览器单帧周期 (16.6ms)                                                                        |
     |                                                                                               |
     |  [宏任务: Scheduler 工作切片] -> [微任务队列] -> [Style/Layout/Paint] -> [Compositor 屏幕刷新] |
     +-----------------------------------------------------------------------------------------------+
            |                                                      |
            | 执行 5ms 后 deadline 到达                            | 浏览器空闲
            v                                                      v
     [yieldToHost(): port2.postMessage()]                   [port1.onmessage 触发]
     主线程立刻释放，交给浏览器排版绘制！ <------------------------+ 恢复现场，继续执行下一个 Fiber 节点
     (用户输入与动画获得零延迟响应！)

选择 `MessageChannel` 而非 `setTimeout(fn, 0)` 的核心原因在于：根据 HTML 规范，嵌套超过 5 层的 `setTimeout` 会强制引入至少 **4 毫秒的硬性延迟惩罚（4ms Clamping Penalty）**；而 `MessageChannel` 在大多数主流浏览器中可以在渲染完成后以接近 0 毫秒的超低开销立即触发宏任务出队。

5ms 弹性时间切片与 `shouldYield` 判定微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在调度循环中，`shouldYieldToHost()` 函数是判断当前工作单元是否必须中断的核心门禁：

.. code-block:: javascript

   // Scheduler 时间切片判定核心逻辑
   let frameDeadline = 0;
   const frameLength = 5; // 默认每个时间切片分配 5 毫秒

   function shouldYieldToHost() {
     const currentTime = getCurrentTime();
     // 如果当前单次宏任务执行时间已超过 5ms
     if (currentTime >= frameDeadline) {
       // 检查当前是否有更高优先级的原生输入事件 (如触摸、按键) 处于等待调度状态
       if (navigator.scheduling && navigator.scheduling.isInputPending) {
         return navigator.scheduling.isInputPending();
       }
       return true;
     }
     return false;
   }

通过将每次占用主线程的计算窗口严格压制在 **5 毫秒左右**，React 确保即使在执行极其庞大的整树 Diff 计算时，主线程也能每隔 5 毫秒主动“向浏览器鞠躬让步”，给予合成器线程、用户触控事件和 CSS 动画充足的执行窗口，从而在物理上消灭卡顿。

双最小堆 (Min-Heap) 任务队列设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Scheduler 内部维护了两个标准的二进制最小堆（Binary Min-Heap）数据结构：
- **`taskQueue`（待执行任务堆）**：按照任务的绝对过期时间 `expirationTime` 排序，堆顶始终是距离超时最近（或已超时）的最紧急任务；
- **`timerQueue`（延迟任务堆）**：按照任务的开始时间 `startTime` 排序，存放通过延时注册的任务。

在每次工作切片开始时，调度器首先检查 `timerQueue`，将已到达生效时间的延迟任务拔出并推入 `taskQueue`。随后，从 `taskQueue` 堆顶不断弹出最高优先级的任务进行切片执行。

26.6 Lanes 优先级模型：从 ExpirationTime 到 31 位二进制掩码调度
------------------------------------------------------------------------

在 React 16 早期，系统使用 **ExpirationTime（过期时间戳）** 作为任务优先级的标量度量。一个较大的数值代表较早超时，因而具备较高优先级。

ExpirationTime 模型的表达力坍塌
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

随着并发特性的深入演进，ExpirationTime 暴露了其本质缺陷：
1. **无法表达非连续的多批次关联（Non-continuous Batching）**：一个时间戳只是一个连续标量。如果存在两个互不相关的后台低优更新（如 CPU 计算密集型的代码编辑器语法高亮与网络轮询的数据图表刷新），系统无法表达“将任务 A 与任务 C 合并批处理，但同时跳过任务 B”的离散集合关系；
2. **缺乏多维任务语义**：标量无法有效区分“因用户物理持续交互（输入/滚动）产生的紧急任务”、“由 `startTransition` 显式降低优先级的低敏任务”以及“由 Suspense 发起的重试任务”。

Lanes 31 位整型二进制掩码体系
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

从 React 17 开始，调度内核全面演进为 **Lanes 优先级模型**。它利用一个 32 位有符号整数中的低 **31 位二进制位（Bitmask）**，将优先级空间建模为一个可以由 CPU 位运算指令光速求解的代数集合：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 React 31 位二进制 Lanes 优先级全景图                              |
   +---------------------------------------------------------------------------------------------------+

   二进制掩码位 (从低位到高位，数值越小，物理优先级越高):
   
   0b0000000000000000000000000000001 (0x01) -> SyncLane (离散用户输入: click, keydown, input)
   0b0000000000000000000000000000010 (0x02) -> InputContinuousHydrationLane
   0b0000000000000000000000000000100 (0x04) -> InputContinuousLane (连续交互: mousemove, scroll)
   0b0000000000000000000000000001000 (0x08) -> DefaultHydrationLane
   0b0000000000000000000000000010000 (0x10) -> DefaultLane (普通数据更新: fetch, promise, setTimeout)
   0b0000000000000000000000000100000 (0x20) -> TransitionHydrationLane
   0b0000000000000000000011111000000 (0x7C0) -> TransitionLanes (TransitionLane1 ~ 16, 共有 16 条车道)
   0b0000000000001111111100000000000        -> RetryLanes (Suspense 重试车道)
   0b0100000000000000000000000000000        -> IdleLane (闲置空闲车道)
   0b1000000000000000000000000000000        -> OffscreenLane (离屏隐藏组件预渲染)

位运算驱动的极速优先级判定算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Lanes 模型将复杂的集合运算与优先级决策降维为基础的 CPU 位运算指令，其性能极其惊人：

1. **提取集合中最高优先级的单条车道（提取最低有效位 LSB）**：
   
   在计算机补码系统中，使用 `lane & -lane` 可以在单条汇编指令内瞬间获取整数中最右侧的第一个二进制 `1`：

   .. code-block:: javascript

      // 提取 highestPriorityLane
      function getHighestPriorityLane(lanes) {
        return lanes & -lanes;
      }

   例如，若 `lanes = 0b00010100`（同时包含 DefaultLane 与 InputContinuousLane），则：
   
   .. math::

      	ext{lanes} = 0b00010100 \
      -	ext{lanes} = 0b11101100 \
      	ext{lanes} \ \& \ -	ext{lanes} = 0b00000100 \quad (	ext{瞬间提取出最高优先级的 InputContinuousLane！})

2. **合并车道集合（求并集）**：
   
   .. code-block:: javascript

      fiber.lanes = fiber.lanes | nextLane;

3. **剔除已完成车道（求差集）**：
   
   .. code-block:: javascript

      fiber.lanes = fiber.lanes & ~completedLane;

4. **判断是否存在重叠冲突（求交集）**：
   
   .. code-block:: javascript

      const hasConflict = (wipLanes & incomingLanes) !== 0;

并发特性实战底层解密：`useTransition` 与高优任务插队
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

利用 Lanes 模型，React 彻底解锁了现代并发交互能力：

.. code-block:: javascript

   function SearchPage() {
     const [input, setInput] = useState('');
     const [list, setList] = useState([]);
     const [isPending, startTransition] = useTransition();

     function handleChange(e) {
       // 1. 同步用户按键响应：分配 SyncLane (最高优先级)
       setInput(e.target.value);

       // 2. 耗时列表重算：分配 TransitionLane (低优先级车道)
       startTransition(() => {
         setList(generateLargeList(e.target.value));
       });
     }
     // ...
   }

当用户连续高频敲击键盘时，系统底层的执行时序如下：
1. `setInput` 触发，Scheduler 收到 `SyncLane` 更新，主线程立即响应，输入框字符毫无延迟地显示；
2. 调度器利用空闲时间片，在 WIP 树上启动属于 `TransitionLane` 的长列表渲染；
3. 用户在列表渲染到一半时突然按下了下一个字母：
   - 产生新的 `SyncLane` 任务；
   - 调度器检测到更高优先级的 `SyncLane` 到达，其优先级高于当前 WIP 树正在执行的 `TransitionLane`；
   - **中断并丢弃当前未完成的 WIP 树！**（因为这是纯内存操作，尚未进入 Commit 阶段，丢弃该半成品树完全无任何副作用）；
   - 立即转头执行新的按键输入；
   - 用户输入完成后，再次从头启动最新参数下的 `TransitionLane` 列表计算。

这种插队机制从物理层面消除了传统前端框架在面对海量数据筛选时输入框“敲字假死”的通病。

26.7 性能边界与工程取舍：Virtual DOM 并不天然等于更高绝对性能
------------------------------------------------------------------------

在深入理解了 Virtual DOM 与 Fiber 架构的全部精密实现后，架构师必须清醒地审视这套机制的真实性能边界与代价。

破除“虚拟 DOM 比直接原生 DOM 快”的误区
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在纯粹的单次操作性能上限上：

.. math::

   	ext{Virtual DOM 性能} = 	ext{原生 DOM 操作开销} + 	ext{创建 VNode 内存开销} + 	ext{执行 Diff 算法计算开销}

**没有任何框架能够突破底层宿主平台的物理限制**。框架的最终归宿依然是调用 `document.createElement` 与 `element.setAttribute`。Virtual DOM 的真正工程价值在于：
- **保障应用性能的下限（High Performance Baseline）**：它防止了普通开发者写出随意的全量 DOM 重建与未优化的强制同步重排，通过内部批处理与启发式 Diff 确保无论 UI 多么复杂，更新成本都收敛在与变更量成正比的可控范围内；
- **跨平台宿主解耦**：Fiber 节点与具体的渲染后端（React DOM、React Native、React Three Fiber 等）彻底解耦，使得同一套状态逻辑可以驱动 Web 浏览器、iOS/Android 原生控件乃至 3D WebGL 渲染管线。

Fiber 架构带来的固有内存与垃圾回收开销
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

精密的分片调度是有显式物理成本的：
- **V8 堆内存常驻翻倍**：由于双缓存机制的存在，每个组件长期维持着两个相互通过 `alternate` 镜像引用的 Fiber 实例，加之 Hook 单向链表（`memoizedState`）的额外封装，大型 React 应用的运行时内存驻留量显著高于原生代码；
- **GC 压力依然存在**：尽管 Fiber 节点本身被尽可能复用，但在 Render 阶段高频执行组件函数时，函数作用域内新产生的临时对象、内联闭包函数、新 JSX Element 散列对象依然会海量涌入 V8 新生代（New Space），触发频繁的 Scavenge 垃圾回收周期。

工业级架构优化准则与避坑指南
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **善用 `React.memo` 阻断 Fiber 树遍历扩散**：
   在 Fiber 的 `beginWork` 阶段，只要父组件重新执行，默认情况下其所有子代 Fiber 节点都会被派发执行更新检查。合理使用 `React.memo`（对比 props 引用不变性），可以让协调器在命中节点时直接返回 `null`，瞬间剪枝跳过整个数千节点的深层子树计算。
2. **警惕 `key` 的反模式使用**：
   - **严禁使用随机数（如 `Math.random()`）作为 key**：这会导致每一轮渲染该节点及其整个子树被判定为“全新类型”，引发整棵 C++ DOM 树的彻底销毁与重建，使得所有输入焦点、CSS 过渡状态与内部缓存完全丢失；
   - **避免在可重排列表中使用数组下标（Index）作为 key**：在列表项插入或删除时，Index 的错位会诱骗 Diff 算法执行错误的属性就地复用，不仅引发严重的 UI 状态错乱，还会迫使所有节点全部执行无意义的重新渲染。
3. **精准评估架构替代范式**：
   在超高频数据流（如高频量化交易行情看板、百兆级实时数据图表）场景中，Virtual DOM 与 Fiber 的分片调度开销可能反过来成为吞吐量瓶颈。在这种极限吞吐场景下，后续章节将展开的 **细粒度响应式更新（Fine-Grained Reactivity / Signals）** 或直接操作底层 Canvas/WebGL 是更为适配的架构解法。

小结与下章导读
------------------------------------------------------------------------

本章作为 **Part 5: 客户端架构、DOM 抽象与前端运行时** 的第二篇核心专著，自顶向下穿透了现代声明式框架的虚拟 DOM 与 Fiber 调度中枢：
- 解密了 Virtual DOM 作为纯 JavaScript 不可变描述树的代数本质，推导了经典树编辑距离 :math:`O(n^3)` 复杂度在现实应用中的计算不可行性，以及 React 依赖三大先验假设将协调算法强行降维至 :math:`O(n)` 的实现逻辑；
- 剖析了列表同层 Diff 的核心状态机，推导了基于 `lastPlacedIndex` 判定节点向右移动的判定链条；
- 深入批判了早期 Stack Reconciler 依赖原生递归调用栈霸占主线程、击穿 16.6ms 帧预算引发严重交互掉帧（Jank）的物理缺陷；
- 完整拆解了 React Fiber 的物理内存拓扑，阐明了其基于“首子-右兄弟-父节点”单链表三指针拓扑如何将递归栈解构为可中断遍历状态机；
- 深入解密了借鉴计算机图形学的双缓存（Double Buffering）机制，系统推导了可中断纯计算的 Render 阶段与原子化同步提交的 Commit 三大子阶段；
- 系统揭密了独立 Scheduler 基于 `MessageChannel` 宏任务与 5ms 弹性时间切片（Time Slicing）的协作机制，剖析了双最小堆任务队列的设计精妙；
- 严格推导了从 ExpirationTime 到 31 位二进制 Lanes 位掩码的演化逻辑，解析了 `lane & -lane` 等 CPU 级位运算如何赋予 React 毫秒级抢占插队与并发过渡能力；
- 客观标定了 Virtual DOM 的性能边界，澄清了其作为基准下限保障而非绝对上限的工程定位。

然而，无论 Fiber 架构的链表遍历与位运算如何精巧，Virtual DOM 终归需要在运行时在内存中重新计算树形差异。前端技术演进的钟摆并未停止在此。如果我们在编译期就通过静态分析获知哪些状态真正绑定了哪些具体 DOM 属性，能否彻底跳过虚拟 DOM 树的构建与 Diff，实现零运行时代价的原子级更新？

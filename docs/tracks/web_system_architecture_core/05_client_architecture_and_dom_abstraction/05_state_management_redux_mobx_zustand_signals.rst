.. note:: 前置背景与认知承接
   在上一章中，我们系统推导了客户端路由状态机与企业级微前端架构的底层实现（Chapter 28：客户端路由与微前端架构：History API 状态机、PopState 拦截与多应用沙箱隔离机制）。我们证明了：单页应用（SPA）通过捕获用户交互、劫持全局链接点击，并在基数树（Radix Tree）路由匹配与会话历史堆栈（Session History Stack）之间建立确定性映射，实现了无文档重载的平滑页面切换与多独立应用的运行时沙箱编排。

   然而，路由仅解决了宏观页面级别的导航与可见性映射问题。当用户进入特定页面后，整个客户端运行时将面临密集的数据交互与动态变更：用户输入、WebSocket 高频推送、后台长轮询、表单草稿与多组件跨层级协同，均需要读写与派生海量的业务数据。如果状态管理设计不当，极其微小的数值变更将沿着组件层级向上扩散，引发无序的全局级联重渲染（Cascade Re-rendering），彻底耗尽渲染主线程的时间切片，甚至导致由于异步竞态引发的状态撕裂（Tearing）。

   本章将深入状态管理范式的核心腹地：从经典的不可变单向数据流（Redux/Flux）、透明响应式观察者（MobX）、轻量闭包切片订阅（Zustand），到去中心化原子图（Jotai/Recoil）与细粒度 Signals 范式。我们将深入剖析结构共享的垃圾回收（GC）代价、Proxy 依赖收集栈、React 18 `useSyncExternalStore` 防撕裂底层协议，以及不同范式在内存占用、并发渲染与渲染更新粒度上的物理极限与工程选型权衡。

29.1 状态管理范式的物理本质与核心矛盾：UI = f(state) 的计算开销与依赖收敛
------------------------------------------------------------------------
在现代声明式前端运行时中，界面渲染被形式化定义为关于状态的纯函数映射：

.. math::

   	ext{UI} = f(	ext{State})

然而，在物理硬件与运行时的真实约束下，该公式隐藏着巨大的计算复杂度陷阱：

1. **粗粒度全量重算开销**：若 :math:`	ext{State}` 被视为不可分割的单一巨石对象，每一次微小属性的改变都意味着整个函数 :math:`f` 的重新求值。在包含 :math:`N` 个节点的组件树中，若无任何优化，更新遍历的时间复杂度为 :math:`O(N)`。
2. **虚拟 DOM 调和代价值**：即使框架引入了 Virtual DOM 树的比对（Reconciliation），遍历大型虚拟节点树所产生的堆内存分配、垃圾回收（GC）压力以及 CPU 指令开销，依然会在高频交互场景下（如画布拖拽、实时金融行情跳动）造成严重的交互掉帧（INP 劣化）。
3. **依赖收敛的物理追求**：理想的状态管理系统必须具备**依赖精准收敛（Dependency Convergence）**能力——当特定状态 :math:`S_k` 发生变更时，系统能够在 :math:`O(1)` 或 :math:`O(K)`（:math:`K \ll N`，其中 :math:`K` 为实际依赖该状态的视图单元）的计算复杂度内，精准定位受影响的组件节点甚至直接定位底层的 DOM 属性，将其余 :math:`N - K` 个无关节点的计算开销严格降为零。

状态分类学与所有权边界 (State Taxonomy)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在设计状态拓扑前，架构师必须对客户端运行时的状态属性实施清晰的物理分类：

.. list-table:: 前端运行时状态属性与所有权矩阵
   :widths: 20 20 30 30
   :header-rows: 1

   * - 状态分类
     - 权威事实源 (Source of Truth)
     - 生命周期与持久化边界
     - 典型应用场景与技术方案
   * - **局部 UI 交互状态**
     - 组件内部内存
     - 严格随组件实例挂载而生、随卸载而销毁。
     - Modal 显隐、展开/折叠面板、Hover 样式（`useState` / 组件局部变量）。
   * - **共享客户端状态**
     - 客户端全局 Store
     - 跨多路由存活，用户登出或刷新时重置。
     - 用户全局权限、购物车选品列表、即时聊天草稿（Redux / Zustand / MobX）。
   * - **远程服务状态缓存**

     - 可被复制、分享、持久化于书签中。
     - 搜索查询参数、Tab 分页标识符（`URLSearchParams`）。

核心矛盾：不可变数据流与细粒度响应式的工程哲学对抗
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了解决组件如何感知状态变化并触发视图更新的问题，前端工程界分化出两条截然相反的演化路径：

- **不可变单向数据流（Immutable & Explicit Dispatch）**：
  强调状态的只读性与更新的可预测性。任何状态变更必须显式分发 Action，通过纯函数生成全新的状态对象指针。视图通过浅层引用比较（`prev !== next`）判定是否需要执行重渲染。
- **透明响应式观察者（Mutable & Transparent Reactivity）**：
  强调状态的就地可变性与依赖追踪的自动化。通过底层代理机制（Proxy / Getter / Setter），运行时在组件渲染期间自动记录被读取的属性依赖图。当属性被直接赋值时，响应式拓扑网络自动精准驱动受影响的订阅者重渲染。

这两种哲学在内存开销、开发心智负担、时间旅行调试以及高并发场景下的表现存在深层次的物理差异。

29.2 不可变单向数据流范式 (Redux / Flux)：纯函数 Reducer 与浅比较开销

Redux 承袭了 Elm 架构与 Facebook Flux 的思想，将整个应用程序的共享状态收拢进一个全局单一事实源（Single Source of Truth）的中央 Store。

结构共享 (Structural Sharing) 的内存机制与 GC 影响
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
“不可变（Immutability）”绝不意味着在每次更新时对整个状态树执行昂贵的全量深拷贝（Deep Clone）。如果每次状态微调都需要深拷贝百万字节的树结构，系统将瞬间因 CPU 拷贝开销与堆内存暴涨而崩溃。

Redux 依赖 **结构共享（Structural Sharing）** 机制：只有从根节点到发生修改的叶子节点路径上的所有祖先对象会被浅层复制（Shallow Clone），而其余未修改的树状分支则原样复用旧有对象的内存指针：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 不可变状态树的结构共享内存拓扑                                    |
   +---------------------------------------------------------------------------------------------------+

            旧状态树 (Root 1)                             新状态树 (Root 2)
                 [Root] (0x001)                                [Root] (0x009) [新分配]
                /      \                                      /      \
       [Branch A]      [Branch B]                    [Branch A]      [Branch B] (0x00A) [新分配]
        (0x002)         (0x003)                       (0x002)         /      \
        /      \        /      \                    (直接复用)  [Leaf C]      [Leaf D] (0x00B) [新分配]
      ...      ...   [Leaf C]  [Leaf D]                          (0x004)        (修改为新值)
                      (0x004)   (0x005)                         (直接复用)

在上述过程中，当 `Leaf D` 发生变更时：
1. `Leaf D` 被分配新的内存对象 `0x00B`；
2. 它的父节点 `Branch B` 必须浅拷贝为 `0x00A`，将其右子节点指针指向 `0x00B`，而左子节点指针继续直接复用未修改的 `Leaf C (0x004)`；
3. 根节点 `Root` 浅拷贝为 `0x009`，左指针复用 `Branch A (0x002)`，右指针指向 `Branch B (0x00A)`。

浅比较（Shallow Equality Check）的代数原理与时间复杂度
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
结构共享为 UI 层带来了确定性的性能红利。当某个下游组件仅消费 `Branch A` 时，它在接收到 Store 变更通知后，只需执行极简的引用全等比对：

.. code-block:: javascript

   function shouldComponentUpdate(prevBranchA, nextBranchA) {
     // 仅需单次指针比对，时间复杂度严格为 O(1)
     return prevBranchA !== nextBranchA;
   }

因为 `Branch A` 的物理内存地址仍为 `0x002`，`prevBranchA === nextBranchA` 判定为 `true`，该组件及其下方整颗子树即可立即跳过（Bailout）调和流水线，无需深入检查叶子节点。

物理缺陷与性能开销模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
尽管不可变单向数据流具备极致的可预测性与可调试性，但其在物理层面上存在固有的架构缺陷：
1. **频繁的短命对象分配与 GC 压力**：高频更新（如鼠标移动采样、键盘输入）会促使 JavaScript 引擎的年轻代堆内存（New Space）迅速填满，频繁触发 Scavenge 垃圾回收，引起间歇性的主线程停顿（Jank）。
2. **选择器缓存失效应激（Selector Cache Miss）**：如果开发者在 `useSelector` 中编写了数组映射或对象重构（例如 `state => state.todos.filter(t => t.active)`），则每次 Store 广播时均会产生一个全新的数组指针，导致浅比较永久失效，强制触发无意义的连带重渲染。必须通过 `reselect` 这类带有输入记忆（Memoization）的高阶选择器才能弥补。

29.3 观察者与透明响应式范式 (MobX)：Proxy 拦截、依赖图与自动重渲染
------------------------------------------------------------------------
与 Redux 强制的不可变约束相反，MobX 采纳了**透明功能响应式编程（Transparent Functional Reactive Programming, TFRP）**范式。它允许开发者直接以面向对象的习惯就地修改数据（`order.price = 42`），由底层运行时自动追踪依赖并以最小粒度驱动视图更新。

ES6 Proxy 依赖收集微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
现代响应式系统的核心是 ES6 `Proxy` 拦截器。MobX 内部通过维护一个全局唯一的当前计算上下文栈（Derivation Stack），在属性读取（Getter）与属性赋值（Setter）时完成依赖关系的自动编织：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                ES6 Proxy 自动化依赖追踪状态机流程                                 |
   +---------------------------------------------------------------------------------------------------+

   [React 组件渲染函数 / Reaction 执行]
         |
         v
   1. 将当前组件的 Reaction 对象推入全局求值栈: globalDerivationStack.push(reaction)
         |
         v
   2. 执行组件渲染代码，访问可观察对象属性: const val = order.price;
         |
         v (触发 Proxy Getter 拦截器)
   3. [Proxy Getter Handler]:
         +---> 检查全局求值栈顶部是否存在活跃的 Reaction
         +---> 存在: 在当前属性的可观察节点 (ObservableNode) 与当前 Reaction 之间双向注册依赖边
               (Observable.observers.add(reaction), reaction.observing.add(observable))
         +---> 返回底层的真实属性值
         |
         v
   4. 组件渲染执行完毕，退出栈帧: globalDerivationStack.pop()
   
   -----------------------------------------------------------------------------------------------------
   [用户事件修改属性: order.price = 99;]
         |
         v (触发 Proxy Setter 拦截器)
   5. [Proxy Setter Handler]:
         +---> 物理更新对象属性值
         +---> 遍历当前属性的可观察节点持有的 observers 集合
         +---> 通知所有受影响的 Reaction 节点进入脏状态 (Mark Stale)
         +---> 调度受影响的组件执行精准重渲染 (Schedule Re-render)

响应式有向图的三元核心节点
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MobX 将应用逻辑拆解为包含三种核心节点的有向无环图（DAG）：

.. list-table:: 响应式有向图核心节点与职责分工
   :widths: 20 25 30 25
   :header-rows: 1

   * - 节点类型
     - 物理表现形态
     - 数据流拓扑角色
     - 变化驱动与传播机制
   * - **Observable**
     - 存储状态的叶子变量
     - **数据源（Source）**：持有基准可变数据。
     - 被赋值修改时向其所有观察者发射变化通知。
   * - **Computed**
     - 纯函数派生值
     - **中间变换节点（Transform）**：具备缓存能力。
     - 惰性求值（Lazy Evaluation）；输入未变时直接命中缓存。
   * - **Reaction / Observer**
     - 副作用 / UI 组件
     - **数据终点（Sink）**：消费数据并产生物理副作用。
     - 接收到脏标记后自动排队，调度主线程重绘或执行 I/O。

事务批处理与瞬态错乱消除 (Glitch Freedom)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在复杂的响应式网络中，一个底层状态的改变可能通过多条不同深度的计算路径最终汇入同一个组件（钻石依赖问题，Diamond Dependency）：

.. code-block:: text

            [Observable: Base Price]
                   /        \
                  v          v
          [Computed: Tax]  [Computed: Discount]
                  \          /
                   v        v
              [Reaction: Total UI]

若系统未经过拓扑排序处理，`Tax` 更新后立即触发 `Total UI` 计算，此时 `Discount` 尚未更新，`Total UI` 将在中间瞬态渲染出一个错误的错误总价；随后 `Discount` 更新，`Total UI` 再次重算。这种中间短暂的不一致状态被称为 **瞬态错乱（Glitch）**。

为了消解该问题，MobX 要求状态写入必须包裹在显式或隐式的事务（`action`）中：
1. **冻结副作用传播**：在事务执行期间，所有的属性修改仅更新内存值并将受影响的下游节点打上“脏（Stale）”标记，绝对不触发任何 Reaction 运行；
2. **基于拓扑深度的批量调度**：当外层事务代码完全执行退出后，调度器统一对脏节点按照依赖拓扑深度进行排序，以自底向上的顺序统一执行微任务广播，确保下游节点在计算时其所有前置依赖均已处于最终一致状态。

29.4 极简闭包与分片订阅范式 (Zustand)：无 Context 开销的外部 Store
------------------------------------------------------------------------
随着 React 16.8 Hooks 的普及，以 Redux 为代表的传统状态库暴露了心智复杂、样板代码繁重的痛点；而直接基于 React 原生 `createContext` 构建的全局共享方案，又会陷入致命的 **Provider 全量穿透重渲染陷阱**（任何 Context 值的细微变化，都会迫使树下所有调用了该 Context 的组件无条件执行重渲染，无论其消费的是否为受影响的字段）。

Zustand 应运而生。其核心设计哲学是：**完全跳出 React 组件树的约束，将状态托管于独立的纯 JavaScript 闭包内存中，仅在组件需要订阅的切片数据发生实质改变时，精准唤起特定组件的渲染**。

外部 Store 的极简闭包原语
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Zustand 的底层内核极其轻量，其本质是一个经典的发布-订阅闭包（Vanilla Store）：

.. code-block:: typescript

   type StateListener<T> = (state: T, prevState: T) => void;

   export function createStore<T>(createState: (set: any, get: any) => T) {
     let state: T;
     const listeners: Set<StateListener<T>> = new Set();

     const getState = () => state;

     const setState = (partial: any, replace?: boolean) => {
       const nextState = typeof partial === 'function' ? partial(state) : partial;
       if (!Object.is(nextState, state)) {
         const previousState = state;
         state = (replace ?? (typeof nextState !== 'object' || nextState === null))
           ? nextState
           : Object.assign({}, state, nextState);
         // 同步广播通知所有活跃的订阅者
         listeners.forEach((listener) => listener(state, previousState));
       }
     };

     const subscribe = (listener: StateListener<T>) => {
       listeners.add(listener);
       // 返回注销清理函数
       return () => listeners.delete(listener);
     };

     state = createState(setState, getState);
     return { getState, setState, subscribe };
   }

React 18 并发渲染下的状态撕裂与 `useSyncExternalStore`
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 React 18 之前，将外部数据源接入 React 组件通常借助 `useEffect` 配合 `useState`。但在 React 18 引入的 **并发渲染（Concurrent Rendering）** 机制下，这种做法会导致灾难性的 **状态撕裂（State Tearing）** 故障：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                               并发模式下的状态撕裂 (State Tearing) 物理成因                       |
   +---------------------------------------------------------------------------------------------------+

   时间轴 -------------------------------------------------------------------------------------------->

   [React 并发渲染开始: 时间切片 1]
         |
         +---> 组件 Tree A 渲染，读取外部 Store 值: v1
         |     (React 主线程让出控制权，浏览器响应外部异步网络或计时器事件)
         |
   [外部异步事件发生]
         |
         +---> 外部 Store 被直接突变修改为: v2
         |
   [React 恢复并发渲染: 时间切片 2]
         |
         +---> 组件 Tree B 渲染，读取外部 Store 值: v2
         |
   [最终 Commit 阶段提交至真实 DOM]
         |
         v
   屏幕上同时呈现: Tree A 基于 v1，Tree B 基于 v2！产生严重的数据不一致与界面错乱（Tearing）

为了终结外部状态源在并发渲染中的撕裂风险，React 官方团队在 18.0 中推出了全新的底层同步原语 **`useSyncExternalStore`**：

.. code-block:: typescript

   import { useSyncExternalStore } from 'react';

   export function useStore<T, Slice>(
     store: ReturnType<typeof createStore<T>>,
     selector: (state: T) => Slice,
     equalityFn: (a: Slice, b: Slice) => boolean = Object.is
   ): Slice {
     // useSyncExternalStore 接收三个核心参数：
     // 1. subscribe: 注册监听的函数
     // 2. getSnapshot: 返回当前不可变状态快照的函数
     // 3. getServerSnapshot: 用于服务端渲染 (SSR) 的初始快照
     const slice = useSyncExternalStore(
       store.subscribe,
       () => selector(store.getState()),
       () => selector(store.getState())
     );
     return slice;
   }

`useSyncExternalStore` 的工作机制包含严密的物理保护：
- 在并发渲染执行树遍历期间，如果检测到通过 `getSnapshot()` 读取的值发生了改变，React 立即判定当前渲染上下文已经过期，自动强行中断（Deopt）并发时间切片，丢弃未完成的并发树，回退至同步阻塞模式重新渲染，绝对杜绝不同组件捕获到不同版本快照的可能性。

切片选择器 (Slice Selector) 与内存跳过机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Zustand 中，组件通过传入细粒度的选择器切片（Slice Selector）实现极高精度的更新收敛：

.. code-block:: typescript

   // 仅当 user.name 发生改变时才触发此组件重渲染；即使 store 内的 cart、orders 剧烈变动，该组件毫不知情
   const userName = useUserStore((state) => state.user.name);

由于切片提取直接发生在 `getSnapshot` 内部，只有当选择器计算出的返回值未通过浅比较（`equalityFn`）时，`useSyncExternalStore` 才会向 React 调度器发起重渲染请求，将更新范围严格收敛在具体的组件实体上。

29.5 原子化状态拓扑与派生图 (Recoil / Jotai)：自底向上的数据流
------------------------------------------------------------------------
无论是 Redux 的单一集中式 Store，还是 Zustand 的模块化切片 Store，它们的架构范式都是 **自顶向下（Top-Down）** 的：开发者必须预先声明一个涵盖所有业务分支的父级状态树结构。

当面对 **高动态性、树状节点关系繁复或富协作画布（如 Figma 形状图层、流程图设计器）** 等业务场景时，自顶向下的架构会面临严峻挑战：每一个图元或卡片不仅有自身的位置与大小，还与其他图元存在分组、吸附或派生连接关系。如果将数万个图元存放在一个巨型字典中，图元之间的依赖流转将变得极为笨拙。

为了解决这个问题，以 Recoil 和 Jotai 为代表的 **原子化状态管理范式（Atomic State Management）** 应运而生。

原子 (Atom) 的本质与内存布局
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
原子化范式彻底放弃了中央巨石 Store，将状态的最小单元解构为相互独立的 **原子（Atoms）**：

- 原子是**定义状态规范的一等公民（First-Class Citizens）**，在语法上只是一个轻量级的不可变配置对象（带有唯一 Symbol 或字符串标识）；
- 原子的真实数据实体并不保存在原子对象内部，而是由渲染树顶层的 `Provider`（或全局运行时的 `WeakMap`）集中托管：

.. code-block:: typescript

   // Jotai 原子的极简实现拓扑示意
   export interface Atom<Value> {
     key: symbol;
     init: Value;
     read?: (get: <V>(a: Atom<V>) => V) => Value;
     write?: (get: any, set: any, update: any) => void;
   }

   export function atom<Value>(initialValue: Value): Atom<Value> {
     return {
       key: Symbol(),
       init: initialValue,
     };
   }

   // 实际运行时中，组件树上下文维护全局状态 WeakMap
   const storeState = new WeakMap<Atom<any>, any>();

派生原子与动态依赖有向无环图 (DAG)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
原子化状态的核心威力在于 **自底向上的声明式派生能力（Derived Atoms）**。一个原子可以由其他一个或多个原子通过只读或读写函数组合而成：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 Jotai / Recoil 原子依赖拓扑图                                     |
   +---------------------------------------------------------------------------------------------------+

            [Atom A: Unit Price]          [Atom B: Quantity]
                    \                         /
                     \                       /  (声明式组合依赖)
                      v                     v
                 [Derived Atom C: Subtotal = A * B]       [Atom D: Coupon Discount]
                                 \                                /
                                  \                              /
                                   v                            v
                              [Derived Atom E: Final Price = C - D]
                                                |
                                                v
                                    [CheckoutButton Component]
                             (仅订阅 Final Price，无感知 Unit Price)

当 `Atom A (Unit Price)` 发生改变时：
1. 派生图引擎自顶向下执行脏标记传播（Dirty Marking），自动判定依赖 `Atom A` 的下游派生原子包括 `Derived Atom C` 与 `Derived Atom E`；
2. 调度器触发增量计算，重新评估 `Derived Atom E` 的最终值；
3. 仅挂载了 `useAtomValue(FinalPriceAtom)` 的组件会收到微任务重渲染通知；而仅订阅了无关原子的视图区域在物理层面上完全感知不到变更的发生。

动态原子族 (Atom Family) 与可变拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
针对无限列表或动态表格场景，原子化库提供了参数化原子族（Atom Family）模式：

.. code-block:: typescript

   // 依据图元 ID 动态生成对应的原子，每个图元拥有完全独立的内存订阅单元
   const shapeAtomFamily = atomFamily((shapeId: string) => {
     return atom({ id: shapeId, x: 0, y: 0, color: '#000' });
   });

当用户在画布中拖动 `shapeId = 'shape-999'` 的图元时，仅有 `shapeAtomFamily('shape-999')` 对应的订阅者会触发局部重绘，其余 9999 个图元组件在渲染流水线中保持完全静止。这种动态拓扑构建能力是传统自顶向下 Store 难以优雅实现的。

       v              v                                                         v               v

- **场景 A：超大规模多团队协同的企业级核心系统（金融账务、ERP 核心流程）**
  **首选 Redux Toolkit**。其严格的不可变约束、强制的 Action 审计流与强大的 DevTools 时间旅行调试能力，能够在代码库规模突破百万行、研发人员突破数百人时，提供最高的系统确定性与最低的诡异 Bug 追踪成本。
- **场景 B：中大型单页应用、通用 Web 应用（SaaS 平台、协作看板、电商控制台）**
  **首选 Zustand**。它彻底清除了样板代码与 Context 穿透惩罚，借助原生 `useSyncExternalStore` 获得对 React 18 并发特性的完美支持，配合 `createJSONStorage` 可以极快落地与持久化存储的联动。
- **场景 C：高复杂度网格拓扑、画布渲染、富交互低代码平台**
  **首选 Jotai 或 Recoil**。其去中心化的自底向上原子拓扑，使得系统能够以图元为单位动态分发订阅，彻底避免画布中单个图元位移导致全画布千万节点被迫扫描重算。
- **场景 D：追求极限渲染帧率、突破虚拟 DOM 性能瓶颈的性能敏感型界面**
  **首选 Signals（基于 SolidJS 或 Preact Signals）**。它将响应式拓扑下沉至编译期与原生 DOM 绑定，彻底切断视图渲染对 React 树比对调和机制的依赖，实现真正意义上的纳秒级直接 DOM 属性赋新。

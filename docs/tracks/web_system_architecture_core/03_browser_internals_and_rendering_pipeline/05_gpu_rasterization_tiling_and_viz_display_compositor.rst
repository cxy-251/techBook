Chapter 16: GPU 栅格化、分块渲染与 Viz 显示合成框架：从 cc::RasterTask 到 Skia、SharedImage 与 Chromium Viz Display Compositor

.. note:: 前置背景与认知承接
   前一章系统剖析了 Blink 绘制流水线（Paint Pipeline）、CSS 2.1 附录 E 的七级层叠上下文、Transform/Clip/Effect/Scroll 四大属性树解耦架构，以及合成器线程（Compositor Thread）通过 `LayerTreeHostImpl` 镜像实现与主线程解耦的 120Hz 硬件加速执行模型。在合成器线程完成图层划分与属性树绑定后，内存中持有的依然是一组记录在 `PaintRecord` 中的**矢量绘图操作序列（Skia PaintOps）**。

16.1 分块渲染架构 (Tiling) 与显存预算管理
------------------------------------------------------------------------

在现代 Web 应用中，一个页面的总尺寸往往远超物理视口（Viewport）。例如一个包含数千行内容的无限滚动列表或长文章，其文档高度可能达到数万像素。

整层栅格化的显存爆炸危机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

假设一个页面在 4K 分辨率（物理像素宽度 $W = 3840$）下的文档高度为 $H = 20000	ext{px}$。若渲染引擎将整个文档作为一个单一图层分配连续显存并执行完整栅格化：

.. math::

   	ext{VRAM Cost} = W 	imes H 	imes 4	ext{ Bytes (RGBA8888)} = 3840 	imes 20000 	imes 4 = 307,200,000	ext{ Bytes} \approx 292.97	ext{ MB}

- **物理约束**：单张页面仅图层位图就消耗近 300MB 显存。当用户打开数十个标签页，或者多图层重叠时，移动端与桌面端 GPU 显存将在瞬间耗尽，触发内核 OOM（Out of Memory）强杀进程。
- **计算浪费**：用户在任一时刻通过屏幕只能看到视口内部约 $3840 	imes 2160$（约 31.6MB）的内容，超出视口上下数万像素的区域耗费了巨量算力进行栅格化，却从未被用户肉眼观测。

分块模型与 PictureLayerTiling 拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了解决显存与算力浪费，Chromium 合成器（`cc` 模块）采用了**分块渲染（Tiling）**机制。合成器将每个合成图层在空间坐标系上均匀切割为固定尺寸的矩形网格（通常为 $256 	imes 256$ 或 $512 	imes 512$ 物理像素），每一个网格单元被称为一个 **Tile（图块）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  图层空间切割与 PictureLayerTiling 拓扑模型              |
   +-------------------------------------------------------------------------+

   [ 完整图层: 宽度 3840px, 高度 20000px ]
   +-----------+-----------+-----------+ ... +-----------+
   | Tile(0,0) | Tile(1,0) | Tile(2,0) | ... | Tile(7,0) |  <--- 屏幕视口外 (暂不分配显存)
   +-----------+-----------+-----------+ ... +-----------+
   | Tile(0,1) | Tile(1,1) | Tile(2,1) | ... | Tile(7,1) |  <--- 预热区 (Soon Bin: 异步排队)
   +-----------+-----------+-----------+ ... +-----------+
   | Tile(0,2) | Tile(1,2) | Tile(2,2) | ... | Tile(7,2) |  <=== 当前屏幕可见视口 (Visible Bin:
   | Tile(0,3) | Tile(1,3) | Tile(2,3) | ... | Tile(7,3) |       最高优先级栅格化, 锁定显存)
   +-----------+-----------+-----------+ ... +-----------+
   | Tile(0,4) | Tile(1,4) | Tile(2,4) | ... | Tile(7,4) |  <--- 预热区 (Soon Bin: 异步排队)
   +-----------+-----------+-----------+ ... +-----------+
   | Tile(0,5) | Tile(1,5) | Tile(2,5) | ... | Tile(7,5) |  <--- 屏幕视口外 (Eventually / Never)
   +-----------+-----------+-----------+ ... +-----------+

TileManager 优先级调度状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

`TileManager` 依据当前视口位置与滚动预测速度向量，将页面中的所有 Tile 划分进四个离散的优先级调度桶（Priority Bins）：

.. list-table:: Chromium TileManager 优先级调度状态机与显存分配策略
   :widths: 20 30 25 25
   :header-rows: 1
   :class: tight-table

   * - 优先级桶 (Priority Bin)
     - 空间判定范围
     - 调度行为
     - 显存分配策略
   * - **NOW_BIN (Visible)**
     - 当前视口与视口交叉相交区域的 Tile
     - 最高优先级，阻塞当前帧提交，必须同步或极速完成栅格化
     - 强行持有显存纹理，禁止被 LRU 缓存驱逐
   * - **SOON_BIN (Pre-paint)**
     - 围绕可见视口外围拓展预热区域（预测未来 300ms~500ms 滚动可见）
     - 放入异步后台任务队列，在 GPU 空闲时逐步栅格化
     - 允许分配显存，但在显存吃紧时可随时降级丢弃
   * - **EVENTUALLY_BIN**
     - 距离视口较远但在当前可见图层范围内的 Tile
     - 极低优先级，仅在系统具有充裕显存和闲置算力时预演
     - 仅保留矢量绘图指令，不分配真实显存位图
   * - **NEVER_BIN**
     - 被完全遮挡（Occluded）或不可见图层的 Tile
     - 不执行任何栅格化调度
     - 严禁分配任何显存

动态分辨率与 Pinch-to-Zoom 栅格化缩放
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当用户在触控屏上执行双指缩放（Pinch-to-Zoom）时，页面放大倍率 $S$ 发生连续变化。如果每次微小缩放都重新栅格化全页，GPU 吞吐将瞬间崩溃：

1. **瞬态阶段（In-Flight Gestures）**：合成器仅对已有 Tile 纹理应用 4x4 变换矩阵（Texture Bilinear Filtering 缩放），产生轻微模糊但保持绝对稳定的 120Hz 响应；
2. **稳定阶段（Gesture End）**：缩放手势结束或速度减缓时，合成器为图层创建新的 `PictureLayerTilingSet`，以目标设备物理像素密度（Raster Scale = $S 	imes 	ext{DevicePixelRatio}$）重新分配高分辨率 Tile 并执行精细栅格化，最终平滑替换低清纹理。

16.2 从 CPU 软件栅格化到 OOP-R (进程外 GPU 栅格化)
------------------------------------------------------------------------

浏览器栅格化架构经历了两代根本性的演进：从早期的 CPU 软件栅格化，到现代的 **OOP-R（Out-of-Process GPU Rasterization，进程外 GPU 栅格化）**。

传统 CPU 软件栅格化模式及其物理瓶颈
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在早期 Chromium 与 WebKit 架构中：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    传统 CPU 软件栅格化流水线及其瓶颈                    |
   +-------------------------------------------------------------------------+

   [ Renderer 进程: Worker 线程 ]
        |
        | 1. 调用 CPU Skia 软件光栅化器 (扫描线算法, 绘制几何/文字)
        v
   [ 主内存系统内存 (RAM): 共享内存 SharedMemory Bitmap ]
        |
        | 2. IPC 发送 SharedMemory 句柄给 GPU 进程 (跨进程同步开销)
        v
   [ GPU 进程: Command Buffer ]
        |
        | 3. 调用 glTexSubImage2D / glTexImage2D 执行主机到设备拷贝 (Host-to-Device Copy)
        v
   [ 物理 GPU 显存 (VRAM) 纹理 ]

- **物理带宽墙**：每一帧都在 CPU 主存生成数 MB 位图，并通过 PCIe / SoC 内存总线执行一次昂贵的内存上传（Texture Upload），消耗大量总线带宽与 CPU 周期；
- **指令无法利用 GPU 并行硬件**：复杂的矢量抗锯齿、渐变填充与路径裁剪完全运行在串行 CPU 上，无法利用 GPU 成百上千个 ALU 核心的并行算力。

OOP-R (进程外 GPU 栅格化) 架构革命
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代 Chromium 默认启用了 **OOP-R** 架构，彻底消除了 Renderer 进程中的位图生成与跨进程像素传输：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 Chromium OOP-R (进程外 GPU 栅格化) 执行拓扑             |
   +-------------------------------------------------------------------------+

   [ 1. Renderer 进程 (合成器线程) ]
        |
        |  * 持有 PaintOpBuffer 矢量绘图指令序列 (体积仅几 KB 到几十 KB)
        |  * 收集当前需要栅格化的 Tile 边界与变换矩阵
        v
   [ 2. Mojo IPC / GPU Command Buffer (轻量指令跨进程通道) ]
        |
        |  * 发送序列化的 PaintOps 字节流 (零像素数据!)
        v
   [ 3. GPU 进程 (Viz / Raster Decoder) ]
        |
        |  * 接收 PaintOps 序列
        |  * 调用 GPU 版 Skia (Ganesh / Graphite) 后端
        v
   [ 4. 直接在物理 GPU 显存纹理 (SharedImage) 上执行硬件着色器渲染 ]
        * 顶点着色器 (Vertex Shader) 计算图元顶点
        * 片段着色器 (Fragment Shader) 执行抗锯齿、渐变与纹理采样
        * 结果直接写入绑定的 FrameBuffer (物理 VRAM)，零内存拷贝!

Skia 图形后端演进：Ganesh 与 Graphite
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 GPU 进程内部，Skia 图形库负责将 `PaintOps` 翻译为现代图形 API 调用：

- **Skia Ganesh（上一代 GPU 后端）**：基于 OpenGL ES / Vulkan / Metal 的传统状态驱动抽象层。由于需要兼容古老的 OpenGL 状态机，其在管线状态对象（PSO）管理与多线程命令录制上存在固有时延；
- **Skia Graphite（现代下一代 GPU 后端）**：专为 Vulkan、Metal 与 Dawn（WebGPU）设计的现代化不可变架构。完全消除了全局状态跟踪，引入显式渲染图（Render Graph）重排与合并，支持多线程极速录制 GPU 硬件命令缓冲区（Command Buffers）。

字形图集 (Glyph Atlas) 与距离场字体 (SDF) 技术
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

网页文本占栅格化负载的 60% 以上。GPU 栅格化如果逐字解析 TrueType/OpenType 矢量贝塞尔曲线，开销极其高昂：

1. **字形缓存图集（Glyph Atlas）**：GPU 进程在显存中维护一张全局的大型单通道纹理图集（通常为 $2048 	imes 2048	ext{ R8}$）。FreeType / HarfBuzz / DirectWrite 仅在首次遇到新字符时将其光栅化并存入图集；
2. **GPU 批量绘制**：渲染文本时，GPU 仅需将文本拆解为一系列带有 UV 坐标的矩形网格（Quads），在着色器中通过一次单纹理采样即可完成成千上万个字形的亚像素抗锯齿渲染；
3. **有向距离场（Signed Distance Field - SDF）**：针对高频缩放文本，图集存储字符轮廓的距离场标量，着色器利用 `smoothstep()` 在任意缩放尺度下即时重构极度锐利的矢量边缘，彻底避免重复栅格化。

16.3 显存纹理抽象底座：SharedImage 与 Mailbox 跨进程流转
------------------------------------------------------------------------

在多进程沙箱隔离架构下，Renderer 进程、GPU 进程以及浏览器 UI 进程各自运行在独立的虚拟地址空间中。一个进程分配的 GPU 纹理显存，如何被另一个进程安全读取并进行最终合成？

传统 OpenGL 共享上下文的缺陷
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

早期采用的 `EGLImage` 或 OpenGL 共享上下文（Shared Context）机制具有严重的架构硬伤：
- 强行绑定在单图形 API 上，无法跨 Vulkan、Metal 与 DirectX 混用；
- 缺少显式的内存所有权和同步契约，多进程并发读写极易发生显存踩踏或死锁；
- 无法利用现代操作系统专有的底层零拷贝共享句柄。

Chromium SharedImage 跨平台底座
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Chromium 设计了 **SharedImage** 框架，作为所有 GPU 纹理显存分配、跨进程流转与跨图形 API 互操作的单一抽象层：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    Chromium SharedImage 跨平台架构模型                  |
   +-------------------------------------------------------------------------+

   [ 上层抽象: gpu::Mailbox (128-bit 全局唯一随机凭证 GUID) ]
        |
        +-----------------------------------+-----------------------------------+
        |                                   |                                   |
   [ Windows 平台 ]                   [ macOS / iOS 平台 ]                [ Linux / Android 平台 ]
   * D3D11 / D3D12 Texture            * IOSurface (Apple 物理显存)        * DMA-BUF / AHardwareBuffer
   * DXGI Shared Handle               * IOSurfaceID                       * Prime File Descriptor (FD)
        |                                   |                                   |
        +-----------------------------------+-----------------------------------+
                                            v
                 [ 底层操作系统内核物理显存页框 (Zero-Copy 共享底座) ]

gpu::Mailbox 与 gpu::SyncToken 同步原语
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 Renderer 进程或 WebGL 引擎创建一个 `SharedImage` 时：

1. **生成全局凭证**：分配系统底层物理显存，并生成一个 128 位的全局唯一标识符 `gpu::Mailbox`；
2. **跨进程引用**：Renderer 进程仅需通过 Mojo 将 `gpu::Mailbox` 作为轻量值传递给 GPU 进程或 Viz 显示合成器；
3. **异步同步屏障（SyncToken）**：由于 GPU 指令是完全异步并发执行的，为了保证 Viz 消费纹理时，Renderer 的栅格化着色器已经全部执行完毕，Chromium 引入了 `gpu::SyncToken`：

.. math::

   	ext{SyncToken} = \langle 	ext{CommandBufferNamespace}, 	ext{CommandBufferID}, 	ext{ReleaseCount} \rangle

- **无锁等待机制**：生产者（如 WebGL 上下文）在完成绘制命令提交后插入一条标记，获取带有单调递增编号的 `SyncToken`；消费者（Viz 合成器）在读取该 Mailbox 前，向驱动插入一条针对该 `SyncToken` 的等待指令。GPU 硬件内部的事件计数器自动完成依赖同步，**CPU 全程零阻塞**！

.. list-table:: 现代浏览器纹理流转模式对比：Zero-Copy vs One-Copy
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 纹理流转模式
     - 物理数据通路与实现
     - 核心优缺点与适用场景
   * - **Zero-Copy (零拷贝模式)**
     - 直接由操作系统分配支持硬件扫描直出的底层显存缓冲（Windows DXGI / macOS IOSurface / Linux DMA-BUF）。GPU 栅格化直接写入该缓冲，显示控制器直接读取。
     - **极高吞吐、零内存带宽浪费**。要求硬件与操作系统驱动深度支持，是现代高端桌面与移动端的主流标准。
   * - **One-Copy (单拷贝暂存模式)**
     - GPU 进程先在共享 Staging Buffer（临时上传环形缓冲）中写入数据，随后通过 GPU DMA 引擎执行一次显存内 Copy 转移至最终纹理。
     - **通用性好、兼容老旧驱动**。消耗额外一份临时显存与少量内部总线带宽，用于低端硬件或特定格式转码兜底。

16.4 Chromium Viz 显示合成服务微架构 (Viz Display Compositor)
------------------------------------------------------------------------

在 2018 年之前，合成与最终屏幕显示逻辑分散在 Browser 主进程和各 Renderer 进程中。为了实现沙箱隔离与架构解耦，Chromium 将显示合成逻辑彻底下沉，构建了独立的 **Viz（Visuals）** 架构。

Viz 架构多源输入拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Viz 作为一个常驻在 GPU 进程中的独立服务（也可在低端设备上运行于专属独立进程），充当了浏览器所有可视化内容的“中央显示调度台”：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Chromium Viz 显示合成服务输入拓扑                   |
   +-------------------------------------------------------------------------+

   [ Client 1: 页面主文档 Renderer ] ----+
        (发送网页内容 CompositorFrame)    |
                                           |
   [ Client 2: 跨源 iframe (OOPIF) ] -----+
        (发送隔离子框架 CompositorFrame)  |
                                           +---> [ Viz Display Compositor (GPU 进程) ]
   [ Client 3: 浏览器 UI 进程 ] ----------+            |
        (发送地址栏/标签页 CompositorFrame)|            | 1. SurfaceAggregator 递归合并
                                           |            | 2. 深度排序与遮挡剔除
   [ Client 4: 硬件视频解码器 ] ----------+            | 3. 生成最终 AggregatedFrame
        (发送硬件 Overlay 视频流帧)                     v
                                                [ 操作系统显示后端 (DWM / CALayer / DRM) ]

CompositorFrame 数据结构剖析
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每个客户端生成的 `CompositorFrame` 是一份纯粹的轻量级几何元数据描述包，其内部并不包含任何像素，而是包含：

1. **RenderPass 列表**：一个或多个渲染通道。通常包含一个主 `RootRenderPass`，以及若干个用于滤镜或特殊混合的离屏 `RenderPass`；
2. **QuadList（绘制四边形阵列）**：每个 RenderPass 内部包含一系列排好序的 `DrawQuad`：
   - `TileDrawQuad`：指向特定 `SharedImage`（Mailbox）的图块纹理；
   - `SolidColorDrawQuad`：纯色矩形（无需纹理，直接片元填充，极其节约显存）；
   - `TextureDrawQuad`：直接由 WebGL、WebGPU 或 `<video>` 生成的动态视频/画布纹理；
   - `SurfaceDrawQuad`：嵌套子表面占位符（用于挂载跨源 iframe 的渲染输出）。

Surface 体系与 SurfaceAggregator 聚合算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了支持 Site Isolation（站点隔离）与 Out-of-Process iframes（OOPIF，跨源独立进程 iframe），每个独立的渲染客户端拥有一个专属的 `viz::Surface`：

.. math::

   	ext{SurfaceId} = \langle 	ext{FrameSinkId}, 	ext{LocalSurfaceId} \rangle

- `FrameSinkId`：标识客户端身份（例如某个特定的 iframe 渲染进程）；
- `LocalSurfaceId`：由父容器在尺寸变化、设备像素比变更时单调递增的序列号（确保尺寸变更时父子容器像素级同步，杜绝拉伸白边）。

`SurfaceAggregator` 在每个 VSYNC 周期执行遍历算法：
1. **递归展开**：从根 Surface（浏览器 UI）出发，遇到 `SurfaceDrawQuad` 时，定位对应子进程提交的最新有效 `Surface` 并递归内联展开；
2. **属性空间合并**：将各子 Surface 的局部变换矩阵与剪裁矩形，通过属性树计算折叠到统一的全局根屏幕空间；
3. **全局遮挡剔除（Occlusion Culling）**：依据从前向后（Front-to-Back）的顺序，计算每个 `DrawQuad` 是否被前方的不透明 Quad 完全覆盖。被完全遮挡的 Quad 直接从渲染队列中物理剔除，彻底消除了 GPU 片元着色器的无效 Overdraw；
4. **生成 AggregatedFrame**：输出一份扁平、无冗余的全局合成帧。

16.5 操作系统级显示呈现 (Presentation) 与硬件覆盖层 (Hardware Overlays)
------------------------------------------------------------------------

当 Viz 完成 `AggregatedFrame` 的构建后，最终一步是将这些几何四边形交付给操作系统的显示服务器（Display Server）进行物理点阵发光。

.. list-table:: 主流操作系统显示服务与 Chromium Viz 接入后端
   :widths: 20 25 30 25
   :header-rows: 1
   :class: tight-table

   * - 操作系统平台
     - 系统显示服务器/窗口管理器
     - Chromium Viz 呈现层实现
     - 核心特性
   * - **Windows**
     - DWM (Desktop Window Manager)
     - `DirectComposition` / DXGI SwapChain
     - 硬件级 Visual 树提交，支持多平面覆盖层 (MPO)
   * - **macOS**
     - WindowServer
     - `CoreAnimation` (CALayer / CAMetalLayer)
     - 基于 IOSurface 跨进程共享，系统级视网膜色彩管理
   * - **Android**
     - SurfaceFlinger
     - `Hardware Composer (HWC)` / EGLSurface
     - 硬件图层直通显示控制器，极低功耗
   * - **Linux**
     - Wayland Compositor / X11
     - Wayland Subsurfaces / KMS/DRM (GBM)
     - 零拷贝 DMA-BUF 扫描输出 (Page Flip)

硬件覆盖层 (Hardware Overlays / MPO) 的节能机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统的渲染模式下，如果网页上正在播放一段 4K 60FPS 视频，Viz 必须在每个刷新周期启动 GPU 着色器，将 4K 视频帧纹理与网页的其他 UI 元素在显存中执行一次 Alpha 混合合成（GPU Composition），再将合成结果送显。这会导致 GPU 显存带宽居高不下。

现代操作系统与 GPU 提供了 **多平面硬件覆盖层（Multi-Plane Overlays - MPO / Hardware Overlays）** 技术：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  硬件覆盖层 (Hardware Overlay) 零合成直通拓扑           |
   +-------------------------------------------------------------------------+

   [ 浏览器常规 UI 元素 ] --------> [ 写入常规 UI 显存平面 (Plane 0) ] ---+
                                                                         |
   [ 硬件解码器输出的 4K 视频流 ] -> [ 直接挂载到覆盖层平面 (Plane 1) ] ---+
                                                                         |
                                                                         v
                                    [ 物理显示控制器硬件扫描电路 (Display Controller) ]
                                    * 硬件电路在发出 HDMI/DP 信号的纳秒级瞬间,
                                    * 实时完成图层叠加与缩放!
                                    * 100% 绕过 GPU 着色器合成, 节约 30%~50% 显存功耗!

帧定时控制与 VSYNC 闭环驱动 (Frame Pacing)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了避免画面撕裂（Screen Tearing）并保持极致流畅，整个渲染流水线由显示器的物理垂直同步信号（VSYNC）严格驱动：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     VSYNC 信号驱动的全链路渲染闭环流水线                 |
   +-------------------------------------------------------------------------+

   [ 硬件 VSYNC 脉冲 (如 120Hz = 8.33ms 周期) ]
        |
        +---> [ 1. Viz 产生 BeginFrame 信号 ]
        |          |
        |          +---> 分发给 Renderer 进程主线程: 触发 requestAnimationFrame 与 Layout/Paint
        |          +---> 分发给 Renderer 进程合成器线程: 触发 Scroll/Transform 动画与分块调度
        |
        v
   [ 2. Renderer 提交 CompositorFrame ] (通常在下一个 VSYNC 到来前提交)
        |
        v
   [ 3. Viz 消费并执行 SurfaceAggregation 与 GPU Draw ]
        |
        v
   [ 4. SwapBuffers / Present ] (翻转前后显存缓冲区 Front/Back Buffers)
        |
        v
   [ 5. 操作系统显示控制器在下一个 VSYNC 扫描沿将新帧输出至物理 OLED/LCD 点阵 ]
        |
        v
   [ 6. 产生 Presentation Feedback 时间戳 ] (精确标记 LCP 终点与输入延迟 INP)

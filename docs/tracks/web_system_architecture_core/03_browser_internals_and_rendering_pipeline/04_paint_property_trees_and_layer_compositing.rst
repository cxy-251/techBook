========================================================================
Chapter 15: 绘制流水线、属性树构建与硬件加速图层合成：从 DisplayItem 到 Property Trees 与 Compositor 架构
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了布局引擎（Layout Pipeline）如何从 DOM 与 `ComputedStyle` 派生 `LayoutTree`、Blink LayoutNG 不可变 `PhysicalFragment` 树架构、盒模型空间计算、外边距折叠代数方程、BFC/IFC 格式化上下文以及 Flexbox 与 CSS Grid 的多轮空间求解算法。当布局流水线精确求解出页面中所有可见元素的绝对几何包围盒 $(x, y, w, h)$ 后，渲染引擎并不能直接将像素发射到屏幕上。从几何数据到物理像素呈现，必须经过**绘制（Paint）**、**属性树构建（Property Trees Construction）**以及**合成（Compositing）**三大核心阶段。本章将深入 Chromium Blink 内核的 `CompositeAfterPaint` (CAP) 架构，系统剖析从 Layout 碎片到 `DisplayItemList` 的绘制指令记录过程、CSS 2.1 附录 E 的七级层叠上下文绘制顺序、Transform/Clip/Effect/Scroll 四大属性树解耦架构、硬件加速图层提升与层爆炸规避机制，以及合成器线程（Compositor Thread）如何完全绕过 JavaScript 主线程实现 120Hz 丝滑滚动与硬件动画。

15.1 绘制流水线微架构与 DisplayItemList 构建
------------------------------------------------------------------------

在现代浏览器中，**绘制（Paint）阶段的核心职责不是直接生成位图（Bitmap），而是记录一份结构化的“矢量绘图指令序列”（Display List）**。

布局几何 vs 绘制指令集
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

布局阶段确定了元素“**在何处有多大**”（Where & What Size），而绘制阶段确定了元素“**先画什么、后画什么、以何种样式绘制**”（Order, Styling & Vector Operations）。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Blink 绘制流水线核心数据结构演进                    |
   +-------------------------------------------------------------------------+

   [ 1. 遍历 LayoutObject 树 (按层叠上下文顺序) ]
        |
        v
   [ 2. 生成原子 DisplayItem 序列 ]
        |  * DrawRect(Background, Color)
        |  * DrawBorder(BorderBox, Style)
        |  * DrawTextBlob(Glyphs, Font, Offset)
        |  * DrawImage(Texture, SourceRect, DestRect)
        v
   [ 3. 聚合为不可变 PaintRecord (底层基于 Skia PaintOpBuffer) ]
        |  * 记录每个 PaintChunk 的属性树状态 (Property Tree State)
        v
   [ 4. 交付给合成器流水线 (cc::LayerTreeHost) 进行光栅化调度 ]

层叠上下文 (Stacking Context) 与 CSS 2.1 七级绘制顺序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

根据 CSS 2.1 规范附录 E，同一个层叠上下文内部的所有子元素，必须严格按照自后向前的**七级绘制顺序（7-Layer Stacking Order）**依序记录进 `DisplayItemList` 中，以保证正确的视觉遮挡关系：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  同一个层叠上下文内部的 7 级标准绘制顺序                |
   +-------------------------------------------------------------------------+

   [ 视线方向：从屏幕最底层 (Back) 向最顶层 (Front) 依序绘制 ]

   1. 最底层 (Back)  ---> 根元素或当前层叠上下文容器的【背景与边框】(Background & Borders)
   2. 负层叠层       ---> 带有【负 z-index】的子层叠上下文节点 (按 z-index 升序排列)
   3. 块级流节点     ---> 参与普通文档流的【非行内、非定位块级子元素】(In-Flow Block-level)
   4. 浮动流节点     ---> 所有【非定位浮动元素】(Float Boxes)
   5. 行内流节点     ---> 参与普通流的【行内级元素与纯文本节点】(In-Flow Inline-level & Text)
   6. 零/默认层叠层  ---> 【z-index: auto】与【z-index: 0】的定位元素 (Positioned Elements)
   7. 最顶层 (Front) ---> 带有【正 z-index】的子层叠上下文节点 (按 z-index 升序排列)

.. list-table:: 现代 CSS 中显式触发创建独立层叠上下文的属性矩阵
   :widths: 30 70
   :header-rows: 1
   :class: tight-table

   * - 触发属性类别
     - 具体声明组合
   * - **根元素**
     - 文档根节点 `<html>`
   * - **定位与层级**
     - `position: absolute / relative` 配合 `z-index` 非 `auto`；`position: fixed / sticky`
   * - **弹性与网格容器子项**
     - Flex / Grid 容器的直接子元素且 `z-index` 非 `auto`
   * - **不透明度与混合模式**
     - `opacity` 小于 1.0；`mix-blend-mode` 非 `normal`
   * - **变换、滤镜与透视**
     - `transform`, `filter`, `perspective`, `backdrop-filter`, `clip-path`, `mask` 声明非 `none`
   * - **隔离属性 (现代推荐)**
     - `isolation: isolate`（专为显式无副作用创建层叠上下文设计）
   * - **硬件意图提示**
     - `will-change` 指定了上述任一创建层叠上下文的属性

15.2 现代属性树架构 (Property Trees) 解耦革命
------------------------------------------------------------------------

在早期的浏览器内核（如 2015 年前的 WebKit / Blink）中，绘制与合成直接遍历 `LayoutObject` 树或 `GraphicsLayer` 树。如果一个父容器发生矩阵变换（`transform: rotate(45deg)`）或滚动（`scroll`），引擎必须以递归的方式遍历其所有的子节点，重新计算每个子节点在屏幕上的绝对几何坐标并执行重绘。

这种深度耦合树结构带来了两大致命缺陷：
1. **深层 DOM 遍历开销**：当页面包含数千个子节点时，滚动一次需要消耗数十毫秒 CPU 时间，严重阻塞主线程；
2. **状态共享与剪裁计算爆炸**：多层级嵌套的 `overflow: hidden` 与 3D 变换相互交织，坐标空间转换矩阵在深层节点上极易发生浮点累积误差。

四大独立属性树 (Property Trees) 拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了从根本上解决上述问题，Chromium 引入了**属性树（Property Trees）**架构，将与空间变换和视觉特效相关的状态从 DOM/Layout 树中完全剥离，构建了四棵高度扁平、正交解耦的专用属性树：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   Chromium Blink 四大独立属性树拓扑模型                 |
   +-------------------------------------------------------------------------+

   [ 1. Transform Tree (变换树) ]
   * 管理所有平移、缩放、3D 旋转、透视矩阵 (4x4 齐次变换矩阵) 以及 2D 滚动偏移基准。
   * 每个节点仅记录其相对于父 Transform 节点的局部矩阵 (Local Matrix)。

   [ 2. Clip Tree (剪裁树) ]
   * 管理 overflow: hidden/clip, clip-path, border-radius 圆角剪裁矩形。
   * 记录每个剪裁区域关联的 Transform ID，实现剪裁框随变换自动联动。

   [ 3. Effect Tree (特效树) ]
   * 管理 opacity 不透明度, filter 滤镜, mix-blend-mode 混合模式, mask 遮罩与 render surface。
   * 记录特效发生的起点与终点节点，指导合成器分配离屏渲染表面 (RenderSurface)。

   [ 4. Scroll Tree (滚动树) ]
   * 管理所有可滚动容器的当前滚动偏移量 (Scroll Offset Delta)、滚动边界与超折叠弹簧属性。

属性节点 ID 绑定与 PaintChunk 解耦
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在属性树架构下，绘制流水线生成的每一个绘制块（`PaintChunk`）不再持有复杂的绝对矩阵，而仅仅持有四个轻量级的整数索引：

.. math::

   	ext{PaintChunkState} = \langle 	ext{TransformNodeID}, 	ext{ClipNodeID}, 	ext{EffectNodeID}, 	ext{ScrollNodeID} \rangle

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PaintChunk 与属性树节点关联模型                     |
   +-------------------------------------------------------------------------+

   [ PaintChunk 1: 侧边栏按钮 ] ---> State: <Transform#2, Clip#1, Effect#1, Scroll#0>
   [ PaintChunk 2: 滚动内容卡片 ] -> State: <Transform#4, Clip#2, Effect#1, Scroll#1>

- **零重绘滚动与动画（Zero-Repaint Animation）**：当用户在页面上滑动滚轮时，**主线程完全不需要重新执行 Paint 流水线**！合成器线程只需直接修改 `Scroll Tree` 对应节点的 `offset.y`，或修改 `Transform Tree` 对应节点的矩阵，GPU 在光栅化与图层绘制阶段自动级联计算出最新的屏幕映射。

15.3 图层提升 (Layer Promotion) 与合成图层分配
------------------------------------------------------------------------

为了实现硬件加速渲染，浏览器必须将页面的 `DisplayList` 划分并组装为若干个独立的**合成图层（Composited Layers / `cc::Layer`）**。每个合成图层拥有独立的 GPU 纹理显存备份。

显式图层提升条件 (Explicit Layer Promotion)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个元素具备以下特征时，渲染引擎会为其单独分配一个独立的合成图层：

1. **硬件加速动画声明**：正在执行 `transform` 或 `opacity` 的 CSS 动画 / Web Animations，或声明了 `will-change: transform / opacity`；
2. **专用硬件渲染上下文**：包含硬件加速的 `<video>` 视频解码流、WebGL / WebGPU `<canvas>` 上下文；
3. **硬件级视口隔离**：使用了特定 3D 渲染上下文（`transform: translateZ(0)` / `perspective`）；
4. **后台独立加速滤镜**：声明了昂贵的 `backdrop-filter` 磨砂玻璃特效（需要捕获图层背后的合成内容）。

隐式图层提升与层重叠爆炸 (Layer Explosion) 危机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个普通元素在 Z 轴视觉空间上，覆盖在一个已被提升为独立合成图层的元素上方时，为了维持正确的图层遮挡关系，浏览器**被迫将该普通元素及其上方所有的兄弟元素全部提升为合成图层**。这一机制称为**隐式重叠提升（Overlap Promotion）**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     隐式重叠提升引发的图层爆炸 (Layer Explosion)        |
   +-------------------------------------------------------------------------+

   [ 页面结构: 1 个底层动画弹窗 + 1000 个普通列表项 ]

   [ 元素 A (底层): will-change: transform ] ----------> 提升为 Composited Layer #1 (GPU 纹理)
        |
        v (视觉重叠覆盖)
   [ 元素 B_1 ~ B_1000 (位于 A 上方的列表项) ]
        |
        +---> 触发 Overlap 判定！浏览器被迫将 1000 个列表项全部提升为独立图层！
        |
        v
   [ 结果: 产生 1001 个独立的 GPU 显存纹理！]
   * 显存暴增: 1000 * (1080 * 100 * 4B) ≈ 432 MB VRAM!
   * 崩溃现象: 移动端瞬间触发 OOM 强杀，页面掉帧卡死！

Blink CompositeAfterPaint (CAP) 智能图层合并 (Squashing)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了根除隐式提升引发的图层爆炸，现代 Blink 内核实现了 **CompositeAfterPaint (CAP)** 架构：
1. **绘制先行（Paint First）**：主线程首先完成全页面的 `DisplayItemList` 与属性树构建；
2. **图层智能聚类（Layer Clustering & Squashing）**：合成分配器扫描所有 `PaintChunk`，将拥有相同或相近属性树状态的多个相邻 `PaintChunk` **压实合并（Squash）到同一个合成图层中**，仅在确实需要独立动画或绝对隔离时才开辟新图层，将全页图层数量严格压制在个位数。

15.4 合成器线程架构与 Off-Main-Thread 执行模型
------------------------------------------------------------------------

现代浏览器渲染引擎的性能核心，在于实现了 **主线程（Main Thread）** 与 **合成器线程（Compositor Thread）** 的完全并发解耦：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    主线程与合成器线程双缓冲解耦执行拓扑                 |
   +-------------------------------------------------------------------------+

   [ 渲染进程: 主线程 (Main Thread) ]           [ 渲染进程: 合成器线程 (Compositor Thread) ]
   +------------------------------+             +---------------------------------------+
   | JavaScript 执行 (V8 引擎)    |             | 接收操作系统垂直同步信号 (VSYNC)      |
   | DOM 树 / Style / Layout 计算 |             | 接收用户高频触控/滚轮输入事件         |
   | 生成 PaintRecord 与属性树    |             |                                       |
   |                              |             |                                       |
   | LayerTreeHost (主线程图层树) |             | LayerTreeHostImpl (合成器图层树镜像)  |
   +------------------------------+             +---------------------------------------+
                 |                                                  |
                 +================== Commit 阶段 ===================+
                 |  * 主线程阻塞微秒级时间，将图层数据与属性树镜像拷贝  |
                 |  * 一旦 Commit 完毕，主线程立即释放，继续执行 JS!  |
                 v                                                  v
   [ 主线程继续响应重业务逻辑... ]               [ 合成器线程独立调度: ]
                                                |  1. 更新 Transform / Scroll 矩阵
                                                |  2. 计算图层可见性与分块 (Tiling)
                                                |  3. 分发光栅化任务 (Raster Tasks)
                                                v
                                         [ 发送 DrawQuad 指令至 GPU 进程 Viz 组件 ]

Compositor-Driven 硬件动画的极致流畅性
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个动画仅修改 `transform` 或 `opacity` 时：
1. 主线程在动画启动时完成图层提升，将动画关键帧曲线与目标属性树节点提交给合成器线程；
2. **在随后的动画执行全过程中，主线程处于 100% 空闲状态**！即使此时主线程正在执行一个耗时 5 秒的复杂 JS 死循环，**合成器线程依然能以稳定的 120Hz/60Hz 帧率，在每个 VSYNC 周期独立计算插值并驱动 GPU 渲染**，用户感知不到任何掉帧。

非被动事件监听器 (Non-Passive Listeners) 对快速滚动的阻塞
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

合成器线程能够独立处理页面滚动的物理路径称为 **Fast-Path Scrolling**。然而，若页面注册了监听滚动的事件处理函数：

.. code-block:: javascript

   // 默认模式 (passive: false)
   window.addEventListener('touchstart', function(e) {
       if (someCondition) {
           e.preventDefault(); // 阻断默认滚动！
       }
   });

- **卡顿成因**：由于合成器线程无法预知 JS 是否会调用 `e.preventDefault()` 阻止滚动，在每次触控发生时，**合成器线程必须被强制挂起，等待主线程空闲并执行完 JS 回调后，才能决定是否启动滚动**！若主线程卡顿，滚动交互将出现严重的触控迟滞。
- **现代工程解决方案**：显式声明 `{ passive: true }`，向合成器做出不可撤销的契约保证（承诺绝不调用 `preventDefault`），允许合成器线程零等待立即启动 Fast-Path 滚动：

.. code-block:: javascript

   // 现代高性能滚动契约
   window.addEventListener('touchstart', onTouchStart, { passive: true });

小结与下章导读
------------------------------------------------------------------------

本章从底层指令与多线程拓扑出发，系统解构了从 `LayoutTree` 到 `DisplayItemList` 的绘制记录流程、CSS 2.1 附录 E 的七级层叠上下文顺序、Transform/Clip/Effect/Scroll 四大属性树如何彻底消除深层重绘、合成图层提升条件与 CAP 压实合并防层爆炸机制，以及合成器线程通过 `LayerTreeHostImpl` 镜像实现与主线程解耦的 120Hz 硬件加速执行模型。

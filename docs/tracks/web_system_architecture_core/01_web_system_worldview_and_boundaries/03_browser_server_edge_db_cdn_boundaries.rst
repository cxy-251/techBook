========================================================================
Chapter 3: 核心执行边界拓扑：浏览器、源服务器、边缘计算、持久化数据库与 CDN 缓存
========================================================================

.. note:: 前置背景与认知承接
   前两章确立了现代 Web 的系统集成表面与架构演进历程。在多执行区流式系统中，各大边界并非抽象的概念划分，而是由真实的物理硬件、进程沙箱、通信协议与数据一致性协议所定义的硬性边界。本章将对浏览器客户端、CDN 边缘缓存、Edge 运行时、源服务器（Origin Server）与持久化数据库五大核心执行边界进行深度拓扑剖析，解构各边界的运行时模型、跨边界协议契约、安全信任阶梯与数据流转物理开销。

------------------------------------------------------------------------
3.1 五大核心执行边界的微架构与隔离拓扑
------------------------------------------------------------------------

在现代 Web 基础设施中，一次用户交互的生命周期跨越了物理空间与计算模型截然不同的五大执行边界：

.. list-table:: 现代 Web 五大核心执行边界微架构与系统属性矩阵
   :widths: 18 20 20 22 20
   :header-rows: 1
   :class: tight-table

   * - 执行边界
     - 物理宿主与运行时
     - 内存与进程隔离模型
     - 冷启动时延 (Cold Start)
     - 典型系统能力与限制
   * - 1. 浏览器客户端 (Browser)
     - 用户本地终端 / V8 / WebKit
     - 多进程沙箱 (Site Isolation)
     - 0 ms (常驻本地进程)
     - 具有完整 DOM/GPU 能力；完全不可信，禁止直连数据库
   * - 2. CDN 边缘缓存 (CDN Cache)
     - 全球 Anycast PoP 节点 / Nginx / Varnish
     - 内存 + SSD 分层存储缓存池
     - 0 ms (静态常驻代理)
     - 仅支持基于 HTTP 规范（RFC 9111）的只读响应缓存与压缩
   * - 3. 边缘计算运行时 (Edge Runtime)
     - Cloudflare Workers / Vercel Edge / Deno
     - 轻量级 V8 Isolate 沙箱隔离
     - 0 ~ 5 ms (极速快照恢复)
     - 支持标准 Web APIs；无持久化本地磁盘，受限单次 CPU 时间 (50ms)
   * - 4. 集中式源服务器 (Origin Server)
     - 区域数据中心 / Linux 容器 / Node.js / Go
     - 独立 OS 进程与容器命名空间
     - 200 ~ 2000 ms (容器启动)
     - 完整 POSIX 系统调用、私有网络访问、持有长期数据库连接池
   * - 5. 持久化数据边界 (Database)
     - PostgreSQL / MySQL / Redis / NVMe 阵列
     - 数据库服务进程、内存缓冲池 (Buffer Pool)
     - 0 ms (常驻服务)
     - ACID 强一致性事务保证、行级锁/表级锁并发控制、WAL 日志持久化

3.2 跨边界通信协议与序列化成本模型
------------------------------------------------------------------------

当数据跨越不同的执行边界时，必须通过网络协议栈进行传输，并经历数据结构的序列化与反序列化（SerDe）。

跨边界传输协议矩阵
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       现代 Web 跨边界网络通信拓扑                       |
   +-------------------------------------------------------------------------+

   [ 浏览器客户端 (Browser) ]
        |
        | 协议: HTTP/3 (QUIC/UDP) / HTTP/2 (TLS 1.3)
        | 数据: HTML Stream / JSON / RSC Wire Format
        v
   [ CDN 边缘节点 (PoP / Edge Anycast) ]
        |
        | 协议: HTTP/2 多路复用长连接池
        | 数据: 标准 HTTP Request / Response Headers
        v
   [ 边缘计算 (Edge Worker) ]
        |
        | 协议: gRPC over HTTP/2 / 双向流 / 专有 TCP
        | 数据: Protocol Buffers / 紧凑二进制格式
        v
   [ 集中式源服务器 (Origin Server - Node.js/Go) ]
        |
        | 协议: PostgreSQL 专有二进制协议 / Redis RESP 协议
        | 数据: TCP 套接字原生字节流
        v
   [ 核心数据库集群 (Database / Cache) ]

序列化格式的物理性能开销
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在服务端渲染与流式水合过程中，序列化开销往往占据了服务端的相当比例的 CPU 时间：

1. **JSON 格式**：虽然人类可读且与 JavaScript 原生兼容，但其冗余的键名重复、浮点数文本化转换及字符串转义会带来显著的 CPU 解析与带宽膨胀开销。
2. **React Server Components (RSC) Wire Format**：采用基于行（Line-by-line）的流式 JSON 扩展语法，以组件树引用的形式流式下发 UI 节点与数据插槽，允许客户端在数据尚未完全抵达前即开始并行解析渲染。
3. **Protocol Buffers / FlatBuffers**：在 Edge 与 Origin Server 的微服务内部 RPC 中，采用二进制模式，支持零拷贝（Zero-Copy）反序列化，极大降低垃圾回收（GC）压力。

3.3 安全信任阶梯与防御深度 (Defense-in-Depth)
------------------------------------------------------------------------

现代 Web 架构必须贯彻**纵深防御（Defense-in-Depth）**原则，依据各边界的信任等级设置严格的防护关卡：

.. list-table:: 跨边界安全信任阶梯与防护策略
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 边界跃迁路径
     - 潜在攻击与安全威胁
     - 核心防护机制与契约
   * - Browser $	o$ CDN/Edge
     - 恶意脚本注入 (XSS)、CSRF 伪造、DDoS 洪水
     - CSP 策略、SameSite 严格 Cookie、WAF 规则清洗、IP 速率限制
   * - Edge $	o$ Origin Server
     - 凭据伪造、鉴权绕过、重放攻击
     - JWT 边缘快速验签、非对称公钥校验、mTLS 双向认证
   * - Origin $	o$ Database
     - SQL 注入、越权读写、死锁挂起
     - 参数化查询预编译 (Prepared Statements)、最小权限 DB 账号、连接池隔离

3.4 数据引力与多级缓存穿透拓扑
------------------------------------------------------------------------

**数据引力（Data Gravity）**是分布式系统的核心物理规律：海量用户数据与事务状态由于体积庞大且具备强一致性要求，天然沉淀在核心数据中心内，无法随意向全球边缘节点完整复制。

读路径的多级缓存金字塔 (Read Path)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了在数据引力的约束下实现全球低延迟访问，读操作通过 6 级缓存金字塔进行逐层分流：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       现代 Web 六级读缓存穿透拓扑                       |
   +-------------------------------------------------------------------------+

   [ 用户请求发起 ]
        |
        v
   1. [ 浏览器内存/磁盘缓存 (Memory Cache & HTTP Disk Cache) ]
        | (Cache Miss)
        v
   2. [ Service Worker 离线缓存 (Cache Storage API) ]
        | (Cache Miss)
        v
   3. [ 全球 CDN 边缘节点缓存 (Edge HTTP Cache - RFC 9111) ]
        | (Cache Miss)
        v
   4. [ 边缘键值存储 (Edge KV / Global Stale-While-Revalidate) ]
        | (Cache Miss)
        v
   5. [ 源站集中式缓存 (Redis / Memcached In-Memory Cluster) ]
        | (Cache Miss)
        v
   6. [ 数据库物理存储 (PostgreSQL Buffer Pool & NVMe Disk) ]

写路径与精准缓存失效 (Write Path & Invalidation)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

数据写入（如用户下单扣减库存）必须直穿所有缓存层，直达数据库核心事务引擎。写操作完成后，系统必须面临经典难题——**分布式缓存失效（Cache Invalidation）**：

- **基于标签的显式失效 (Tag-Based Invalidation)**：页面渲染时向 CDN 注入 `Cache-Tag: product-101` 响应头。当数据库数据更新后，服务端向 CDN 调度接口发送 Purge 请求，原子化废弃全球边缘节点上的相关缓存块。
- **Stale-While-Revalidate 异步重验**：允许 CDN 在后台异步请求源站更新数据的同时，先行向客户端返回旧缓存（Stale Data），兼顾极致延迟与最终一致性。

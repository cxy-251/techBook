========================================================================
Chapter 2: Web 架构边界演进：从两端请求响应到 Browser/Server/Edge/DB 多执行区协同
========================================================================

.. note:: 前置背景与认知承接
   第一章确立了现代 Web 的六大执行区全景与“路径、边界、状态、故障”分析范式。本章将沿时间与系统复杂度轴线，系统解构 Web 架构的三次重大范式跃迁：从经典客户端-服务器两端请求响应模型，到前后端分离的 SPA/RESTful 架构，再到当代围绕 Browser/Edge/Server/DB 构建的多执行区分布式流式系统。通过对比各时代的计算重心位移与状态所有权迁移，揭示现代架构演进的底层物理推力与工程妥协。

------------------------------------------------------------------------
2.1 经典两端模型：请求-响应与集中式服务端渲染 (Classic Client-Server SSR)
------------------------------------------------------------------------

在 Web 发展的早期与成熟期（以 LAMP、Java EE Servlet/JSP、Ruby on Rails、Django 为代表），整个系统的物理拓扑严格收敛于简单的**客户端-源服务器两端模型**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       经典两端请求-响应架构拓扑                         |
   +-------------------------------------------------------------------------+

   [ 浏览器 (Thin Client) ]                       [ 集中式源服务器 (Origin Server) ]
          |                                                       |
          | --- 1. HTTP GET /products/101 ----------------------> |
          |                                                       | 2. 鉴权与 Session 解析
          |                                                       | 3. 查询本地/内网数据库
          |                                                       | 4. 模板引擎拼接生成完整 HTML
          | <--- 5. HTTP 200 OK (完整 HTML 文本流) ---------------- |
          |                                                       |
   6. 解析 DOM 树并呈现                                           |
   7. 用户点击链接或提交表单                                      |
          | --- 8. HTTP POST /orders (Form Submit) -------------> | (触发全页重新加载)

经典两端模型的系统特性与边界特征
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **瘦客户端假设（Thin Client）**：浏览器仅作为排版与渲染终端，本地仅运行极其轻量的脚本（如表单前端验证或简单的 DOM 特效），不承担任何业务状态管理与路由决策。
2. **绝对集中的安全信任边界**：所有业务逻辑、数据库查询、密钥凭证与会话状态（Session State）完全封闭在数据中心内网。向外暴露的仅是经过渲染后的无状态 HTML 页面。
3. **架构优势与物理瓶颈**：
   - **优势**：首屏渲染极其迅速且无客户端 JavaScript 编译开销；SEO 友好；安全模型简单直观。
   - **瓶颈**：每一次交互均伴随全页重新加载（Full Page Reload），引发明显的白屏闪烁；当用户与源服务器相隔数千公里时，跨洋网络延迟（RTT > 200ms）导致每一次点击的等待时间被急剧放大。

------------------------------------------------------------------------
2.2 前后端分离与单页应用 (SPA)：客户端运行时的边界膨胀
------------------------------------------------------------------------

随着 2005 年 Ajax 技术的普及以及 2010 年后现代 JavaScript 框架（Backbone, Angular, React, Vue）的爆发，Web 架构发生了深刻的“**计算重心大迁移**”——前后端分离与单页应用（Single Page Application - SPA）成为工业界主流。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       前后端分离单页应用 (SPA) 架构拓扑                  |
   +-------------------------------------------------------------------------+

   [ 浏览器 (Rich Client Runtime) ]              [ API 网关 / 微服务集群 ]
          |                                                       |
          | --- 1. 静态请求 index.html (空壳) -----------------> [ CDN / 静态存储 ]
          | <--- 2. 返回包含 <div id="root"></div> 的 HTML ------- |
          | --- 3. 下载大型 app.bundle.js (数 MB) -------------> |
          | <--- 4. 返回完整客户端应用代码 ---------------------- |
          |                                                       |
   5. 客户端 V8 执行 JS 初始化应用                                |
   6. 挂载客户端路由器 (History API)                              |
          |                                                       |
          | --- 7. 发起异步数据请求: GET /api/v1/user ----------> |
          | <--- 8. 返回纯结构化 JSON 数据 ---------------------- | 9. 数据库查询与业务校验
          |                                                       |
   10. 客户端在内存构建 Virtual DOM 并局部更新真实 DOM

计算重心外移带来的得失权衡
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **架构收益**：
  - 实现了无刷新的流畅局部交互，页面切换仅涉及细粒度数据请求；
  - 实现了前后端团队的完全解耦：前端工程化聚焦于 UI 组件树与交互状态机，后端聚焦于领域模型与微服务 API。
- **暴露的新系统性痛点**：
  - **首屏白屏时间（FP / FCP）恶化**：浏览器必须串行完成“下载 HTML → 下载大体积 JS Bundle → V8 解析与 JIT 编译 → 发起异步 API 请求 → 接收 JSON → 客户端生成 DOM”的超长瀑布流链条。
  - **客户端硬件资源过载**：移动端低端设备在执行数百 KB 至数 MB 的 JS 代码时，主线程长时间被占用（Long Tasks），导致交互响应严重卡顿（INP 劣化），并加剧电量消耗。
  - **SEO 索引困境**：搜索引擎爬虫无法可靠执行复杂的客户端异步渲染逻辑，导致公共 Web 内容的发现能力大幅下降。

2.3 边缘计算与分布式多执行区的兴起 (The Edge & Multi-Zone Era)
------------------------------------------------------------------------

为了解决 SPA 客户端臃肿与经典两端 SSR 延迟过高的固有矛盾，现代 Web 架构引入了**边缘计算（Edge Computing）与多执行区协同模型**。

光速物理极限与边缘节点价值
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

光在光纤中的传播速度约为 $2 	imes 10^8 	ext{ m/s}$。从伦敦到加利福尼亚的数据往返，仅纯物理传输耗时就超过 70ms，叠加骨干网路由器排队与 TLS 握手，一次跨境 HTTP 请求的端到端时延通常在 150~300ms。

边缘计算将执行环境直接部署在全球数百个 Anycast CDN 边缘节点（Point of Presence - PoP）上，将用户与计算环境的距离缩短至 5~20ms：

.. list-table:: 传统 Node.js 服务端与现代 Edge Runtime 微架构对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 系统微架构维度
     - 区域源服务器 (Node.js / Docker 容器)
     - 现代边缘运行时 (V8 Isolates / Edge Workers)
   * - 进程与内存模型
     - 独立操作系统进程或容器，内存占用 30MB~500MB
     - 单进程内轻量级 V8 Isolate 隔离，内存占用 < 5MB
   * - 冷启动延迟 (Cold Start)
     - 200 ms ~ 2000 ms (容器拉起与运行时初始化)
     - 0 ms ~ 5 ms (Isolate 快照恢复与即时编译)
   * - 系统能力与 API 范围
     - 完整 POSIX API (文件系统 `fs`, 原始套接字 `net`)
     - 严格受限的标准 Web APIs (`Fetch`, `Streams`, `Crypto`)
   * - 地理分布与扩展性
     - 单一或少数几个区域数据中心 (如 us-east-1)
     - 全球数百个 PoP 节点自动按就近流量弹性分发

2.4 计算重心与状态所有权演进矩阵
------------------------------------------------------------------------

纵观 Web 架构的四次主要演进阶段，计算重心、渲染位置与状态所有权发生了持续的再平衡：

.. list-table:: Web 四大架构范式系统核心属性全景对比
   :widths: 16 20 20 22 22
   :header-rows: 1
   :class: tight-table

   * - 架构范式
     - 路由控制权
     - 渲染执行区
     - 状态事实源 (State Ownership)
     - 数据流与传输协议
   * - 1. 经典两端 SSR
     - 完全由服务端路由表控制
     - 源服务器单体进程
     - 服务端集中式 Session / DB
     - 完整 HTML 文本流，全页重载
   * - 2. 纯客户端 SPA
     - 浏览器客户端路由 (History API)
     - 客户端主线程 V8
     - 客户端内存 Store (Redux/Zustand)
     - 无状态 JSON API / GraphQL
   * - 3. 同构混合 SSR/SSG
     - 前端框架统一双端路由
     - Node.js 预渲染 + 客户端全量水合
     - 双端状态快照同步 (`__INITIAL_STATE__`)
     - HTML 骨架 + 大体积 Client Bundle
   * - 4. 现代多执行区流式全栈
     - 细粒度分层路由 (Edge / Server)
     - Edge / Server 组件级流式渲染 + 局部水合
     - 分布式状态：Edge 凭据 + Server 数据库 + Client 交互
     - HTTP/3 流式分块传输 (RSC Payload / HTML Stream)

2.5 现代全栈架构演进的底层物理推力与工程权衡
------------------------------------------------------------------------

驱动 Web 系统架构不断演进与重构的根本动力，源自三大约束力量的持续博弈：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       现代 Web 架构三大约束力量博弈                     |
   +-------------------------------------------------------------------------+
        |
        +---> 1. 光速与网络往返物理上限 (Speed of Light & Network RTT)
        |        * 要求：首字节响应与轻量逻辑必须尽可能靠近用户边缘 (Edge)
        |
        +---> 2. 终端设备算力与电量方差 (Client Device Diversity & Battery)
        |        * 要求：剥离客户端多余 JavaScript 代码，将重型渲染回收至云端
        |
        +---> 3. 数据引力与数据合规性 (Data Gravity & Privacy Governance)
                 * 要求：核心持久化数据无法全量搬运至边缘，必须留在合规数据中心

现代 Web 架构的“不可能三角”
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在实际架构设计中，工程团队必须在以下三个维度中进行权衡取舍：

1. **极致首屏呈现速度（Zero-JS Initial Paint）**：通过服务端与边缘流式渲染实现毫秒级首屏展现；
2. **富客户端即时交互响应（Rich Client Interactivity）**：通过局部客户端运行时保障无刷新的复杂交互体验；
3. **低运维与心智复杂度（Low Architectural Complexity）**：控制跨执行区代码调试、状态同步与分布式缓存失效的工程复杂度。

现代全栈架构（如 React Server Components、Qwik 可恢复性水合、Astro 孤岛架构）正是工业界在上述物理约束下探索出的最新系统级平衡点。

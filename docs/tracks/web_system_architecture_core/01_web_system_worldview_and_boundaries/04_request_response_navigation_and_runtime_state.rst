========================================================================
Chapter 4: 请求语义、导航生命周期与分布式运行时状态
========================================================================

.. note:: 前置背景与认知承接
   前三章系统解构了现代 Web 的集成表面、架构演进路径以及五大执行边界微架构。在静态的系统拓扑之上，Web 系统的动态本质是一套围绕“状态（State）”的分布式状态机流转系统。本章将深入解构 HTTP 请求响应的严格语义、浏览器导航生命周期全流程（从 URL 解析、DNS/TCP/TLS 握手、Document Commit 到 BFCache 冻结），并全面剖析运行时状态（Runtime State）在 URL、DOM、客户端 Store、Cookie、Session 与数据库中的物理分布与同步模型。

------------------------------------------------------------------------
4.1 HTTP 请求响应的系统语义与协议契约
------------------------------------------------------------------------

HTTP 协议不仅是一套数据传输格式，更是定义了分布式系统中各节点行为预期与副作用（Side Effects）的契约系统。理解 HTTP 方法的严格代数属性是设计高可靠 Web 架构的前提。

安全度 (Safety) 与 幂等性 (Idempotency)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. list-table:: 核心 HTTP 方法的代数属性与系统副作用契约
   :widths: 15 15 15 30 25
   :header-rows: 1
   :class: tight-table

   * - HTTP 方法
     - 安全性 (Safe)
     - 幂等性 (Idempotent)
     - 核心系统语义
     - 默认缓存行为 (RFC 9111)
   * - `GET` / `HEAD`
     - 是
     - 是
     - 仅检索资源，绝对禁止对服务端状态产生业务副作用
     - 允许启发式或显式缓存
   * - `PUT`
     - 否
     - 是
     - 完整替换目标资源；多次执行结果与单次执行完全一致
     - 默认不可缓存，使关联 URI 缓存失效
   * - `DELETE`
     - 否
     - 是
     - 删除目标资源；连续多次调用服务端最终状态不变 (资源均不存在)
     - 默认不可缓存，使关联 URI 缓存失效
   * - `POST`
     - 否
     - 否
     - 提交数据处理；多次调用将创建多个从属实体或触发多次业务扣费
     - 仅在显式包含有效缓存控制头时允许
   * - `PATCH`
     - 否
     - 否
     - 对资源进行局部修改 (Partial Update)；运算可能包含增量累加
     - 默认不可缓存

状态码流转与条件验证机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

HTTP 状态码构成了浏览器与中间代理的决策分支基准：

- **304 Not Modified（条件请求协商）**：当浏览器发起带 `If-None-Match: "e3b0c442"` 或 `If-Modified-Since` 头部的验证请求时，若服务端判定资源未变，立即返回空的 304 响应，直接激活本地磁盘缓存，消除数据传输体积。
- **内容协商 (Content Negotiation)**：客户端通过 `Accept: text/html,application/xhtml+xml` 与 `Accept-Encoding: gzip, br, zstd` 声明解码能力，服务端根据客户端能力动态选择最高压缩比算法（如 Brotli 或 Zstandard）输出。

4.2 浏览器文档导航生命周期全流程剖析
------------------------------------------------------------------------

当用户在浏览器地址栏输入 URL 并按下回车，或者点击页面上的超链接时，浏览器内核将启动跨越多个系统进程的标准导航状态机：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  现代浏览器文档导航全生命周期时序拓扑                   |
   +-------------------------------------------------------------------------+

   [ 1. 触发导航 (Input / Click) ]
        |
        v
   [ 2. 检查当前文档 BeforeUnload 拦截 ]
        |
        v
   [ 3. Browser 主进程发起网络请求任务 -> IPC 通信 -> Network 网络进程 ]
        |
        +---> DNS 递归解析 (DNS Cache / DoH)
        +---> TCP 三次握手 + TLS 1.3 协商 (ALPN: h2/h3)
        +---> 发送 HTTP GET 请求并等待首字节 (TTFB)
        v
   [ 4. 接收响应头并进行安全与类型判定 (Response Assessment) ]
        |  * 校验 Content-Type 与 X-Content-Type-Options: nosniff
        |  * 处理 301/302/307/308 HTTP 重定向循环
        |  * 判定为 HTML 文档 (若为下载附件则移交下载管理器)
        v
   [ 5. 确定目标渲染进程 (Site Isolation / Process Allocation) ]
        |  * 若跨源 (Cross-Origin) 且未开启复用，创建全新的沙箱 Renderer 进程
        v
   [ 6. 提交导航 (Commit Navigation) ]
        |  * Network 进程将数据流通道直接转移给目标 Renderer 进程
        |  * 浏览器主进程更新地址栏 URL、安全小锁图标与前进/后退历史栈
        |  * 旧文档触发 Unload / PageHide 并移入 BFCache (往返缓存)
        v
   [ 7. 渲染进程流式解析与呈现 (Document Loading) ]
           * HTML Tokenizer 流式构建 DOM 树 -> 加载外部 CSS/JS -> 首次内容绘制 (FCP)

4.3 SPA 软导航 (Soft Navigation) vs 浏览器硬导航 (Hard Navigation)
------------------------------------------------------------------------

单页应用（SPA）与现代全栈流式框架对传统导航行为进行了重构，引入了“软导航”范式：

.. list-table:: 浏览器硬导航与客户端 SPA 软导航对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 导航机制维度
     - 浏览器原生硬导航 (Hard Navigation)
     - 客户端 SPA 软导航 (Soft Navigation)
   * - 触发与执行机制
     - 浏览器主进程重新发起网络请求，销毁或冻结当前渲染进程
     - 拦截链接点击事件，调用 `history.pushState()` 仅修改地址栏 URL
   * - 页面重载范围
     - 整个页面上下文、全局 JavaScript 堆内存与 DOM 树彻底重置
     - 保持当前 JavaScript 运行时，仅异步拉取数据并局部替换组件树
   * - 页面过渡感知
     - 伴随短暂的白屏与屏幕重绘闪烁
     - 无缝过渡，支持骨架屏（Skeleton）与自定义页面切换动画
   * - 固有工程风险
     - 每次导航需重新加载并编译整页 JS/CSS 资源
     - 易累积内存泄漏（未解绑事件/定时器）、滚动位置恢复异常与焦点陷阱

4.4 分布式运行时状态 (Runtime State) 的六层物理分布拓扑
------------------------------------------------------------------------

在现代全栈 Web 系统中，**状态（State）**并非孤立存在于某一行代码中，而是被分散固化在从用户视口到数据中心存储的六个物理层级中：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       现代 Web 六层分布式状态拓扑                       |
   +-------------------------------------------------------------------------+

   [ Layer 1: URL 状态 (URL Path / Query / Hash) ]
        * 唯一定位资源与视图过滤条件，天然具备跨设备分享与书签持久性
        * 存储形态: ?page=2&sort=desc#section-3 (字符串状态机)

   [ Layer 2: DOM 瞬态状态 (Ephemeral DOM State) ]
        * 文本框输入中内容、光标焦点、CSS 动画进行态、局部滚动偏移量
        * 存储形态: HTMLInputElement.value, Element.scrollTop (易失)

   [ Layer 3: 客户端内存状态 (Client Application Memory State) ]
        * 前端组件树状态、全局 Store (Redux, Zustand, Vuex)、内存缓存
        * 存储形态: JavaScript 堆内存对象 (刷新页面即归零)

   [ Layer 4: 客户端持久化存储 (Client Storage State) ]
        * 离线草稿、用户个性化偏好、大型数据集缓存
        * 存储形态: IndexedDB, LocalStorage, Cache Storage (受同源沙箱保护)

   [ Layer 5: 安全会话凭证状态 (Session & Credential State) ]
        * 用户登录身份标识、双因素认证令牌
        * 存储形态: HttpOnly SameSite Cookie, Encrypted JWT (网络请求自动携带)

   [ Layer 6: 服务端持久化状态 (Server Persistent State - Source of Truth) ]
        * 核心业务实体、订单记录、账户余额、库存事实
        * 存储形态: 关系型数据库 (PostgreSQL), 内存数据库 (Redis)

4.5 状态同步、竞态条件与数据一致性治理
------------------------------------------------------------------------

由于网络延迟的不确定性，多层状态之间的同步必然面临并发一致性与竞态挑战。

网络竞态条件 (Network Race Conditions) 与 AbortController 防御
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当用户在筛选面板中高频快速切换选项（例如连续点击“价格升序”和“销量优先”）时，由于网络传输的波动，先发起的请求可能后抵达客户端：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       网络竞态导致旧数据覆写最新状态                    |
   +-------------------------------------------------------------------------+

   时间线:
   T1: 用户点击 [价格升序] -> 发起 Request A (因网络拥堵耗时 800ms)
   T2: 用户点击 [销量优先] -> 发起 Request B (因快速命中 Edge 耗时 200ms)
   T3: Request B 响应抵达 -> 客户端渲染 [销量优先] 列表 (符合预期)
   T4: Request A 响应延迟抵达 -> 客户端错误覆写并渲染 [价格升序] 列表 (数据错乱！)

**标准防御范式**：利用 Web 标准的 `AbortController` 信号，在发起新请求时自动原子化取消未竟的旧请求：

.. code-block:: javascript

   let currentAbortController = null;

   async function fetchProducts(sortKey) {
       // 1. 若前序请求尚在进行，立即主动中断底层网络连接
       if (currentAbortController) {
           currentAbortController.abort();
       }
       currentAbortController = new AbortController();

       try {
           const response = await fetch(`/api/products?sort=${sortKey}`, {
               signal: currentAbortController.signal
           });
           const data = await response.json();
           renderProductList(data);
       } catch (err) {
           if (err.name === 'AbortError') {
               // 预期内的正常取消，静默忽略
               return;
           }
           showErrorToast(err);
       }
   }

乐观 UI 更新 (Optimistic UI Updates) 与事务回滚
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了消除网络 RTT 带来的交互迟钝感，现代 UI 采用乐观更新机制：

1. **瞬时状态突变**：用户点击“点赞”或“加购物车”时，客户端直接在 Layer 2/3 立即将状态更新为成功态，并播放动效；
2. **生成逆向补丁 (Rollback Patch)**：在发起异步请求的同时，将突变前的状态快照压入回滚栈；
3. **异常自动对齐**：若服务端最终返回 4xx/5xx 或网络超时，客户端依据回滚快照原子化恢复原始状态，并向用户弹出重试提示。

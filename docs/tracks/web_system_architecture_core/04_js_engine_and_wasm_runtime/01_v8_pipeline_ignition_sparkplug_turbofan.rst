18.1 现代 JavaScript 引擎分层执行 (Tiered Execution) 演进哲学
------------------------------------------------------------------------

JavaScript 虚拟机面临着两个在底层计算原理上完全相悖的工程诉求：
1. **极限启动速度（Fast Startup & Low Latency）**：用户在打开网页时，脚本必须立即进入可执行状态，任何冗长的预编译与全量代码静态分析都会直接推迟首屏可交互时间（TTI / FCP）；
2. **极限峰值吞吐（Peak Throughput & Sustained Performance）**：对于循环密集型、数学计算与框架 Diff 等高频热点代码，引擎必须生成高度向量化、寄存器分配最优的本地机器码（Native Machine Code），以应对海量数据处理。

V8 架构演进路线与分层执行全景
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了同时兼顾冷启动低延迟、低内存占用与高吞吐执行，V8 经历了从早期“双编译器架构”到现代“多层级协同分层执行体系（Multi-Tier Execution Pipeline）”的深刻演进：

18.2 源码扫描、词法语法分析与 AST 构建
------------------------------------------------------------------------

当浏览器主线程通过网络层接收到 JavaScript 脚本流（或从 Service Worker / Cache Storage 提取缓存）后，V8 引擎首先接管 UTF-8 / UTF-16 字符流。

词法扫描 (Scanning) 与 Token 流生成
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

扫描器（Scanner）是一个基于单字符前向预测的有限状态机。其核心职责是将无结构的连续字符流切割为离散的、强类型的语法记号（Tokens），并过滤空白字符与注释：

1. **Token 分类**：关键字（`function`, `const`, `return`）、标识符（变量名、函数名）、字面量（数字 `42`、字符串 `"web"`）、运算符（`+`, `===`, `=>`）与标点符号；
2. **源码位置记录**：为每个 Token 记录绝对字符偏移量（Character Offset），用于后续在抛出异常时生成高精度调用栈（Stack Trace）并支持 Source Map 源码映射。

语法解析 (Parsing) 的两级分流：Eager vs Lazy Parsing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于一个包含数万行代码的大型 Web 应用（如 10MB 的 Vendor Bundle），在首屏启动时往往只有 20%~30% 的函数会被立即执行，其余 70%+ 的代码仅在用户点击特定按钮、打开侧边栏或触发复杂业务时才会被调用。如果引擎在页面加载阶段强行对全量代码执行深度编译，将造成灾难性的 CPU 浪费与主线程卡顿。

为此，V8 实现了 **完整解析（Full Eager Parser）** 与 **预解析（Pre-parser / Lazy Parser）** 的精确分流：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  V8 预解析 (Pre-parser) 与全量解析流水线                |
   +-------------------------------------------------------------------------+

   源码顶层作用域代码 (Top-Level Code)
            |
            v
   [ Full Eager Parser (全量立即解析) ]
        * 行为: 构建完整抽象语法树 (AST) 与精准作用域树 (Scope Tree)
        * 产物: 立即送入 BytecodeGenerator 生成 Ignition 字节码并就绪执行
        * 遇到内部未调用的嵌套函数声明时: 拦截并移交 Pre-parser!
            |
            v
   [ Pre-parser (惰性快速扫描器) ]
        * 行为: 1. 仅校验最基本的语法合法性 (Syntax Error Detection)
        *       2. 扫描并记录变量声明与闭包引用 (Variable Allocation & Inner Scope)
        *       3. 绝对不构建 AST 节点! 不生成任何字节码! 内存开销降为 0!
        * 记录: 函数体在源码中的起止字节位置 (Start/End Position)
            |
            v (当用户点击按钮，首次调用该内部函数时)
   [ JIT 运行时按需唤醒 (JIT Wakeup) ]
        * 根据保存的位置指针，重新从源码切片调起 Full Parser 生成完整 AST 与 Bytecode!

作用域分析 (Scope Analysis) 与变量分配模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在构建 AST 的同时，Parser 必须完成变量在物理内存中的分配决策：
- **栈分配（Stack Allocation）**：对于仅在局部函数内使用、未被任何内部闭包捕获的局部变量，分配在虚拟机的执行栈槽位（Stack Slots / Registers）中，生命周期随函数返回瞬间被硬件栈指针销毁，访问速度极快；
- **堆分配（Context Allocation）**：若局部变量被内部嵌套函数引用（形成闭包 Closure），该变量必须被逃逸提升至 V8 堆上的 `Context` 对象中，确保外部函数执行完毕退栈后，闭包仍然能够通过堆指针持久化访问该变量。

18.3 Ignition 字节码解释器：基于累加器的虚拟寄存器机架构
------------------------------------------------------------------------

在 V8 早期版本中，Full-Codegen 编译器直接将 AST 编译为未经优化的本地机器码。由于机器码体积极其庞大（通常为源码体积的 5~10 倍），导致移动终端在加载多个标签页时极易遭遇内存溢出（OOM）。

Ignition 解释器的引入彻底重塑了 V8 的内存架构。Ignition 采用了一种**紧凑的、基于累加器（Accumulator Register, 简写为 ``a0`` 或 ``acc``）的虚拟寄存器机（Virtual Register Machine）**。

基于累加器架构的微设计优势
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

与基于纯栈模型（如 JVM / Python 虚拟机频繁进行 `push`/`pop`）以及基于三地址码多通用寄存器模型（如 LuaJIT）不同，基于隐式累加器的架构具有以下物理优势：
1. **指令长度极短**：绝大多数算术、逻辑与加载指令隐式以累加器作为源操作数或目标操作数，无需在字节码中显式编码额外的寄存器编号，大幅缩减字节码体积；
2. **硬件映射高效**：累加器可直接绑定到物理 CPU 的核心通用寄存器（如 x86-64 的 `rax` 或 ARM64 的 `x0`），消除大量的内存搬运指令。

实战字节码解构：从 JavaScript 源码到 Ignition 指令序列
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

考虑一段计算商品总价的典型高频函数：

.. code-block:: javascript

   function calculateTotal(items, taxRate) {
     let sum = 0;
     for (let i = 0; i < items.length; i++) {
       sum += items[i].price;
     }
     return sum * (1 + taxRate);
   }

通过 V8 调试标志 `--print-bytecode` 反编译该函数，Ignition 生成的紧凑字节码指令流如下：

.. code-block:: text

   [Generated Bytecode for function: calculateTotal]
   Parameter count 3 (this, items, taxRate)
   Register count 5 (r0: sum, r1: i, r2: items.length, r3: temp, r4: temp)

   // 1. let sum = 0;
   0x00 : LdaSmi [0]                 // 将小整数 0 加载至累加器 (acc = 0)
   0x02 : Star r0                    // 将累加器值写入局部寄存器 r0 (sum = acc)

   // 2. let i = 0;
   0x04 : LdaSmi [0]                 // acc = 0
   0x06 : Star r1                    // r1 = acc (i = 0)

   // 3. 循环条件判断: i < items.length
   0x08 : LdaNamedProperty a0, [0], [1] // 从参数 a0 (items) 读取命名属性 'length' 到 acc
                                        // 注: [0] 是常量池索引，[1] 是 Feedback Vector 槽位!
   0x0c : Star r2                    // r2 = items.length
   0x0e : Ldar r1                    // acc = r1 (加载 i)
   0x10 : TestLessThan r2, [3]       // 比较 acc (i) 与 r2 (length)，结果存入 acc，记录反馈槽位 [3]
   0x13 : JumpIfFalse [32]           // 若为 false，条件跳转至循环体外部 (偏移 0x33)

   // 4. 循环体: sum += items[i].price
   0x15 : LdaKeyedProperty a0, r1, [4]  // 读取 items[i] 对象到 acc，记录反馈槽位 [4]
   0x19 : Star r3                    // r3 = items[i]
   0x1b : GetNamedProperty r3, [1], [6] // 读取 r3.price 到 acc，记录反馈槽位 [6]
   0x1f : Add r0, [8]                // acc = acc + r0 (price + sum)，记录数值类型反馈槽位 [8]
   0x22 : Star r0                    // r0 = acc (更新 sum)

   // 5. 循环步进: i++
   0x24 : LdaSmi [1]                 // acc = 1
   0x26 : Add r1, [9]                // acc = acc + r1 (i + 1)
   0x29 : Star r1                    // r1 = acc (更新 i)
   0x2b : Jump [-37]                 // 无条件回跳至循环判断点 (偏移 0x08)

   // 6. return sum * (1 + taxRate);
   0x2d : LdaSmi [1]                 // acc = 1
   0x2f : Add a1, [10]               // acc = 1 + taxRate (参数 a1)
   0x32 : Mul r0, [11]               // acc = acc * r0 (计算最终结果)
   0x35 : Return                     // 返回累加器中的值

18.4 Sparkplug 基线编译器：零 IR 线性发射机器码
------------------------------------------------------------------------

在 Ignition 解释器架构中，即使字节码设计极其紧凑，解释器在执行每条字节码时仍必须经历**指令分发循环（Interpreter Dispatch Loop）**：
1. 读取当前字节码 Opcode；
2. 索引解释器全局函数跳转表（Dispatch Table）；
3. 执行间接跳转（Indirect Jump）进入对应的 Handler；
4. Handler 执行完毕后更新虚拟程序计数器（Bytecode PC），再次跳转。

这一分发循环会造成不可忽视的 CPU 分支预测失败（Branch Mispredictions）与指令缓存颠簸。

Sparkplug 的直译设计哲学
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了消除解释器分发循环的开销，同时避免顶层 JIT 编译器的巨大耗时，V8 引入了 **Sparkplug 基线编译器**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 Sparkplug 零中间表示 (Zero-IR) 编译机制                 |
   +-------------------------------------------------------------------------+

   Ignition 字节码序列 (Bytecode Stream)
        |
        | (Sparkplug 单遍顺序扫描遍历, 绝对不构建抽象语法树或控制流图!)
        v
   [ 1:1 线性指令发射器 (Linear Code Generator) ]
        * 遇到 LdaSmi [0]      ===> 直接发射汇编: `mov rax, 0`
        * 遇到 Star r0         ===> 直接发射汇编: `mov [rbp - 8], rax`
        * 遇到 Ldar r1         ===> 直接发射汇编: `mov rax, [rbp - 16]`
        * 遇到 TestLessThan r2 ===> 发射汇编: 调用内置 Builtin 或直接生成 `cmp` 指令
        |
        v
   [ 本地机器码 (Native Machine Code) ]
        * 栈帧结构与 Ignition InterpreterFrame 保持 100% 二进制对齐!
        * 零开销共享同一份 Feedback Vector 槽位!

Sparkplug 的栈帧完全兼容性 (Frame Compatibility)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Sparkplug 的核心工程精妙之处在于**栈帧同构设计**。Sparkplug 生成的机器码在执行时，其物理栈内存中变量的偏移量、累加器的维护位置以及对 `FeedbackVector` 的引用，与 Ignition 解释器的 `InterpreterFrame` 具有完全相同的内存布局。

这意味着：
- 函数可以在 Ignition 与 Sparkplug 之间以**零成本（Zero-Cost）**进行双向切换；
- 栈上替换（On-Stack Replacement, OSR）在遇到长时间运行的循环时，无需进行复杂的堆栈内存重构，即可平滑升级。

18.5 运行时类型反馈体系：Feedback Vector 与内联缓存 (Inline Caches)
------------------------------------------------------------------------

JavaScript 是一门完全无静态类型约束的动态语言。在执行 `obj.x` 时，`obj` 可能是普通对象、原型链继承对象、带有 Getter 的代理对象，甚至是带有动态拦截器的 Proxy。

如果每次属性访问都要回退到 C++ 运行时遍历原型链并进行字符串哈希匹配，执行耗时将高达数百个时钟周期。为此，V8 构建了极其精密的**运行时类型反馈体系**。

Feedback Vector 的槽位结构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每个被编译的 JavaScript 函数都会关联一个全局唯一的 `FeedbackVector` 数据结构。在字节码中，所有涉及属性读取、方法调用、算术运算和关系比较的指令，都会被静态分配一个专属的 **反馈槽位索引（Slot Index）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    V8 Feedback Vector 反馈槽位内存结构                  |
   +-------------------------------------------------------------------------+

   calculateTotal 的 FeedbackVector:
   +-----------+-----------------------+-------------------------------------+
   | Slot 索引 | 关联的字节码指令      | 记录的运行时类型反馈状态 (Metadata) |
   +===========+=======================+=====================================+
   | Slot [1]  | LdaNamedProperty 'len'| Monomorphic: Map_Array -> Offset #12|
   +-----------+-----------------------+-------------------------------------+
   | Slot [4]  | LdaKeyedProperty [i]  | Monomorphic: PackedSmiArray         |
   +-----------+-----------------------+-------------------------------------+
   | Slot [6]  | GetNamedProperty 'prc'| Monomorphic: Map_Item -> Offset #16 |
   +-----------+-----------------------+-------------------------------------+
   | Slot [8]  | Add (sum + price)     | SignedSmall (SMI) / Number Float64  |
   +-----------+-----------------------+-------------------------------------+

内联缓存 (Inline Cache, IC) 的四态状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于每个属性访问点（CallSite / Property Access Point），内联缓存根据运行过程中捕获到的对象隐藏类（Map / Hidden Class）数量，经历严格的状态演进：

.. list-table:: 内联缓存 (Inline Cache) 四级状态机流转与底层机制
   :widths: 15 20 35 30
   :header-rows: 1
   :class: tight-table

   * - IC 状态
     - 捕获的 Map 数量
     - 内部数据结构与执行行为
     - 硬件与微架构开销
   * - **Uninitialized**
     - 0
     - 初始状态，槽位为空。
     - 第一次执行时触发轻量级运行时查询并记录首次观察到的 Map。
   * - **Monomorphic (单态)**
     - 1
     - **最高性能黄金状态**。槽位中直接缓存了该单一 `Map` 指针及其在内存中的物理偏移量 `Offset`。
     - 硬件执行时仅需：单次 `cmp [obj.map], CachedMap`，匹配成功后直接单周期 `mov rax, [obj + Offset]` 寻址！
   * - **Polymorphic (多态)**
     - 2 ~ 4
     - 槽位升级为一个小型跳转数组（Map 判别链），线性比对 2~4 个不同的 `Map` 与对应的 `Offset`。
     - 增加 2~4 次指针比对与分支跳转，性能略有下降，但依然高度受控。
   * - **Megamorphic (超多态)**
     - 5 个及以上
     - 属性访问模式严重发散。槽位被标记为全局超多态，放弃内联缓存数组。
     - 彻底退化为全局 Stub 查找或通用 C++ 原型链遍历，性能产生断崖式下跌。

------------------------------------------------------------------------
18.6 TurboFan 顶层 JIT 编译器：Sea-of-Nodes 图与投机深度优化
------------------------------------------------------------------------

当一个函数在 Ignition / Sparkplug 中被高频调用（调用计数器溢出，或长时间运行的循环触发 OSR），且其 `FeedbackVector` 中的类型反馈高度收敛在单态或受控多态时，V8 调度后台编译线程启动 **TurboFan 顶层优化编译器**。

Sea-of-Nodes 图表示的革命性设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统编译器通常采用显式的控制流图（Control Flow Graph, CFG）来严格约束指令的先后执行顺序，这在处理包含复杂异常、动态属性查找的语言时极度僵化。

TurboFan 采用了革命性的 **Sea-of-Nodes（节点之海）** 中间表示：
- **控制依赖边（Control Edges）**、**数据依赖边（Data Edges）** 与 **内存状态依赖边（Effect Edges）** 全部被建模在同一张有向无环图中；
- 节点之间在初始阶段没有任何人为施加的顺序约束，只有严格的数据流和内存因果约束。这赋予了优化器极致的**指令重排、公共子表达式消除与死代码裁剪自由度**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     TurboFan Sea-of-Nodes 核心优化流水线                |
   +-------------------------------------------------------------------------+

   Ignition Bytecode + Feedback Vector (单态类型证据)
            |
            v
   [ 1. Inlining Phase (函数内联阶段) ]
        * 将微型回调函数、Getter/Setter 直接展开嵌入调用点，消除栈帧创建与调用开销
            |
            v
   [ 2. Typed Lowering & Speculative Optimization (投机特化降级) ]
        * 将通用动态操作符 `Add` 投机特化为单周期硬件整数加法 `Int32Add` 或浮点 `Float64Add`
        * 在图的入口显式插入类型守卫节点: `CheckMaps` 与 `CheckBounds`
            |
            v
   [ 3. Escape Analysis & Scalar Replacement (逃逸分析与标量替换) ]
        * 若对象字面量（如 `{ x: 1, y: 2 }`）未逃逸出当前函数作用域:
        * 彻底取消堆内存分配 (Zero Heap Allocation)! 将对象字段直接打散分配至 CPU 物理寄存器!
            |
            v
   [ 4. Loop Optimization & Redundancy Elimination (循环优化与冗余消除) ]
        * 循环不变代码外提 (LICM)
        * 数组边界检查消除 (Bounds Check Elimination): 证明 `i < length` 后直接消除每次循环的 `CheckBounds`
            |
            v
   [ 5. Instruction Scheduling & Register Allocation (寄存器分配与机器码发射) ]
        * 基于线性扫描（Linear Scan）算法为 Sea-of-Nodes 分配真实的物理寄存器 (x86-64 / ARM64)
        * 最终发射高度向量化 (SIMD) 的最优本地机器码!

18.7 投机假设破灭：动态反优化 (Deoptimization) 的微架构机制与性能断崖
------------------------------------------------------------------------

TurboFan 能够生成媲美 C++ 的极速机器码，完全建立在对 `FeedbackVector` 类型的**投机假设（Speculation）**之上。然而，JavaScript 的语言规范允许代码在任何时刻传入违反此前模式的新对象。

一旦投机假设在运行时被打破，JIT 生成的机器码将无法继续执行，必须执行极其昂贵的 **反优化（Deoptimization, 简称 Deopt）**。

Deopt 的三类触发场景与判定
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **Eager Deopt（同步主动反优化）**：机器码内置的保护性断言（如 `CheckMaps` 或 `CheckSmi`）检测到传入对象的 Map 与编译期假设不符，当前 CPU 指令流立即同步跳转至 Deopt Bailout 入口；
2. **Lazy Deopt（惰性被动反优化）**：当全局原型链被修改（例如某个第三方库污染了 `Array.prototype`），或者代码通过 `eval` 动态注入了全局变量，V8 会在底层通过代码修补（Code Patching）将原本运行中的优化函数标记为废弃，当该函数执行到返回点或下一个检查点时被动触发 Deopt；
3. **Soft Deopt（软反优化）**：优化代码执行到了未被类型反馈覆盖的代码分支，引擎主动退出并重新累积反馈。

反优化栈展开与状态重构微架构过程
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |             TurboFan 机器码发生 Eager Deopt 时的物理栈展开与重构        |
   +-------------------------------------------------------------------------+

   [ 执行中的 TurboFan 优化机器码栈帧 ]
   CPU 寄存器: [ rax = sum, rcx = i, rdx = items_ptr ]
        |
        | =====> 执行指令: CheckMaps r3, Expected_Map (假设当前元素为 { price: Number })
        | =====> 运行时传入了异常对象: { price: "99.9" } (字符串类型!) 校验失败!
        v
   [ 触发 Bailout Handler (调用 V8 运行时反优化器 Deoptimizer) ]
        |
        +-- 1. 挂起当前线程执行流，捕获物理寄存器与硬件栈指针上下文；
        +-- 2. 查找编译期固化在机器码元数据中的 Bailout Table 映射表；
        +-- 3. 解析当前机器码 PC 对应回原始 Ignition 字节码的 Bytecode Offset；
        +-- 4. 在物理堆栈上【逆向重构】出等价的 Ignition InterpreterFrame 虚拟栈帧:
        |      - 将物理寄存器 `rax` 的值还原回局部变量槽位 `r0` (sum)
        |      - 将物理寄存器 `rcx` 的值还原回局部变量槽位 `r1` (i)
        |      - 将累加器 `acc` 恢复为当前正在操作的操作数
        +-- 5. 将程序计数器 (PC) 精确重置回 Ignition 解释器的对应字节码指令；
        |
        v
   [ 无缝回退至 Ignition 字节码解释器继续执行 ]
        * 整个降级过程对应用代码完全透明，业务语义 100% 正确（字符串加法正常执行）；
        * 代价: 产生微秒级 CPU 挂起开销，并将该函数的反馈槽位污染为 Megamorphic，禁止再次激进优化!

.. list-table:: 工业级场景下导致 V8 发生严重 Deopt 的高危编码模式与重构策略
   :widths: 25 35 40
   :header-rows: 1
   :class: tight-table

   * - 高危编码模式
     - 破坏的 JIT 投机假设
     - 工业级正向重构规范
   * - **动态增删对象属性**
     - 破坏对象固定 Map，导致属性读取由 Monomorphic 骤降为 Megamorphic
     - 严格在构造函数中以固定顺序初始化全部字段；严禁使用 `delete obj.prop`（推荐设置为 `undefined` 或使用 `Map` 数据结构）。
   * - **混合数据类型数组**
     - 破坏数组元素类型假设（`PACKED_SMI_ELEMENTS` 降级为 `HOLEY_ELEMENTS`）
     - 保证高频数组内部元素类型的绝对纯净；严禁在同质数字数组中掺杂 `null` 或字符串。
   * - **未受控的函数多态调用**
     - 破坏 Call Feedback Slot 单一目标假设，阻止 TurboFan 函数内联
     - 关键渲染与计算路径上的高频辅助函数保持入参契约稳定，避免传入结构迥异的多种参数形态。

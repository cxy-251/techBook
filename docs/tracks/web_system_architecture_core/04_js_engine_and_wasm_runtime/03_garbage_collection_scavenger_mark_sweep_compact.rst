========================================================================
Chapter 20: V8 垃圾回收微架构：分代假设、Scavenger 新生代拷贝、Major GC 增量标记与并发内存整理
========================================================================

.. note:: 前置背景与认知承接
   在前两章中，我们分别深入剖析了 Google V8 虚拟机的分层执行流水线（Chapter 18：Ignition、Sparkplug 与 TurboFan）以及堆内存对象的物理结构与隐藏类演进（Chapter 19：Tagged 指针、In-Object 属性与内联缓存）。我们明确了 JavaScript 对象在堆内存中并非静态存在，而是随着程序运行被高频创建、跃迁与销毁。

   在 C/C++ 等手动管理内存的语言中，程序员通过 `malloc/free` 控制内存生命周期，伴随而来的是悬垂指针（Dangling Pointer）与内存泄漏的巨大风险。JavaScript 运行时通过内嵌的自动化垃圾回收器（Garbage Collector, 简称 GC）在运行时阶段跟踪对象的存活性，自动释放不可达的垃圾内存。然而，垃圾回收并非零成本的抽象：垃圾扫描、标记与内存整理需要消耗 CPU 计算周期与总线带宽；在单线程事件循环模型下，若 GC 导致主线程暂停（Stop-The-World, STW），将直接表现为用户界面的掉帧卡顿（Jank）与交互响应延迟（INP 恶化）。

   为了在“高吞吐”与“低延迟”之间达成极限平衡，现代 V8 引入了代际垃圾回收拓扑、Scavenger 新生代拷贝算法、三色标记与 Orinoco 并发增量架构。本章将深入 V8 垃圾回收器的底层微架构：解构弱分代假设与堆空间划分、追踪 Cheney 算法在半空间（Semi-Space）间的物理流转、剖析写屏障（Write Barrier）与记忆集（Remembered Set）如何解决跨代引用扫描难题、解剖 Major GC 的三色标记与内存碎片滑动整理机制，并建立面向 Web 性能优化的内存泄漏诊断模型。

20.1 弱分代假设与 V8 堆内存分代拓扑
------------------------------------------------------------------------

垃圾回收器的底层设计哲学建立在一个经过工业界数十年验证的统计学规律之上——**弱分代假设（Weak Generational Hypothesis）**：

1. **绝大多数对象的生命周期极其短暂**：在典型的 Web 应用执行过程中，大部分对象作为函数局部变量、临时字符串拼接、中间计算闭包或事件参数被创建，并在其所在的调用栈或事件循环任务结束后立即变为无用垃圾（“朝生夕灭”）；
2. **存活时间越长的对象，未来继续存活的概率越高**：经历过多次垃圾回收仍未被释放的对象（如全局状态、模块单例、长生命周期 DOM 绑定），往往在应用生命周期内常驻。

若采用统一的全局垃圾回收器对整个堆内存无差别执行全量扫描，每次清理都将浪费巨额 CPU 周期遍历数万个长期存活的对象。为此，V8 将堆内存划分为 **新生代（New Space / Young Generation）** 与 **老生代（Old Space / Old Generation）**，针对不同生命周期特征采用截然不同的回收算法。

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                                 V8 堆内存多区域分代拓扑全景                                       |
   +---------------------------------------------------------------------------------------------------+

   +---------------------------------------------------------------------------------------------------+
   |                                      V8 4GB 堆内存笼 (Heap Cage)                                  |
   +---------------------------------------------------------------------------------------------------+
   |  [ 新生代 New Space (8MB ~ 64MB) ]                                                                |
   |  +-----------------------------------+-----------------------------------+                        |
   |  |   From Space (半空间 1, 活跃分配) |    To Space (半空间 2, 拷贝接收)  |                        |
   |  +-----------------------------------+-----------------------------------+                        |
   |                                                                                                   |
   |  [ 老生代 Old Generation ]                                                                        |
   |  +-----------------------------------+-----------------------------------+                        |
   |  |   Old Pointer Space               |   Old Data Space                  |                        |
   |  |   (包含对外指针的对象, GC 深度遍历) |   (纯原始数据/字符串, GC 免指针遍历)|                        |
   |  +-----------------------------------+-----------------------------------+                        |
   |  |   Large Object Space (大对象空间, >128KB 独占连续虚拟页, 不参与 Scavenger 移动)                |
   |  +-----------------------------------+-----------------------------------+                        |

.. list-table:: V8 堆内存各分区职责与物理特征对比
   :widths: 20 15 25 40
   :header-rows: 1
   :class: tight-table

   * - 堆空间分区
     - 典型物理尺寸
     - 回收器算法
     - 内部存储对象与管理机制
   * - **New Space (新生代)**
     - 8MB ~ 64MB (动态调整)
     - **Minor GC (Scavenger)**
     - 由两个对等的 Semi-Space 组成。所有新分配的小对象优先在此通过连续指针推移（Bump Allocation）极速创建。
   * - **Old Pointer Space**
     - 数百 MB ~ 数 GB
     - **Major GC (Mark-Sweep-Compact)**
     - 存放存活下来的、内部包含指向其他堆对象指针的老生代对象。GC 标记阶段必须深度追踪其内部每一个指针字段。
   * - **Old Data Space**
     - 数百 MB ~ 数 GB
     - **Major GC (Mark-Sweep-Compact)**
     - 存放纯原始数据（如长字符串、未装箱的 Float64 数组、字节码）。GC 标记阶段判定存活后**无需扫描其内部**，大幅节省标记时间。
   * - **Large Object Space**
     - 动态按需分配
     - **Major GC 单独管理**
     - 体积超过 128KB 的大对象。大对象在新生代移动将带来灾难性的内存复制开销，因此直接在此通过操作系统虚拟内存页链表管理，永不发生物理拷贝。
   * - **Code Space**
     - 数十 MB ~ 百 MB
     - **Major GC**
     - 存放 Sparkplug 与 TurboFan 编译生成的本地机器码。由于涉及安全代码执行，该空间在内核层面配置 `PROT_EXEC` 属性，与数据堆严格隔离。
   * - **Map Space**
     - 数 MB ~ 数十 MB
     - **Major GC**
     - 存放所有的隐藏类（Map / Hidden Classes）。所有 Map 尺寸完全相同，无内部碎片。
   * - **Read-Only Space**
     - 数 MB
     - **不参与 GC**
     - 存放不可变的系统根对象（如 `undefined`、`null`、`true` 单例以及内置全局原型的不可变描述符）。

20.2 Minor GC (Scavenger) 与半空间 Cheney 拷贝算法
------------------------------------------------------------------------

新生代空间专门用于承载生命周期短暂的高频对象。为了实现纳秒级的对象分配与极速回收，V8 在新生代采用了基于 **半空间（Semi-Space）** 的 **Cheney 拷贝垃圾回收算法（Scavenger）**。

碰撞指针分配器 (Bump Allocator)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在新生代的当前活跃半空间（From-Space）中，对象的分配不通过空闲链表查找，而是直接采用 **碰撞指针（Bump-the-Pointer / Allocation Pointer）** 机制：

.. code-block:: text

   [ From-Space 连续内存区 ]
   +---------------------------------------+---------------------------------------+
   | 已分配对象 A | 已分配对象 B | 对象 C  |           未使用的连续空闲空间        |
   +---------------------------------------+---------------------------------------+
                                           ^                                       ^
                                    allocation_top                         allocation_limit

1. 当执行 `const obj = { x: 1 }` 时，引擎仅需一条汇编加法指令将 `allocation_top` 指针向前推移 `size` 字节；
2. 若推移后的指针未超过 `allocation_limit`，分配立即在 1~2 个 CPU 周期内完成；
3. 若 `allocation_top + size > allocation_limit`，表明 From-Space 空间耗尽，立即触发一次 Minor GC。

Cheney 拷贝算法的物理执行流转
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Scavenger 回收的核心机制是：**只扫描并复制活对象，未被访问的垃圾对象在空间清空时被瞬间批量丢弃**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  Scavenger (Cheney 算法) 内存流转过程                   |
   +-------------------------------------------------------------------------+

   [ 初始状态: From-Space 存满, 触发 Minor GC ]
   From-Space: [ 根可达 A (活) ] [ 垃圾 B (死) ] [ A 引用的 C (活) ] [ 垃圾 D (死) ]
   To-Space:   [                                                            ] (纯净空闲)

   [ 阶段 1: 扫描根集合 (Roots), 复制直接可达对象 A 到 To-Space ]
   From-Space: [ 转发指针 -> A' ] [ 垃圾 B (死) ] [ 对象 C (活) ] [ 垃圾 D (死) ]
   To-Space:   [ 对象 A' (待扫描字段) ]
               ^                     ^
              scan                  free

   [ 阶段 2: 推进 scan 指针, 遍历 A' 的字段, 发现指向 C, 将 C 拷贝至 To-Space ]
   From-Space: [ 转发指针 -> A' ] [ 垃圾 B (死) ] [ 转发指针 -> C' ] [ 垃圾 D (死) ]
   To-Space:   [ 对象 A' (已扫描完毕) ] [ 对象 C' (待扫描字段) ]
                                      ^                      ^
                                     scan                   free

   [ 阶段 3: scan 追平 free 指针, 广度优先遍历结束! 角色互换 (Swap) ]
   From-Space 被完全标记为空闲; 原 To-Space 成为新的 From-Space 继续接受分配!

Cheney 算法的底层关键细节：
- **转发指针（Forwarding Address）**：当存活对象从 From-Space 拷贝到 To-Space 后，V8 会立即在该对象原本位于 From-Space 的头部写入一个指向其新地址的转发指针。当后续遍历其他对象发现同样引用了该旧地址时，无需重复拷贝，直接读取转发指针就地更新引用即可；
- **广度优先搜索（BFS）**：通过维护 `scan` 与 `free` 两个简单指针即可实现队列式遍历，整个回收过程完全无需递归，亦无需额外的遍历辅助栈空间；
- **消除内存碎片**：存活对象被连续紧凑地写入 To-Space 的起始端，天然消除了所有内存碎片，使得下一次 Bump Allocation 依然能够连续高速进行。

对象晋升机制 (Tenuring / Promotion)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

若一个对象生命周期较长，频繁在 From-Space 与 To-Space 之间来回拷贝将导致严重的 CPU 搬移与总线带宽浪费。因此，V8 制定了严格的 **对象晋升（Promotion）** 规则，满足以下任一条件的新生代对象将被直接转移至老生代：

1. **代际计数阈值（Age Threshold）**：每个新生代对象头部包含一个代际标记。首次经历 Minor GC 存活下来的对象被标记为“已存活一次”；当其经历第二次 Minor GC 依然存活时，将其直接拷贝到老生代（Old Pointer Space 或 Old Data Space）；
2. **To-Space 水位保护阈值**：在执行 Scavenger 过程中，若 To-Space 已经使用的内存空间超过总容量的 **25%**，为防止单次回收撑爆新生代并保证下一次分配具备足够余量，后续所有存活对象将不再进入 To-Space，而是直接晋升至老生代。

20.3 跨代引用与记忆集 (Remembered Set) / 写屏障微架构
------------------------------------------------------------------------

分代垃圾回收的致命挑战在于 **跨代引用（Cross-Generational References）**：

.. code-block:: javascript

   // globalState 位于老生代 (Old Space)
   // newObj 是刚刚在新生代 (New Space) 分配的对象
   globalState.latestItem = newObj;

若在 Minor GC 执行时，仅仅从调用栈和全局变量开始扫描新生代，将无法发现 `newObj` 正被老生代中的 `globalState` 强引用，从而将本应存活的 `newObj` 错误回收。然而，若 Minor GC 为了查找跨代引用而去完整扫描整个老生代堆内存，Minor GC 将退化为全量 GC，分代隔离带来的性能优势将荡然无存。

卡表 (Card Table) 与记忆集 (Remembered Set)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

V8 采用 **记忆集（Remembered Set）** 记录所有“由老生代指向新生代”的指针位置：

1. **内存卡页划分（Card Table）**：V8 将老生代内存以 512 字节为固定粒度切分为若干个连续的内存卡页（Card）；
2. **卡表位图映射**：维护一个紧凑的字节数组（Card Table），每个字节对应一个 512 字节的老生代卡页；
3. **Dirty 状态标记**：当某个 512 字节卡页内的老生代对象持有了指向新生代的指针时，将该卡页对应的 Card Table 字节标记为 `Dirty (0x01)`。

写屏障 (Write Barrier) 汇编级拦截
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了在不产生运行时锁与繁重函数调用的前提下精准捕获跨代指针变更，JIT 编译器（Sparkplug / TurboFan）在生成所有对象属性赋值的机器码时，均内联注入了一段高效的 **写屏障（Write Barrier）** 指令序列：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     V8 汇编级写屏障 (Write Barrier) 拦截逻辑            |
   +-------------------------------------------------------------------------+

   [ 执行 JavaScript 属性写入: host_obj.field = value ]
        |
        | 1. 执行物理内存写入:
        |    mov [r_host + offset], r_value
        |
        | 2. 【快速检查 (Fast Path)】: 检查写入的 value 是否为 HeapObject 且位于新生代?
        |    test r_value, 0x1                      ; 检查是否为 Tagged 指针 (非 Smi)
        |    jz .Ldone                              ; 若为小整数 Smi, 绝不可能指向新生代, 瞬间跳过!
        |
        | 3. 【分代边界检查】: 检查 host 是否在老生代, 且 value 是否在新生代?
        |    ; 利用堆基址与内存掩码执行极速位运算比对
        |    xor r_tmp, r_host, r_value
        |    test r_tmp, kPageAlignmentMask
        |    jz .Ldone                              ; 同代引用, 跳过!
        |
        | 4. 【标记卡表 (Mark Dirty)】:
        |    ; 将 host 对象地址右移 9 位 (除以 512) 获取 Card 索引, 标记卡表为 Dirty
        |    shr r_host, 9
        |    mov byte [r13_card_table_base + r_host], 0x1
        |
   .Ldone:

在 Minor GC 执行期间，垃圾回收器**完全无需遍历整个老生代**，仅需扫描卡表中被标记为 `Dirty` 的稀疏卡页，提取其中的跨代指针直接加入根集合。这使得 Minor GC 的停顿时间能够稳定控制在 **1ms ~ 3ms** 极速区间。

20.4 Major GC (Mark-Sweep-Compact) 三阶段全景
------------------------------------------------------------------------

当老生代空间逐渐耗尽，或对象晋升速率过快触发自适应内存阈值时，V8 将启动针对全量堆空间的 **Major GC（在内部称为 Full Mark-Compact）**。Major GC 采用经典的 **标记-清除-整理（Mark-Sweep-Compact）** 架构。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                        Major GC 三阶段处理流程                          |
   +-------------------------------------------------------------------------+

   [ 阶段 1: Mark (三色标记) ]
   深度遍历根对象引用图, 使用黑/灰/白三色位图精确标记所有全局可达的存活对象

   [ 阶段 2: Sweep (内存清除) ]
   遍历老生代连续虚拟页, 将所有未被标记的白色死对象空间归还至空闲链表 (Free List)

   [ 阶段 3: Compact (内存压缩整理) ] (按需执行)
   针对碎片化严重的内存页, 将分散的存活对象滑动搬移至连续紧凑区域, 修正全量指针

三色标记法 (Tri-color Marking) 微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

V8 采用 **三色标记法** 抽象描述对象的可达性扫描状态：

- **白色（White）**：未被垃圾回收器发现的对象。在标记阶段开始时，除根对象外的所有堆对象均为白色；标记阶段结束时，依然保持白色的对象即为不可达的垃圾；
- **灰色（Grey）**：已被垃圾回收器发现并访问，但其持有的直接引用子对象尚未完成扫描；
- **黑色（Black）**：自身已被访问，且其包含的所有直接引用子对象均已被扫描并推入标记队列。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       三色标记状态演进与位图映射                        |
   +-------------------------------------------------------------------------+

   [ 初始状态 ]
   Roots (黑) ---> [ 对象 A (灰) ]      [ 对象 B (白) ]      [ 对象 C (白) ]

   [ 标记推进 ]
   从灰色栈弹出对象 A, 扫描 A 的字段, 发现引用了 C:
   1. 将 C 的标记位图由白色置为灰色, 将 C 压入工作栈 (MarkingWorklist);
   2. 对象 A 的所有字段扫描完毕, A 由灰色跃迁为黑色!

   Roots (黑) ---> [ 对象 A (黑) ]      [ 对象 B (白) ]      [ 对象 C (灰) ]
                                                                   |
                                                                   v
                                                            (继续深度遍历...)

在物理实现层面，V8 为每个 512KB 的堆内存页配置了独立的 **标记位图（Marking Bitmap）**。每个对象对应的 Tagged 指针在位图中占用 2 个比特，分别编码 `[00: 白色]`, `[10: 灰色]`, `[11: 黑色]`，完全无需在对象头部额外添加字段。

清除阶段 (Sweeping) 与分级空闲链表 (Free-List)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

标记结束后，所有仍为白色的对象均被判定为垃圾。在清除（Sweeping）阶段，V8 遍历内存页的标记位图，将连续的死对象内存块解构为空闲区间（Free Chunk），并将其挂载到所属内存页的 **分级空闲链表（Categorized Free Lists）** 中。

空闲链表按照内存块尺寸划分为多个区间桶（Bins）：
- `Bin 0`: 16 ~ 32 字节
- `Bin 1`: 32 ~ 64 字节
- `Bin 2`: 64 ~ 128 字节
- `...`
- `Bin N`: 大内存块

当老生代后续需要为晋升的对象分配内存时，直接根据所需尺寸在对应 Bin 中快速进行 $O(1)$ 查找与切割复用。

内存外碎片危机与滑动压缩整理 (Compacting)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

单纯依靠 Mark-Sweep 会导致严重的问题——**内存外碎片（External Fragmentation）**：经过长期的分配与清除后，内存中可能存在大量细碎的可用空闲块，其总容量充足，但没有任何单个空闲块能够容纳一个新晋升的连续大对象，从而被迫向操作系统申请新物理页，引发严重的虚拟内存膨胀。

为此，V8 在 Major GC 中引入了 **滑动压缩（Sliding Compactor）**：

.. code-block:: text

   [ 整理前: 严重的碎片化老生代内存页 ]
   +-----------+-----------+-----------+-----------+-----------+-----------+
   | 活对象 A  |  空闲块 1 | 活对象 B  |  空闲块 2 |  空闲块 3 | 活对象 C  |
   +-----------+-----------+-----------+-----------+-----------+-----------+

   [ 压缩算法: 将存活对象向左平移紧密排列, 释放尾部连续大空间 ]
   +-----------+-----------+-----------+-----------------------------------+
   | 活对象 A  | 活对象 B' | 活对象 C' |        完全连续的巨型空闲空间     |
   +-----------+-----------+-----------+-----------------------------------+

滑动压缩算法分为三个严密子阶段：
1. **计算目标地址（Calculate Addresses）**：遍历存活对象，计算每个对象平移后的新物理偏移量，并将新地址记录在对象头部或临时映射表中；
2. **指针重写（Update Pointers）**：全量遍历堆中所有的存活对象指针，若指针指向了即将发生搬移的对象，直接根据映射表将其更新为目标新地址；
3. **物理数据搬移（Relocate Objects）**：通过高性能内存拷贝指令（如 `memmove` / SIMD 加速）将对象实际物理数据搬移至新槽位。

------------------------------------------------------------------------
20.5 并发、增量与并行垃圾回收演进（Orinoco 架构）
------------------------------------------------------------------------

在早期的 V8 实现中，无论是 Scavenger 还是 Full GC，执行时都必须完全暂停 JavaScript 主线程（Stop-The-World, STW）。对于一个占用 1.5GB 内存的大型单页应用或 Node.js 服务端进程，一次完整的 Major GC 停顿时间可长达 **500ms ~ 1000ms**，这在 60Hz/120Hz 刷新率的现代 Web 交互中将造成灾难性的卡死。

V8 历时数年重构了垃圾回收核心架构，推出了名为 **Orinoco** 的全并发增量垃圾回收流水线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                        V8 Orinoco 三维 GC 并发加速矩阵                  |
   +-------------------------------------------------------------------------+

   1. 并行 (Parallel)    : 主线程暂停期间, 唤醒多个 Worker 线程协同加速单次停顿
                           [ Main Thread (STW) ] === 并行分担工作 ===>
                           [ Worker 1 ] [ Worker 2 ] [ Worker 3 ]

   2. 增量 (Incremental) : 将单次漫长的停顿切分为上千个微小的 1ms 切片, 穿插在 JS 宏任务间
                           [ JS 执行 ] -> [ GC 1ms ] -> [ JS 执行 ] -> [ 渲染帧 ] -> [ GC 1ms ]

   3. 并发 (Concurrent)  : JS 主线程全速执行业务代码的同时, Worker 线程在后台完全并发标记/清除
                           [ Main Thread ]: === 全速执行 JavaScript (0 停顿!) ===>
                           [ Background  ]: --- 后台并发三色标记与内存清除 ------->

并发标记 (Concurrent Marking) 与插入型写屏障
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

并发标记允许后台 Worker 线程在 JavaScript 主线程全速运行时，并发遍历对象引用图并修改标记位图。这引发了并发读写的数据一致性挑战：

.. code-block:: text

   [ 并发标记冲突场景 ]
   1. 后台 GC 线程扫描完毕对象 A (A 变为黑色);
   2. 主线程并发执行: `A.newField = B` (其中 B 原本为不可达的白色对象);
   3. 主线程随后删除了其他对 B 的引用: `parent.ref = null`;
   4. 后台 GC 线程不会再次扫描黑色对象 A, 导致 B 保持白色, 最终被错误回收!

为了捍卫并发标记的正确性，V8 在并发模式下激活了 **插入型写屏障（Dijkstra Write Barrier）**：
- 每当主线程向一个已被标记为黑色的对象写入新的属性引用时，写屏障强制将该被引用的新对象（如对象 B）着色为灰色，并将其推入后台 Worker 线程的共享工作栈（`MarkingWorklist`）；
- 从而确保了 **强三色不变性（Strong Tri-color Invariant）**：黑色对象绝对不允许直接指向白色对象。

.. list-table:: 现代 V8 各类 GC 阶段的并发模式与主线程停顿预算
   :widths: 20 25 35 20
   :header-rows: 1
   :class: tight-table

   * - 垃圾回收阶段
     - 采用的 Orinoco 模式
     - 物理执行机制
     - 主线程典型停顿 (STW)
   * - **Minor GC 标记**
     - **Parallel (并行)**
     - 主线程暂停，利用 4~8 个 Worker 线程并发扫描 Roots 与 Remembered Set。
     - 1ms ~ 2ms
   * - **Minor GC 拷贝**
     - **Parallel (并行)**
     - 多个 Worker 线程并行将 From-Space 存活对象拷贝至 To-Space 并更新指针。
     - 0.5ms ~ 1.5ms
   * - **Major GC 标记**
     - **Concurrent + Incremental**
     - **90% 以上的工作量在后台 Worker 线程并发完成**。主线程仅在启动与最终收尾时执行极短的原子切片。
     - < 1ms (单切片)
   * - **Major GC 清除**
     - **Concurrent (完全并发)**
     - 后台 Worker 线程独立遍历内存页并填充 Free List，主线程完全无感。
     - **0ms (零主线程停顿)**
   * - **Major GC 压缩**
     - **Parallel (并行)**
     - 针对需要整理的碎片页，主线程配合 Worker 线程并行执行多页滑动压缩。
     - 2ms ~ 5ms

20.6 Web 性能视角下的内存泄漏特征与分析排查拓扑
------------------------------------------------------------------------

在垃圾回收器自动化托管内存的体系下，**内存泄漏的本质是：开发者无意中保留了本应销毁对象的全局可达引用路径，导致垃圾回收器将其判定为活对象而无法释放**。

四大典型前端内存泄漏物理机理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: javascript

   // 1. 游离 DOM 节点驻留 (Detached DOM Tree Retention)
   const detachedElements = [];
   function createLeakyButton() {
     const btn = document.createElement("button");
     btn.innerHTML = "Click Me";
     document.body.appendChild(btn);
     document.body.removeChild(btn); // 从 DOM 树中移除
     detachedElements.push(btn);      // 但全局数组持有其引用! 导致整个 DOM 子树与关联监听器全部驻留堆内存!
   }

   // 2. 闭包上下文意外常驻 (Closure Context Retention)
   let outerScopeHolder;
   function allocateLargeBuffer() {
     const largeData = new Uint8Array(1024 * 1024 * 10); // 10MB
     const unusedFunction = function() {
       console.log(largeData); // 闭包引用了 largeData
     };
     outerScopeHolder = function() {
       // 虽然本函数没用 largeData，但与 unusedFunction 共享同一个外部 Lexical Context!
       console.log("Alive");
     };
   }

   // 3. 强引用缓存未设上限 (Unbounded Strong Cache)
   const globalCache = new Map(); // 必须使用 WeakMap 代替, 否则所有放入的 key 对象永久无法被 GC!
   function cacheUserData(userObj, data) {
     globalCache.set(userObj, data);
   }

   // 4. 定时器闭包未清理 (Uncleared Timers)
   function startPolling() {
     const hugeContext = { buffer: new Array(1000000) };
     setInterval(() => {
       // 该回调每秒执行，导致 hugeContext 永远可达，无法被回收
       console.log(hugeContext.buffer.length);
     }, 1000);
   }

Chrome DevTools Memory 面板核心指标与排查拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

排查 JavaScript 内存泄漏时，必须深刻理解 Chrome DevTools Heap Snapshot 暴露的两大核心度量衡：

1. **Shallow Size（浅层大小）**：
   - 对象自身物理结构在堆上直接占用的内存字节数（例如 `JSObject` 的头指针 + In-Object 槽位，通常仅为 24 ~ 64 字节）；
2. **Retained Size（保留大小）**：
   - **当该对象被回收后，连同其独占持有的下游引用链全部被级联释放后，能够从堆中省出的总内存字节数**。排查内存泄漏时，应始终按照 Retained Size 降序排序，迅速定位支配树（Dominator Tree）的根部节点。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  支配树 (Dominator Tree) 与 Retained Size 模型          |
   +-------------------------------------------------------------------------+

   [ 垃圾回收根节点 (GC Roots) ]
                 |
                 v
        [ 对象 A (Shallow: 32B, Retained: 10MB) ] <--- 支配节点 (Dominator)
              /     \
             v       v
   [ 对象 B: 2MB ]  [ 对象 C: 8MB ]
             \       /
              v     v
        [ 共享叶子节点 D: 500KB ]

   * 对象 A 是 B, C, D 的唯一支配节点 (若销毁 A, 则 B, C, D 全部变为不可达并被清理);
   * 因此, A 的 Retained Size = Shallow(A) + Shallow(B) + Shallow(C) + Shallow(D) = 10MB!
   * 在 Heap Snapshot 中排查问题，只需直接断开指向对象 A 的引用链，即可瞬间释放 10MB 内存!

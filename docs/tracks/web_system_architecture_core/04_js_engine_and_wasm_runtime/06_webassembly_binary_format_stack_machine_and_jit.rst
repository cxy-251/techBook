Chapter 23: WebAssembly 运行时微架构：二进制格式解析、栈式虚拟机、编译流水线与 JIT 机器码生成
================================================================================

.. note:: 前置背景与认知承接
   在上一章中，我们系统解构了现代 Web 平台的多线程并发架构（Chapter 22：Dedicated/Shared/Service Worker 线程模型、V8 Isolate 独立堆内存划分、SharedArrayBuffer 虚拟内存共享、Spectre 侧信道防御与 Atomics 硬件原子指令）。虽然多线程机制解耦了主线程 UI 渲染与后台密集计算，但 Worker 线程内部执行的 JavaScript 代码依然受限于动态弱类型的运行时特性：即使经过 V8 TurboFan 深度优化编译，JIT 机器码仍须保留类型保护（Type Guard）去优化检查点，遇到非常态数据结构时依然会发生退化回退（Deoptimization）。

   WebAssembly（简称 WASM）提供了一种具备静态强类型、确定性内存布局和高度紧凑二进制编码的低级字节码体系。本章将深入剖析 WebAssembly 在现代浏览器内核中的运行时微架构：解构 WASM 二进制文件的魔数、版本标识与 13 种核心段（Section）的物理存储格式；推导 LEB128 变长编码的编解码位操作逻辑；剖析基于操作数栈（Operand Stack）的栈式虚拟机求值模型与单遍静态类型验证算法；深入结构化控制流（Structured Control Flow）如何消除不可约控制流图以加速机器码生成；解析基于 4GB 虚拟内存预留与硬件保护页（Guard Pages）实现的零开销内存沙箱隔离；剖析 V8 内部的 Liftoff 极速基线编译器与 TurboFan 优化编译器的分层编译流水线与流式编译重叠机制；最后解密基于 Table 的类型安全间接函数调用（`call_indirect`）控制流完整性保障。

23.1 WebAssembly 架构定位与系统级执行拓扑
------------------------------------------------------------------------

在浏览器内核的整体拓扑中，WebAssembly 并非一个孤立运行于操作系统之上的虚拟机，它与 JavaScript 宿主环境紧密耦合在同一个执行上下文与同一条操作系统线程中。

物理执行特征与确定性保证
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

WebAssembly 相比 JavaScript 提供了截然不同的执行保障：
1. **静态强类型系统**：仅包含四种基础数值类型（`i32`, `i64`, `f32`, `f64`）以及 128 位向量类型（`v128`）。所有指令的输入与输出类型在编译阶段严格确定；
2. **零垃圾回收暂停（Zero GC Pauses）**：WASM 核心代码的常规计算完全在自身的线性内存（Linear Memory）中进行，这是一块独立于 V8 堆内存的连续字节缓冲区。物理内存的分配与释放由编译器（如 Rust/C++ 的 `malloc`/`free` 或栈指针推移）直接管理，不增加 V8 垃圾回收器的标记与扫描负载；
3. **消除投机去优化（No Deoptimization Bailout）**：JavaScript 引擎的最高性能依赖于类型假设（Type Feedback）。一旦假设被多态参数破坏，CPU 必须暂停执行并回滚栈帧至解释器，产生数百个周期的管线抖动。WASM 由于具备精确的静态类型签名，JIT 生成的原生机器码是一次性确定的，执行过程具有严格的耗时可预测性。

23.2 WASM 二进制格式与段 (Section) 结构深解
------------------------------------------------------------------------

WebAssembly 采用高度紧凑的二进制编码规范。一个合法的 `.wasm` 二进制文件由 4 字节魔数、4 字节版本号以及紧随其后的若干个自描述数据段（Section）构成。

物理文件头结构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------+-------------------+-------------------+-------------------+
   | 字节 0 ~ 3        | 字节 4 ~ 7        | 字节 8 ~ ...      | 字节 N ~ ...      |
   +-------------------+-------------------+-------------------+-------------------+
   | 魔数 (Magic)      | 版本号 (Version)  | 段 1 (Section 1)  | 段 2 (Section 2)  |
   | 0x00 0x61 0x73 0x6D | 0x01 0x00 0x00 0x00 | [ID][Size][Payload| [ID][Size][Payload|
   | ("\0asm")         | (Version 1)       | ...               | ...               |
   +-------------------+-------------------+-------------------+-------------------+

LEB128 变长整数编码算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了最小化网络传输体积，WASM 规范规定所有整数（包括指令操作数、数组长度、段尺寸、局部变量索引）均采用 **LEB128（Little Endian Base 128）** 格式进行序列化。

LEB128 属于可变长度字节编码：每个字节的最高有效位（MSB，第 7 位）作为**延续标志位（Continuation Bit）**。若该位为 1，代表后续字节仍包含有效数字位；若该位为 0，代表当前字节是数字的终止字节。低 7 位（位 0 ~ 位 6）存储实际的数据有效载荷。

.. code-block:: text

   数字 624485 (十六进制 0x98765) 的无符号 LEB128 (unsigned LEB128 / uleb128) 编码过程:

   1. 二进制形式 (20 位):
      0000 1001 1000 0111 0110 0101

   2. 从低位开始划分为 7 位的组:
      组 0 (位 0~6):   1100101 (0x65)
      组 1 (位 7~13):  0001110 (0x0E)
      组 2 (位 14~20): 0100110 (0x26)

   3. 为前两组加上延续位 1 (0x80), 最后一组加上延续位 0:
      字节 0: 1100101 | 0x80 = 11100101 (0xE5)
      字节 1: 0001110 | 0x80 = 10001110 (0x8E)
      字节 2: 0100110 | 0x00 = 00100110 (0x26)

   4. 最终编码输出字节序列:
      [ 0xE5, 0x8E, 0x26 ] (仅占用 3 字节, 相比固定 32 位整型节省 25% 空间)

在 V8 的解码实现中，解析无符号 LEB128 的 C++ 核心逻辑如下：

.. code-block:: cpp

   // V8 内部的 LEB128 快速流式解码实现
   inline uint32_t ReadVarUint32(const uint8_t** pc, const uint8_t* limit) {
     uint32_t result = 0;
     uint32_t shift = 0;
     while (*pc < limit) {
       uint8_t byte = **pc;
       (*pc)++;
       result |= (byte & 0x7F) << shift;
       if ((byte & 0x80) == 0) return result; // 延续位为 0, 顺利返回
       shift += 7;
       if (shift >= 35) break; // 防止整型溢出恶意输入
     }
     // 触发解码格式异常
     V8_Fatal("Malformed LEB128 integer stream");
     return 0;
   }

13 种核心段（Section）规范与布局拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

紧随文件头之后的是一系列段结构。每个段的头部包含 1 字节的 **段 ID（Section Code）** 以及用 LEB128 编码的 **段字节长度（Size）**，其后是该段的完整有效负载。除 Custom Section 可以在文件中任意位置出现外，其余非自定义段在文件中必须严格按照指定的序号升序排列，以便解析器执行流式编译。

.. list-table:: WebAssembly 核心段物理定义与解析职责矩阵
   :widths: 8 16 28 48
   :header-rows: 1
   :class: tight-table

   * - 段 ID
     - 段名称 (Section)
     - 包含的核心数据结构
     - 运行时引擎装配与校验职责
   * - `0x00`
     - **Custom**
     - 名称字符串、调试符号（DWARF）、源代码映射
     - 引擎可选择性忽略，不参与执行，专供 DevTools 源码调试映射。
   * - `0x01`
     - **Type**
     - 函数签名向量：`[ (param_types) -> (return_types) ]`
     - 预声明所有函数的输入输出强类型，构造全局函数签名类型字典。
   * - `0x02`
     - **Import**
     - 外部模块名、字段名、导入项描述（函数/内存/表/全局）
     - 收集宿主（JavaScript）提供的外部引用，在实例化阶段执行类型安全匹配绑定。
   * - `0x03`
     - **Function**
     - 函数对应的类型索引数组：`[type_idx_0, type_idx_1, ...]`
     - 建立模块内部函数与 Type 段中签名的映射索引表。
   * - `0x04`
     - **Table**
     - 表定义：元素引用类型（`funcref`）、初始大小与最大限制
     - 分配不透明指针引用表，为间接函数调用（`call_indirect`）构建安全跳转目标池。
   * - `0x05`
     - **Memory**
     - 线性内存描述：初始页面数（64KB 单位）、最大页面数、是否共享
     - 请求操作系统分配连续虚拟内存空间（`mmap`），构建模块独占的线性字节缓冲区。
   * - `0x06`
     - **Global**
     - 全局变量类型、可变性标记（mutable）、初始化表达式
     - 初始化模块内全局标量状态（存储于独立于线性内存的引擎原生寄存器区）。
   * - `0x07`
     - **Export**
     - 导出名称字符串、导出项类别、内部实体索引
     - 构造模块对外的暴露接口，生成供 JavaScript 直接调用的导出函数包装器。
   * - `0x08`
     - **Start**
     - 启动函数索引（`func_idx`）
     - 在实例化完成后由引擎自动调用的无参初始化入口点。
   * - `0x09`
     - **Element**
     - 表索引、偏移量初始化表达式、函数索引列表
     - 将具体的函数索引填充至 Table 的指定槽位中，激活静态跳转地址。
   * - `0x0A`
     - **Code**
     - 局部变量声明、函数体原始字节码指令流
     - **核心计算载荷**。提供所有函数的原始字节码，供 JIT 编译器翻译为机器指令。
   * - `0x0B`
     - **Data**
     - 内存索引、线性内存偏移量计算表达式、原始初始字节数组
     - 将静态常量、字符串字面量直接 memcpy 写入线性内存的起始区域。
   * - `0x0C`
     - **Data Count**
     - 包含的 Data 段条目数量（u32 LEB128）
     - 优化验证流水线，允许流式编译在接收到 Code 段前校验批量内存指令。

23.3 栈式虚拟机 (Stack Machine) 与结构化控制流
------------------------------------------------------------------------

操作数栈模型与紧凑度物理原理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

物理微处理器（如 x86-64、ARM64）普遍采用基于寄存器的执行模型（Register-based Machine），指令中必须显式编码源寄存器和目标寄存器的编号（例如 `add eax, ebx` 中必须耗费指令位宽描述操作数寻址）。

WebAssembly 选择采用 **栈式虚拟机（Stack-based Machine）** 作为中间表示。栈式指令隐含操作数来源于**操作数栈（Operand Stack）**顶端，指令执行后将结果压回栈顶：
- 指令 `i32.add` 仅占用 **单字节（操作码 `0x6A`）**，完全省略了操作数寻址字段；
- 操作数栈是一个完全逻辑化的概念。现代 JIT 编译器在编译过程中，通过单遍寄存器分配算法将栈顶数值直接缓存在物理寄存器中，在硬件层面产生与手写寄存器代码完全相同的指令序列。

.. code-block:: text

   计算表达式: (a + b) * (c - d) 在 WASM 栈式机中的物理执行流:

   指令序列                操作数栈状态变迁 (从底向顶)
   -----------------------------------------------------------------
   local.get 0 (加载 a)    | a |
   local.get 1 (加载 b)    | a | b |
   i32.add                 | (a + b) |
   local.get 2 (加载 c)    | (a + b) | c |
   local.get 3 (加载 d)    | (a + b) | c | d |
   i32.sub                 | (a + b) | (c - d) |
   i32.mul                 | ((a + b) * (c - d)) |

静态类型验证算法 (Type Validation)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在字节码被执行或编译为本地汇编之前，浏览器引擎必须执行**单遍线性类型验证算法**。这一过程确保字节码无法伪造指针或违规破坏栈平衡。

验证器内部维护一个平行的“类型栈”（Type Stack）：
1. 遇到 `local.get` 时，查询局部变量签名表，将对应的静态类型（如 `I32`）压入类型栈；
2. 遇到 `i32.add` 时，检查类型栈顶部的两个元素是否均为 `I32`；若不匹配（如一个是 `F64`），立即中断编译并抛出 `WebAssembly.CompileError`；
3. 函数结束（`end`）时，类型栈必须恰好剩余函数声明所规定的返回值类型数量与顺序。

这一验证过程的时间复杂度严格为 $O(N)$（$N$ 为字节码长度），完全阻断了任何动态类型错误穿透至底层硬件执行阶段。

结构化控制流 (Structured Control Flow)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统汇编语言和 Java 字节码允许使用任意的无条件跳转指令（`goto` / `jmp`），这可能导致构建出控制流图中的**不可约循环（Irreducible Loops）**（即循环存在多个不同的入口点）。优化编译器在处理不可约流图时，必须引入复杂的节点分裂算法，产生巨大的 JIT 编译延迟。

WebAssembly 彻底废黜了任意跳转指令，强制采用 **结构化控制流（Structured Control Flow）**。所有控制转移必须通过显式的嵌套块结构表达：

.. list-table:: WebAssembly 结构化控制流原语及其物理跳转目标
   :widths: 15 25 35 25
   :header-rows: 1
   :class: tight-table

   * - 指令关键字
     - 操作码 (Opcode)
     - 物理跳转行为与目标
     - 控制流语义映射
   * - `block`
     - `0x02`
     - 建立前向跳转保护区。`br` 指令将跳转至该 block 对应的 `end` 之后。
     - 对应高级语言的常规代码块或 `switch` 分支。
   * - `loop`
     - `0x03`
     - 建立回跳循环保护区。`br` 指令将跳转回该 loop 的**开头（起始处）**。
     - 对应高级语言的 `while(true)` 或 `for` 循环头部。
   * - `if / else`
     - `0x04 / 0x05`
     - 弹出栈顶 `i32` 条件。若为 1 执行 if 分支；若为 0 且存在 else 则执行 else 分支。
     - 对应经典分支判断。
   * - `br`
     - `0x0C [label_idx]`
     - 无条件跳转至第 `label_idx` 层嵌套控制块的边界。
     - 对应 `break`（针对 block）或 `continue`（针对 loop）。
   * - `br_if`
     - `0x0D [label_idx]`
     - 弹出栈顶 `i32`。仅当条件非零时执行跳转，否则线性推进。
     - 条件中断与循环继续判定。
   * - `br_table`
     - `0x0E [labels...]`
     - 弹出栈顶 `i32` 作为索引查表跳转。索引越界时跳入默认标签。
     - 紧凑跳转表，直接映射硬件多路跳转指令。

结构化控制流的工程收益在于：**控制流天然保持为可约图（Reducible Flow Graph）**。编译器在单次自顶向下的线性扫描中，即可精准计算所有局部变量的定值-使用链（Def-Use Chains），使得 JIT 能够在毫秒级时间内生成高效的原生分支汇编。

23.4 线性内存模型 (Linear Memory) 与硬件保护页
------------------------------------------------------------------------

线性内存的物理抽象
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

WebAssembly 实例的操作数栈和局部变量对用户程序是完全不可寻址的（无法获取栈变量的物理指针）。所有堆分配数据、结构体和数组必须统一存放于 **线性内存（Linear Memory）** 中。

线性内存从逻辑上看是一段从地址 0 开始递增的无符号字节数组。
- **页面粒度（Page Size）**：以 **64KB（65,536 字节）** 为固定基本单位；
- **动态扩容**：通过 `memory.grow(delta_pages)` 指令请求操作系统分配更多连续虚拟内存页面。扩容操作可能引发底层内存页的重新映射。

4GB 虚拟内存预留与硬件保护页机制 (Guard Pages)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于每一次内存加载（例如 `i32.load offset=4 (base_ptr)`），程序都需要访问内存地址 `address = base_ptr + offset`。如果每次访存都插入显式软件指令检查是否越界：

.. code-block:: text

   // 软件分支检查伪代码 (传统方式, 带来严重的性能衰减)
   if ((base_ptr + offset + 4) > memory_byte_length) {
       trap(ERROR_OUT_OF_BOUNDS);
   }
   return *reinterpret_cast<int32_t*>(memory_base + base_ptr + offset);

这种显式边界比较会引入大量条件分支指令，导致 CPU 分支预测器资源枯竭，降低 20%~30% 的密集运算性能。

现代 64 位浏览器内核（以 V8 为代表）引入了基于 **操作系统虚拟内存管理单元（MMU）的硬件保护页（Guard Pages）机制**，彻底消除了常规访存的软件分支检查：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                             V8 64位架构下 WASM 线性内存虚拟地址映射图                             |
   +---------------------------------------------------------------------------------------------------+

   0x0000_0000_0000
   |
   v
   +---------------------------------------+  <--- 物理可访问区域 (Accessible Memory)
   | 实际分配的物理内存页面                |       由当前内存大小决定 (例如 16 个 Page = 1MB)
   | 具有读写权限 (PROT_READ | PROT_WRITE) |       正常内存加载在此物理命中
   +---------------------------------------+
   | 预留的可增长虚拟地址空间              |  <--- 尚未映射物理页的预留空间
   | (总计持续预留至 4GB 边界)             |       由系统 mmap PROT_NONE 占位
   |                                       |
   +---------------------------------------+
   0x0001_0000_0000 (4GB 边界)
   |
   v
   +---------------------------------------+  <--- 硬件保护页区 (Guard Pages: 占用连续数 GB 虚拟地址)
   | 绝对不可访问的警戒虚拟空间            |       权限为 PROT_NONE
   | 任何读取与写入均无法通过 MMU 权限校验 |       由 CPU MMU 直接触发硬件缺页异常
   |                                       |
   +---------------------------------------+
   0x0002_0000_0000 (8GB / 10GB 边界)

物理执行机理分析：
1. **虚拟地址预留**：在 64 位操作系统中，虚拟地址空间极其广阔（$2^{48}$ 字节）。V8 在创建 `WebAssembly.Memory` 时，直接通过 `mmap` 系统调用预留一个连续的 **8GB 虚拟地址段**（前 4GB 供 WASM 寻址，后 4GB+ 设为完全禁止访问的保护页 `PROT_NONE`）；
2. **纯原生地址生成**：由于 WASM 默认采用 32 位地址指针（`i32`），最大可能寻址范围为 $2^{32} - 1 = 4	ext{GB}$。即使加上指令内编码的立即数偏移量（Offset，最大 4GB），计算出的最大虚拟偏移量也不会超出 8GB 范围；
3. **消除所有软件检查指令**：JIT 编译器生成的机器码仅包含单条汇编指令：`mov eax, [r14 + rdi]`（其中 `r14` 为内存物理基址寄存器，`rdi` 为 32 位基址加上偏移）；
4. **硬件级越界捕获**：
   - 若地址落在当前物理已分配的内存页内，硬件无阻碍直通读取，性能达到 100% 原生速度；
   - 若地址超出当前已分配页面（但在 8GB 范围内），由于触发了未映射页或进入了后方的 Guard Pages，**CPU 的硬件 MMU 立即触发页面错误（Page Fault），向内核发出 `SIGSEGV`（Linux/macOS）或 `STATUS_ACCESS_VIOLATION`（Windows）信号**；
   - 浏览器内核注册了全局异常信号处理器（Signal Handler），精准捕获该硬件中断，并将其原地转换为 WebAssembly 的运行时异常（`WebAssembly.RuntimeError: memory access out of bounds`）。

第一层：Liftoff 基线编译器的物理设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Liftoff 是 V8 专为 WebAssembly 设计的极速单遍编译器。它的核心使命是**零延迟启动**：
- **不构建中间控制流图（No CFG/No IR）**：Liftoff 逐字节读取 WASM 字节码，遇到一条操作码立即将其直接发射为对应的 x86-64 或 ARM64 汇编指令；
- **虚拟寄存器栈（Virtual Register Stack）**：在编译期间，Liftoff 追踪当前的逻辑操作数栈。如果物理寄存器充足，栈顶的数值直接保留在物理寄存器（如 `rax`, `rcx`）中，避免不必要的物理内存溢出；
- 其编译速度达到每秒处理 10MB~20MB 二进制字节码，使得几兆字节大小的游戏或应用在下载完成的瞬间即可立即可执行。

第二层：TurboFan 优化编译器与高吞吐保证
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在应用通过 Liftoff 启动后，后台工作线程集群会自动拉取热点函数，提交给 **TurboFan** 编译器进行深度物理优化：
1. **节点海（Sea-of-Nodes）图表示**：将控制流与数据依赖统一建模为图节点，执行高级冗余消除；
2. **内存访问合并**：将多个相邻的连续字节读写指令合并为单条 64 位或 128 位宽总线加载指令；
3. **SIMD 128 向量化映射**：将 WASM 的 `v128` 操作码直接映射到 CPU 专属的 AVX2 / NEON 硬件向量寄存器，单时钟周期并发处理 4 个 32 位单精度浮点运算。

当 TurboFan 编译生成完毕后，引擎在函数表入口对应的 **调用跳板槽（Dispatch Slot）** 上执行一次 64 位原子写指针替换（Atomic Pointer Swap）。下一次调用该函数时，控制流直接无缝切入 TurboFan 生成的高吞吐指令序列中。

23.6 表 (Table) 与间接调用 (call_indirect) 微架构
------------------------------------------------------------------------

控制流完整性 (Control Flow Integrity) 的安全设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 C/C++ 等编译型语言中，虚函数调用（Virtual Method Table）和函数指针是核心基础语言特性。在传统机器架构中，函数指针直接保存目标代码在进程虚拟内存中的**物理内存绝对地址**。

如果 WebAssembly 允许将真实物理内存地址直接保存在线性内存中，恶意代码便可通过改写线性内存缓冲区制造出非法指针，直接劫持指令指针寄存器（RIP/PC）跳转至任意内存位置，从而彻底打破浏览器的沙箱防御模型。

为了根绝此类安全隐患，WebAssembly 引入了 **表（Table）** 结构，构建起强安全边界：

.. code-block:: text

   +---------------------------------------------------------------------------------------------------+
   |                             WebAssembly Table 间接函数调用安全检查全景                            |
   +---------------------------------------------------------------------------------------------------+

   WASM 线性内存 (Linear Memory)
   [ 存储虚表索引 index: 2 ] (仅仅是一个简单的整型数值, 绝非内存裸指针!)
          |
          v
   +---------------------------------------------------------------------------------------------------+
   | 执行指令: call_indirect (type_idx = 0)                                                             |
   | 操作数栈顶包含待调用的 table_index                                                                 |
   +---------------------------------------------------------------------------------------------------+
          |
          |--- [ 第一道安全校验: 边界检查 (Bound Check) ]
          |    验证 table_index < Table.length?
          |    若越界 -> 抛出 RuntimeError: table index out of bounds
          |
          v
   +---------------------------------------------------------------------------------------------------+
   | WebAssembly Table 结构体 (宿主引擎受保护原生内存, 外部完全不可逆向修改)                            |
   |                                                                                                   |
   | 索引 0: [ 函数实例 ptr: 0x7FFF10 ] | 真实函数签名索引: Type 0  (i32, i32) -> i32                 |
   | 索引 1: [ 函数实例 ptr: 0x7FFF80 ] | 真实函数签名索引: Type 1  (f64) -> f64                      |
   | 索引 2: [ 函数实例 ptr: 0x800020 ] | 真实函数签名索引: Type 0  (i32, i32) -> i32                 |
   | 索引 3: [ nullptr / 空槽位       ] | 状态: 未初始化                                              |
   +---------------------------------------------------------------------------------------------------+
          |
          |--- [ 第二道安全校验: 空指针检查 (Null Check) ]
          |    验证 Table[table_index].ptr != nullptr?
          |    若为空 -> 抛出 RuntimeError: uninitialized element
          |
          |--- [ 第三道安全校验: 动态函数签名强类型精确比对 (Type Signature Matching) ]
          |    验证 Table[table_index].actual_type_idx == call_indirect_declared_type_idx?
          |    若不匹配 -> 抛出 RuntimeError: indirect call type mismatch
          |
          v
   [ 安全校验全部通过! ]
   读取底层可执行机器码地址, 执行 CPU 间接跳转指令: call rax

`call_indirect` 校验的微架构开销与优化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

`call_indirect` 通过三次连环校验实现了严格的**控制流完整性（Control Flow Integrity, CFI）**：
1. **边界检查**：阻断任意越界索引寻址；
2. **非空检查**：防止跳转进入野指针和零地址段；
3. **类型签名检查**：确保即使索引被蓄意篡改，所执行的目标函数也必须拥有与调用处完全一致的参数与返回值签名，从物理层面杜绝了通过栈帧错位破坏寄存器状态的漏洞利用链条。

在 JIT 编译生成的汇编层面，V8 引擎通过将 Table 的基址和类型索引内联进调用跳板中，将这三道校验指令压缩至不足 6 条轻量级汇编指令以内，保持了极高的间接调用吞吐率。

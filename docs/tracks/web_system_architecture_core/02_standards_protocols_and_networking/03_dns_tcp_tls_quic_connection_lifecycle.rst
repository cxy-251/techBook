========================================================================
Chapter 8: 传输层连接建立全景：DNS、TCP、TLS 1.3 与 QUIC
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了 URL 的四重系统角色、WHATWG 解析状态机与同源策略（SOP）的安全判定。当浏览器通过 URL 锁定目标网络资源的 Host 与协议后，渲染主链路并不能立即发起 HTTP 语义交互，而是必须先穿越物理网络拓扑，在客户端与目标服务器之间建立安全、可靠的传输层双向管道。本章将系统解构 DNS 分层递归解析与现代安全加密（DoH/DoT）、TCP 三次握手与慢启动拥塞控制状态机、TLS 1.2 vs TLS 1.3 密钥协商握手延迟优化（从 2-RTT 到 1-RTT/0-RTT），以及基于 UDP 构建的下一代传输协议 QUIC（HTTP/3 核心底座）的连接迁移与单 RTT 握手微架构。

------------------------------------------------------------------------
8.1 DNS 寻址微架构：从分层递归解析到 DoH/DoT 安全加密
------------------------------------------------------------------------

当浏览器准备向 `https://example.com/api` 发送请求时，第一道物理屏障是将人类可读的字符串域名解析为底层路由所需的 IPv4（32-bit）或 IPv6（128-bit）物理 IP 地址。

域名解析的五级阶梯式查找链路
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       DNS 五级阶梯式缓存与递归解析拓扑                  |
   +-------------------------------------------------------------------------+

   [ 浏览器发起域名寻址: example.com ]
        |
        v (1. 命中则直接返回，TTL 衰减)
   [ 浏览器内部 DNS 缓存 (Chrome: chrome://net-internals/#dns) ]
        |
        v (2. 检查系统 hosts 文件与本地网络服务)
   [ 操作系统内核 DNS 缓存 (macOS: mDNSResponder / Windows: DNS Client) ]
        |
        v (3. 局域网网关查询)
   [ 本地家庭/企业路由器 DNS 缓存 ]
        |
        v (4. 递归解析起点)
   [ 本地 ISP 递归 DNS 服务器 (Local DNS / LDNS) ]
        |
        +---> [ 全球根域名服务器 (Root Nameservers - 13组任播 Anycast 集群) ]
        |        | 响应: 返回负责 .com 的顶级域名服务器 IP
        |        v
        +---> [ 顶级域名服务器 (TLD Nameservers - .com 集群) ]
        |        | 响应: 返回负责 example.com 的权威域名服务器 IP
        |        v
        +---> [ 权威域名服务器 (Authoritative Nameservers - 如 Cloudflare/DNSPod) ]
                 | 响应: 返回目标服务器 A/AAAA 记录 (如 93.184.216.34)

DNS 性能瓶颈与安全缺陷
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **RTT 往返时延累加**：在未经缓存的首次冷启动解析中，递归查询需要跨越多个大洲的主干网络，带来 $50	ext{ms} \sim 300	ext{ms}$ 的纯寻址等待。
- **UDP 明文传输风险**：传统 DNS 采用 UDP 53 端口无加密明文通信，极易在局域网与运营商链路中遭受 **DNS 劫持（DNS Hijacking）**、**缓存投毒（DNS Cache Poisoning）** 与流量嗅探。

现代 DNS 加密传输协议 (DoH vs DoT)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. list-table:: 现代 DNS 安全加密协议对比矩阵
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 协议类型
     - 传输层与端口
     - 握手协议与标准化
     - 防嗅探与网络穿透特性
   * - **传统 DNS**
     - UDP / TCP 53 端口
     - 无加密（RFC 1035）
     - 完全明文暴露，极易被防火墙审查或中间人伪造
   * - **DoT (DNS over TLS)**
     - TCP 853 端口
     - 专用 TLS 加密（RFC 7858）
     - 链路级强加密，但由于使用独立 853 端口，易被企业网关识别拦截
   * - **DoH (DNS over HTTPS)**
     - TCP / UDP 443 端口
     - HTTPS 报文（RFC 8484）
     - **与常规 Web 流量完全融合**；CDN 节点直接响应，具备极高穿透力与防伪造能力

8.2 TCP 三次握手与慢启动 (Slow Start) 拥塞控制
------------------------------------------------------------------------

在获取目标物理 IP 后，客户端网络栈必须与目标服务器建立面向连接的、可靠的传输控制协议（TCP）会话。

三次握手 (Three-Way Handshake) 状态机与 1-RTT 开销
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                        TCP 三次握手物理时延时序                         |
   +-------------------------------------------------------------------------+

   Client (客户端)                                    Server (服务端)
      |                                                     |
      | -------- [ 1. SYN: seq = x ] ---------------------> | (状态: LISTEN -> SYN_RCVD)
      |                                                     |
      | <------- [ 2. SYN-ACK: seq = y, ack = x + 1 ] ----- |
      |                                                     |
      | -------- [ 3. ACK: ack = y + 1 ] + (首包 HTTP 数据) -> | (状态: ESTABLISHED)
      |                                                     |
      [ 经历完整 1 个 RTT (Round-Trip Time) 往返时延后，连接正式建立 ]

- **SYN Flood 攻击与 SYN Cookies 防御**：攻击者通过发送海量伪造源 IP 的 SYN 包打满服务端的半连接队列（Half-Open Backlog）。现代内核通过 `tcp_syncookies` 算法，直接利用客户端 IP、端口与时间戳哈希计算初始序列号 $y$，无需在服务端分配内存即可抵抗拒绝服务攻击。

TCP 慢启动 (Slow Start) 与拥塞窗口 (cwnd) 限制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

新建的 TCP 连接无法立即以满带宽发送数据，必须经历**慢启动（Slow Start）**阶段以探测链路容量：

1. **初始拥塞窗口 (Initial Congestion Window - `initcwnd`)**：依据 RFC 6928，现代操作系统默认设置为 10 个最大报文段（MSS，约 $14.6	ext{ KB}$）。
2. **指数翻倍扩张**：每收到一个完整窗口的 ACK 确认，拥塞窗口翻倍（$10 	o 20 	o 40 	ext{ MSS}$），直至触碰慢启动阈值（`ssthresh`）或发生丢包。
3. **首屏加载代价**：若一个 HTML 页面体积为 $100	ext{ KB}$，即使服务器带宽高达 1Gbps，也必须经历约 3~4 个 RTT 的往返才能完成全部数据发送！

------------------------------------------------------------------------
8.3 TLS 1.2 vs TLS 1.3 密钥协商握手与 0-RTT 会话复用
------------------------------------------------------------------------

在 TCP 连接建立后，HTTPS 必须通过传输层安全协议（TLS）协商对称加密密钥，以保障通信机密性与完整性。

TLS 1.2 的 2-RTT 延迟瓶颈
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 TLS 1.2（RFC 5246）中，完成身份认证与密钥协商需要 **整整 2 个 RTT**：

1. `ClientHello` $	o$ `ServerHello + Certificate + ServerKeyExchange` (1-RTT)
2. `ClientKeyExchange + ChangeCipherSpec` $	o$ `Finished + ChangeCipherSpec` (2-RTT)
3. 加上底层 TCP 握手，从连接发起至首字节数据发送共需 **3-RTT**！

TLS 1.3 (RFC 8446) 的 1-RTT 革命
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

TLS 1.3 彻底剔除了脆弱的静态 RSA 密钥交换算法，强制要求使用具备**前向安全性（Forward Secrecy）**的临时 Diffie-Hellman 算法（ECDHE），并将握手时延直接减半至 **1-RTT**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                        TLS 1.3 极速单 RTT 握手时序                      |
   +-------------------------------------------------------------------------+

   Client                                             Server
      |                                                 |
      | --- [ ClientHello + SupportedGroups           |
      |       + KeyShare (预测性携带椭圆曲线公钥参数) ] --> |
      |                                                 | (服务端单程计算共享主密钥!)
      | <-- [ ServerHello + KeyShare                  |
      |       + EncryptedExtensions + Certificate     |
      |       + CertVerify + Finished ] --------------- | (握手消息全加密!)
      |                                                 |
      | === [ 对称加密通道瞬间建立！直接发送 HTTP 载荷 ] ====> |

0-RTT 早期数据会话恢复 (Early Data / Pre-Shared Key)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当客户端与服务器曾经建立过连接时，服务端会下发一个预共享密钥凭单（NewSessionTicket）。当用户再次重连该站点时：

- 客户端在重连的首个 TCP 包中，直接附带通过 PSK 加密的 **Early Data（0-RTT 载荷）**；
- **重放攻击（Replay Attack）防范准则**：由于中间人可以拦截并重复广播 0-RTT 数据包，**RFC 8446 严格规定 0-RTT 仅可用于幂等的只读请求（如 HTTP GET），严禁承载改变状态的 POST/PUT 交易**！

8.4 QUIC 协议与 HTTP/3 传输层革命
------------------------------------------------------------------------

尽管 TCP + TLS 1.3 已经做到了极致优化，但 TCP 协议固有的两大物理缺陷依然桎梏着现代 Web：

1. **协议栈僵化 (Ossification)**：TCP 固化在操作系统内核与全球路由器固件中，升级微小改动需耗时数十年。
2. **传输层队头阻塞 (Transport-Level Head-of-Line Blocking)**：在 HTTP/2 多路复用中，若底层 TCP 发生哪怕一个数据包丢失，操作系统内核将强制暂停接收缓冲区中后续所有已到达的 Stream 数据，直到丢失的 TCP 包重传完毕！

QUIC (Quick UDP Internet Connections - RFC 9000) 核心架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

QUIC 彻底抛弃了内核 TCP，直接建立在用户态 UDP 之上，实现了传输层与安全层的完全重构：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   传统 HTTPS 栈 vs 现代 HTTP/3 (QUIC) 协议栈            |
   +-------------------------------------------------------------------------+

   [ 传统 HTTPS (HTTP/2) ]                   [ 现代 HTTP/3 (QUIC) ]
   +------------------------------+         +------------------------------+
   | HTTP/2 应用层 (二进制分帧)   |         | HTTP/3 应用层 (QPACK 头部压缩)|
   +------------------------------+         +------------------------------+
   | TLS 1.3 安全传输层           |         | QUIC 协议 (用户态实现)       |
   +------------------------------+         | - 单 RTT 加密与连接一体化    |
   | TCP 传输层 (内核态/队头阻塞) |         | - 原生独立流 (无队头阻塞)    |
   +------------------------------+         | - 64-bit 连接迁移 ConnectionID|
   | IP 网络层                    |         +------------------------------+
   +------------------------------+         | UDP 数据报传输层 (极速无状态)|
                                            +------------------------------+
                                            | IP 网络层                    |
                                            +------------------------------+

QUIC 关键微架构优势
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **单 RTT 握手全融合**：QUIC 将传输层连接建立与 TLS 1.3 加密握手合并为单个交互。初次连接仅需 1-RTT，会话恢复仅需 0-RTT 即可开始双向数据传输。
2. **原生独立多路复用**：每个 QUIC Stream 拥有完全独立的序列号与滑动窗口。当 Stream A 丢包时，仅 Stream A 进入单流等待，Stream B 与 Stream C 保持全速吞吐，彻底根治队头阻塞。
3. **连接迁移 (Connection Migration)**：
   传统 TCP 依据四元组 `(SrcIP, SrcPort, DstIP, DstPort)` 标识连接，当手机从 Wi-Fi 切换到 5G 移动蜂窝网络时，IP 改变导致 TCP 强制断开重连。
   QUIC 使用全局唯一的 **64 位 Connection ID** 标识逻辑连接，无论客户端 IP 与端口如何变动，通信链路始终保持活跃与无缝漫游！

8.5 网络连接时延预算 (RTT Budget) 与全链路瀑布图
------------------------------------------------------------------------

物理世界的光速传播限制（光纤中光速约为 $2 	imes 10^8	ext{ m/s}$，每 $1000	ext{km}$ 往返带来约 $10	ext{ms}$ 理论硬时延）决定了连接建立阶段的 RTT 消耗是页面首字节时间（TTFB）的决定性瓶颈。

   :widths: 25 25 25 25
   :header-rows: 1
   :class: tight-table

   * - 协议栈组合
     - 冷启动握手阶段
     - 经历 RTT 轮次

   * - **HTTP/1.1 + TLS 1.2**
     - DNS + TCP (1) + TLS 1.2 (2) + HTTP (1)
     - **5 RTT**
     - **500 ms**
   * - **HTTP/2 + TLS 1.3**
     - DNS + TCP (1) + TLS 1.3 (1) + HTTP (1)
     - **3 RTT**
     - **300 ms**
   * - **HTTP/3 (QUIC 冷连)**
     - DNS + QUIC (1) + HTTP/3 (1)
     - **2 RTT**
     - **200 ms**

     - DNS 缓存 + QUIC 0-RTT 数据随路发送

浏览器端连接预热优化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了进一步抹平传输层握手时延，前端架构师应在 HTML 头部显式注入连接提示：

.. code-block:: html

   <!-- 提前发起 DNS 递归解析 -->
   <link rel="dns-prefetch" href="https://api.example.com">

   <!-- 提前建立 TCP + TLS 1.3 安全加密连接管道 -->
   <link rel="preconnect" href="https://cdn.example.com" crossorigin>

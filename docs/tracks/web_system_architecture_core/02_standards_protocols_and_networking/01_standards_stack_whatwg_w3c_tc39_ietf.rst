========================================================================
Chapter 6: Web 标准组织分层契约：WHATWG、W3C、TC39 与 IETF
========================================================================

.. note:: 前置背景与认知承接
   第一模块（Chapter 1~5）系统解构了现代 Web 的系统集成表面、多执行区演进、五大执行边界拓扑与全栈框架封装机理。从本章开始，全书进入第二模块——标准契约、网络协议与资源交付。Web 是人类计算历史上规模最大、跨厂商博弈最复杂的开放平台。浏览器之所以能够解析并运行来自全球数以亿计不同源的代码，根本原因在于其严格遵循了一套跨厂商分层的标准化平台契约。本章将深入解构 WHATWG、W3C、TC39 与 IETF 四大核心标准组织的分层契约、Living Standard 演进机制与 Web 平台测试套件（WPT）的互操作性保障。

6.1 Web 平台的开放标准分层金字塔
------------------------------------------------------------------------

现代 Web 平台的稳定性并非建立在任何单一商业公司的私有技术之上，而是建立在由四大国际标准化组织共同维护的分层契约金字塔之上：

.. list-table:: 现代 Web 平台四大标准组织分工与治理矩阵
   :widths: 18 20 32 30
   :header-rows: 1
   :class: tight-table

   * - 标准组织
     - 核心治理主体
     - 维护规范领域与核心标准
     - 规范发布范式与生命周期
   * - **WHATWG**
(Web 超文本应用工作组)
     - 浏览器引擎核心厂商
(Apple, Google, Mozilla, Microsoft)
     - **HTML、DOM、Fetch、URL、Streams、Encoding、Web Storage**
     - **Living Standard (活标准)**
无固定版本号，随引擎实现持续滚动提交
   * - **W3C**
(万维网联盟)
     - 全球企业、科研机构与标准化组织
     - **CSS 规范簇 (CSS WG)、WebGPU、WebAuthn、ARIA 无障碍树、WebAssembly (联合)**
     - **Recommendation (正式推荐标准)**
从 WD $	o$ CR $	o$ PR $	o$ REC 阶段制推进
   * - **TC39**
(Ecma 技术委员会 39)
     - 语言设计专家、引擎实现者、学术界
     - **ECMAScript (JavaScript 语言规范)、Test262、Intl 国际化 API**
     - **Stage 0~4 提案推进制**
每年 6 月发布年度固定快照 (ES2024/ES2025)
   * - **IETF**
(互联网工程任务组)
     - 国际互联网技术专家、网络运营商
     - **TCP、TLS 1.3、QUIC、HTTP/1.1~HTTP/3、WebSockets、WebRTC (传输层)**
     - **RFC 文档体系 (Request for Comments)**
从 Proposed Standard $	o$ Internet Standard

6.2 WHATWG vs W3C：从 XHTML 分裂到 Living Standard 统一
------------------------------------------------------------------------

理解现代 HTML 与 DOM 规范的运作逻辑，必须回溯一段深刻的标准化博弈历史：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  Web 标准化演进历史：从对抗走向 Living Standard 统一     |
   +-------------------------------------------------------------------------+

   [ 2000年代初: W3C 推动 XHTML 2.0 ]
        * 试图强推严苛的 XML 语法格式；
        * 遇到微小语法错误直接黄屏死锁 (Draconian Error Handling)，破坏既有 Web。
        |
        +---> [ 2004年: 浏览器厂商成立 WHATWG 独立对抗 ]
        |        * 确立核心铁律: "Don't break the Web" (不破坏现有 Web)；
        |        * 编写 HTML5 规范，确立容错词法状态机与 DOM 原生 API。
        v
   [ 2019年: W3C 与 WHATWG 签署历史性合作备忘录 (MOU) ]
        |
        +---> WHATWG 成为 HTML 与 DOM 唯一权威事实源 (Single Source of Truth)；
        +---> W3C 放弃独立制定 HTML，转为同步 WHATWG 活标准并发布快照。

Living Standard (活标准) 的工程哲学
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **持续交付与零版本停滞**：不再设定“HTML6”或“DOM5”等固化大版本。规范文档直接托管于 GitHub，任何浏览器引擎完成新特性的互操作性验证后，规范即时合并生效。
- **以事实实现为导向 (Implementation-Driven)**：如果所有主流浏览器引擎在某个边界行为上的物理实现与文本规范冲突，**修改规范以匹配浏览器事实行为**，而非强行要求浏览器破坏亿万既有网站的兼容性。

6.3 TC39 标准化推进流程与语言演进机制
------------------------------------------------------------------------

JavaScript（ECMAScript）的演进受严格的 TC39 五阶段流程（Stage 0 至 Stage 4）治理：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       TC39 语言特性提案推进状态机                       |
   +-------------------------------------------------------------------------+

   [ Stage 0: 稻草人阶段 (Strawman) ]
        |  * 初始构想，社区与委员会成员均可提交
        v
   [ Stage 1: 正式提案 (Proposal) ]
        |  * 确定问题空间与解决诉求，产出高层 API 形状设计与跨模块考量
        v
   [ Stage 2: 草案阶段 (Draft) ]
        |  * 使用精确的 ECMAScript 规范形式语言（元语法）完整描述语法与执行语义
        v
   [ Stage 3: 候选阶段 (Candidate) ]
        |  * 规范语义完全定型，必须产出完整的测试套件；
        |  * 【硬性条件】: 至少需要 2 个独立引擎（如 V8、JSC、SpiderMonkey）完成全功能实验性实现
        v
   [ Stage 4: 完成阶段 (Finished) ]
           * 全量合入 Test262 官方测试套件，正式并入下一年度的 ECMAScript 标准

在前端工程化中，Babel / SWC 转换器与 Polyfill 仅应在 Stage 3 阶段介入生产环境，避免因早期 Stage 提案语法大幅变动引发不可维护的工程风险。

6.4 Web 平台的互操作性契约与 Web Platform Tests (WPT)
------------------------------------------------------------------------

过去开发者必须针对 IE、Firefox、Chrome 编写大量差异化的兼容分支（User-Agent Sniffing）。现代 Web 平台的兼容性保障，完全依托于工业级测试基建——**Web Platform Tests (WPT)**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  WPT 跨浏览器引擎自动化互操作性流水线                   |
   +-------------------------------------------------------------------------+

   [ 官方 WPT 测试仓库 (数十万个跨标准自动化用例) ]
        |
        +---> [ Chromium (Blink / V8) CI 流水线 ]     --> 自动对齐测试通过率
        +---> [ WebKit (Safari / JSC) CI 流水线 ]     --> 自动捕获规范偏离
        +---> [ Gecko (Firefox / SpiderMonkey) CI ]  --> 持续回归验证

- **每日持续集成验证**：各大引擎每次代码提交，均自动运行全量 WPT 测试。一旦某引擎的实现与其他引擎存在偏差，CI 立即报错阻断合并。
- **Interop 联合行动 (Interop 2023/2024/2025)**：Apple、Google、Microsoft、Mozilla 等厂商每年联合签署年度互操作性目标，集中攻克 Container Queries、Subgrid、CSS Nesting、WebCodecs 等前沿标准的跨平台一致性。

6.5 渐进增强原则与现代 Baseline 理念
------------------------------------------------------------------------

在面对碎片化的用户终端时，现代架构设计应当贯彻两大核心准则：

渐进增强 (Progressive Enhancement) 与特性检测 (Feature Detection)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

绝对禁止使用 User-Agent 字符串判定浏览器能力。必须使用原生**特性检测（Feature Detection）**：

.. code-block:: javascript

   // JavaScript 运行时特性检测
   if ('gpu' in navigator) {
       // 浏览器支持 WebGPU，加载高性能硬件光线追踪渲染管线
       initWebGPUPipeline();
   } else {
       // 平滑降级至 WebGL 2.0 传统光栅化管线
       initWebGLFallback();
   }

.. code-block:: css

   /* CSS 样式层级特性检测 */
   @supports (container-type: inline-size) {
       .card-container {
           container-type: inline-size;
       }
   }

Baseline 工业级选型标准
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了消除团队在技术选型时的犹豫与风险，Web 平台确立了 **Baseline** 标准分级：

1. **新可用 (Newly Available)**：当某项特性在 Chrome、Edge、Firefox、Safari 四大核心浏览器的最新稳定版中均获得支持时，被标记为 Newly Available；
2. **广泛可用 (Widely Available)**：当该特性在全平台稳定版支持**满 30 个月**后，自动升格为 Widely Available。架构师可放心在生产环境中直接使用，无需任何 Polyfill 或降级保护。

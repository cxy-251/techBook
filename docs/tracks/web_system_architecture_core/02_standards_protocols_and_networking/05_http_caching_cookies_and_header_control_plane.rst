================================================================================
HTTP 控制平面：Cache-Control 强弱缓存、条件请求、Cookie 属性与 Vary 机制
================================================================================

.. note:: 前置背景与上下文承接

   在上一章中，我们解构了从 HTTP/1.1 纯文本管道化、HTTP/2 二进制分帧多路复用，到 HTTP/3 基于 QUIC/UDP 消除传输层队头阻塞的演进历程。然而，无论底层传输管道如何优化，物理距离与带宽消耗依然存在固有上限。本章将深入 HTTP 控制平面（Control Plane），剖析 RFC 9111 缓存规范、强弱缓存决策状态机、条件请求验证、状态保持凭证（Cookie）及跨网关 Vary 缓存键扩展，建立端到端无冗余传输的控制体系。

--------------------------------------------------------------------------------
HTTP 缓存架构层次与 RFC 9111 规范语义
--------------------------------------------------------------------------------

现代 Web 系统中的 HTTP 缓存并非单点内存池，而是分布在请求链路上的层次化存储拓扑。根据 RFC 9111（前身为 RFC 7234），HTTP 缓存分为私有缓存（Private Cache）与共享缓存（Shared Cache）两大类。

.. list-table:: 典型 HTTP 缓存拓扑节点及其物理特性对比
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 缓存层次
     - 物理承载实体
     - 作用域与隔离级别
     - 典型读写延迟与容量上限
   * - 内存缓存 (Memory Cache)
     - 浏览器 Renderer 进程堆内存
     - 单页面会话生命周期，进程独占
     - 延迟 < 1ms，容量受进程上限限制（通常 < 200MB）
   * - 磁盘缓存 (Disk Cache)
     - 浏览器 Network 进程文件系统
     - 跨标签页、跨会话共享，Origin 隔离
     - 延迟 5~20ms，容量受操作系统配额管理（通常数 GB）
   * - 边缘缓存 (Edge/CDN Cache)
     - Anycast PoP 节点 SSD/内存
     - 区域所有终端用户共享
     - 延迟 10~30ms，容量集群级扩展（数 TB 至 PB 级）
   * - 源站前置反向代理
     - Nginx / Varnish / API Gateway
     - 保护后端应用集群
     - 延迟 < 5ms（内网链路），容量数百 GB 至 TB 级

根据规范，缓存命中的基本判定条件建立在请求方法、请求 URI 及相应头部控制字段的代数集合上。默认情况下，仅针对安全且幂等的 GET、HEAD 请求执行响应存储；POST、PUT、DELETE 等修改状态的操作不仅自身不可缓存，还会对匹配 URI 的现有缓存条目触发隐式失效（Invalidation）。

--------------------------------------------------------------------------------
Cache-Control 指令集与新鲜度计算模型
--------------------------------------------------------------------------------

HTTP/1.1 废弃了依赖绝对物理时钟的 ``Expires`` 头部，转而采用以秒为单位的相对时间指令集 ``Cache-Control``。新鲜度生命周期（Freshness Lifetime）的计算决定了客户端是否可以直接使用本地副本而无需发起网络事务。

核心指令语义与执行策略
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``Cache-Control`` 由一组以逗号分隔的单向或双向指令组成，覆盖存储策略、新鲜度期限及重新验证要求。

.. list-table:: Cache-Control 核心指令语义与执行约束
   :widths: 25 35 40
   :header-rows: 1
   :class: tight-table

   * - 控制指令
     - 规范适用主体
     - 物理行为与执行约束
   * - ``no-store``
     - 客户端 / 中介网关 / 源站
     - 禁止任何节点将响应写入持久化或临时存储，严格防御敏感数据泄漏
   * - ``no-cache``
     - 客户端 / 中介网关
     - 允许存储副本，强制使用前必须向源站发起条件请求验证新鲜度
   * - ``max-age=<seconds>``
     - 客户端 / 共享缓存
     - 资源自生成或验证通过起，可被视作新鲜状态的相对秒数
   * - ``s-maxage=<seconds>``
     - 仅限共享中介缓存（CDN / 代理）
     - 覆盖 ``max-age`` 与 ``Expires``，专用于公共边缘节点
   * - ``public``
     - 中介网关
     - 显式声明即使包含 Authorization 头部，中介缓存亦可共享存储
   * - ``private``
     - 浏览器终端
     - 仅限最终用户的单一客户端设备存储，严禁 CDN 等共享网关暂存
   * - ``immutable``
     - 客户端
     - 声明在有效生命期内内容永不变更，刷新页面时抑制条件验证请求
   * - ``stale-while-revalidate=<sec>``
     - 客户端 / 共享网关
     - 允许过期间隔内直接返回陈旧数据，同时在后台异步发起重验

新鲜度寿命与当前年龄代数推导
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

RFC 9111 定义了严密的新鲜度判定算法。当且仅当响应的当前年龄（Current Age）小于新鲜度寿命（Freshness Lifetime）时，响应被视为有效新鲜：

.. math::

   	ext{is\_fresh} = 	ext{CurrentAge} < 	ext{FreshnessLifetime}

其中新鲜度寿命优先取自明确配置的指令值：

.. math::

   	ext{FreshnessLifetime} = \begin{cases}
   s	ext{-maxage}, & 	ext{若存在且处于共享缓存} \
   max	ext{-age}, & 	ext{若存在显式 max-age} \
   	ext{Expires} - 	ext{Date}, & 	ext{若存在绝对过期头部} \
   (	ext{Date} - 	ext{Last-Modified}) 	imes 0.1, & 	ext{启发式默认估计（Heuristic）}
   \end{cases}

当前年龄由响应在传输链路上的驻留时间、网络往返时延（RTT）及上游中介注入的 ``Age`` 头部累加计算：

.. math::

   	ext{ApparentAge} = \max(0, 	ext{ResponseTime} - 	ext{Date})

.. math::

   	ext{CorrectedAge} = 	ext{AgeValue} + (	ext{ResponseTime} - 	ext{RequestTime})

.. math::

   	ext{CurrentAge} = 	ext{CorrectedAge} + (	ext{CurrentTime} - 	ext{ResponseTime})

这一公式消除了客户端与源服务器之间的物理时钟偏移（Clock Skew）对有效性判定的干扰。

--------------------------------------------------------------------------------
条件请求与弱验证器状态机：ETag 与 Last-Modified
--------------------------------------------------------------------------------

当缓存副本过期（Stale）后，客户端无需直接全量重拉资源，而是通过携带验证器发起条件请求（Conditional Request），由服务端判定内容是否发生实质变更。

强验证器 (ETag) 与弱验证器 (W/ETag)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

实体标签（Entity Tag，ETag）是资源状态的不透明指纹标识符（Opaque Token）：

1. **强验证器 (Strong ETag)**：格式形如 ``ETag: "1234abcd"``。保证实体在字节级别完全等同。只要资源发生一个字节的变更，强 ETag 必须改变。强验证器可用于范围请求（Range Request / 206 Partial Content）的断点续传验证。
2. **弱验证器 (Weak ETag)**：格式形如 ``ETag: W/"1234abcd"``。仅保证实体在语义层面上等价。例如对 HTML 执行等价的空白符压缩、动态时间戳轻度修改，均可保留弱 ETag。弱 ETag 严禁用于支持断点续传的范围请求验证。

时间戳验证器 (Last-Modified)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``Last-Modified`` 记录资源最后一次在文件系统或数据库中的修改时间戳（精确至秒）。受限于 HTTP-date 格式的时间精度，一秒内发生的多次写操作无法被正确区分，因此通常作为 ETag 之后的第二优先级兜底验证机制。

条件验证状态转移矩阵
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

客户端通过头部映射将本地记录的指纹回传至服务端：

- ``ETag`` 映射为 ``If-None-Match: "1234abcd"``
- ``Last-Modified`` 映射为 ``If-Modified-Since: Tue, 01 Sep 2026 12:00:00 GMT``

服务端的校验执行顺序遵循 RFC 9110 规定的严格前置条件判定状态机：

.. code-block:: text

   [收到条件请求]
          |
          v
   检查是否存在 If-None-Match ?
         / \
       Yes  No
       /      \
      v        v
   匹配当前 ETag?   检查是否存在 If-Modified-Since ?
     /   \                      / \
   Match  Mismatch            Yes  No
    /       \                 /      \
   v         v               v        v
  [304]     [200]      资源在此之后修改?  [200 全量返回]
                         /   \
                       Yes    No
                       /        \
                      v          v
                    [200]       [304 未修改]

当命中 304 Not Modified 时，服务端仅返回 HTTP 状态行及更新后的头部（例如刷新 ``max-age``），省略 Body 实体，将网络字节传输降至数百字节的纯元数据负载。

--------------------------------------------------------------------------------
状态保持控制：Cookie 核心属性与安全隔离
--------------------------------------------------------------------------------

HTTP 本身为无状态协议。为在跨请求会话中追踪用户身份与应用上下文，网景公司引入的 Cookie 机制经 RFC 6265 形成了受控状态存储模型。

Cookie 物理构成与传输机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当服务端向客户端响应头注入 ``Set-Cookie`` 时，浏览器将其持久化至私有 Cookie 数据库（按 `Domain` 与 `Path` 双重索引）。在此后的每个匹配网络请求中，浏览器都会自动在请求头部序列化拼接 ``Cookie: key1=value1; key2=value2``。

.. list-table:: Set-Cookie 关键属性及其安全约束
   :widths: 20 30 50
   :header-rows: 1
   :class: tight-table

   * - Cookie 属性
     - 取值规范
     - 物理防御边界与约束机制
   * - ``HttpOnly``
     - 布尔标志（无值）
     - 彻底切断客户端 DOM API 访问通道，``document.cookie`` 无法读取，防御 XSS 凭据窃取
   * - ``Secure``
     - 布尔标志（无值）
     - 仅当连接为 TLS 加密通道（HTTPS）时才允许传输，防御中间人明文嗅探
   * - ``SameSite``
     - ``Strict`` / ``Lax`` / ``None``
     - 控制跨站点（Cross-Site）上下文下的携带策略，防御跨站请求伪造（CSRF）
   * - ``Domain``
     - 域名字符串（如 ``example.com``）
     - 显式设置包含所有子域；未设置时默认仅限当前完全限定域名（FQDN）且不包含子域
   * - ``Path``
     - 绝对路径字符串
     - 仅当请求路径以该前缀开头时方才携带，实现应用内部路径级物理隔离
   * - ``Max-Age`` / ``Expires``
     - 秒数 / RFC 1123 日期
     - 定义持久化到磁盘的过期时刻；未设置时作为 Session Cookie，浏览器关闭即销毁

SameSite 状态机与跨站点边界
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``SameSite`` 属性是抵御跨站请求伪造（CSRF）的关键机制。其核心判定依赖有效顶级域名加一级子域名（eTLD+1）：

1. **SameSite=Strict**：在任何跨站点请求中完全禁止携带该 Cookie，即使是从外部网站点击普通超链接跳转亦被阻断。
2. **SameSite=Lax**：默认安全级别。在跨站点导航中，仅当满足“顶级导航（Top-Level Navigation）”且请求方法为“安全方法（GET/HEAD 等）”时才允许携带；对于所有 POST 跨站请求或 ``<iframe>``、``<img>`` 嵌套请求均予拦截。
3. **SameSite=None**：允许跨站请求在所有场景下携带，但规范强制要求必须同时配置 ``Secure`` 标志，确保跨域传输始终受 TLS 保护。

--------------------------------------------------------------------------------
Vary 机制与多维缓存键 (Cache Key) 拆解
--------------------------------------------------------------------------------

默认情况下，HTTP 缓存键（Cache Key）由以下元组严格构成：

.. math::

   	ext{CacheKey}_{	ext{default}} = \langle 	ext{HTTP Method}, 	ext{Request URI} \rangle

多维度内容协商的缓存混淆问题
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当源站根据客户端请求头提供差异化表示时（例如响应头由 ``Accept-Encoding`` 决定采用 Gzip 还是 Brotli 压缩；由 ``Accept-Language`` 决定英语还是中文；由客户端指纹分发移动端或桌面端视图），简单的 URI 缓存键会导致严重的缓存污染（例如将返回给移动端的内容错误缓存并提供给桌面端）。

Vary 头的协议语义与缓存键扩展
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``Vary`` 响应头告知下游各级缓存系统：在计算缓存条目唯一性时，必须将所列出的请求头部字段作为辅助维度注入主缓存键中：

.. math::

   	ext{CacheKey}_{	ext{extended}} = \langle 	ext{Method}, 	ext{URI}, 	ext{RequestHeader}[	ext{Field}_1], \dots \rangle

当源站返回：

.. code-block:: http

   HTTP/1.1 200 OK
   Content-Type: text/html; charset=utf-8
   Content-Encoding: br
   Vary: Accept-Encoding, User-Agent

缓存网关针对该资源将分化出二维索引空间：

.. list-table:: 扩展缓存键下的独立存储实例映射
   :widths: 35 35 30
   :header-rows: 1
   :class: tight-table

   * - 请求头 Accept-Encoding
     - 请求头 User-Agent 特征
     - 缓存匹配结果
   * - ``gzip, deflate, br``
     - ``Mozilla/5.0 (Mobile)``
     - 实例 A (Brotli 压缩 + 移动布局)
   * - ``gzip, deflate, br``
     - ``Mozilla/5.0 (Windows NT)``
     - 实例 B (Brotli 压缩 + 桌面布局)
   * - ``gzip, deflate``
     - ``Mozilla/5.0 (Mobile)``
     - 实例 C (Gzip 压缩 + 移动布局)

过度 Vary 的缓存碎片化惩罚
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

直接使用 ``Vary: User-Agent`` 或未归一化的 ``Accept-Encoding`` 会导致极其严峻的缓存碎片化（Cache Fragmentation）。由于全球各浏览器的 User-Agent 字符串包含细微的版本差异与扩展注入，会导致缓存命中率骤降至接近 0%。

现代工程实践的规范化解决方案包括：

1. **网关层头部归一化 (Header Normalization)**：CDN 边缘节点在处理 Vary 之前，将成百上千种 ``Accept-Encoding`` 统一降采样为 ``br``、``gzip`` 或 ``identity`` 三个规范枚举值。
2. **区分设备类型标头**：通过边缘计算函数解析 User-Agent 后生成标准化特征标头（例如 ``X-Device-Type: mobile | desktop``），仅对该标准化衍生头执行 Vary。

现代 Web 应用缓存架构设计准则
--------------------------------------------------------------------------------

结合前端构建流水线与现代边缘架构，工业界确立了内容哈希与长期不可变缓存的标准分流范式：

.. list-table:: 现代 Web 静态与动态资源缓存架构标准模式
   :widths: 25 35 40
   :header-rows: 1
   :class: tight-table

   * - 资源类型与分类
     - 推荐 Cache-Control 策略
     - 工程配套与失效机制
   * - 带内容哈希的静态资源 (JS/CSS/WebP)
     - ``public, max-age=31536000, immutable``
     - 文件名包含 SHA-256 签名（如 ``app.a8f9c2.js``），更新代码即改变 URL，彻底消除缓存冲突
   * - 入口文档 (index.html)
     - ``no-cache``
     - 允许客户端本地缓存，但每次导航强制 304 条件请求验证，保证随时感知最新资源引用
   * - 动态业务接口 API
     - ``private, no-store`` 或 ``s-maxage=60, stale-while-revalidate=300``
     - 视实时性需求而定。高频读接口利用边缘短暂平滑削峰，结合 Cache-Tag 显式驱逐

小结与下章导读
--------------------------------------------------------------------------------

本章系统解构了 HTTP 控制平面的核心机制：从 RFC 9111 规范定义的新鲜度代数模型，到 ETag/Last-Modified 驱动的条件请求状态机；从 Cookie 在安全隔离维度的微架构约束，到 Vary 机制对多维缓存键的扩展控制。这些机制共同保障了 Web 系统在跨越数千公里网络链路时的极速响应与强一致性。

在掌握了传输层连接与控制平面交互之后，接下来的关键问题在于：当浏览器从一个源（Origin）跨域请求另一台源站的资源时，浏览器内核如何在底层施加权限约束与数据隔离？下一章将深入剖析：跨源资源共享 (CORS)、跨源隔离 (Cross-Origin Isolation) 与浏览器同源防御体系。

20.1 GPU 纹理处理单元 (TPU) 与纹理缓存微架构
------------------------------------------------------------------------

为什么 GPU 绝对不能使用 PNG、JPEG 或 WebP 等常规无损/有损图像压缩格式？

GPU 纹理采样的核心物理约束
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **确定性随机访问 ($O(1)$ Random Access)**：像素着色器以任意不可预测的 $(u, v)$ 坐标采样纹理。GPU 必须能在硬件单周期内，直接根据坐标数学计算出目标数据在显存中的物理字节偏移量。PNG/JPEG 的熵编码（Huffman / 算术编码）是变长流式编码，若要读取右下角的一个像素，必须先顺序解码整张图像。
2. **硬件流水线解压时延恒定**：GPU 硬件解压器必须在固定的时钟周期内完成解压并送入纹理滤波单元，不能产生不可控的计算分支发散与内存停顿。

纹理处理单元 (TPU) 与 Morton 瓦片化排列
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  现代 GPU 纹理采样流水线与缓存拓扑                      |
   +-------------------------------------------------------------------------+

   [ 像素着色器执行 Texture2D.Sample(uv) 指令 ]
        |
        v
   [ 1. 纹理地址发生器 (Texture Address Generator - TAG) ]
        |  * 计算屏幕偏导数 (ddx/ddy)，解算 Mipmap 等级与纹素坐标 (s, t)
        |  * 将 (s, t) 转换为 Morton Z-Order 瓦片化物理显存地址
        v
   [ 2. 片上 L1 纹理缓存 (Texture Cache - TC) ]
        |  * 命中则直接提供压缩块数据 (4x4 纹素块)
        |  * 未命中则向 L2 缓存 / 外部 LPDDR/GDDR 发起合并请求 (Coalesced Read)
        v
   [ 3. 硬件解压缩引擎 (Dedicated Decompression Unit) - 零延迟并行解压 ]
        |  * 并行将 BCn / ASTC 压缩块瞬间还原为浮点 Texel 颜色
        v
   [ 4. 纹理滤波单元 (Texture Filtering Unit - TFU) ]
        |  * 硬件执行双线性 (Bilinear) / 三线性 (Trilinear) / 各向异性加权插值
        v
   [ 返回最终过滤后的颜色矢量 (float4) 给着色器 ALU ]

- **Morton 码（Z-Order 曲线）与瓦片化（Tiling）**：
  传统行优先存储（Linear Layout）在 Y 轴方向跨行采样时会跨越极大的显存步长，引发灾难性的 Cache Miss。GPU 将纹理在显存中按照 $4 	imes 4$ 或 $8 	imes 8$ 的微小正方形瓦片进行 Z-Order 排列，确保空间相邻的 4 个双线性采样点在物理内存中永远紧邻存储，使得 L1 纹理缓存命中率达到 95% 以上！

20.2 桌面端块压缩算法全景：从 BC1 到 BC7
------------------------------------------------------------------------

**块压缩（Block Compression - BC）** 将图像划分为独立的 $4 	imes 4$ 像素块（包含 16 个 Texels），每个块独立编码为固定长度的 64-bit（压缩比 8:1，平均每像素 4 位 - 4 bpp）或 128-bit（压缩比 4:1，平均每像素 8 位 - 8 bpp）二进制块。

.. list-table:: DirectX / Vulkan 桌面端 BCn 纹理压缩标准全景矩阵
   :widths: 12 15 15 28 30
   :header-rows: 1
   :class: tight-table

   * - 格式名称
     - 块字节大小
     - 压缩率 (bpp)
     - 通道与端点微架构
     - 典型应用场景
   * - **BC1 (DXT1)**
     - 64-bit
     - 4 bpp (8:1)
     - 2 个 RGB565 端点 + 16 个 2-bit 线性插值索引（支持 1-bit Alpha 裁剪）
     - 不透明漫反射贴图 (Albedo/Diffuse)
   * - **BC3 (DXT5)**
     - 128-bit
     - 8 bpp (4:1)
     - 64-bit 颜色（同 BC1）+ 64-bit 独立 Alpha（2 个 8-bit 端点 + 3-bit 索引）
     - 包含平滑半透明通道的贴图 (RGBA)
   * - **BC4**
     - 64-bit
     - 4 bpp (8:1)
     - 单通道（2 个 8-bit 端点 + 3-bit 索引插值 8 级灰度）
     - 灰度遮罩、粗糙度 (Roughness)、高度图
   * - **BC5 (3Dc)**
     - 128-bit
     - 8 bpp (4:1)
     - **双通道解耦**（2 个独立 BC4 块分别存储切线空间法线 $X$ 与 $Y$）
     - **切线空间法线贴图 (Normal Map)**
   * - **BC6H**
     - 128-bit
     - 8 bpp (4:1)
     - **HDR 半精度浮点 (FP16)**，支持 14 种复杂几何分区模式
     - HDR 环境贴图、天空盒、辐射度缓存
   * - **BC7**
     - 128-bit
     - 8 bpp (4:1)
     - **高保真 RGBA**，支持 8 种模式、子块划分与独立 P-Bit 精度微调
     - 高品质次世代角色材质、次表面散射贴图

法线贴图的 BC5 压缩与数学还原
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

若将法线贴图存入 BC1，由于 RGB 通道被强制投影到同一根颜色轴上，$X$ 与 $Y$ 之间的相关性会引发严重的**交叉通道压缩失真（Cross-Channel Block Artifacts）**，导致光照高光产生破碎马赛克。

**BC5 的绝妙设计**：
1. 彻底剔除 $Z$ 分量，仅将 $X$ 和 $Y$ 分量分别用两个独立的 BC4 块进行高保真压缩；
2. 着色器采样后利用法线的单位长度约束（$\|\vec{n}\| = 1$），通过单条开方指令动态重建 $Z$ 分量：

.. math::

   n_z = \sqrt{\max\left(0, \; 1 - n_x^2 - n_y^2\right)}

- 不仅完全消除了通道干扰，且法线有效精度从 BC1 的 5~6 位跃升至精准的 8 位，彻底拯救了高光曲面画质！

20.3 移动端统一块压缩标准：ASTC 算法微架构
------------------------------------------------------------------------

在移动生态中，早期由各芯片厂商分裂割据的格式（高通 ATC、Imagination PVRTC、ARM ETC2）带来了巨大的包体打包冗余。ARM 与 Khronos 联合推出的 **ASTC（Adaptive Scalable Texture Compression）** 终结了碎片化，成为现代移动与主机平台的终极标准。

ASTC 的两大突破性设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **固定 128 位块大小 + 可变物理像素足迹 (Variable Block Footprint)**：
   ASTC 的每个压缩数据块固定为 128 位，但其覆盖的物理像素足迹可在 $4 	imes 4$ 到 $12 	imes 12$ 之间任意选择，实现了从超高质量到极限压缩比的平滑调节：

   .. math::

      	ext{bpp} = \frac{128	ext{ bits}}{	ext{BlockWidth} 	imes 	ext{BlockHeight}}

.. list-table:: 典型 ASTC 块足迹与压缩特性矩阵
   :widths: 20 20 25 35
   :header-rows: 1
   :class: tight-table

   * - 分块足迹 (Footprint)
     - 压缩比率 (bpp)
     - 内存压缩倍率
     - 工业级适用资产类型
   * - **ASTC 4x4**
     - 8.00 bpp
     - 4:1
     - 极高精度法线贴图、高精角色面部特写
   * - **ASTC 6x6**
     - 3.56 bpp
     - 9:1
     - **主流 3D 游戏通用默认材质、反照率贴图**
   * - **ASTC 8x8**
     - 2.00 bpp
     - 16:1
     - 远景地貌、植被叶片、粒子特效贴图
   * - **ASTC 12x12**
     - **0.89 bpp**
     - **36:1 (极度轻量)**
     - 移动端超轻量光照贴图 (Lightmap)、UI 装饰图

2. **有界整数序列编码 (BISE - Bounded Integer Sequence Encoding)**：
   在常规二进制编码中，存储一个取值范围为 $0 \sim 4$（基数 5）的三元量化值，必须占用 3-bit（浪费 $8 - 5 = 3$ 个状态空间）。
   **BISE 算法** 将 5 个基数 5 的三元组打包进 7-bit 整数中（$5^5 = 3125 < 2^{12} = 4096$），将信息熵利用率提升至 **99.6%**，在极其有限的 128 位空间内塞入了端点模式、分区索引与权重网格。

20.4 Mipmap 链、各向异性过滤与椭圆足迹采样
------------------------------------------------------------------------

当远离摄像机的三维物体表面贴图被投影到微小的屏幕像素网格时，单个屏幕像素可能覆盖了贴图上的数十个 Texels。若直接采样，将违反香农采样定理引发剧烈的莫尔条纹（Moiré Patterns）与高频走样闪烁。

Mipmap 金字塔构建与三线性插值 (Trilinear Filtering)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

GPU 预先为纹理生成一系列按 $2 	imes$ 逐级降采样的分辨率金字塔（Mip Level $0, 1, 2, \dots, N$）。着色器通过屏幕空间偏导数（$	ext{ddx} / 	ext{ddy}$）解算采样足迹跨度：

.. math::

   \rho = \max\left( \sqrt{\left(\frac{\partial u}{\partial x}\right)^2 + \left(\frac{\partial v}{\partial x}\right)^2}, \; \sqrt{\left(\frac{\partial u}{\partial y}\right)^2 + \left(\frac{\partial v}{\partial y}\right)^2} \right), \quad \lambda = \log_2(\rho)

- **三线性过滤**：先在连续浮点 Mip 等级 $\lfloor \lambda \rfloor$ 与 $\lceil \lambda \rceil$ 两层内部各自执行 4 采样点双线性插值（Bilinear），再在层间执行线性混合（Lerp），实现无缝的距离过渡。

各向同性过度模糊与各向异性过滤 (Anisotropic Filtering) 几何推导
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当物体表面以极大的掠射角（如地平线、平坦道路）面对摄像机时，圆形屏幕像素在纹理空间中的投影被剧烈拉伸为一个长宽比极大的**窄长椭圆足迹（Anisotropic Footprint）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  各向同性 Mipmap 模糊 vs 各向异性过滤足迹               |
   +-------------------------------------------------------------------------+

   纹理 UV 空间投影足迹:
                                    / / / (窄长各向异性椭圆, 轴长比 8:1)
   [ 传统各向同性 Mipmap ]:
   * 强制采用最大轴长作为正方形滤波核 (虚线大圆)
   * 结果: 沿短轴方向引入了数十倍的过度平均 -> 道路远端模糊成一片泥浆！
   ---------------------------------------------------------------------------
   [ 现代各向异性过滤 (16x AF) ]:
   * 硬件沿椭圆长轴方向均匀排布 N 个细分探针采样点 (Probes):
        ( * )---( * )---( * )---( * )---( * )---( * )---( * )---( * )
   * 在细化 Mip 等级下分别执行双线性采样并加权求和
   * 结果: 完美保留高频细节，道路标线与碎石纹理在极远端依然清晰锐利！

20.5 虚拟纹理系统 (Virtual Texturing / SVT) 与 Nanite 纹理基石
------------------------------------------------------------------------

在开放世界与影视级超大场景中，全场景 $8	ext{K} \sim 16	ext{K}$ 贴图的总数据量可轻易突破 100GB，远超物理显存（8GB~24GB）上限。**稀疏虚拟纹理（Sparse Virtual Texturing - SVT）** 通过将操作系统虚拟内存分页机制引入 GPU，彻底打破了显存墙。

SVT 虚拟化页表与物理缓存池架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     稀疏虚拟纹理 (SVT) 运行微架构                       |
   +-------------------------------------------------------------------------+

   [ 逻辑虚拟纹理空间 (巨型虚拟寻址, 如 64K x 64K, 切分为 128x128 虚拟页) ]
                                   |
        +--------------------------+--------------------------+
        | (查表命中: 虚拟页已换入显存)                         | (未命中: 触发异步加载)
        v                                                     v
   [ GPU 片上物理页表 (Page Table) ]               [ 写入反馈缓冲区 (Feedback Buffer) ]
        |                                                     |
        v                                                     v (CPU / IO 调度)
   [ 物理纹理缓存池 (Physical Page Pool) ]        [ 异步 DirectStorage / NVMe 流送 ]
   (显存中仅分配例如 2048 个实际物理槽位)            [ 从磁盘读取对应 128x128 Tile 写入显存 ]

反馈驱动的精准流送 (Feedback-Driven Streaming)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. **反馈缓冲输出 (Feedback Pass)**：
   着色器在渲染时，以低分辨率将当前视口真正能被看到的页面索引 `(Page_X, Page_Y, Mip_Level)` 写入轻量级的反馈缓冲区（Feedback Buffer）。
2. **零显存浪费与 Nanite 底座**：
   玩家背后的物体、被完全遮挡的建筑、以及超远距离模型的顶层高精 Mip 页面**永远不会被加载进显存**。物理显存中永远只常驻当前视锥内所需的数千个 Tile，使得渲染系统能够以仅仅 2GB 的物理显存预算，流畅渲染总数据量达数百 GB 的超写实数字孪生世界！

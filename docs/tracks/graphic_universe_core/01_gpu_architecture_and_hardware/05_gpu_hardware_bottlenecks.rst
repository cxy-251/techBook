5.1 GPU 性能约束模型：Roofline 模型与运行态上限
------------------------------------------------------------------------

在评估任何图形着色器（Shader）或通用计算内核（Compute Kernel）的执行效率时，**Roofline 性能模型**提供了最直观的理论天花板判定依据。该模型将算法的理论计算吞吐量绑定在两个物理极限之上：硬件峰值算力（Peak Compute Performance）与显存物理峰值带宽（Peak Memory Bandwidth）。

算术强度与 Roofline 坐标体系
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Roofline 模型的横轴为**算术强度（Arithmetic Intensity - $I$）**，定义为计算核心每从显存/缓存子系统读取或写入 1 字节数据所执行的浮点运算次数（FLOPs / Byte）；纵轴为**可达到的计算吞吐性能（Attainable Performance - $P$）**，单位为 TFLOPS：

.. math::

   P(I) = \min\left( P_{	ext{peak}}, \; I 	imes B_{	ext{peak}} \right)

- $P_{	ext{peak}}$：GPU 核心的物理峰值浮点计算能力（例如 40 TFLOPS）；
- $B_{	ext{peak}}$：显存控制器的物理峰值聚合带宽（例如 1.0 TB/s）；
- $I_{	ext{turning}} = \frac{P_{	ext{peak}}}{B_{	ext{peak}}}$：**性能拐点（Turning Point）**。当着色器的算术强度低于该拐点时，无论如何优化指令执行，性能均死死受限于显存搬运速度；只有超过该拐点，性能才进入算力主导区。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                       GPU 顶层 Roofline 性能模型坐标图                  |
   +-------------------------------------------------------------------------+
   性能 P (TFLOPS)
       ^
   Pmax|-----------------------------------/================================ (算力受限区 Compute-Bound)
       |                                  /
       |                                 /
       |                                /
       |                               /
       |                              /  (斜率 = 显存峰值带宽 Bmax)
       |                             /
       |                            /
       |                           /   (显存带宽受限区 Memory-Bound)
       |                          /
       +-------------------------+---------------------------------------->
       0                    I_turning                               算术强度 I (FLOPs/Byte)

5.2 算力瓶颈 (Compute Bound) 的微架构归因与指令吞吐
------------------------------------------------------------------------

当性能分析工具显示 GPU 的计算核心利用率（ALU Pipe Utilization）接近 100% 时，着色器进入算力受限状态。算力瓶颈在微架构层面可进一步细分为以下结构性约束：

1. **基础浮点单元 (FP32 ALU) 饱和**：片段或计算着色器中充斥着密集的乘加指令（FMA - Fused Multiply-Add）。现代 GPU 的 FMA 单元支持单时钟周期完成 $A 	imes B + C$ 运算（计为 2 FLOPs）。若代码中包含无法利用 FMA 的独立加法或乘法，执行吞吐将折半。
2. **特殊函数单元 (SFU / Transcendental) 吞吐断崖**：
   - 着色器中的高阶数学函数（如 `sin`, `cos`, `rsqrt`, `exp2`, `log2`, `pow`）并非由通用 FP32 ALU 计算，而是路由至芯片上物理面积较小的特殊函数单元（SFU）。
   - 在主流 GPU 架构中，每个计算单元（SM/CU）内 SFU 的数量通常仅为标准 FP32 ALU 的 **1/4 至 1/8**。
   - 大量调用 `pow`、`acos` 或非线性拟合函数会导致 SFU 派发端口成为严重瓶颈，导致通用 ALU 大面积空转等待。
3. **数据冒险与指令级并行度 (ILP) 缺失**：
   - 写后读（RAW - Read After Write）相关性使得后续指令必须等待前序指令的计算结果写入寄存器堆。
   - 若着色器循环内指令依赖链过长且缺乏无关指令进行调度填充，流水线将频繁触发 `Warp Stall on Execution Dependency`。

5.3 显存带宽与延迟瓶颈 (Memory Bound & Latency Bound)
------------------------------------------------------------------------

显存瓶颈并非单一现象，在底层必须严格区分为**带宽吞吐受限（Bandwidth Bound）**与**访存时延受限（Latency Bound）**。

显存带宽受限 (Bandwidth Bound)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **微架构表征**：DRAM 外部总线利用率（DRAM Throughput）或 L2 缓存总线利用率突破 80%~90%。
- **物理成因**：一帧内搬运的总字节数突破了物理显存带宽上限。常见于全屏 4K 分辨率下的多渲染目标（MRT）输出、未启用压缩格式的深度缓冲区写入，以及缺乏 Mipmap 支持的高频大图采样。
- **治理策略**：降低格式位宽（如 `RGBA16F` 转为编码后的 `RG16F` 或 `RGBA8`）、应用 ASTC/BC 硬件块压缩纹理、启用 TBDR 片上内存暂存（Memoryless Attachments）。

访存时延受限 (Latency Bound)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **微架构表征**：DRAM 物理带宽利用率并不高（可能仅 30%~50%），但计算核心的空转率极高，分析工具报告 `Warp Stall on Long Scoreboard / Memory Throttle` 占比极高。
- **物理成因**：由于访问地址高度离散或间接寻址链过长，导致 L1/L2 缓存频繁未命中（Cache Miss）。每个 Warp 在发起显存读取后必须挂起长达 400~800 个时钟周期等待数据返回，而驻留的活跃 Warp 数量不足以填满该延迟气泡。
- **治理策略**：优化数据结构局部性（AoS 转 SoA）、合并内存事务（Memory Coalescing）、利用共享内存（LDS/Shared Memory）进行显式组内分块加载。

5.4 寄存器压力与占用率断崖 (Occupancy Cliff)
------------------------------------------------------------------------

**占用率（Occupancy）**定义为每个计算单元（SM/CU）上当前驻留的活跃 Warp 数量与该计算单元物理允许的最大 Warp 数量之比。GPU 隐藏显存长延迟的核心机制在于 Warp 调度器的零开销上下文切换；若占用率过低，计算核心将失去延迟掩盖能力。

寄存器分配机制与阶梯式断崖
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每个 SM/CU 内部的物理寄存器堆（VGPR File）容量是固定的（通常为 64 KB ~ 256 KB）。编译器在编译着色器时，必须为每个线程分配固定数量的寄存器（Registers per Thread）。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 每个线程寄存器用量与 SM 活跃 Warp 数量断崖曲线          |
   +-------------------------------------------------------------------------+
   活跃 Warp 数量 (Occupancy)
       ^
    64 |================= [<= 32 Regs/Thread: 达到 100% 满占用率]
       |                 \
    48 |                  \
       |                   +------------------ [33~48 Regs/Thread: 占用率跌至 75%]
    32 |                                      \
       |                                       +------------- [49~64 Regs: 跌至 50%]
    16 |                                                     \
       |                                                      +--- [>64 Regs: 跌至 25% 极度危险区]
       +------------------------------------------------------------------------>
       0                32                   48              64    寄存器数量 (Regs/Thread)

当着色器由于局部变量过多、复杂分支嵌套或激进的循环展开，导致寄存器需求由 32 个微增至 33 个时，物理寄存器堆无法同时容纳原先数量的线程块，SM 允许驻留的 Warp 数量将发生**断崖式骤降**。

寄存器溢出 (Register Spill) 的物理惩罚
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

若着色器代码极为复杂，寄存器需求超过了硬件单线程最大上限（如 255 个寄存器），编译器将被迫触发**寄存器溢出（Register Spill）**：将超额的临时变量转移至本地显存区间（Local Memory / Scratch Space）。原本单周期的寄存器读取瞬间退化为数百周期的显存访存，引发严重的帧率雪崩。

5.5 控制流发散与前端提交气泡 (Divergence & Submission Bottlenecks)
------------------------------------------------------------------------

分支发散 (Branch Divergence) 的算力折损
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个 Warp 内的 32 个线程在执行 `if-else` 条件分支时进入了不同路径，SIMT 执行单元必须串行执行两条分支，并通过 Active Mask 掩码屏蔽未命中线程：

.. math::

   	ext{SIMD Efficiency} = \frac{	ext{Active Threads in Path A} + 	ext{Active Threads in Path B}}{32 	imes 2}

若一个 Warp 内仅有 1 个线程执行 `if` 分支，其余 31 个线程执行 `else` 分支，硬件必须耗费两倍的指令执行周期，有效算力利用率腰斩。

CPU 提交气泡与驱动饥饿 (GPU Starvation Bubble)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **现象**：GPU 总体利用率（GPU Utilization）呈锯齿状剧烈波动，在帧起始阶段存在长达 2~5 ms 的完全空闲段。
- **物理成因**：CPU 渲染主线程在进行场景遍历、视锥剔除或物理模拟时耗时过长，未能及时向命令队列录制并提交首批命令列表（Command Lists）。GPU 命令处理器执行完上一帧末尾的 Present 呈现后无事可做，产生硬件饥饿气泡。
- **应对准则**：解耦 CPU 逻辑更新与渲染录制、启用多线程并行录制命令列表，并在 Shadow Pass 完成后立刻发起第一批次异步提交。

5.6 工业级 GPU 瓶颈诊断决策树 (Profiling Decision Tree)
------------------------------------------------------------------------

在面对复杂的掉帧与性能劣化时，依据性能分析工具（Nsight / RenderDoc / Xcode）的底层性能计数器建立系统化的排查决策矩阵：

.. list-table:: 工业级 GPU 性能瓶颈排查与优化决策矩阵
   :widths: 18 22 28 32
   :header-rows: 1
   :class: tight-table

   * - 诊断阶段
     - 核心性能计数器
     - 瓶颈类型判定
     - 首选优化方案
   * - 1. 顶层分流
     - GPU Total Time vs VRAM Bandwidth
     - 若带宽 > 80% 则进入显存分析；若带宽低且时延高进入算力/延迟分析
     - 确定宏观瓶颈归属区间
   * - 2. 算力诊断
     - ALU Utilization & SFU Pipe Active
     - 若 ALU > 85% 为算力受限；若 SFU Pipe > 50% 为特殊函数受限
     - 精简数学模型、将 `pow/sin` 转为查找表或多项式拟合、转 FP16 半精度
   * - 3. 访存诊断
     - L2 Hit Rate & Uncoalesced Transactions
     - 若 L2 Hit < 50% 且发散事务高，为访存发散与局部性破坏
     - 重排数据结构为 SoA、启用纹理 Mipmap 链、优化 Cache Line 对齐
   * - 4. 占用率诊断
     - Warp Occupancy & Registers/Thread
     - 若 Occupancy < 50% 且 Regs > 48，为寄存器压力瓶颈
     - 消除非必要临时变量、控制循环展开粒度、调整线程块尺寸
   * - 5. 控制流诊断
     - Branch Divergence & Warp Execution Efficiency
     - 若分支效率 < 60%，为 SIMT 发散受限
     - 将分支重构为基于材质分桶的数据排序，消除动态复杂判断
   * - 6. 提交与同步
     - GPU Idle Time & Pipeline Wait Time
     - 若存在大段 Idle 或 Barrier Wait，为 CPU 提交饥饿或粗粒度屏障
     - 拆分细粒度 Render Pass、异步计算交错填充、多线程命令录制

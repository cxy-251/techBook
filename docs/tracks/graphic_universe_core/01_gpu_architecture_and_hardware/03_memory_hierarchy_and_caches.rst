========================================================================
Chapter 3: 显存层级、缓存拓扑与带宽延迟模型
========================================================================

.. note:: 前置背景与认知承接
   前两章剖析了 GPU 的硬件计算单元拓扑与 SIMD/SIMT 指令级调度机制。在现代实时图形渲染中，计算单元的理论峰值算力往往数倍于显存总线供给能力，绝大多数帧耗时瓶颈直接收敛于显存子系统。本章将解构 GPU 内部从物理寄存器堆、片上 L1/Shared Memory、巨型 L2 Cache 到外部 DRAM（GDDR6/HBM/统一内存）的访问时延与吞吐边界，建立显存合并访问（Memory Coalescing）的底层优化模型与多级缓存复用策略。

------------------------------------------------------------------------
3.1 GPU 内存层级拓扑与存取成本金字塔
------------------------------------------------------------------------

GPU 的内存体系设计呈现出极其陡峭的时延与带宽金字塔结构。着色器执行指令时，数据在存储层级中所处的物理位置，直接决定了该指令是单周期完成还是触发长达数百个时钟周期的流水线挂起。

.. list-table:: GPU 多级存储层次物理参数与访问成本矩阵
   :widths: 18 18 20 22 22
   :header-rows: 1
   :class: tight-table

   * - 存储层级
     - 物理位置
     - 典型容量
     - 访问时延 (Cycles)
     - 聚合带宽 (Bandwidth)
   * - 物理寄存器堆 (VGPR)
     - 计算核心内部 (SM/CU)
     - 64 KB ~ 256 KB / SM
     - 1 时钟周期
     - 10 ~ 30 TB/s (芯片总聚合)
   * - 共享内存 / LDS
     - 片上可编程 SRAM
     - 64 KB ~ 128 KB / SM
     - 15 ~ 30 时钟周期
     - 5 ~ 15 TB/s
   * - L1 缓存 / Texture Cache
     - 片上专用/通用缓存
     - 32 KB ~ 128 KB / SM
     - 30 ~ 80 时钟周期
     - 3 ~ 8 TB/s
   * - L2 缓存 (共享)
     - 片上全局共享 SRAM
     - 4 MB ~ 96 MB (现代 GPU)
     - 150 ~ 300 时钟周期
     - 1.5 ~ 4 TB/s
   * - 外部显存 (DRAM / VRAM)
     - 独立 GDDR6 / HBM3
     - 8 GB ~ 48 GB
     - 400 ~ 800+ 时钟周期
     - 300 GB/s ~ 3 TB/s
   * - 系统统一内存 (UMA)
     - SoC 共享 LPDDR5X
     - 16 GB ~ 128 GB
     - 400 ~ 800+ 时钟周期
     - 100 ~ 800 GB/s (多模块共享)

为了具体追踪各存储层级的数据流转，我们以一个经典的延迟渲染几何通道（G-Buffer Generation Pass）配合全屏光照计算（Lighting Pass）作为贯穿全章的分析实体：

1. **几何通道多目标输出**：片段着色器计算表面法线、粗糙度、金属度及基础色，各属性在寄存器中解算后，通过输出合并单元（ROP）并发写入 4 个全分辨率 Render Target（G-Buffer Attachments），产生巨大的外部显存写入带宽压力。
2. **光照计算读取**：全屏光照通道对屏幕上的每个像素采样 G-Buffer，若相邻像素读取相同的深度与材质参数，L2 缓存与 L1 Texture Cache 将吸收绝大部分重复读取请求。
3. **材质纹理采样**：同时向外部显存发起 4K PBR 纹理（Albedo, Normal, Roughness Map）的采样请求，纹理采样单元（TMU）通过硬件解压格式并利用 Mipmap 保持极高的数据局部性。

3.2 显存合并访问（Memory Coalescing）与缓存行对齐机制
------------------------------------------------------------------------

当一个 Warp（32 个线程）同时执行一条显存读取指令（如读取顶点属性或结构化缓冲区数据）时，显存控制器并不会独立发起 32 次物理访问，而是通过硬件内存合并单元（Coalescing Unit）将相邻线程的请求聚合为尽可能少的物理缓存行事务（Cache Line Transactions）。

缓存行事务聚合原理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代 GPU 的 L2 缓存和 DRAM 控制器通常以 32-Byte、64-Byte 或 128-Byte 为最小读写事务单元（Transaction Segment）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  合并访问 (Coalesced) vs 分散访问 (Uncoalesced)          |
   +-------------------------------------------------------------------------+

   [ 理想情况: 32 个线程读取连续 4 字节数据 (共 128 字节) ]
   Threads:  T0  T1  T2  T3 ... T31
   Address: [0x00, 0x04, 0x08, 0x0C ... 0x7C]
   -> 硬件合并机制: 触发 1 次 128-Byte 显存事务 (总线利用率: 100%)

   [ 严重发散情况: 32 个线程读取大步长或随机地址数据 ]
   Threads:  T0     T1     T2     T3  ...  T31
   Address: [0x00,  0x100, 0x200, 0x300 ... 0x1F00]
   -> 硬件合并机制: 分裂为 32 次独立的 128-Byte 显存事务！
   -> 实际传输数据: 32 x 128 B = 4096 字节
   -> 有效数据量:   32 x 4 B = 128 字节 (总线利用率: 仅 3.125%！)

数据组织形态：AoS 与 SoA 的底层性能差异
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在设计顶点缓冲区（Vertex Buffer）、实例数据（Instance Data）及计算着色器结构体时，数组结构（Structure of Arrays - SoA）与结构体数组（Array of Structures - AoS）的选择直接决定了内存事务效率：

.. code-block:: cpp

   // 结构体数组 (AoS - Array of Structures)
   struct Particle_AoS {
       float posX, posY, posZ; // 12 字节
       float velX, velY, velZ; // 12 字节
       float lifeTime;         // 4 字节
       float size;             // 4 字节 (共 32 字节)
   };
   // 缓冲区定义: Particle_AoS particles[N];

   // 数组结构 (SoA - Structure of Arrays)
   struct Particle_SoA {
       float posX[N], posY[N], posZ[N];
       float velX[N], velY[N], velZ[N];
       float lifeTime[N];
       float size[N];
   };

在仅需要更新粒子位置的计算通道中：

- **AoS 模式**：线程 $i$ 读取 `particles[i].posX`，线程 $i+1$ 读取 `particles[i+1].posX`。相邻线程的访问地址在内存中间隔了 32 字节（Stride = 32B）。一个 128-Byte 事务仅能容纳 4 个线程的有效数据，需要 8 次物理事务才能满足一个 Warp，总线有效载荷仅为 37.5%。
- **SoA 模式**：所有线程访问连续的 `posX[i]` 数组。32 个线程的读取地址在物理内存中首尾相连，1 次 128-Byte 事务即可完全满足整个 Warp，总线利用率达到 100%。

3.3 纹理缓存（Texture Cache）微架构与 Mipmap 空间局部性
------------------------------------------------------------------------

纹理访问具备鲜明的二维甚至三维空间局部性（相邻的屏幕像素通常采样相邻的 UV 坐标）。传统的线性内存排布（Row-Major Layout）无法在纵向跨行采样时保持局部性，因此 GPU 硬件采用了特殊的纹理平铺与采样优化技术。

莫顿码与瓦片化纹理存储 (Morton Code / Tiling Layout)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在纹理上传至 GPU 显存时，驱动程序会将其重排为基于 Z-Order 曲线（莫顿码 - Morton Order）或特定微块（Micro-Tiles，如 8×8 或 16×16 Texels）的平铺格式：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              线性内存排列 vs 莫顿曲线 (Z-Order Tiled) 排列              |
   +-------------------------------------------------------------------------+
   
   线性行优先排列 (Row-Major):         Z-Order 瓦片化排列 (2x2 Micro-Tiles):
   (0,0) (1,0) (2,0) (3,0)              [ (0,0)  (1,0) ]  [ (2,0)  (3,0) ]
   (0,1) (1,1) (2,1) (3,1)  --->        [ (0,1)  (1,1) ]  [ (2,1)  (3,1) ]
   (0,2) (1,2) (2,2) (3,2)
   (0,3) (1,3) (2,3) (3,3)              [ (0,2)  (1,2) ]  [ (2,2)  (3,2) ]
                                        [ (0,3)  (1,3) ]  [ (2,3)  (3,3) ]

在瓦片化排布下，无论采样器在水平方向还是垂直方向发生 2×2 双线性插值足迹移动，所涉及的 4 个 Texel 物理内存地址均紧密相邻在同一缓存行内，避免了行跨度过大导致的频繁 Cache Line 颠簸（Thrashing）。

Mipmap 机制对显存带宽与工作集的物理节约
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Mipmap 的核心价值不仅在于消除高频走样摩尔纹，更在于严格限制采样器的工作集（Working Set）尺寸：

.. list-table:: 远距离物体采样启用与未启用 Mipmap 时的微架构对比
   :widths: 20 40 40
   :header-rows: 1
   :class: tight-table

   * - 运行参数
     - 未启用 Mipmap (仅 4K 顶层)
     - 启用 Mipmap (自动硬件选择 Mip 5)
   * - 采样足迹跨度
     - 相邻像素在 4K 纹理上跨越数十个 Texels
     - 相邻像素在 128×128 纹理上连续紧邻
   * - 缓存行局部性
     - 严重发散，每次采样命中不同 Cache Line
     - 高度对齐，4 个采样点共享同一缓存行
   * - L1 Texture Hit Rate
     - 极低 (低于 20%)
     - 极高 (通常高于 85%)
   * - 显存总线数据流量
     - 产生大量未被使用的冗余字节传输
     - 仅传输降采样后紧凑的有效数据字节

3.4 现代渲染管线中的显存带宽优化法则
------------------------------------------------------------------------

在工业级图形管线中，控制显存带宽消耗应遵循以下四大核心设计准则：

法则 1：G-Buffer 数据结构压缩与通道紧凑打包
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

延迟渲染 G-Buffer 的写入和读取是全屏带宽的主要消耗源。通过数学编码与通道打包，可大幅减少 Render Target 的数量与位宽：

- **八面体法线编码 (Octahedron Normal Encoding)**：单位三维法线向量通过八面体投影压缩至 2 个 16 位浮点通道（`RG16F`）或 2 个无符号归一化 8 位整数（`RG8_UNORM`），取代传统的 `RGBA16F`（节约 50%~75% 显存带宽）。
- **材质属性复合打包**：将金属度（Metallic）、粗糙度（Roughness）、环境光遮蔽（AO）及材质类型 ID 分别打包进单个 32-bit `RGBA8_UNORM` 纹理的 R、G、B、A 通道中，单次采样即可获取全量 PBR 表面特征。

法则 2：GPU 硬件块压缩纹理标准 (BCn / ASTC) 的全面应用
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

未压缩的 32-bit RGBA 图像每个像素占用 4 字节。GPU 硬件支持专用的块压缩格式（Block Compression），其最大特征是**支持在显存与缓存中保持压缩状态，仅在 TMU 采样输出给着色器时才硬件实时解压**：

.. list-table:: 常用 GPU 硬件块压缩格式技术特性
   :widths: 22 18 30 30
   :header-rows: 1
   :class: tight-table

   * - 格式名称
     - 压缩比 / BPP
     - 适用平台
     - 推荐应用通道
   * - BC1 (DXT1)
     - 8:1 (4 bpp)
     - 桌面端 (DirectX/Vulkan)
     - 不带 Alpha 的 RGB 基础漫反射贴图
   * - BC4 / BC5
     - 4:1 (4/8 bpp)
     - 桌面端 (DirectX/Vulkan)
     - BC4 用于单通道粗糙度，BC5 用于两通道切线空间法线
   * - BC7
     - 4:1 (8 bpp)
     - 桌面端高质量标准
     - 高质量 RGBA 漫反射与高精度平滑法线
   * - ASTC (4x4 ~ 8x8)
     - 4:1 ~ 16:1
     - 移动端 / Apple Silicon / 现代 Vulkan
     - 全平台通用色彩、法线及高动态范围 HDR 纹理

法则 3：贴片延迟渲染 (TBDR) 中的片上内存零开销交换
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在移动端 GPU 与 Apple Silicon 体系中，充分利用 TBDR 架构的 Tile Memory（片上高速 SRAM）：

- 将 G-Buffer 各层声明为瞬态附件（Transient Attachments / Memoryless Render Targets）。
- 在同一 Render Pass 内完成 G-Buffer 绘制与 Lighting 计算，所有中间数据完全在片上 Tile Memory 中生成并被立即消费，最终仅向系统内存写回单一的 Tone Mapped 最终颜色缓冲区。外部 DRAM 往返带宽消耗下降 70% 以上。

法则 4：双缓冲与环形暂存区 (Staging Ring Buffer) 批量上传
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Host 向 Device 上传动态常量或顶点数据时，禁止逐帧反复创建/销毁微小 Buffer。建立基于环形队列的持久化映射暂存区（Persistent Mapped Staging Buffer）：

.. code-block:: cpp

   // 环形暂存上传缓冲区架构
   class DynamicBufferRing {
   public:
       void* AllocateSegment(size_t size, size_t alignment, size_t& outOffset) {
           // 按硬件对齐要求向后递增偏移量
           outOffset = (currentOffset + alignment - 1) & ~(alignment - 1);
           if (outOffset + size > totalRingSize) {
               outOffset = 0; // 回卷至环形缓冲区头部
           }
           currentOffset = outOffset + size;
           return static_cast<char*>(mappedBaseAddress) + outOffset;
       }
   private:
       void* mappedBaseAddress;
       size_t currentOffset = 0;
       size_t totalRingSize = 64 * 1024 * 1024; // 64 MB
   };

3.5 显存性能分析与 Profiling 证据链建立
------------------------------------------------------------------------

在面对帧率下降或掉帧问题时，通过图形性能分析工具（Profiler）确立明确的物理证据链：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     显存性能瓶颈诊断决策流                              |
   +-------------------------------------------------------------------------+

   [ 步骤 1: 抓帧并定位 GPU 耗时最高的 Pass ]
        |
        v
   [ 步骤 2: 观察硬件性能计数器 (Nsight / Xcode GPU Profiler) ]
        |
        +---> 若 Memory Throughput (VRAM Bandwidth) > 80% 峰值:
        |        * 诊断: 显存总线带宽饱和 (Bandwidth Bound)
        |        * 应对: 缩减 Render Target 数量/格式、开启纹理压缩、降分辨率
        |
        +---> 若 L2 Cache Hit Rate < 50% 且 Warp Stall on Memory > 40%:
        |        * 诊断: 访存局部性破坏 / 随机访问发散 (Latency Bound)
        |        * 应对: AoS 布局转 SoA、补齐 Mipmap、按空间排布重排数据
        |
        +---> 若 Compute ALU Utilization 极低且 Memory Stall 极高:
                 * 诊断: 寄存器压力导致 Occupancy 下降，无法隐藏读取延迟
                 * 应对: 优化着色器局部变量，精简临时向量，提升驻留 Warp 数量

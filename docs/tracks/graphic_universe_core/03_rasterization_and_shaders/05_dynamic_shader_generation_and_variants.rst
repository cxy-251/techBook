========================================================================
Chapter 15: 动态着色器生成与变体管理：宏组合、PSO 缓存与爆炸控制
========================================================================

.. note:: 前置背景与认知承接
   前一章解构了进阶可编程阶段的演进全貌（几何着色器、硬件曲面细分与现代基于 Meshlet 簇的网格着色管线）。在现代 3D 游戏引擎（如 Unreal Engine 5、Unity、自研商业引擎）中，一套基础材质或渲染通道代码，必须根据光照模型（前向/延迟）、阴影过滤模式（PCF/PCSS/CSM）、雾效算法、实例化（Instancing）、平台特性（D3D12/Vulkan/Metal）以及材质属性开关，动态派生出成千上万种具体的机器执行码。这种机制赋予了引擎极高的模块化表达能力，但也带来了令图形程序员与引擎架构师深恶痛绝的“着色器变体爆炸（Shader Permutation Explosion）”与随之而来的编译卡顿。本章将系统剖析着色器变体空间的笛卡尔积数学模型、Uber Shader 的硬件执行代价、工业级变体静态/动态剔除算法、PSO 驱动级磁盘缓存与预热流水线，以及基于无绑定架构（Bindless）与运行时分支的现代变体消除演进。

------------------------------------------------------------------------
15.1 着色器变体 (Shader Permutations) 的本质与产生机理
------------------------------------------------------------------------

在高级着色语言（HLSL / GLSL）中，为了使单一材质资产能够灵活适配不同的渲染条件，引擎通常采用**条件编译预处理宏（Preprocessor Macros）**来组织代码：

.. code-block:: hlsl

   // 典型材质着色器中的条件编译宏定义分支
   #if defined(HAS_NORMAL_MAP)
       float3 normal = SampleNormalMap(input.UV, input.TBN);
   #else
       float3 normal = normalize(input.NormalWS);
   #endif

   #if defined(SHADOW_QUALITY_HIGH)
       float shadow = SamplePCSSShadow(input.ShadowCoord);
   #elif defined(SHADOW_QUALITY_LOW)
       float shadow = SampleHardShadow(input.ShadowCoord);
   #else
       float shadow = 1.0f;
   #endif

变体空间的笛卡尔积数学爆炸模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每一个独立的条件编译宏，都会在编译期将代码分裂为完全独立的二进制分支。若一个通用着色器定义了 $K$ 组相互正交的特性开关，第 $i$ 组开关包含 $N_i$ 个互斥选项，则该着色器在理论上产生的**总变体数（Total Permutations）**由笛卡尔积严格给出：

.. math::

   P_{	ext{total}} = \prod_{i=1}^{K} N_i = N_1 	imes N_2 	imes \dots 	imes N_K

.. list-table:: 现代商业引擎通用材质着色器的特性宏维度分解
   :widths: 25 35 40
   :header-rows: 1
   :class: tight-table

   * - 特性维度 (Feature Category)
     - 宏选项枚举 (Macros)
     - 互斥分支数 ($N_i$)
   * - **光照模型 (Lighting)**
     - `UNLIT`, `FORWARD_PBR`, `DEFERRED_GBUFFER`, `TOON`
     - 4
   * - **法线贴图模式 (Normals)**
     - `NO_NORMALMAP`, `TANGENT_NORMAL`, `OBJECT_NORMAL`
     - 3
   * - **阴影过滤 (Shadows)**
     - `SHADOW_OFF`, `SHADOW_HARD`, `SHADOW_PCF`, `SHADOW_PCSS`
     - 4
   * - **环境光照 (GI / IBL)**
     - `IBL_OFF`, `IBL_CUBEMAP`, `IBL_SH_ORDER3`, `SCREEN_SPACE_GI`
     - 4
   * - **顶点动画 (Animation)**
     - `STATIC_MESH`, `SKINNING_4BONE`, `SKINNING_8BONE`, `VERTEX_MORPH`
     - 4
   * - **实例化模式 (Instancing)**
     - `INSTANCING_OFF`, `INSTANCING_GPU_BUFFER`
     - 2
   * - **雾效算法 (Volumetric Fog)**
     - `FOG_NONE`, `FOG_LINEAR`, `FOG_EXP2`, `FOG_FROXEL`
     - 4
   * - **后期色彩映射 (ToneMap)**
     - `TONEMAP_ACES`, `TONEMAP_FILMIC`, `TONEMAP_LUT`
     - 3
   * - **理论变体总数**
     - $4 	imes 3 	imes 4 	imes 4 	imes 4 	imes 2 	imes 4 	imes 3$
     - **36,864 个独立变体！**

若整个项目包含 50 个不同类型的主着色器，全局变体总数将轻松突破 **100 万个**！
如果单个变体编译耗时 0.05 秒，离线全量编译将耗时 **13.8 小时**，生成的着色器二进制包体积高达数十吉字节（GB），彻底瘫痪构建服务器与客户端内存！

15.2 Uber Shader 架构与动态分支 (Dynamic Branching) 的硬件代价
------------------------------------------------------------------------

初学者常提出疑问：“为什么不直接将宏定义改为运行时 `if (u_HasNormalMap)` 的动态分支，从而将 36,864 个变体压缩为 1 个超级通用着色器（Uber Shader）？”

在 GPU SIMT（单指令多线程）微架构下，纯动态分支具有极其昂贵的物理惩罚：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  Uber Shader 动态分支三大物理微架构惩罚                 |
   +-------------------------------------------------------------------------+

   [ 惩罚 1: 分支发散 (Warp Divergence) ]
   * Warp 内 32 个线程若条件不一致 (如部分像素有法线贴图，部分无):
     -> 硬件串行化执行两个分支，ALU 利用率暴跌至 50% 以下！

   [ 惩罚 2: 寄存器顶格分配与占用率暴跌 (Worst-Case Register Bloat) ]
   * 编译器分配寄存器必须按全着色器中最复杂的极端分支预留:
     -> VGPR 占用从 32 个激增至 128 个!
     -> 单个 SM 并发线程束 (Active Warps) 数量断崖式下跌，完全无法掩盖访存延迟！

   [ 惩罚 3: L1 指令缓存高频失效 (Instruction Cache Thrashing) ]
   * 超级着色器编译出的机器码体积巨大 (> 64KB):
     -> 超出 SM 片上 L1 指令缓存容量，指令拉取高频停顿 (Instruction Stalls)!

因此，**静态宏变体（静态剥离冗余代码、精简寄存器分配）依然是保证极致运行时性能的唯一基石**。工程的关键在于如何在“变体组合爆炸”与“执行能效”之间求取严密的平衡。

15.3 工业级着色器变体精简与剔除策略 (Shader Stripping)
------------------------------------------------------------------------

为了在构建期将百万级变体精确压缩至数千个实际生效的有效变体，现代引擎构建管线建立了**四级变体剔除网（Shader Stripping Pipeline）**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   工业级四级着色器变体智能剔除流水线                    |
   +-------------------------------------------------------------------------+

   [ 原始全量理论变体空间 (1,000,000+ 变体) ]
        |
        v
   [ 1. 逻辑互斥剪枝 (Mutex Logic Stripping) ]
        |  * 规则: 当定义 UNLIT 时，强制剔除所有 SHADOW_*, GI_*, NORMALMAP 变体
        |  * 缩减比例: -70%
        v
   [ 2. 目标平台能力剪裁 (Platform Capability Stripping) ]
        |  * 规则: 构建 Android/iOS 包时，剔除 DXR 光线追踪、Mesh Shader 变体
        |  * 缩减比例: -50%
        v
   [ 3. 资产引用静态依赖分析 (Asset Usage-Driven Stripping) ]
        |  * 规则: 扫描全工程材质球实际配置，剔除未被任何材质引用的宏组合
        |  * 缩减比例: -80%
        v
   [ 4. 变体收集清单引导预热 (Shader Variant Collection Pre-warming) ]
        |  * 规则: 仅烘焙录制清单中的常用变体，其余罕见变体走异步按需 JIT
        v
   [ 最终交付包体实际变体数量: 2,000 ~ 5,000 个有效变体 (压缩率 > 99.5%) ]

.. list-table:: 着色器变体管理策略工业权衡对比
   :widths: 20 25 25 30
   :header-rows: 1
   :class: tight-table

   * - 管理策略
     - 构建期时间与包体
     - 运行时内存占用
     - 掉帧风险与适用场景
   * - **暴力全量预编译**
     - 构建数小时，包体数 GB
     - 显存占用极高
     - 零运行时编译掉帧；但极易因内存爆仓崩溃
   * - **纯 Uber Shader 分支**
     - 构建极快（秒级），包体极小
     - 显存占用极低
     - 严重分支发散，寄存器压力过大，运行时画质与帧率受损
   * - **资产扫描静态精简**
     - 构建较快（数分钟），包体可控
     - 显存占用健康
     - **工业界首选标准**；保证性能的同时杜绝无效变体
   * - **清单收集 + 异步 JIT**
     - 构建极快，包体极小
     - 动态按需分配
     - 配合回退占位 PSO，兼顾开发期调试与平滑帧时

15.4 管线状态对象 (PSO) 缓存体系与异步预热流水线
------------------------------------------------------------------------

在现代显式底层 API（DirectX 12 / Vulkan / Metal）中，仅有编译好的着色器字节码（DXIL/SPIR-V）是无法直接提交绘制的，驱动必须将着色器与光栅化状态、深度模板测试、混合模式与输入布局整合成**不可变管线状态对象（PSO）**。

驱动级磁盘缓存架构 (Pipeline Cache)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

驱动在首次执行 `CreateGraphicsPipelineState` 时，会将 JIT 生成的硬件原生 ISA 微码保存至磁盘：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    DirectX 12 / Vulkan 驱动级 PSO 缓存架构              |
   +-------------------------------------------------------------------------+

   [ 渲染主线程发出 PSO 创建请求: Hash(VS, PS, Blend, Depth, Layout) ]
        |
        v
   [ 内存 PSO 缓存表 (In-Memory Fast Map) ] -> 命中则数纳秒内直接返回!
        |
        v (未命中)
   [ 磁盘 PSO 缓存文件 (Pipeline Library / Disk Blob) ]
        |  * 校验驱动版本与硬件 GPU ID
        |  * 命中则执行内存映射 (mmap) 秒级加载
        v (首次启动/驱动更新导致失效)
   [ 触发昂贵的 GPU 驱动 JIT 编译 (耗时 5ms ~ 100ms) ]
        |
        +---> 生成原生机器码并写回磁盘缓存文件!

双层异步预热与占位着色器 (Fallback Stubs) 流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了根除游戏运行过程中的微卡顿（Stutter），现代渲染架构引入了**双层异步预热流水线**：

1. **预热加载界面 (Pre-warming Stage)**：在关卡加载进度条期间，后台并发线程池遍历 `ShaderVariantCollection` 清单，调用 API 将所有常用 PSO 全量预热完毕；
2. **运行时突发缺失保护 (Runtime Fallback Stub)**：
   若玩家在游戏中触发了一个未被预热的全新变体：
   - 渲染主线程**绝不阻塞等待编译**，而是立即指派一个已编译就绪的简化版通用占位 PSO（如纯色无光照 Stub PSO）绘制当前帧；
   - 同时将未命中的 PSO 编译请求异步投递给后台工作线程（Worker Thread）；
   - 后台编译完成后，在下一帧安全期原子替换材质绑定的 PSO 句柄，实现视觉无感平滑过渡。

15.5 终极演进：Bindless 架构与标量化重构消灭变体
------------------------------------------------------------------------

在现代图形学前沿（如 Unreal Engine 5 Nanite/Lumen 与现代 GPU-Driven 管线）中，架构师正在利用最新的硬件能力从根本上消除宏定义变体：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |          传统宏变体切换 vs 现代 Bindless + 标量化重构消灭变体           |
   +-------------------------------------------------------------------------+

   [ 传统方案: 靠宏定义生成 100 个变体 ]
   #if HAS_ALBEDO_TEX
       Texture2D g_Albedo : register(t0);
   #endif
   #if HAS_EMISSIVE_TEX
       Texture2D g_Emissive : register(t1);
   #endif
   * 缺陷: 每种贴图组合都是不同着色器，频繁切换 PSO 导致驱动状态开销！

   [ 现代方案: 全局无绑定描述符堆 (Bindless Descriptor Heap) ]
   struct MaterialConstants {
       uint albedoTexIndex;    // 32-bit 索引 (0xFFFFFFFF 代表无贴图)
       uint normalTexIndex;
       uint roughnessTexIndex;
   };
   // 单一通用着色器处理全场景材质:
   Texture2D allTextures[] : register(t0, space0); // 无限容量全局资源池!

   if (mat.albedoTexIndex != INVALID_ID) {
       color *= allTextures[NonUniformResourceIndex(mat.albedoTexIndex)].Sample(s, uv);
   }

- **动态统一分支（Dynamically Uniform Branching）**：由于同一个网格批次（DrawCall / Meshlet）内部的所有像素共享完全相同的材质常量，现代 GPU 标量计算单元（Scalar Unit / Wavefront Control）能够瞬间完成条件跳转，**分支发散惩罚彻底归零**。

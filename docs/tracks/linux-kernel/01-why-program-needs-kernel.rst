程序输出一行文字时，为什么需要内核？
====================================

Roadmap 对应知识
----------------

* ``aiBook`` Linux Kernel Roadmap：``Part 1 / What Is the Linux Kernel Really Managing?``；
* Roadmap 首次引入提交：``3a5cc4afdbf4c6ab0d50003e38b06235f1186e40``。

这一篇只回答一个问题：字符串已经在程序内存里，CPU 也正在执行程序，为什么输出它时还要进入内核？

先预测
------

下面的程序会把 ``hello`` 写到标准输出：

.. code-block:: c

   #include <unistd.h>

   int main(void)
   {
       const char message[] = "hello\n";
       ssize_t written = write(STDOUT_FILENO, message, sizeof(message) - 1);

       return written == (ssize_t)(sizeof(message) - 1) ? 0 : 1;
   }

先判断哪一种解释更接近实际情况：

#. ``write`` 直接把字符复制到屏幕显存；
#. C 标准库独自决定字符最终写到哪里；
#. 程序把文件描述符、内存地址和字节数交给内核，由内核处理对应输出对象。

先保留自己的答案，再继续向下读。

三个参数分别表达什么
--------------------

``write`` 接收三个关键参数：

``STDOUT_FILENO``
   数值通常是 ``1``，表示当前进程的标准输出文件描述符。

``message``
   用户态内存中字符串首字节的地址。

``sizeof(message) - 1``
   请求写出的字节数。这里减去字符串结尾的 ``\0``，因此请求写出 6 个字节。

程序提供的是“写哪个句柄、数据在哪里、写多少字节”。它没有提供终端硬件地址，也没有描述终端驱动如何工作。

观察系统调用
------------

在 Linux 环境中可以使用下面的命令观察 ``write``：

.. code-block:: console

   $ cc -Wall -Wextra -O0 hello.c -o hello
   $ strace -e write ./hello

预期结果，尚未在本仓库环境实测：

.. code-block:: console

   write(1, "hello\n", 6) = 6
   hello
   +++ exited with 0 +++

不同 ``strace`` 版本的引号、转义和输出顺序可能略有差异。需要观察的核心事实只有三个：

#. 程序请求执行 ``write``；
#. 第一个参数是文件描述符 ``1``；
#. 返回值 ``6`` 表示这次调用写出了 6 个字节。

从这三个事实开始推理
------------------

第一步：数据属于当前进程
~~~~~~~~~~~~~~~~~~~~~~~~

``message`` 位于当前进程的用户态地址空间。程序能够读取和修改这段内存，因为它属于自己的可访问范围。

第二步：输出对象不由这段代码决定
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

代码只传入文件描述符 ``1``。文件描述符不是终端地址，它是当前进程用来引用一个已打开对象的整数句柄。

运行程序时，``1`` 通常连接到终端；执行下面的重定向后，它会连接到文件：

.. code-block:: console

   $ ./hello > output.txt

程序中的 ``write(STDOUT_FILENO, ...)`` 没有变化，输出位置却变了。这说明程序通过文件描述符引用对象，而不是直接控制某一种设备。

第三步：内核负责解释这次请求
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Linux ``write(2)`` 接口的语义是：把 ``buf`` 开始的最多 ``count`` 个字节写入 ``fd`` 所引用的对象，并返回实际写出的字节数。

进入内核后，需要根据当前进程的文件描述符表找到 ``fd`` 对应的打开对象，再沿该对象支持的写入路径继续处理。这个路径可能通向终端、普通文件、管道或 socket。

这一篇暂时不展开系统调用入口、``struct file``、VFS 和驱动函数。此处只建立第一层判断：

   用户程序描述请求，内核保存并解释进程可以访问的系统对象。

改变一个条件
------------

把文件描述符改成无效值：

.. code-block:: c

   ssize_t written = write(-1, message, sizeof(message) - 1);

预测返回值，再查看 ``write(2)`` 的错误规则。

预期结果是返回 ``-1``，并把 ``errno`` 设置为 ``EBADF``。原因不是字符串无效，而是 ``-1`` 不能在当前进程中解析成一个可写的打开对象。

这个变化说明，文件描述符的解释权不在程序变量本身。程序只能提交一个数字，内核根据当前进程的状态判断这个数字是否有效以及它指向什么。

常见误解
--------

``内核只是硬件驱动的集合``
   驱动属于内核的一部分。这个例子已经表明，内核还维护进程可访问的文件描述符，并负责把统一的写入请求分发到不同对象。

``调用 write 就一定是在写磁盘``
   ``fd`` 可以引用终端、普通文件、管道或 socket。相同的 ``write`` 接口不等于相同的最终设备。

``write 成功就表示数据已经永久写入磁盘``
   ``write`` 返回成功只表示本次接口已经接受并处理了相应字节。对于普通文件，它不保证数据已经提交到永久存储。

能力检查
--------

#. 为什么 ``write`` 不需要接收终端的硬件地址？
#. ``./hello`` 和 ``./hello > output.txt`` 使用相同代码，为什么输出位置不同？
#. ``write(-1, ...)`` 失败时，哪一个前提被破坏了？
#. 仅凭 ``write(1, ...)`` 能否判断最终对象一定是终端？

答案与推理
----------

#. 程序提交的是文件描述符。内核根据当前进程的文件描述符表找到对应对象，再进入该对象的写入路径，因此调用方不需要知道硬件地址。
#. shell 在启动程序前改变了文件描述符 ``1`` 指向的对象。程序仍然引用 ``1``，内核解析到的对象已经从终端变成文件。
#. ``fd`` 必须在当前进程中对应一个可写的打开对象。``-1`` 无法满足这个条件，因此返回 ``EBADF``。
#. 不能。文件描述符 ``1`` 表示标准输出的位置，标准输出可以被重定向到文件、管道或其他对象。

独立任务
--------

不要修改 C 程序，分别预测下面三条命令的可见结果：

.. code-block:: console

   $ ./hello
   $ ./hello > output.txt
   $ ./hello | wc -c

需要解释的重点不是命令语法，而是三次运行中“文件描述符 ``1`` 指向了什么”。

完成标准
--------

读者能够独立说明：

* 为什么用户程序使用文件描述符，而不是直接控制输出设备；
* 为什么同一个 ``write`` 调用可以写向终端、文件或管道；
* 为什么无效文件描述符会在内核边界失败；
* ``write`` 返回成功为什么不等于数据已经永久落盘。

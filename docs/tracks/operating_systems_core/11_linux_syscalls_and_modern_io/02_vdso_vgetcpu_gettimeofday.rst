第 2 节：vDSO (Virtual Dynamic Shared Object) 与用户态无系统调用直读硬件计时器
========================================================================================

.. note::
   **前置背景与上下文承接**
   * **体系结构基准**：承接模块 11 第 1 节中关于 x86_64 原生 ``SYSCALL`` / ``SYSRET`` 系统调用微观全链路、``MSR_LSTAR`` 硬件跳转与 168 字节 ``struct pt_regs`` 现场构造。
   * **核心使命**：解构 Linux 7.2 内核如何打破“凡访问内核数据必陷特权级”的传统桎梏，通过 **vDSO（Virtual Dynamic Shared Object）** 与 **VVAR（Virtual Variable Page）** 只读共享内存架构，在用户态（Ring 3）达成 **0 次系统调用、0 次特权级切换、0 次上下文开销** 的亚纳秒级硬件时钟与拓扑读取；深入剖析内核 ``arch/x86/entry/vdso/vma.c:map_vdso()`` 与 ELF 镜像内存映射时序；逐行推导 ``struct vdso_time_data`` / ``struct vdso_clock`` 顺序锁（SeqLock）无锁一致性读取状态机；解构用户态执行 ``RDTSC`` / ``RDTSCP`` / ``RDPID`` 硬件指令直读 TSC 周期计数器并结合 ``mult`` / ``shift`` 线性时间换算数学模型；剖析容器化时间命名空间（Time Namespace / ``timens``）的偏移虚拟化，以及 ``gettimeofday()`` / ``clock_gettime()`` / ``getcpu()`` 从 100ns 骤降至 5~10ns 的微观物理时钟时序。

第一幕：特权级切换的性能天花板与 vDSO 破局哲学
----------------------------------------------

系统调用是操作系统为保护硬件资源设立的安全边界。然而，在某些超高频调用的场景下，特权级切换本身成为了整个计算机系统的吞吐量杀手。

1.1 高频时间戳调用的系统灾难
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在现代高并发服务器场景中：
* **分布式追踪系统**（如 OpenTelemetry、SkyWalking）在每个 RPC 请求的出入口都需要记录微秒甚至纳秒级时间戳；
* **高频交易系统**（HFT）与分布式数据库（如 TiDB、CockroachDB）每秒需要调用数百万次 ``clock_gettime(CLOCK_REALTIME)`` 或 ``gettimeofday()``；
* 即使 x86_64 的 ``SYSCALL`` 指令已将单次陷入内核的耗时压缩到 50 ~ 100 纳秒，**数百万次系统调用依然会白白吞噬 20% ~ 40% 的 CPU 算力**，伴随而来的还有流水线清空、分支预测失效与上下文切换抖动。

.. important::
   **颠覆性物理哲学**：
   时间戳、时钟周期与当前 CPU 编号本质上只是**系统全局只读状态**，完全不涉及对硬件的破坏性写入或特权级资源变更。既然如此，为何一定要强迫 CPU 切换到 Ring 0？

1.2 从 ``vsyscall`` 到 ``vDSO`` 的架构演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                            Linux 免系统调用时钟技术演进史                         |
   |                                                                                   |
   |  [早期 vsyscall 机制 (2000s)]                                                     |
   |  - 架构: 在内核高位固定虚拟地址 (0xffffffffff600000) 映射一个只读代码页           |
   |  - 致命缺陷:                                                                      |
   |    1. 固定内存地址彻底破坏了 ASLR (地址空间布局随机化)，沦为 ROP 攻击的绝佳跳板;   |
   |    2. 容量仅有 4KB，仅能容纳 4 个系统调用槽位，无法动态扩展;                      |
   |    3. 在内核开启特权级隔离 (SMAP/SMEP) 后兼容性极差。                              |
   |                                                                                   |
   |  [现代 vDSO 机制 (Virtual Dynamic Shared Object)]                                 |
   |  - 架构: 内核在内存中动态生成一个标准的 ELF64 动态共享库 (.so);                  |
   |  - 核心突破:                                                                      |
   |    1. 完全受 ASLR 保护，由 glibc 动态链接器 (ld-linux) 在启动时随机重定位;         |
   |    2. 支持标准的 ELF 符号解析、版本控制与 gdb 调试回溯 (Dwarf 栈展开);            |
   |    3. 配合 [vvar] 数据页，实现纯用户态亚纳秒级直读硬件时钟!                       |
   +-----------------------------------------------------------------------------------+

第二幕：双页共生拓扑——``[vdso]`` 代码段与 ``[vvar]`` 数据页映射
----------------------------------------------------------------

当任何一个用户空间进程通过 ``execve()`` 加载运行时，Linux 内核会为其地址空间悄悄注入一对“双子星”内存映射。

2.1 用户进程虚拟内存中的双子拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                            vDSO 与 VVAR 双页内存映射模型                          |
   |                                                                                   |
   |  [用户进程虚拟地址空间 (User Virtual Space)]                                      |
   |                                                                                   |
   |  0x7fff_xxxx_0000 ┌──────────────────────────────────────────┐                    |
   |                   │ [vvar] 虚拟变量数据页 (VM_READ, 只读)    │                    |
   |                   │ 存放 struct vdso_time_data / 时钟参数    │                    |
   |  0x7fff_xxxx_2000 ├──────────────────────────────────────────┤                    |
   |                   │ [vdso] 虚拟动态共享库 (VM_READ | VM_EXEC)│                    |
   |                   │ 包含 __vdso_clock_gettime 等机器指令代码 │                    |
   |                   └──────────────────────────────────────────┘                    |
   |                                │                    │                             |
   |      ┌─────────────────────────┘                    └──────────────┐              |
   |      ▼ (物理页映射)                                                ▼ (物理页映射) |
   |  [内核全局共享只读物理页]                                  [内核编译期代码物理页] |
   |  struct vdso_data (由内核每 tick 异步写入)                 vDSO ELF64 代码段      |
   +-----------------------------------------------------------------------------------+

2.2 启动装载流水线（``arch/x86/entry/vdso/vma.c:map_vdso()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在进程二进制文件装配阶段（``arch_setup_additional_pages()``）：
1. **申请虚拟区间**：内核调用 ``get_unmapped_area()`` 在用户空间随机分配一段连续的 VMA 槽位；
2. **挂载代码页**：调用 ``_install_special_mapping()`` 将 ``vdso64_image`` 映射为用户态可执行的 ``[vdso]``；
3. **挂载数据页**：调用 ``vdso_install_vvar_mapping()`` 将内核时间数据物理页映射为用户态只读的 ``[vvar]``；
4. **传递入口向量**：内核通过 ELF 辅助向量表（Auxiliary Vector），将 ``AT_SYSINFO_EHDR`` 指针指向 ``[vdso]`` 的 ELF 头部，供动态链接器 ``ld.so`` 进行符号重定向。

第三幕：硬件时钟源直读与数学换算模型（``RDTSC`` / ``RDTSCP``）
----------------------------------------------------------------

vDSO 之所以能摆脱内核陷入，其底层依赖于现代 x86 处理器提供的**高精度片上硬件时间戳计数器（TSC, Time Stamp Counter）**。

3.1 恒定 TSC（Invariant TSC）的硬件保障
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
早期的 TSC 计数器频率会随着 CPU 的节能降频（SpeedStep / P-States）而改变，导致计时失准。现代 x86_64 处理器全面支持 **Invariant TSC（恒定 TSC）**：
* TSC 计数器由主板基准时钟（如 100MHz 晶振）经由硬件倍频器驱动，以绝对恒定的频率单调递增；
* 即使 CPU 进入休眠模式或超频加速，TSC 计数器的递增速率保持绝对恒定；
* 用户态指令 **``rdtsc``** 与 **``rdtscp``** 在 Ring 3 下拥有直接执行特权，执行仅消耗 **5 ~ 10 个时钟周期**。

3.2 定点数乘移位快速时间转换算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
CPU 读取到的 TSC 是一个纯粹的“时钟周期数”（Cycles）。要将其转换为国际标准的秒（sec）与纳秒（nsec），必须除以 CPU 的时钟频率。然而，CPU 整数除法指令（``DIV``）耗时高达 40~80 个周期，且不支持浮点运算。

.. important::
   **内核定点数乘移位数学模型（``lib/vdso/gettimeofday.c``）**：
   Linux 内核通过在 ``vvar`` 中预先计算好的乘数 ``mult`` 和移位因子 ``shift``，将昂贵的除法转换为极速的乘法与右移位运算：

   $$\Delta_{	ext{cycles}} = \mathbf{TSC}_{	ext{current}} - \mathbf{cycle\_last}$$

   $$\Delta_{	ext{ns}} = \frac{\Delta_{	ext{cycles}} 	imes \mathbf{mult}}{2^{\mathbf{shift}}}$$

   $$\mathbf{Current\_Time}_{	ext{nsec}} = \mathbf{basetime}_{	ext{nsec}} + \Delta_{	ext{ns}}$$

   $$\mathbf{Current\_Time}_{	ext{sec}} = \mathbf{basetime}_{	ext{sec}} + \lfloor \frac{\mathbf{Current\_Time}_{	ext{nsec}}}{10^9} \rfloor$$

内核全局时钟子系统（Timekeeping）在每次硬件时钟中断（Tick）时更新一次基准参数（``cycle_last`` 与 ``basetime``），确保 $\Delta_{	ext{cycles}}$ 始终维持在一个极小范围内，彻底避免 64 位整数乘法溢出。

第四幕：顺序锁（SeqLock）无锁一致性读取流水线
----------------------------------------------

由于内核的 ``update_vsyscall()`` 会在后台并发更新 ``vvar`` 数据页中的 ``cycle_last`` 与 ``basetime``，如果用户态线程恰好在更新中间读取，将产生致命的数据撕裂（Torn Read）。

4.1 顺序锁（SeqLock）读写状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了在纯用户态实现零系统调用且绝对线程安全的原子读取，vDSO 采用了经典的 **顺序锁（Sequence Lock）机制**：
* 序列号 ``seq`` 为偶数：表示当前数据处于稳定一致状态；
* 序列号 ``seq`` 为奇数：表示内核正在写入修改数据页。

4.2 ``__cvdso_clock_gettime()`` 核心执行流水线（``lib/vdso/gettimeofday.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                     __cvdso_clock_gettime() 用户态无锁读取时序                    |
   |                                                                                   |
   |  do {                                                                             |
   |      /* 1. 读取序列号: 若 seq 为奇数，说明内核正在更新，执行 pause 指令自旋等待 */|
   |      seq = vdso_read_begin(vc);                                                   |
   |                                                                                   |
   |      /* 2. 直接执行硬件汇编指令 rdtsc 读取当前 CPU 硬件周期数 */                  |
   |      cycles = __arch_get_hw_counter(vc->clock_mode, vd);                          |
   |                                                                                   |
   |      /* 3. 利用定点数公式: ns = ((cycles - cycle_last) * mult) >> shift */       |
   |      ns = vdso_calc_ns(vc, cycles, vdso_ts->nsec);                                |
   |      sec = vdso_ts->sec;                                                          |
   |                                                                                   |
   |      /* 4. 再次校验序列号: 若期间被内核更新打断 (seq 发生改变)，则重新循环读取 */ |
   |  } while (vdso_read_retry(vc, seq));                                              |
   |                                                                                   |
   |  /* 5. 格式化输出 timespec 结构体，全程耗时仅 5 ~ 10 纳秒! */                     |
   |  ts->tv_sec = sec + ns / 1000000000UL;                                            |
   |  ts->tv_nsec = ns % 1000000000UL;                                                 |
   +-----------------------------------------------------------------------------------+

第五幕：容器化时间隔离（Time Namespace）与 ``vgetcpu`` 硬件极速寻址
-------------------------------------------------------------------

随着云计算与容器技术的发展，vDSO 在保持亚纳秒性能的同时，实现了容器级隔离与 CPU 拓扑读取。

5.1 Time Namespace（时间命名空间）虚拟化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Kubernetes / Docker 容器中，用户可能需要修改容器内的系统时间（如测试未来时间账单逻辑），但绝不能影响宿主机物理时间：
* **vDSO 双数据页架构**：内核在 ``[vvar]`` 页面之后紧接着映射了一个 ``timens`` 数据页；
* **透明偏移累加**：当进程加入 Time Namespace 后，vDSO 代码在计算完真实物理时间后，直接在纯用户态加上该容器专属的 ``timens_offset.sec`` 与 ``timens_offset.nsec``，**零性能损耗地实现了容器时间虚拟化**！

5.2 ``vgetcpu`` 与 ``RDPID`` 硬件单周期寻址
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
读取当前进程运行在哪个 CPU 核心与哪个 NUMA 节点上（``sched_getcpu()`` / ``getcpu()``）同样是高并发服务器调度与内存亲和性绑定的高频操作。
1. **``MSR_TSC_AUX`` 硬件存储**：Linux 内核在每个 CPU 初始化时，向 CPU 内部的 ``MSR_TSC_AUX`` 寄存器写入格式化数据：
   $$\mathbf{MSR\_TSC\_AUX} = (\mathbf{node\_id} \ll 12) \mid \mathbf{cpu\_id}$$
2. **``RDPID`` 单指令直读**：现代 x86 CPU 引入了用户态可执行指令 ``rdpid %rax``：
   * 指令执行仅需 **1 个时钟周期（约 0.3 纳秒）**！
   * 用户态直接从 ``%rax`` 寄存器的低 12 位提取 CPU ID，高位提取 NUMA 节点 ID；
   * 彻底告别传统 ``sys_getcpu`` 耗时上百纳秒的系统调用历史！

小结与下章导读
--------------

本节深入解构了 Linux 7.2 内核 vDSO 与 VVAR 双页共生架构：从高频系统调用的性能危机到 ELF64 共享对象动态映射，从 Invariant TSC 硬件直读到定点乘移位时间换算模型，从 SeqLock 顺序锁无锁读取流水线到 Time Namespace 容器时间隔离与 ``RDPID`` 单周期 CPU 拓扑寻址。

vDSO 解决了只读轻量级调用的极致性能问题。然而，在以磁盘 I/O 和网络通信为代表的繁重数据读写领域，传统的阻塞与非阻塞 I/O 系统调用（如 ``read()`` / ``write()``）依然面临着每次 I/O 都必须进行两次特权级切换与数据拷贝的瓶颈。

在 **第 3 节：现代异步 I/O 核心引擎：``io_uring`` 提交队列 (SQ) 与完成队列 (CQ) 共享内存环形缓冲区设计** 中，我们将深入解构彻底重塑 Linux 存储与网络性能的下一代异步 I/O 革命——``io_uring`` 的双环形缓冲区设计、无锁并发提交与内核轮询（SQPOLL）微观全链路。

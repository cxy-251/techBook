.. note::
   **前置背景与上下文承接**
   * **体系结构基准**：承接模块 11 第 1 节（x86_64 原生系统调用微观链路与 ``entry_SYSCALL_64``）与第 3 节（现代异步 I/O 引擎 ``io_uring`` 的 SQ/CQ 环形缓冲区设计）。

第一幕：高并发的阿喀琉斯之踵——从 ``select/poll`` 到 ``epoll`` 的范式跃迁
-----------------------------------------------------------------------

在早期的 UNIX/Linux 网络编程模型中，事件多路复用主要由 ``select()``（1983 年 BSD 引入）与 ``poll()``（1986 年 System V 引入）主导。

1.1 经典 ``select()`` 与 ``poll()`` 的 $O(N)$ 性能深渊
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当互联网并发规模迈向数万乃至数十万连接（C10K/C100K 问题）时，传统多路复用机制面临三大不可逾越的物理瓶颈：
1. **用户/内核态全量内存拷贝**：每次调用 ``select()`` 必须将整个文件描述符位图（``fd_set``）或 ``pollfd`` 数组从用户空间完整拷贝到内核空间，返回时再次全量拷回；
2. **内核态 $O(N)$ 盲目全遍历**：内核无法得知哪个描述符发生事件，必须线性遍历所有 $N$ 个描述符（即使 100 万个连接中仅有 1 个活跃，也要遍历 100 万次并调用底层的 ``f_op->poll()``）；
3. **高频注册与注销开销**：每次调用都必须把当前进程挂入每个套接字的等待队列中，返回前再逐一注销，造成灾难性的自旋锁争用与 CPU 缓存行污染。

1.2 ``epoll`` 的破局哲学：空间换时间与中断驱动
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
2002 年，Linux 2.5.44 引入了由 Davide Libenzi 设计的 **``epoll``** 机制，彻底颠覆了多路复用的运行范式：

::

   +-----------------------------------------------------------------------------------+
   |                           select / poll vs epoll 核心指标对比                     |
   |                                                                                   |
   |  指标维度             select / poll                      epoll                    |
   |  ───────────────────────────────────────────────────────────────────────────────  |
   |  元数据存储位置       用户态 (每次调用全量拷贝进内核)     内核态常驻 (红黑树管理)  |
   |  监控对象数量限制     select 限制 1024; poll 受限于内存   无上限 (仅受系统物理内存限制)|
   |  就绪事件检测复杂度   O(N) 线性全量轮询遍历               O(1) 常数时间 (硬件中断推入)|
   |  事件返回方式         返回全量集合 (用户需自遍历寻找)     仅返回就绪事件数组       |
   |  底层唤醒触发机制     进程轮询扫描                        网卡中断驱动回调挂载     |
   +-----------------------------------------------------------------------------------+

第二幕：核心数据结构拓扑——``eventpoll``、``epitem`` 与 ``eppoll_entry``
------------------------------------------------------------------------

在 ``fs/eventpoll.c`` 中，``epoll`` 的微观世界由三大核心数据结构协同驱动：

::

   +-----------------------------------------------------------------------------------+
   |                             epoll 核心数据结构三维拓扑                            |
   |                                                                                   |
   |  [应用层 epfd] ──► [struct file] ──(private_data)──► [struct eventpoll]           |
   |                                                      ├── rbr (红黑树根, 存所有监控项) |
   |                                                      ├── rdllist (就绪双向链表)    |
   |                                                      ├── ovflist (扫描暂存单向链表)|
   |                                                      ├── wq (等待队列, 供 wait 睡眠)|
   |                                                      └── lock / mtx (自旋锁/互斥锁)|
   |                                                               │                   |
   |                     ┌─────────────────────────────────────────┴──────┐            |
   |                     ▼                                                ▼            |
   |            [struct epitem] (红黑树节点)                     [struct epitem]       |
   |            ├── ffd (目标 file* + fd)                                              |
   |            ├── rdllink ─────────────────────────► 挂入 ep->rdllist 就绪链表      |
   |            ├── ovflist_next ────────────────────► 挂入 ep->ovflist 溢出链表      |
   |            ├── event (感兴趣事件掩码 + u64 data)                                  |
   |            └── pwqlist ─────────────────────────┐                                 |
   |                                                 ▼                                 |
   |                                       [struct eppoll_entry] (等待队列项)          |
   |                                       ├── base ──► 指回 struct epitem             |
   |                                       ├── wait ──► wait.func = ep_poll_callback   |
   |                                       └── whead ─► 挂在被监听 Socket 的等待队列头!|
   +-----------------------------------------------------------------------------------+

2.1 控制中枢：``struct eventpoll``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **``struct rb_root_cached rbr``**：带最左节点缓存的红黑树，存储所有被监控的描述符条目（``epitem``），提供 $O(\log N)$ 的插入、删除与查找效率；
* **``struct list_head rdllist``**：双向循环就绪链表，仅包含当前已经触发事件的 ``epitem``，供 ``epoll_wait()`` 极速提取；
* **``struct epitem *ovflist``**：溢出单向链表。当内核正在向用户空间拷贝事件（持有互斥锁但未持自旋锁）时，新到来的就绪事件临时串联在此，防止锁竞争；
* **``wait_queue_head_t wq``**：等待队列头，存放调用 ``epoll_wait()`` 阻塞休眠的进程上下文。

2.2 监控实体：``struct epitem``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每个被监控的文件描述符都对应一个分配在 Slab 专用缓存（``epi_cache``）中的 ``epitem`` 结构体：
* **``struct epoll_key ffd``**：由 ``struct file *`` 与整型 ``fd`` 构成的复合键（Key），保证红黑树检索的唯一性；
* **``struct epoll_event event``**：记录用户配置的感兴趣事件（如 ``EPOLLIN | EPOLLOUT | EPOLLET``）以及附带的 64 位 ``data``；
* **``struct eppoll_entry *pwqlist``**：指向该描述符关联的所有底层等待队列节点。

第三幕：文件描述符管理与回调挂载——``epoll_ctl(EPOLL_CTL_ADD)`` 执行流水线
--------------------------------------------------------------------------

当应用程序执行 ``epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev)`` 时，内核执行一套严密的插入与回调安装流程：

::

   +-----------------------------------------------------------------------------------+
   |                        epoll_ctl(EPOLL_CTL_ADD) 微观执行流水线                    |
   |                                                                                   |
   |  1. 获取 ep->mtx 互斥锁，进行防环检测 (ep_loop_check，防止 epoll 互相嵌套成环);     |
   |  2. 在红黑树 ep->rbr 中搜索目标 fd (ep_find)，若已存在则返回 -EEXIST;             |
   |  3. 从 epi_cache 分配新的 struct epitem 并初始化;                                 |
   |  4. 将 epitem 插入红黑树 (ep_rbtree_insert);                                      |
   |  5. 核心挂载: 构建 struct ep_pqueue，将 pt->qproc 函数指针指向 ep_ptable_queue_proc;|
   |  6. 调用底层 vfs_poll(file, &epq.pt):                                             |
   |     └──► 触发底层驱动 (如 socket 的 tcp_poll):                                    |
   |          └──► 调用 poll_wait(file, sk_sleep(sk), pt):                             |
   |               └──► 回调 ep_ptable_queue_proc():                                   |
   |                    1. 从 pwq_cache 分配 struct eppoll_entry;                      |
   |                    2. 将 wait.func 设置为 ep_poll_callback;                       |
   |                    3. 将 wait 节点加入目标 Socket 的等待队列 sk->sk_wq->wait!     |
   |  7. 若调用 vfs_poll 时底层已经有就绪事件:                                         |
   |     └──► 立即将该 epitem 加入 ep->rdllist 就绪链表，并唤醒 ep->wq 上的等待进程!   |
   |  8. 释放 ep->mtx 互斥锁。                                                         |
   +-----------------------------------------------------------------------------------+

.. important::
   **一次挂载，终身受用**：
   与 ``select/poll`` 每次调用反复加解挂等待队列不同，``epoll`` 仅在 ``EPOLL_CTL_ADD`` 时向目标底层注册一次 ``ep_poll_callback``。在此之后，无论经过多少次 ``epoll_wait()``，内核回调均常驻有效，彻底消除重复建制开销！

第四幕：中断驱动的纳秒级就绪流转——``ep_poll_callback()`` 唤醒状态机
---------------------------------------------------------------------

当网卡硬件收到数据包时，整个系统经历一条从晶体管电平到进程唤醒的高速传导链路：

::

   +-----------------------------------------------------------------------------------+
   |                        网卡中断到 epoll 唤醒全链路时钟时序                        |
   |                                                                                   |
   |  [物理网卡收到以太网帧]                                                           |
   |  - 网卡 DMA 将数据包写入 Host 内存 Ring Buffer，触发 PCIe MSI-X 中断;              |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [CPU 响应硬中断 ──► 调度 NAPI 软中断 (NET_RX_SOFTIRQ)]                            |
   |  - net_rx_action() ──► napi_poll() ──► 驱动构建 sk_buff;                          |
   |  - 交付 TCP/IP 协议栈: ip_rcv() ──► tcp_v4_rcv();                                 |
   |  - 将数据包挂入对应 Socket 接收队列: tcp_queue_rcv();                             |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [协议栈触发唤醒回调]                                                             |
   |  - sk->sk_data_ready(sk) ──► wake_up_interruptible_sync_poll(sk_sleep(sk), ...);  |
   |  - 遍历 Socket 的等待队列，命中之前注册的 eppoll_entry!                           |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [执行 ep_poll_callback() 回调函数 (位于软中断/中断上下文)]                       |
   |  1. 获取 ep->lock IRQ-safe 自旋锁 (spin_lock_irqsave);                            |
   |  2. 检查事件掩码: 若传入的 POLLIN 与 epi->event.events 匹配:                      |
   |     ├── 分支 A (当前 epoll 正在向用户态扫描拷贝事件, ep_is_scanning(ep) == true): |
   |     │   └──► 将 epi 串入 ep->ovflist 单向溢出链表 (LIFO 暂存);                    |
   |     └── 分支 B (当前 epoll 处于空闲状态, 未在扫描):                               |
   |         └──► 若 epi 不在就绪链表上，调用 list_add_tail(&epi->rdllink, &ep->rdllist);|
   |  3. 检查是否有在 ep->wq 上睡眠的进程:                                             |
   |     └──► 调用 wake_up(&ep->wq)，将阻塞在 epoll_wait 的工作进程唤醒并置为就绪态!   |
   |  4. 释放自旋锁 (spin_unlock_irqrestore)。                                         |
   +-----------------------------------------------------------------------------------+

第五幕：事件收割与用户态安全交付——``epoll_wait()`` 流水线
----------------------------------------------------------

当应用程序调用 ``epoll_wait(epfd, events, maxevents, timeout)`` 时，内核进入事件收割与投递状态机：

5.1 阻塞等待与定时器控制（``ep_poll()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **快速判断**：调用 ``ep_events_available(ep)``，若 ``rdllist`` 非空则无需睡眠，直接进入提取流程；
2. **睡眠挂起**：若就绪链表为空且 ``timeout != 0``：
   * 将当前任务封装为等待项（``wait.func = ep_autoremove_wake_function``）挂入 ``ep->wq``；
   * 将当前进程状态设置为 ``TASK_INTERRUPTIBLE``；
   * 调用 ``schedule_hrtimeout_range()`` 让出 CPU 调度权，进入高精度定时休眠；
3. **被唤醒**：当网络中断触发 ``ep_poll_callback()`` 唤醒 ``ep->wq``，或超时定时器到期时，进程被唤醒重返 CPU。

5.2 事件批量扫描与交付流水线（``ep_send_events()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       ep_send_events() 双链表安全扫描流水线                       |
   |                                                                                   |
   |  1. 【进入扫描态 (ep_start_scan)】:                                               |
   |     - 获取 ep->lock 自旋锁;                                                       |
   |     - 将 ep->rdllist 整体剪切/转移到本地栈变量链表 scan_batch (list_splice_init); |
   |     - 将 ep->ovflist 置为 NULL (正式开启扫描溢出暂存模式!);                       |
   |     - 释放 ep->lock 自旋锁。                                                      |
   |            │                                                                      |
   |            ▼                                                                      |
   |  2. 【无锁/低锁遍历 scan_batch 链表并向用户空间拷贝】:                            |
   |     - 遍历 scan_batch 中的每个 epitem:                                            |
   |       a. 调用 ep_item_poll(epi): 再次调用底层 vfs_poll，确认事件依然真实有效;    |
   |       b. 调用 copy_to_user(): 将事件掩码与 epi->event.data 写入用户态 events 数组;|
   |       c. 【触发模式核心分支】:                                                    |
   |          ► 若为水平触发 (LT): 将该 epitem 重新挂回 ep->rdllist 尾部!              |
   |          ► 若为边缘触发 (ET): 将该 epitem 彻底从链表摘除，绝不放回!               |
   |            │                                                                      |
   |            ▼                                                                      |
   |  3. 【结束扫描态 (ep_done_scan)】:                                                |
   |     - 再次获取 ep->lock 自旋锁;                                                   |
   |     - 遍历 ep->ovflist 溢出链表: 将扫描期间由中断产生的新事件合并回 ep->rdllist;  |
   |     - 将 ep->ovflist 重置为 EP_UNACTIVE_PTR (关闭溢出模式);                       |
   |     - 释放 ep->lock 自旋锁;                                                       |
   |     - 返回本次成功交付给用户的就绪事件总数。                                      |
   +-----------------------------------------------------------------------------------+

第六幕：LT（水平触发）vs ET（边缘触发）的微观物理时钟与状态机差异
-----------------------------------------------------------------

``epoll`` 支持两种截然不同的事件通知模式，其本质区别在于 **就绪事件交付后，内核是否自动将条目重新放回就绪链表（``rdllist``）**。

.. table:: 水平触发 (Level-Triggered) vs 边缘触发 (Edge-Triggered) 深度对比
   :widths: 20 40 40

   +======================+============================================+============================================+
   | 比较维度             | 水平触发 (LT / 默认模式)                   | 边缘触发 (ET / ``EPOLLET``)                |
   +======================+============================================+============================================+
   | **内核链表流转**     | 事件拷贝到用户态后，**重新放回 rdllist**   | 事件拷贝到用户态后，**彻底从 rdllist 摘除**|
   +----------------------+--------------------------------------------+--------------------------------------------+
   | **事件触发时机**     | **电平触发**：只要缓冲区有未读数据，持续触发| **跳变沿触发**：仅在“无数据$\rightarrow$有数据”瞬间触发一次|
   +----------------------+--------------------------------------------+--------------------------------------------+
   | **用户态读取要求**   | 可以分批次读取，未读完下次调用继续通知     | **必须循环 read 直至返回 ``-EAGAIN``**     |
   +----------------------+--------------------------------------------+--------------------------------------------+
   | **描述符阻塞属性**   | 可以使用阻塞或非阻塞 I/O                   | **必须强制使用非阻塞 I/O (``O_NONBLOCK``)**|
   +----------------------+--------------------------------------------+--------------------------------------------+
   | **系统调用频率**     | 相对较高（持续触发可能导致重复就绪）       | 极低（单次跳变仅唤醒一次，吞吐性能极高）   |
   +----------------------+--------------------------------------------+--------------------------------------------+

6.1 边缘触发（ET）的潜在饥饿与并发陷阱
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **死锁/假死陷阱**：若应用程序在 ET 模式下只执行了一次 ``read()`` 且未读尽缓冲区数据，因未发生新的“跳变沿”，底层中断不会再次调用 ``ep_poll_callback()``，导致该连接永远处于等待假死状态！
* **解决铁律**：ET 模式下必须将套接字设为 ``O_NONBLOCK``，且在事件到来时以 ``while ((n = read(fd, buf, len)) > 0)`` 紧凑循环排空数据，直到收到 ``EAGAIN`` 或 ``EWOULDBLOCK`` 错误码。

小结与下章导读
--------------

本节深入解构了 Linux 7.2 事件多路复用引擎 ``epoll`` 的全景微观机制：从 ``select/poll`` 的 $O(N)$ 轮询瓶颈，到 ``eventpoll`` 架构的常驻内核哲学；从基于红黑树（``rbr``）的 $O(\log N)$ 描述符组织，到网卡中断触发 ``ep_poll_callback()`` 极速推入就绪链表；从 ``ep_send_events()`` 在 ``rdllist`` 与 ``ovflist`` 之间的无锁/双链表安全扫描，到 LT 水平触发与 ET 边缘触发的微观状态机差异。

除了多路复用与异步 I/O 之外，操作系统与用户进程之间还存在一种古老而强大的异步通信机制——**信号（Signals）**。

在 **第 5 节：信号处理机制 (Signals)：信号生成、悬挂队列、内核向用户态栈帧注入与 ``sigreturn``** 中，我们将深入解构信号在内核中的生命周期——从硬件异常或系统调用产生信号、挂入未决信号集（``pending``）、内核从系统调用返回前夕的信号扫描（``exit_to_user_mode_loop``）、在用户栈上伪造 ``sigframe`` 栈帧劫持 RIP 指针跳转至用户态 Handler，以及执行 ``sigreturn`` 恢复现场的精妙时钟时序。

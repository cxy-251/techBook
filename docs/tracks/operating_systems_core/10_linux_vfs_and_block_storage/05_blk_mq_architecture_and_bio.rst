第一幕：从单队列大锁危机到 blk-mq 革命——通用块层的体系重构
----------------------------------------------------------

通用块层（Generic Block Layer）处于文件系统（VFS / Page Cache）与底层硬件驱动（NVMe, SCSI, SATA, virtio-blk）之间，负责将离散的内存缓冲区请求整合成符合物理介质特性的块 I/O 请求。

1.1 经典单队列架构的百万 IOPS 崩溃点
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在早期机械硬盘（HDD）时代，Linux 采用经典的单队列（Single-Queue）块层架构：
* 每个块设备全局仅维护一条单一的请求队列（``struct request_queue``）；
* 所有 CPU 核心在提交 I/O 时，必须共同争抢同一把粗粒度全局自旋锁（``q->queue_lock``）。

当存储介质演进为现代 PCIe NVMe 固态硬盘（单盘支持 64K 个独立硬件队列，吞吐量突破数百万 IOPS，延迟降至数十微秒）时，单队列架构彻底崩塌：**在 64 核或 128 核服务器上，高达 $80\% \sim 90\%$ 的 CPU 算力被白白浪费在争抢全局自旋锁的空转（Lock Contention）与跨核缓存行伪共享（Cacheline Bouncing）中！**

1.2 blk-mq 双层队列解耦哲学
~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了彻底释放百万级 IOPS 的硬件潜能，Linux 引入了 **blk-mq（Block Multi-Queue）** 架构，将块层彻底拆分为两层独立的队列拓扑：

   |                                                                                   |
   |  [CPU 0]        [CPU 1]        [CPU 2]       ...       [CPU N-1]                  |
   |    │               │              │                        │                      |
   |    ▼               ▼              ▼                        ▼                      |
   |  ┌───────────┐  ┌───────────┐  ┌───────────┐         ┌───────────┐                |
   |  │ sw_ctx[0] │  │ sw_ctx[1] │  │ sw_ctx[2] │   ...   │sw_ctx[N-1]│ (Per-CPU 软件  |
   |  │ 暂存队列  │  │ 暂存队列  │  │ 暂存队列  │         │ 暂存队列  │  队列: 零锁竞争)|
   |  └─────┬─────┘  └─────┬─────┘  └─────┬─────┘         └─────┬─────┘                |
   |        │              │              │                     │                      |

   |  └─────┬─────┘                 └─────┬─────┘               └─────┬─────┘  物理通道)  |
   |        │                             │                           │                |
   |        ▼                             ▼                           ▼                |

第二幕：I/O 物理描述符核心基石——``struct bio``、``bio_vec`` 与迭代器
-------------------------------------------------------------------

在 Linux 通用块层中，一次 I/O 传输的物理内存载体是 **``struct bio``（``include/linux/blk_types.h``）**。

2.1 物理散布-聚集（Scatter-Gather）向量模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
一个文件系统请求可能由多个在物理内存中不连续的物理页片段组成。``struct bio`` 通过包含一组 ``struct bio_vec`` 数组实现物理页片段的高效聚合：

::

   +-----------------------------------------------------------------------------------+
   |                           struct bio 内存与物理拓扑布局                           |
   |                                                                                   |
   |  struct bio {                                                                     |
   |      struct bio          *bi_next;         /* 链表指针 (挂入 request 或 plug 链表)*/|
   |      struct block_device *bi_bdev;         /* 目标块设备实体 */                   |
   |      blk_opf_t           bi_opf;          /* 操作码 (REQ_OP_READ/WRITE) 与标志位 */|
   |      atomic_t            __bi_remaining;   /* 拆分子 bio 剩余未完成计数器 */      |
   |      struct bvec_iter    bi_iter;          /* 核心光标迭代器 (跟踪传输进度) */    |
   |      struct bio_vec      *bi_io_vec;       /* 散布/聚集向量数组指针 */            |
   |      unsigned short      bi_vcnt;          /* bio_vec 数组元素总数 */             |
   |      bio_end_io_t        *bi_end_io;       /* I/O 硬件完成中断回调函数指针 */     |
   |  };                                                                               |
   |                                                                                   |
   |  [散布向量数组: bi_io_vec]                                                        |
   |  ┌──────────────────┬──────────────────┬──────────────────┐                      |
   |  │ bio_vec[0]        │ bio_vec[1]        │ bio_vec[2]       │ ...                  |
   |  │ ├── bv_page: PageA│ ├── bv_page: PageB│ ├── bv_page: PageC│                      |
   |  │ ├── bv_offset: 0  │ ├── bv_offset: 512│ ├── bv_offset: 0  │                      |
   |  │ └── bv_len: 4096  │ └── bv_len: 2048  │ └── bv_len: 4096  │                      |
   |  └──────────────────┴──────────────────┴──────────────────┘                      |
   +-----------------------------------------------------------------------------------+

2.2 核心光标迭代器：``struct bvec_iter``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了在 I/O 部分完成或拆分时避免昂贵的内存数据移动，内核引入了只读光标结构体 ``struct bvec_iter``：
* **``bi_sector``**：当前未完成传输的物理起始扇区号（512 字节为一扇区）；
* **``bi_size``**：整个 bio 当前剩余未传输的总字节数；
* **``bi_idx``**：当前正在传输的 ``bi_io_vec`` 数组下标；
* **``bi_bvec_done``**：当前 ``bio_vec[bi_idx]`` 内部已经完成传输的字节偏移量。

调用 ``bio_advance(bio, bytes)`` 时，内核仅仅推进 ``bi_iter`` 内部的数值，底层物理页指针与数组结构毫发无损！

第三幕：``sbitmap`` 高并发标签分配器与硬件请求 ``struct request``
-----------------------------------------------------------------

底层硬件驱动（如 NVMe 控制器）能同时并发处理的命令数量是有限的（由 Queue Depth 决定，例如 1024）。通用块层必须为每一个在飞（In-Flight）的硬件命令分配一个唯一的整型 **``tag``**。

3.1 ``sbitmap``（可扩展位图）架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在高并发多核场景下，多个 CPU 同时向一个硬件队列申请 tag 会导致位图自旋锁严重拥塞。Linux 7.2 采用 **``sbitmap``（``include/linux/sbitmap.h``）**：
* 将大位图按字（Word）分块打散；
* 每个 CPU 核心维护私有的轮询游标，优先在本地字中通过 ``ffs()``（Find First Set）硬件位运算快速获取空闲 bit；
* 配合自适应休眠等待队列（``sbitmap_queue``），达成无锁纳秒级的 Tag 分配。

3.2 ``struct request`` 结构体解构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``struct request`` 是实际交付给底层硬件驱动的最终命令容器：

::

   +-----------------------------------------------------------------------------------+
   |                           struct request 核心物理拓扑                             |
   |                                                                                   |
   |  struct request {                                                                 |
   |      struct request_queue *q;              /* 归属的块设备总控队列 */             |
   |      struct blk_mq_ctx    *mq_ctx;         /* 提交该请求的 CPU 软件暂存上下文 */  |
   |      struct blk_mq_hw_ctx *mq_hctx;        /* 绑定的底层硬件派发上下文 */         |
   |      int                  tag;             /* 硬件分配的唯一命令标签 (Tag Index) */|
   |      sector_t             __sector;        /* 物理磁盘起始绝对扇区号 */           |
   |      unsigned int         __data_len;      /* 传输总数据字节数 */                 |
   |      struct bio           *bio;            /* 串联的第一个 struct bio */          |
   |      struct bio           *biotail;        /* 串联的最后一个 struct bio */        |
   |      unsigned short       nr_phys_segments;/* DMA 物理散布段总数 (Scatterlist 项数)*/|
   |      enum mq_rq_state     state;           /* 请求状态: IDLE / IN_FLIGHT / COMPLETE*/|
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

第四幕：I/O 提交与调度流转全时序（``submit_bio`` -> ``blk_mq_submit_bio``）
----------------------------------------------------------------------------

当文件系统或 Page Cache 调用 ``submit_bio(bio)`` 时，控制流进入 ``block/blk-mq.c:blk_mq_submit_bio()``。

4.1 提交与派发全景流水线
~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                        blk_mq_submit_bio() 核心执行时序                           |
   |                                                                                   |
   |  [ 1. 文件系统/Page Cache 调用 submit_bio(bio) ]                                  |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 2. 硬件边界拆分 (__bio_split_to_limits) ]                                      |
   |  - 检查设备最大扇区与 DMA 段限制，必要时切片为多个子 bio;                         |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 3. 请求合并探测 (blk_mq_attempt_bio_merge) ] ──► (前后向扇区连续?)             |
   |            │                                                                      |
   |            ├─► 【合并成功 (Merge Hit)】                                           |
   |            │   - 将 bio 挂入已有 request 尾部/头部，更新 __data_len 与段数;       |
   |            │   - 零分配开销 ──► 【极速返回!】                                     |
   |            │                                                                      |
   |            └─► 【合并失败 (Merge Miss)】                                          |
   |                │                                                                  |
   |                ▼                                                                  |
   |  [ 4. 申请/复用 struct request (blk_mq_get_new_requests) ]                        |
   |  - 从 sbitmap 中获取硬件 Tag，初始化 request 结构体;                              |
   |  - 将 bio 绑定到 request->bio;                                                    |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 5. 进程蓄水池插栓探测 (current->plug) ]                                        |
   |            │                                                                      |
   |            ├─► 【存在 Plug 蓄水池】                                               |
   |            │   - 将 request 挂入 current->plug->mq_list 暂存;                     |
   |            │   - 等待批量合并与批量冲刷 (blk_mq_flush_plug_list); ──► 【返回】     |
   |            │                                                                      |
   |            └─► 【无 Plug 蓄水池】                                                 |
   |                │                                                                  |
   |                ▼                                                                  |
   |  [ 6. 派发决策: 直发通道 vs 调度器入队 ]                                          |
   |  - 判断: 若无 I/O 调度器且硬件通道未拥塞:                                         |
   |    ► 调用 blk_mq_try_issue_directly(hctx, rq);                                    |
   |    ► 直接调用 q->mq_ops->queue_rq(hctx, &bd);                                     |
   |    ► 硬件敲响 NVMe 门铃 (Doorbell MMIO 写入) ──► 【直接发射上天!】                |
   |  - 否则: 将 request 插入软件队列/调度器，触发异步硬件队列运转 (blk_mq_run_hw_queue)|
   +-----------------------------------------------------------------------------------+

4.2 蓄水池插栓机制（Plug & Unplug）的高性能原理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当进程执行大文件拷贝或数据库批量写入时，频繁向 NVMe 控制器写入 MMIO 门铃寄存器会引发严重的 PCIe 总线事务开销。
* **插栓（Plug）**：``blk_start_plug(&plug)`` 在进程上下文中开启局部蓄水池，将生成的多个请求缓存在本地；
* **拔栓（Unplug）**：``blk_finish_plug(&plug)`` 触发批量连续合并，并通过一次硬件调用（``queue_rqs``）将数十个请求批量推入硬件，极大摊薄了 PCIe 总线开销与中断频率。

第五幕：硬件完成中断与跨核软中断分发（``blk_mq_complete_request``）
-------------------------------------------------------------------

当存储硬件完成数据物理传输后，控制流自底向上逆向返回内核。

5.1 硬件中断响应与 $O(1)$ 请求检索
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **MSI-X 硬件中断**：NVMe 控制器向 CPU 发送消息中断；
2. **中断处理例程（ISR）**：从 NVMe 完成队列（CQ）中读取完成项，获取其返回的整型 ``command_id``（即 ``tag``）；
3. **$O(1)$ 定位请求**：调用 ``blk_mq_tag_to_rq(tags, tag)``，无需遍历任何链表，直接通过数组下标取回原始的 ``struct request``。

5.2 跨核 IPI 负载均衡与软中断回结
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                     blk_mq 异步完成与软中断分发时序                              |
   |                                                                                   |
   |  [ 1. 硬件中断 ISR 调用 blk_mq_complete_request(rq) ]                             |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 2. 核心亲和性判定 (blk_mq_complete_need_ipi) ]                                 |
   |  - 判断: 当前中断 CPU 是否与提交 I/O 的原始 CPU 共享 L2/L3 缓存?                   |
   |            │                                                                      |
   |            ├─► 【不共享缓存 (跨 NUMA/跨物理核)】                                  |
   |            │   - 调用 blk_mq_complete_send_ipi(rq);                               |
   |            │   - 发送单核 IPI 中断，将完成逻辑路由回原始提交 CPU 处理, 保护缓存热度!|
   |            │                                                                      |
   |            └─► 【本地处理】                                                       |
   |                │                                                                  |
   |                ▼                                                                  |
   |  [ 3. 触发软中断 (BLOCK_SOFTIRQ / blk_done_softirq) ]                             |
   |  - 调用 blk_update_request(rq, error, bytes):                                     |
   |    ► 推进 bio->bi_iter;                                                           |
   |    ► 若 bio 全部传输完毕，调用 bio->bi_end_io(bio) ──► 唤醒 Page Cache / 进程等待;|
   |  - 调用 __blk_mq_free_request(rq):                                                |
   |    ► 释放 sbitmap 中的硬件 Tag;                                                   |
   |    ► 将 struct request 重置为空闲态 ──► 【全流程闭环结束!】                       |
   +-----------------------------------------------------------------------------------+

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 通用块层与 blk-mq 多队列体系：单队列全局大锁危机的根因、Per-CPU 软件暂存队列与硬件派发队列的双层解耦拓扑、``struct bio`` 物理向量模型与 ``bvec_iter`` 光标迭代、``sbitmap`` 无锁标签分配器、Plug 批量插栓与 Direct Issue 直发硬件通道，以及 MSI-X 硬件中断响应与跨核 IPI 亲和性完成分发全时序。

通用块层为物理磁盘提供了统一的高并发块读写接口。在此之上，真正的物理文件系统必须将文件、目录、权限以及元数据持久化映射为磁盘上的具体数据块，并提供严密的掉电一致性保证。

在 **第 6 节：ext4 / F2FS 物理磁盘布局、元数据日志事务 (JBD2) 与闪存写入优化** 中，我们将深入解构经典 ext4 块组（Block Group）、Inode 表、Extents 范围树物理布局、JBD2 日志事务状态机（三阶段提交：Running $\rightarrow$ Committing $\rightarrow$ Checkpoint），以及现代闪存专用文件系统 F2FS 的异地追加写（LFS）与段清理垃圾回收算法。

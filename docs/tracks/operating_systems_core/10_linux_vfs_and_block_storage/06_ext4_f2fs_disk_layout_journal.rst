第一幕：经典块布局之巅——ext4 物理磁盘拓扑与 Extents 范围树
----------------------------------------------------------

作为 Linux 最成熟稳定的工业级文件系统，ext4（Fourth Extended Filesystem）在磁盘上构建了层次分明的物理块组拓扑。

1.1 磁盘扇区宏观版图与灵活块组（Flex Block Group）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
磁盘在格式化为 ext4 时被划分为固定大小的逻辑块（Block，通常为 4KB）。整盘进一步被切分为一系列连续的 **块组（Block Groups）**：

::

   +-----------------------------------------------------------------------------------+
   |                             ext4 物理磁盘全局布局拓扑                             |
   |                                                                                   |
   |  [0 ~ 1024B 保留区 (用于 x86 MBR / BIOS 引导码)]                                  |
   |  ┌──────────────────────────────────────────────────────────────────────────────┐ |
   |  │ 块组 0 (Block Group 0)  │ 块组 1 (Block Group 1) │ ... │ 块组 N (Block Group N)│ |
   |  └─────────────────────────┴────────────────────────┴─────┴───────────────────────┘ |
   |                                                                                   |
   |  [单个块组 (Block Group) 内部微观物理结构]                                        |
   |  ┌──────────┬──────────┬──────────┬──────────┬────────────────┬─────────────────┐ |
   |  │ 超级块    │ 块组描述符│ 块位图   │ Inode位图│ Inode 表       │ 物理数据块区    │ |
   |  │ (Super   │ 表 (GDT) │ (Block   │ (Inode   │ (Inode Table)  │ (Data Blocks)   │ |
   |  │  Block)  │          │  Bitmap) │  Bitmap) │                │                 │ |
   |  │ 1024 B   │ N 个描述符│ 1 Block  │ 1 Block  │ 若干连续 Blocks│ 包含 32768 Blocks│ |
   |  └──────────┴──────────┴──────────┴──────────┴────────────────┴─────────────────┘ |
   +-----------------------------------------------------------------------------------+

为了克服传统块组中元数据分散导致磁头剧烈寻道的问题，ext4 引入了 **灵活块组（Flex Block Group）**：将连续 16~64 个逻辑块组的元数据（块位图、Inode 位图与 Inode 表）紧密打包集中存放在组首，从而为后续的数据块区留出数 GB 绝对连续的物理写入通道！

1.2 Inode 结构体与 Extents 范围树解构（``fs/ext4/extents.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ext2/3 时代，文件数据块采用间接指针（12 个直接块 + 单重/双重/三重间接块）寻址，对于大型文件需要多级递归寻址且极易产生碎片。ext4 彻底废弃该模型，引入 **Extents 连续范围树**：

::

   +-----------------------------------------------------------------------------------+
   |                           ext4 Inode 与 Extent 树物理拓扑                         |
   |                                                                                   |
   |  struct ext4_inode (256 字节) {                                                   |
   |      __le16 i_mode;        /* 文件权限与类型 */                                   |
   |      __le32 i_size_lo;     /* 文件大小低 32 位 */                                 |
   |      __le32 i_flags;       /* 标志位 (EXT4_EXTENTS_FL = 0x80000 启用 Extent 树) */|
   |      __le32 i_block[15];   /* 60 字节专用存储区: 直接内嵌 Extent 树根节点! */     |
   |  };                                                                               |
   |                                                                                   |
   |  [i_block[15] 内嵌 Extent 树根节点: 60 字节]                                      |
   |  ┌────────────────────────────────────────────────────────┐                       |
   |  │ ext4_extent_header (12 字节: magic=0xF30A, entries, max, depth=0/1...)         │
   |  ├────────────────────────────────────────────────────────┤                       |
   |  │ 若 depth == 0 (叶子节点直接内嵌 4 个 ext4_extent):     │                       |
   |  │ ├── ext4_extent[0] (ee_block: 0,   ee_len: 2048, ee_start: 0x100000)          │
   |  │ ├── ext4_extent[1] (ee_block: 2048,ee_len: 1024, ee_start: 0x100800)          │
   |  │ └── ...                                                │                       |
   |  │ 若 depth > 0 (内部索引节点内嵌 4 个 ext4_extent_idx):  │                       |
   |  │ ├── ext4_extent_idx[0] (ei_block: 0, ei_leaf: 下级索引/叶子物理块号)          │
   |  │ └── ...                                                │                       |
   |  └────────────────────────────────────────────────────────┘                       |
   +-----------------------------------------------------------------------------------+

.. table:: Extent 树核心数据结构字段与物理语义
   :widths: 25 35 40

   +==============================+=======================================+=============================================+
   | 数据结构                     | 核心字段与长度                        | 物理意义与微观特性                          |
   +==============================+=======================================+=============================================+
   | **``struct ext4_extent_header``**| ``eh_magic (0xF30A), eh_entries,``    | 树节点标头（12 字节），记录当前层级条目数、  |
   |                              | ``eh_max, eh_depth, eh_generation``   | 最大容量与树深度（``depth=0`` 代表叶子节点）|
   +------------------------------+---------------------------------------+---------------------------------------------+
   | **``struct ext4_extent_idx``**| ``ei_block, ei_leaf_lo, ei_leaf_hi``  | 内部索引项（12 字节），将逻辑块号路由到下一 |
   |                              |                                       | 级物理 Extent 索引块                        |
   +------------------------------+---------------------------------------+---------------------------------------------+
   | **``struct ext4_extent``**   | ``ee_block, ee_len, ee_start_lo/hi``  | 叶子数据项（12 字节），单条目直接映射多达   |
   |                              |                                       | **32768 个连续物理块（128MB）**！           |
   +------------------------------+---------------------------------------+---------------------------------------------+

深度为 0 的 Extent 树直接内嵌在 Inode 内部，无需任何额外元数据磁盘读取；一棵 4 层深度的 Extent 树即可轻松索引高达 **1 EB（$2^{60}$ 字节）** 的单文件物理空间！

第二幕：掉电一致性守门人——JBD2 日志事务引擎核心状态机
----------------------------------------------------

当向文件系统写入数据时，内核必须更新三处物理介质：**数据块、Inode 元数据与块位图**。如果写入过程中突然遭遇系统掉电或内核崩溃，这三处更新无法原子完成，将导致严重的元数据损坏与数据丢失。

2.1 JBD2 预写式日志（Write-Ahead Logging / WAL）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Linux 内核通过独立的 **JBD2（Journaling Block Device 2 / ``fs/jbd2/``）** 子系统提供通用事务保护：在将变更写入文件系统主数据区（In-Place）之前，先将所有变更作为一个原子事务写入独立的循环日志区（Journal）。

.. table:: JBD2 三大日志模式权衡矩阵
   :widths: 20 25 25 30

   +======================+=================================+=================================+=============================================+
   | 日志模式             | 数据块写入路径                  | 元数据写入路径                  | 性能与安全性权衡                            |
   +======================+=================================+=================================+=============================================+
   | **``data=journal``** | 先写入 Journal，再写入主数据区  | 随数据一同写入 Journal          | **最高安全性**，掉电绝不丢数据；写入放大 2x |
   +----------------------+---------------------------------+---------------------------------+---------------------------------------------+
   | **``data=ordered``** | **先刷入主数据区**，完成后提交  | 写入 Journal 并在数据落盘后提交 | **默认黄金平衡**，杜绝文件元数据指向旧脏数据|
   +----------------------+---------------------------------+---------------------------------+---------------------------------------------+
   | **``data=writeback``**| 异步随意刷入主数据区            | 仅元数据写入 Journal            | **最高吞吐量**，但掉电后文件可能残留旧数据  |
   +----------------------+---------------------------------+---------------------------------+---------------------------------------------+

2.2 复合事务（Compound Transaction）生命周期状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了避免每个系统调用单独刷盘导致的 I/O 阻塞，JBD2 将并发进程的多个写操作（``handle_t``）合并为一个巨大的 **复合事务（``transaction_t``）**：

::

   +-----------------------------------------------------------------------------------+
   |                           JBD2 复合事务生命周期流转状态机                         |
   |                                                                                   |
   |  [ 1. T_RUNNING (运行态: 持续接收应用写入 handle) ]                               |
   |  - 进程调用 jbd2_journal_start() 预扣 Credits 缓冲配额;                           |
   |  - 将修改的脏元数据挂入 transaction->t_buffers 链表;                              |
   |            │                                                                      |
   |            ▼ (达到 5 秒定时器超时 或 事务空间占满)                                |
   |  [ 2. T_LOCKED (锁定态: 关闭写入窗口) ]                                           |
   |  - 唤醒内核守护线程 kjournald2;                                                   |
   |  - 停止接收新的 handle，等待当前在飞（In-Flight）handle 退出 (jbd2_journal_stop); |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 3. T_FLUSH / T_COMMIT (提交态: 物理落盘) ]                                     |
   |  - Step A: (data=ordered) 刷写所有关联 Inode 的脏数据块 (t_inode_list);           |
   |  - Step B: 向 Journal 连续写入描述符块 (Descriptor Block) 与所有脏元数据块;       |
   |  - Step C: 触发硬件写屏障 (REQ_PREFLUSH | REQ_FUA);                               |
   |  - Step D: 写入提交记录块 (Commit Block, 携带 CRC32C 校验和);                     |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 4. T_FINISHED (归档态: Checkpoint 检查点等待) ]                                |
   |  - 事务已安全持久化在 Journal 中! 将其挂入 t_checkpoint_list;                     |
   |  - 等待后台回写线程将主数据区刷盘完毕后，清理释放该 Journal 空间 (Cleanup Tail)。 |
   +-----------------------------------------------------------------------------------+

2.3 Fast Commit（快提交）亚毫秒极速事务
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在数据库高频调用 ``fsync()`` 的场景下，提交整个复合事务（往往包含数百个无关块）开销巨大。ext4 与 JBD2 引入了 **Fast Commit（``JBD2_FEATURE_INCOMPAT_FAST_COMMIT``）**：
* 仅在专用 Fast Commit 区域紧凑记录发生变更的单个 Inode 增量或 Extent 变更 Delta；
* 完全绕过完整事务提交流水线，使 ``fsync()`` 延迟降低 **$60\% \sim 80\%$**！

2.4 崩溃恢复三遍扫描算法（``jbd2_journal_recover()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当系统意外掉电重启并重新挂载 ext4 时，内核运行三遍扫描恢复：
1. **Pass 1 (Scan)**：扫描 Journal 头部，定位最近一次有效 Checkpoint 的起始位置，检查所有 Commit Block 的 CRC32C 校验和，确立有效事务边界；
2. **Pass 2 (Revoke)**：构建已撤销块哈希表（Revoke Table），记录在事务之后被释放删除的物理块，防止旧日志误覆盖新分配的数据；
3. **Pass 3 (Replay)**：顺序重放所有校验合法的元数据块，将其物理覆写至文件系统主数据区，实现毫秒级自愈！

第三幕：闪存时代的架构革命——F2FS 物理布局与冷热分流追加写
--------------------------------------------------------

机械硬盘的物理特征是“原位可覆写、寻道开销大”；而基于 NAND Flash 晶体管的固态存储（SSD/UFS/NVMe）具有截然相反的物理约束：
* **读写以页（Page，4KB~16KB）为单位**；
* **擦除以块（Erase Block，2MB~16MB）为单位**；
* **禁止原位覆写（Erase-Before-Write）**：物理页写入前必须整块擦除。

传统文件系统的随机原位覆写会导致固态硬盘内部的 FTL（闪存转换层）产生灾难性的垃圾回收与写放大（WAF 高达 5~10），迅速磨损闪存寿命。为此，三星主导研发了专为闪存定制的 **F2FS（Flash-Friendly File System / ``fs/f2fs/``）**。

3.1 F2FS 物理六大分区全景拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

   |  │ SB  │ CP  │ SIT │ NAT │ SSA │                   Main Area                    │ |
   |  │(超级│(检查│(段信│(节点│(段摘│               (核心数据与节点主存储区)             │ |
   |  │ 块) │ 点) │ 息表│ 地址│ 要区│                                                │ |
   |  │     │     │ )   │ 表) │ )   │                                                │ |
   |  └─────┴─────┴─────┴─────┴─────┴────────────────────────────────────────────────┘ |

   |     │     │     │     │     │                         ▼                           |
   |     │     │     │     │     │               由数万个 Segment (2MB) 构成           |

   |     └────────────────────────────────► 双副本超级块 (0x00 与 0x1000 偏移)         |

3.2 节点地址表（NAT）终结“游走树”（Wandering Tree）难题
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
经典的日志结构文件系统（LFS）采用异地追加写（Append-Only）。当修改一个数据块 $D$ 时，必须将其写入新物理地址 $D'$；这导致指向它的直接 Inode $I$ 也必须修改地址为 $I'$，进而导致父目录、祖父目录逐级向上发生级联变动，直到根节点——这就是著名的 **游走树灾难（Wandering Tree Problem）**。

::

   +-----------------------------------------------------------------------------------+
   |                         F2FS NAT 机制如何化解游走树灾难                           |
   |                                                                                   |
   |  [传统 LFS 级联雪崩]                                                              |
   |  Root Inode' ◄── Parent Inode' ◄── Inode' ◄── Direct Node' ◄── Data Block' (改1点动全树)|
   |                                                                                   |
   |  [F2FS NAT 解耦架构]                                                              |
   |  Parent Inode (保持不动!) ──► Inode (保持不动!) ──► Direct Node (nid=50)          |
   |                                                           │                       |
   |                                                           ▼                       |
   |                                       ┌───────────────────────────────────────┐   |
   |                                       │ 节点地址表 (Node Address Table / NAT) │   |
   |                                       │ ├── Node ID 50 ──► 物理块号 0x880000  │   |
   |                                       └───────────────────────────────────────┘   |
   |                                                           │                       |
   |                                                           ▼                       |
   |                                              物理数据块 Data Block' (新地址写入)  |
   +-----------------------------------------------------------------------------------+

**破局之道**：F2FS 在所有 Inode/索引节点与磁盘物理地址之间插入了 **NAT（Node Address Table）** 虚拟映射层。数据块变动时，仅需更新直接 Node 并将其在 NAT 表中的物理块号更新，**所有上层父级 Inode 与目录树结构完全无需变动**！

3.3 六路冷热分流异地追加写（Multi-Head Logging）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
F2FS 在 Main Area 内部同时打开 6 个独立的活动写入段（Segment），按数据更新频率实施物理隔离：

.. table:: F2FS 六路冷热数据隔离写入流
   :widths: 20 25 55

   +======================+=================================+===================================================================+
   | 写入流类型           | 涵盖数据实体                    | 核心设计哲学                                                      |
   +======================+=================================+===================================================================+
   | **Hot Node**         | 目录 Inode 描述符               | 更新极频繁，寿命极短                                              |
   +----------------------+---------------------------------+-------------------------------------------------------------------+
   | **Warm Node**        | 普通文件 Inode 描述符           | 常规更新频率                                                      |
   +----------------------+---------------------------------+-------------------------------------------------------------------+
   | **Cold Node**        | 文件的间接索引块、数据移动块    | 只读或极少修改                                                    |
   +----------------------+---------------------------------+-------------------------------------------------------------------+
   | **Hot Data**         | 目录项数据块 (Dentry Blocks)    | 随文件创建/删除高频变动                                           |
   +----------------------+---------------------------------+-------------------------------------------------------------------+
   | **Warm Data**        | 普通用户文件数据块              | 大多数应用写入流                                                  |
   +----------------------+---------------------------------+-------------------------------------------------------------------+
   | **Cold Data**        | 多媒体大文件、压缩/只读归档数据 | 长期不可变，聚集在独立段中，GC 时几乎不需要搬移！                 |
   +----------------------+---------------------------------+-------------------------------------------------------------------+

第四幕：F2FS 段清理与垃圾回收（Garbage Collection）微观时序
-----------------------------------------------------------

异地追加写不可避免地会在旧物理段中留下大量无效数据块。当可用空闲段不足时，内核触发垃圾回收（GC）。

4.1 双模垃圾回收策略状态机（``fs/f2fs/gc.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                             F2FS 垃圾回收算法决策状态机                           |
   |                                                                                   |
   |  [ 1. 前台同步 GC (Foreground GC / 内存紧急水位) ]                                |
   |  - 触发条件: 进程分配块时发现可用段耗尽 (Free Segments < Threshold);              |
   |  - 算法模型: **贪心算法 (Greedy Algorithm)**;                                     |
   |  - 决策依据: 立即扫描 SIT 表，挑出无效块最多（Dirty 程度最高）的 Segment 强制清理;|
   |  - 特性: 追求单次回收速度，尽快释放空间，允许承受一定的写放大。                   |
   |                                                                                   |
   |  [ 2. 后台异步 GC (Background GC / 守护线程 f2fs_gc) ]                            |
   |  - 触发条件: 系统 I/O 空闲时定时唤醒;                                             |
   |  - 算法模型: **成本-收益算法 (Cost-Benefit Algorithm)**;                         |
   |  - 效益公式:                                                                      |
   |                    $$	ext{Cost-Benefit} = \frac{1 - u}{2u} 	imes 	ext{Age}$$   |
   |                    (其中 $u$ 为有效块占比，$	ext{Age}$ 为自上次修改以来的时间)   |
   |  - 特性: 优先挑选“有效块极少且长时间未修改（冷数据）”的段进行迁移，使闪存写放大降 |
   |          至极限接近 1.0！                                                         |
   +-----------------------------------------------------------------------------------+

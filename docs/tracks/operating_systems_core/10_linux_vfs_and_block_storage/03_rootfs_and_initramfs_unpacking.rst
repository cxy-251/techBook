第一幕：早期文件系统的“先有鸡还是先有蛋”——rootfs 内存文件系统诞生
------------------------------------------------------------------

在虚拟文件系统（VFS）的世界中，任何文件的读取、驱动的加载、配置文件的解析，都必须依赖一棵完整的 VFS 树（包含根挂载点 ``struct vfsmount`` 与根目录项 ``struct dentry``）。

1.1 引导期的文件系统真空状态
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Linux 内核启动初期，物理硬件世界处于一片真空状态：
* NVMe / SATA 存储控制器驱动尚未加载；
* 硬盘 MBR / GPT 分区表尚未解析；
* ext4 / XFS 文件系统驱动模块尚未初始化。

如果内核必须从物理磁盘上读取根文件系统，但读取磁盘又必须依赖存储驱动，这就陷入了经典的“先有鸡还是先有蛋”的死锁难题。
* **物理破解之道**：内核在内存 RAM 中**无中生有地凭空构建一个纯内存虚拟根文件系统——``rootfs``**！

1.2 Linux 7.2 现代双层架构：nullfs (ID 1) + rootfs (ID 2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在传统早期内核中，``rootfs`` 作为整个 VFS 树的绝对不可动摇的根节点（Root of Namespace），无法被真正卸载（``umount``）或跨越。这导致早期 initramfs 所占用的内存结构难以在挂载真实磁盘根文件系统后被干净剥离。

在 Linux 7.2 中（``fs/namespace.c:init_mount_tree()``），内核引入了一项极其优雅的现代化拓扑革新——**双层根挂载架构**：

::

   +-----------------------------------------------------------------------------------+
   |                       Linux 7.2 初始挂载树 (init_mount_tree) 拓扑                 |
   |                                                                                   |
   |  [不可变底座: nullfs (Mount ID 1)] ──► 真正的命名空间底层锚点 (init_mnt_ns.root)   |
   |            │                                                                      |
   |            ▼ (覆盖挂载 Overmount)                                                 |
   |  [可变根文件系统: rootfs (Mount ID 2)] ──► 当前进程 root / pwd 实际指向的内存文件系统 |
   |  ├── /init (早期用户空间 PID 1 执行体)                                            |
   |  ├── /dev (由内核 mknod 生成的 console, null 等早期设备节点)                      |
   |  └── /lib/modules (硬件驱动动态内核模块 .ko)                                      |
   +-----------------------------------------------------------------------------------+

.. table:: nullfs 与 rootfs 双层挂载角色对比
   :widths: 20 35 45

   +================+========================+==================================================================+
   | 挂载层级       | 挂载 ID (Mount ID)     | 物理职能与设计意义                                               |
   +================+========================+==================================================================+
   | **nullfs**     | **Mount ID = 1**       | **不可变底层基石**。作为 ``init_mnt_ns`` 的绝对根锚点，永不卸载 |
   +----------------+------------------------+------------------------------------------------------------------+
   | **rootfs**     | **Mount ID = 2**       | **可变内存文件系统**。挂载在 nullfs 之上，承载解压后的 initramfs |
   +----------------+------------------------+------------------------------------------------------------------+

**架构飞跃**：当系统后续通过 ``pivot_root()`` 切换到真实磁盘根分区时，可以将真实物理磁盘挂载点直接置换到 nullfs 之上，并将旧的 ``rootfs`` 彻底卸载剥离，实现内存与挂载树的绝对纯净！

第二幕：initramfs 容器架构与 cpio New ASCII 物理编码协议
---------------------------------------------------------

早期用户空间（Early Userspace）通过 **``initramfs``（Initial RAM File System）** 传递给内核。

2.1 initrd vs initramfs 的物理本质差异
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **传统 initrd（Initial RAM Disk）**：在内存中模拟一个虚拟块设备（``/dev/ram0``），格式为 ext2 磁盘镜像。内核必须为其建立双重缓存（块设备的 Buffer Cache + 文件系统的 Page Cache），不仅浪费 50% 内存，而且解包与读写受限于块层 I/O 调度流水线；
* **现代 initramfs**：纯 **cpio 归档文件流**。内核直接将其流式解压至 ``rootfs`` 的 Page Cache 中，零块设备抽象，零内存冗余复制，纳秒级就绪。

2.2 cpio New ASCII 格式（Magic: ``070701`` / ``070702``）头部规范
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Linux 内核采用 **SVR4 便携式 cpio 格式（New ASCII Format）**。其文件头由连续 **110 字节的纯 ASCII 字符** 构成，彻底消除了跨 CPU 架构的大端序（Big-Endian）/ 小端序（Little-Endian）二进制兼容障碍：

::

   +-----------------------------------------------------------------------------------+
   |                       cpio New ASCII 文件头 (110 字节) 物理布局                   |
   |                                                                                   |
   |  偏移 (Offset)   长度 (Bytes)   字段名称 (Field)     物理语义说明                 |
   |  0x00            6              c_magic              魔数: "070701" (标准) /      |
   |                                                        "070702" (带 CRC32 校验)   |
   |  0x06            8              c_ino                Inode 编号 (8 位十六进制文本)|
   |  0x0E            8              c_mode               文件类型与权限位 (S_IFREG等) |
   |  0x16            8              c_uid                所有者 UID                   |
   |  0x1E            8              c_gid                所属组 GID                   |
   |  0x26            8              c_nlink              硬链接计数                   |
   |  0x2E            8              c_mtime              修改时间戳                   |
   |  0x36            8              c_filesize           文件体数据物理长度 (Bytes)   |
   |  0x3E            8              c_maj                主设备号                     |
   |  0x46            8              c_min                次设备号                     |
   |  0x4E            8              c_rmaj               特殊设备主设备号             |
   |  0x56            8              c_rmin               特殊设备次设备号             |
   |  0x5E            8              c_namesize           文件名字符串长度 (含 '\0')   |
   |  0x66            8              c_chksum             CRC32 校验和 (针对 070702)   |
   |  0x6E            namesize       filename             以 '\0' 结尾的文件路径名     |
   |  ...             (Pad to 4B)    Padding              对齐填充 (文件名按 4 字节对齐) |
   |  ...             filesize       filedata             文件体二进制数据             |
   |  ...             (Pad to 4B)    Padding              对齐填充 (文件体按 4 字节对齐) |
   +-----------------------------------------------------------------------------------+

第三幕：内核态流式解包状态机（``init/initramfs.c``）
----------------------------------------------------

内核在 ``init/initramfs.c`` 中实现了一个极其精密的高性能 **8 状态有限状态机（Finite State Machine, FSM）**，负责在零拷贝/流式管道中边解压边重组文件系统目录树。

3.1 8 状态有限状态机流转拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       initramfs 流式解包 8 状态有限状态机                         |
   |                                                                                   |
   |  [ Start ] ──(读取 110 字节 cpio 头部)──► [ GotHeader ]                           |
   |      ▲                                         │                                  |
   |      │ (遇到填充 0)                            ├─► S_ISLNK  ──► [ GotSymlink ]    |
   |  [ Reset ]                                     ├─► S_ISREG  ──► [ GotName ]       |
   |      ▲                                         └─► 未知类型 ──► [ SkipIt ]        |
   |      │                                                               │            |
   |      │               ┌───────────────────────────────────────────────┘            |
   |      │               ▼                                                            |
   |  [ SkipIt ] ◄── [ CopyFile ] ◄──(S_ISREG 开启目标文件写入数据)                      |
   |      │                                                                            |
   |      └─────────► 遍历直至遇到文件结束哨兵: "TRAILER!!!"                           |
   +-----------------------------------------------------------------------------------+

3.2 多源压缩格式自动嗅探与解压总线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
内核通过 ``decompress_method(buf, len, &name)`` 探测归档首部的压缩魔数：
* **Zstandard (zstd)**：魔数 ``0x28, 0xB5, 0x2F, 0xFD``（现代 Linux 推荐默认，解压吞吐达 1.5 GB/s）；
* **XZ (LZMA2)**：魔数 ``0xFD, '7', 'z', 'X', 'Z', 0x00``（极致压缩比）；
* **Gzip (deflate)**：魔数 ``0x1F, 0x8B``（经典兼容格式）。

解压引擎以流式回调方式向 **``flush_buffer()``** 泵送原始 cpio 字节流，无需在内核内存中解压出完整的几百兆临时镜像文件。

3.3 核心文件类型实体还原时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在状态机的 ``do_name()`` 与 ``do_copy()`` 阶段，内核针对不同文件类型调用专用的早期系统调用封装：
1. **目录（``S_ISDIR``）**：
   * 调用 ``init_mkdir(path, mode)`` 创建 VFS 目录节点；
   * 调用 ``init_chown()`` / ``init_chmod()`` 恢复权限；
   * 将目录加入 ``dir_list`` 链表，待解包全流程结束后在 ``dir_utime()`` 中统一修补目录修改时间戳（避免创建子文件时刷新父目录 mtime）。
2. **普通文件（``S_ISREG``）**：
   * 调用 ``filp_open(path, O_WRONLY|O_CREAT|O_TRUNC|O_LARGEFILE, mode)`` 创建空文件；
   * 在 ``do_copy()`` 循环中调用 ``kernel_write()`` 将解压出的数据块直接写入文件的 Page Cache；
   * 若启用了 ``csum_present``（070702 协议），累加计算 ``io_csum`` 并与头部的 ``hdr_csum`` 执行严格校验；
   * 调用 ``fput(wfile)`` 闭合文件并持久化。
3. **符号链接（``S_ISLNK``）**：
   * 读取内联的目标路径，调用 ``init_symlink(target, path)`` 创建软链接；
   * 调用 ``init_chown(..., AT_SYMLINK_NOFOLLOW)`` 修复所属权。
4. **设备节点（``S_ISCHR`` / ``S_ISBLK`` / ``S_ISFIFO`` / ``S_ISSOCK``）**：
   * 调用 ``init_mknod(path, mode, rdev)`` 在内存文件系统中构建初始设备节点（例如初始化不可或缺的 ``/dev/console`` 字符设备，主设备号 5，次设备号 1）。
5. **硬链接（Hardlink）哈希重组**：
   * 当遇到 ``nlink >= 2`` 的文件时，调用 ``find_link(major, minor, ino, mode, path)`` 在 32 槽位链表哈希表中检索；
   * 若为首次遇到该 Inode，将当前路径名录入哈希表；
   * 若非首次遇到，调用 ``init_link(old_path, current_path)`` 直接建立硬链接，避免重复写入文件体数据。

第四幕：双源载入拓扑——内置 initramfs 与外部 GRUB2 initramfs 协同
-----------------------------------------------------------------

Linux 7.2 支持两路来源的 initramfs 深度协同：

::

   +-----------------------------------------------------------------------------------+
   |                     内置 vs 外部 initramfs 载入与内存生命周期                     |
   |                                                                                   |
   |  [来源 1: 内置 initramfs]                                                         |
   |  - 链接在内核镜像 .init.ramfs 段 (__initramfs_start ~ __initramfs_size)           |
   |  - 职能: 提供最小化救援 shell 或空目录结构                                        |
   |                                                                                   |
   |  [来源 2: 外部 initramfs (由 GRUB2 加载)]                                         |
   |  - 物理内存区间: initrd_start ~ initrd_end (由 memblock_reserve 保护)             |
   |  - 职能: 包含全量硬件驱动 (.ko)、udev 规则与真实 rootfs 探测脚本                  |
   |            │                                                                      |
   |            ▼ 触发解包流水线 (do_populate_rootfs)                                  |
   |  1. unpack_to_rootfs(__initramfs_start, __initramfs_size); /* 解包内置 */         |
   |  2. unpack_to_rootfs((char *)initrd_start, initrd_end - initrd_start); /* 覆盖解包*/|
   |            │                                                                      |
   |            ▼ 内存释放与物理回收                                                   |
   |  - 调用 free_initrd_mem(initrd_start, initrd_end); ──► 物理页全量归还伙伴系统!    |
   +-----------------------------------------------------------------------------------+

第五幕：多核异步解包与早期 PID 1 执行交割
-----------------------------------------

解包一个庞大的现代 Linux 发行版 initramfs（体积常达 50MB~150MB，包含大量显卡、网卡、RAID 驱动模块）通常耗费数百毫秒至数秒。

5.1 异步解包调度机制（``populate_rootfs``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``init/initramfs.c:populate_rootfs()`` 中，内核利用 **``async_schedule_domain``** 将解包流水线分发给异步内核工作线程：

::

   static int __init populate_rootfs(void)
   {
       /* 将 do_populate_rootfs 派发至独立的 initramfs_domain 异步线程域 */
       initramfs_cookie = async_schedule_domain(do_populate_rootfs, NULL,
                                                &initramfs_domain);
       usermodehelper_enable();

       /* 若配置了同步等待模式 (initramfs_async=0)，则在此阻塞 */
       if (!initramfs_async)
           wait_for_initramfs();
       return 0;
   }
   rootfs_initcall(populate_rootfs);

主引导核无需死等解包完成，可以并发执行 ACPI 子系统初始化、PCI 设备枚举与外设固件准备。

5.2 早期 PID 1 诞生与大门开启
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在内核主线程即将启动首个用户态进程前，调用 **``wait_for_initramfs()``** 确保异步解包全部完成。

此时，``rootfs`` 内部已包含完整的用户空间环境：
1. 内核尝试通过 ``kernel_execve()`` 执行位于根目录的 **``/init``** 脚本；
2. ``/init`` 脚本在早期用户空间中运行，加载 NVMe/SATA 驱动，解析 UUID，初始化 LVM / LUKS 加密卷；
3. 将探测到的真实物理硬盘分区挂载到 ``/sysroot``；
4. 调用 ``switch_root / pivot_root`` 将系统根目录跃迁至真实物理磁盘，并执行最终的 ``/sbin/init``（systemd）！

小结与下章导读
--------------

本节深入解构了 Linux 7.2 早期虚拟根文件系统构建与 initramfs 解包的微观全貌：nullfs (ID 1) + rootfs (ID 2) 现代化双层嵌套挂载拓扑、cpio New ASCII 8 状态有限状态机解析流水线、多源压缩流式解压适配、文件/目录/符号链接/设备节点与硬链接重组、双源 initramfs 协同，以及多核异步解包与向早期 PID 1（``/init``）的执行交割。

在文件被解压写入 ``rootfs`` 或从磁盘读写的过程中，所有的数据流均流经了 VFS 的核心中枢——**页缓存（Page Cache）**。内核究竟如何为每个文件构建高速缓存？``address_space`` 结构体如何管理文件与物理页的映射关系？XArray 基数树如何支撑高并发的页检索？脏页（Dirty Pages）又是如何被异步回写到底层存储介质的？

在 **第 4 节：页缓存 (Page Cache) 机制：``address_space`` 结构、XArray 检索与脏页异步回写** 中，我们将深入剖析 Page Cache 的微观架构、``address_space_operations`` 核心回调、XArray 锁优化与平衡回写守护进程（flusher threads）的物理时钟时序。

第一幕：磁盘与内存的纳秒鸿沟——页缓存 (Page Cache) 物理哲学与 ``address_space`` 拓扑
-----------------------------------------------------------------------------------

在计算机体系结构中，物理存储介质与片上 DRAM 之间存在着巨大的访问延迟鸿沟：
* **DRAM 内存访问延迟**：约 $50 \sim 100	ext{ ns}$；
* **PCIe 5.0 NVMe 固态硬盘延迟**：约 $10 \sim 30\ \mu	ext{s}$（慢约 $300$ 倍）；
* **传统机械硬盘（HDD）寻道延迟**：约 $5 \sim 10	ext{ ms}$（慢约 $100,000$ 倍）。

如果每次文件读写都直接穿透到底层物理块设备，CPU 将长期陷于 I/O 阻塞等待。为此，Linux 内核设计了 **页缓存（Page Cache）**，将空闲物理内存全量转化为磁盘数据的动态高速镜像。

1.1 ``struct address_space`` 的双重身份
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 VFS 中，``struct address_space`` 是连接“文件逻辑偏移量（``pgoff_t``）”与“物理内存页（``struct folio`` / ``struct page``）”的抽象容器：

::

   +-----------------------------------------------------------------------------------+
   |                    Inode 与 Address Space 物理拓扑关系                            |
   |                                                                                   |
   |  [文件实体: struct inode]                                                         |
   |  ├── i_ino (Inode 编号) / i_size (文件逻辑大小)                                   |
   |  ├── i_data (内嵌的默认 address_space 实体)                                       |
   |  └── i_mapping ──► 指向实际生效的 address_space (普通文件指向 &i_data;            |
   |                    块设备特殊文件指向底层 bdev->bd_inode->i_mapping)             |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [缓存中枢: struct address_space]                                                 |
   |  ├── host ─────────────► 反向指针，指向所属的 struct inode                        |
   |  ├── i_pages ──────────► XArray 核心数据结构 (管理全部缓存物理页 Folios)          |
   |  ├── invalidate_lock ──► 读写信号量 (保护页缓存内容与磁盘块映射的一致性)          |
   |  ├── i_mmap ───────────► 区间树 (struct rb_root_cached, 跟踪所有共享/私有 mmap)   |
   |  ├── nrpages ──────────► 当前缓存的物理页总数                                     |
   |  ├── writeback_index ──► 循环异步回写起始页索引 (pgoff_t)                         |
   |  └── a_ops ────────────► 函数指针表 (struct address_space_operations)             |
   +-----------------------------------------------------------------------------------+

1.2 地址空间操作表（``struct address_space_operations``）核心契约
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
不同文件系统（ext4, XFS, Btrfs, tmpfs, NFS）通过实现 ``a_ops`` 回调，定义其专属的页缓存交互逻辑：
* **``read_folio(file, folio)``**：从磁盘读取一个完整的物理页数据填充至页缓存；
* **``writepages(mapping, wbc)``**：将该地址空间中的脏页（Dirty Folios）批量回写到底层存储；
* **``dirty_folio(mapping, folio)``**：将指定的干净页标记为脏页并更新 XArray 标记位图；
* **``readahead(rac)``**：执行自适应预读，异步发起连续多个物理页的磁盘 DMA 读取；
* **``write_begin(...) / write_end(...)``**：通用带缓存写入的两阶段事务协议；
* **``direct_IO(iocb, iter)``**：绕过页缓存的 Direct I/O（``O_DIRECT``）直通接口；
* **``migrate_folio(mapping, dst, src, mode)``**：物理内存碎片整理时的页迁移回调。

第二幕：从基数树 (Radix Tree) 到 XArray 革命——``i_pages`` 极限检索与标记位图
------------------------------------------------------------------------------

在 Linux 早期版本中，``address_space`` 使用基数树（Radix Tree）索引物理页。随着现代系统内存容量迈向 TB 级、多核高并发竞争加剧以及大页（Huge Folios / Transparent Huge Pages）的普及，内核全面演进为 **XArray（``include/linux/xarray.h``）**。

2.1 XArray 拓扑架构与分层检索
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
XArray 是一棵高度优化的自适应多叉检索树。以 64 位系统为例，它以文件的逻辑页偏移量（``pgoff_t index``，即文件字节偏移量 $\gg 12$）为键，进行 $O(\log_{64} N)$ 的极速定位：

::

   +-----------------------------------------------------------------------------------+
   |                             XArray 多叉分层检索拓扑                               |
   |                                                                                   |
   |  文件页偏移量 index: [ 63 ... 18 | 17 ... 12 | 11 ... 6 | 5 ... 0 ] (6 位一组，64 叉)|
   |                               │           │          │          │                 |
   |  xa_head ─────────────────────┘           │          │          │                 |
   |    │ (Level 3 Node: 64 槽位)              │          │          │                 |
   |    └────────► [ Slot i ] ─────────────────┘          │          │                 |
   |                 │ (Level 2 Node: 64 槽位)            │          │                 |
   |                 └────────► [ Slot j ] ───────────────┘          │                 |
   |                              │ (Level 1 Node: 64 槽位)          │                 |
   |                              └────────► [ Slot k ] ─────────────┘                 |
   |                                           │                                       |
   |                                           ▼                                       |
   |                                    [ struct folio * ] (物理页描述符指针)          |
   +-----------------------------------------------------------------------------------+

2.2 RCU 无锁并发读取（Lockless RCU Walk）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
XArray 的核心优势在于其完全兼容 **RCU（Read-Copy Update）无锁机制**：
* 读操作（``filemap_get_page()`` / ``xa_load()``）在 ``rcu_read_lock()`` 保护下进行，无需获取任何自旋锁或信号量，多核并发读取性能线性扩展；
* 写操作（插入/删除页、拆分/合并大页）通过 ``xa_lock_irq()`` 自旋锁保护，并在修改内部节点指针时使用内存屏障（Memory Barriers），确保读端永远看到自洽的树结构。

2.3 三色标记位图（XArray Marks）与脏页瞬态感知
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
XArray 在每个内部节点的元数据中内嵌了 **分层标记位图（Marks）**，自底向上递归汇总子树的状态。当根节点的某标记位置 1 时，代表整棵树中至少存在一个匹配的物理页：

.. table:: Page Cache XArray 核心标记位图
   :widths: 25 20 55

   +==============================+==================+==================================================================+
   | 标记常量 (Mark Macro)        | XArray 物理槽位  | 核心语义与设计机制                                               |
   +==============================+==================+==================================================================+
   | **``PAGECACHE_TAG_DIRTY``**  | **``XA_MARK_0``**| **脏页标记**。表明该页已被写入修改但尚未持久化至物理磁盘         |
   +------------------------------+------------------+------------------------------------------------------------------+
   | **``PAGECACHE_TAG_WRITEBACK``| **``XA_MARK_1``**| **正在回写标记**。表明该页正在执行磁盘 DMA 写入，锁定禁止二次回写|
   +------------------------------+------------------+------------------------------------------------------------------+
   | **``PAGECACHE_TAG_TOWRITE``**| **``XA_MARK_2``**| **待回写快照标记**。在发起 sync 时快照当前脏页，防止活锁（Livelock）|
   +------------------------------+------------------+------------------------------------------------------------------+

**剪枝搜索优势**：当后台回写线程遍历脏页时，调用 ``xas_for_each_marked(&xas, folio, ULONG_MAX, PAGECACHE_TAG_DIRTY)``，算法直接顺着 ``XA_MARK_0`` 为 1 的树枝跳跃前进，完全跳过数百万个干净页所在的子树，扫描复杂度从 $O(N)$ 暴降为 $O(	ext{Dirty})$！

第三幕：读操作流水线——命中极速通道、预读算法 (Readahead) 与缺页中断
--------------------------------------------------------------------

当进程调用 ``read(fd, buf, count)`` 发起读请求时，控制流进入 ``mm/filemap.c:filemap_read()``。

3.1 读请求全生命周期流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           filemap_read() 核心执行流水线                           |
   |                                                                                   |
   |  [ 1. 进程发起系统调用 read() ]                                                   |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 2. 查询 XArray (filemap_get_pages) ] ──► (RCU 无锁极速检索)                   |
   |            │                                                                      |
   |            ├─► 【缓存命中 (Cache Hit)】                                           |
   |            │   - 检查 folio 是否处于 PageUptodate (数据最新);                     |
   |            │   - 调用 copy_page_to_iter() 将内核 Page Cache 零拷贝/快速拷贝至用户态; |
   |            │   - 标记 touch_atime() 刷新访问时间戳; ──► 【极速返回!】             |
   |            │                                                                      |
   |            └─► 【缓存未命中 (Cache Miss)】                                        |
   |                │                                                                  |
   |                ▼                                                                  |
   |  [ 3. 触发窗口自适应预读引擎 (page_cache_sync_ra) ]                              |
   |  - 计算预读窗口 (struct file_ra_state);                                           |
   |  - 向伙伴系统申请一组物理页 (alloc_pages);                                        |
   |  - 插入 XArray 并挂载至 LRU 活跃链表;                                             |
   |  - 调用 a_ops->readahead() 或 a_ops->read_folio() 构造 struct bio 派发块设备 DMA;  |
   |  - 进程进入不可中断睡眠 (TASK_UNINTERRUPTIBLE)，等待磁盘中断唤醒;                 |
   |  - I/O 完成后置位 PG_uptodate，唤醒进程拷贝数据 ──► 【返回用户空间】              |
   +-----------------------------------------------------------------------------------+

3.2 窗口自适应预读状态机（``struct file_ra_state``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
顺序读取大文件时，内核通过 **双窗口异步预读（Asynchronous Readahead）** 掩盖 I/O 延迟：
* **当前窗口（Current Window）**：包含正在被进程同步读取的物理页；
* **先行预读窗口（Ahead Window）**：在当前窗口尚未读完时，内核已在后台向磁盘异步预订了下一批连续物理页；
* **预读触发标记（Async Marker）**：内核将先行窗口的第一页打上标记。当进程读取推进到该标记页时，立即静默发起再下一批物理页的异步 DMA，实现“计算与 I/O 彻底流水线并行重叠”！

第四幕：写操作流水线与脏页标记——``write_begin`` / ``write_end`` 与写回防线
---------------------------------------------------------------------------

当进程执行 ``write(fd, buf, count)`` 时，内核遵循标准的 **两阶段提交协议（Two-Phase Commit Protocol）**。

4.1 带缓存写入两阶段执行流水线（``generic_perform_write``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                     generic_perform_write() 两阶段写入协议                        |
   |                                                                                   |
   |  [ 第一阶段: a_ops->write_begin() 预备事务 ]                                      |
   |  1. 根据 offset 计算目标页索引 index = pos >> PAGE_SHIFT;                         |
   |  2. 检索或在 XArray 中分配物理页 folio (若为部分写且页不在缓存中，从磁盘读入原内容); |
   |  3. 锁定 folio (folio_lock)，防止并发访问;                                        |
   |  4. 文件系统执行底层预分配 (如 ext4_da_write_begin 执行延迟块分配 Delayed Alloc); |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 核心搬运: copy_page_from_iter_atomic() ]                                       |
   |  - 禁用内核抢占/处理缺页，将用户空间 buf 数据拷贝至内核 Page Cache 物理页对应偏移处; |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 第二阶段: a_ops->write_end() 提交事务 ]                                        |
   |  1. 确认实际拷贝成功的字节数 copied;                                              |
   |  2. 更新 inode 逻辑大小: i_size = max(i_size, pos + copied);                     |
   |  3. 调用 folio_mark_dirty(folio):                                                 |
   |     ► 置位 folio 标志位 PG_dirty;                                                 |
   |     ► 沿 XArray 树自底向上置位 PAGECACHE_TAG_DIRTY (XA_MARK_0);                   |
   |     ► 调用 __mark_inode_dirty(inode, I_DIRTY_PAGES) 将 inode 挂入回写队列;        |
   |  4. 解锁 folio (folio_unlock);                                                    |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [ 脏页反压防御: balance_dirty_pages_ratelimited() ]                              |
   |  - 检查系统当前脏页总量是否越过警戒水位线 ──► 必要时强制进程休眠节流!             |
   +-----------------------------------------------------------------------------------+

4.2 脏页水位线防御体系与进程反压（Throttling）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了防止失控的写入进程疯狂消耗物理内存导致系统 OOM，内核设立了两道绝对防线：

::

   +-----------------------------------------------------------------------------------+
   |                             脏页内存水位线反压防御体系                            |
   |                                                                                   |
   |  [ 物理内存全满 (100%) ] ──────────────────────────────────────────────────────── |
   |         ▲                                                                         |
   |         │                                                                         |
   |         ├── dirty_ratio (默认约 20% RAM / dirty_bytes) ────────────────────────── |
   |         │   【硬限直接反压 Direct Throttling】                                    |
   |         │   - 写入进程被强制剥夺 CPU 陷入同步睡眠 (io_schedule);                  |
   |         │   - 进程自身必须停下来协助执行同步脏页刷盘，直到脏页比例降回安全线以下! |
   |         │                                                                         |
   |         ├── dirty_background_ratio (默认约 10% RAM / dirty_background_bytes) ──── |
   |         │   【软限后台刷盘 Background Flush】                                     |
   |         │   - 唤醒后台 flusher 工作线程 (wb_workfn) 展开异步后台回写;             |
   |         │   - 前台写入进程无需阻塞，继续全速写入 Page Cache;                      |
   |         │                                                                         |
   |         ▼                                                                         |
   |  [ 干净物理内存 (0%) ]                                                            |
   +-----------------------------------------------------------------------------------+

第五幕：异步回写引擎 (Flusher Threads) 与回写控制状态机
-------------------------------------------------------

脏页在内存中驻留不仅面临断电丢失风险，且最终必须持久化到非易失性介质上。负责这一宏伟工程的是 **BDI 回写子系统（Backing Device Info Writeback / ``fs/fs-writeback.c``）**。

5.1 ``bdi_writeback`` 三级队列调度拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每个存储块设备（如 ``/dev/nvme0n1``）维护着专属的 ``struct bdi_writeback``（简称 ``wb``），其内部运行着三级 Inode 流转状态机：

::

   +-----------------------------------------------------------------------------------+
   |                         bdi_writeback 三级 Inode 回写流转状态机                   |
   |                                                                                   |
   |  [ 脏 Inode 生成 (mark_inode_dirty) ]                                             |
   |            │                                                                      |
   |            ▼ 按 dirtied_when 升序排列                                             |
   |  [ wb->b_dirty 队列 ] ◄─── (暂存最新被修改的 Inodes)                             |
   |            │                                                                      |
   |            ▼ (达到 dirty_expire_interval 30秒 或 触发 sync)                        |
   |  [ wb->b_io 派遣队列 ] ◄─── (按产生时间先后批量弹出的待回写批次)                  |
   |            │                                                                      |
   |            ▼ 调用 __writeback_single_inode() -> a_ops->writepages()               |
   |  [ 执行物理刷盘 ]                                                                 |
   |            │                                                                      |
   |            ├─► 【回写完全成功且干净】 ──► 移出回写队列，挂入 wb->b_attached       |
   |            ├─► 【未写完或部分阻塞】   ──► 暂存到 wb->b_more_io 队列               |
   |            └─► 【回写期间被再次写脏】 ──► 重新推回 wb->b_dirty 尾部               |
   +-----------------------------------------------------------------------------------+

5.2 物理页回写原子状态跃迁（Folio Writeback State Transition）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当执行具体的页刷盘时，每个 ``struct folio`` 经历严密的物理状态跃迁：
1. **``folio_start_writeback(folio)``**：
   * 清除 ``PG_dirty`` 标志位；
   * 在 XArray 中清除 ``PAGECACHE_TAG_DIRTY``，同时原子置位 **``PAGECACHE_TAG_WRITEBACK``（``XA_MARK_1``）**；
   * 增加设备与全局 ``NR_WRITEBACK`` 统计计数器；
2. **块层 I/O 派发**：
   * 将 Folio 包装进 ``struct bio``，向底层通用块层（blk-mq）提交异步 DMA 写入传输；
3. **硬件 DMA 中断完成回调**：
   * 硬盘控制器发出中断信号，驱动调用 **``folio_end_writeback(folio)``**；
   * 清除 ``PAGECACHE_TAG_WRITEBACK`` 标记；
   * 触发 ``wake_up_page(&folio->page, PG_writeback)``，唤醒所有在 ``sync`` / ``fsync`` / ``wait_on_page_writeback()`` 上等待该页刷盘完成的阻塞线程！

5.3 Cgroup 写入者外来 Inode 仲裁（Boyer-Moore 多数票算法）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在容器化（Docker / Kubernetes）多租户场景下，若多个 Cgroup 并发向同一个共享文件写入数据，内核如何判定该 Inode 的回写 I/O 带宽应归属于哪个 Cgroup？
* **Boyer-Moore 多数票裁决机制**：内核在 ``wbc_detach_inode()`` 中统计各 Cgroup 写入的字节数；
* 当检测到外来 Cgroup 连续在 2 秒历史窗口内占据了超过 50% 的 I/O 份额时，触发 ``inode_switch_wbs()``，将 Inode 动态平滑迁移至新的 Cgroup 回写实体，实现精准的 cgroup v2 I/O 限速（I/O Throttling）与资源隔离！

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 页缓存机制的微观世界：``address_space`` 核心映射拓扑、XArray 多叉树结构与三色标记位图（``PAGECACHE_TAG_DIRTY / WRITEBACK / TOWRITE``）、读流水线与双窗口异步预读状态机、带缓存写入两阶段协议与脏页水位反压限流，以及 BDI 回写引擎三级 Inode 队列流转、物理页回写状态跃迁与 Cgroup 归属仲裁。

当 Page Cache 的脏页被决定推向磁盘，或者进程发起 Direct I/O 时，所有的内存页请求最终都被打包成同一个核心物理数据载体——**``struct bio``**，并注入到 Linux 内核最宏伟的高并发硬件分发中枢——**通用块层（Generic Block Layer）**。

在 **第 5 节：通用块层与 ``struct bio`` 结构流转：多队列架构 (blk-mq) 软件暂存队列与硬件派发队列** 中，我们将深入解构 ``struct bio`` 物理向量内存布局、请求合并（Bio Merging）算法、现代多队列架构（blk-mq）软件暂存队列（Software Staging Queue）与硬件派发队列（Hardware Dispatch Queue）的纳秒级无锁派发时序。

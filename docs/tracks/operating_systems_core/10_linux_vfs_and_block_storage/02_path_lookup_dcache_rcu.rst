第一幕：路径解析的性能风暴与 Dcache 散列表拓扑
----------------------------------------------

在现代多核服务器与高并发云原生场景中，路径解析（Path Lookup）是操作系统调用最为频繁的代码路径之一（单机每秒可达数百万次 ``stat`` / ``open`` / ``access`` 调用）。

1.1 磁盘遍历与引用计数的锁风暴
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
如果在解析路径 ``/usr/share/nginx/html/index.html`` 时，内核每次都从磁盘读取目录数据块，系统 I/O 延迟将达毫秒级；而如果在内存树中遍历时为每个节点频繁执行 ``dget()`` / ``dput()`` 原子加减，多核 CPU 之间将产生极其惨烈的 **L3 缓存行颠簸（Cacheline Bouncing）**，导致多核吞吐断崖式下跌。

1.2 全局 Dcache 散列表拓扑（``fs/dcache.c:dentry_hashtable``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了实现 $O(1)$ 的内存目录项检索，Linux 内核维护了一个庞大的全局哈希表：

::

   +-----------------------------------------------------------------------------------+
   |                        Dcache 全局散列表 (dentry_hashtable) 拓扑                  |
   |                                                                                   |
   |  Bucket Index = hash_32(parent_dentry ^ name_hash, d_hash_shift)                  |
   |                                                                                   |
   |  dentry_hashtable                                                                 |
   |  [ Bucket 0 ] ──► [ struct hlist_bl_node ] ──► [ struct hlist_bl_node ] ──► NULL  |
   |  [ Bucket 1 ] ──► NULL                                                            |
   |  [ Bucket 2 ] ──► [ struct hlist_bl_node ] ──► NULL                               |
   |  ...                                                                              |
   |  [ Bucket N ] ──► [ struct hlist_bl_node ] ──► [ struct hlist_bl_node ] ──► NULL  |
   +-----------------------------------------------------------------------------------+

* **位锁链表头（``struct hlist_bl_head``）**：哈希表的每个桶利用链表头指针的最低有效位（Bit 0）充当自旋锁，既省去了独立的锁变量内存，又支持细粒度桶并发；
* **双因子复合哈希**：哈希键由 **父目录 Dentry 指针地址（``parent``）** 与 **子文件名哈希值（``name_hash``）** 深度异或混合而成，彻底消除不同目录下同名文件的哈希碰撞。

1.3 ``WORD_AT_A_TIME`` 64 位单指令字符串哈希加速
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位 x86_64 体系下，Linux 内核不使用传统的逐字节循环哈希，而是采用 **``WORD_AT_A_TIME``** 寄存器并行技术（``fs/namei.c:hash_name``）：
* 一次从内存加载 8 字节（64 位宽字：``load_unaligned_zeropad``）；
* 使用纯位运算指令在单周期内同时探测 8 个字节中是否存在 ``/`` 分隔符或 ``\0`` 终止符；
* 利用黄金分割比乘法常数（``GOLDEN_RATIO_64``）与循环移位（``rol64``）将 8 字节数据混合进 64 位哈希累加器中；
* 字符串哈希与长度计算性能相比传统逐字节扫描提升 **800%**！

第二幕：路径解析总控引擎——``struct nameidata`` 与状态机初始化
--------------------------------------------------------------

路径查找的核心控制中枢是局部结构体 **``struct nameidata``**（位于内核栈上，完全无需堆内存分配）。

2.1 ``struct nameidata`` 上下文状态机（``fs/namei.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                        struct nameidata 路径解析上下文结构                        |
   |                                                                                   |
   |  struct nameidata {                                                               |
   |      struct path             path;           /* 当前已解析推进到的 (vfsmount, dentry) */|
   |      struct qstr             last;           /* 当前正在解析的单个路径分量名称与哈希*/|
   |      struct path             root;           /* 当前进程的全局根目录 (用于绝对路径) */|
   |      struct inode            *inode;         /* 当前路径节点的 dentry->d_inode 缓存 */|
   |      unsigned int            flags;          /* 查找标志位 (LOOKUP_RCU, LOOKUP_FOLLOW)*/|
   |      unsigned int            seq, next_seq;  /* 当前 Dentry 与下一 Dentry 的顺序锁序号*/|
   |      unsigned int            m_seq, r_seq;   /* mount_lock 与 rename_lock 顺序锁快照*/|
   |      int                     total_link_count; /* 符号链接递归遍历累计计数器 */    |
   |      struct saved            *stack;         /* 符号链接多层嵌套回溯栈 */         |
   |      struct filename         *name;          /* 用户态拷贝至内核态的原始路径名 */ |
   |      int                     dfd;            /* 起始目录文件描述符 (AT_FDCWD / dirfd)*/
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

2.2 ``path_init()`` 启动状态机时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当系统调用触发 ``filename_lookup() -> path_lookupat()`` 时：
1. **默认开启 RCU-walk**：设置 ``nd->flags |= LOOKUP_RCU``，调用 ``rcu_read_lock()`` 进入无锁读临界区；
2. **捕获全局拓扑快照**：读取挂载表顺序锁 ``mount_lock.seqcount`` 与重命名顺序锁 ``rename_lock.seqcount`` 的初始序列号（``nd->m_seq``, ``nd->r_seq``）；
3. **定位起始基准锚点**：
   * **绝对路径（以 ``/`` 开头）**：调用 ``nd_jump_root()``，将起始点锚定在当前进程根目录 ``current->fs->root``；
   * **相对路径且 ``dfd == AT_FDCWD``**：将起始点锚定在当前工作目录 ``current->fs->pwd``；
   * **相对路径且 ``dfd >= 0``**：从打开的文件描述符中提取 ``file->f_path`` 作为起始点。

第三幕：RCU-walk 无锁并发路径遍历流水线
----------------------------------------

RCU-walk 是 Linux VFS 路径查找皇冠上的明珠。其核心哲学是：**在整条路径解析过程中，不增加任何引用计数，不获取任何自旋锁或信号量，零写操作访问共享数据结构！**

::

   +-----------------------------------------------------------------------------------+
   |                         RCU-walk 无锁并发逐级推进流水线                           |
   |                                                                                   |
   |  [进入 link_path_walk() 分量循环]                                                 |
   |  1. may_lookup(): lookup_inode_permission_may_exec() 极速判定当前目录 MAY_EXEC 权限;  |
   |  2. hash_name(): 64 位单指令计算分量名称哈希与长度;                               |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [lookup_fast(): Dcache 快速通道]                                                 |
   |  - 调用 __d_lookup_rcu(parent, &nd->last, &nd->next_seq);                         |
   |  - 深入 dentry_hashtable 匹配 parent + hash，获取子 dentry 指针与 dentry->d_seq;    |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [父节点一致性自校验]                                                             |
   |  - 执行 read_seqcount_retry(&parent->d_seq, nd->seq);                             |
   |  - 若父节点在子节点查找期间被重命名或删除 ──► 立即触发 try_to_unlazy() 升格重试!   |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [step_into(): 步入下一级路径节点]                                                |
   |  - 检查子节点 dentry->d_seq: read_seqcount_retry(&dentry->d_seq, nd->next_seq);    |
   |  - 更新当前路径: nd->path.dentry = dentry; nd->inode = dentry->d_inode;           |
   |  - 传递序列号: nd->seq = nd->next_seq;                                            |
   |  - 循环推进至下一个路径分量!                                                      |
   +-----------------------------------------------------------------------------------+

3.1 顺序锁（Seqlock / ``seqcount_spinlock_t``）防御模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 RCU-walk 期间，写操作（如 ``rename``, ``unlink``）可能正在并发修改 Dentry 树。
* **写端**：在修改 Dentry 前后，执行 ``write_seqcount_begin(&dentry->d_seq)`` 与 ``write_seqcount_end()``，将序号由偶数变成奇数再变回偶数；
* **读端（RCU-walk）**：在读取子 Dentry 前采样序号，读取完毕后调用 ``read_seqcount_retry()``。如果序号变为奇数或与采样值不一致，代表读期间发生了并发修改，读端立即察觉并放弃当前无效数据！

第四幕：特殊路径节点穿越——挂载点、符号链接与 ``..`` 父目录回溯
---------------------------------------------------------------

路径遍历过程中会遭遇三种打破线性逻辑的复杂场景：

4.1 跨挂载点无锁穿越（``fs/namei.c:__follow_mount_rcu``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当遇到一个挂载点目录（如根分区下的 ``/mnt``，其上挂载了独立的 ext4 分区）：
1. 检查目录标志位 ``dentry->d_flags & DCACHE_MOUNTED``；
2. 在 RCU 保护下深入挂载散列表调用 ``__lookup_mnt(nd->path.mnt, dentry)``；
3. 将 ``nd->path.mnt`` 切换为子挂载点实例，并将 ``nd->path.dentry`` 瞬时切换至子文件系统的根目录 ``mounted->mnt.mnt_root``；
4. 采样新根节点的 ``d_seq`` 并校验 ``mount_lock`` 全局序列号，确保挂载树未发生并发卸载。

4.2 符号软链接（Symlink）跳转（``pick_link``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当遇到软链接文件时：
* **嵌套栈保护**：将当前解析进度压入 ``nd->stack[nd->depth++]`` 数组；
* **递归深度防御**：若累计解析符号链接次数超过 **``MAXSYMLINKS (40)``**，立即返回 ``-ELOOP`` 错误，彻底粉碎死循环软链接对内核栈的攻击；
* **获取目标串**：读取 ``inode->i_link`` 获取指向的目标路径字符串，将其重新喂入 ``link_path_walk()`` 进行递归遍历。

4.3 ``..`` 父目录安全回溯（``follow_dotdot_rcu``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
处理 ``..`` 返回上一级目录是 VFS 中最危险的操作之一（容易发生越权逃逸）：
* 若当前 Dentry 恰好是子文件系统的根目录（``mnt->mnt_root``），调用 ``choose_mountpoint_rcu`` 向上穿越回宿主挂载点的挂载目录；
* 读取 ``dentry->d_parent`` 获取父目录指针；
* 调用 ``path_connected()`` 执行拓扑连通性校验，严防并发 ``rename`` 将正在遍历的目录移出根命名空间导致沙箱逃逸！

第五幕：从 RCU-walk 优雅降级与升格——``try_to_unlazy()`` 与 ``complete_walk()``
--------------------------------------------------------------------------------

虽然 RCU-walk 性能极其卓越，但它无法处理需要睡眠阻塞的场景：
1. **Dcache 未命中（Cache Miss）**：内存中没有该 Dentry，必须从物理磁盘下发 I/O 读取目录项（``lookup_slow``）；
2. **复杂安全与 ACL 判定**：遇到需要睡眠查询安全模块或网络鉴权的 Inode；
3. **并发写冲突**：顺序锁校验失败（``read_seqcount_retry()`` 返回 true）。

5.1 ``try_to_unlazy()`` 原位原子升格机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当 RCU-walk 遇到阻碍时，内核绝不会粗暴地从根目录重新开始，而是调用 **``try_to_unlazy(nd)``** 将当前行进到的节点 **原位升格为带引用计数的 Ref-walk 模式**：

::

   +-----------------------------------------------------------------------------------+
   |                       try_to_unlazy() 原位原子升格流水线                          |
   |                                                                                   |
   |  1. 对当前节点执行无锁引用计数提升:                                                |
   |     lockref_get_not_dead(&nd->path.dentry->d_lockref);                            |
   |                                                                                   |
   |  2. 再次执行顺序锁校验:                                                           |
   |     if (read_seqcount_retry(&dentry->d_seq, nd->seq))                             |
   |         goto fail; /* 升格失败，彻底退出 RCU 模式并重新从头 Ref-walk */           |
   |                                                                                   |
   |  3. 对当前路径的 vfsmount 和根目录获取引用计数 (mntget, path_get);                |
   |                                                                                   |
   |  4. 调用 rcu_read_unlock() 退出 RCU 模式，切换为 Ref-walk 模式，从当前节点继续推进! |
   +-----------------------------------------------------------------------------------+

5.2 ``complete_walk()`` 终点完工交割
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当路径顺利解析到最后一个目标分量且系统依然处于 RCU-walk 模式时：
1. 调用 ``try_to_unlazy(nd)`` 将最终目标 Dentry 与 vfsmount 转换为正式持有强引用计数的 ``struct path``；
2. 退出 RCU 临界区；
3. 路径解析圆满落幕，向调用方（如 ``do_open()``, ``vfs_stat()``）返回最终的 ``struct path`` 结构体实体！

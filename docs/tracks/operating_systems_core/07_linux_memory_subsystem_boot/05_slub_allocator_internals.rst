第 5 节：SLUB 细粒度对象分配器：kmem_cache 拓扑、cpu_slab 无锁快速路径与 node_slab 慢速路径
========================================================================================

.. note::
   **前置背景与上下文承接**
   * **体系结构基准**：承接模块 07 第 4 节中关于分区伙伴系统（Buddy System）的 64 字节 ``struct page`` 拓扑、Zone 内存区域划分与 Order 0~10 物理页块分配。
   * **核心使命**：解构建立在伙伴系统之上的小内存对象分配之王——**SLUB 细粒度对象分配器（``mm/slub.c``）**；深入剖析高速缓存描述符 ``struct kmem_cache``、Per-CPU 本地缓存 ``struct kmem_cache_cpu`` 与 NUMA 节点缓存 ``struct kmem_cache_node`` 的三层拓扑；逐行推导基于事务 ID（``TID``）与 ``this_cpu_cmpxchg_double`` 双字原子比较交换的 **无锁快速路径（Lockless Fast Path）**；深度解构 ``c->partial`` 本地部分满链表、``n->partial`` 节点自旋锁慢速路径、``allocate_slab()`` 向上级伙伴系统申请物理页与空闲单向链表格式化（``setup_object``）；解构对象释放流水线、冻结标志（``frozen``）防止跨核锁竞争，以及空闲 Slab 自动向伙伴系统归还物理页的内存收缩机制。

----------------------------------------------------------------------------------------

第一幕：小内存对象的分配困境与 SLUB 的诞生哲学
----------------------------------------------

分区伙伴系统以 4KB 物理页为最小分配粒度。然而，操作系统内核内部充斥着海量小粒度数据结构：
* 一个进程描述符 ``struct task_struct`` 约数千字节；
* 一个文件节点 ``struct inode`` 约 600 字节；
* 一个目录项缓存 ``struct dentry`` 约 192 字节；
* 一个内核链表节点往往仅有数十字节。

1.1 内部碎片危机与 Slab 架构演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
若每次申请 32 字节结构体都直接向伙伴系统索要一个 4KB 物理页，系统将产生高达 **$99.2\%$ 的内部内存碎片**（Internal Fragmentation）！为此，Linux 引入了基于对象池复用理念的 Slab 系列分配器：

::

   +-----------------------------------------------------------------------------------+
   |                           Linux Slab 系列分配器演进史                             |
   |                                                                                   |
   |  [经典 SLAB 分配器 (1990s)]                                                       |
   |  - 特性: 维护庞大的外置队列 (Array Cache / Slab List) 与硬件着色 (Cache Coloring)  |
   |  - 痛点: 在大规模多核与海量 NUMA 节点下，元数据开销急剧膨胀，队列锁竞争严重       |
   |                                                                                   |
   |  [SLOB 分配器 (Simple List Of Blocks)]                                            |
   |  - 特性: 专为嵌入式小内存设备设计，基于 First-Fit 算法在单页内切片                |
   |  - 痛点: 缺乏多核扩展性与并发保护                                                 |
   |                                                                                   |
   |  [SLUB 分配器 (现代 Linux 默认标准)]                                              |
   |  - 架构飞跃: 彻底抛弃复杂外置队列，元数据直接下沉嵌入 struct slab / struct page    |
   |  - 性能王炸: 引入 Per-CPU 无锁 CAS (Compare-And-Swap) 极速通道，5~10 时钟周期直达! |
   +-----------------------------------------------------------------------------------+

1.2 通用高速缓存与专用高速缓存矩阵
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
SLUB 管理的缓存分为两大阵营：
1. **专用缓存（Custom Caches）**：为特定内核对象量身定制（如 ``"task_struct"``, ``"mm_struct"``, ``"dentry"``, ``"inode_cache"``），对象大小恒定，初始化时带构造函数；
2. **通用缓存（Generic kmalloc Caches）**：为 ``kmalloc(size)`` 服务的 2 的幂次方大小数组（``kmalloc-8, 16, 32, 64, 128, ..., 8192``）。

第二幕：三层拓扑架构——``kmem_cache``、``cpu_slab`` 与 ``node_slab``
-------------------------------------------------------------------

SLUB 分配器构建了极致优化的三层物理与逻辑拓扑体系：

::

   +-----------------------------------------------------------------------------------+
   |                          SLUB 分配器三层核心拓扑全景                              |
   |                                                                                   |
   |  [顶层总控: struct kmem_cache]                                                    |
   |  ├── size (对齐后对象物理跨度) / object_size (纯有效载荷)                         |
   |  ├── offset (对象内空闲指针 freepointer 偏移量)                                   |
   |  └── oo (kmem_cache_order_objects: 最佳物理页阶数 Order 与对象容纳量)             |
   |            │                                                                      |
   |            ├──────────────────────────────────────────┐                           |
   |            ▼                                          ▼                           |
   |  [L1 层: Per-CPU 本地极速通道]              [L2 层: NUMA 节点级共享池]             |
   |  struct kmem_cache_cpu {                    struct kmem_cache_node {              |
   |      void **freelist; ──► 当前活跃对象链        spinlock_t list_lock;             |
   |      unsigned long tid;──► 事务 ID             struct list_head partial;         |
   |      struct slab *slab;──► 当前活跃 Slab       unsigned long nr_partial;         |
   |      struct slab *partial; ──► 本地部分满链表  struct list_head full;            |
   |  } (每个 CPU 核心各一份, 零锁争用!)         } (每个 NUMA 节点各一份, 粗粒度锁)     |
   +-----------------------------------------------------------------------------------+

2.1 ``struct slab`` 物理页元数据多态复用
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Linux 7.2 中，每个 Slab 物理页（由伙伴系统分配的 1 页或多页连续内存）通过结构体 ``struct slab`` 进行状态跟踪：
* **``void *freelist``**：指向该 Slab 内第一个空闲对象的虚拟内存地址；
* **``unsigned inuse:16``**：记录当前 Slab 中已分配出去的对象数量；
* **``unsigned objects:15``**：该 Slab 所能容纳的总对象容量；
* **``unsigned frozen:1``**：**冻结标志位**。当该 Slab 被挂载到某 CPU 的 ``cpu_slab`` 或 ``cpu_partial`` 上时，``frozen`` 置 1。此时其他 CPU 只能向其归还对象，禁止从该 Slab 偷取对象，彻底隔绝多核竞争！

第三幕：纳秒级无锁分配——``this_cpu_cmpxchg_double`` 快速路径
-------------------------------------------------------------

当进程在内核态调用 ``kmem_cache_alloc(s, gfp)`` 时，SLUB 首先尝试进入极致优化的 **无锁快速路径（Lockless Fast Path）**。

3.1 事务 ID（``TID``）与 ABA 竞态终结
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在单核或抢占环境下，如果一个线程在读取 ``c->freelist`` 后被中断抢占，其他线程执行了分配与释放，可能导致 ``freelist`` 指针值未变但内部链表已彻底改变（经典的 ABA 内存破坏问题）。
* **破解之道**：内核在每个 CPU 维护一个 64 位单调递增的事务 ID（``TID``）。每次发生任何分配、释放或 Slab 切换时，``TID`` 强制自增！

3.2 快速路径汇编级流水线（``mm/slub.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       SLUB 无锁快速路径原子状态机                                 |
   |                                                                                   |
   |  struct kmem_cache_cpu *c = raw_cpu_ptr(s->cpu_slab);                             |
   |                                                                                   |
   |  /* 1. 原子读取当前 CPU 的 freelist 首对象指针与事务 ID */                        |
   |  void *object = c->freelist;                                                      |
   |  unsigned long tid = c->tid;                                                      |
   |                                                                                   |
   |  if (likely(object && c->slab)) {                                                 |
   |      /* 2. 从当前对象内部读取其内嵌的下一个空闲对象指针 next_object */            |
   |      void *next_object = get_freepointer(s, object);                              |
   |                                                                                   |
   |      /* 3. 执行 128 位双字原子比较并交换指令 (this_cpu_cmpxchg_double) */         |
   |      if (likely(this_cpu_cmpxchg_double(                                         |
   |              s->cpu_slab->freelist, s->cpu_slab->tid,                             |
   |              object, tid,                                                         |
   |              next_object, next_tid(tid)))) {                                      |
   |          return object; /* 命中！单条原子指令，零锁竞争，5~10 个时钟周期直接返回! */|
   |      }                                                                            |
   |  }                                                                                |
   |  /* CAS 失败或 freelist 为空，落入慢速路径 */                                     |
   +-----------------------------------------------------------------------------------+

第四幕：多级分层慢速分配时序——从 ``cpu_partial`` 到伙伴系统
------------------------------------------------------------

当当前活跃 Slab 的 ``c->freelist`` 耗尽（变成 NULL）时，分配器调用 **``__slab_alloc() -> new_slab_objects()``** 启动分层解冻与填充：

::

   +-----------------------------------------------------------------------------------+
   |                          SLUB 慢速路径逐级升级流水线                              |
   |                                                                                   |
   |  [L1 级: 活跃 Slab 内部探测]                                                      |
   |  - 检查当前 c->slab->freelist 是否在并发释放中重新产生了空闲对象;                 |
   |  - 若有，解冻并重载至 c->freelist ──► 成功返回                                    |
   |            │                                                                      |
   |            ▼ (活跃 Slab 完全耗尽)                                                 |
   |  [L2 级: 本地 Per-CPU Partial 链表获取]                                           |
   |  - 检查 c->partial 链表是否有可用 Slab;                                           |
   |  - 若有，弹出一个 Slab 提升为新的活跃 c->slab，重载 c->freelist ──► 成功返回       |
   |            │                                                                      |
   |            ▼ (本地 Partial 链表耗尽)                                              |
   |  [L3 级: NUMA 节点 Partial 链表获取]                                              |
   |  - 获取 node->list_lock 自旋锁;                                                   |
   |  - 从 node->partial 批量转移若干 Slab 填充本地 c->partial，并激活一个 ──► 成功返回|
   |            │                                                                      |
   |            ▼ (NUMA 节点 Partial 链表亦全空)                                       |
   |  [L4 级: 向上级伙伴系统申请全新物理页]                                            |
   |  - 调用 allocate_slab(s, flags, node) ──► 调用 alloc_pages(s->oo.order);          |
   |  - 调用 setup_object() 将物理页切片并用 freepointer 串联为单向链表;               |
   |  - 标记 slab->frozen = 1，挂载为当前活跃 c->slab ──► 成功返回                     |
   +-----------------------------------------------------------------------------------+

第五幕：对象释放与 Slab 生命周期闭环
------------------------------------

内存释放函数 ``kmem_cache_free(s, object)`` 同样具备极致的对称性能。

5.1 释放快速路径
~~~~~~~~~~~~~~~~
若被释放的 ``object`` 归属于当前 CPU 当前活跃的 ``c->slab``：
1. 将当前对象的 freepointer 指向现有的 ``c->freelist``；
2. 执行 ``this_cpu_cmpxchg_double`` 将 ``c->freelist`` 原子重置为当前对象；
3. 过程完全无锁，瞬间完成对象归还。

5.2 释放慢速路径与物理内存收缩（``__slab_free``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
若被释放的对象属于非活跃 Slab 或由其他 CPU 释放：
1. 递减该 Slab 的 ``slab->inuse`` 活跃计数；
2. **从全满变为部分满**：若此前该 Slab 为全满状态，将其重新挂入对应 NUMA 节点的 ``node->partial`` 链表；
3. **全空 Slab 物理页销毁**：若 ``slab->inuse == 0``（Slab 中所有对象均已归还空闲），且节点 Partial 链表中的空闲 Slab 数量超过阈值（``nr_partial > s->min_partial``）：
   * 将该 Slab 彻底从 partial 链表中摘除；
   * 调用 **``__free_pages(page, order)``**，将整个 Slab 占用的全部物理页**完整退还给伙伴系统**！

这一机制确保了小内存对象在瞬时波峰退去后，物理内存能迅速回流到伙伴系统中，防止操作系统长期驻留无用的内存气泡。

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 SLUB 细粒度对象分配器的架构设计：三层拓扑模型（``kmem_cache`` / ``cpu_slab`` / ``node_slab``）、基于事务 ID（``TID``）与 ``this_cpu_cmpxchg_double`` 的单指令无锁快速路径、四级慢速分配状态机、对象单向链表切片格式化，以及 Slab 冻结与全空物理页向伙伴系统的收缩归还。

至此，伙伴系统（页级分配）与 SLUB（对象级分配）共同构筑了内核物理内存管理的坚实底座。然而，内核中还存在一类特殊的内存需求——申请虚拟地址连续、但物理地址可以不连续的大块内存（如加载内核模块、超大驱动缓冲区），以及对固定外设物理地址的直接映射。

在 **第 6 节：``vmalloc`` 虚拟地址连续空间管理、Fixmap 固定映射与临时内核映射 (kmap)** 中，我们将深入解构 ``vmalloc`` 红黑树与区间树分配算法、动态建立非连续页表映射、Fixmap 编译期固定虚拟槽位，以及内核高位内存映射的物理时序。

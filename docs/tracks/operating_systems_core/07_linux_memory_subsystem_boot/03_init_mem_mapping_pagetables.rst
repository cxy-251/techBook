第一幕：直接物理内存映射区 (Direct Mapping) 的物理哲学与宏伟蓝图
----------------------------------------------------------------

在 64 位 x86_64 体系下，Linux 内核设计了一项极其壮丽的虚拟内存工程——**全物理内存直接映射（Direct Physical Memory Mapping）**。

1.1 什么是 ``PAGE_OFFSET`` 直接映射？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
内核将系统中的所有物理内存 RAM $[0, 	ext{Max\_Phys}]$，以 $1:1$ 连续线性平移的方式，永久映射到 64 位内核虚拟地址空间的基准线 **``PAGE_OFFSET``** 之上：

$$	ext{Virtual\_Address} = 	ext{Physical\_Address} + \mathbf{PAGE\_OFFSET}$$

::

   +-----------------------------------------------------------------------------------+
   |                       直接物理映射区 (PAGE_OFFSET) 拓扑结构                       |
   |                                                                                   |
   |  [物理内存空间 (Physical RAM)]         [内核虚拟直接映射区 (Virtual Direct Map)] |
   |                                                                                   |
   |  0x0000000000000000 (0 MB)  ─────────► 0xFFFF888000000000 (PAGE_OFFSET 基地址)    |
   |  0x0000000000100000 (1 MB)  ─────────► 0xFFFF888000100000                        |
   |  0x0000000040000000 (1 GB)  ─────────► 0xFFFF888040000000                        |
   |  0x0000001000000000 (64 GB) ─────────► 0xFFFF889000000000                        |
   |  ...                                   ...                                        |
   |  Max_Physical_RAM           ─────────► 0xFFFF888000000000 + Max_Physical_RAM      |
   +-----------------------------------------------------------------------------------+

.. table:: 4 级分页 vs 5 级分页直接映射区参数对比
   :widths: 25 35 40

   +----------------------+----------------------------+--------------------------------------------+
   | 分页体系             | ``PAGE_OFFSET`` 虚拟基地址 | 最大直接物理映射寻址容量                   |
   +======================+============================+============================================+
   | **4 级分页 (48-bit)**| ``0xFFFF888000000000``     | **64 TB** 物理内存直接线性映射             |
   +----------------------+----------------------------+--------------------------------------------+
   | **5 级分页 (57-bit)**| ``0xFF10000000000000``     | **32 PB** (32768 TB) 物理内存直接线性映射  |
   +----------------------+----------------------------+--------------------------------------------+

1.2 为什么必须建立全物理内存直接映射？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **$O(1)$ 极速虚实地址转换**：内核访问任意物理页时，无需繁琐地动态修改页表或调用 ``ioremap()``，只需通过两条纳秒级算术宏即可双向转换：
   $$	ext{__va}(phys) = (void *)((unsigned\ long)(phys) + 	ext{page\_offset\_base})$$
   $$	ext{__pa}(virt) = (phys\_addr\_t)((unsigned\ long)(virt) - 	ext{page\_offset\_base})$$
2. **核心内存子系统的供血底座**：伙伴系统分配的物理页、SLUB 分配的内核小对象（如 ``struct task_struct``, ``struct inode``）在内核态均通过直接映射区虚拟地址进行高速读写。

第二幕：1GB/2MB 大页加速与自适应拆分算法（``split_mem_range``）
---------------------------------------------------------------

如果为数十 GB 乃至数 TB 的物理内存全部使用传统的 4KB 小页进行映射，将产生两项灾难性的开销：
1. **页表内存自身膨胀**：映射 1TB 物理内存需要 $2.6 	imes 10^8$ 个 PTE 表项，仅页表本身就消耗 **2GB 物理内存**；
2. **TLB 严重颠簸（TLB Thrashing）**：CPU 的 L1/L2 TLB 缓存仅有数百到数千项，频繁的 4KB 页表遍历将导致系统性能下降 15%~30%。

2.1 巨页（Huge Pages）对 TLB 的降维打击
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **1GB 巨页（Page Map Level 3 / PUD）**：一个 PUD 表项直接映射 1GB 连续物理内存，仅需 1 个 TLB 项即可覆盖 1GB 空间！映射 1TB 内存仅需 1024 个表项（**页表仅占 8KB**）；
* **2MB 大页（Page Map Level 2 / PMD）**：一个 PMD 表项直接映射 2MB 连续物理内存，映射 1TB 内存仅需 $5.2 	imes 10^5$ 个表项（**页表仅占 4MB**）。

2.2 物理区间自适应拆分状态机（``arch/x86/mm/init.c:split_mem_range()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了在非规整的物理内存（含散碎对齐与内存空洞）上最大化使用 1GB 和 2MB 巨页，内核运行 **自适应五段式拆分算法**：

::

   +-----------------------------------------------------------------------------------+
   |                        split_mem_range() 五段式物理拆分模型                       |
   |                                                                                   |
   |  [物理内存区间: Start ───────────────────────────────────────────────────────► End]|
   |                                                                                   |
   |  ┌──────────┬──────────────┬───────────────────────────┬──────────────┬─────────┐ |
   |  │ 4KB 头部 │  2MB 头部    │       1GB 巨页核心主体    │  2MB 尾部    │4KB 尾部 │ |
   |  │ (散碎页) │  (未对齐 1G) │  (1GB 对齐且长度为 1G 倍数)│ (未对齐 1G)  │(散碎页) │ |
   |  └──────────┴──────────────┴───────────────────────────┴──────────────┴─────────┘ |
   |       │            │                     │                    │            │      |
   |       ▼            ▼                     ▼                    ▼            ▼      |
   |    PTE 映射     PMD (PS=1)           PUD (PS=1)           PMD (PS=1)    PTE 映射  |
   +-----------------------------------------------------------------------------------+

算法自动探测 CPUID 中的 ``X86_FEATURE_GBPAGES``（1GB 巨页支持）与 ``X86_FEATURE_PSE``（2MB 大页支持），将中间大跨度连续物理 RAM 尽可能用 1GB 巨页覆盖，两侧按 2MB 与 4KB 递减对齐。

第三幕：五级页表自顶向下动态装配与 ``alloc_low_pages()`` 供血
-------------------------------------------------------------

在 ``arch/x86/mm/init_64.c:__kernel_physical_mapping_init()`` 中，内核从顶级页表开始自顶向下递归装配直接映射树：

::

   +-----------------------------------------------------------------------------------+
   |                     __kernel_physical_mapping_init() 装配流水线                   |
   |                                                                                   |
   |  [遍历 PGD (Level 5 / Level 4 顶层目录)]                                          |
   |  - pgd = pgd_offset_k(vaddr);                                                     |
   |  - 若 pgd 为空，调用 alloc_low_page() 分配一页 P4D/PUD 表并写入 pgd_populate;     |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [phys_p4d_init() 遍历 P4D 目录 (5 级分页专属)]                                   |
   |  - 若 p4d 为空，调用 alloc_low_page() 分配一页 PUD 表并写入 p4d_populate;         |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [phys_pud_init() 遍历 PUD 目录 (Level 3)]                                        |
   |  - 判断: 若当前地址 1GB 对齐且支持 1GB 巨页 (page_size_mask & PG_LEVEL_1G):         |
   |    ► 直接写入 set_pud_init(pud, pfn_pud(paddr, prot_sethuge(prot)));             |
   |    ► 表项中 Bit 7 (_PAGE_PSE) 置 1 ──► 硬件完成 1GB 巨页直连，跳过下级页表!       |
   |  - 否则: alloc_low_page() 分配 PMD 表，调用 pud_populate;                         |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [phys_pmd_init() 遍历 PMD 目录 (Level 2)]                                        |
   |  - 判断: 若当前地址 2MB 对齐且支持 2MB 大页 (page_size_mask & PG_LEVEL_2M):         |
   |    ► 直接写入 set_pmd_init(pmd, pfn_pmd(paddr, prot_sethuge(prot)));             |
   |    ► 表项中 Bit 7 (_PAGE_PSE) 置 1 ──► 硬件完成 2MB 大页直连，跳过 PTE!           |
   |  - 否则: alloc_low_page() 分配 PTE 表，调用 pmd_populate_kernel;                  |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [phys_pte_init() 写入 4KB 基准页 (Level 1)]                                      |
   |  - set_pte_init(pte, pfn_pte(paddr, prot));                                       |
   +-----------------------------------------------------------------------------------+

3.1 ``alloc_low_pages()`` 自举内存供血机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在构建直接映射页表时，分配页表页必须满足一个先决条件：**新分配的页表页自身的物理地址，必须能够被当前 CPU 访问！**
* **第一阶段（BRK 预留区）**：优先从静态预留的 ``pgt_buf``（位于内核镜像末端的 BRK 空间）中切片分配；
* **第二阶段（memblock 滚动自举）**：当 BRK 耗尽后，内核调用 ``memblock_phys_alloc_range()``，在**刚刚建立好直接映射的物理内存区间中**动态申请新的物理页作为下一批页表页！这种“用已映射的物理页支撑未映射区域的页表建设”的滚动递推设计，彻底解决了无限内存的自举映射问题。

第四幕：双向映射拓扑——自顶向下 (Top-Down) vs 自底向上 (Bottom-Up)
------------------------------------------------------------------

在 ``arch/x86/mm/init.c:init_mem_mapping()`` 中，直接映射的铺设方向根据系统配置分为两类：

::

   if (memblock_bottom_up()) {
       unsigned long kernel_end = __pa_symbol(_end);
       /* 自底向上模式 (KASLR / 特定 NUMA): 先映射内核上方的内存，再映射低端内存 */
       memory_map_bottom_up(kernel_end, end);
       memory_map_bottom_up(ISA_END_ADDRESS, kernel_end);
   } else {
       /* 自顶向下模式 (标准默认): 从最大物理地址向下逐步推进铺设 */
       memory_map_top_down(ISA_END_ADDRESS, end);
   }

第五幕：主页表正式载入与 TLB 全局冲刷（``load_cr3``）
------------------------------------------------------

当全系统物理内存的直接映射页表全部构建完毕后，内核执行历史性的页表切换：

::

   /* 1. 将正式内核母表 swapper_pg_dir (即 init_top_pgt) 物理地址装入 CR3 */
   load_cr3(swapper_pg_dir);

   /* 2. 触发全局 TLB 冲刷，彻底使 CPU 内部所有旧的临时映射缓存失效 */
   __flush_tlb_all();

   /* 3. 执行早期内存坏块测试 (若配置) */
   early_memtest(0, max_pfn_mapped << PAGE_SHIFT);

.. important::
   **直接映射区落成时刻的系统运行基准**：
   * **虚实通透**：整机全部物理 RAM 已完全且永久地映射在 ``PAGE_OFFSET``（``0xFFFF888000000000`` / ``0xFF10000000000000``）之上；
   * **巨页覆盖**：绝大部分物理内存通过 1GB / 2MB 巨页连接，TLB 缺失率降至极低；
   * **权限隔离**：主页表 ``swapper_pg_dir`` 成为全内核进程公用的内核态母表；
   * **伙伴系统就绪**：为下一章构建以 ``struct page`` 数组和 Zone 为核心的伙伴系统（Buddy System）扫清了所有的虚拟地址访问障碍！

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 内核直接物理内存映射区（``PAGE_OFFSET``）的宏伟设计、1GB/2MB 硬件巨页加速原理、``split_mem_range()`` 五段式自适应拆分状态机、PGD/P4D/PUD/PMD/PTE 层次装配时序、``alloc_low_pages()`` 滚动自举分配，以及正式主页表 ``swapper_pg_dir`` 激活与 TLB 冲刷。

直接映射区建立后，内核获得了常数级访问全物理内存的特权。紧接着，内核必须为每一个物理页帧（Page Frame）建立元数据描述符，并将整机内存按硬件特性划分为不同的管理区域（Zone）。

在 **第 4 节：伙伴系统 (Buddy System)：struct page、Zone (DMA/Normal/HighMem)、阶数拆分与合并** 中，我们将深入解构 ``struct page`` 极限 64 字节结构体拓扑、``vmemmap`` 虚拟稀疏内存模型、Zone 内存区域划分，以及阶数（Order 0~10）物理页块的拆分与合并核心算法。

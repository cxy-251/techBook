第一幕：多核并发的物理困境与 Per-CPU 架构设计哲学
--------------------------------------------------

在对称多处理（Symmetric Multiprocessing, SMP）体系中，多核共享内存带来了一个严重的微架构瓶颈——**缓存行颠簸（Cache Line Bouncing / False Sharing）**。

1.1 全局共享变量的硬件性能坍塌
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
若系统中所有 CPU 核心频繁读写同一个全局变量（如调度运行队列、进程上下文切换计数、网络包吞吐计数）：
* **MESI 协议风暴**：每当一个 CPU 核心写入该变量时，其所在的 L1/L2 缓存行被标记为 Modified，CPU 必须通过片上总线广播 **RFO（Request For Ownership）** 信号，强制使其他所有 CPU 核心中对应的缓存行全量失效（Invalid）；
* **总线拥塞与停顿**：其他核心在下次访问时被迫从共享 L3 缓存或物理 DRAM 重新加载，导致核间总线被一致性流量淹没，多核并行吞吐呈断崖式下跌。

1.2 Per-CPU 变量的物理哲学：空间换并发
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了彻底消灭核间锁竞争与缓存行冲突，Linux 内核确立了 **Per-CPU 存储模型**：
* **物理独立副本**：为系统中的每个物理 CPU 核心单独分配一份专属于自己的内存副本；
* **单核独占访问**：每个 CPU 核心仅读写属于自己的那份私有副本，**无需获取任何自旋锁，绝不引发任何跨核缓存行广播**，达成线性的多核横向扩展潜能！

第二幕：链接期模板与运行期物理克隆（setup_per_cpu_areas）
---------------------------------------------------------

Per-CPU 变量在系统中的诞生经历了一次从“单一编译模板”到“多核物理裂变”的精妙过程。

2.1 链接脚本中的 ``.data..percpu`` 节区（``vmlinux.lds.S``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在内核编译期，所有使用 ``DEFINE_PER_CPU(type, name)`` 声明的变量被链接器集中归拢在 **``.data..percpu`` 节区** 中：

::

   +-----------------------------------------------------------------------------------+
   |                       .data..percpu 静态编译期模板拓扑                            |
   |                                                                                   |
   |  __per_cpu_start (基准偏移 0x0000) ┌────────────────────────────────────────┐       |
   |                                    │ cpu_number (当前 CPU 逻辑编号)         │       |
   |                                    ├────────────────────────────────────────┤       |
   |                                    │ this_cpu_off (当前核心的 Per-CPU 偏移) │       |
   |                                    ├────────────────────────────────────────┤       |
   |                                    │ current_task (当前运行进程 task_struct)│       |
   |                                    ├────────────────────────────────────────┤       |
   |                                    │ runqueues (EEVDF 调度器私有运行队列)   │       |
   |                                    ├────────────────────────────────────────┤       |
   |                                    │ kmem_cache_cpu (SLUB 本地对象缓存池)   │       |
   |  __per_cpu_end   (大小: PERCPU_SZ) └────────────────────────────────────────┘       |
   +-----------------------------------------------------------------------------------+

.. important::
   在编译期生成的二进制符号表中，所有 Per-CPU 变量的地址**并不是真正的虚拟地址，而是相对于 ``__per_cpu_start`` 的相对偏移量（Offset）**！

2.2 ``setup_per_cpu_areas()`` 物理多核克隆流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``arch/x86/kernel/setup_percpu.c:setup_per_cpu_areas()`` 中，内核为每个 CPU 实例化物理内存：

::

   +-----------------------------------------------------------------------------------+
   |                      setup_per_cpu_areas() 多核克隆流水线                         |
   |                                                                                   |
   |  [步骤 1: 物理内存分配 (pcpu_embed_first_chunk)]                                  |
   |  - 遍历所有可能存在的 CPU: for_each_possible_cpu(cpu);                            |
   |  - 通过 memblock 为每个 CPU 核心分配一块连续物理内存 (Chunk, 满足 PMD 2MB 对齐);  |
   |            │                                                                      |
   |            ▼ 步骤 2: 模板内容全量深拷贝                                           |
   |  - 将 .data..percpu 静态模板完整 memcpy 复制到每个 CPU 核心的专属物理 Chunk 中;    |
   |            │                                                                      |
   |            ▼ 步骤 3: 计算并持久化每个 CPU 的绝对偏移量                           |
   |  - 计算公式: __per_cpu_offset[cpu] = Chunk_Base[cpu] - (unsigned long)__per_cpu_start;|
   |  - 将该值写入全局数组 __per_cpu_offset[cpu];                                      |
   |  - 写入该核心私有变量: per_cpu(this_cpu_off, cpu) = __per_cpu_offset[cpu];        |
   |            │                                                                      |
   |            ▼ 步骤 4: 激活当前引导核 (BSP) 的硬件段基址                            |
   |  - switch_gdt_and_percpu_base(0) ──► 将 __per_cpu_offset[0] 装入 MSR_GS_BASE !     |
   +-----------------------------------------------------------------------------------+

第三幕：x86_64 硬件段基址寻址——GS 寄存器与 MSR_GS_BASE
-------------------------------------------------------

在 64 位长模式下，Intel 与 AMD 废除了传统的分段机制（CS/DS/ES/SS 段基址被硬件强制固定为 0），但保留了两个特殊的段寄存器——**FS 与 GS**，允许加载任意 64 位基地址。

3.1 FS 与 GS 的架构分工
~~~~~~~~~~~~~~~~~~~~~~~
* **FS 寄存器**：留给用户态应用程序作为 **线程局部存储（Thread Local Storage, TLS）** 的指针基准（如 glibc 的 ``pthread_self()``）；
* **GS 寄存器**：由 Linux 内核独占，专门存放当前物理 CPU 的 **Per-CPU 区域物理/虚拟基地址**！

3.2 硬件寄存器矩阵与 ``SWAPGS`` 原子切换指令
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了实现用户态与内核态在陷入系统调用时无缝切换 GS 段基准，x86_64 硬件提供了两组专用的 MSR 寄存器：

::

   +-----------------------------------------------------------------------------------+
   |                           GS 寄存器硬件 MSR 架构与 SWAPGS                         |
   |                                                                                   |
   |  [MSR_GS_BASE (0xC0000101)]        [MSR_KERNEL_GS_BASE (0xC0000102)]              |
   |  (当前 CPU 硬件实际生效的 GS 基址)  (内核/用户态备用影子基址)                       |
   |             │                                      │                              |
   |             └───────────────┐      ┌───────────────┘                              |
   |                             ▼      ▼                                              |
   |                 执行 SWAPGS 硬件原子交换指令 (1 周期)                             |
   |                             ▲      ▲                                              |
   |             ┌───────────────┘      └───────────────┐                              |
   |             │                                      │                              |
   |  [用户态 GS 基址 (TLS 指针)]       [内核 Per-CPU 基址 (__per_cpu_offset[cpu])]     |
   +-----------------------------------------------------------------------------------+

* **陷入内核时刻（SYSCALL / 中断入口）**：CPU 执行 **``swapgs``** 指令，硬件在 1 个时钟周期内将 ``MSR_KERNEL_GS_BASE`` 中的内核 Per-CPU 基址瞬切至 ``MSR_GS_BASE``；
* **返回用户态时刻（SYSRET / IRETQ 前夕）**：再次执行 **``swapgs``**，将用户态 TLS 指针恢复回 ``MSR_GS_BASE``。

第四幕：单指令原子操作——``this_cpu_*`` 汇编指令微观解构
-------------------------------------------------------

得益于 GS 段寄存器的硬件寻址支持，Linux 7.2 的 Per-CPU 读写被编译器直接翻译为极限高效的单条汇编指令。

4.1 ``%gs:`` 段前缀（Segment Override Prefix）编译器魔法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``arch/x86/include/asm/percpu.h`` 中，读写本地 Per-CPU 变量被定义为内联汇编宏：

::

   #define this_cpu_read(var) \
       ({ typeof(var) pdo_ret__; \
          asm volatile("movq %%gs:%1, %0" : "=r"(pdo_ret__) : "m"(var)); \
          pdo_ret__; })

4.2 核心操作的机器码与时钟周期对比
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. table:: Per-CPU 核心操作与常规全局变量汇编时钟时序对比
   :widths: 20 30 50

   +--------------------------+------------------------------+----------------------------------------------------+
   | 内核 C 语言宏操作        | 编译生成的 x86_64 汇编指令   | 物理执行机制与微架构优势                           |
   +==========================+==============================+====================================================+
   | **``this_cpu_read(v)``** | ``movq %gs:v(%rip), %rax``   | **1 个时钟周期**：硬件自动将 ``GS_BASE + v`` 寻址， |
   |                          |                              | 直接从 L1 Cache 读取本地副本，零跨核通信开销       |
   +--------------------------+------------------------------+----------------------------------------------------+
   | **``this_cpu_write(v)``**| ``movq %rax, %gs:v(%rip)``   | **1 个时钟周期**：直接写入本地 L1 缓存行，         |
   |                          |                              | 绝不使其他核心的 Cache 失效                        |
   +--------------------------+------------------------------+----------------------------------------------------+
   | **``this_cpu_inc(v)``**  | ``incq %gs:v(%rip)``         | **单条原子指令**：在读-改-写（RMW）周期内执行完成，|
   |                          |                              | **天然免疫内核抢占（Preemption Safe）**，无需加锁  |
   +--------------------------+------------------------------+----------------------------------------------------+
   | **``this_cpu_cmpxchg``** | ``cmpxchgq %r8, %gs:v(%rip)``| **本地无锁 CAS**：支持在单核私有池中实现原子状态迁移|
   +--------------------------+------------------------------+----------------------------------------------------+

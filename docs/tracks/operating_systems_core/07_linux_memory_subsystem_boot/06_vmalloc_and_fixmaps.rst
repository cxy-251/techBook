第一幕：虚拟连续的物理哲学——``vmalloc`` 架构与虚拟地址空间拓扑
--------------------------------------------------------------

在操作系统运行过程中，伙伴系统（Buddy System）负责分配物理连续的页块。然而，随着系统长期运行与物理内存碎片化，申请大跨度连续物理页（如连续 16MB 或 64MB）的失败率显著上升。

1.1 为什么内核需要 ``vmalloc``？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **解耦物理连续性**：许多大型内核子系统（如可加载内核模块 ``.ko``、eBPF JIT 编译执行区、动态 I/O 缓冲区、大型哈希表）**仅要求虚拟地址连续，对底层物理页的连续性毫无要求**；
* **物理碎片粘合剂**：``vmalloc`` 将伙伴系统分配出来的散碎、离散的 4KB/2MB 物理页，在独立的虚拟地址空间中通过页表重新缝合，呈现为一段平坦、连续的虚拟内存缓冲区。

1.2 64 位 ``vmalloc`` 虚拟地址空间拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位体系下，``vmalloc`` 拥有独立且浩瀚的专用虚拟地址空间，与直接映射区（``PAGE_OFFSET``）及内核代码段（``__START_KERNEL_map``）保持严格隔离：

::

   +-----------------------------------------------------------------------------------+
   |                       Linux 64 位内核虚拟内存全景与 vmalloc 区                    |
   |                                                                                   |
   |  0xFFFF888000000000 ~ 0xFFFFC8FFFFFFFFFF: 直接物理内存映射区 (PAGE_OFFSET, 64TB)   |
   |  ──────────────────────────────────────────────────────────────────────────────── |
   |  0xFFFFC90000000000 ~ 0xFFFFE8FFFFFFFFFF: vmalloc 动态虚拟内存分配区 (32 TB)      |
   |       │                                                                           |
   |       ├── [vmap_area 1: 内核模块 ext4.ko 代码段 (12MB, 映射 3072 个离散物理页)]   |
   |       ├── [保护安全页 (Guard Page, 4KB, Non-Present, 防越界溢出)]                 |
   |       ├── [vmap_area 2: eBPF JIT 指令区 (64MB, 映射 16384 个离散物理页)]           |
   |       └── [保护安全页 (Guard Page, 4KB, Non-Present, 防越界溢出)]                 |
   |  ──────────────────────────────────────────────────────────────────────────────── |
   |  0xFFFFEA0000000000 ~ 0xFFFFEAFFFFFFFFFF: vmemmap 物理页描述符数组 (struct page) |
   |  0xFFFFFFFF80000000 ~ 0xFFFFFFFFFEFFFFFF: __START_KERNEL_map (内核静态代码与数据) |
   |  0xFFFFFFFFFF000000 ~ 0xFFFFFFFFFFFFFFFF: Fixmap 编译期固定映射区 (Local APIC等)  |
   +-----------------------------------------------------------------------------------+

第二幕：$O(\log N)$ 空间检索——``vmap_area`` 增强型红黑树与空闲块分配
--------------------------------------------------------------------

为了在高达数十 TB 的虚拟地址空间中纳秒级寻找一段空闲的连续虚拟区间，Linux 7.2 采用了基于 **增强型红黑树（Augmented Red-Black Tree）** 的管理架构。

2.1 ``struct vmap_area`` 与 ``struct vm_struct`` 双核心拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           vmap_area 与 vm_struct 拓扑关系                         |
   |                                                                                   |
   |  struct vmap_area {                                                               |
   |      unsigned long va_start;           /* 虚拟空间起始地址 */                      |
   |      unsigned long va_end;             /* 虚拟空间结束地址 (含 4KB Guard Page) */  |
   |      unsigned long subtree_max_size;   /* 增强红黑树特性: 当前子树最大空闲区间跨度 */|
   |      struct rb_node rb_node;           /* 挂入全局已分配虚拟区间红黑树 */          |
   |      struct list_head list;            /* 挂入按地址排序的全局双向链表 */          |
   |      struct vm_struct *vm;             /* 反向关联底层物理资源描述符 */            |
   |  };                                                                               |
   |                                                                                   |
   |  struct vm_struct {                                                               |
   |      void *addr;                       /* 对应 vmap_area 的用户可用起始虚拟地址 */ |
   |      unsigned long size;               /* 实际可用字节大小 (不含 Guard Page) */    |
   |      unsigned long flags;              /* 标志位: VM_ALLOC / VM_MAP / VM_IOREMAP */|
   |      struct page **pages;              /* 指向离散物理页 struct page* 指针数组 */  |
   |      unsigned int nr_pages;            /* 绑定的 4KB 物理页数量 */                 |
   |      phys_addr_t phys_addr;            /* 当用于 ioremap 时记录的设备物理基地址 */ |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

2.2 增强型红黑树的首适配（First-Fit）$O(\log N)$ 检索算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **传统红黑树痛点**：若仅按地址排序，查找一段满足 ``size`` 要求的空闲空间需要遍历链表，时间复杂度为 $O(N)$；
* **增强特性（Augmented Subtree Size）**：每个树节点动态维护 ``subtree_max_size``，表示以该节点为根的左子树、右子树以及自身空隙中所存在的**最大连续空闲虚拟跨度**；
* **单向剪枝下潜**：分配器从根节点出发，如果左子树的 ``subtree_max_size >= size``，直接向左下潜；否则向右下潜。整个搜索在 **$O(\log N)$ 步** 内必定定位到最左侧满足条件的空闲区间，彻底消除了大规模虚拟内存碎片下的搜索性能衰减！

第三幕：``vmalloc()`` 物理页离散申请与逐级页表动态拼接
------------------------------------------------------

当调用 ``vmalloc(size)`` 时，内核执行一套严密的四阶段装配流水线：

::

   +-----------------------------------------------------------------------------------+
   |                           vmalloc(size) 执行全景流水线                            |
   |                                                                                   |
   |  [调用 vmalloc(size)]                                                             |
   |            │                                                                      |
   |            ▼ 阶段 1: 虚拟空间锁定与元数据建立                                     |
   |  - size 对齐为 PAGE_SIZE 整数倍，额外增加 4KB Guard Page;                         |
   |  - alloc_vmap_area(): 从增强红黑树检索并锁定空闲虚拟区间 [va_start, va_end);       |
   |  - 分配 struct vm_struct 并初始化 pages 指针数组 (kmalloc 申请);                   |
   |            │                                                                      |
   |            ▼ 阶段 2: 批量物理页帧极速申请 (alloc_pages_bulk_array)                |
   |  - 调用伙伴系统批量分配接口 alloc_pages_bulk_array_node():                        |
   |    从指定 NUMA 节点的伙伴系统中并发抓取 nr_pages 个离散的 4KB 物理页;             |
   |    将每个物理页的 struct page* 依次填入 vm->pages[i];                             |
   |            │                                                                      |
   |            ▼ 阶段 3: 逐级页表动态装配 (vmap_pages_range)                          |
   |  - 遍历 vmalloc 虚拟区间对应的内核主页表 (init_mm.pgd):                           |
   |    vmap_p4d_range() ──► vmap_pud_range() ──► vmap_pmd_range() ──► vmap_pte_range() |
   |  - 为每个离散物理页写入 PTE: set_pte(pte, mk_pte(page, prot));                    |
   |            │                                                                      |
   |            ▼ 阶段 4: 同步全局页表与多核可见性                                     |
   |  - arch_sync_kernel_mappings(): 将顶层页表修改同步至所有 CPU 的活跃 PGD 中;        |
   |  - 返回 vm->addr 虚拟基地址给调用方!                                              |
   +-----------------------------------------------------------------------------------+

3.1 惰性 TLB 冲刷与批量回收机制（Lazy TLB Purging）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当调用 ``vfree(addr)`` 释放虚拟内存时：
1. **解除页表**：``vunmap_range()`` 清空对应的 PTE 表项；
2. **释放物理页**：将 ``vm->pages`` 中的所有物理页归还伙伴系统；
3. **延迟冲刷（Lazy Purge）**：内核并不立即触发全核 TLB 广播（因为跨核 IPI 中断开销极大），而是将已解除映射的 ``vmap_area`` 挂入全局 ``vmap_purge_list``；
4. **批量触发**：当累计释放的虚拟内存达到阈值（如 ``2MB * num_online_cpus()``）或虚拟空间紧张时，内核统一触发一次 **``flush_tlb_kernel_range()``**，批量收回所有虚拟区间，达成吞吐与实时性的完美平衡。

第四幕：编译期固定地址——Fixmap 固定映射与硬件寄存器锚定
--------------------------------------------------------

在内核虚拟空间的最顶端，存在一块特殊的静态区域——**Fixmap（Fixed Virtual Address Mapping）**。

4.1 什么是 Fixmap？
~~~~~~~~~~~~~~~~~~~
* **编译期常量寻址**：与 ``vmalloc`` 在运行期动态计算虚拟地址不同，Fixmap 的虚拟地址在编译期通过枚举索引严格固定：
  $$\mathbf{Fixmap\_Virt}(idx) = \mathbf{FIXADDR\_TOP} - (idx \ll 	ext{PAGE\_SHIFT})$$
* **虚拟地址不变，物理页动态切换**：Fixmap 的虚拟指针永不改变，但内核可以在运行期纳秒级修改其背后的单个 PTE，将其重定向至不同的物理硬件寄存器或缓冲区。

4.2 核心 Fixmap 槽位与硬件物理锚定
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                             Fixmap 核心槽位拓扑矩阵                               |
   |                                                                                   |
   |  顶端高地址: FIXADDR_TOP (0xFFFFFFFFFF5FB000 附近)                                |
   |       │                                                                           |
   |       ├── [FIX_VSYSCALL: 虚拟系统调用页面 (用户态只读映射)]                       |
   |       ├── [FIX_APIC_BASE: 局部中断控制器 Local APIC MMIO 寄存器物理页 (0xFEE00000)]|
   |       ├── [FIX_IO_APIC_BASE_0 ~ N: 主板 IO-APIC 物理芯片 MMIO 寄存器 (0xFEC00000)]|
   |       ├── [FIX_RO_IDT: 只读中断描述符表影子映射 (防内核漏洞篡改 IDT)]              |
   |       ├── [FIX_BTMAP_BASE: 早期启动阶段专用的 16 个临时探测槽位 (early_ioremap)]   |
   |       └── [FIX_GDT / FIX_TSS: Per-CPU 任务状态段与段描述符]                       |
   +-----------------------------------------------------------------------------------+

4.3 ``set_fixmap()`` 物理重绑定微观时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当内核需要访问 Local APIC 寄存器时：

::

   set_fixmap_nocache(FIX_APIC_BASE, apic_phys_addr);
   ├──► pte = get_fixmap_pte(FIX_APIC_BASE);
   ├──► set_pte(pte, pfn_pte(apic_phys_addr >> PAGE_SHIFT, PAGE_KERNEL_IO_NOCACHE));
   └──► __native_flush_tlb_one_kernel(__fix_to_virt(FIX_APIC_BASE));

此后，内核访问宏 ``APIC_BASE`` 即可直接读写物理 APIC 芯片，完全免除了动态分配虚拟空间的任何开销！

第五幕：临时内核映射 (kmap) 的现代演进与 64 位体系解构
------------------------------------------------------

在操作系统教科书中，``kmap``（Kernel Mapping）是一个经典的必讲概念。然而在现代 64 位 Linux 7.2 内核中，``kmap`` 经历了一场彻底的架构蜕变。

5.1 32 位 HighMem 时代的历史局限与 ``kmap()`` 痛点
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **32 位困境**：在 32 位系统下，4GB 虚拟地址空间中内核仅占 1GB（``0xC0000000 ~ 0xFFFFFFFF``），直接映射区只能覆盖前 896MB 物理内存；
* 超过 896MB 的物理内存被称为 **高端内存（HighMem）**，必须通过有限的临时页表槽位（``kmap_atomic``）动态切换映射，频繁导致死锁与上下文切换瓶颈。

5.2 64 位体系结构下 HighMem 的终结与 ``kmap_local_page()`` 零开销演进
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位 x86_64 体系下：
* 直接映射区（``PAGE_OFFSET``）容量高达 **64TB（4级分页）/ 32PB（5级分页）**，全机所有物理 RAM 已永久直接映射；
* **零开销宏展开**：在 ``include/linux/highmem.h`` 中，``kmap_local_page()`` 直接内联为指针算术运算：

::

   static inline void *kmap_local_page(struct page *page) {
       return page_address(page); /* 直接返回: __va(page_to_pfn(page) << PAGE_SHIFT) ! */
   }
   static inline void kunmap_local(const void *addr) {
       /* 64 位下无临时页表需要解除，编译为空操作 (No-op)! */
   }

这一演进使得全内核在保持与旧代码 API 完全兼容的前提下，彻底消除了临时映射的页表修改与 TLB 冲刷开销，达成了物理极致的执行效率！

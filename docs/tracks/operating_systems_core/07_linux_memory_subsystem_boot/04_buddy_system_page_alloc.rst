第一幕：物理页帧的微观视界——``struct page`` 极限压缩与 ``vmemmap`` 拓扑
-------------------------------------------------------------------------

在操作系统管理的世界中，4KB（$2^{12}$ 字节）物理页是内存分配与硬件 MMU 调度的最小原子粒子。现代计算机动辄拥有数百 GB 乃至数 TB 内存（例如 64GB 内存包含 $16,777,216$ 个物理页帧 PFN）。

1.1 64 字节极限压缩架构
~~~~~~~~~~~~~~~~~~~~~~~
如果为每个物理页分配一个 1KB 的元数据结构体，仅管理 64GB 物理内存就需要消耗 **16GB 的元数据**！为此，Linux 内核通过极度苛刻的联合体（Unions）重载，将 **``struct page`` 严格压缩至 64 字节**（在 64 位 x86_64 体系下），使整机物理页元数据开销仅占总内存的 **$1.56\%$**（$\frac{64}{4096}$）。

::

   +-----------------------------------------------------------------------------------+
   |                           struct page 核心字段物理语义                            |
   |                                                                                   |
   |  struct page {                                                                    |
   |      unsigned long flags;              /* 核心标志位与元数据位图 (含 Zone/Node 编码) */ |
   |      union {                                                                      |
   |          struct {                                                                 |
   |              struct list_head lru;     /* 在伙伴系统中复用为 buddy_list 双向链表节点 */|
   |              struct address_space *mapping; /* 归属的文件地址空间或匿名映射指针 */|
   |              pgoff_t index;            /* 在文件中的页偏移量 */                   |
   |              unsigned long private;    /* 在伙伴系统中存储当前页块的阶数 (Order)! */|
   |          };                                                                       |
   |          /* SLUB 对象分配器复用的元数据槽位 */                                    |
   |          struct {                                                                 |
   |              void *freelist;           /* 指向 slab 内第一个空闲对象的指针 */     |
   |              unsigned counters;        /* inuse 计数、objects 总数与 frozen 标志 */ |
   |          };                                                                       |
   |      };                                                                           |
   |      atomic_t _refcount;               /* 物理页引用计数: 0=空闲, >0=正在使用 */    |
   |      atomic_t _mapcount;               /* 页表映射计数: -1=未映射, 0=单进程映射 */ |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

1.2 ``vmemmap`` 虚拟稀疏内存 $O(1)$ 寻址架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``CONFIG_SPARSEMEM_VMEMMAP`` 模式下，内核在直接映射区附近开辟了一段独立的连续虚拟地址空间（``vmemmap``），用来整齐存放所有物理页的 ``struct page`` 描述符：

$$	ext{pfn\_to\_page}(pfn) = \mathbf{vmemmap} + pfn$$
$$	ext{page\_to\_pfn}(page) = page - \mathbf{vmemmap}$$

无论物理内存如何稀疏，内核通过单条汇编基址加减指令即可在纳秒级完成物理页帧号（PFN）与元数据结构体（``struct page``）的双向转换！

第二幕：物理内存区域 (Zone) 划分与反碎片迁移类型 (Migratetype)
---------------------------------------------------------------

受限于不同总线与外设硬件的物理寻址缺陷，操作系统无法将所有内存同等对待，必须按硬件约束划分为不同的 **内存管理区域（Zone）**。

2.1 物理内存分区架构（``enum zone_type``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                             x86_64 物理内存 Zone 拓扑                             |
   |                                                                                   |
   |  0 MB ┌────────────────────────────────────────────────────────┐                  |
   |       │ ZONE_DMA (0 ~ 16MB)                                    │ (供 24 位 ISA 设备)|
   | 16 MB ├────────────────────────────────────────────────────────┤                  |
   |       │ ZONE_DMA32 (16MB ~ 4GB)                                │ (供 32 位 PCI 设备)|
   |  4 GB ├────────────────────────────────────────────────────────┤                  |
   |       │ ZONE_NORMAL (4GB ~ 系统最大物理内存)                   │ (常规内核与用户态) |
   |       ├────────────────────────────────────────────────────────┤                  |
   |       │ ZONE_MOVABLE (动态划分)                                │ (全可移动/热插拔)  |
   | Max   └────────────────────────────────────────────────────────┘                  |
   +-----------------------------------------------------------------------------------+

2.2 逻辑反碎片迁移类型（``enum migratetype``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
**外部碎片（External Fragmentation）** 是连续大页分配失败的头号杀手。Linux 内核根据物理页是否可以移动，将内存划分为不同的迁移链表：
* **``MIGRATE_UNMOVABLE``**：内核核心代码、页表项、SLUB 描述符（物理位置固定，绝不可移动）；
* **``MIGRATE_MOVABLE``**：用户空间进程匿名页、Page Cache 文件缓存页（可通过修改页表透明移动）；
* **``MIGRATE_RECLAIMABLE``**：Dentry / Inode 缓存（不可移动但可被内存扫描器直接丢弃释放）；
* **``MIGRATE_HIGHATOMIC``**：中断或原子上下文紧急分配专用保留池。

通过将不可移动的“硬石头”集中存放在专用页块（Pageblock）中，避免其散落污染整块连续内存，使得 2MB 透明大页（THP）分配成功率提升至 95% 以上。

第三幕：伙伴系统数据结构与阶数分层（``free_area[0..10]``）
-----------------------------------------------------------

在 ``include/linux/mmzone.h`` 中，每个 Zone 内部维护着一个核心数据结构——**``free_area[NR_PAGE_ORDERS]`` 阶数数组**。

3.1 阶数拓扑与块容量对照
~~~~~~~~~~~~~~~~~~~~~~~~
Linux 7.2 默认支持 **11 个阶数（Order 0 ~ 10，``MAX_PAGE_ORDER = 10``）**：

.. table:: 伙伴系统 Order 阶数与连续内存容量对照表
   :widths: 15 25 30 30

   +===========+========================+========================+==========================================+
   | Order 阶数| 包含物理页数 ($2^K$)   | 连续物理内存容量       | 典型应用场景                             |
   +===========+========================+========================+==========================================+
   | **0**     | 1 页                   | **4 KB**               | 单页用户进程代码/数据、普通小文件读写    |
   +-----------+------------------------+------------------------+------------------------------------------+
   | **1**     | 2 页                   | **8 KB**               | 早期 32 位内核栈、轻量 DMA 缓冲区        |
   +-----------+------------------------+------------------------+------------------------------------------+
   | **2**     | 4 页                   | **16 KB**              | **x86_64 64 位进程内核栈 (thread_union)**|
   +-----------+------------------------+------------------------+------------------------------------------+
   | **3**     | 8 页                   | **32 KB**              | 中等 SLUB Slab 内存块                    |
   +-----------+------------------------+------------------------+------------------------------------------+
   | **9**     | 512 页                 | **2 MB**               | **x86_64 PMD 透明大页 (THP)**            |
   +-----------+------------------------+------------------------+------------------------------------------+
   | **10**    | 1024 页                | **4 MB**               | 伙伴系统最大原子分配单元                 |
   +-----------+------------------------+------------------------+------------------------------------------+

3.2 ``struct free_area`` 双层拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每个阶数的 ``struct free_area`` 包含一组按迁移类型划分的双向循环链表：

::

   struct free_area {
       struct list_head free_list[MIGRATE_TYPES]; /* 每个迁移类型一条独立空闲链表 */
       unsigned long    nr_free;                  /* 该阶数下当前空闲块的总数量 */
   };

第四幕：伙伴分配与拆分算法（``rmqueue() -> expand()``）
-------------------------------------------------------

当内核调用 ``alloc_pages(gfp_mask, order)`` 申请内存时，分配器首先尝试从目标阶数获取内存；若目标链表为空，则触发阶梯式二叉拆分（Bisecting）。

4.1 向上探测与阶梯拆分流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       伙伴系统 expand() 二叉拆分微观流程                          |
   |                                                                                   |
   |  [申请 Order 1 (8KB) 物理页]                                                      |
   |  1. 检查 free_area[1]: 为空 (nr_free = 0)                                         |
   |  2. 向上探测 free_area[2]: 依然为空                                               |
   |  3. 探测到 free_area[3] (32KB): 找到一块空闲大块!                                 |
   |            │                                                                      |
   |            ▼ 4. 执行第一级二叉拆分 (Order 3 -> Order 2)                           |
   |  - 从 free_area[3] 摘除 32KB 页块 (包含 8 个 4KB 页);                             |
   |  - 将后半部 16KB (4 页) 挂入 free_area[2] 空闲链表，设置 private=2, SetPageBuddy; |
   |            │                                                                      |
   |            ▼ 5. 执行第二级二叉拆分 (Order 2 -> Order 1)                           |
   |  - 将前半部 16KB 再次对半裁切;                                                    |
   |  - 将后半部 8KB (2 页) 挂入 free_area[1] 空闲链表，设置 private=1, SetPageBuddy;  |
   |            │                                                                      |
   |            ▼ 6. 达成目标                                                          |
   |  - 将最终剩下的前半部 8KB (Order 1) 标记为已分配，返回给调用方!                   |
   +-----------------------------------------------------------------------------------+

第五幕：伙伴释放与位异或合并算法（``__free_one_page()``）
---------------------------------------------------------

内存释放过程是伙伴系统最具数学美感的设计。系统利用纯二进制位运算，在常数时间内判定伙伴状态并完成自底向上的级联聚合。

5.1 什么是“伙伴”（Buddy）？
~~~~~~~~~~~~~~~~~~~~~~~~~~~
两个内存块互为伙伴必须同时满足三个硬性条件：
1. **大小相同**：阶数（Order）完全相等；
2. **物理连续**：在物理地址空间紧密相邻；
3. **边界对齐**：二者合并后的大块基地址必须满足更高阶的自然对齐。

.. important::
   **伙伴地址判定的二进制异或铁律**：
   对于 PFN 为 ``pfn``、阶数为 ``order`` 的页块，其唯一伙伴的物理页帧号由**位异或运算**绝对确定：

   $$\mathbf{buddy\_pfn = pfn \oplus (1 \ll order)}$$

   $$\mathbf{combined\_pfn = pfn \ \& \ buddy\_pfn}$$

5.2 ``__free_one_page()`` 级联聚合状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                     __free_one_page() 伙伴级联聚合流水线                          |
   |                                                                                   |
   |  while (order < MAX_PAGE_ORDER) {                                                 |
   |      /* 1. 异或运算瞬间算出理论伙伴 PFN */                                        |
   |      buddy_pfn = pfn ^ (1 << order);                                              |
   |      buddy = find_buddy_page_pfn(page, pfn, order, &buddy_pfn);                   |
   |                                                                                   |
   |      /* 2. 检查伙伴是否处于空闲态且阶数一致 */                                    |
   |      if (!buddy || !PageBuddy(buddy) || buddy_order(buddy) != order)              |
   |          goto done_merging; /* 伙伴正在被使用，终止合并 */                        |
   |                                                                                   |
   |      /* 3. 伙伴同样空闲！将其从当前阶数空闲链表中摘除 */                          |
   |      __del_page_from_free_list(buddy, zone, order, buddy_mt);                     |
   |                                                                                   |
   |      /* 4. 合并为更高阶页块，基地址取二者较小者 (位与运算) */                     |
   |      combined_pfn = buddy_pfn & pfn;                                              |
   |      page = page + (combined_pfn - pfn);                                          |
   |      pfn = combined_pfn;                                                          |
   |      order++; /* 阶数自增，继续循环向上尝试合并! */                               |
   |  }                                                                                |
   |  done_merging:                                                                    |
   |  set_buddy_order(page, order);                                                    |
   |  __add_to_free_list(page, zone, order, migratetype, to_tail);                     |
   +-----------------------------------------------------------------------------------+

第六幕：Per-CPU 页面集合 (PCP) 与水线 (Watermarks) 机制
-------------------------------------------------------

为了追求极致的高并发与多核性能，伙伴系统构建了无锁前端与多级水线保护。

6.1 PCP (Per-CPU Pages) 无锁快速路径
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **痛点**：多核 CPU 并发申请 Order 0（4KB）单页时，频繁争抢 ``zone->lock`` 自旋锁会导致严重的锁总线颠簸；
* **解法**：为每个 CPU 核心设立本地 ``struct per_cpu_pages`` 链表。单页分配直接在本地 CPU 关中断下完成，零锁争用！只有当本地 PCP 链表耗尽或超出高水线时，才通过 ``rmqueue_bulk()`` 批量向底层 Zone 申请或归还内存。

6.2 内存水线（Watermarks）动态调节机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每个 Zone 维护三道水位线：

::

   +-----------------------------------------------------------------------------------+
   |                               Zone 内存水线防御体系                               |
   |                                                                                   |
   |  [内存耗尽 (0)] ──────► 触发 OOM Killer (杀进程保系统)                            |
   |         ▲                                                                         |
   |         │ WMARK_MIN (最低安全线: 触发同步直接内存回收 Direct Reclaim)              |
   |         │                                                                         |
   |         │ WMARK_LOW (低水位线: 异步唤醒后台平衡守护进程 kswapd 开始换页)           |
   |         │                                                                         |
   |         │ WMARK_HIGH (高水位线: kswapd 停止换页，系统恢复平稳)                    |
   |         ▼                                                                         |
   |  [内存充足 (Total)]                                                               |
   +-----------------------------------------------------------------------------------+

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 分区伙伴系统的微观设计：64 字节 ``struct page`` 拓扑、``vmemmap`` 虚拟稀疏内存 $O(1)$ 寻址、Zone 物理分区与迁移反碎片机制、Order 0~10 阶数分层、``expand()`` 二叉拆分算法、``__free_one_page()`` 位异或级联聚合数学模型，以及 PCP 无锁快速路径与三级内存水线。

伙伴系统以 4KB 物理页为最小分配单位。然而，操作系统内核内部充斥着大量数字节到数千字节的小型数据结构（如几十字节的 ``struct inode``、上千字节的 ``struct task_struct``）。如果每次都向伙伴系统申请 4KB 大页，将产生灾难性的内部碎片。

在 **第 5 节：SLUB 细粒度对象分配器：kmem_cache 拓扑、cpu_slab 无锁快速路径与 node_slab 慢速路径** 中，我们将深入解构建立在伙伴系统之上的小内存对象分配之王——SLUB 分配器的全景架构与微观无锁流转时序。

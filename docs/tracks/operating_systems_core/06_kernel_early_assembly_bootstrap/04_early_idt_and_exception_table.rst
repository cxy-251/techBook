第一幕：早期异常防御的物理必然性——裸机与完整 IDT 间的危险真空期
-----------------------------------------------------------------

在操作系统进入通用 C 语言初始化阶段（``start_kernel()``）之前，内核面临着一段极其脆弱的 **中断真空期**：

::

   +-----------------------------------------------------------------------------------+
   |                             早期异常捕获的物理必然性                              |
   |                                                                                   |
   |  [早期引导危险操作]                                                               |
   |  - 访问未经映射的物理内存 (动态页表扩展) ──► 触发 #PF (缺页异常, Vector 14)       |
   |  - 嗅探不存在或受限的 CPU 特权 MSR 寄存器 ──► 触发 #GP (通用保护异常, Vector 13) |
   |  - 机密虚拟机执行 CPUID / IN / OUT 指令 ──► 触发 #VC / #VE 虚拟化异常            |
   |            │                                                                      |
   |            ▼ (若此时没有加载任何 IDT 表!)                                         |
   |  [硬件连锁灾难: Double Fault -> Triple Fault]                                     |
   |  1. CPU 试图通过 IDT 分发异常，但 IDT 为空 (Limit=0);                             |
   |  2. 异常无法递送，硬件自动将其升级为 Double Fault (#DF, 双重错误, Vector 8);      |
   |  3. 分发 #DF 时依然无法找到处理入口;                                              |
   |  4. CPU 瞬间进入 Shutdown 模式，发出 RESET# 硬件引脚信号 ──► 机器瞬时黑屏重启!     |
   +-----------------------------------------------------------------------------------+

为了彻底破除这一致命隐患，Linux 7.2 内核在执行任何复杂的 C 语言逻辑前，必须在汇编层预先挂载一个能够拦截全部 32 种 CPU 硬件异常的 **早期中断描述符表（Early IDT）**。

第二幕：32 向量汇编桩阵列与错误码对齐（early_idt_handler_array）
-----------------------------------------------------------------

在 x86_64 微架构中，CPU 硬件在分发不同类型的异常时，其压栈行为存在天然的不一致性。

2.1 硬件错误码（Error Code）压栈差异
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **带错误码的异常（Hardware Pushes Error Code）**：
  当发生与内存分段、分页或权限相关的严重故障时，CPU 硬件在压入 ``RIP, CS, RFLAGS, RSP, SS`` 之后，会**自动在栈顶额外压入一个 64 位的错误码（Error Code）**：
  * ``#DF (Vector 8)``: 双重错误（错误码恒为 0）
  * ``#TS (Vector 10)``: 无效 TSS 任务段
  * ``#NP (Vector 11)``: 段不存在异常
  * ``#SS (Vector 12)``: 栈段错误异常
  * ``#GP (Vector 13)``: 通用保护错误（错误码包含引发异常的段选择子或 IDT 索引）
  * ``#PF (Vector 14)``: 缺页异常（错误码包含读/写、用户/内核、保留位违规等标志位）
  * ``#AC (Vector 17)``: 对齐检查错误
  * ``#CP (Vector 21)``: 控制流保护错误
* **不带错误码的异常（Hardware Pushes NO Error Code）**：
  其余所有常规异常（如 ``#DE 0`` 除零、``#DB 1`` 调试、``#BP 3`` 断点、``#UD 6`` 无效指令码），CPU 硬件**绝不压入错误码**。

2.2 汇编桩宏展开与 Dummy 占位对齐（``arch/x86/kernel/head_64.S``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了让后续通用的 C 语言异常处理函数能够解析出统一结构的 ``struct pt_regs`` 寄存器帧，``head_64.S`` 使用汇编宏生成了 32 个高度优化的汇编桩：

::

   +-----------------------------------------------------------------------------------+
   |                     early_idt_handler_array 汇编桩生成逻辑                        |
   |                                                                                   |
   |  i = 0                                                                            |
   |  .rept NUM_EXCEPTION_VECTORS (32 个异常向量)                                      |
   |      .if ((EXCEPTION_ERRCODE_MASK >> i) & 1) == 0                                 |
   |          UNWIND_HINT_IRET_REGS                                                    |
   |          ENDBR                                                                    |
   |          pushq   $0              /* 硬件未压错误码: 手动压入 8 字节 Dummy 0 占位! */|
   |      .else                                                                        |
   |          UNWIND_HINT_IRET_REGS offset=8                                           |
   |          ENDBR                                                                    |
   |      .endif                                                                       |
   |      pushq   $i                  /* 压入当前异常的向量编号 Vector Number (0..31) */|
   |      jmp     early_idt_handler_common                                             |
   |      i = i + 1                                                                    |
   |      .fill early_idt_handler_array + i*EARLY_IDT_HANDLER_SIZE - ., 1, 0xcc        |
   |  .endr                                                                            |
   +-----------------------------------------------------------------------------------+

通过这套汇编宏展开：
* 对于不带错误码的异常，代码主动补推一个 ``$0``；
* 最终保证当跳转进入 ``early_idt_handler_common`` 时，栈顶结构**在物理上绝对统一**：栈顶第 1 项为异常向量号，第 2 项为错误码，第 3~7 项为 CPU 硬件自动压入的现场！

第三幕：``pt_regs`` 寄存器现场全量保存与递归死锁侦测
---------------------------------------------------

所有 32 个汇编桩在完成初步对齐后，统一汇聚至 **``early_idt_handler_common``**：

3.1 ``pt_regs`` 完整寄存器压栈时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   SYM_CODE_START_LOCAL(early_idt_handler_common)
       cld                             /* 清除方向标志 */

       /* 1. 递归异常死锁检测：自增全局计数器 */
       incl    early_recursion_flag(%rip)

       /* 2. 构造 struct pt_regs: 依次保存全部 64 位通用寄存器 */
       pushq   %rsi                    /* 保存调用者现场 */
       movq    8(%rsp), %rsi           /* RSI = 提取此前压栈的异常向量号 Vector */
       movq    %rdi, 8(%rsp)           /* 将 RDI 存入原本存放 Vector 的栈槽位 */
       pushq   %rdx
       pushq   %rcx
       pushq   %rax
       pushq   %r8
       pushq   %r9
       pushq   %r10
       pushq   %r11
       pushq   %rbx
       pushq   %rbp
       pushq   %r12
       pushq   %r13
       pushq   %r14
       pushq   %r15

       /* 3. 按照 System V AMD64 ABI 规范传递参数给 C 语言函数 */
       movq    %rsp, %rdi              /* 参数 1 (RDI) = 指向 struct pt_regs 栈顶指针 */
                                       /* 参数 2 (RSI) = 异常向量号 trapnr */

       /* 4. 调用 C 语言早期异常总控函数 */
       call    do_early_exception

       /* 5. 异常成功处理完成，恢复现场 */
       decl    early_recursion_flag(%rip)
       jmp     restore_regs_and_return_to_kernel
   SYM_CODE_END(early_idt_handler_common)

3.2 ``early_recursion_flag`` 递归死锁熔断机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在异常处理函数执行期间，如果发生二次故障（例如在处理 `#GP` 时代码再次触发了非法的内存读写）：
* 如果任由异常无限递归压栈，将迅速耗尽 16KB 内核栈并引发物理内存覆写；
* 内核在 ``do_early_exception()`` 中检测 ``early_recursion_flag > 1`` 时，立即判定系统处于严重递归死锁，输出紧急错误日志并执行 ``cli; hlt;`` 熔断停机，防止破坏其他物理内存。

第四幕：早期异常分发矩阵与双重错误 (#DF) 终极防护
-------------------------------------------------

在 ``arch/x86/kernel/head64.c:do_early_exception()`` 中，内核对捕获的异常进行多路解耦分发：

::

   +-----------------------------------------------------------------------------------+
   |                          do_early_exception() 多路分发状态机                       |
   |                                                                                   |
   |  [do_early_exception(struct pt_regs *regs, int trapnr)]                           |
   |            │                                                                      |
   |            ├──► 情况 A: 缺页异常 (#PF, Vector 14)                                  |
   |            │    - 判断: if (early_make_pgtable(native_read_cr2())) return;        |
   |            │    - 动作: 动态切片分配 2MB 大页并修复页表，直接成功返回!            |
   |            │                                                                      |
   |            ├──► 情况 B: AMD SEV-ES 虚拟化通信异常 (#VC, Vector 29)                 |
   |            │    - 动作: 调用 handle_vc_boot_ghcb() 执行 GHCB 半虚拟化协议协商     |
   |            │                                                                      |
   |            ├──► 情况 C: Intel TDX 虚拟化异常 (#VE, Vector 20)                      |
   |            │    - 动作: 调用 tdx_early_handle_ve() 完成安全通道拦截               |
   |            │                                                                      |
   |            └──► 情况 D: 其他常规异常 (如读取未实现 MSR 触发的 #GP 13)             |
   |                 - 动作: 调用 early_fixup_exception(regs, trapnr)                  |
   |                 - 逻辑: 检索内核异常修复表 (__ex_table), 将 RIP 重定向至安全修补点|
   +-----------------------------------------------------------------------------------+

4.1 异常修复表（``__ex_table``）与安全容错
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在内核探测某些非通用 CPU 的特定 MSR 寄存器时（如执行 ``rdmsr``），若硬件不支持该 MSR，CPU 会抛出 ``#GP`` 异常。
* 内核在链接时生成了一张只读的 **异常修复表（``__ex_table``）**；
* 当 ``early_fixup_exception()`` 捕获到 ``#GP`` 时，在表中查找引发异常的 ``RIP``，若找到对应的修补项，则将 ``regs->ip`` 直接修改为安全的容错返回点，使内核无需硬编码穷举所有 CPU 型号即可自适应探测硬件特性！

我们系统化完成了 Linux 7.2 内核从 64 位裸机跳转到通用 C 语言初始化中枢的完整平台建制：

* 早期异常捕获网已全面覆盖；
* 引导参数 ``boot_params`` 与命令行已安全存放在内核静态内存中；
* 指令流正式步入全架构通用的 C 语言总入口——**``init/main.c:start_kernel()``**！

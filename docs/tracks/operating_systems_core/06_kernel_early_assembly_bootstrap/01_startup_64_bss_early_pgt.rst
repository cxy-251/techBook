第一幕：未压缩内核汇编总入口——``startup_64`` 硬件初始化流水线
--------------------------------------------------------------

当 CPU 在自解压器的推动下执行长跳转进入 **``arch/x86/kernel/head_64.S:startup_64``** 时，操作系统内核主体正式接管整机硬件。

1.1 握手瞬间的 CPU 物理寄存器状态
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                    startup_64 入口时刻 CPU 绝对硬件物理状态                       |
   |                                                                                   |
   |  - 运行模式:      64 位长模式原生执行状态 (CR0.PE=1, CR0.PG=1, CR4.PAE=1, CS.L=1)  |
   |  - RSI 寄存器:    严格指向 4096 字节 struct boot_params 零页物理地址              |
   |  - CR3 寄存器:    挂载由自解压器生成的早期恒等映射页表 (含 0~4GB 低端映射)        |
   |  - RFLAGS 寄存器: RFLAGS.IF = 0 (全局关闭外部硬件中断)                            |
   |  - RIP 寄存器:    startup_64 物理加载基地址 (由 KASLR 随机决定)                   |
   +-----------------------------------------------------------------------------------+

1.2 初始运行栈与 GDT 描述符加载
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``head_64.S`` 的最前部指令立即执行寄存器安全保护与栈初始化：

::

   .code64
   SYM_CODE_START_NOALIGN(startup_64)
       UNWIND_HINT_END_OF_STACK

       /* 1. 保护零页指针：将 RSI 存入被调用者保存寄存器 R15，防止被 C 函数调用破坏 */
       movq    %rsi, %r15

       /* 2. 挂载汇编阶段临时调用栈 (__top_init_kernel_stack) */
       leaq    __top_init_kernel_stack(%rip), %rsp

       /* 3. 清零 GSBASE 寄存器 (切断历史段基址残留，防止意外访问 Per-CPU 变量崩溃) */
       movl    $MSR_GS_BASE, %ecx
       xorl    %eax, %eax
       xorl    %edx, %edx
       wrmsr

       /* 4. 加载正式内核 64 位 GDT 与 IDT 表 */
       call    __pi_startup_64_setup_gdt_idt

       /* 5. 远返回强制刷新 CS 寄存器为内核官方选择子 __KERNEL_CS */
       pushq   $__KERNEL_CS
       leaq    .Lon_kernel_cs(%rip), %rax
       pushq   %rax
       lretq
   .Lon_kernel_cs:

第二幕：未初始化数据段 (BSS) 与早期堆 (brk) 物理清零机制
---------------------------------------------------------

在 CPU 迈入 C 语言世界（``x86_64_start_kernel``）之前，必须执行一个至关重要的物理内存操作——**清空 BSS 段与早期动态堆区**。

2.1 为什么 C 语言运行时必须强制预先清空 BSS 段？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **C 语言标准铁律**：C 语言规范要求所有未显式初始化的全局变量和静态变量（如 ``boot_params``, ``phys_base``, ``init_top_pgt``）默认初值必须严格为 0；
2. **ELF 文件物理特性**：在编译产物中，``.bss`` 节区被标记为 ``SHT_NOBITS``，在磁盘文件中并不占用实际字节。当内核解压至物理内存时，``.bss`` 所对应的物理页充斥着上电随机噪点、旧固件调用残留或解压缓冲区的历史脏数据；
3. **严重后果**：若不清零，内核在后续访问任何未初始化指针（如全局链表头指针、自旋锁变量）时，将读取到非零野值，引发不可逆的物理内存越界与崩溃！

2.2 ``clear_bss()`` 内存清零微观时序（``arch/x86/kernel/head64.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   void __init clear_bss(void) {
       /* 1. 清空全局未初始化静态变量区: __bss_start ~ __bss_stop */
       memset(__bss_start, 0,
              (unsigned long) __bss_stop - (unsigned long) __bss_start);

       /* 2. 清空早期内存动态分配堆区: __brk_base ~ __brk_limit */
       memset(__brk_base, 0,
              (unsigned long) __brk_limit - (unsigned long) __brk_base);
   }

.. danger::
   **clear_bss 期间的日志禁令**：
   内核源码在 ``clear_bss()`` 上方明确注明：
   ``/* Don't add a printk in there. printk relies on the PDA/Per-CPU which is not initialized yet. */``
   此时绝对禁止调用 ``printk()``，因为输出系统所依赖的 Per-CPU 区域与 printk 环形缓冲区尚未完成清零初始化。

第三幕：0 号进程 (init_task) 初始内核栈与每 CPU 变量拓扑
---------------------------------------------------------

在操作系统理论中，每个执行线程都必须依附于一个任务控制块（Task Control Block）。Linux 内核的 0 号任务——**``init_task``（又称 Swapper 进程 / Idle Thread）**，是全系统中唯一一个在编译期由静态宏静态初始化的原始进程。

3.1 ``init_task`` 的栈内存物理拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位 x86_64 体系下，内核为 0 号进程静态分配了一个 16KB（4 个连续物理页）的联合体 ``union thread_union``：

::

   +-----------------------------------------------------------------------------------+
   |                       0 号进程 (init_task) 16KB 栈内存拓扑                        |
   |                                                                                   |
   |  高地址 (0xFFFF8880...4000) ┌──────────────────────────────────────────────┐        |
   |                             │ 栈顶 (Stack Top, TASK_threadsp(current_task))│ ◄─ RSP |
   |                             │ ↓ 栈向下递增增长方向 (Downwards Growth)      │        |
   |                             ├──────────────────────────────────────────────┤        |
   |                             │ 动态内核函数调用栈帧 (Stack Frames)          │        |
   |                             │                                              │        |
   |                             ├──────────────────────────────────────────────┤        |
   |                             │ struct thread_info (低地址, 记录 flags 等)   │        |
   |  低地址 (0xFFFF8880...0000) └──────────────────────────────────────────────┘        |
   +-----------------------------------------------------------------------------------+

3.2 ``common_startup_64`` 中的切栈汇编时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``arch/x86/kernel/head_64.S:common_startup_64`` 中：

::

   .Lsetup_cpu:
       /* 1. 根据当前 CPU 编号获取 Per-CPU 偏移量 (RDX) */
       movq    __per_cpu_offset(,%rcx,8), %rdx

       /* 2. 提取 0 号进程的内核栈指针并直接载入硬件栈寄存器 RSP */
       movq    current_task(%rdx), %rax
       movq    TASK_threadsp(%rax), %rsp

       /* 3. 加载内核专属 GDT 描述符表 (gdt_page) */
       subq    $16, %rsp
       movw    $(GDT_SIZE-1), (%rsp)
       leaq    gdt_page(%rdx), %rax
       movq    %rax, 2(%rsp)
       lgdt    (%rsp)
       addq    $16, %rsp

此时，CPU 彻底告别了自解压阶段的临时小栈，正式拥有了 16KB 操作系统级别的工业级内核栈！

第四幕：早期页表演进——从 ``early_top_pgt`` 到 ``init_top_pgt``
----------------------------------------------------------------

页表是虚拟内存体系的生命线。在内核早期启动过程中，页表经历了一次从“双重映射”向“高位纯净映射”的关键蜕变。

4.1 抹除低端恒等映射（``reset_early_page_tables``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **历史背景**：在自解压和早期汇编阶段，为了确保 PC 指针在低端物理地址连续执行，``early_top_pgt[0]`` 建立了 0~4GB 的恒等映射；
* **安全风险**：一旦 CPU 跳转到了高位虚拟地址（``0xFFFFFFFF8100xxxx``），低端物理映射若继续存在，会导致内核态空指针解引用（如访问地址 ``0x0``）无法被硬件捕获，掩盖严重 Bug；
* **物理清除时序**（``head64.c:reset_early_page_tables()``）：

::

   static void __init reset_early_page_tables(void) {
       /* 1. 将 early_top_pgt 的前 511 个表项 (0 ~ 510) 全量清零! */
       memset(early_top_pgt, 0, sizeof(pgd_t) * (PTRS_PER_PGD - 1));
       next_early_pgt = 0;

       /* 2. 重新刷新 CR3 寄存器，彻底销毁低端恒等映射 */
       write_cr3(__sme_pa_nodebug(early_top_pgt));
   }

通过该函数，CPU 仅保留第 511 项（``__START_KERNEL_map`` 对应的顶端 2GB 高位映射），任何对低端地址的非法访问将立即触发硬件缺页异常（#PF）！

4.2 构造 ``init_top_pgt`` 最终早期页表
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
紧接着，内核将高位映射迁移至正式的顶层页表 ``init_top_pgt``：

::

   /* 1. 清空 init_top_pgt 页表页 */
   clear_page(init_top_pgt);

   /* 2. 将 early_top_pgt 中的第 511 项 (内核镜像高位映射) 永久复制到 init_top_pgt[511] */
   init_top_pgt[511] = early_top_pgt[511];

这个 ``init_top_pgt`` 将作为母表，贯穿后续物理内存直接映射区（``PAGE_OFFSET``）与 ``vmalloc`` 区域的动态挂载。

第五幕：引导数据全量深拷贝与跨入 C 语言大门
-------------------------------------------

在内存与页表纯净化后，``head64.c`` 将低端内存中的引导数据迁移至内核内部：

5.1 ``copy_bootdata()`` 数据深拷贝
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **零页深拷贝**：将引导加载器传递的 ``real_mode_data`` 完整复制到内核静态 BSS 变量 ``boot_params``：
   ::

      memcpy(&boot_params, real_mode_data, sizeof(boot_params));
      sanitize_boot_params(&boot_params);

2. **命令行深拷贝**：从 ``boot_params.hdr.cmd_line_ptr`` 读取命令行物理地址，拷贝至 ``boot_command_line`` 数组；
3. **内存释放**：此后低端物理内存中的原始实模式数据可被操作系统全量回收再利用。

5.2 触发 C 语言总入口（``x86_64_start_kernel``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``head64.c`` 的末尾：
1. **加载早期微码（Microcode）**：调用 ``load_ucode_bsp()`` 修复 CPU 已知硬件缺陷；
2. **执行核心跃迁**：

::

   x86_64_start_reservations(real_mode_data);
   └──► x86_early_init_platform_quirks();
   └──► start_kernel(); /* 终极跨入 Linux 体系无关通用 C 语言初始化总控! */

小结与下章导读
--------------

本节深入剖析了未压缩内核汇编入口 ``startup_64``、BSS 段与早期堆物理清零机制、0 号进程（``init_task``）初始 16KB 内核栈的挂载，以及从 ``early_top_pgt`` 抹除低端映射到构建 ``init_top_pgt`` 最终早期页表的完整时序。

在进入通用内存管理之前，现代 x86_64 处理器还支持扩展的 5 级分页（5-Level Paging / LA57）机制，以支持高达 128PB 的海量虚拟寻址。

在 **第 2 节：5 级分页 (LA57) 与 4 级分页动态检测、CR4 寄存器配置与 CPUID 特性拓扑嗅探** 中，我们将深入剖析 Linux 7.2 如何在运行期动态嗅探 CPU 是否支持 LA57 特性、在 32 位低端跳板内存中动态切换 CR4.LA57 控制位，以及构建 5 级分页 PML5 拓扑的微观实现。

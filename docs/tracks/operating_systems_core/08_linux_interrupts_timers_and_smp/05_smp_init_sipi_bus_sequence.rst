第一幕：从单核孤岛到多核并行——SMP 硬件物理角色仲裁
---------------------------------------------------

现代 x86_64 服务器与桌面处理器由数十乃至数百个物理 CPU 核心构成。然而在按下电源键的第一纳秒，计算机并不是所有核心齐头并进，而是经历了一次残酷的硬件“选主”仲裁。

1.1 硬件加电选主（Hardware BSP Selection）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当主板供电芯片拉高 POWER_GOOD 信号并释放全部 CPU 核心的复位引脚（``RESET#``）时：
* **片上 Local APIC 硬件仲裁**：所有 CPU 核心内部的 Local APIC 硬件控制器通过片内系统总线展开电气仲裁；
* **决出引导核（BSP）**：竞选胜出的核心在硬件层面将其特权寄存器 **``MSR_IA32_APICBASE[8]``（BSP 标志位）自动置 1**，成为全系统的 **引导处理器（Bootstrap Processor, BSP）**；
* **挂起从属核（AP）**：其余所有未胜出的核心（``APICBASE.BSP == 0``）被称为 **应用处理器（Application Processor, AP）**。它们的内部微架构被硬件强制置于 **Wait-For-SIPI（等待启动中断）低功耗挂起状态**，其指令执行流水线与时钟全部锁死，等待 BSP 后续发送总线信号唤醒。

::

   +-----------------------------------------------------------------------------------+
   |                       多核 SMP 上电初始硬件状态机                                 |
   |                                                                                   |
   |  [系统加电复位 RESET#] ──► 全部物理核心片上 Local APIC 执行硬件总线仲裁            |
   |                                   │                                               |
   |                 ┌─────────────────┴─────────────────┐                             |
   |                 ▼                                   ▼                             |
   |     [BSP (引导处理器, CPU 0)]           [AP 1, AP 2 ... AP N-1 (从属应用核)]      |
   |  - MSR_IA32_APICBASE[8] = 1         - MSR_IA32_APICBASE[8] = 0                    |
   |  - 执行 0xFFFFFFF0 复位向量         - 进入 Wait-For-SIPI 挂起状态                 |
   |  - 引导 BIOS -> GRUB -> Linux 内核  - 流水线停跳，晶体管低功耗静默，等待唤醒      |
   +-----------------------------------------------------------------------------------+

1.2 ACPI MADT 拓扑资产勘探
~~~~~~~~~~~~~~~~~~~~~~~~~~
BSP 在进入内核通用阶段后，通过解析 ACPI **MADT（Multiple APIC Description Table）** 表，读取出系统中所有物理存在的 Local APIC 描述符，获取每个核心的物理硬件编号（Physical APIC ID），并构建全局逻辑映射数组 ``cpuid_to_apicid[]``。

第二幕：Local APIC 中断命令寄存器 (ICR) 位域微观切片与 IPI 协议
---------------------------------------------------------------

BSP 唤醒从属 AP 的唯一硬件途径，是通过自身的 Local APIC 向系统总线发射特定格式的 **核间中断（Inter-Processor Interrupt, IPI）**。

2.1 中断命令寄存器（ICR）在 xAPIC vs x2APIC 下的映射
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **传统 xAPIC 模式**：通过 MMIO 物理地址映射，分为两个 32 位寄存器：
  * ``0xFEE00300``：ICR 低 32 位（控制命令与属性）；
  * ``0xFEE00310``：ICR 高 32 位（目标物理 APIC ID，位于 Bits 56..63）；
* **现代 x2APIC 模式**：通过 64 位 MSR 寄存器直接访问：
  * **``MSR_IA32_X2APIC_ICR (0x00000830)``**：单条 64 位 ``wrmsr`` 指令原子写入，彻底消除了传统 MMIO 总线锁与多次写入的同步开销。

2.2 ICR 寄存器位域微观解构
~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   63                            32 31                          18 17 16 15 14 13 12 11 10  8 7       0
   +-------------------------------+------------------------------+-----+--+--+--+--+--+-----+---------+
   |   Destination APIC ID         | Reserved / Shorthand         |Dest |  |T |L |  |D |Dest|Deliv| Vector  |
   |   (目标 CPU 核心物理编号)     |                              |Shor |  |M |v |  |S |Mode|Mode | (启动页)|
   +-------------------------------+------------------------------+-----+--+--+--+--+--+-----+---------+

   :widths: 18 20 62

   +--------------------+------------------------+--------------------------------------------------------------------------------+
   | 字段名称           | 位域位置               | 硬件物理语义与多核唤醒设置                                                     |
   +====================+========================+================================================================================+
   | **``Vector``**     | Bits 0..7 (8 位)       | **中断/启动向量号**：在 SIPI 中表示从核启动的物理内存页号（0x00 ~ 0xFF）        |
   +--------------------+------------------------+--------------------------------------------------------------------------------+
   | **``DelivMode``**  | Bits 8..10 (3 位)      | **传递模式**：``101b (0x5)`` = **INIT IPI**；``110b (0x6)`` = **STARTUP IPI**  |

第三幕：INIT-SIPI-SIPI 硬件唤醒总线时钟时序微观推导
---------------------------------------------------

根据 Intel SDM 与 AMD APM 官方架构规范，BSP 唤醒一个处于休眠中的从属 AP 必须严格遵循 **INIT-SIPI-SIPI 状态机时序**。

3.1 唤醒状态机五步微观时钟时序（``arch/x86/kernel/smpboot.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       INIT-SIPI-SIPI 硬件唤醒总线时钟时序                         |
   |                                                                                   |
   |  [步骤 1: 发送 INIT IPI (硬件重置)]                                               |
   |  - BSP 写入 ICR: Delivery Mode = 101b (INIT), Level = 1, Vector = 0x00            |
   |  - 总线动作: 目标 AP 接收到 INIT 信号，执行片上微架构复位，进入准备启动状态        |
   |            │                                                                      |
   |            ▼ [步骤 2: 10 毫秒物理稳定延迟] (udelay(10000))                         |
   |  - BSP 循环等待 10ms，确保目标 AP 内部的 PLL 锁相环、供电电压与缓存电路彻底稳定   |
   |            │                                                                      |
   |            ▼ [步骤 3: 发送第 1 次 STARTUP IPI (SIPI-1)]                           |
   |  - BSP 写入 ICR: Delivery Mode = 110b (SIPI), Vector = (trampoline_phys >> 12)    |
   |  - 总线动作: 目标 AP 捕获 SIPI 信号，提取 Vector，强制将 CS:IP 指向跳板物理基址!  |
   |            │                                                                      |
   |            ▼ [步骤 4: 200 微秒响应监测] (udelay(200))                             |
   |  - BSP 等待 200 微秒并检测内存同步标志 (检查 AP 是否已开始执行跳板代码)           |
   |            │                                                                      |
   |            ▼ [步骤 5: 发送第 2 次 STARTUP IPI (SIPI-2)] (容错双保险)              |
   |  - 若 AP 尚未响应，BSP 再次发射一次完全相同的 SIPI 信号，杜绝偶发总线抖动导致漏检 |
   +-----------------------------------------------------------------------------------+

第四幕：1MB 以下实模式跳板内存 (trampoline_64.S) 与地址折算
------------------------------------------------------------

当 AP 接收到 SIPI 信号的那一刻，硬件发生了一次惊人的“时空倒流”——**强大的 64 位现代多核 CPU，在唤醒的第一瞬间被硬件强制降级为 16 位 8086 实模式！**

4.1 物理启动地址的数学折算公式
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
CPU 硬件在捕获 SIPI 后，直接将 ICR 传递的 8 位 ``Vector`` 填入代码段寄存器的高 8 位：

$$\mathbf{CS = 	ext{Vector} 	imes 0	ext{x100}}, \quad \mathbf{IP = 0x0000}$$

根据 16 位实模式寻址公式 $	ext{Physical\_Address} = (	ext{CS} \ll 4) + 	ext{IP}$：

$$\mathbf{	ext{Physical\_Address} = (	ext{Vector} 	imes 0	ext{x100} \ll 4) + 0 = 	ext{Vector} 	imes \mathbf{0	ext{x1000}} \equiv 	ext{Vector} 	imes 4096}$$

.. important::
   **1MB 内存屏障的物理必然性**：
   * 由于 ``Vector`` 仅有 8 个二进制位，其最大取值为 ``0xFF (255)``；
   * 因此从核能够执行的第一条指令物理地址上限为：
     $$	ext{Max\_Start\_Addr} = 255 	imes 4096 = 1,044,480	ext{ 字节} = \mathbf{1020	ext{ KB}} < \mathbf{1	ext{ MB}}$$
   * **工程铁律**：Linux 内核必须在 **1MB 以下的低端物理内存中** 开辟一块跳板内存（Trampoline），将 ``arch/x86/realmode/rm/trampoline_64.S`` 编译出的机器码安置于此，否则从核硬件根本无法寻址！

4.2 ``trampoline_64.S`` 汇编极速狂飙流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
从核在跳板内存中执行 16 位机器码，以惊人的速度完成从实模式向 64 位长模式的“四级火箭跃迁”：

::

   +-----------------------------------------------------------------------------------+
   |                       trampoline_64.S 模式跃迁汇编流水线                          |
   |                                                                                   |
   |  [1. 16 位实模式入口] (CS = Vector * 0x100, IP = 0)                              |
   |  - cli; cld;                                                                      |
   |  - lidtl tr_idt(%rip); lgdtl tr_gdt(%rip) (加载 32 位临时 GDT)                    |
   |  - movl %cr0, %eax; orl $X86_CR0_PE, %eax; movl %eax, %cr0 (开启保护模式!)        |
   |  - ljmpl $__KERNEL32_CS, $pa(startup_32) (长跳转冲刷流水线)                       |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [2. 32 位保护模式]                                                               |
   |  - movl $__KERNEL_DS, %eax; movl %eax, %ds; movl %eax, %es; movl %eax, %ss;       |
   |  - movl %cr4, %eax; orl $(X86_CR4_PAE | X86_CR4_LA57), %eax; movl %eax, %cr4;     |
   |  - movl $pa(init_top_pgt), %eax; movl %eax, %cr3 (加载 64 位正式顶级页表!)        |
   |  - movl $MSR_EFER, %ecx; rdmsr; btsl $_EFER_LME, %eax; wrmsr (使能长模式 LME!)    |
   |  - movl $CR0_STATE, %eax; movl %eax, %cr0 (开启分页 PG=1, 激活 IA-32e 长模式!)    |
   |  - ljmpl $__KERNEL_CS, $pa(startup_64)                                            |
   |            │                                                                      |
   |            ▼                                                                      |
   |  [3. 64 位原生模式 (secondary_startup_64)]                                       |
   |  - jmp secondary_startup_64 (进入正式从核 64 位总入口!)                           |
   +-----------------------------------------------------------------------------------+

第五幕：从核入队与多核握手同步机制
----------------------------------

在 BSP 唤醒 AP 的过程中，二者通过共享内存建立起严密的同步握手栅栏（Synchronization Barrier）：

::

   +-----------------------------------------------------------------------------------+
   |                           多核 SMP 上电同步握手状态机                             |
   |                                                                                   |
   |     [BSP (引导处理器)]                                [AP (从属应用处理器)]       |
   |              │                                                 │                  |
   |              ├─► 1. 准备 AP 专属数据 (栈/Per-CPU)               │                  |
   |              ├─► 2. 发送 INIT-SIPI-SIPI 总线信号 ─────────────►│ (接收并启动跳板) |
   |              │                                                 │                  |
   |              │                                                 ▼                  |
   |              │                                      3. 完成长模式穿越             |
   |              │                                      4. 挂载专属 0 号线程栈        |
   |              │                                      5. 回写 cpu_callin_map        |
   |              │◄────────────────────────────────────────────────┤                  |
   |              ▼ 6. 检测到 AP 握手响应 (Acked)                                      |
   |  [标记该 AP 在线 (CPU Online)] ──► 循环唤醒下一个 AP (直至全核上线!)              |
   +-----------------------------------------------------------------------------------+

通过这套严密的硬件总线电平协议与软件握手栅栏，Linux 7.2 内核将整机上百个独立的物理 CPU 核心牢固地凝结为一个高度协同、内存共享的现代对称多处理计算集群！

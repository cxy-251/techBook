第一幕：从 16 位实模式 IVT 到 64 位 IDT 的硬件进化史
----------------------------------------------------

在 x86 体系结构的演进历程中，中断分发机制经历了一次根本性的范式跃迁：

::

   +-----------------------------------------------------------------------------------+
   |                           x86 中断分发机制三代硬件演进                             |
   |                                                                                   |
   |  [16 位实模式: IVT 中断向量表]                                                    |
   |  - 物理位置: 固定于内存最低端 0x0000 ~ 0x03FF (1024 字节)                         |
   |  - 表项结构: 4 字节实模式远指针 (CS:IP), 无权限控制 (任何程序可随意篡改)          |
   |                                                                                   |
   |  [32 位保护模式: 8 字节 IDT]                                                      |
   |  - 物理位置: 由 IDTR 寄存器指向任意 4GB 内存                                      |
   |  - 表项结构: 8 字节门描述符 (中断门、陷阱门、任务门), 支持 DPL 权限与 TSS 硬件切栈  |
   |                                                                                   |
   |  [64 位长模式: 16 字节 IDT (IA-32e Mode)]                                         |
   |  - 物理位置: 由 64 位 IDTR 寄存器指向虚拟地址空间 (可映射至顶端只读区)            |
   |  - 表项结构: 16 字节扩展门描述符 (废除硬件任务门, 引入 IST 独立异常栈劫持机制!)   |
   +-----------------------------------------------------------------------------------+

1.1 64 位 IDT 门描述符（``gate_desc``）位域微观切片
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位模式下，每个中断门描述符占用 **16 字节（128 位）**，其微观位域排布如下：

::

   127                                                               96
   +------------------------------------------------------------------+
   |                       保留位 (Reserved, 必须置 0)                |
   +------------------------------------------------------------------+
   95                                                                64
   +------------------------------------------------------------------+
   |                目标处理函数虚拟地址高 32 位 (Offset [63:32])     |
   +------------------------------------------------------------------+
   63                               48 47 46 45 44 43    40 39 37 36 35 34 32 31           16 15            0
   +----------------------------------+--+-----+--+--------+-----+-----+------+--------------+----------------+
   | 目标处理函数地址中段 [31:16]     |P | DPL |0 | Type   | 000 | Ign | IST  | 段选择子 CS  | 地址低16位[15:0|
   |                                  |  |     |  | (0xE/F)|     |     |(3位) | (__KERNEL_CS)|                |
   +----------------------------------+--+-----+--+--------+-----+-----+------+--------------+----------------+

.. table:: 64 位门描述符关键字段物理语义
   :widths: 15 20 65

   +----------------+------------------------+--------------------------------------------------------------------------------+
   | 字段名称       | 位域位置               | 硬件物理语义与控制功能                                                         |
   +================+========================+================================================================================+
   | **``Offset``** | [15:0], [63:48], [95:64| **目标入口地址**：拼接构成 64 位中断处理函数的绝对虚拟入口地址                 |
   +----------------+------------------------+--------------------------------------------------------------------------------+
   | **``Segment``**| Bits [31:16]           | **代码段选择子**：固定为 ``__KERNEL_CS (0x10)``，硬件自动载入 64 位内核代码段  |
   +----------------+------------------------+--------------------------------------------------------------------------------+
   | **``IST``**    | Bits [34:32] (3 位)    | **中断栈表索引**：0=使用当前内核栈；1~7=硬件自动强制切换至 TSS 中对应的独立栈   |
   +----------------+------------------------+--------------------------------------------------------------------------------+
   | **``Type``**   | Bits [43:40] (4 位)    | **门类型**：``0xE`` = 64 位中断门 (Interrupt Gate)；``0xF`` = 64 位陷阱门 (Trap Gate)|
   +----------------+------------------------+--------------------------------------------------------------------------------+
   | **``DPL``**    | Bits [46:45] (2 位)    | **描述符特权级**：0=Ring 0 内核专用；3=Ring 3 用户态可触发（如 INT 3 断点）    |
   +----------------+------------------------+--------------------------------------------------------------------------------+
   | **``P``**      | Bit 47 (1 位)          | **存在位**：1=该描述符在内存中有效；0=触发 ``#NP (Vector 11)`` 段不存在异常     |
   +----------------+------------------------+--------------------------------------------------------------------------------+

第二幕：中断门 (Interrupt Gate) vs 陷阱门 (Trap Gate) 硬件分发时序
-------------------------------------------------------------------

在 x86_64 微架构中，中断门与陷阱门的根本差异体现在 **硬件响应瞬间对 RFLAGS 寄存器中断标志位（IF）的自动处理**。

2.1 硬件时钟周期级微观分发对比
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                 中断门 (Interrupt Gate) vs 陷阱门 (Trap Gate) 硬件时序            |
   |                                                                                   |
   |  [触发中断/异常信号]                                                              |
   |            │                                                                      |
   |            ▼ 1. 硬件特权级检查 (CPL <= DPL) 与 IST 栈指针加载                     |
   |  - 若触发来自 Ring 3，自动切换至 Ring 0 栈;                                       |
   |  - 若 IST != 0，强制将 RSP 替换为 TSS.ist[IST-1];                                 |
   |            │                                                                      |
   |            ▼ 2. 硬件原子压栈 (SS, RSP, RFLAGS, CS, RIP, [Error Code])             |
   |            │                                                                      |
   |            ├──► 若为【中断门 (Type 0xE)】:                                        |
   |            │    - **CPU 硬件自动将 RFLAGS.IF 清零 (CLI)**!                         |
   |            │    - 物理语义: 彻底关闭可屏蔽外部中断，防止中断嵌套引发内核栈崩溃;    |
   |            │                                                                      |
   |            └──► 若为【陷阱门 (Type 0xF)】:                                        |
   |                 - **CPU 硬件保持 RFLAGS.IF 不变**!                                |
   |                 - 物理语义: 保持原有中断使能状态，允许在处理异常时被高优先级中断抢占|
   +-----------------------------------------------------------------------------------+

2.2 DPL 特权级安全隔离铁律
~~~~~~~~~~~~~~~~~~~~~~~~~~
* **内核专用门（DPL = 0）**：绝大多数硬件中断与异常（如 `#GP 13`、`#PF 14`、定时器中断）的 DPL 设为 0。若用户态进程恶意执行汇编指令 `int $14` 试图伪造缺页异常，CPU 硬件检测到 `CPL(3) > DPL(0)`，直接拦截并就地处决，引发 `#GP(Vector 13)` 通用保护错误！
* **用户态可访问门（DPL = 3）**：内核通过 `SYSG()` 宏仅将极少数特定向量开放给 Ring 3：
  1. `#BP (Vector 3)`：断点异常（用于 GDB / LLDB 动态下断点）；
  2. `#OF (Vector 4)`：溢出异常（用于 `INTO` 指令）；
  3. `0x80 (Vector 128)`：传统 32 位兼容系统调用入口（`int $0x80`）。

第三幕：硬件级救生索——64 位 TSS 与 IST 独立异常栈机制
------------------------------------------------------

在 32 位系统中，操作系统可以使用硬件任务门（Task Gate）在发生致命错误时切换全新的 TSS 任务。但在 64 位长模式下，硬件任务切换被彻底废除。为了在内核栈发生严重故障时挽救系统，x86_64 硬件引入了 **IST（Interrupt Stack Table）**。

3.1 栈溢出（Stack Overflow）引发的三级重置（Triple Fault）死锁
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
假设内核在执行深度递归调用时，内核栈不慎耗尽并发生溢出：
1. 内核触发了缺页异常（`#PF`）或栈段错误（`#SS`）；
2. CPU 试图向当前已经损坏/溢出的栈顶压入硬件上下文（`RIP, CS, RFLAGS, RSP, SS`）；
3. 压栈操作再次触发缺页故障；
4. 异常嵌套导致 CPU 触发 **双重错误（Double Fault, `#DF`, Vector 8）**；
5. 如果 `#DF` 依然使用当前的默认内核栈，压栈第三次失败；
6. **灾难降临**：CPU 立即进入 Shutdown 状态，拉低物理 `RESET#` 引脚，整机瞬间断电黑屏重启！

3.2 IST 硬件强制换栈的救生原理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了切断上述死亡链条，Linux 7.2 内核为 `#DF` 等关键异常配置了 **IST 独立异常栈**：

::

   +-----------------------------------------------------------------------------------+
   |                           TSS.ist[] 独立异常栈硬件切换模型                        |
   |                                                                                   |
   |  [64 位 Task State Segment (TSS)]                                                 |
   |  ┌─────────────────────────────────────────────────────────────────────────────┐  |
   |  │ RSP0: 默认 Ring 0 内核栈顶 (用于用户态陷入内核)                             │  |
   |  ├─────────────────────────────────────────────────────────────────────────────┤  |
   |  │ IST[0] (Index 1): DOUBLEFAULT_STACK 栈顶 (专用 4KB 双重错误救生栈)          │  |
   |  │ IST[1] (Index 2): NMI_STACK 栈顶 (专用 4KB 不可屏蔽中断栈)                  │  |
   |  │ IST[2] (Index 3): MCE_STACK 栈顶 (专用 4KB 机器检查异常栈)                  │  |
   |  │ IST[3] (Index 4): DEBUG_STACK 栈顶 (专用 4KB 调试与硬件断点栈)              │  |
   |  │ IST[4] (Index 5): VC_STACK 栈顶 (AMD SEV 虚拟化通信专用栈)                  │  |
   |  └─────────────────────────────────────────────────────────────────────────────┘  |
   |                                      ▲                                            |
   |                                      │ 硬件检测到 gate_desc.IST = 1               |
   |                                      │                                            |
   |  [触发 #DF (Vector 8)] ──────────────┴──► CPU 强行令 RSP = TSS.ist[0] !           |
   |                                           (在崭新、绝对干净的物理栈上安全压栈!)    |
   +-----------------------------------------------------------------------------------+

通过 IST 机制，即使内核主栈被彻底破坏，CPU 也能在一个绝对纯净的 4KB 独立栈上安全运行 `#DF` 处理函数，打印出详尽的寄存器崩溃现场（Oops / Panic），彻底告别静默重启！

第四幕：IDT 全量装配流水线与只读安全加固
-----------------------------------------

在 ``start_kernel() -> trap_init()`` 中，内核完成了正式 IDT 的装配与安全加固。

4.1 ``trap_init()`` 与 ``idt_setup_traps()`` 执行时序（``idt.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           IDT 正式装配与安全加固流水线                            |
   |                                                                                   |
   |  [步骤 1: 安装标准硬件异常门 (idt_setup_traps)]                                   |
   |  - 遍历 def_idts[] 静态数组:                                                      |
   |    ► 将 0~31 号 CPU 异常向量逐个写入全局 idt_table;                               |
   |    ► 将 #DF (IST 1)、#NMI (IST 2)、#MC (IST 3)、#DB (IST 4) 绑定对应 IST 独立栈;    |
   |                                                                                   |
   |  [步骤 2: 挂载 IA32 兼容系统调用门]                                               |
   |  - 若支持 32 位兼容模式，安装 Vector 0x80 (SYSG DPL3);                            |
   |                                                                                   |
   |  [步骤 3: CPU 入口区只读映射加固 (idt_map_in_cea)]                                |
   |  - 将 idt_table 物理页映射至 CPU Entry Area (CEA) 只读虚拟地址;                   |
   |  - 执行 set_memory_ro((unsigned long)&idt_table, 1) ──► 将 IDT 物理页标记为只读!  |
   |                                                                                   |
   |  [步骤 4: 激活正式 IDT (load_current_idt)]                                        |
   |  - lidt %cs:idt_descr ──► 将只读 IDT 地址正式装入 CPU IDTR 硬件寄存器!            |
   +-----------------------------------------------------------------------------------+

4.2 为什么必须将 IDT 设置为物理只读（Read-Only）？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **黑客提权经典手法**：在传统的操作系统漏洞利用中，攻击者一旦获得内核任意内存写权限，最常用的手法就是篡改 IDT 中某个常用中断向量（如 `0x80` 或 `#PF`）的目标处理函数指针，将其指向攻击者注入的 Shellcode；
* **物理只读免疫**：Linux 7.2 通过 `set_memory_ro` 将 `idt_table` 所在的物理页表项属性中的 `R/W` 位清零。此后任何试图写入 IDT 的操作都会立即在硬件层面触发缺页异常（`#PF`），从物理上彻底封死了篡改中断门提权的攻击路径。

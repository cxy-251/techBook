第一幕：硬件与逻辑的解耦大桥——分层 IRQ Domain 映射机制
-------------------------------------------------------

在复杂的现代计算平台中，主板上并存着多种物理中断控制器（Legacy PIC 8259A、I/O APIC、PCIe MSI/MSI-X 控制器、GPIO 中断控制器与 IOMMU 中断重映射硬件）。

1.1 为什么现代多核必须引入 IRQ Domain？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **硬件中断号碰撞（Hardware IRQ Collision）**：每一个物理控制器内部的引脚编号都是从 0 开始自增的（例如 I/O APIC 的 Pin 0 和 8259A 的 IRQ 0）。如果操作系统直接使用硬件编号，系统内部将产生灾难性的命名冲突；
* **解耦抽象**：Linux 内核将硬件引脚编号称为 **``hwirq``**，将内核通用中断描述符数组的索引称为 **逻辑中断号 ``virq`` (Virtual IRQ Number)**。
* **``struct irq_domain``（中断域）**：充当 ``hwirq`` 与 ``virq`` 之间的双向翻译官。

1.2 树状分层 IRQ Domain（Hierarchical IRQ Domain）拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 x86_64 体系下，PCIe MSI 消息中断需要经过多层硬件控制器的协同解析，形成了经典的 4 级树状中断域：

::

   +-----------------------------------------------------------------------------------+
   |                          树状分层 IRQ Domain 物理映射架构                         |
   |                                                                                   |
   |  [顶层外设域: PCIe MSI / MSI-X Domain] ──► 负责解析设备专属的 MSI 消息格式        |
   |            │                                                                      |
   |            ▼ (Parent Domain)                                                      |
   |  [中介重映射域: IOMMU Interrupt Remapping Domain] ──► 负责校验中断源与分配 IRTE 表|
   |            │                                                                      |
   |            ▼ (Parent Domain)                                                      |
   |  [核心向量域: Vector Domain (Local APIC)] ──► 负责向目标 CPU 分配 IDT 向量 (0x20..)|
   |            │                                                                      |
   |            ▼                                                                      |
   |  [物理递送: CPU 硬件引脚响应并执行对应 IDT 中断服务程序]                          |
   +-----------------------------------------------------------------------------------+

1.3 ``irq_domain_alloc_irqs()`` 递归分配时序（``kernel/irq/irqdomain.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当驱动程序申请一个 MSI 中断时：
1. 顶级 MSI Domain 调用 ``domain->ops->alloc()``；
2. 递归向上调用父级 IOMMU Domain 分配中断重映射表项（IRTE）；
3. 再次递归调用 Vector Domain 在目标 CPU 的 256 位位图中分配空闲的 IDT 向量号；
4. 自顶向下装配硬件寄存器，最终返回一个全局唯一的操作系统逻辑中断号 ``virq``。

第二幕：中断上下半部 (Top/Bottom Half) 的物理分流哲学
-----------------------------------------------------

在计算机体系结构中，硬件中断处理面临着极其严苛的物理矛盾。

2.1 硬件中断上下文（HardIRQ Context）的物理死锁禁区
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. table:: 硬件中断上下文三大物理禁区
   :widths: 20 30 50

   +--------------------+------------------------+------------------------------------------------------------------------------+
   | 禁区规则           | 涉及底层调用           | 违反导致的硬件后果                                                           |
   +====================+========================+==============================================================================+
   | **绝对禁止休眠**   | ``msleep()``, 调度器   | 中断上下文没有独立的进程描述符（task_struct），休眠将导致 CPU 调度器直接崩溃 |
   +--------------------+------------------------+------------------------------------------------------------------------------+
   | **禁止获取阻塞锁** | ``mutex_lock()``       | 若互斥锁被其他阻塞线程持有，中断无法等待，引发死锁                           |
   +--------------------+------------------------+------------------------------------------------------------------------------+
   | **禁止长时间执行** | 耗时循环、复杂解析     | 硬件中断处理期间 CPU 处于关中断状态，会导致后续时钟与网络中断严重丢包与抖动  |
   +--------------------+------------------------+------------------------------------------------------------------------------+

2.2 上下半部物理分工模型
~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           中断上下半部物理执行流水线                              |
   |                                                                                   |
   |  [硬件触发中断: INTR 引脚拉高]                                                    |
   |            │                                                                      |
   |            ▼                                                                      |
   |  【上半部: Top Half / HardIRQ (关中断, 纳秒级响应)】                              |
   |  - 响应硬件: 读写外设状态寄存器，清除引脚电平 (ACK);                              |
   |  - 提取数据: 从 DMA 描述符环形缓冲区提取数据包元数据;                             |
   |  - 标记下半部: 执行 raise_softirq(NET_RX_SOFTIRQ) 置位待处理位图;                 |
   |  - 发送 EOI: 向 Local APIC 写入 EOI 寄存器;                                       |
   |  - 退出 HardIRQ ──► 开中断 (local_irq_enable)!                                    |
   |            │                                                                      |
   |            ▼                                                                      |
   |  【下半部: Bottom Half / SoftIRQ / Workqueue (开中断, 毫秒级处理)】                |
   |  - 协议栈流转: TCP/IP 校验和计算、路由检索、Socket 缓存排队;                      |
   |  - 复杂业务处理: 磁盘 I/O 事务提交、数据深拷贝、唤醒用户态等待进程!               |
   +-----------------------------------------------------------------------------------+

第三幕：软中断 (Softirq) 核心架构与 ``__do_softirq()`` 执行状态机
------------------------------------------------------------------

**软中断（Softirq）** 是 Linux 内核中响应速度最快、性能最高但受限最严的下半部机制。

3.1 10 大静态软中断向量拓扑（``include/linux/interrupt.h``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
软中断在编译期静态固定为 10 个核心向量（按优先级从高到低排列）：

::

   +-----------------------------------------------------------------------------------+
   |                            10 大静态软中断向量拓扑表                              |
   |                                                                                   |
   |  0. HI_SOFTIRQ         ──► 高优先级 Tasklet 专用处理通道                          |
   |  1. TIMER_SOFTIRQ      ──► 低精度内核定时器 (Timer Wheel) 时钟滴答分发            |
   |  2. NET_TX_SOFTIRQ     ──► 网络数据包发送驱动队列清理                             |
   |  3. NET_RX_SOFTIRQ     ──► 网络 NAPI 数据包高速轮询与协议栈接收                   |
   |  4. BLOCK_SOFTIRQ      ──► 通用块设备 I/O 完成回调处理                            |
   |  5. IRQ_POLL_SOFTIRQ   ──► 存储与网络的高性能通用轮询通道                         |
   |  6. TASKLET_SOFTIRQ    ──► 常规 Tasklet 异步回调通道                              |
   |  7. SCHED_SOFTIRQ      ──► EEVDF 调度器周期性负载均衡 (Load Balancing)            |
   |  8. HRTIMER_SOFTIRQ    ──► 高精度定时器 (High-Resolution Timers) 回调             |
   |  9. RCU_SOFTIRQ        ──► RCU (Read-Copy Update) 宽限期检测与回调垃圾回收        |
   +-----------------------------------------------------------------------------------+

3.2 ``__do_softirq()`` 微观执行时序与防饥饿熔断（``kernel/softirq.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当 CPU 从硬中断退出（``irq_exit()``）或执行 ``local_bh_enable()`` 时，若检测到当前 CPU 的 Per-CPU 变量 ``local_softirq_pending()`` 非零，立即触发 ``__do_softirq()``：

::

   +-----------------------------------------------------------------------------------+
   |                          __do_softirq() 执行状态机与防饥饿机制                     |
   |                                                                                   |
   |  [步骤 1: 现场保护与位图快照]                                                     |
   |  - local_irq_disable();                                                           |
   |  - pending = local_softirq_pending(); /* 获取当前 CPU 待处理软中断位图 (10 位) */ |
   |  - set_softirq_pending(0);            /* 原子清零，允许硬中断再次置位新中断 */    |
   |  - local_irq_enable();                /* 重新开中断! 软中断在开中断状态下执行 */  |
   |                                                                                   |
   |  [步骤 2: 遍历位图执行回调]                                                       |
   |  - while ((vec = ffs(pending))) {                                                 |
   |        softirq_vec[vec - 1].action(); /* 执行对应子系统注册的软中断函数 */        |
   |        pending &= ~(1 << (vec - 1));                                              |
   |    }                                                                              |
   |                                                                                   |
   |  [步骤 3: 循环检测与防饥饿熔断 (Anti-Starvation Guard)]                           |
   |  - local_irq_disable();                                                           |
   |  - pending = local_softirq_pending();                                             |
   |  - if (pending && --max_restart && (now - start < MAX_SOFTIRQ_TIME)) goto 步骤 1; |
   |                                                                                   |
   |  - 【熔断分流】: 若循环超过 10 次 (MAX_SOFTIRQ_RESTART) 或耗时超过 2ms:           |
   |    ► 唤醒本 CPU 专属守护线程: wakeup_softirqd() (ksoftirqd/N)!                   |
   |    ► 强制退出软中断，让出 CPU 执行权给用户态进程，彻底消除软中断风暴饥饿!         |
   +-----------------------------------------------------------------------------------+

第四幕：Tasklet 串行化机制与设计演进
------------------------------------

**Tasklet** 是基于 ``HI_SOFTIRQ`` 与 ``TASKLET_SOFTIRQ`` 构建的一套面向设备驱动的简易下半部封装。

4.1 Tasklet 的数据结构与单核互斥铁律
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **``struct tasklet_struct``**：
  包含 ``state``（状态位图）、``count``（引用计数）、``func``（回调函数）与 ``data``（参数）；
* **单核并发安全铁律**：
  在多核 SMP 环境下，**同一个 Tasklet 实例绝对禁止在多个 CPU 上并发执行！**
  * 当 CPU A 正在执行某个 Tasklet 时，其 ``state`` 被置位 ``TASKLET_STATE_RUN``；
  * 若 CPU B 同时调度到了该 Tasklet，检测到 ``TASKLET_STATE_RUN`` 后会立即跳过该 Tasklet 并将其重新插入未决链表，确保驱动代码无需编写复杂的多核重入自旋锁。

第五幕：并发托管工作队列 (cmwq) 架构与进程上下文异步执行
--------------------------------------------------------

虽然软中断和 Tasklet 极为高效，但它们依然运行在**中断上下文（Interrupt Context）**中，绝对无法休眠。为了让下半部能够调用耗时 I/O、获取互斥锁（Mutex）与分配内存，Linux 提供了 **工作队列（Workqueue）**。

5.1 工作队列 vs 软中断全维度对比
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. table:: Linux 核心下半部机制技术特性横向对比
   :widths: 20 25 25 30

   +------------------+------------------------+------------------------+------------------------------------------------+
   | 特性维度         | 软中断 (Softirq)       | Tasklet                | 并发托管工作队列 (cmwq)                        |
   +==================+========================+========================+================================================+
   | **执行上下文**   | 中断上下文 (软中断)    | 中断上下文 (软中断)    | **进程上下文 (内核工作线程 kworker)**          |
   +------------------+------------------------+------------------------+------------------------------------------------+
   | **能否休眠**     | **绝对禁止**           | **绝对禁止**           | **完全允许** (可调用 mutex, sleep, I/O)        |
   +------------------+------------------------+------------------------+------------------------------------------------+
   | **多核并发能力** | 支持同类型在多核并发   | 同一实例单核串行化     | 多工作者线程池高并发执行                       |
   +------------------+------------------------+------------------------+------------------------------------------------+
   | **典型应用场景** | 网络收发 (NAPI)、时钟  | 老旧设备驱动异步回调   | 文件系统回写、设备探测、异步 I/O 事务          |
   +------------------+------------------------+------------------------+------------------------------------------------+

5.2 cmwq (Concurrency Managed Workqueue) 动态并发状态机（``kernel/workqueue.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Linux 7.2 采用先进的 **cmwq（并发托管工作队列）** 模型，彻底消除了传统工作队列每个驱动独占线程造成的系统线程膨胀：

::

   +-----------------------------------------------------------------------------------+
   |                           cmwq 动态并发线程池管理模型                             |
   |                                                                                   |
   |  [驱动提交工作: queue_work(system_wq, &work)]                                     |
   |            │                                                                      |
   |            ▼ 挂载至本 CPU 专属的 worker_pool 链表                                 |
   |  [worker_pool (每个 CPU 拥有 Normal 与 HighPri 两个独立线程池)]                   |
   |            │                                                                      |
   |            ▼ 唤醒空闲工作者线程 (kworker/N:M) 执行 work->func()                   |
   |  ┌─────────────────────────────────────────────────────────────────────────────┐  |
   |  │ 【cmwq 动态并发自适应调节状态机】                                           │  |
   |  │                                                                             │  |
   |  │ 1. 运行中: kworker 处于 Running 状态 ──► 占据当前 CPU 1 个并发槽位;         │  |
   |  │                                                                             │  |
   |  │ 2. 阻塞时: kworker 调用 mutex_lock() 或 I/O 陷入 Sleep:                     │  |
   |  │    ► 调度器钩子 wq_worker_sleeping() 立即感知当前 CPU 活跃工作者归零!       │  |
   |  │    ► 自动在线程池中唤醒下一个备用 kworker，接替执行链表中的下一个 work!     │  |
   |  │                                                                             │  |
   |  │ 3. 唤醒时: 阻塞解除，调度器钩子 wq_worker_waking() 重新将并发槽位纳入统筹!  │  |
   |  └─────────────────────────────────────────────────────────────────────────────┘  |
   +-----------------------------------------------------------------------------------+

通过 cmwq 动态感知内核睡眠与唤醒的精巧设计，Linux 7.2 保证了即使某个工作项发生长时间磁盘 I/O 阻塞，也不会拖垮整个 CPU 的异步工作队列处理能力！

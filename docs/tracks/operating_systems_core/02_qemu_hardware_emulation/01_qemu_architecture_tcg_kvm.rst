========================================================================================
第 1 节：QEMU 核心架构：TCG 动态二进制翻译状态机与 KVM 内核虚拟机硬件加速原理
========================================================================================

.. note::
   **前置背景与体系结构坐标**
   * **体系结构基准**：承接模块 01 中关于 x86_64 处理器物理寄存器拓扑、硬件中断/异常分发与快速系统调用（SYSCALL）的底层电路级定义。
   * **核心使命**：解构在物理计算机上电之前，虚拟机监视器（VMM）如何在宿主机软件中构建出一个完整的 x86_64 物理处理器与硬件总线系统。深入剖析纯软件全系统模拟的 **TCG (Tiny Code Generator) 动态二进制翻译状态机** 与翻译块（TranslationBlock）高速缓存；对比解构基于现代处理器硬件虚拟化扩展（Intel VT-x / AMD-V）的 **Linux KVM 内核驱动模型**、VCPU 线程状态机与 ``ioctl(KVM_RUN)`` / VM-Exit 硬件退出捕获微观循环。

第一幕：硬件虚拟化的两种世界观——纯软件模拟 vs 硬件原生存化
---------------------------------------------------------

在计算机体系结构中，要在一个已经运行的操作系统（宿主机，Host OS）之上运行另一个完整的操作系统（客户机，Guest OS），存在两条根本不同的工程路线：

::

   [路线 A：纯软件全系统模拟 (TCG 引擎)]
   客户机 x86_64 指令 ──► [TCG 前端反编译] ──► TCG 中间表示 (IR) ──► [TCG 后端生成] ──► 宿主机机器码 (ARM64/x86) ──► 宿主 CPU 执行

   [路线 B：硬件辅助虚拟化 (KVM + VT-x 引擎)]
   客户机 x86_64 指令 ──► [Intel VMX 非根模式直接下发物理执行] ──► 遇到敏感硬件操作 ──► 触发 VM-Exit 硬件陷出 ──► QEMU/KVM 拦截模拟

1.1 纯软件全系统模拟（Full Emulation）的物理本质
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当宿主机与客户机的体系结构不一致时（例如在 Apple Silicon ARM64 芯片的 Mac 上模拟运行 x86_64 Linux 7.2 内核），硬件无法直接执行客户机指令，必须采用全软件模拟：
* **指令翻译开销**：每一条客户机机器码必须先由模拟器在内存中逐字节解码，转换为中间表示，再重新编译为宿主机的原生机器码；
* **寄存器映射**：客户机的物理寄存器（如 ``RAX``, ``CR3``, ``RFLAGS``）退化为宿主机内存中一个名为 ``CPUX86State`` 的 C 语言结构体字段；
* **物理代价**：纯解释执行的运行效率通常仅有物理硬件原生速度的 **1% ~ 5%**，即使引入动态即时编译（JIT），性能也通常限制在 **10% ~ 30%**。

1.2 硬件辅助虚拟化（Hardware-Assisted Virtualization）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当宿主机与客户机体系结构一致（如 x86_64 物理机上运行 x86_64 虚拟机）且物理 CPU 支持虚拟化扩展（Intel VT-x / AMD-V）时：
* 物理 CPU 硬件引入了全新的运行模式：**VMX Root Operation（根模式，宿主内核运行态）** 与 **VMX Non-Root Operation（非根模式，客户机操作系统运行态）**；
* 客户机绝大部分非特权计算指令（加减乘除、内存读写）**100% 以裸机全速直接在物理 CPU 核心上执行**，执行速度接近 **95% ~ 99%**；
* 仅当客户机试图执行修改物理硬件状态的敏感操作（如修改 ``CR3`` 切换页表、执行 ``IN/OUT`` 读写主板 I/O 端口、访问未映射的物理 MMIO 地址）时，物理 CPU 硬件自动冻结客户机，保存现场并触发 **VM-Exit（虚拟机退出）**，将控制权交回宿主机 Linux KVM 内核模块。

第二幕：QEMU TCG 动态二进制翻译状态机微观全流程
-----------------------------------------------

在 QEMU 源码库（``/Volumes/LinuxKernel/qemu``）中，纯软件模拟核心由 **TCG (Tiny Code Generator)** 子系统承担。

2.1 双阶段编译流水线：从客户机机器码到宿主原生指令
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
TCG 并不直接将源架构指令硬翻译为目标架构指令，而是采用经典的编译器两段式架构（前端生成中间表示，后端分配寄存器并生成机器码）：

::

   +-----------------------------------------------------------------------------------+
   |                                 TCG 动态编译流水线                                |
   |                                                                                   |
   |  [客户机 x86_64 机器码]  (如: add %rbx, %rax)                                     |
   |            │                                                                      |
   |            ▼ 阶段一：TCG 前端翻译器 (target/i386/tcg/translate.c)                 |
   |  [TCG 平台无关中间表示 (IR)]                                                     |
   |     - ld_i64 tmp0, env, offsetof(CPUX86State, regs[R_EBX])                       |
   |     - ld_i64 tmp1, env, offsetof(CPUX86State, regs[R_EAX])                       |
   |     - add_i64 tmp1, tmp1, tmp0                                                    |
   |     - st_i64 tmp1, env, offsetof(CPUX86State, regs[R_EAX])                       |
   |            │                                                                      |
   |            ▼ 阶段二：TCG 后端代码生成器 (tcg/tcg.c / tcg/aarch64/ / tcg/i386/)    |
   |  [宿主机原生机器码 (Host Native ASM)] (写入 JIT 执行缓冲区 CodeGenBuffer)          |
   |     - ARM64: ldr x0, [x19, #offset_rbx]; ldr x1, [x19, #offset_rax]; add x1, x1, x0; ...|
   +-----------------------------------------------------------------------------------+

2.2 翻译块（TranslationBlock, TB）与基本块直接链化（Direct Block Chaining）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了避免每执行一条指令就进行一次编译，TCG 以 **基本块（Basic Block）** 为最小翻译单元构建 **TranslationBlock (TB)**：
* **划分边界**：一段连续的指令序列，只有一个入口和一个出口，遇到任何跳转、分支（``JMP``, ``JNE``, ``CALL``, ``RET``）或特权指令时结束该 TB；
* **代码缓存（JIT Cache）**：生成的宿主机机器码存放在一块巨大的可执行内存区域（``code_gen_buffer``，通常数百 MB），并通过物理 PC 地址构建哈希表快速索引。

.. important::
   **基本块直接链化优化（Direct Block Chaining）**：
   在最初的设计中，每个 TB 执行完毕后必须返回 QEMU 的中央调度器（``cpu_exec()``）查询下一个 TB 的哈希表，导致严重的上下文切换开销。
   TCG 采用动态补丁技术：当 TB_A 确定会跳转至 TB_B 时，TCG 后端在运行时直接覆写 TB_A 末尾的宿主跳转指令机器码（``tb_set_jmp_target``），将其直连到 TB_B 在宿主内存中的入口。多个 TB 在宿主内存中形成一条高速执行链，完全绕过解释器主循环。

2.3 软件 MMU（SoftMMU）与快速 TLB 查询机制
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在全系统模拟中，客户机的操作系统认为自己在操作物理内存，但实际上客户机物理地址（GPA, Guest Physical Address）最终必须映射到 QEMU 进程在宿主机中的虚拟地址（HVA, Host Virtual Address）。

在 ``accel/tcg/cputlb.c`` 中，QEMU 为每个虚拟 CPU 维护了一个纯软件构建的 **SoftMMU TLB 快速缓存矩阵**：

.. math::

   	ext{TLB\_Index} = (	ext{Guest\_VA} \gg 12) \ \& \ (	ext{CPU\_TLB\_SIZE} - 1)

* **快速命中路径（Fast Path）**：生成的宿主机机器码直接提取 GVA 的哈希索引，比对 ``CPUTLBEntry`` 中的 Tag。若命中且权限匹配，直接将 GVA 加上物理偏移转换得到 HVA 裸内存指针，实现纳秒级单指令读取；
* **慢速未命中路径（Slow Path）**：若未命中，生成的代码跳转进入 C 语言函数 ``helper_le_ld_mmu()``，调用虚拟 MMU 递归遍历客户机多级页表（PGD->P4D->PUD->PMD->PTE），建立新的 TLB 表项；若检测到访问地址属于虚拟外设（如显存或网卡寄存器），则分发给对应的虚拟设备 I/O 回调函数。

第三幕：KVM 硬件加速内核模块与 VCPU 线程模型
---------------------------------------------

在支持硬件虚拟化的 Linux 宿主机上，QEMU 转换为纯粹的 **用户态设备模型与控制平面**，而将 CPU 与内存虚拟化全权委托给 Linux 内核中的 **KVM (Kernel-based Virtual Machine)** 模块。

3.1 Linux ``/dev/kvm`` 字符设备接口与三层句柄拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
QEMU 与 KVM 之间的交互完全基于标准的 Linux VFS 字符设备文件 ``/dev/kvm`` 与 ``ioctl`` 系统调用体系：

::

   +-----------------------------------------------------------------------------------+
   |                                 KVM 三层句柄拓扑体系                              |
   |                                                                                   |
   |  [系统全局句柄 (System FD)]                                                       |
   |  kvm_fd = open("/dev/kvm", O_RDWR);                                               |
   |  (负责探测硬件虚拟化扩展支持、获取全局内存槽数量上限与 API 版本)                   |
   |            │                                                                      |
   |            ▼ ioctl(kvm_fd, KVM_CREATE_VM, 0);                                     |
   |  [虚拟机实例句柄 (VM FD)]                                                         |
   |  vm_fd = ...                                                                      |
   |  (代表一台完整的虚拟计算机，负责管理 EPT/NPT 嵌套页表、分配客户机物理内存槽)       |
   |            │                                                                      |
   |            ▼ ioctl(vm_fd, KVM_CREATE_VCPU, vcpu_id);                              |
   |  [虚拟 CPU 句柄 (VCPU FD)]                                                        |
   |  vcpu_fd = ...                                                                    |
   |  (代表一个独立的 CPU 计算核心，对应一个物理线程与独立的硬件 VMCS 控制结构)          |
   +-----------------------------------------------------------------------------------+

3.2 QEMU 中 VCPU 线程的事件主循环
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 QEMU 源码 ``accel/kvm/kvm-all.c`` 与 ``system/cpus.c`` 中，每一个虚拟 CPU（VCPU）在宿主机中都被创建为一个标准的 **POSIX 操作系统线程（pthread）**：

::

   static void *kvm_cpu_thread_fn(void *arg) {
       CPUState *cpu = arg;
       int r;

       rcu_register_thread();
       qemu_mutex_lock_iothread();
       qemu_thread_get_self(cpu->thread);
       cpu->created = true;
       qemu_cond_signal(&qemu_cpu_cond);

       /* VCPU 核心执行主死循环 */
       do {
           if (cpu_can_run(cpu)) {
               r = kvm_cpu_exec(cpu);  /* 陷入内核态运行客户机 */
               if (r == EXCP_DEBUG) {
                   cpu_handle_guest_debug(cpu);
               }
           }
           qemu_wait_io_event(cpu);    /* 等待异步 I/O 事件唤醒 */
       } while (!cpu->unplug || cpu_can_run(cpu));

       return NULL;
   }

第四幕：VM-Exit 硬件退出与共享内存区 ``struct kvm_run`` 交互
------------------------------------------------------------

当 VCPU 线程调用 ``ioctl(vcpu_fd, KVM_RUN, 0)`` 时，CPU 从宿主内核态切换到 VMX 非根模式，开始在物理硬件上直接执行客户机代码。

4.1 Intel VT-x 硬件控制结构（VMCS）与 VM-Exit 诱因
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每个 VCPU 在物理内存中绑定一个 4KB 大小的 **VMCS (Virtual Machine Control Structure)** 硬件控制页。VMCS 严格记录了客户机与宿主机的物理寄存器状态以及**退出控制条件（VM-Exit Controls）**。

当客户机内部发生以下敏感事件时，物理 CPU 硬件自动暂停执行，将退出原因写入 VMCS，并产生 VM-Exit 退出到宿主机 KVM：

.. table:: 常见 VM-Exit 退出原因与硬件拦截分类
   :widths: 20 25 25 30

   +--------------------------+-----------------------+--------------------------+------------------------------------------------+
   | 退出原因枚举 (Exit Reason)| 触发物理操作          | 硬件发生场景             | 宿主机 KVM / QEMU 处理行为                     |
   +==========================+=======================+==========================+================================================+
   | ``EXIT_REASON_CPUID``    | 客户机执行 ``CPUID``  | 嗅探处理器特性标志       | KVM 拦截并根据 QEMU 配置返回虚拟化特性掩码     |
   +--------------------------+-----------------------+--------------------------+------------------------------------------------+
   | ``EXIT_REASON_IO_INSTR`` | 客户机执行 ``IN/OUT`` | 读写传统主板端口 (0x00..) | 陷入 QEMU 设备模型（如模拟 8259A/串口/PCI 配置）|
   +--------------------------+-----------------------+--------------------------+------------------------------------------------+
   | ``EXIT_REASON_EPT_VIOL`` | 访问未映射 GPA 物理页 | 访问 MMIO 硬件映射区域   | 触发 MMIO 设备读写模拟或动态分配 EPT 物理宿主页|
   +--------------------------+-----------------------+--------------------------+------------------------------------------------+
   | ``EXIT_REASON_HLT``      | 客户机执行 ``HLT``    | CPU 空闲等待中断         | KVM 将 VCPU 线程置于睡眠状态，让出宿主机 CPU   |
   +--------------------------+-----------------------+--------------------------+------------------------------------------------+

4.2 零拷贝共享内存区：``struct kvm_run`` 微观通信
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
每次 VM-Exit 如果都通过复杂的数据拷贝返回用户态，将造成巨大的系统调用开销。KVM 与 QEMU 之间采用高效的 **共享内存环元（Shared Memory Mapping）**：

在初始化时，QEMU 调用 ``mmap(NULL, mmap_size, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu_fd, 0)``，将内核态维护的 ``struct kvm_run`` 结构体直接映射到 QEMU 进程地址空间。

::

   +-----------------------------------------------------------------------------------+
   |                    QEMU (用户态) 与 KVM (内核态) 共享内存结构                      |
   |                                                                                   |
   |  struct kvm_run {                                                                 |
   |      __u32 exit_reason;   /* 退出原因: KVM_EXIT_IO / KVM_EXIT_MMIO / ... */        |
   |      __u8  ready_for_interrupt_injection;                                         |
   |      ...                                                                          |
   |      union {                                                                      |
   |          /* KVM_EXIT_IO 端口访问数据包 */                                         |
   |          struct {                                                                 |
   |              __u8  direction; /* 0=读 (IN), 1=写 (OUT) */                         |
   |              __u8  size;      /* 1, 2, 4 字节 */                                  |
   |              __u16 port;      /* 端口号，如 0x3F8 (串口) / 0xCF8 (PCI 配置) */    |
   |              __u32 count;     /* 字符串 I/O 计数 */                               |
   |              __u64 data_offset; /* 数据在 kvm_run 映射区内的偏移地址 */          |
   |          } io;                                                                    |
   |          /* KVM_EXIT_MMIO 内存映射 I/O 数据包 */                                  |
   |          struct {                                                                 |
   |              __u64 phys_addr; /* 访问的客户机物理地址 GPA */                      |
   |              __u8  data[8];   /* 写入的数据或等待填充的读取数据 */                |
   |              __u32 len;       /* 读写长度 (1..8 字节) */                          |
   |              __u8  is_write;  /* 1=写, 0=读 */                                    |
   |          } mmio;                                                                  |
   |      };                                                                           |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

4.3 设备模拟分发微观时序
~~~~~~~~~~~~~~~~~~~~~~~~
1. **VM-Exit 触发**：客户机试图向串口端口 ``0x3F8`` 输出字符 ``'A'``（执行指令 ``outb %al, $0x3F8``）；
2. **KVM 内核拦截**：物理 CPU 退出到 KVM 内核，KVM 检查发现该端口属于用户态设备模型，将 ``exit_reason`` 填充为 ``KVM_EXIT_IO``，将 ``port=0x3F8``、``data='A'`` 写入 ``struct kvm_run``，随后 ``ioctl(KVM_RUN)`` 正常返回用户态；
3. **QEMU 用户态分发**：QEMU 的 VCPU 线程被唤醒，从 ``struct kvm_run`` 中读取数据，通过内部虚拟总线路由将数据送达虚拟串口设备结构体（``SerialState``）；
4. **再次进入**：QEMU 处理完毕后，再次调用 ``ioctl(KVM_RUN)``，物理 CPU 恢复执行客户机下一条指令。

第五幕：TCG vs KVM 核心数据结构与性能对比
-----------------------------------------

.. table:: QEMU 纯软件 TCG 模式与 KVM 硬件加速模式全景对比
   :widths: 20 40 40

   +--------------------------+-------------------------------------+-----------------------------------------------+
   | 维度                     | TCG (Tiny Code Generator) 模式      | KVM (Kernel-based Virtual Machine) 模式       |
   +==========================+=====================================+===============================================+
   | **执行载体**             | 宿主用户态 JIT 动态翻译机器码       | 物理 CPU VMX 非根模式直接原生执行             |
   +--------------------------+-------------------------------------+-----------------------------------------------+
   | **虚拟 CPU 寄存器实体**  | 宿主内存堆中的 ``CPUX86State`` 结构体| 物理 CPU 真实硬件寄存器 + 硬件 VMCS 控制页    |
   +--------------------------+-------------------------------------+-----------------------------------------------+
   | **内存地址翻译**         | SoftMMU 软件哈希表 + C 语言慢速查表 | 物理 MMU 硬件二级转换 (Intel EPT / AMD NPT)   |
   +--------------------------+-------------------------------------+-----------------------------------------------+
   | **跨体系结构支持**       | 支持（可在 ARM64 上模拟 x86/MIPS）  | 不支持（宿主机与客户机必须保持同构 ISA）      |
   +--------------------------+-------------------------------------+-----------------------------------------------+
   | **算术运算性能**         | ~ 10% - 30% 物理机速度              | ~ 95% - 99% 物理机速度 (几乎零损耗)           |
   +--------------------------+-------------------------------------+-----------------------------------------------+

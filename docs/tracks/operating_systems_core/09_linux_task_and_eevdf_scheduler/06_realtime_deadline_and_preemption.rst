第一幕：Linux 调度类层次拓扑与优先级金字塔
------------------------------------------

在 Linux 内核调度架构中，多调度器并非平级竞争，而是构成了一条严格的 **单向绝对优先链表（Scheduling Hierarchy）**。

1.1 调度类的绝对霸权等级链
~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``kernel/sched/sched.h`` 中，内核通过函数指针表将所有调度类串联为降序链表：

::

   +-----------------------------------------------------------------------------------+
   |                           Linux 内核调度类绝对优先级链表                          |
   |                                                                                   |
   |  [stop_sched_class]       ──► 停机与 CPU 迁移最高特权类 (处理热插拔/负载均衡)     |
   |         │                                                                         |
   |         ▼                                                                         |
   |  [dl_sched_class]         ──► SCHED_DEADLINE (硬实时，基于最早物理截止时间 EDF)   |
   |         │                                                                         |
   |         ▼                                                                         |
   |  [rt_sched_class]         ──► SCHED_FIFO / SCHED_RR (软实时，100 级静态优先级)     |
   |         │                                                                         |
   |         ▼                                                                         |
   |  [fair_sched_class]       ──► SCHED_NORMAL / SCHED_BATCH (通用公平，EEVDF 调度器)  |
   |         │                                                                         |
   |         ▼                                                                         |
   |  [idle_sched_class]       ──► 0 号任务 / Idle Thread (系统无事可做时的待机死循环) |
   +-----------------------------------------------------------------------------------+

.. important::
   **霸权执行铁律**：
   在每次触发 ``schedule()`` 挑选下一个任务时，调度器自顶向下遍历该链表。**只要高阶调度类中存在哪怕 1 个处于就绪态的任务，低阶调度类（包括 EEVDF）中的所有任务都将绝对被阻塞，得不到任何 CPU 时间片！**

1.2 优先级数字与反转物理映射
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``include/linux/sched/prio.h`` 中，内核为所有进程规定了 $0 \sim 139$ 的统一数值优先级（**数值越小，优先级越高**）：

.. table:: Linux 全局进程优先级分布图
   :widths: 20 25 25 30

   +======================+======================+======================+==========================================+
   | 调度类别             | 内核内部 ``p->prio`` | 用户态视角数值       | 调度管理实体                             |
   +======================+======================+======================+==========================================+
   | **SCHED_DEADLINE**   | **-1** (逻辑最高)    | 独立参数三元组       | ``dl_sched_class`` (EDF 算法)            |
   +----------------------+----------------------+----------------------+------------------------------------------+
   | **POSIX Real-Time**  | **0 ~ 99**           | **99 ~ 1** (反向映射)| ``rt_sched_class`` (FIFO/RR 优先级位图)  |
   +----------------------+----------------------+----------------------+------------------------------------------+
   | **Normal (EEVDF)**   | **100 ~ 139**        | **Nice -20 ~ +19**   | ``fair_sched_class`` (虚拟运行时间)      |
   +----------------------+----------------------+----------------------+------------------------------------------+

第二幕：软实时基石——``SCHED_FIFO`` 与 ``SCHED_RR`` 机制
-------------------------------------------------------

POSIX 实时调度属于“软实时”（Soft Real-Time）范畴，适用于音频播放、工业 PLC 轮询及高频网络包收发。

2.1 100 级位图优先级数组（``struct rt_prio_array``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了在纳秒级时间内挑选出最高优先级的实时任务，``rt_rq`` 维护了位图索引数组：

::

   struct rt_prio_array {
       DECLARE_BITMAP(bitmap, MAX_RT_PRIO + 1); /* 100 位的位图 (0..99) */
       struct list_head queue[MAX_RT_PRIO];     /* 每个优先级一条独立双向链表 */
   };

* **单指令 $O(1)$ 查找**：调度器通过 ``sched_find_first_bit(array->bitmap)`` 函数，底层直接映射到 x86_64 处理器的 **``BSR``（Bit Scan Reverse）或 ``TZCNT``** 硬件汇编指令，在 **1 个时钟周期** 内瞬间定位到当前最高优先级的非空链表！

2.2 ``SCHED_FIFO`` 与 ``SCHED_RR`` 的微观行为差异
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **``SCHED_FIFO``（先入先出）**：
  * 无时间片概念。一旦抢占到 CPU，除非主动调用 ``sleep()``/``sched_yield()`` 或被更高优先级的实时任务抢占，否则**永远霸占 CPU 运行**；
* **``SCHED_RR``（循环轮转）**：
  * 分配固定时间片（默认 ``RR_TIMESLICE = 100ms``）；
  * 在时钟中断 ``task_tick_rt()`` 中递减时间片；当时间片归零时，重置时间片并将该任务移至**同优先级链表的末尾**，允许同优先级的其他 RR 任务轮流执行。

2.3 实时带宽熔断保护（RT Throttling）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了防止编写有死循环 Bug 的实时进程将整台机器锁死，Linux 7.2 内置了 **实时带宽看门狗（``sched_rt_runtime_us``）**：
* 默认在每 1 秒（``sched_rt_period_us = 1000000``）周期内，所有实时任务占用的 CPU 时间上限为 **0.95 秒（950,000 微秒）**；
* 强制为普通 EEVDF 任务保留 **50ms**。一旦 RT 耗尽 950ms 预算，立即触发节流（Throttling），强制让出 CPU 直到下一个周期开始。

第三幕：硬实时之巅——``SCHED_DEADLINE``、CBS 与 EDF 算法
-------------------------------------------------------

对于自动驾驶传感器融合、航空航天航控机及高精度电机控制，简单的优先级已无法满足严苛的时序要求。Linux 7.2 内核提供了工业级硬实时算法——**``SCHED_DEADLINE``**。

3.1 参数三元组 $(C_i, D_i, T_i)$ 模型
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                       SCHED_DEADLINE 任务周期性物理时序                           |
   |                                                                                   |
   |  [周期 1 起点] ──────────────────────► [相对截止时间 D_i] ────────► [周期 1 终点 T_i] |
   |  ├───────────────────┬───────────────────────┤                    │               |
   |  │ 实际运行时间 C_i  │       空闲等待区      │ (必须在此前完成!)  │               |
   |  └───────────────────┴───────────────────────┘                    │               |
   |                                                                   ▼               |
   |                                                           [周期 2 起点 (T_i)]     |
   +-----------------------------------------------------------------------------------+

* **$C_i$（Runtime / 预算）**：该任务在单周期内所能消耗的物理 CPU 时间上限；
* **$D_i$（Deadline / 相对截止时间）**：自周期启动起，任务必须完成计算的极限物理时间；
* **$T_i$（Period / 周期）**：任务周期性被唤醒的物理时间跨度（通常 $C_i \le D_i \le T_i$）。

3.2 恒定带宽服务器（CBS / Constant Bandwidth Server）与 EDF 决策
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **EDF（Earliest Deadline First）全局最优决策**：
   * 所有就绪的 DEADLINE 任务按其 **绝对截止时间（Absolute Deadline = 唤醒时刻 + $D_i$）** 组织在专用红黑树 ``dl_rq->rb_root`` 中；
   * 调度器每次挑选绝对截止时间最近的任务运行。数学上已严格证明，在单核不可抢占/可抢占环境下，EDF 是最优实时调度算法。
2. **CBS 带宽隔离保护**：
   * 任务运行时每消耗 1 纳秒，递减 ``dl_se->runtime``；
   * 若任务在当前周期用尽了 $C_i$ 预算，CBS 立即强制将其推入 ``throttled`` 队列，剥夺运行权，直到物理时钟到达下一个周期起点 $T_i$ 触发高精度定时器重置预算！

3.3 带宽准入控制（Admission Control 不等式）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
任何进程尝试切换为 ``SCHED_DEADLINE`` 时，内核必须运行严格的数学准入测试：

$$\mathbf{\sum_{i=1}^N \frac{C_i}{\min(D_i, T_i)} \le U_{\max} = M 	imes 	ext{sched\_rt\_runtime\_us} / 	ext{sched\_rt\_period\_us}}$$

其中 $M$ 为当前 CPU 核心数。一旦新任务的加入会导致系统总利用率突破安全阈值（默认 95%），系统调用 ``sched_setattr()`` 立即强硬返回 **``-EBUSY``**，从物理法则上确保已注册的实时任务永不超时（Zero Deadline Overrun）！

第四幕：微观状态机——抢占计数器 ``preempt_count`` 硬件拓扑
---------------------------------------------------------

操作系统要实现任意时刻的即时抢占，必须具备精密的上下文自省能力。内核在当前 CPU 的任务线程结构体中维护着一个核心整型变量——**``preempt_count``**。

4.1 32 位 ``preempt_count`` 物理位图解构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                         32 位 preempt_count 内部物理布局                          |
   |                                                                                   |
   |   31            20 19          16 15           8 7                               0|
   |  ┌────────────────┬──────────────┬──────────────┬────────────────────────────────┐|
   |  │   NMI Context  │   HARDIRQ    │   SOFTIRQ    │      PREEMPT DISABLE COUNT     │|
   |  │   (Bit 20, 1b) │ (Bit 16~19)  │ (Bit 8~15)   │  (Bit 0~7, 0~255 锁嵌套层数)   │|
   |  └────────────────┴──────────────┴──────────────┴────────────────────────────────┘|
   +-----------------------------------------------------------------------------------+

* **``Bit 0 ~ 7 (PREEMPT_MASK)``**：记录当前代码显式调用 ``preempt_disable()`` 或获取自旋锁（``spin_lock``）的嵌套深度；
* **``Bit 8 ~ 15 (SOFTIRQ_MASK)``**：记录软中断 Softirq 执行或 ``local_bh_disable()`` 的嵌套层数；
* **``Bit 16 ~ 19 (HARDIRQ_MASK)``**：记录硬件中断 ISR 处理程序的嵌套深度；
* **``Bit 20 (NMI_MASK)``**：标识不可屏蔽中断 NMI 处理上下文。

4.2 抢占触发铁律与微观时序
~~~~~~~~~~~~~~~~~~~~~~~~~~
.. important::
   **内核态安全抢占的三大先决条件**：
   1. **``preempt_count == 0``**（当前未持有任何自旋锁，且不在任何中断或下半部上下文中）；
   2. **``!irqs_disabled()``**（本地 CPU 物理中断处于开启状态）；
   3. **``TIF_NEED_RESCHED`` 置位**（存在更高优先级任务请求调度）。

在中断返回内核态（``ret_to_kernel``）或调用 ``preempt_enable()`` 释放最后一把自旋锁时，若上述条件同时成立，内核立即调用 **``preempt_schedule()``** 完成瞬时上下文切换！

第五幕：动态内核抢占架构——``PREEMPT_DYNAMIC`` 与运行时热切
-----------------------------------------------------------

历史上，Linux 内核的抢占模型是在编译期静态固化的。为了兼顾超算服务器的高吞吐与机器人/车载系统的高实时，Linux 7.2 全面普及了 **``PREEMPT_DYNAMIC``（动态抢占）**。

5.1 三大核心抢占模型对比
~~~~~~~~~~~~~~~~~~~~~~~~
* **``PREEMPT_NONE``（无抢占 / 服务器模式）**：
  * 内核代码执行期间完全不被抢占。只有当进程陷入系统调用返回用户态、或显式调用 ``schedule()`` / ``cond_resched()`` 时才发生切换；拥有极致的吞吐性能与最小的上下文切换开销；
* **``PREEMPT_VOLUNTARY``（自愿抢占 / 桌面与通用服务器默认）**：
  * 在内核耗时循环和关键路径中散布检查桩点 ``might_resched()``，在保障吞吐的同时兼顾基本的交互响应；
* **``PREEMPT_FULL``（完全抢占 / 低延迟与实时工作站模式）**：
  * 除持有自旋锁和中断临界区外，内核代码在任意指令处均可被更高优先级任务强制抢占，延迟控制在微秒级。

5.2 ``static_call`` 机器码级运行时零开销热切
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Linux 7.2 中，切换抢占模型无需重启系统或重新编译内核。内核利用 **``static_call``（静态调用热补丁）** 技术：

::

   +-----------------------------------------------------------------------------------+
   |                    PREEMPT_DYNAMIC 静态调用机器码热补丁机制                       |
   |                                                                                   |
   |  [切换为 PREEMPT_NONE 模式]:                                                      |
   |  ► 内核将 preempt_schedule 桩点内存的机器码直接覆写为【NOP (0x90)】(单字节空操作)!|
   |  ► CPU 执行分支预测时直接滑过，达成 0.00 纳秒的绝对零额外开销!                   |
   |                                                                                   |
   |  [切换为 PREEMPT_FULL 模式]:                                                      |
   |  ► 内核通过 text_poke 将 NOP 瞬间改写为【CALL preempt_schedule】跳转指令!         |
   |  ► 立即激活全内核指令级无死角完全抢占!                                            |
   +-----------------------------------------------------------------------------------+

系统管理员只需通过启动参数 ``preempt=full``，或在运行时执行：

.. code-block:: bash

   echo full > /sys/kernel/debug/sched/preempt

即可在不中断任何业务的前提下，实现操作系统物理特性的乾坤大挪移！

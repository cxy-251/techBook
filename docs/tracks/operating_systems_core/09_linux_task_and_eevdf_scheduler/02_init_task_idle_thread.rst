第一幕：无中生有的元初生命——``init_task`` 静态编译拓扑
------------------------------------------------------

在标准的操作系统进程生命周期中，除了 0 号进程之外，所有用户态与内核态进程都必须通过已有进程调用 ``fork()`` / ``clone()`` 复制产生。

1.1 为什么必须存在一个静态编译的 0 号进程？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在上电复位与自解压阶段，操作系统面临一个极端的先有鸡还是先有蛋困境：
* 此时**物理内存分配器尚未建立、SLUB 对象池尚未初始化、调度运行队列全为空**；
* CPU 没有办法通过动态申请内存来创建首个进程描述符；
* **破局之道**：Linux 内核在链接期直接通过静态汇编与 C 语言宏，在内核 ``.data`` 段中强行构造出一个完整的 ``struct task_struct`` 实体——**``init_task``**！它在编译产物生成的那一刻起，就已经拥有了合法的任务控制块。

1.2 ``INIT_TASK`` 静态装配宏微观解构（``init/init_task.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           init_task 编译期静态拓扑装配                            |
   |                                                                                   |
   |  struct task_struct init_task __aligned(L1_CACHE_BYTES) = {                       |
   |      .__state        = 0,                     /* TASK_RUNNING: 初始处于可运行态 */|
   |      .stack          = &init_thread_union.stack, /* 绑定 16KB 静态内核栈 */       |
   |      .usage          = REFCOUNT_INIT(2),      /* 初始引用计数 */                  |
   |      .flags          = PF_KTHREAD,            /* 纯内核线程标志 */                |
   |      .prio           = MAX_PRIO - 20,         /* 默认普通静态优先级 120 */        |
   |      .static_prio    = MAX_PRIO - 20,                                             |
   |      .normal_prio    = MAX_PRIO - 20,                                             |
   |      .sched_class    = &idle_sched_class,     /* 绑定最低优先级空闲调度类! */     |
   |      .se             = {                                                          |
   |          .load       = { .weight = 0 },       /* 调度权重为 0 */                  |
   |      },                                                                           |
   |      .mm             = NULL,                  /* 内核线程无用户虚拟地址空间 */    |
   |      .active_mm      = &init_mm,              /* 借用全局内核静态 init_mm 内存拓扑*/|
   |      .pid            = 0,                     /* 操作系统 0 号进程! */            |
   |      .tgid           = 0,                                                         |
   |      .tasks          = LIST_HEAD_INIT(init_task.tasks), /* 全系统进程链表母头! */ |
   |      .comm           = "swapper",             /* 经典命名: swapper */             |
   |      .files          = &init_files,           /* 静态空文件描述符表 */            |
   |      .fs             = &init_fs,              /* 静态根文件系统路径上下文 */      |
   |      .signal         = &init_signals,         /* 静态信号处理结构体 */            |
   |      .sighand        = &init_sighand,                                             |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

通过上述静态定义，``init_task`` 作为全系统进程树的根基节点（Root Node），其 ``tasks`` 链表头将串联起系统后续创建的所有进程。

第二幕：多核 SMP 空闲线程克隆——``fork_idle()`` 动态繁衍
--------------------------------------------------------

在现代对称多处理（SMP）系统中，每个 CPU 核心在没有就绪任务时都必须运行各自的空闲线程。

2.1 引导核（BSP）与从属核（AP）的 Idle 物理差异
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **CPU 0（BSP 引导核）**：直接继承并运行静态编译的 ``init_task``，无需动态克隆；
* **CPU 1 ~ N（AP 从属核）**：每个从属核心必须拥有各自专属的 ``struct task_struct`` 描述符和独立的 **16KB 内核物理栈**。若多核共享同一个栈，多个 CPU 在响应中断时将发生栈指针（RSP）互踩，瞬间引发内核奔溃！

2.2 ``idle_threads_init()`` 派生流水线（``kernel/smpboot.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在多核 SMP 上电准备阶段，引导核遍历所有可用的 CPU 核心：

::

   +-----------------------------------------------------------------------------------+
   |                       idle_threads_init() 多核派生时序                            |
   |                                                                                   |
   |  void __init idle_threads_init(void) {                                            |
   |      unsigned int cpu;                                                            |
   |      for_each_possible_cpu(cpu) {                                                 |
   |          if (cpu != boot_cpu_id)                                                  |
   |              idle_init(cpu);                                                      |
   |      }                                                                            |
   |  }                                                                                |
   |                                                                                   |
   |  static void __init idle_init(unsigned int cpu) {                                 |
   |      struct task_struct *tsk = fork_idle(cpu);                                    |
   |      └──► 调用 copy_process(&init_task, ...)                                      |
   |           1. 从伙伴系统分配独立的 16KB 联合体 (union thread_union);               |
   |           2. 从 SLUB kmem_cache 中分配新的 struct task_struct;                    |
   |           3. 将 PID 强制设为 0;                                                   |
   |           4. 将线程名称命名为 "swapper/1", "swapper/2", ...                       |
   |  }                                                                                |
   +-----------------------------------------------------------------------------------+

第三幕：每 CPU 运行队列绑定——``init_idle()`` 调度接入
-------------------------------------------------------

当每个核心的 Idle 线程创建就绪后，内核通过 **``kernel/sched/core.c:init_idle()``** 将其与对应 CPU 的运行队列（``struct rq``）实现硬连接。

3.1 运行队列的指针锁定时序
~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           init_idle() 运行队列绑定状态机                          |
   |                                                                                   |
   |  void init_idle(struct task_struct *idle, int cpu) {                              |
   |      struct rq *rq = cpu_rq(cpu);                                                 |
   |      unsigned long flags;                                                         |
   |                                                                                   |
   |      raw_spin_lock_irqsave(&rq->lock, flags);                                     |
   |                                                                                   |
   |      /* 1. 将该 CPU 运行队列当前正在执行的任务指针指向 idle */                    |
   |      rcu_assign_pointer(rq->curr, idle);                                          |
   |                                                                                   |
   |      /* 2. 将运行队列的 idle 守护指针永久绑定该线程 */                            |
   |      rcu_assign_pointer(rq->idle, idle);                                          |
   |                                                                                   |
   |      /* 3. 强制将其调度类锁定为最低优先级的 idle_sched_class */                   |
   |      idle->sched_class = &idle_sched_class;                                       |
   |                                                                                   |
   |      /* 4. 关键标志: on_rq = 0 (绝不进入常规就绪队列红黑树!) */                   |
   |      idle->on_rq = 0;                                                             |
   |      idle->state = TASK_RUNNING;                                                  |
   |                                                                                   |
   |      /* 5. 绑定 CPU 亲和性: 该任务只能在当前 CPU 上运行，禁止跨核迁移 */          |
   |      set_task_cpu(idle, cpu);                                                     |
   |                                                                                   |
   |      raw_spin_unlock_irqrestore(&rq->lock, flags);                                |
   |  }                                                                                |
   +-----------------------------------------------------------------------------------+

3.2 为什么 Idle 任务的 ``on_rq`` 必须设为 0？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **调度逻辑隔离**：Idle 任务是操作系统的兜底任务。如果将其挂入常规的 EEVDF 红黑树，它将参与虚拟运行时间（vruntime）的计算，抢占正常用户进程的时间片；
* **兜底选择机制**：在调度主函数 ``pick_next_task()`` 中，调度器自顶向下依次遍历：
  $$	ext{Stop-Task} \rightarrow 	ext{Deadline} \rightarrow 	ext{Real-Time (RT)} \rightarrow 	ext{Fair (EEVDF)}$$
* 只有当上述所有调度队列**全部为空（没有任何就绪任务）**时，调度器才无需查询红黑树，直接返回 ``rq->idle``！

第四幕：主核蜕变与 Idle 永恒状态机（``cpu_startup_entry`` -> ``do_idle``）
---------------------------------------------------------------------------

在 ``init/main.c:start_kernel()`` 执行完所有子系统（内存、中断、调度、VFS）的初始化后，指令流步入启动总控的终点站——**``rest_init()``**。

4.1 0 号主线程的身份蜕变
~~~~~~~~~~~~~~~~~~~~~~~~
在 ``rest_init()`` 中：
1. 调用 ``kernel_thread(kernel_init, ...);`` $\rightarrow$ 派生全系统首个动态进程 **PID 1（``kernel_init``，后续演变为 systemd）**；
2. 调用 ``kernel_thread(kthreadd, ...);`` $\rightarrow$ 派生全系统内核守护线程之父 **PID 2（``kthreadd``）**；
3. **完成历史使命**：0 号主线程已完成引导阶段的所有拓荒工作，它调用：
   ::

      cpu_startup_entry(CPUHP_ONLINE); /* 跨越临界点，永不返回! */

   正式蜕变为 CPU 0 的专属 Idle 守护线程！

4.2 ``do_idle()`` 永恒循环微观状态机（``kernel/sched/idle.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           do_idle() 核心执行循环流水线                            |
   |                                                                                   |
   |  static void do_idle(void) {                                                      |
   |      while (!need_resched()) {                                                    |
   |          /* 1. 关本地中断，准备进入休眠 */                                        |
   |          local_irq_disable();                                                     |
   |                                                                                   |
   |          /* 2. 检查是否有挂起的 RCU 回调或时钟事件 */                             |
   |          rcu_idle_enter();                                                        |
   |                                                                                   |
   |          /* 3. 调用 CPUIDLE 子系统，进入硬件低功耗休眠 */                         |
   |          cpuidle_idle_call(); ──► [执行 HLT / MWAIT 指令, CPU 晶体管暂停震荡!]   |
   |                                                                                   |
   |          /* 4. 被外部硬件中断唤醒后恢复执行 */                                   |
   |          rcu_idle_exit();                                                         |
   |          local_irq_enable();                                                      |
   |      }                                                                            |
   |                                                                                   |
   |      /* 5. 检测到 TIF_NEED_RESCHED 标志置位，立即让出 CPU! */                     |
   |      schedule_idle(); ──► [切换上下文至新就绪的工作进程!]                         |
   |  }                                                                                |
   +-----------------------------------------------------------------------------------+

第五幕：硬件级低功耗时钟时序——HLT 与 MWAIT 指令微架构解构
---------------------------------------------------------

在早期简单的操作系统中，空闲循环通常是一个死循环（``while(1);``）。这种设计会导致 CPU 核心以最大时钟频率持续空转，产生极其恐怖的电力消耗与发热。

5.1 ``HLT`` 硬件停机指令微架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **执行时序**：当 CPU 执行 ``hlt`` 指令时，处理器内部的指令译码与执行单元立即挂起，关闭核心主时钟树（Clock Gating），CPU 进入 **C1 电源节能状态（C1 Halt State）**；
* **功耗削减**：CPU 动态功耗从数十瓦瞬间跌落至毫瓦级别；
* **中断响应**：一旦外部物理引脚（INTR / NMI）收到中断信号，CPU 硬件在纳秒级自动恢复时钟并执行中断服务例程（ISR）。

5.2 ``MONITOR / MWAIT`` 现代高速缓存行监视指令
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在现代 x86_64 处理器上，Linux 使用更高级的 ``MONITOR / MWAIT`` 指令集实现深度低功耗状态（C1E, C3, C6）：
1. **``MONITOR`` 指令**：CPU 硬件建立对特定内存地址区间（如当前任务的 ``thread_info->flags`` 所在 64 字节缓存行）的电平变动监控；
2. **``MWAIT`` 指令**：CPU 进入深度睡眠状态；
3. **纳秒级硬件唤醒**：当其他 CPU 核心向该调度标志写入 ``TIF_NEED_RESCHED`` 时，总线一致性协议（MESI）导致本地缓存行失效，CPU 内部硬件侦测逻辑在 **数十纳秒内瞬间唤醒流水线**，消除传统 IPI 跨核中断开销！

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 操作系统中唯一的元初进程——0 号任务（``init_task``）的静态编译诞生哲学、多核 SMP 架构下的 ``fork_idle()`` 动态派生时序、``init_idle()`` 与每 CPU 运行队列（``struct rq``）的绑定机制、``do_idle()`` 永恒循环状态机，以及 ``HLT`` / ``MWAIT`` 硬件芯片级低功耗休眠与中断快速唤醒机制。

0 号任务成功扎根并派生出 PID 1 与 PID 2 后，操作系统具备了繁殖整个进程森林的全部能力。而所有新进程诞生的共同通道，正是著名的 ``clone()`` / ``fork()`` 系统调用。

在 **第 3 节：进程创建核心机制：``kernel_clone()``、``copy_process()`` 与写时复制 (COW) 机制** 中，我们将深入解构进程创建的总控中枢 ``kernel_clone()``、复制任务描述符（``copy_process``）、虚拟内存写时复制（Copy-On-Write, COW）页表只读降级与缺页触发物理克隆的微观全时序。

第一幕：进程繁衍的总控中枢——``kernel_clone()`` 与统一系统调用抽象
------------------------------------------------------------------

在 Linux 操作系统中，无论是经典的 ``fork()``、轻量级共享内存的 ``vfork()``、POSIX 线程库（NPTL）依赖的 ``pthread_create()`` 底层系统调用 ``clone()`` / ``clone3()``，还是内核自身创建后台工作线程的 ``kernel_thread()``，所有进程与线程创建的路径在内核内部全部高度抽象并收敛于同一个总控入口——**``kernel/fork.c:kernel_clone()``**。

1.1 ``struct kernel_clone_args`` 统一参数容器
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Linux 7.2 将所有创建标志与用户态指针统一封装为 ``struct kernel_clone_args``：

::

   +-----------------------------------------------------------------------------------+
   |                     struct kernel_clone_args 核心控制字段                         |
   |                                                                                   |
   |  struct kernel_clone_args {                                                       |
   |      u64 flags;                /* CLONE_* 标志位掩码 (如 CLONE_VM, CLONE_FS 等) */ |
   |      int __user *pidfd;        /* 用于接收 pidfd 文件描述符的用户态地址 */         |
   |      int __user *child_tid;    /* 子进程写入 TID 的用户态地址 (CLONE_CHILD_SETTID) */|
   |      int __user *parent_tid;   /* 父进程写入 TID 的用户态地址 (CLONE_PARENT_SETTID)*/|
   |      int exit_signal;          /* 子进程退出时向父进程发送的信号 (默认 SIGCHLD) */ |
   |      unsigned long stack;      /* 用户态栈底起始地址 (线程创建时指定) */           |
   |      unsigned long stack_size; /* 用户态栈尺寸 */                                 |
   |      unsigned long tls;        /* 线程局部存储 (TLS) 描述符基地址 */               |
   |      pid_t *set_tid;           /* 指定特定 PID (容器迁移/checkpoint 还原专用) */   |
   |      int cgroup;               /* 目标 Cgroup 文件描述符 (CLONE_INTO_CGROUP) */    |
   |      int (*fn)(void *);        /* 内核线程执行函数入口指针 */                     |
   |      void *fn_arg;             /* 内核线程参数指针 */                             |
   |      bool kthread;             /* 是否为内核线程 (PF_KTHREAD) */                  |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

1.2 ``kernel_clone()`` 执行状态机流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                           kernel_clone() 顶层执行流水线                           |
   |                                                                                   |
   |  pid_t kernel_clone(struct kernel_clone_args *args) {                             |
   |      /* 1. 参数合法性与互斥性预检 (如 CLONE_PIDFD 与 CLONE_PARENT_SETTID 冲突) */ |
   |      ...                                                                          |
   |                                                                                   |
   |      /* 2. 核心繁育流水线: 复制进程所有控制块与环境 */                            |
   |      struct task_struct *p = copy_process(NULL, trace, NUMA_NO_NODE, args);       |
   |      if (IS_ERR(p)) return PTR_ERR(p);                                            |
   |                                                                                   |
   |      /* 3. 获取子进程在当前 PID 命名空间下的全局数值 PID */                       |
   |      struct pid *pid = get_task_pid(p, PIDTYPE_PID);                             |
   |      pid_t nr = pid_vnr(pid);                                                     |
   |                                                                                   |
   |      /* 4. 若为 vfork 则初始化完成量 (Completion)，阻塞等待子进程 exec/exit */    |
   |      if (clone_flags & CLONE_VFORK) {                                             |
   |          p->vfork_done = &vfork;                                                  |
   |          init_completion(&vfork);                                                 |
   |      }                                                                            |
   |                                                                                   |
   |      /* 5. 唤醒新进程: 将其状态置为 TASK_RUNNING 并挂入 EEVDF 运行队列! */        |
   |      wake_up_new_task(p);                                                         |
   |                                                                                   |
   |      /* 6. 若为 vfork，父进程在此让出 CPU 进入休眠，直至子进程调用 execve 或退出*/|
   |      if (clone_flags & CLONE_VFORK)                                               |
   |          wait_for_vfork_done(p, &vfork);                                          |
   |                                                                                   |
   |      return nr; /* 父进程返回子进程的 PID! */                                     |
   |  }                                                                                |
   +-----------------------------------------------------------------------------------+

第二幕：生命的细胞分裂——``copy_process()`` 十二步流水线深度推导
--------------------------------------------------------------

**``copy_process()``** 是整个 Linux 内核中最为庞大、精密且严苛的函数之一。它完成了新进程所有软硬件状态的克隆：

::

   +-----------------------------------------------------------------------------------+
   |                         copy_process() 十二步克隆流水线                           |
   |                                                                                   |
   |  Step 1:  标志位安全沙箱与互斥校验 (CLONE_THREAD / CLONE_SIGHAND / CLONE_VM 等)    |
   |  Step 2:  dup_task_struct() ──► 从 SLUB 分配 task_struct 与 16KB 独立内核栈       |
   |  Step 3:  copy_creds() ──► 复制凭证与安全上下文，检查 RLIMIT_NPROC 进程数上限      |
   |  Step 4:  sched_fork() ──► 初始化调度实体 se，设为 TASK_NEW，锁定初始 CPU 运行队列|
   |  Step 5:  copy_files() ──► 共享 fd 表 (CLONE_FILES) 或 dup_fd() 深度克隆 fd 表     |
   |  Step 6:  copy_fs() ──► 共享根目录/工作目录 (CLONE_FS) 或 copy_fs_struct()         |
   |  Step 7:  copy_sighand() & copy_signal() ──► 复制信号处理函数与未决信号队列       |
   |  Step 8:  copy_mm() ──► 共享地址空间 (线程) 或 dup_mm() 建立 COW 写时复制页表      |
   |  Step 9:  copy_namespaces() ──► 继承或创建全新 Namespaces (Mount/UTS/IPC/Net/PID)  |
   |  Step 10: copy_thread() ──► 装配 CPU 硬件寄存器栈帧，强制设置 childregs->rax = 0!   |
   |  Step 11: alloc_pid() ──► 在各层级 PID Namespace 中分配唯一 PID 结构体            |
   |  Step 12: 挂载全系统进程树与哈希表 (tasks/children/sibling)，释放 tasklist_lock   |
   +-----------------------------------------------------------------------------------+

2.1 ``dup_task_struct()`` 实体克隆与独立栈分配
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **描述符分配**：调用 ``alloc_task_struct_node()`` 从 SLUB 高速缓存 ``task_struct_cachep`` 中为子进程申请一个纯净的 ``struct task_struct``；
* **浅拷贝母体**：执行 ``*tsk = *orig;``，将父进程的所有字段完整复制过来；
* **分配 16KB 专属内核栈**：调用 ``alloc_thread_stack_node()`` 为子进程分配专属的 ``union thread_union`` 内核栈。若开启 ``CONFIG_VMAP_STACK``，该栈在虚拟地址上连续但在物理内存上通过 ``vmalloc`` 离散映射，并在栈末尾打上 **``0x57AC6E9D`` 栈金丝雀（``STACK_END_MAGIC``）** 以防范栈溢出。

2.2 为什么 ``fork()`` 会返回两次？——``copy_thread()`` 汇编栈帧揭秘
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
教科书中经典的“``fork()`` 调用一次却返回两次：父进程返回子进程 PID，子进程返回 0”的微观物理真相，完全隐藏在 ``arch/x86/kernel/process_64.c:copy_thread()`` 中：

::

   +-----------------------------------------------------------------------------------+
   |                       copy_thread() 寄存器栈帧装配微观图                          |
   |                                                                                   |
   |  [子进程 16KB 内核栈顶: task_top_of_stack(p)]                                     |
   |                                                                                   |
   |  ┌────────────────────────────────────────────────────────┐                       |
   |  │ struct pt_regs (用户态寄存器现场备份)                  │                       |
   |  │ ├── rip = 父进程系统调用下的一条指令地址               │                       |
   |  │ ├── rsp = 子进程用户态栈指针 (args->stack)             │                       |
   |  │ └── rax = 0; ◄───【核心硬件铁律: 强制将 RAX 置零!】   │                       |
   |  ├────────────────────────────────────────────────────────┤                       |
   |  │ struct fork_frame (内核态上下文切换栈帧)               │                       |
   |  │ ├── rbx, r12, r13, r14, r15, rbp (被调用者保存寄存器)  │                       |
   |  │ └── ret_addr = ret_from_fork (子进程首次调度返回入口)   │                       |
   |  └────────────────────────────────────────────────────────┘                       |
   +-----------------------------------------------------------------------------------+

* **父进程返回路径**：父进程在 ``kernel_clone()`` 执行完毕后，正常从系统调用返回，其 ``RAX`` 寄存器中存放的是新分配的子进程 PID（``nr``）；
* **子进程返回路径**：子进程在未来被调度器选中时，CPU 恢复其内核栈并跳转至 ``ret_from_fork`` $\rightarrow$ ``entry_SYSCALL_64_after_hwframe``，最后通过 ``iretq`` / ``sysretq`` 弹出 ``pt_regs`` 返回用户态。由于其 ``pt_regs->rax`` 在创建时被强行写入了 ``0``，**子进程醒来时读取到的函数返回值永远是 0**！

第三幕：虚拟内存的神来之笔——写时复制 (COW) 机制微观全时序
----------------------------------------------------------

在早期 UNIX 系统中，``fork()`` 会将父进程的所有物理内存全量拷贝一份给子进程。如果父进程占用了 32GB 物理内存，全量拷贝将消耗数百毫秒的总线带宽，而绝大多数子进程随后会立即调用 ``execve()`` 加载新程序，导致刚刚拷贝的 32GB 内存被瞬间释放。

为了消除这种巨大的算力与带宽浪费，Linux 引入了基于 MMU 硬件保护机制的 **写时复制（Copy-On-Write, COW）**。

3.1 第一阶段：进程创建期的页表只读降级（``copy_page_range()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当 ``copy_process()`` 触发 ``copy_mm() -> dup_mm() -> dup_mmap()`` 时，内核递归遍历父进程的所有虚拟内存区域（VMA）：

::

   +-----------------------------------------------------------------------------------+
   |                        dup_mmap() 页表只读降级与引用激增                          |
   |                                                                                   |
   |  [父进程虚拟地址空间]                              [物理内存 RAM]                 |
   |  PTE_Parent ──(只读: _PAGE_RW=0)──┐                                               |
   |                                   ├──► [4KB 物理页帧 (PFN: 0x1A2B)]               |
   |  [子进程虚拟地址空间]             │    - _refcount = 2 (物理引用计数从 1 变为 2)  |
   |  PTE_Child  ──(只读: _PAGE_RW=0)──┘    - 此时物理内存零拷贝，仅复制了页表项!      |
   +-----------------------------------------------------------------------------------+

1. **写保护降级**：对于所有私有可写页面（``VM_WRITE & ~VM_SHARED``），内核调用 ``pte_wrprotect()`` 将父进程和子进程的 PTE 表项中的 **写权限位（Bit 1: ``_PAGE_RW``）彻底清零**；
2. **物理引用计数翻倍**：调用 ``get_page()`` / ``folio_get()`` 将该物理页的 ``_refcount`` 从 1 递增至 2；
3. **极速完成**：整个 ``fork()`` 过程仅耗费数微秒（只需拷贝几页页表，不发生任何物理数据搬运）。

3.2 第二阶段：运行期的硬件异常捕获（MMU ``#PF`` 缺页异常）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当父进程或子进程尝试对共享页面执行写操作（如 ``*ptr = 0x55;``）时：
1. **硬件拦截**：CPU MMU 硬件在执行内存写入时，检测到该虚拟地址对应的 PTE 具有可读属性但 **``_PAGE_RW == 0``（只读）**；
2. **抛出异常**：MMU 立即终止写入指令，向 CPU 核心注入 **14 号缺页异常 ``#PF``**，硬件错误码为 **``0x7``（Protection Violation + Write + User）**；
3. **进入内核态**：CPU 压栈并跳转至 IDT 表中的 ``asm_exc_page_fault`` 汇编入口，最终路由至 ``mm/memory.c:do_wp_page()``。

3.3 第三阶段：物理内存分裂与重绑定（``mm/memory.c:do_wp_page()``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                         do_wp_page() COW 物理分裂微观流水线                       |
   |                                                                                   |
   |  do_wp_page(struct vm_fault *vmf) {                                               |
   |      struct page *old_page = vmf->page;                                           |
   |                                                                                   |
   |      /* 判断 A: 该物理页是否处于多进程共享状态 (page_count > 1)? */               |
   |      if (page_count(old_page) > 1) {                                              |
   |          /* 1. 向伙伴系统申请一个全新的 4KB 物理页 */                             |
   |          struct page *new_page = alloc_page_vma(GFP_HIGHUSER_MOVABLE, vma, addr); |
   |                                                                                   |
   |          /* 2. 将旧物理页中的 4KB 数据完整拷贝至新物理页 */                       |
   |          copy_user_highpage(new_page, old_page, vmf->address, vma);               |
   |                                                                                   |
   |          /* 3. 构造全新的 PTE 表项: 指向 new_page 且恢复 _PAGE_RW 写权限! */      |
   |          pte_t entry = mk_pte(new_page, vma->vm_page_prot);                       |
   |          entry = pte_mkwrite(pte_mkdirty(entry));                                 |
   |                                                                                   |
   |          /* 4. 原子更新当前进程的 PTE 页表项并刷新本地 TLB */                     |
   |          set_pte_at_notify(mm, vmf->address, vmf->pte, entry);                    |
   |                                                                                   |
   |          /* 5. 释放对旧物理页的引用 (old_page->_refcount 递减恢复为 1) */         |
   |          put_page(old_page);                                                      |
   |          return VM_FAULT_WRITE;                                                   |
   |      }                                                                            |
   |                                                                                   |
   |      /* 判断 B: 独占状态 (page_count == 1: 另一方已经分裂过或退出了) */           |
   |      wp_page_reuse(vmf); ──► [直接设置 _PAGE_RW=1 恢复写权限，零内存分配开销!]    |
   |  }                                                                                |
   +-----------------------------------------------------------------------------------+

通过上述精妙的硬件协同状态机，Linux 实现了“只在真正需要修改数据的那一瞬间，才付出单页 4KB 内存复制的最小代价”，将操作系统的并发吞吐推向极致。

第四幕：新生命的破土而出——``wake_up_new_task()`` 激活与调度接入
----------------------------------------------------------------

当进程描述符、内核栈、文件表与页表全部装配完毕后，新进程正式在系统中合法存在。最后一步是让其接入 CPU 调度系统。

4.1 状态跃迁与就绪入队
~~~~~~~~~~~~~~~~~~~~~~
在 ``kernel/sched/core.c:wake_up_new_task()`` 中：
1. **状态翻转**：将任务状态从初生的 ``TASK_NEW`` 翻转为可运行的 **``TASK_RUNNING``**；
2. **计算初始虚拟运行时间**：调度器为其分配初始的虚拟运行时间（``vruntime``），确保其既不会因为新诞生而无休止霸占 CPU，也不会因为刚创建就饿死；
3. **入队红黑树**：调用 ``activate_task(rq, p, ENQUEUE_NOCLOCK)`` 将新进程正式挂入对应 CPU 运行队列的 EEVDF 红黑树就绪队列；
4. **抢占检测（``check_preempt_curr()``）**：
   * 若新进程的虚拟截止时间（Deadline）早于当前正在运行的父进程，或系统配置了 ``sysctl_sched_child_runs_first = 1``；
   * 调度器立即置位父进程的 ``TIF_NEED_RESCHED`` 标志，强制父进程在系统调用返回时触发上下文切换，让子进程**率先运行**！

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 进程创建机制的宏观拓扑与底层物理时钟时序：``kernel_clone()`` 统一入口、``copy_process()`` 十二步精密克隆流水线、16KB 独立内核栈与 ``task_struct`` 分配、``copy_thread()`` 栈帧装配与 ``RAX=0`` 双返回值物理本质、写时复制（COW）从页表只读降级到硬件 ``#PF(0x7)`` 异常与物理分裂全时序，以及 ``wake_up_new_task()`` 调度接入。

当新进程被唤醒并挂入就绪队列后，调度器将在适当时机选中它，并执行 CPU 物理控制权的移交。

在 **第 4 节：上下文切换微观过程：``__switch_to()`` 与 ``__switch_to_asm()`` 寄存器与栈指针原子切换** 中，我们将深入剖析内核调度执行的最深层底层核心——解构 CPU 通用寄存器保存、内核栈指针 ``RSP`` 硬件原子切换、CR3 页表根基切换、FPU/AVX 浮点上下文惰性保存，以及从一个进程空间无缝跳跃至另一个进程空间的微观全时序。

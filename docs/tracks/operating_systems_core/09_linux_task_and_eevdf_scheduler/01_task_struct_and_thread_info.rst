第一幕：操作系统的灵魂中枢——``struct task_struct`` 宏伟全景
--------------------------------------------------------------

在 Linux 操作系统的设计哲学中，不存在传统操作系统中“重量级进程”与“轻量级线程”的生硬物理割裂。Linux 采用统一的 **单一任务模型（1:1 Threading Model）**：无论是一个独立的进程，还是进程内部的一个并发线程，在内核底层均由一个完全平等的 **``struct task_struct``** 实例进行描述。

1.1 进程与线程的微观本质
~~~~~~~~~~~~~~~~~~~~~~~~
* **进程与线程的唯一区别**：在于多个 ``task_struct`` 之间是否通过指针共享资源；
* **单进程多线程**：多个独立的 ``task_struct`` 拥有不同的 PID（线程 ID），但它们的 ``mm`` 指针共享同一个 ``struct mm_struct``（虚拟内存地址空间），它们的 ``files`` 指针共享同一个 ``struct files_struct``（打开文件表），且它们的 ``tgid``（Thread Group ID / 线程组 ID，即用户态看到的进程 PID）完全相同；
* **独立进程**：多个 ``task_struct`` 拥有各自独立的 ``mm_struct``（独立页表）与独立的 ``files_struct``。

1.2 任务生命周期状态矩阵（Task State Matrix）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``include/linux/sched.h`` 中，每个任务在任意时刻都精确处于以下状态机的一环：

::

   +-----------------------------------------------------------------------------------+
   |                           struct task_struct 状态转移状态机                       |
   |                                                                                   |
   |                     ┌───────────────────────────────┐                             |
   |                     │   TASK_RUNNING (0, 就绪/运行) │ ◄───────────────┐           |
   |                     └───────────────┬───────────────┘                 │           |
   |                                     │                                 │           |
   |                   等待资源 / 睡眠   │                                 │           |
   |            ┌────────────────────────┴────────────────────────┐        │           |
   |            ▼                                                 ▼        │ 事件到达  |
   |  ┌───────────────────────────┐             ┌──────────────────────────┴─┐ (唤醒)  |
   |  │ TASK_INTERRUPTIBLE (1)    │             │ TASK_UNINTERRUPTIBLE (2)   │         |
   |  │ (可中断浅睡眠: 响应信号)  │             │ (不可中断深睡眠: 屏蔽信号) │         |
   |  └─────────────┬─────────────┘             └──────────────────────────┬─┘         |
   |                │                                                      │           |
   |                └────────────────────────►◄────────────────────────────┘           |
   |                                          │                                        |
   |                                          ▼ do_exit() 退出                         |
   |                               ┌─────────────────────────────┐                     |
   |                               │     EXIT_ZOMBIE (32, 僵尸)  │                     |

   |                                              │ 父进程 wait4() 回收                |
   |                                              ▼                                    |
   |                               ┌─────────────────────────────┐                     |
   |                               │     EXIT_DEAD (64, 销毁)    │                     |
   |                               └─────────────────────────────┘                     |
   +-----------------------------------------------------------------------------------+

.. table:: 核心任务状态物理语义
   :widths: 25 20 55

   +-------------------------------+------------------+----------------------------------------------------------------------------+
   | 状态常量                      | 数值掩码         | 硬件/内核调度行为与生命周期特征                                            |
   +===============================+==================+============================================================================+
   | **``TASK_RUNNING``**          | ``0x00000000``   | 任务正在 CPU 上执行，或者处于 EEVDF 运行队列（``rq``）中等待被调度分发     |
   +-------------------------------+------------------+----------------------------------------------------------------------------+
   | **``TASK_INTERRUPTIBLE``**    | ``0x00000001``   | 浅睡眠态：等待特定硬件事件（如网络数据包到达），接收到信号时会立即被提前唤醒|
   +-------------------------------+------------------+----------------------------------------------------------------------------+
   | **``TASK_UNINTERRUPTIBLE``**  | ``0x00000002``   | 深睡眠态：通常等待不可拆分的块设备物理 I/O，**禁止被信号打断**，计入系统负载|
   +-------------------------------+------------------+----------------------------------------------------------------------------+
   | **``__TASK_STOPPED``**        | ``0x00000004``   | 收到 ``SIGSTOP``、``SIGTSTP`` 等暂停信号后进入的停止执行状态               |
   +-------------------------------+------------------+----------------------------------------------------------------------------+
   | **``EXIT_ZOMBIE``**           | ``0x00000020``   | 僵尸态：任务已释放绝大部分内存与文件，仅保留 ``task_struct`` 等待父进程回收|
   +-------------------------------+------------------+----------------------------------------------------------------------------+

第二幕：调度子系统挂载点——``sched_entity`` 与优先级拓扑
-------------------------------------------------------

``task_struct`` 内部嵌入了多个调度实体（Scheduling Entities），使同一个任务能够被不同的调度类（Scheduling Class）无缝接管。

2.1 调度实体三剑客
~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                        task_struct 内部多调度类实体挂载点                         |
   |                                                                                   |
   |  struct task_struct {                                                             |
   |      const struct sched_class *sched_class; /* 调度类函数指针表 (EEVDF/RT/DL/Idle)*/|
   |                                                                                   |
   |      struct sched_entity      se;           /* EEVDF 调度实体 (完全公平调度) */   |
   |      struct sched_rt_entity   rt;           /* 实时调度实体 (SCHED_FIFO / RR) */  |
   |      struct sched_dl_entity   dl;           /* 截止时间调度实体 (SCHED_DEADLINE)*/|
   |      ...                                                                          |
   |  };                                                                               |
   +-----------------------------------------------------------------------------------+

* **``struct sched_entity se`` (EEVDF 调度实体)**：
  * ``u64 vruntime``：虚拟运行时间（记录任务已消耗的标准化 CPU 算力）；
  * ``u64 deadline``：虚拟截止时间（EEVDF 算法的核心选轴依据）；
  * ``u64 vlag``：虚拟滞后量（用于裁决任务是否有资格抢占 CPU）；
  * ``struct load_weight load``：权重因子（由 Nice 值映射计算得出）；
* **``struct sched_rt_entity rt`` (实时调度实体)**：
  * ``unsigned int time_slice``：RR 轮转调度的剩余时间片；
* **``struct sched_dl_entity dl`` (DEADLINE 调度实体)**：
  * ``u64 runtime / deadline / period``：基于 CBS（Constant Bandwidth Server）的最坏执行时间保证。

2.2 优先级矩阵（Priority Hierarchy）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Linux 内核将优先级统一归一化为 ``[0, 139]`` 的整数空间：
* **``0 ~ 99`` (实时优先级)**：数值越小优先级越高，由 ``task->rt_priority`` 映射；
* **``100 ~ 139`` (常规优先级)**：对应传统 Unix 的 **Nice 值（``-20 ~ +19``）**：
  $$	ext{static\_prio} = 	ext{DEFAULT\_PRIO}(120) + 	ext{nice}$$
* **动态优先级（``prio``）**：当常规进程持有互斥锁被实时进程等待时，通过 **优先级继承协议（Priority Inheritance, PI）**，其 ``prio`` 瞬间提升至实时进程级别，彻底消除“优先级翻转”死锁隐患！

第三幕：资源所有权解耦——内存、文件、信号与命名空间拓扑
-------------------------------------------------------

``task_struct`` 并非简单的数据容器，而是整个操作系统所有物理与逻辑资源的聚合枢纽。

::

   +-----------------------------------------------------------------------------------+
   |                           task_struct 核心子系统解耦拓扑                          |
   |                                                                                   |
   |  struct task_struct                                                               |
   |  ├── pid_t pid (全局线程 ID) / pid_t tgid (进程组 ID)                              |
   |  │                                                                                |
   |  ├── struct mm_struct *mm ──────► [ 虚拟内存拓扑: PGD 页表 / VMA 链表 / 内存映射 ]|
   |  │   struct mm_struct *active_mm (内核线程借用上下文)                             |
   |  │                                                                                |
   |  ├── struct files_struct *files ─► [ 打开文件描述符表: fd_array[] -> struct file ]|
   |  │                                                                                |
   |  ├── struct fs_struct *fs ───────► [ 根目录 (root) 与当前工作目录 (pwd) 路径 ]     |
   |  │                                                                                |
   |  ├── struct signal_struct *signal► [ 共享信号集合 / 共享定时器 / 进程统计 ]        |
   |  │   struct sighand_struct *sighand [ 信号处理函数分发数组: sa_handler[] ]        |
   |  │                                                                                |
   |  └── struct nsproxy *nsproxy ────► [ 6 大隔离命名空间: PID/Mount/Net/IPC/UTS/User ]|
   +-----------------------------------------------------------------------------------+

3.1 ``mm`` vs ``active_mm``：用户进程与内核线程的边界
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **用户进程**：``task->mm`` 与 ``task->active_mm`` 严格相等，均指向描述该进程用户态虚拟空间的 ``mm_struct``；
* **内核线程（Kernel Thread / Daemon）**：
  * 内核线程完全没有用户态地址空间，其 ``task->mm == NULL``；
  * 当内核线程被调度上 CPU 时，为了避免无谓的 CR3 页表切换与 TLB 冲刷开销，内核线程将 ``active_mm`` 指向**上一个被剥夺 CPU 的前任进程的 ``mm_struct``**，借壳执行内核逻辑，极大地节约了硬件切换开销。

第四幕：16KB 内核栈物理内存布局与 ``thread_info`` / ``thread_struct``
----------------------------------------------------------------------

每个任务在进入内核态（通过系统调用、硬件中断或异常）时，都必须拥有一个绝对隔离、受保护的内核调用栈。

4.1 16KB ``union thread_union`` 物理内存拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位 x86_64 体系下，内核为每个任务分配 4 个连续物理页（16KB，``THREAD_SIZE``）：

::

   +-----------------------------------------------------------------------------------+
   |                         16KB 内核栈 (union thread_union) 拓扑                     |
   |                                                                                   |
   |  高地址 (0xFFFF8880...4000) ┌──────────────────────────────────────────────┐        |
   |                             │ 栈顶 (Stack Top, TASK_threadsp(task))        │ ◄─ RSP |
   |                             ├──────────────────────────────────────────────┤        |
   |                             │ struct pt_regs (中断/系统调用压入的现场)     │        |
   |                             │  - SS, RSP, RFLAGS, CS, RIP, R15~RAX 等      │        |
   |                             ├──────────────────────────────────────────────┤        |
   |                             │ 动态内核 C 函数调用栈帧 (Downwards Growth)   │        |
   |                             │                  │                           │        |
   |                             │                  ▼ 栈向下增长方向            │        |
   |                             │                                              │        |
   |                             │ ... 空闲栈空间 (Free Stack) ...              │        |
   |                             ├──────────────────────────────────────────────┤        |
   |                             │ struct thread_info (低地址, 记录 flags 标志) │        |
   |                             ├──────────────────────────────────────────────┤        |
   |  低地址 (0xFFFF8880...0000) │ STACK_END_MAGIC (0x57AC6E9D, 栈底金丝雀哨兵) │        |
   |                             └──────────────────────────────────────────────┘        |
   +-----------------------------------------------------------------------------------+

4.2 ``struct thread_info`` 核心调度标志位（``flags``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``thread_info`` 存放在栈的基底部，其内部最核心的字段是 ``unsigned long flags``：
* **``_TIF_NEED_RESCHED (Bit 3)``**：
  * **重新调度标志**：当发生时钟中断发现当前任务时间片耗尽，或者更高优先级任务被唤醒时，调度器将该位置 1；
  * 当 CPU 即将从中断、异常或系统调用返回用户空间的一瞬间，内核汇编代码检查该位，若置 1 则立即触发 ``schedule()`` 强制发生抢占！
* **``_TIF_SIGPENDING (Bit 2)``**：标记当前任务有挂起的未处理信号，需在返回用户空间前执行信号处理。

4.3 体系结构特定现场（``struct thread_struct``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
存放在 ``task_struct.thread`` 中，用于在任务被换出 CPU 时，由 ``__switch_to()`` 汇编代码保存硬件寄存器的状态：
* ``unsigned long sp``：保存任务让出 CPU 时的内核栈指针；
* ``unsigned long fsbase / gsbase``：保存用户态 TLS 段基址；
* ``struct fpu fpu``：保存 AVX-512 / SSE 浮点运算扩展寄存器状态。

第五幕：Per-CPU 当前任务寻址——``current`` 宏微观实现
----------------------------------------------------

在内核代码中，无论处于哪个子系统，都可以随时通过调用 **``current``** 宏获取当前正在执行的 ``struct task_struct *`` 指针。

5.1 ``current`` 宏在 x86_64 上的纳秒级汇编展开
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在多核并发环境下，每个 CPU 核心同一时刻执行的任务各不相同。Linux 7.2 将 ``current_task`` 作为 **Per-CPU 变量** 进行管理：

::

   /* 定义在 arch/x86/include/asm/current.h */
   DECLARE_PER_CPU(struct task_struct *, current_task);

   static __always_inline struct task_struct *get_current(void) {
       return this_cpu_read_stable(current_task);
   }
   #define current get_current()

当 GCC/Clang 编译 ``current`` 时，直接展开为一条利用 **``GS`` 寄存器** 的硬件寻址指令：

::

   movq    %gs:current_task, %rax

.. important::
   **GSBASE 硬件寻址的物理极致**：
   * 在模块 08 中，从核上线时已将本核心专属的 Per-CPU 基地址写入了 ``MSR_GS_BASE``；
   * 因此，``movq %gs:current_task, %rax`` 指令通过 CPU 内部的段基址加法器，**在单个时钟周期内、零内存总线锁争用、零函数调用开销** 下，瞬间抓取到当前核心的 ``task_struct`` 指针！

第一幕：特权级硬件隔离的物理实现——CPL, DPL 与 RPL 校验矩阵
---------------------------------------------------------

现代操作系统的核心安全边界（内核态 vs 用户态）绝非纯软件层面的变量判断，而是由 CPU 内部逻辑门与比较器电路在每一次内存访问与指令解码时执行的硬性物理校验。

1.1 特权级与段选择子（Segment Selectors）的硬件编码
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 x86 体系结构中，特权级被划分为 4 个环形层级（Ring 0 ~ Ring 3），其中现代操作系统（Linux / macOS / Windows）仅使用 Ring 0（最高特权级，内核态）与 Ring 3（最低特权级，用户态）。硬件通过三组特权级字段构建访问控制矩阵：

::

   15                                                  3   2   1   0
   +-----------------------------------------------------+---+-------+
   |             描述符索引 (Descriptor Index)            |TI |  RPL  |
   +-----------------------------------------------------+---+-------+
   (TI: 0=GDT, 1=LDT; RPL: 请求特权级 0..3)

1. **CPL (Current Privilege Level, 当前特权级)**：
   * 存储于当前代码段寄存器（``CS``）与栈段寄存器（``SS``）的最低 2 位（Bits 0..1）；
   * 指示当前 CPU 正在执行的代码所处的特权级别（00b = Ring 0, 11b = Ring 3）。
2. **DPL (Descriptor Privilege Level, 描述符特权级)**：
   * 存储于全局描述符表（GDT）或中断描述符表（IDT）中的段描述符属性字节内（Bits 45..46）；
   * 规定了访问该段内存或门描述符所需的最低特权门槛。
3. **RPL (Requested Privilege Level, 请求特权级)**：
   * 存储于指向段描述符的选择子（Selector）自身的最低 2 位；
   * 用于防止低特权代码借由高特权指针越权访问受保护数据（防提权攻击）。

1.2 硬件比较器电路逻辑与访问校验时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当 CPU 流水线执行一条数据访问指令（如 ``mov (%rdi), %rax``）时，内存管理单元（MMU）与段校验逻辑在单时钟周期内进行硬件比较：

.. table:: x86 硬件特权级检查规则与物理比较公式
   :widths: 25 35 40

   +--------------------------+-------------------------------------+----------------------------------------------------+
   | 访问类型                 | 硬件校验准则 (电路判断公式)         | 校验失败时的硬件行为                               |
   +==========================+=====================================+================================================----+
   | **数据段访问** (DS/ES/FS)| $\max(	ext{CPL}, 	ext{RPL}) \le 	ext{DPL}$ | 触发通用保护异常（General Protection Fault, #GP 13）|
   +--------------------------+-------------------------------------+----------------------------------------------------+
   | **非一致代码段跳转**     | $	ext{CPL} == 	ext{DPL}$ 且 $	ext{RPL} \le 	ext{DPL}$ | 禁止跨特权直接跳转，触发 #GP 13                     |
   +--------------------------+-------------------------------------+----------------------------------------------------+
   | **一致代码段跳转**       | $	ext{CPL} \ge 	ext{DPL}$         | 允许低特权执行高特权代码段，但 **CPL 保持不变**    |
   +--------------------------+-------------------------------------+----------------------------------------------------+
   | **门描述符调用** (Call Gate)| $	ext{CPL} \le 	ext{Gate.DPL}$ 且 $	ext{RPL} \le 	ext{Gate.DPL}$ | 允许通过受控大门向更高特权级（DPL=0）受限跃迁      |
   +--------------------------+-------------------------------------+----------------------------------------------------+

1.3 特权指令（Privileged Instructions）的硬件电路阻断
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 CPU 指令译码器内部，特定控制指令被硬连线绑定了特权检查逻辑：

* **核心特权指令**：``LGDT``（加载 GDT）、``LIDT``（加载 IDT）、``LTR``（加载任务寄存器）、``MOV CR0/CR3/CR4``（修改控制与页表基址寄存器）、``WRMSR/RDMSR``（读写 MSR 寄存器）、``CLI/STI``（开关中断）、``HLT``（挂起停机）；
* **硬件阻断时序**：当指令解码器在译码阶段检测到当前 ``CPL != 0`` 时，硬件微码立即拒绝将控制信号发送给执行单元，并直接生成内部硬件异常，强制压栈并跳转至向量 13（#GP 故障处理入口）。

第二幕：传统软中断系统调用（``INT 0x80``）的性能枷锁
-----------------------------------------------------

在 Linux 早期的 32 位 x86 时代，用户空间程序向内核请求服务（如文件读写、创建进程）唯一合法的受控途径是执行软中断指令 ``INT 0x80``。

2.1 ``INT 0x80`` 调用的微观全链路
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
从用户态执行 ``INT 0x80`` 到进入内核服务，CPU 必须历经以下沉重的硬件步骤：

::

   [用户态程序 (Ring 3)]
          │ 执行 INT 0x80 指令
          ▼
   1. 查 IDTR 寄存器，读取物理内存中的 IDT 基地址；
   2. 访问内存读取 Vector 0x80 (128) 对应的 8 字节/16 字节门描述符；
   3. 硬件比较器检查：CPL (3) <= Gate.DPL (3)，通过门权限；
   4. 访问任务状态段 TSS (Task State Segment)，读取内存中的内核栈顶指针 ESP0/RSP0；
   5. 切换栈指针，将旧 SS, 旧 ESP/RSP, 旧 EFLAGS/RFLAGS, 旧 CS, 旧 EIP/RIP 写入新内核栈内存；
   6. 清除 EFLAGS 中的 TF/IF 标志位；
   7. 从门描述符中提取目标内核代码段选择子与处理函数偏移，写入 CS:EIP/RIP；
          │
          ▼
   [内核态入口 (Ring 0)]

2.2 时钟周期开销与流水线惩罚
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``INT 0x80`` 与后续返回指令 ``IRET`` 的硬件设计初衷是处理突发性异常，而非高频的系统服务请求。其物理瓶颈极其显著：

1. **多次主板/缓存总线访问**：单次系统调用需要分别读取 IDT 描述符、读取 TSS 结构体、向内核栈写入多达 5 个双字/四字；
2. **流水线清空惩罚（Pipeline Flush）**：软中断会导致 CPU 指令预取单元、分支预测器与乱序执行引擎全部强制重置；
3. **开销数据**：在奔腾时代（Pentium II/III），一次简单的 ``getpid()`` 系统调用通过 ``INT 0x80`` 往返耗时高达 **150 ~ 250 个时钟周期**，成为高并发 I/O 的致命瓶颈。

第三幕：现代快速系统调用（Fast System Call）微观架构与 MSR 寄存器组
-------------------------------------------------------------------

为了彻底打破中断门的性能枷锁，处理器厂商（AMD 与 Intel）在硬件层面设计了专用的快速系统调用指令。其核心思想是：**彻底废弃一切内存数据结构查询（不查 IDT、不查 TSS、不写内存栈），将跳转目标地址、段选择子与屏蔽掩码全量固化在 CPU 芯片内部的高速寄存器中。**

在 64 位长模式下，AMD 制定的 ``SYSCALL / SYSRET`` 规范被确立为行业统一标准。

::

   +-----------------------------------------------------------------------------------+
   |                             CPU 内部专用 MSR 寄存器组                             |
   |                                                                                   |
   |  [MSR_LSTAR (0xC0000082)]  ──► [ 64-bit 内核入口物理/虚拟基址 (entry_SYSCALL_64)] |
   |                                                                                   |
   |  [MSR_STAR  (0xC0000081)]  ──► [ 63..48: 用户段选择子基址 | 47..32: 内核段选择子] |
   |                                                                                   |
   |  [MSR_SFMASK(0xC0000084)]  ──► [ 32-bit RFLAGS 清零掩码 (屏蔽 IF, TF, DF 等)]     |
   |                                                                                   |
   |  [MSR_KERNEL_GS_BASE]      ──► [ 64-bit 内核 Per-CPU 结构体基地址 (用于 SWAPGS)]  |
   +-----------------------------------------------------------------------------------+

3.1 核心 MSR 寄存器的硬件结构与配置
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在操作系统启动引导阶段（Linux 7.2 的 ``arch/x86/kernel/cpu/common.c:syscall_init()``），内核会通过特权指令 ``wrmsr`` 将以下硬件参数直接写入 CPU 片上模型特定寄存器：

1. **``MSR_LSTAR`` (Long Mode Target Address, MSR 0xC0000082)**：
   * 存储 64 位内核系统调用总汇编入口地址。在 64 位 Linux 中，该寄存器被恒定写入 ``entry_SYSCALL_64`` 的函数地址。
2. **``MSR_STAR`` (System Call Target Address, MSR 0xC0000081)**：
   * **Bits 47..32 (Kernel CS/SS)**：存放内核代码段基址选择子（如 ``__KERNEL_CS``）。硬件约定内核代码段选择子为 $Base$，数据段选择子为 $Base + 8$；
   * **Bits 63..48 (User CS/SS)**：存放用户态段选择子基址（如 ``__USER32_CS``）。硬件约定在执行 ``SYSRET`` 返回时，用户数据段为 $Base + 8$，用户 64 位代码段为 $Base + 16$。
3. **``MSR_SFMASK`` / ``MSR_FMASK`` (System Call Flag Mask, MSR 0xC0000084)**：
   * 包含系统调用发生时必须在 ``RFLAGS`` 中自动被硬件清零的位掩码；
   * Linux 7.2 默认设置屏蔽：中断标志 ``IF``（位 9，保证系统调用进入瞬间原子关中断）、陷阱标志 ``TF``（位 8）、方向标志 ``DF``（位 10）、嵌套任务 ``NT``（位 14）。

第四幕：``SYSCALL`` 与 ``SYSRET`` 指令微观时钟时序状态机
-------------------------------------------------------

``SYSCALL`` 指令完全在 CPU 片内寄存器之间进行数据搬移，不产生任何总线写内存事务，耗时仅需几个时钟周期。

4.1 ``SYSCALL`` 指令在硬件微码中的原子跃迁
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当 Ring 3 用户程序执行机器码 ``0F 05``（``SYSCALL``）时，CPU 硬件在一个原子时钟周期序列中执行如下操作：

::

   [用户态 (Ring 3) 运行中]
             │
             ▼ 执行 SYSCALL 指令 (0F 05)
   1. 暂存返回指令地址：RCX <= RIP (下一条用户指令地址)；
   2. 暂存用户标志寄存器：R11 <= RFLAGS；
   3. 加载内核入口地址：RIP <= MSR_LSTAR；
   4. 屏蔽标志位：RFLAGS <= RFLAGS & ~MSR_SFMASK (硬件原子清除 IF，关闭外部中断)；
   5. 特权级原子跃迁：
      - CS.Selector <= MSR_STAR[47:32];
      - CS 描述符属性被硬件强制置为：Base=0, Limit=0xFFFFF, Type=Code, DPL=0, L=1 (64-bit);
      - SS.Selector <= MSR_STAR[47:32] + 8;
      - SS 描述符属性被硬件强制置为：Base=0, Limit=0xFFFFF, Type=Data, DPL=0;
      - CPL 硬件状态机从 3 跃迁为 0 (进入 Ring 0);
   6. 流水线转向 RIP 执行。

.. danger::
   **快速系统调用的关键物理特征——RSP 栈指针保持原样**：
   与 ``INT 0x80`` 自动读取 TSS 并切换栈不同，``SYSCALL`` 指令**完全不触碰 ``RSP`` 寄存器**！
   在进入内核入口 ``entry_SYSCALL_64`` 的第一瞬间，CPU 虽已处于 Ring 0 特权级，但 **``RSP`` 依然指向不可信的用户态内存栈**。如果此时发生中断或压栈，将直接引发内核崩溃或安全漏洞。

4.2 Linux 7.2 内核汇编入口 ``entry_SYSCALL_64`` 的安全切栈
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了解决上述栈安全物理现实，Linux 7.2 内核在 ``arch/x86/entry/entry_64.S`` 中采用了高度精巧的汇编切栈流水线：

::

   SYM_CODE_START(entry_SYSCALL_64)
       UNWIND_HINT_ENTRY
       ENDBR
       swapgs                              /* 1. 交换 GS 寄存器，切换到内核 Per-CPU 区域 */
       movq    %rsp, %gs:scratch_rsp       /* 2. 将用户态 RSP 暂存至 Per-CPU 临时变量 */
       movq    %gs:cpu_current_top_of_stack, %rsp /* 3. 将 RSP 切换为真正的内核栈顶 */

       /* 4. 在内核栈上自底向上构造完整的 pt_regs 结构体 */
       pushq   $__USER_DS                  /* pt_regs->ss */
       pushq   %gs:scratch_rsp             /* pt_regs->sp (刚才暂存的用户 RSP) */
       pushq   %r11                        /* pt_regs->flags (刚才 SYSCALL 硬件暂存在 R11 的用户 RFLAGS) */
       pushq   $__USER_CS                  /* pt_regs->cs */
       pushq   %rcx                        /* pt_regs->ip (刚才 SYSCALL 硬件暂存在 RCX 的用户 RIP) */
       pushq   %rax                        /* pt_regs->orig_ax (系统调用号) */
       ...
       pushq   %rdi; pushq %rsi; pushq %rdx; pushq %rcx; pushq %rax; ... /* 压入其余通用寄存器 */

       call    do_syscall_64               /* 5. 跳转执行 C 语言系统调用分发总函数 */

4.3 ``SYSRET`` 指令微观返回时序
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
当系统调用处理完成、返回值存入 ``RAX`` 后，内核恢复通用寄存器，最后执行机器码 ``48 0F 07``（``SYSRETQ``）：

1. 从 ``RCX`` 寄存器中恢复指令指针：``RIP <= RCX``；
2. 从 ``R11`` 寄存器中恢复标志位：``RFLAGS <= R11``；
3. 从 ``MSR_STAR[63:48]`` 重新计算并加载用户态 ``CS``（Ring 3）与 ``SS``；
4. 特权级从 Ring 0 恢复为 Ring 3；
5. CPU 在下一个时钟周期完全无停顿地从用户态断点推进。

单次快速系统调用的往返开销降至 **10 ~ 20 个 CPU 时钟周期**，较传统软中断提速超过 10 倍。

第五幕：体系结构对比——Intel ``SYSENTER / SYSEXIT``
---------------------------------------------------

在 32 位时代，Intel 曾引入了另一套快速系统调用指令 ``SYSENTER / SYSEXIT``：

* **依赖的 MSR**：
  * ``IA32_SYSENTER_CS (0x174)``：内核代码段；
  * ``IA32_SYSENTER_ESP (0x175)``：内核栈指针（由硬件直接写入 ESP）；
  * ``IA32_SYSENTER_EIP (0x176)``：内核入口地址。
* **物理缺陷**：``SYSENTER`` 不会自动保存返回用户态的 EIP 与 ESP，必须由用户态库（vDSO）在调用前手动将返回地址压入 EBX/EDX，实现极为繁琐。
* **行业归宿**：在 64 位长模式下，AMD 设计的 ``SYSCALL / SYSRET`` 架构凭借更优的寄存器映射语义，成为所有现代 64 位操作系统（包括运行在 Intel CPU 上的 Linux）的标准实现。

第一幕：core.img 物理内存拓扑与宏观架构切片
-------------------------------------------

在传统的引导设计中，加载器往往受限于实模式 1MB 内存与单一磁盘驱动。而 GRUB2 的革命性突破在于将自身构筑为一个具备动态模块扩展能力的 **微型操作系统内核**，其核心载体即为由 ``grub-mkimage`` 工具合成的 **``core.img`` 镜像**。

1.1 core.img 磁盘与内存结构切片
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                                 core.img 内部结构分解                             |
   |                                                                                   |
   |  [第 1 扇区 (512 字节)]                                                           |
   |  - diskboot.S: 包含 Blocklist (扇区物理块列表) 与循环读盘汇编循环                  |
   |            │                                                                      |
   |            ▼ 循环读取剩余扇区至物理内存 0x8200 及以上                             |
   |  [解压器与跳转跳板 (startup_raw.S, 约 2KB)]                                       |
   |  - 16 位实模式入口 -> real_to_prot (保护模式跃迁)                                 |
   |  - grub_gate_a20: 四重保险激活 A20 地址线                                         |
   |  - grub_reed_solomon_recover: 修复 MBR Gap 潜在磁盘数据损坏                       |
   |  - _LzmaDecodeA: LZMA 硬件级流式解压引擎                                          |
   |            │                                                                      |
   |            ▼ 解压缩输出目标地址: 0x00100000 (1MB 物理内存边界)                    |
   |  [解压后的 GRUB2 内核本体 (kernel.exec, 约 100KB ~ 200KB)]                        |
   |  - 内存管理器 (mm.c): 链表堆分配器                                                |
   |  - 动态模块加载器 (dl.c): ELF 符号解析与重定位                                    |
   |  - 设备与虚拟文件系统 (VFS) 抽象层 (disk.c, file.c, fs.c)                         |
   |  - 终端控制与命令解析引擎 (normal.mod, parser, script)                            |
   |  - 预打包基础驱动模块 (如 biosdisk.mod, part_msdos.mod, ext2.mod)                 |
   +-----------------------------------------------------------------------------------+

第二幕：保护模式跃迁与 A20 多重保险激活流水线
---------------------------------------------

在 ``grub-core/boot/i386/pc/startup_raw.S`` 中，当 ``diskboot.S`` 将全部扇区读入内存后，执行长跳转命中位于 ``0x00008200`` 的 ``startup_raw.S:start`` 入口。

2.1 保护模式跃迁（``real_to_prot``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
代码首先在 16 位实模式下重置段寄存器与栈，随后立即调用实模式向保护模式转换跳板 ``real_to_prot``：

::

   /* 16 位实模式代码 */
   LOCAL (codestart):
       cli
       xorw    %ax, %ax
       movw    %ax, %ds
       movw    %ax, %ss
       movw    %ax, %es
       movl    $GRUB_MEMORY_MACHINE_REAL_STACK, %ebp /* 设置实模式临时栈 */
       movl    %ebp, %esp
       sti
       movb    %dl, LOCAL(boot_drive) /* 保存物理启动盘号 */

       /* 跃迁进入 32 位保护模式 */
       calll   real_to_prot

       .code32
       cld
       call    grub_gate_a20          /* 在 32 位模式下开启 A20 地址线 */

2.2 A20 地址线四重激活算法（``grub_gate_a20``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
A20 地址线是否真正导通，直接决定了 CPU 访问 1MB（``0x100000``）以上物理内存时是否会发生致命的回绕（Wrap-around）。GRUB2 在 ``startup_raw.S`` 中实现了一套被称为“四重保险”的工业级探测与激活流水线：

::

   +-----------------------------------------------------------------------------------+
   |                           grub_gate_a20 激活状态机                                |
   |                                                                                   |
   |  [步骤 1：状态检查 (gate_a20_check_state)]                                        |
   |  - 向 0x00008000 写入数值 A，向 0x00108000 (1MB+8000) 写入数值 A-1;              |
   |  - 读回 0x00008000: 若数值发生改变，说明两处物理地址发生回绕 (A20 未开启);        |
   |  - 若数值保持独立，说明 A20 已开启，直接退出成功!                                |
   |            │ (未开启)                                                             |
   |            ▼                                                                      |
   |  [步骤 2：尝试 BIOS 标准中断服务 (INT 15h, AX=0x2401)]                            |
   |  - 切回实模式调用 INT 15h 启用 A20 门控，切回保护模式再次检测;                    |
   |            │ (仍未开启)                                                           |
   |            ▼                                                                      |
   |  [步骤 3：尝试系统控制端口 A (System Control Port A, I/O 0x92)]                   |
   |  - 读取端口 0x92: inb $0x92, %al                                                  |
   |  - 置位 Bit 1:    orb $0x02, %al; outb %al, $0x92 (快速 A20 激活)                 |
   |  - 重新检测 A20 状态;                                                             |
   |            │ (仍未开启)                                                           |
   |            ▼                                                                      |
   |  [步骤 4：尝试 8042 键盘控制器 (Keyboard Controller)]                             |
   |  - 向命令端口 0x64 发送 0xD1 (写输出端口命令);                                    |
   |  - 等待输入缓冲清空，向数据端口 0x60 发送 0xDF (将 A20 选通引脚拉高);             |
   |  - 最终循环 100 次复检，确保 1MB 以上地址线 100% 导通。                           |
   +-----------------------------------------------------------------------------------+

第三幕：里德-所罗门纠错与 LZMA 物理内存自解压
---------------------------------------------

3.1 里德-所罗门（Reed-Solomon）磁盘坏块自动修复
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
由于 MBR Gap（LBA 1 ~ 2047）在传统磁盘分区表中属于未定义区域，部分老旧杀毒软件、Windows 激活工具或流氓引导扇区修改器可能会误写该区域的部分扇区，导致 ``core.img`` 字节损坏。

GRUB2 在编译 ``core.img`` 时，利用 **里德-所罗门编码（Reed-Solomon Code）** 计算冗余校验块，并在解压前调用 ``grub_reed_solomon_recover()``：
* **数学纠错能力**：即使磁盘上的 ``core.img`` 连续若干个扇区发生比特翻转或被覆盖破坏，纠错算法能够自动在内存中重建出完好无损的原始压缩数据流，极大提升了引导生存能力。

3.2 LZMA 流式解压缩向 1MB 内存边界的物理搬迁
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
纠错完成后，控制权交由精简版汇编 LZMA 解压器 ``_LzmaDecodeA``（``lzma_decode.S``）：

::

   post_reed_solomon:
       movl    $GRUB_MEMORY_MACHINE_DECOMPRESSION_ADDR, %edi /* 目标地址: 0x00100000 (1MB) */
       movl    $LOCAL(decompressor_end), %esi                /* 压缩源数据起始地址 */
       movl    LOCAL(uncompressed_size), %ecx                /* 解压后内核总字节数 */
       pushl   %edi
       pushl   %ecx
       call    _LzmaDecodeA                                  /* 执行 LZMA 算法解压 */
       popl    %ecx
       popl    %esi                                          /* ESI 恢复为 0x00100000 */

       /* 传递运行时跳板参数给 GRUB2 内核 */
       movl    LOCAL(boot_dev), %edx                         /* EDX = 启动磁盘设备号 */
       movl    $prot_to_real, %edi                           /* EDI = 保护模式转实模式函数指针 */
       movl    $real_to_prot, %ecx                           /* ECX = 实模式转保护模式函数指针 */
       movl    $LOCAL(realidt), %eax                         /* EAX = 实模式 IDT 结构体指针 */
       
       jmp     *%esi                                         /* 最终长跳转：进入 0x100000 处的 GRUB2 内核! */

在这一跳中，CPU 正式脱离了实模式 1MB 低端内存的物理束缚，全面进驻 1MB 以上的高端物理内存（High Memory），开启了现代化 C 语言内核的执行环境。

第四幕：GRUB2 动态模块子系统 (dl.c) 架构
-----------------------------------------

进入 ``grub_main()`` 后，GRUB2 面临着与宏内核（Monolithic Kernel）类似的设计抉择：如何支持成百上千种不同的文件系统（ext4, xfs, btrfs, zfs, fat）、磁盘阵列（LVM, RAID, LUKS 加密）与终端命令？

GRUB2 的核心中枢仅仅是一个微内核，所有外围驱动均被编译为独立的 **ELF 目标文件（``.mod`` 模块）**，由动态模块加载器 **``grub-core/kern/dl.c``** 进行运行时按需装载。

4.1 核心数据结构解构（``include/grub/dl.h``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   struct grub_dl {
       char *name;                 /* 模块名称 (如 "ext2", "part_gpt") */
       int ref_count;              /* 引用计数 (防止被正在使用的其他模块意外卸载) */
       struct grub_dl_dep *dep;    /* 该模块依赖的父模块单向链表 */
       struct grub_dl_segment *segment; /* 加载到内存中的各个 ELF 节区段链表 */
       void (*init)(struct grub_dl *); /* 模块初始化入口 (如 grub_mod_init) */
       void (*fini)(void);         /* 模块卸载析构函数 */
       void *base;                 /* 模块在堆中分配的内存基地址 */
       grub_size_t sz;             /* 模块总占用内存字节数 */
       struct grub_dl *next;       /* 挂载在全局已加载模块链表 (grub_dl_head) */
   };

第五幕：运行时 ELF 节区重定位与开链哈希符号解析
-----------------------------------------------

在 ``grub-core/kern/dl.c:grub_dl_load_core_noinit()`` 中，一个 ``.mod`` 模块的装载经历 6 个精密的链接步骤：

::

   [磁盘 .mod 文件 / 内存中的 ELF 目标文件]
                    │
                    ▼
   1. grub_dl_check_header(): 校验 ELF32/ELF64 头部魔数 (0x7F 'E' 'L' 'F') 与架构合法性
                    │
                    ▼
   2. grub_dl_resolve_dependencies(): 解析 .moddeps 节区，递归调用 grub_dl_load() 加载依赖模块
                    │
                    ▼
   3. grub_dl_load_segments(): 扫描所有 SHF_ALLOC 节区 (.text, .data, .rodata, .bss)，
      在堆中通过 grub_memalign() 分配对齐空间并拷贝数据
                    │
                    ▼
   4. grub_dl_resolve_symbols(): 遍历模块符号表 (SHT_SYMTAB)，进行符号未决解析与全局导出
                    │
                    ▼
   5. grub_dl_relocate_symbols(): 遍历重定位表 (SHT_REL / SHT_RELA)，修复代码中的绝对/相对地址
                    │
                    ▼
   6. 执行模块构造函数 mod->init(mod) ──► 将驱动正式挂载入 GRUB2 全局服务树!

5.1 开链哈希全局符号表（``grub_symtab[509]``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了支持模块之间以及模块与内核之间的函数调用（如 ext4 模块调用内核的 ``grub_malloc`` 与 ``grub_disk_read``），GRUB2 在内存中维护了一个大小为 509 的 **开链哈希全局符号表**：

::

   #define GRUB_SYMTAB_SIZE 509
   static struct grub_symbol *grub_symtab[GRUB_SYMTAB_SIZE];

   /* 经典乘法哈希函数 */
   static unsigned grub_symbol_hash(const char *s) {
       unsigned key = 0;
       while (*s)
           key = key * 65599 + *s++;
       return (key + (key >> 5)) % GRUB_SYMTAB_SIZE;
   }

当新模块导出符号时，通过 ``grub_dl_register_symbol()`` 挂入哈希链表；当模块需要引用外部函数时，通过 ``grub_dl_resolve_symbol()`` 在哈希表中 $O(1)$ 时间复杂度获取其物理绝对地址。

5.2 重定位表项修复微观时序（``SHT_REL``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在编译期，模块内部调用外部函数处的机器码地址被填为 0。在装载阶段，``grub_dl_relocate_symbols()`` 遍历所有重定位条目：

* **``R_386_32 / R_X86_64_64`` (绝对地址重定位)**：
  $$	ext{Target\_Location} \leftarrow 	ext{Target\_Location} + 	ext{Symbol.Value}$$
* **``R_386_PC32 / R_X86_64_PC32`` (相对程序计数器跳转重定位)**：
  $$	ext{Target\_Location} \leftarrow 	ext{Target\_Location} + 	ext{Symbol.Value} - 	ext{Current\_PC\_Address}$$

通过这一指令修补过程，ELF 目标文件被完全动态链接为可直接在 32 位/64 位保护模式下原生执行的二进制代码。

小结与下章导读
--------------

本节深入剖析了 GRUB2 ``core.img`` 核心镜像的物理架构、``startup_raw.S`` 保护模式跃迁、A20 地址线四重激活算法、里德-所罗门坏块纠错、LZMA 向 1MB 内存解压，以及 ``dl.c`` 动态模块加载器与 ELF 符号重定位的完整微观流水线。

动态模块引擎就绪后，GRUB2 获得了动态加载文件系统驱动的能力。它将开始挂载磁盘分区并寻找配置文件。

在 **第 3 节：最小文件系统驱动实现（ext2/4, FAT, Btrfs）与 ``/boot/grub/grub.cfg`` 语法解析引擎** 中，我们将深入剖析 GRUB2 如何在不依赖操作系统的环境下实现 ext4 Inode 查找、Extent 树解析，以及如何解析 ``grub.cfg`` 脚本语法以生成交互式启动菜单。

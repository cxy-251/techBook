第一幕：vmlinuz 复合二进制容器的物理结构全景解构
-----------------------------------------------

在 Linux 磁盘的 ``/boot`` 目录下，我们看到的 ``vmlinuz-7.2-generic`` 并非一个常规的 ELF 可执行文件，而是一个精心设计的 **复合多架构自解压容器（Hybrid Self-Extracting Container）**。

1.1 vmlinuz 物理宏观切片（双阶段混合架构）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

::

   +-----------------------------------------------------------------------------------+
   |                                 vmlinuz 复合容器物理布局                          |
   |                                                                                   |
   |  [阶段一：实模式存根与头部 setup.bin (大小由 setup_sects 决定, 通常 16KB ~ 32KB)] |
   |  0x0000 ┌────────────────────────────────────────────────────────┐                |
   |         │ MS-DOS 存根 ("MZ" 魔数 0x5A4D) + PE/COFF 头部 (EFISTUB)  │                |
   |  0x01F1 ├────────────────────────────────────────────────────────┤                |
   |         │ struct setup_header (包含 "HdrS" 签名、协议版本 0x020F) │                |
   |  0x0290 ├────────────────────────────────────────────────────────┤                |
   |         │ 16 位实模式 setup 代码 (main.c, memory.c, cpu.c)         │                |
   |         │ (负责在古老引导器下探测 BIOS/E820 并切入保护模式)        │                |
   |  setup_end └─────────────────────────────────────────────────────┘                |
   |                                                                                   |
   |  [阶段二：保护模式解压器与压缩内核负载 vmlinux.bin (通常 10MB ~ 25MB)]            |
   |  0x0000 ┌────────────────────────────────────────────────────────┐                |
   |         │ 32 位保护模式入口 (arch/x86/boot/compressed/head_64.S)  │ ◄─ GRUB2 直接  |
   |         │ (标号 startup_32，由 setup_header.code32_start 唯一定位)│    跳转命中点! |
   |         ├────────────────────────────────────────────────────────┤                |
   |         │ 64 位长模式跳板与早期页表构建代码 (head_64.S)          │                |
   |         ├────────────────────────────────────────────────────────┤                |
   |         │ C 语言解压引擎 (misc.c, Zstandard / XZ 解压算法)       │                |
   |         ├────────────────────────────────────────────────────────┤                |
   |         │ 压缩的内核本体裸数据 (vmlinux.bin.zst)                 │                |
   |         │ (由真正的 uncompressed ELF64 vmlinux 剥离调试信息后压缩)│                |
   |  _end   └────────────────────────────────────────────────────────┘                |
   +-----------------------------------------------------------------------------------+

1.2 内核编译装配流水线（``arch/x86/boot/tools/build.c``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 Linux 内核编译完成的最后一步，内核构建系统通过 ``tools/build.c`` 工具执行二进制缝合：
1. **生成未压缩内核 ELF**：链接器将各子系统对象链接为根目录下的 ``vmlinux``（ELF64 格式，包含完整符号与 DWARF 调试信息，体积高达 100MB ~ 250MB）；
2. **提取纯裸二进制**：使用 ``objcopy -O binary -R .note -R .comment vmlinux vmlinux.bin`` 剥离所有元数据与符号表；
3. **极限算法压缩**：调用选定的压缩器（如 ``zstd -19`` 或 ``xz``）生成 ``vmlinux.bin.zst``；
4. **构建自解压 ELF**：将压缩数据与 ``arch/x86/boot/compressed/`` 下的解压器汇编代码链接为 ``compressed/vmlinux``；
5. **最终容器缝合**：``build.c`` 依次读取编译好的 ``setup.bin`` 与 ``compressed/vmlinux.bin``，计算对齐填充（Padding），并在头部回填 ``setup_sects`` 与 ``syssize`` 字段，生成最终交付磁盘的 ``vmlinuz``。

第二幕：UEFI/BIOS 双模自适应：PE/COFF 头部与 EFISTUB 机制
---------------------------------------------------------

在现代计算机体系中，一套内核镜像必须同时支持 **传统 Legacy BIOS** 与 **现代 UEFI（含 Secure Boot 安全启动）**。Linux 采用了一种巧妙的格式模拟机制——**EFISTUB (EFI Boot Stub)**。

2.1 PE/COFF 头部的伪装嵌入（``arch/x86/boot/header.S``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``header.S`` 中，内核源码在最前端直接硬编码了 Windows PE32+（Portable Executable）可执行文件格式头部：

::

   .code16
   .section ".bstext", "ax"
   #ifdef CONFIG_EFI_STUB
       /* 1. MS-DOS 兼容魔数 "MZ" (0x5A4D) */
       .word   IMAGE_DOS_SIGNATURE
       .org    0x38
       
       /* 2. 偏移 0x3C 处写入指向 PE 头部的相对偏移 */
       .long   LINUX_PE_MAGIC
       .long   pe_header

   pe_header:
       /* 3. PE 签名 "PE\0\0" (IMAGE_NT_SIGNATURE) */
       .long   IMAGE_NT_SIGNATURE

   coff_header:
       .word   IMAGE_FILE_MACHINE_AMD64        /* 目标架构: x86_64 */
       .word   section_count                   /* 节区数量: .setup, .text, .data, .sbat */
       ...
   optional_header:
       .word   IMAGE_NT_OPTIONAL_HDR64_MAGIC   /* PE32+ 64 位可选头部 */
       .long   setup_size + ZO_efi_pe_entry    /* AddressOfEntryPoint (UEFI 直接执行入口!) */
       .word   IMAGE_SUBSYSTEM_EFI_APPLICATION /* 子系统类型: EFI 应用程序 */
   #endif

2.2 双模引导分发时序
~~~~~~~~~~~~~~~~~~~~
* **当在传统 BIOS 下由 GRUB2 引导时**：
  * GRUB2 识别 ``vmlinuz`` 中的 ``"HdrS"`` 签名，将 ``setup.bin`` 读入低端内存解析参数，并将阶段二的保护模式解压代码完整读入物理内存 **``0x00100000 (1MB)``**，随后执行 ``jmpl *0x100000`` 进入 ``startup_32``；
* **当在 UEFI 固件下直接引导时**：
  * UEFI 固件读取文件开头的 ``"MZ"`` 与 ``"PE"`` 签名，将整个 ``vmlinuz`` 当作标准的 64 位 EFI 应用程序载入内存，并直接调用 ``ZO_efi_pe_entry`` 处的 EFISTUB 驱动代码；
  * EFISTUB 调用 UEFI 固件的 ``GetMemoryMap()`` 与图形输出协议（GOP），在内存中动态组装 ``struct boot_params``，随后自行退出 EFI 启动服务（``ExitBootServices``）跃迁进入 Linux 内核！

第三幕：initramfs / initrd 初始内存盘的物理装载与 CPIO 格式
-----------------------------------------------------------

在现代 Linux 发行版中，根文件系统往往存放在极为复杂的存储拓扑中（如 NVMe 阵列、LVM 逻辑卷、Btrfs 多盘池、LUKS 全盘加密或 iSCSI 网络挂载）。

Linux 内核不可能将成百上千种驱动、LVM 工具与解密密钥管理器全部静态编译进内核本体。因此，必须由引导加载器在启动阶段将一个最小内存根文件系统——**``initramfs``（初始 RAM 文件系统）** 载入物理内存。

3.1 CPIO Newc 归档文件封装规范
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``initramfs`` 在本质上是一个由 Gzip / XZ / Zstd 压缩的 **CPIO 格式归档包**。在其解压后的数据流中，每一个文件与目录均以标准的 110 字节文本头 **``struct cpio_newc_header``** 起始：

::

   +-----------------------------------------------------------------------------------+
   |                 struct cpio_newc_header (110 字节 ASCII 文本头部)                 |
   |                                                                                   |
   |  偏移    大小    字段名称        物理含义与十六进制 ASCII 编码 (如 "00000001")    |
   +===================================================================================+
   |  0x00    6 B     c_magic         CPIO 魔数: 固定为 ASCII 字符串 "070701" (Newc 格式) |
   |  0x06    8 B     c_ino           文件 Inode 编号                                  |
   |  0x0E    8 B     c_mode          文件类型与 POSIX 权限位 (目录/常规文件/设备节点) |
   |  0x16    8 B     c_uid           文件属主 UID                                     |
   |  0x1E    8 B     c_gid           文件属组 GID                                     |
   |  0x26    8 B     c_nlink         硬链接计数                                       |
   |  0x2E    8 B     c_mtime         最后修改时间戳                                   |
   |  0x36    8 B     c_filesize      文件实际数据字节长度 (Hex 格式)                  |
   |  0x5E    8 B     c_namesize      文件名长度 (包含末尾 '\0')                       |
   |  0x6E    ...     filename        文件名字符串 (紧随其后, 4 字节自然对齐)          |
   |  ...     ...     file_data       文件实际二进制内容 (4 字节自然对齐)              |
   +-----------------------------------------------------------------------------------+

* **归档结束标记**：整个 CPIO 镜像的最后一个表项是一个特殊文件，其 ``c_namesize = 11``，文件名为 **``"TRAILER!!!"``**，内核解析到该标记即终止解包。

3.2 高端物理内存安全装载流水线（``grub_cmd_initrd``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 GRUB2 源码 ``grub-core/loader/i386/linux.c:grub_cmd_initrd()`` 中，装载内存盘必须遵循严密的物理地址裁决：

::

   +-----------------------------------------------------------------------------------+
   |                          initramfs 高端物理内存装载状态机                         |
   |                                                                                   |
   |  [步骤 1：确定物理地址上限 initrd_addr_max]                                       |
   |  - 从 setup_header.initrd_addr_max (通常为 0x7FFFFFFF, 即 2GB 边界) 读取上限;      |
   |                                                                                   |
   |  [步骤 2：在 E820 内存图中自顶向下安全分配]                                       |
   |  - 扫描所有 E820_RAM 可用物理内存块;                                              |
   |  - 在 2GB 以下的高位内存找到一段连续且未被占用的内存区 (满足 4KB 页面边界对齐);   |
   |  - 分配起始物理地址: ramdisk_paddr (如 0x07000000, 约 112MB 物理位置);          |
   |                                                                                   |
   |  [步骤 3：从磁盘流式读取 initramfs 镜像]                                          |
   |  - 调用 grub_file_read() 将 initramfs 文件全量写入 ramdisk_paddr;                |
   |                                                                                   |
   |  [步骤 4：回填零页 struct boot_params 字段]                                       |
   |  - boot_params.hdr.ramdisk_image = ramdisk_paddr (32 位物理基地址)                |
   |  - boot_params.hdr.ramdisk_size  = initramfs_file_size (字节总数)                 |
   +-----------------------------------------------------------------------------------+

第四幕：全模块总结与从引导加载器到内核解压器的世纪交接
------------------------------------------------------

至此，**模块 04：GRUB2 引导加载器与内核协议握手** 全部 6 个核心章节已全量落盘！

我们系统化完成了计算机从磁盘 MBR 裸扇区到 32 位平坦保护模式、多文件系统解析与内核协议握手的全景物理演进：
1. **MBR 极限空间**：``boot.S`` 在 446 字节内利用 LBA/CHS 读取第 1 扇区并跳转 ``diskboot.S (0x8000)``；
2. **核心镜像蜕变**：``core.img`` 载入内存、``startup_raw.S`` 跃迁保护模式、A20 四重激活、Reed-Solomon 纠错与 ``dl.c`` 动态模块加载；
3. **文件系统与脚本**：微型 VFS 抽象、ext4 Extent 树多级索引解析、FAT32 簇链追踪、Btrfs B-Tree 键值检索与 ``grub.cfg`` 交互式菜单；
4. **模式穿越准备**：GDT 段描述符 8 字节位域编码、``real_to_prot`` 与 ``prot_to_real`` 双向跳板时序与流水线长跳转冲刷；
5. **协议握手标准**：Linux Boot Protocol 规范、512 字节 ``setup_header`` 与 4096 字节 ``struct boot_params``（零页 Zero Page）全量参数装配；
6. **镜像与内存盘**：``vmlinuz`` 复合容器解构、EFISTUB 双模兼容与 initramfs 在高端内存（2GB 以下）的连续对齐装载。

现在，整机物理内存已经呈现出完美的交接镜像：
* 零页 ``struct boot_params`` 安放在 **``0x00090000``**；
* 命令行参数紧随其后存放在 **``0x00091000``**；
* 初始内存盘 ``initramfs`` 驻留在 **``0x07000000``**；
* ``vmlinuz`` 解压缩引擎与压缩内核镜像驻留在 **``0x00100000 (1MB)``**；
* CPU 处于 **32 位平坦保护模式**，``ESI = 0x00090000``，硬件中断全局关闭。

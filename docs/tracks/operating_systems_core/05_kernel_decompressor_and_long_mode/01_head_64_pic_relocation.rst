========================================================================================
第 1 节：解压器入口 arch/x86/boot/compressed/head_64.S 与位置无关代码 (PIC) 物理重定位
========================================================================================

.. note::
   **前置背景与上下文承接**
   * **体系结构基准**：承接模块 04 第 6 节中关于 GRUB2 将 ``vmlinuz`` 压缩内核镜像写入物理内存 ``0x00100000 (1MB)``、装配零页 ``struct boot_params (0x00090000)``，并通过 ``ESI=0x90000, jmpl *0x100000`` 正式向 Linux 7.2 内核交接控制权的物理状态。
   * **核心使命**：解构 Linux 7.2 内核在裸机上执行的第一行机器指令；剖析自解压器汇编入口 ``arch/x86/boot/compressed/head_64.S:startup_32`` 的微观执行环境；深入解构位置无关代码（PIC）运行期 Delta 偏移量动态测算算法（利用 ``call 1f; popl %ebp`` 硬件指令指针偷取技术）；逐行剖析 GDT 动态自修补（Self-Patching）、双字对齐段选择子加载、``verify_cpu`` 64 位 CPUID 特性硬件嗅探、原地安全解压重定位目标基址（``BP_init_size``）计算公式，以及由 32 位保护模式向 64 位长模式平滑过渡的微观时钟时序。

第一幕：内核的第一纳秒——``startup_32`` 汇编入口与物理执行环境
--------------------------------------------------------------

当 CPU 在引导加载器的推动下跨越物理地址 ``0x00100000`` 时，系统正式脱离了 BIOS 与 GRUB2 的所有软件上下文，进入 Linux 7.2 内核自解压器的最前端汇编入口——**``arch/x86/boot/compressed/head_64.S:startup_32``**。

1.1 握手瞬间的 CPU 物理寄存器状态
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在此刻，硬件寄存器严格遵循 32 位 Linux Boot Protocol 契约：

::

   +-----------------------------------------------------------------------------------+
   |                    startup_32 入口时刻 CPU 绝对硬件物理状态                       |
   |                                                                                   |
   |  - CR0 寄存器:    CR0.PE = 1 (32 位保护模式开启), CR0.PG = 0 (分页机制未开启!)    |
   |  - EFLAGS 寄存器: EFLAGS.IF = 0 (全局关闭外部硬件中断)                            |
   |  - EIP 寄存器:    0x00100000 (或加载器指定的解压器入口物理基地址)                |
   |  - ESI 寄存器:    0x00090000 (严格指向 4096 字节 struct boot_params 零页物理地址)|
   |  - EAX..EDX:      0x00000000 (全部清零)                                           |
   |  - 地址空间:      平坦物理寻址 (Flat Physical Address Space, 0x00000000..0xFFFFFFFF)|
   +-----------------------------------------------------------------------------------+

1.2 初始指令序列与流水线清理
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``head_64.S`` 的最前几条指令执行严密的状态重置：

::

   .code32
   SYM_FUNC_START(startup_32)
       cld                         /* 清除方向标志 (DF=0, 字符串指令自增) */
       cli                         /* 确保全局关中断 (防止无 IDT 触发硬件中断崩溃) */

第二幕：位置无关代码 (PIC) Delta 偏移量动态测算算法
---------------------------------------------------

在传统的静态编译中，程序中的所有全局变量和跳转标号都被硬编码为固定的链接地址（Link-Time Address，通常假定基地址为 0 或 1MB）。

然而在现代 Linux 系统中：
* **KASLR (内核地址空间布局随机化)** 会在启动时将内核随机放置在任意物理内存页；
* **UEFI EFI Stub** 会根据固件内存映射将内核分配到高位物理内存；
* 因此，自解压器代码必须被编译为 **位置无关代码（Position Independent Code, PIC/PIE）**，并在运行期的第一时间动态测算出“实际加载地址”与“编译期标称地址”之间的差值——**Delta 偏移量**。

2.1 “指令指针偷取”硬件技巧微观解构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 32 位 x86 架构中，CPU 没有提供直接读取 ``EIP`` 寄存器的机器指令（64 位下的 ``RIP-relative`` 寻址在 32 位保护模式下不可用）。

Linux 内核在 ``head_64.S`` 中采用了一种绝妙的 **利用调用栈偷取指令指针（EIP Stealing via Stack）** 的硬件技巧：

::

   +-----------------------------------------------------------------------------------+
   |                           Delta 偏移量动态测算汇编流水线                          |
   |                                                                                   |
   |  /* 1. 临时栈借调：借用零页中预留的 4 字节 scratch 字段作为极简临时调用栈 */      |
   |  leal    (BP_scratch+4)(%esi), %esp                                               |
   |                                                                                   |
   |  /* 2. 近调用：硬件将下一条指令的绝对物理地址 (即标号 1f 的真实 EIP) 压入栈顶! */ |
   |  call    1f                                                                       |
   |                                                                                   |
   |  1:                                                                               |
   |  /* 3. 弹出真实绝对地址：将刚刚压栈的真实物理 EIP 弹出至 %ebp 寄存器 */           |
   |  popl    %ebp                                                                     |
   |                                                                                   |
   |  /* 4. 减去编译期标称偏移：rva(1b) = (1b - startup_32) */                         |
   |  subl    $ rva(1b), %ebp                                                          |
   +-----------------------------------------------------------------------------------+

.. important::
   **Delta 测算的物理数学本质**：
   * ``call 1f`` 压入栈顶的是当前物理内存中标号 ``1:`` 的 **绝对运行时物理地址** $	ext{Phys}(1)$;
   * ``rva(1b)`` 是标号 ``1:`` 相对 ``startup_32`` 的 **编译期相对偏移量** $\Delta_{	ext{offset}}$;
   * 执行减法后：
     $$\%ebp = 	ext{Phys}(1) - \Delta_{	ext{offset}} \equiv \mathbf{	ext{Phys}(startup\_32)}$$
   * **物理意义**：从此刻起，``%ebp`` 寄存器中永久且精准地锁定了当前内核在物理内存中的真实基地址！后续所有数据访问均通过 ``rva(Symbol)(%ebp)`` 转换以实现绝对精确的物理寻址。

第三幕：GDT 动态自修补与段寄存器重构
-----------------------------------

尽管引导加载器（GRUB2）此前已经建立了 GDT，但解压器不能对其产生任何外部依赖。解压器必须在内存中构建属于自己的、包含 64 位长模式描述符的独立 GDT。

3.1 GDT 描述符的动态自修补（Self-Patching）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``head_64.S`` 的数据段中，定义了新的 GDT 表：

::

   SYM_DATA_START_LOCAL(gdt)
       .word   gdt_end - gdt - 1       /* 16 位 Limit 界限 */
       .long   0                       /* 32 位 Base 基地址 (编译期填 0, 需运行时动态修补!) */
       .word   0                       /* 对齐填充 */
       .quad   0x00cf9a000000ffff      /* 选择子 0x10: __KERNEL32_CS (32 位兼容代码段) */
       .quad   0x00af9a000000ffff      /* 选择子 0x18: __KERNEL_CS   (64 位长模式代码段) */
       .quad   0x00cf92000000ffff      /* 选择子 0x20: __KERNEL_DS   (32/64 位平坦数据段) */
       .quad   0x0080890000000000      /* TSS 任务状态段描述符 */
       .quad   0x0000000000000000
   SYM_DATA_END_LABEL(gdt, SYM_L_LOCAL, gdt_end)

由于编译期填入的 Base 为 0，内核在运行时必须动态计算 GDT 的真实物理地址并回填（Self-Patching）：

::

   /* 计算当前物理内存中 gdt 的绝对基地址 */
   leal    rva(gdt)(%ebp), %eax

   /* 将绝对地址回填写入 GDT 头部偏移 2 字节处的 Base 字段 */
   movl    %eax, 2(%eax)

   /* 重新加载片内 GDTR 寄存器 */
   lgdt    (%eax)

3.2 段寄存器与代码段 CS 刷新
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. **数据段加载**：将 ``__BOOT_DS (0x20)`` 载入 ``DS, ES, FS, GS, SS``；
2. **私有栈建立**：将 ``ESP`` 切换至解压器专属内部栈 ``boot_stack_end``（位于 ``.bss`` 段）；
3. **远返回强制刷新 CS**：

::

   pushl   $__KERNEL32_CS          /* 压入 32 位代码段选择子 0x10 */
   leal    rva(1f)(%ebp), %eax     /* 压入标号 1f 的绝对物理地址 */
   pushl   %eax
   lretl                           /* 执行 32 位远返回，强制刷新 CS 描述符缓存! */
   1:

第四幕：``verify_cpu`` 硬件特性嗅探与 64 位长模式兼容性验证
-----------------------------------------------------------

在尝试开启 64 位长模式之前，解压器必须验证底层物理 CPU 是否真正具备 64 位处理能力。

4.1 ``verify_cpu.S`` 汇编检测流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``arch/x86/kernel/verify_cpu.S`` 中：

::

   +-----------------------------------------------------------------------------------+
   |                           verify_cpu 硬件特性检测状态机                           |
   |                                                                                   |
   |  [步骤 1：EFLAGS.ID 位翻转检测 (验证 CPUID 指令可用性)]                           |
   |  - 尝试翻转 EFLAGS 寄存器的 Bit 21 (ID 位);                                       |
   |  - 若翻转失败，说明 CPU 是古老的 i486 之前处理器，完全不支持 CPUID 指令!         |
   |                                                                                   |
   |  [步骤 2：查询扩展功能支持上限]                                                   |
   |  - 执行 cpuid (EAX = 0x80000000);                                                 |
   |  - 读回 EAX: 必须 >= 0x80000001 (必须支持扩展功能探测);                           |
   |                                                                                   |
   |  [步骤 3：验证 Long Mode (LM) 硬件支持]                                           |
   |  - 执行 cpuid (EAX = 0x80000001);                                                 |
   |  - 检查 EDX 寄存器 Bit 29 (Long Mode Flag, LM);                                   |
   |  - 若 EDX[29] == 1: CPU 具备完整的 x86_64 硬件长模式引擎，返回 EAX=0 成功!        |
   |  - 若 EDX[29] == 0: 纯 32 位 CPU，返回 EAX=1 失败 ──► 进入 .Lno_longmode 死循环  |
   +-----------------------------------------------------------------------------------+

第五幕：原地安全解压重定位目标物理地址计算公式
----------------------------------------------

在解压缩过程中，解压引擎需要将压缩的内核数据（``vmlinux.bin.zst``）解压为庞大的未压缩内核。

5.1 内存重叠与缓冲区超限（Buffer Overrun）危机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* 如果解压器直接在当前加载位置原地解压，由于未压缩数据的膨胀速度极快，解压输出指针（Output Pointer）很可能会超越压缩数据读取指针（Input Pointer），导致**尚未读取的后续压缩数据被已经解压的数据所覆写破坏**！

::

   危险场景 (原地解压冲突):
   [解压输出指针 ──► 快速膨胀] ───────► (发生碰撞!) ◄─────── [压缩数据输入指针]

5.2 安全移动目标物理地址计算（``%ebx``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
为了绝对避免碰撞，内核采用了一种将自身向高端内存临时后移的策略。在 ``startup_32`` 中：

::

   #ifdef CONFIG_RELOCATABLE
       movl    %ebp, %ebx
       movl    BP_kernel_alignment(%esi), %eax  /* 读取内核对齐粒度 (通常为 2MB) */
       decl    %eax
       addl    %eax, %ebx
       notl    %eax
       andl    %eax, %ebx                       /* 向上按 2MB 边界对齐 */
       cmpl    $LOAD_PHYSICAL_ADDR, %ebx
       jae     1f
   #endif
       movl    $LOAD_PHYSICAL_ADDR, %ebx        /* 默认保底基地址 0x01000000 (16MB) */
   1:
       /* 最终重定位目标地址 %ebx 计算公式 */
       addl    BP_init_size(%esi), %ebx
       subl    $ rva(_end), %ebx

.. math::

   \%ebx = 	ext{Target\_Decompress\_Base} + 	ext{init\_size} - 	ext{Compressed\_Image\_Size}

通过该公式，内核将压缩镜像精准搬移至整个解压缓冲区（由 ``init_size`` 预留的数十兆空间）的最末端。此后，解压缩引擎从末端向前读取压缩数据，从前端向后写入解压内核，两者背道而驰，**在数学上彻底杜绝了内存覆写冲突**！

小结与下章导读
--------------

本节深入剖析了 Linux 7.2 内核自解压器的入口 ``startup_32``、位置无关代码（PIC）的物理基地址 Delta 动态测算算法、运行时 GDT 自修补、``verify_cpu`` 64 位长模式特性验证，以及原地安全解压重定位目标基址的数学计算公式。

在物理内存与重定位目标确定后，CPU 面临着体系结构历史上最关键的一跃——构建 64 位分页表，开启物理地址扩展（PAE）与长模式使能（EFER.LME），正式跨入 64 位长模式（IA-32e）。

在 **第 2 节：早期页表构建：1GB/2MB 大页恒等映射与开启 64 位长模式 (IA-32e)** 中，我们将深入剖析 4 级页表（PML4 / PDPT / PD）在内存中的逐级装配、2048 个 2MB 大页覆盖 4GB 物理空间的数学时序，以及通过切换 ``CR3``、``MSR_EFER`` 与 ``CR0.PG`` 激活 64 位长模式并跳转进入 ``startup_64`` 的全过程。

第一幕：未压缩内核 ELF64 物理容器与 ``vmlinux.lds.S`` 链接拓扑
--------------------------------------------------------------

在解压缩完成后，输出物理缓冲区中呈现的是由 Linux 内核顶层链接脚本 **``arch/x86/kernel/vmlinux.lds.S``** 严密排布的未压缩内核 ELF64 映像。

1.1 64 位高位虚拟地址空间拓扑（High-Half Kernel Mapping）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 64 位 x86_64 体系下，Linux 内核不运行在物理低端内存，而是被链接在 64 位地址空间的最高端 2GB 区域（即著名的 ``__START_KERNEL_map`` 顶层映射区）：

::

   +-----------------------------------------------------------------------------------+
   |                       Linux 64 位内核顶层虚拟地址空间拓扑                         |
   |                                                                                   |
   |  0x0000000000000000 ~ 0x00007FFFFFFFFFFF (128TB): 用户态空间 (User Space)         |
   |  ──────────────────────────────────────────────────────────────────────────────── |
   |  0xFFFF800000000000 ~ 0xFFFFFFFFFFFFFFFF (128TB): 内核态空间 (Kernel Space)       |
   |       │                                                                           |
   |       ├─► 0xFFFF888000000000: 直接物理内存映射区 (PAGE_OFFSET, Direct Mapping)     |
   |       ├─► 0xFFFFC90000000000: vmalloc 动态虚拟内存分配区                          |
   |       ├─► 0xFFFFFFFF80000000: __START_KERNEL_map (内核静态映像顶端 2GB 映射基址)   |
   |       │        │                                                                  |
   |       │        ├─► 0xFFFFFFFF81000000: _text (内核代码段起始基地址)                |
   |       │        ├─► 0xFFFFFFFF82000000: __start_rodata (只读数据段)                |
   |       │        ├─► 0xFFFFFFFF83000000: _sdata (读写数据段)                        |
   |       │        └─► 0xFFFFFFFF84000000: __bss_start (未初始化数据段)               |
   |       └─► 0xFFFFFFFFFE000000: CPU 局部固定映射区 (Fixmap & CPU GDT/TSS)           |
   +-----------------------------------------------------------------------------------+

1.2 ``vmlinux.lds.S`` 核心物理段切片
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
* **``.text`` (代码段)**：存放内核所有核心调度、中断、内存管理函数，权限为只读 + 可执行（RX）；
* **``.rodata`` (只读数据段)**：存放系统调用分发数组（``sys_call_table``）、只读字符串与常量配置；
* **``.init.text / .init.data`` (初始化段)**：存放仅在系统上电启动阶段使用的初始化函数（如 ``setup_arch()``、驱动探测函数）。在系统完全启动并运行 1 号进程后，内核通过 ``free_initmem()`` 将这部分物理内存全量释放并回收到伙伴系统中；
* **``.data..percpu`` (每 CPU 模板段)**：存放所有 ``DEFINE_PER_CPU()`` 宏定义的变量模板，多核启动时为每个 CPU 核心各克隆一份。

第二幕：从解压跳板到内核主体——``jmp *%rax`` 的终极一跳
------------------------------------------------------

在 ``arch/x86/boot/compressed/head_64.S`` 的最末尾，自解压器执行了它生命周期的最后一条机器指令：

::

   .Lrelocated:
       /* 清空解压器 BSS 段 */
       xorl    %eax, %eax
       leaq    _bss(%rip), %rdi
       leaq    _ebss(%rip), %rcx
       subq    %rdi, %rcx
       shrq    $3, %rcx
       rep     stosq

       /* 调用 extract_kernel 解压内核并执行 ELF 解析与重定位 */
       movq    %r15, %rdi             /* RDI = boot_params 零页指针 */
       movq    %rbp, %rsi             /* RSI = 输出目标物理地址 */
       call    extract_kernel         /* RAX 返回未压缩内核入口物理地址! */

       /* 恢复环境并执行终极一跳 */
       movq    %r15, %rsi             /* 协议规定: RSI 必须指向 boot_params */
       jmp     *%rax                  /* 物理长跳转: 命中真正的内核入口 startup_64 ! */

.. important::
   **交接瞬间的 CPU 物理执行环境**：
   * **运行模式**：64 位长模式原生执行状态（``CR0.PG=1, CR4.PAE=1, EFER.LME=1, EFER.LMA=1, CS.L=1``）；
   * **页表挂载**：``CR3`` 依然挂载着自解压器构建的 0~4GB 早期恒等映射页表；
   * **寄存器状态**：``RSI`` 严格保存 ``struct boot_params`` 物理基地址，中断处于全局关闭状态（``IF=0``）；
   * **指令指针**：``RIP`` 正式进入未压缩内核的 **``arch/x86/kernel/head_64.S:startup_64``**。

第三幕：``startup_64`` 早期物理执行环境初始化
----------------------------------------------

进入 ``arch/x86/kernel/head_64.S`` 后，代码开始构建正式内核的底层执行底座。

3.1 初始调用栈与寄存器清洗
~~~~~~~~~~~~~~~~~~~~~~~~~~
由于自解压器的临时栈即将被废弃，内核首先将栈指针切换为内核预留的初始主核栈：

::

   SYM_CODE_START_NOALIGN(startup_64)
       UNWIND_HINT_END_OF_STACK
       
       /* 1. 保护零页指针：将 RSI 存入被调用者保存寄存器 R15 */
       movq    %rsi, %r15

       /* 2. 挂载内核初始启动调用栈 (__top_init_kernel_stack) */
       leaq    __top_init_kernel_stack(%rip), %rsp

       /* 3. 清除 GSBASE 寄存器 (防止残留非法段基址) */
       movl    $MSR_GS_BASE, %ecx
       xorl    %eax, %eax
       xorl    %edx, %edx
       wrmsr

       /* 4. 加载正式内核 GDT 与早期 IDT 描述符 */
       call    __pi_startup_64_setup_gdt_idt

       /* 5. 远返回强制刷新 CS 代码段选择子为正式 __KERNEL_CS */
       pushq   $__KERNEL_CS
       leaq    .Lon_kernel_cs(%rip), %rax
       pushq   %rax
       lretq
   .Lon_kernel_cs:

第四幕：物理到虚拟地址偏移量推导与 ``early_top_pgt`` 页表修补
--------------------------------------------------------------

此时，CPU 虽然处于 64 位模式，但其代码依然通过低端物理地址恒等映射执行。为了能够访问高位虚拟地址（``0xFFFFFFFF81000000``），内核必须构建正式的 **早期顶级页表（``early_top_pgt``）**。

4.1 物理与虚拟地址差值 Delta 计算
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
由于 KASLR 或随机物理装载，内核的实际物理加载地址与编译期标称虚拟地址存在偏差：

::

   leaq    common_startup_64(%rip), %rdi     /* RDI = 当前指令处的运行时真实物理地址 */
   subq    .Lcommon_startup_64(%rip), %rdi   /* 减去编译期静态虚拟符号地址 */

.. math::

   \%rdi = 	ext{Phys}(	ext{common\_startup\_64}) - 	ext{Virt}(	ext{common\_startup\_64}) \equiv \mathbf{\Delta_{	ext{phys\_to\_virt}}}

4.2 早期顶级页表 ``early_top_pgt`` 的双重映射修补（``__startup_64``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
在 ``arch/x86/kernel/head64.c:__startup_64()`` 中，内核动态修补静态编译的 ``early_top_pgt``：

::

   +-----------------------------------------------------------------------------------+
   |                           early_top_pgt 早期双重映射架构                          |
   |                                                                                   |
   |  [early_top_pgt (PML4 顶级页表, 512 个表项)]                                      |
   |  ├── 表项 0: 指向 level3_kernel_pgt (低端恒等映射: 映射物理内存 0 ~ 4GB)         |
   |  │   (确保当前正在执行物理地址指令的 RIP 能够继续连续译码!)                       |
   |  │                                                                                |
   |  └── 表项 511: 同样指向 level3_kernel_pgt (高端虚拟映射: 映射 0xFFFFFFFF80000000) |
   |      (使得后续长跳转进入高位虚拟地址后，能够平滑无缝执行!)                        |
   +-----------------------------------------------------------------------------------+

修补完成后，内核将新页表物理基地址写入 ``CR3`` 寄存器：
::

   movq    %rax, %cr3             /* 激活 early_top_pgt 早期双重映射页表! */

----------------------------------------------------------------------------------------

第五幕：迈入高位虚拟内存大门——跳转 ``common_startup_64``
--------------------------------------------------------

当页表成功支持高位虚拟映射后，内核执行历史性的虚拟化长跳转：

::

   /* 通过绝对虚拟指针执行长跳转 */
   jmp     *.Lcommon_startup_64(%rip)

在 ``jmp *.Lcommon_startup_64(%rip)`` 执行的瞬间：
* **物理翻转**：CPU 内部的指令指针（RIP）瞬间从低端物理地址跃迁至 **``0xFFFFFFFF8100xxxx``**；
* **脱胎换骨**：CPU 正式脱离了实模式与早期引导阶段的低端物理内存视角，全面进驻 64 位 Linux 内核标准高位虚拟内存世界！

5.1 ``common_startup_64`` 的后续交接
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
进入虚拟地址空间后，代码在 ``head_64.S`` 中完成最后的硬件收尾：
1. **启用 CR4 特性**：置位 ``CR4.PGE``（开启全局页）并刷新全局 TLB 缓存；
2. **多核 SMP 引导分发**：根据 APIC ID 区分引导 CPU（BSP, CPU 0）与从属 CPU（AP）；
3. **分配 0 号进程初始栈**：将栈指针切换为静态编译的 0 号进程（Idle Task / ``init_task``）独立内核栈：
   ::

      movq    current_task(%rdx), %rax
      movq    TASK_threadsp(%rax), %rsp

4. **开启系统调用支持**：配置 ``MSR_EFER`` 置位 ``_EFER_SCE``（System Call Enable）与 ``_EFER_NX``（不可执行位）；
5. **调用 C 语言总入口**：
   ::

      movq    %r15, %rdi             /* RDI = boot_params 零页指针 */
      callq   *initial_code(%rip)    /* 跳转进入 x86_64_start_kernel() ! */

第六幕：全模块总结与从解压缩向内核早期平台建制的历史跨越
--------------------------------------------------------

至此，**模块 05：Linux 7.2 内核解压缩与 64 位长模式穿越** 全部 4 节已全量落盘！

我们完整遍历了解压子系统的微观技术奇迹：
1. **PIC 物理重定位**：``startup_32`` 利用栈偷取指令指针（``call 1f; popl %ebp``）动态推导物理基址 Delta，完成 GDT 自修补与 ``verify_cpu`` 64 位特性检测；
2. **长模式跨越**：2048 个 2MB 大页构建 0~4GB 恒等映射，配置 ``CR4.PAE``、``CR3``、``MSR_EFER.LME`` 与 ``CR0.PG`` 开启 IA-32e 并跃迁 ``startup_64``；
3. **解压中枢与随机化**：``extract_kernel()`` 收集多源硬件真随机熵驱动 KASLR、``mem_avoid`` E820 避障、Zstandard 极限流式解压与重定位表项修补；
4. **高位虚拟化跃迁**：ELF64 容器解析、``early_top_pgt`` 双重映射修补，以及通过 ``jmp *.Lcommon_startup_64`` 跨入高位虚拟内存大门。

现在，CPU 已处于 64 位高位虚拟地址空间（``0xFFFFFFFF81000000``），拥有 0 号进程独立内核栈与完整的 64 位长模式指令集支持。

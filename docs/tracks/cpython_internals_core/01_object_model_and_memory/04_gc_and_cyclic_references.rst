=============================================================================
分代垃圾回收器、循环引用检测算法与 gc_generation 双向链表物理拓扑
=============================================================================

.. note:: 前置背景与上下文承接
   在前一章中，我们解构了 CPython 的三层内存分配体系（``RAW`` / ``MEM`` / ``OBJ``）、经典 ``pymalloc`` 小对象内存池以及 Free-Threading 下的 Mimalloc 架构。引用计数（Reference Counting）作为 CPython 的主垃圾回收机制，具备“实时性极高、内存即刻回收、无卡顿暂停”的巨大优势。然而，引用计数存在一个致命的理论图论缺陷——**无法自动回收循环引用（Reference Cycles）**。当对象 A 引用对象 B，且对象 B 反向引用对象 A 时，即使外部已无可达引用，二者的引用计数也永远无法降为 0，从而导致永久性内存泄漏。
   
   为了解决这一顽疾，CPython 构建了一套精密的**分代循环垃圾回收器（Cyclic Garbage Collector, 简称 GC）**。本章将深入 CPython 核心源码文件 ``Python/gc.c``、``Modules/gcmodule.c``、``Include/internal/pycore_gc.h`` 与 ``Python/gc_free_threading.c``，从物理内存前缀 ``PyGC_Head`` 双向链表拓扑出发，深度推导“试探性引用减法（Trial Deletion）”打破孤岛循环引用的完整图论算法、PEP 442 终结器执行与对象复活（Resurrection）处理机制、基于 25% 启发式比率的三代晋升模型，以及 Python 3.13+ Free-Threading 下基于全局 Stop-the-World 安全点的并发 GC 架构。

-----------------------------------------------------------------------------
1. PyGC_Head 物理结构与容器对象追踪拓扑
-----------------------------------------------------------------------------

在 CPython 中，并非所有 Python 对象都会被 GC 追踪。像整数（``int``）、浮点数（``float``）、不可变字符串（``str``）等原子类型不可能包含对其他对象的引用，因此绝不可能构成循环引用。只有**容器类型（Container Objects，如 ``list``、``dict``、``tuple``、``set``、自定义类实例与函数闭包）**才会被 GC 追踪。

标准构建下的 PyGC_Head 负向偏移布局
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于被追踪的容器对象，CPython 在物理内存中分配该对象时，会在 ``PyObject`` 对象头**正前方的负偏移地址处**额外附加一个 16 字节的 ``PyGC_Head`` 结构：

.. code-block:: c

   typedef struct {
       uintptr_t _gc_next;
       uintptr_t _gc_prev;
   } PyGC_Head;

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  GC 追踪对象的物理内存连续排布 (标准构建)               |
   +====================================+====================================+
   | 负偏移 (-16 ~ -1 Bytes)            | 正偏移 (0x00 起始)                 |
   +------------------------------------+------------------------------------+
   | PyGC_Head (16 Bytes)               | PyObject / PyVarObject (对象实体)  |
   | ├── uintptr_t _gc_next (8 Bytes)   | ├── ob_refcnt (8 Bytes)            |
   | └── uintptr_t _gc_prev (8 Bytes)   | ├── ob_type   (8 Bytes)            |
   |                                    | └── 变长数据或实例字典指针 ...     |
   +------------------------------------+------------------------------------+
   ▲                                    ▲
   │                                    │
   AS_GC(op) = op - sizeof(PyGC_Head)   op 指针 (Python 层面暴露的真实对象指针)

- **基地址换算宏**：
  
  .. code-block:: c

     #define AS_GC(op)   ((PyGC_Head*)((char*)(op) - sizeof(PyGC_Head)))
     #define FROM_GC(gc) ((PyObject*)((char*)(gc) + sizeof(PyGC_Head)))

- **``_gc_prev`` 与 ``_gc_next`` 的双重语义与位复用（Bit-stealing）**：
  在非 GC 执行期间，``_gc_next`` 与 ``_gc_prev`` 构成一个双向循环链表节点，用于将对象串联在特定的分代链表（Generation List）中。
  由于 64 位机器上的内存对齐（至少 8 字节/16 字节对齐），指针的最低几位始终为 0。CPython 利用这一特性进行位复用：
  - **``_PyGC_PREV_MASK_FINALIZED`` (Bit 0)**：标记该对象是否已经执行过终结器 ``tp_finalize``。
  - **``_PyGC_PREV_MASK_COLLECTING`` (Bit 1)**：标记该对象当前正处于 GC 收集的候选代中。
  - **高 62 位**：在 GC 算法执行期间，临时用来存储“试探性引用计数（``gc_refs``）”，从而在不额外分配任何辅助内存的情况下完成全图推导！

2. 试探性引用减法（Trial Deletion）：循环引用检测核心算法
-----------------------------------------------------------------------------

CPython GC 的核心图论思想极其精妙：**一个对象真正的有效外部引用数，等于其实际引用计数 ``ob_refcnt`` 减去所有来自当前候选代内部其他对象对它的引用数**。

如果整个孤岛内的所有对象，在相互扣减掉内部引用后，每个对象的有效引用计数全部归零（``gc_refs == 0``），则数学上必然可以证明：**该对象集合是一个与外界完全脱轨的自闭合死锁孤岛，必须整体回收**。

算法分步执行管线
~~~~~~~~~~~~~~~~

在 ``Python/gc.c`` 的 ``deduce_unreachable()`` 函数中，该算法严格分为以下 4 个阶段：

.. code-block:: text

   [GC 候选链表 young (Generation N)]
                 │
                 ▼
   第 1 步：引用计数快照初始化 (update_refs)
   └─ 遍历 young 链表，将每个对象的实际 ob_refcnt 复制到 gc_prev 的 gc_refs 高位中
                 │
                 ▼
   第 2 步：遍历所有内部指针并试探性扣减 (subtract_refs)
   └─ 遍历 young 链表，调用每个对象的 tp_traverse 访问其引用的子对象
   └─ 若被引用子对象亦在 young 中，执行 gc_decref() 将其 gc_refs 减 1
                 │
                 ▼
   第 3 步：可达性判定与孤岛隔离 (move_unreachable)
   └─ 遍历 young 链表：
        ├─ 若 gc_refs > 0：说明存在来自外部（如栈帧/全局变量）的活引用！
        │    └─ 递归调用 tp_traverse(op, visit_reachable)，将该对象能够
        │       传递访问到的所有 gc_refs == 0 对象重新复活并标记为存活。
        └─ 若 gc_refs == 0 且未被复活：
             └─ 确认属于不可达孤岛，移入 unreachable 链表。
                 │
                 ▼
   第 4 步：打破循环并物理销毁 (delete_garbage)
   └─ 对 unreachable 链表中的对象执行 tp_clear，切断内部指针回路，
      触发引用计数正常归零释放。

图解试探性减法实例
~~~~~~~~~~~~~~~~~~

假设存在对象环 $A \leftrightarrow B$，外部有一个临时局部变量 $X 	o A$：

.. code-block:: text

   初始物理状态:
     X (外部引用) ──► A (ob_refcnt = 2) ◄────┐
                      │                     │
                      └───────────────────► B (ob_refcnt = 1)

   Step 1: update_refs()
     gc_refs(A) = 2, gc_refs(B) = 1

   Step 2: subtract_refs()
     遍历 A -> 发现引用 B -> gc_refs(B) 减 1 = 0
     遍历 B -> 发现引用 A -> gc_refs(A) 减 1 = 1

   Step 3: move_unreachable()
     检查 A: gc_refs(A) = 1 > 0  ──► A 确认存活！
     从 A 深度遍历可达子节点 ────► B 被 A 连带复活 (gc_refs(B) 置 1)！
     结论: A 与 B 均存活，不发生错误回收。

若外部变量 $X$ 离开作用域销毁（$X$ 不再指向 $A$）：

.. code-block:: text

   初始物理状态:
     A (ob_refcnt = 1) ◄────┐
     │                     │
     └───────────────────► B (ob_refcnt = 1)

   Step 1: gc_refs(A) = 1, gc_refs(B) = 1
   Step 2: A 减 B (gc_refs(B)=0), B 减 A (gc_refs(A)=0)
   Step 3: A 与 B 均为 0，无外部根节点触发复活 ──► A 和 B 全部移入 unreachable 链表并销毁！

3. 终结器执行与对象复活处理（PEP 442 机制）
-----------------------------------------------------------------------------

在 Python 中，对象可以定义析构方法 ``__del__``（对应 C 槽位 ``tp_finalize``）。当不可达垃圾包含 ``__del__`` 时，执行环境面临严重的重入与对象复活风险：

.. warning:: 对象复活（Object Resurrection）
   用户在 ``__del__`` 方法内部可能会执行 ``global_list.append(self)``，将本已判定为死亡的对象指针重新赋给全局变量，使其引用计数从 0 再次跃升至 1，即“对象复活”。

CPython 3.4+ 引入 PEP 442 规范，在 ``finalize_garbage()`` 与 ``handle_resurrected_objects()`` 中建立了铁律处理流程：

1. **首次执行终结器**：在打破循环前，先对所有包含 ``tp_finalize`` 的垃圾对象调用其析构方法，并打上 ``_PyGC_PREV_MASK_FINALIZED`` 标记。保证**每个对象的 ``__del__`` 在其生命周期内最多只被 GC 调用一次**。
2. **二次可达性探测**：在终结器执行完毕后，GC 绝不盲目销毁内存，而是调用 ``handle_resurrected_objects()`` 重新执行一轮完整的 ``deduce_unreachable()``。
3. **安全隔离**：如果检测到某对象在 ``__del__`` 中复活，GC 会安全地将其移回老年代（Old Generation），仅对那些在终结器运行后依然毫无外部引用的真正死锁垃圾执行 ``tp_clear`` 物理销毁。

4. 三代分发模型与 25% 启发式抗退化比率
-----------------------------------------------------------------------------

CPython 将所有被追踪的容器对象组织为 3 个代（Generations 0, 1, 2）：

- **Generation 0（新生代）**：容纳所有刚刚分配的全新容器对象。
- **Generation 1（中生代）**：容纳在第 0 代 GC 中幸存下来的对象。
- **Generation 2（老年代）**：容纳多次 GC 存活的长期常驻对象（如全局模块、类定义与配置）。

分代回收基于著名的**弱分代假说（Weak Generational Hypothesis）**：*绝大多数对象的生命周期极短，诞生后很快死亡；而经历数次垃圾回收依然存活的对象，往往会长久存活*。

抗 $O(N^2)$ 退化的 25% 启发式规则
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

老年代（Generation 2）中常驻的对象数量通常极其庞大（数十万至数百万）。如果单纯按照计数器阈值（如默认 10 次 Gen 1 触发 1 次 Gen 2）周期性全量扫描老年代，在海量长生命周期对象的工作负载下，GC 开销将退化为灾难性的 $O(N^2)$ 复杂度。

为此，CPython 引入了 Martin von Löwis 提出的 **25% 启发式比例法则**（见 ``Python/gc.c`` 的 ``gc_select_generation()``）：

.. code-block:: c

   if (i == NUM_GENERATIONS - 1
       && gcstate->long_lived_pending < gcstate->long_lived_total / 4)
   {
       continue; /* 老年代新增候选对象未达 25%，跳过全量 GC！ */
   }

只有当自上一次全量收集以来老年代新晋升的对象数量（``long_lived_pending``）超过当前老年代总对象数（``long_lived_total``）的 **25%** 时，才会真正批准触发完整的老年代垃圾回收。这一规则使得全量 GC 的分摊时间复杂度在数学上严格收敛于线性的 $O(N)$。

5. Python 3.13+ Free-Threading 自由线程下的并发 GC
-----------------------------------------------------------------------------

在 PEP 703 移除全局解释器锁后，多个线程在无锁并发运行的同时，内存图谱可能在毫秒内发生剧烈拓扑形变。如果 GC 在遍历 ``tp_traverse`` 的过程中其他线程正在修改指针，将导致悬空指针（Dangling Pointer）或致命的段错误（Segmentation Fault）。

为此，在 ``Python/gc_free_threading.c`` 中，CPython 采用了 **基于 Stop-the-World 安全点的全局并发 GC 架构**：

.. code-block:: text

   [触发 GC 条件满足]
           │
           ▼
   1. 发起全局停顿请求 (_PyEval_StopTheWorld)
      └─ 设置所有线程的 eval_breaker 标志位
      └─ 所有运行 Python 字节码的线程在最近的指令边界安全点进入阻塞挂起
           │
           ▼
   2. 世界静止状态下的并发拓扑分析
      └─ 此时内存拓扑完全冻结，GC 独占执行 deduce_unreachable
      └─ 消除任何跨线程数据竞争与读写冲突
           │
           ▼
   3. 垃圾安全清理与弱引用解除
      └─ 执行 tp_finalize、clear_weakrefs 与 tp_clear
           │
           ▼
   4. 恢复所有工作线程 (_PyEval_StartTheWorld)
      └─ 唤醒所有挂起线程，继续全速并行执行

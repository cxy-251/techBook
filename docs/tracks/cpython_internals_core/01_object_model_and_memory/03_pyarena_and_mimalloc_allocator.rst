=============================================================================
内存分配器架构：从 PyMem/PyObject 内存池到 Python 3.13+ 引入的 Mimalloc 深度剖析
=============================================================================

.. note:: 前置背景与上下文承接
   在前两章中，我们剖析了 CPython 的对象模型物理头（``PyObject`` / ``PyVarObject``）与类型元模型（``PyTypeObject``）的槽位分发状态机。在解释器运行过程中，Python 程序会以极高的频率分配与销毁成千上万个生命周期极短的小对象（如临时整数、局部字符串元组与字典）。如果每一次对象创建与销毁都直接调用操作系统的通用堆分配器（如标准 glibc ``malloc`` / ``free``），频繁的用户态到内核态上下文切换（System Calls）与内存碎片化将使运行时性能急剧恶化。
   
   本章将直接剖析 CPython 核心源码文件 ``Objects/obmalloc.c``、``Python/pyarena.c``、``Include/cpython/pymem.h`` 以及 Python 3.13+ 新增的 ``Include/internal/pycore_mimalloc.h``，自底向上解构 CPython 的三层内存分配体系、经典 ``pymalloc`` 小对象内存池（Arenas, Pools, Blocks）的微观拓扑，编译器前端的单向连续块分配器 ``PyArena``，以及在 Free-Threading（PEP 703 自由线程）革命中全面替换底层内存分配核心的 **Mimalloc 分配器** 架构。

-----------------------------------------------------------------------------
1. CPython 三层内存抽象体系
-----------------------------------------------------------------------------

CPython 将物理内存的申请与释放抽象为三个互不干扰但逐层特化的域（Memory Domains），定义于 ``Include/cpython/pymem.h``：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     CPython 内存分配域三层抽象体系                      |
   +====================+==========================+=========================+
   | 域枚举 (Domain)    | 核心 API                 | 物理管理策略与用途      |
   +--------------------+--------------------------+-------------------------+
   | PYMEM_DOMAIN_RAW   | PyMem_RawMalloc / Free   | 直接封装底层系统 malloc |
   |                    |                          | 无需持有 GIL，用于底座  |
   +--------------------+--------------------------+-------------------------+
   | PYMEM_DOMAIN_MEM   | PyMem_Malloc / Free      | 解释器通用内部缓冲区    |
   |                    |                          | (如字节码生成、符号表)  |
   +--------------------+--------------------------+-------------------------+
   | PYMEM_DOMAIN_OBJ   | PyObject_Malloc / Free   | Python 对象专用分配器   |
   |                    |                          | 挂载 pymalloc / mimalloc|
   +--------------------+--------------------------+-------------------------+

1. **RAW 域（原始系统内存）**：直接向底层 C 运行库或 OS 系统调用（``malloc`` / ``mmap`` / ``VirtualAlloc``）申请内存。此域的操作不受 Python 解释器状态约束，在没有初始化 GIL 或处于线程关闭状态时亦可安全调用。
2. **MEM 域（解释器内部内存）**：用于解释器内部的数据结构、临时字符串缓冲区和解析器缓存。
3. **OBJ 域（Python 对象专用内存）**：针对 Python 对象的生命周期特征进行了特化优化。在传统构建中接入 ``pymalloc``，在 Free-Threading 自由线程构建中接入线程私有堆 ``mimalloc``。

-----------------------------------------------------------------------------
2. 经典 pymalloc 架构：Arenas, Pools 与 Blocks 的微观几何
-----------------------------------------------------------------------------

在传统构建中，``pymalloc`` 是 CPython 的核心对象分配引擎，专门优化小于等于 **512 字节** 的小对象分配请求（在 64 位体系结构下）。其物理结构由三个层次构成：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |              Arena (256 KB 连续虚拟内存块，系统分配基元)                |
   |  +-------------------------------------------------------------------+  |
   |  | Pool 0 (4 KB)  | Pool 1 (4 KB)  | Pool 2 (4 KB)  | ... | Pool 63  |  |
   |  +----------------+----------------+----------------+-----+----------+  |
   +-------------------------------------------------------------------------+
           │
           ▼
   +-------------------------------------------------------------------------+
   |                   单个 Pool (4 KB 物理页对齐结构)                       |
   +====================+====================================================+
   | struct pool_header | 管理元数据 (16/32 Bytes)                           |
   +--------------------+----------------------------------------------------+
   | Block 0            | 严格固定大小的内存切片 (如 16B, 32B, 64B 等)       |
   +--------------------+----------------------------------------------------+
   | Block 1            | 自由单向链表 (Freeblock 指针链接)                  |
   +--------------------+----------------------------------------------------+
   | ...                |                                                    |
   +--------------------+----------------------------------------------------+

1. 尺寸类别（Size Classes）
~~~~~~~~~~~~~~~~~~~~~~~~~~~

``pymalloc`` 将小于等于 512 字节的请求按 16 字节对齐划分为 32 个尺寸类别（Size Classes，索引 0~31）：

$$	ext{Index} = (	ext{Size} - 1) \gg 4$$

例如：1~16 字节映射至类别 0（16 字节 Block），17~32 字节映射至类别 1（32 字节 Block），依此类推。同一个 Pool 内部仅分配相同尺寸类别的 Block，彻底消除了 Pool 内部的外部碎片。

2. Pool 头部元数据：``struct pool_header``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每个 4 KB Pool 的起始地址严格放置一个头部结构体：

.. code-block:: c

   struct pool_header {
       union { block *_padding;
               uint count; } ref;          /* 当前 Pool 中已分配的 Block 计数 */
       block *freeblock;                   /* 空闲 Block 单向链表表头指针 */
       struct pool_header *nextpool;       /* 属于同一 Size Class 的下一个 Pool */
       struct pool_header *prevpool;       /* 属于同一 Size Class 的前一个 Pool */
       uint arenaindex;                    /* 所属 Arena 的全局索引 */
       uint szidx;                         /* 绑定的尺寸类别索引 (0 ~ 31) */
       uint nextoffset;                    /* 尚未初始化的未切片内存起始偏移 */
       uint maxnextoffset;                 /* 允许未切片内存的最大偏移 */
   };

- **高速分配（O(1) Fast-Path）**：若 ``freeblock`` 非空，直接将表头弹出返回；若空但 ``nextoffset < maxnextoffset``，则从高地址未切片区域切出一个新的 Block。
- **内存回收与归还**：当一个 Block 被释放时，直接以头插法插回 ``freeblock`` 链表。当一个 Pool 的所有 Block 全部释放时（``ref.count == 0``），该 Pool 从当前 Size Class 链表摘除，放回 Arena 的可用 Pool 列表。

3. Arena 物理拓扑与基地址计算
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

每个 Arena 大小为 256 KB（恰好容纳 64 个 4 KB Pool）。为了能根据任意一个对象的指针地址在 **$O(1)$ 时间内定位其所属的 ``pool_header``**，CPython 强制所有 Pool 按 4 KB 物理地址对齐。

任意对象指针 ``p`` 所属 Pool 的头部地址计算极其高效：

.. code-block:: c

   #define POOL_BITS 12  /* 1 << 12 = 4096 字节 */
   #define POOL_MASK 0xFFF
   #define POOL_ADDR(p) ((pool_header *)((uintptr_t)(p) & ~(uintptr_t)POOL_MASK))

通过简单的按位与运算清除低 12 位即可直接获取 ``pool_header`` 指针，完全无需遍历全局检索树。

3. 编译期连续区分配器：PyArena
-----------------------------------------------------------------------------

在 Python 前端编译阶段（词法分析、语法解析、AST 生成与符号表分析），解析器需要瞬间创建数十万个临时的 AST 节点（如 ``BinOp``, ``Name``, ``Constant``）。

如果对每个 AST 节点都执行细粒度的 ``malloc`` 与 ``free``，在语法树分析完成后逐一递归遍历释放，将造成极大的 CPU 周期浪费，并且极易发生内存泄漏。

CPython 在 ``Python/pyarena.c`` 中实现了专用的 **单向块式分配器 ``PyArena``**：

.. code-block:: c

   struct _arena {
       /* 已经装满的内存块双向链表 */
       struct _block *a_blocks;
       /* 当前正在分配的活动内存块 */
       struct _block *a_cur_block;
       /* 关联管理的 Python 对象列表 (供编译器阶段持有引用) */
       PyObject *a_objects;
   };

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PyArena 连续分块分配机制                            |
   +=========================================================================+
   | Block 0 (8KB) -> Block 1 (8KB) -> Block 2 (16KB) -> ... -> CurBlock     |
   | [Node1][Node2][Node3][Node4][未分配游标 ──►               ]             |
   +-------------------------------------------------------------------------+

- **极速线性推进（Bump Allocation）**：在当前 Block 内部，分配仅是将游标指针向后推进对象大小字节，耗时仅 1~2 个 CPU 指钟周期。
- **无单节点析构开销**：在 AST 节点生命周期内，不单独执行任何释放操作。
- **一键清空回收（Arena Free）**：当整个 AST 被编译为字节码 Code Object 后，直接调用 ``PyArena_Free(arena)``，一次性遍历链表将所有底层 8KB/16KB 物理大块直接释放给操作系统。

4. Python 3.13+ Free-Threading 内存革命：Mimalloc 深度解析
-----------------------------------------------------------------------------

在 Python 3.13+ 移除 GIL 后，传统的 ``pymalloc`` 面临致命缺陷：``pymalloc`` 的 Arena 与 Pool 结构是进程全局共享且非线程安全的，如果给每个 Pool 访问加锁，会导致多线程高频争用锁；如果采用完全线程私有的简单 Pool，跨线程释放（Thread A 分配对象，传递给 Thread B 释放）将导致内存无法归还或产生竞态条件。

为此，CPython 深度集成了由微软研发的高性能、高伸缩性分配器 **Mimalloc**，并将其作为 Free-Threading 构建（``Py_GIL_DISABLED``）下的默认内存底座。

Mimalloc 的三大核心物理设计
~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Mimalloc 多线程无锁架构拓扑                         |
   +=========================================================================+
   | Thread 0 (Thread-Local Heap)     │ Thread 1 (Thread-Local Heap)         |
   | ├── Page (Free Block List)       │ ├── Page (Free Block List)           |
   | └── Local TLB Allocation         │ └── Local TLB Allocation             |
   +──────────────────────────────────┴──────────────────────────────────────+
                     │                                   │
                     │ (跨线程原子归还无需锁)            │
                     ▼                                   ▼
   +-------------------------------------------------------------------------+
   | Atomic Thread-Free List (单向无锁 CAS 队列，延迟批量收回本地堆)         |
   +-------------------------------------------------------------------------+
                     │
                     ▼
   +-------------------------------------------------------------------------+
   | OS Segments / Virtual Memory Pages (自适应大页释放与跨核心隔离)        |
   +-------------------------------------------------------------------------+

1. **线程私有堆（Thread-Local Heaps, ``mi_heap_t``）**：
   每个 Python 原生工作线程（``PyThreadState``）均独占一个完全无锁的本地堆。线程内的所有 ``PyObject_Malloc`` 请求在当前核心的 L1/L2 缓存中直接命中完成，实现真正的零锁分配。
2. **跨线程无锁释放（Atomic Thread-Free List）**：
   当线程 A 将对象传递给线程 B，线程 B 执行 ``Py_DECREF`` 触发内存释放时，Mimalloc 并不会去争抢线程 A 的堆锁，而是通过原子 CAS 指令（Lock-free Atomic CAS）将该内存块链接进目标 Page 的跨线程释放链表（``thread_free``）。
3. **延迟批量收回（Amortized Local Reclaim）**：
   线程 A 在下一次分配或检查时，一次性将 ``thread_free`` 链表批量并回本地自由链表，将跨线程同步的开销降到了极致。

5. 分配器性能与内存对齐硬件约束
-----------------------------------------------------------------------------

在现代 ARM64（Apple Silicon）与 x86-64 处理器中，如果内存分配的物理地址未按照数据类型位宽对齐（例如 8 字节指针跨越了 64 字节 Cache Line 边界），将引发硬件层面的惩罚性二次总线访问。

不管是 ``pymalloc`` 还是 ``mimalloc``，CPython 均严格执行 **16 字节基地址物理对齐**，确保所有生成的 ``PyObject`` 头及其内部指针字段永不发生跨 Cache Line 访问，极大提升了 CPU 乱序执行与流水线预取的硬件能效。

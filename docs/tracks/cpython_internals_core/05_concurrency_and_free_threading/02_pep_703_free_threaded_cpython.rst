=============================================================================
PEP 703 Free-Threading 架构全景：禁用 GIL 后的内存安全性模型
=============================================================================

.. note:: 前置背景与上下文承接
   在前一章中，我们解构了传统全局解释器锁（GIL）的底层设计哲学、5ms 时间片条件变量状态机以及基于 ``FORCE_SWITCHING`` 的防恶性重夺调度机制。GIL 虽然以粗粒度互斥保证了引用计数与内存分配的安全性，但也彻底封锁了 Python 利用现代多核处理器的并发潜能。
   
   在 Python 3.13 中，**PEP 703（Making the Global Interpreter Lock Optional in CPython）** 的正式落地标志着 CPython 历史上最具革命性的体系重构——**自由线程模式（Free-Threading，构建标识 ``Py_GIL_DISABLED``）**。本章将深入 CPython 核心源码文件 ``Include/internal/pycore_object.h``、``Include/internal/pycore_critical_section.h``、``Include/internal/pycore_mimalloc.h`` 以及 ``Include/internal/pycore_qsbr.h``，全景式解构移除 GIL 后的四大内存安全基石：偏向引用计数（Biased Reference Counting, BRC）、Mimalloc 线程局部内存池拓扑、细粒度临界区（Critical Sections）与 PyMutex 排序防死锁机制，以及基于静止状态生命周期（QSBR）与 Stop-the-World 安全点的并发内存回收体系。

-----------------------------------------------------------------------------
1. PEP 703 架构哲学与四大核心挑战
-----------------------------------------------------------------------------

移除 GIL 的终极困境
~~~~~~~~~~~~~~~~~~~

在过去三十年中，多次移除 GIL 的尝试（如 Greg Stein 的 Free-threading patch 或 Larry Hastings 的 Gilectomy）均以失败告终，核心原因在于：
1. **多核争用导致的单线程性能雪崩**：如果将所有 ``Py_INCREF`` / ``Py_DECREF`` 简单替换为硬件级原子指令（如 x86 的 ``LOCK XADD`` 或 ARM 的 ``LDREX/STREX``），由于频繁的 CPU 缓存行颠簸（Cache-Line Bouncing / MESI 协议失效），单线程吞吐将**暴跌 30%~60%**；
2. **多线程并发读写下的 Use-After-Free**：线程 A 正在读取列表元素，线程 B 并发执行 ``list.pop()`` 并释放了底层内存，线程 A 将直接崩溃；
3. **死锁风险爆炸**：从单一大锁切换为细粒度对象锁时，若无严格的加锁序保证，复杂业务代码极易陷入 AB-BA 循环死锁。

PEP 703 的四大架构支柱
~~~~~~~~~~~~~~~~~~~~~~

为了在消除 GIL 的同时将单线程损耗控制在极低水平（< 5%~10%），PEP 703 确立了四大不可分割的体系支柱：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    PEP 703 Free-Threading 四大体系支柱                   |
   +=========================================================================+
   | 1. 偏向引用计数 (Biased Reference Counting)                             |
   | └─ 区分拥有者线程 (Local) 与异构线程 (Shared), 本地操作保持 0 原子指令!   |
   +-------------------------------------------------------------------------+
   | 2. 线程局部内存分配器 (Thread-Local Mimalloc)                           |
   | └─ 彻底废弃全局 pymalloc Arena 互斥锁, 各线程享有独立无锁分配堆。        |
   +-------------------------------------------------------------------------+
   | 3. 栈式细粒度临界区 (Critical Sections & PyMutex)                       |
   | └─ 1 字节超轻量互斥锁 + 物理地址升序排序 (Lock Ordering) 杜绝死锁。      |
   +-------------------------------------------------------------------------+
   | 4. 延迟内存释放 (QSBR) 与 Stop-the-World (STW) 安全点停顿               |
   | └─ 消除并发无锁读下的 Use-After-Free, 配合 STW 实现无锁分代 GC 回收。    |
   +-------------------------------------------------------------------------+

-----------------------------------------------------------------------------
2. 支柱一：偏向引用计数（Biased Reference Counting）
-----------------------------------------------------------------------------

对象头物理内存革命（32 字节扩展拓扑）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在启用 ``Py_GIL_DISABLED`` 后，``PyObject`` 对象头在 ``Include/cpython/object.h`` 中被重构为拥有独立拥有者线程与双层计数的拓扑：

.. code-block:: c

   struct _object {
       union {
           uintptr_t ob_tid;            /* 拥有者线程 ID (Thread ID) */
           uintptr_t ob_flags;          /* 静态内建/不朽对象标记位 */
       };
       uint32_t ob_ref_local;           /* 拥有者线程私有的本地引用计数 (无锁) */
       uint32_t ob_gc_bits;             /* GC 追踪与延迟释放位 */
       PyMutex ob_mutex;                /* 1 字节对象级轻量级互斥锁 */
       Py_ssize_t ob_ref_shared;        /* 跨线程共享的原子引用计数 + 状态标志位 */
       PyTypeObject *ob_type;           /* 类型对象指针 */
   };

.. code-block:: text

   +-------------------------------------------------------------------------+
   |               Py_GIL_DISABLED 下 PyObject 32 字节对象头拓扑             |
   +=========================================================================+
   | [00-07] ob_tid (8 字节): 拥有者线程 ID (_Py_ThreadId())                 |
   | [08-11] ob_ref_local (4 字节): 本地私有引用计数 (普通汇编指令加减)      |
   | [12-12] ob_gc_bits (1 字节): GC 分代状态                                |
   | [13-13] ob_mutex (1 字节): 轻量级对象互斥锁                             |
   | [14-15] 对齐填充 (2 字节)                                               |
   | [16-23] ob_ref_shared (8 字节): 原子共享引用计数 (含低 2 位标志位)      |
   | [24-31] ob_type (8 字节): 指向类型对象的指针                            |
   +-------------------------------------------------------------------------+

零原子指令的本地极速路径（Local Fast-Path）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一个对象被当前线程创建并在本地高频传递时（绝大多数局部变量的生命周期）：
- ``_Py_IsOwnedByCurrentThread(op)`` 判定为真；
- ``_Py_RefcntAdd()`` 直接以普通 CPU 指令修改 ``ob_ref_local``，**完全不触发原子 CAS（Compare-And-Swap）或总线锁定**，单线程性能与持有 GIL 时几乎完全一致！

跨线程共享与合并协议（Shared Slow-Path）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当对象逃逸到其他线程时：
- 其他线程调用 ``_Py_TryIncRefShared()``，通过原子指令将增量累加至 ``ob_ref_shared``；
- 当拥有者线程运行至解释器安全点或触发析构时，调用 ``_Py_ExplicitMergeRefcount()`` 将 ``ob_ref_shared`` 合并至本地主计数，实现安全的延迟统一归零与物理回收。

3. 支柱二：Mimalloc 线程局部堆（Thread-Local Heaps）
-----------------------------------------------------------------------------

传统 pymalloc 的并发瓶颈
~~~~~~~~~~~~~~~~~~~~~~~~

传统 CPython 的小对象内存分配器 ``pymalloc`` 将内存划分为 256KB 的 Arena 与 4KB 的 Pool。由于 Arena 表与 Pool 空闲链表在整个解释器内是全局共享的，在无 GIL 状态下，每一次对象的 ``malloc`` 与 ``free`` 都必须获取全局自旋锁，将引发灾难性的锁竞争。

Mimalloc 线程局部堆隔离
~~~~~~~~~~~~~~~~~~~~~~~

Python 3.13 自由线程构建深度集成了微软的开源高性能内存分配器 **Mimalloc**：
1. **Thread-Local Heap（TL-Heap）**：每个 OS 线程在创建时自动绑定一个独立的 Mimalloc Heap；
2. **零争用分配**：线程为对象分配内存时，直接从私有 Thread-Local 页框（Pages）中 Bump 分配，完全不需要跨线程互斥锁；
3. **无锁跨线程释放（Cross-Thread Freeing）**：当线程 B 释放由线程 A 分配的对象时，线程 B 利用原子 CAS 操作将内存块推入线程 A 所属 Page 的延迟回收原子单向链表（Thread-Free List），线程 A 在下一次分配时批量认领，彻底实现内存池的解耦。

4. 支柱三：细粒度临界区（Critical Sections）与 PyMutex
-----------------------------------------------------------------------------

1 字节轻量级锁（PyMutex）
~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Include/internal/pycore_lock.h`` 中，CPython 实现了一种仅占用 **1 字节** 的极简锁结构 ``PyMutex``：
- 低位通过原子位操作标记锁定状态；
- 若发生线程争用，未抢到锁的线程进入内核级等待队列（类似 Linux Futex / WebKit Parking Lot 机制），避免占用宝贵的对象头空间。

地址排序防死锁机制（Address-Based Lock Ordering）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当需要同时修改两个对象（如列表拼接 ``list1 + list2`` 或字典更新 ``dict.update()``）时，必须同时锁定两个对象的 ``ob_mutex``。

CPython 在 ``_PyCriticalSection2_BeginMutex()`` 中引入了强制的**内存物理地址升序排序策略**：

.. code-block:: c

   if ((uintptr_t)m2 < (uintptr_t)m1) {
       /* 强制先锁定物理地址较低的互斥锁, 再锁定高地址互斥锁 */
       PyMutex *tmp = m1;
       m1 = m2;
       m2 = tmp;
   }
   PyMutex_Lock(m1);
   PyMutex_Lock(m2);

无论两个线程以何种顺序传入参数（线程 A 调用 ``list_concat(L1, L2)``，线程 B 并发调用 ``list_concat(L2, L1)``），底层均严格遵循全局一致的加锁顺序，**从数学上彻底证明并杜绝了死锁的发生**。

5. 支柱四：QSBR 延迟回收与 Stop-the-World 安全点
-----------------------------------------------------------------------------

基于静止状态的内存回收（QSBR - Quiescent-State-Based Reclamation）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了支持高频容器（如列表、字典索引）的无锁并发读取（Lock-Free Concurrent Read）：
- 读线程在读取元素时不加互斥锁；
- 写线程若执行扩容或替换，旧的底层数组（如 ``_PyListArray``）**严禁立即调用 ``free()`` 释放**，而是调用 ``_PyMem_FreeDelayed()`` 将旧数组推入 QSBR 延迟销毁队列；
- **静止状态（Quiescent State）**：每个线程在每次解释器主循环迭代、函数返回或脱附（Detach）时，向全局 QSBR 上报自己的最新周期计数（Epoch）；
- 当所有活跃线程均至少跨越了一次静止状态时，证明先前处于无锁读取中的所有线程均已退出临界代码，系统方才安全触发 ``free()`` 物理释放，彻底消除 Use-After-Free 隐患！

Stop-the-World（STW）全局安全点停顿
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当执行全局分代循环垃圾回收（GC Collection）、更新全局静态不朽对象或动态加载传统 C 扩展激活瞬态 GIL 时，运行时调用 ``_PyEval_StopTheWorldAll()``：
1. 向所有活跃线程的 ``eval_breaker`` 置位 ``_PY_EVAL_PLEASE_STOP_BIT``；
2. 所有线程在下一个循环边界检测到中断，主动保存上下文并进入挂起态（Suspend）；
3. 主控线程在完全确定性的单线程静止视界下执行全局 GC 遍历与指针修复；
4. 随后调用 ``_PyEval_StartTheWorldAll()`` 广播唤醒所有线程恢复全速并行。

小结与下章导读
-----------------------------------------------------------------------------

本章全景解构了 CPython 3.13+ PEP 703 Free-Threading 的核心安全架构：
1. 偏向引用计数（BRC）如何通过 32 字节对象头、``ob_ref_local`` 与 ``ob_ref_shared`` 实现本地 0 原子指令的高性能开销压制；
2. Mimalloc 线程局部堆（TL-Heap）与无锁延迟回收链表彻底替代全局 pymalloc 互斥锁；
3. 基于 1 字节 ``PyMutex`` 的栈式临界区与地址升序排序防死锁数学模型；
4. 基于 Epoch 的 QSBR 延迟释放机制杜绝无锁读取下的 Use-After-Free；
5. 基于 ``_PY_EVAL_PLEASE_STOP_BIT`` 的全局 Stop-the-World（STW）安全点暂停体系。

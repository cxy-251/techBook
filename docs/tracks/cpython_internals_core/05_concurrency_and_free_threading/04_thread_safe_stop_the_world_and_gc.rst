=============================================================================
Free-Threaded 模式下的 Stop-the-World 安全点停顿机制与 GC
=============================================================================

.. note:: 前置背景与上下文承接
   在前两章中，我们分别解构了 PEP 703 Free-Threading 的四大架构支柱，以及基于 32 字节扩展对象头的偏向引用计数（Biased Reference Counting, BRC）与延迟引用计数（Deferred Reference Counting）。BRC 成功解决了单对象生命周期在拥有者线程与跨线程共享时的无锁极速操作问题。
   
   然而，引用计数机制天生无法回收**有向循环引用图（Cyclic Garbage）**，且在禁用 GIL 后，所有线程都在全速并发修改对象拓扑与指针。在缺乏全局互斥保护的视界下，如何避免垃圾回收器在遍历对象图时因并发突变引发段错误（Segmentation Fault）？本章作为**第 5 模块【并发、GIL 与 3.13+ Free-Threading】的收官之作**，将深入 CPython 核心源码文件 ``Python/gc_free_threading.c``、``Include/internal/pycore_gc.h``、``Include/internal/pycore_pystate.h`` 以及 ``Python/pystate.c``，深度剖析自由线程模式下的全局 **Stop-the-World（STW）协调协议**、线程状态四态流转状态机、去除 ``PyGC_Head`` 负向偏移后的 Mimalloc Segment 级内存扫描拓扑、无锁安全点探测算法，以及 STW 视界下的并行可达性分析与 Trial Deletion 破环终结机制。

-----------------------------------------------------------------------------
1. Free-Threading 垃圾回收的范式转换
-----------------------------------------------------------------------------

传统 GIL GC 的局限与自由线程下的并发危机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统的单解释器（带 GIL）构建中：
- 垃圾回收器仅在持有 GIL 的当前线程中串行运行；
- 运行 GC 时，由于其他 Python 线程均处于休眠等待 GIL 的状态，整个对象图处于天然的**静态快照（Static Snapshot）**中；
- 每个可被 GC 追踪的对象在物理内存中强制前置 **16 字节的 ``PyGC_Head`` 双向链表节点**，所有对象被挂载在全局分代链表（``gc_generation.head``）上。

但在自由线程（``Py_GIL_DISABLED``）构建下，这一范式被彻底击碎：
1. **多线程并发指针修改**：若 GC 线程在没有暂停其他线程的情况下扫描对象引用的 ``tp_traverse``，其他线程随时可能执行 ``list.append()`` 或 ``dict.__setitem__()``，导致 GC 访问悬垂指针（Use-After-Free）或漏标存活对象引发致命的过早释放（Premature Collection）；
2. **全局链表锁争用灾难**：如果数以万计的对象创建时都必须获取全局 GC 链表互斥锁，多核并行创建对象的吞吐将断崖式下跌；
3. **对象头尺寸膨胀极限**：在 64 位平台，若在 32 字节的 BRC 对象头前再前置 16 字节的 ``PyGC_Head``，基础对象尺寸将高达 **48 字节**，造成不可接受的内存浪费。

-----------------------------------------------------------------------------
2. 架构突破：彻底移除 PyGC_Head 与 Mimalloc 分段扫描
-----------------------------------------------------------------------------

零开销对象头与 `ob_gc_bits` 状态编码
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了遏制内存膨胀，CPython 3.13 自由线程构建做出了激进重构：**完全移除了 ``PyGC_Head`` 结构体（``sizeof(PyGC_Head) == 0``）**！

对象的 GC 状态完全压缩在 ``PyObject.ob_gc_bits``（1 字节）位域中：
- ``_PyGC_BITS_TRACKED (0x1)``：标记对象当前是否被 GC 追踪；
- ``_PyGC_BITS_SHARED (0x2)``：标记对象是否已被其他线程共享；
- ``_PyGC_BITS_DEFERRED (0x4)``：标记对象采用延迟引用计数。

Mimalloc Segment 级物理内存遍历
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

既然没有了全局双向链表，GC 在运行时如何找到所有被分配的对象？

CPython 借助深度集成的 **Mimalloc 分配器物理分段（Segments & Pages）元数据**：
- 所有由 GC 追踪的对象均分配在特定的 Mimalloc Heap Page 中；
- 当 GC 启动时，解释器不再遍历双向链表，而是**直接遍历进程内各个线程所拥有的 Mimalloc Segments 与 Pages 物理块**；
- 通过解析 Mimalloc 的块分配位图（Block Allocation Bitmap），以极高的硬件连续内存扫描吞吐（数十 GB/s）瞬时定位所有存活对象首地址，彻底消除了动态维护全局链表的任何运行时开销！

3. Stop-the-World（STW）全局安全点协调协议
-----------------------------------------------------------------------------

线程状态四态流转状态机
~~~~~~~~~~~~~~~~~~~~~~

为了在多核环境下为 GC 或全局元数据更新创造一个绝对安全的单线程静止视界，CPython 设计了高精度的线程状态流转体系：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    Free-Threading 线程状态四态转换图                    |
   +=========================================================================+
   | 1. _Py_THREAD_ATTACHED (运行态)                                         |
   | └─ 线程正在全速执行 Python 字节码, 持有本地引用计数, 随时可能突变对象。    |
   +-------------------------------------------------------------------------+
             │                                              ▲
             │ (_PyThreadState_Detach)                      │ (_PyThreadState_Attach)
             ▼                                              │
   +-------------------------------------------------------------------------+
   | 2. _Py_THREAD_DETACHED (脱附态: 执行系统调用 / C 扩展 I/O)              |
   | └─ 承诺绝对不访问任何 PyObject* 指针。在 STW 期间允许继续全速并发运行!   |
   +-------------------------------------------------------------------------+
             │                                              ▲
             │ (收到 _PY_EVAL_PLEASE_STOP_BIT 中断)          │ (收到 StartTheWorld 广播)
             ▼                                              │
   +-------------------------------------------------------------------------+
   | 3. _Py_THREAD_SUSPENDED (挂起态: STW 安全点静止)                        |
   | └─ 线程在解释器循环边界完成上下文压栈, 进入条件变量阻塞, 处于全局冻结。  |
   +-------------------------------------------------------------------------+

`_PyEval_StopTheWorldAll()` 物理停顿算法
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Python/pystate.c`` 中，发起 STW 的主控线程执行以下步骤：

.. code-block:: c

   void
   _PyEval_StopTheWorldAll(_PyRuntimeState *runtime)
   {
       /* 1. 获取全局 STW 互斥锁, 确保全进程仅有一个 STW 事件在执行 */
       PyMutex_Lock(&runtime->stoptheworld_mutex);

       /* 2. 广播向所有子解释器的所有活跃线程置位 eval_breaker 中断位 */
       _Py_FOR_EACH_TSTATE_BEGIN(interp, tstate) {
           _Py_set_eval_breaker_bit(tstate, _PY_EVAL_PLEASE_STOP_BIT);
       } _Py_FOR_EACH_TSTATE_END(interp);

       /* 3. 阻塞等待所有 ATTACHED 状态的线程主动切换为 SUSPENDED 态 */
       while (atomic_load(&runtime->running_threads_count) > 0) {
           PyCOND_WAIT(&runtime->stw_cond, &runtime->stoptheworld_mutex);
       }
       /* 此时全进程进入确定性静止视界! */
   }

- **零侵入安全点探测**：正在执行 Python 代码的线程在下一个字节码循环回边（Back-edge）或函数调用处读取 ``tstate->eval_breaker``，发现 ``_PY_EVAL_PLEASE_STOP_BIT`` 命中，立即调用 ``_PyThreadState_Suspend()`` 将自身状态原子转为 ``SUSPENDED`` 并发出条件信号，然后进入休眠；
- **非阻塞脱附优化**：处于 ``_Py_THREAD_DETACHED`` 状态的线程（如正在执行 ``socket.recv()`` 或 ``numpy.dot()``）**完全不需要被暂停**，它们继续并行计算，直到它们试图重新 Attach 回 Python 虚拟机时被自动挂起阻断，将 STW 对系统吞吐的负面影响降至最低。

4. 自由线程 Trial Deletion 分代循环垃圾回收算法
-----------------------------------------------------------------------------

在 STW 冻结的安全视界内，主控 GC 线程执行经过自由线程强化的四阶段 **Trial Deletion 循环检测算法**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                   STW 模式下的四阶段循环垃圾回收流水线                  |
   +=========================================================================+
   | Phase 1: 本地与共享计数原子归一 (Refcount Consolidation)                |
   | └── 遍历所有 Mimalloc 存活对象, 将 ob_ref_local 与 ob_ref_shared 合并为  |
   |     确定性的 gc_refs 基准计数, 彻底消除跨线程 BRC 队列未排空的模糊态。 |
   +-------------------------------------------------------------------------+
                                     │
                                     ▼
   +-------------------------------------------------------------------------+
   | Phase 2: 试探性减引用 (Trial Reference Subtraction)                     |
   | └── 对每个追踪对象调用 tp_traverse 槽位, 将被引用子对象的 gc_refs 递减。 |
   |     若一个对象图内部所有对象的 gc_refs 全部归零, 证明其孤立于外界引用!  |
   +-------------------------------------------------------------------------+
                                     │
                                     ▼
   +-------------------------------------------------------------------------+
   | Phase 3: 存活复活与不可达隔离 (Reachable Scan & Unreachable Move)       |
   | └── 从 gc_refs > 0 的可达根对象出发, 深度优先遍历撤销减计数 (Resurrect); |
   |     剩余真正不可达的孤岛对象被批量转移至 unreachable 析构链表。          |
   +-------------------------------------------------------------------------+
                                     │
                                     ▼
   +-------------------------------------------------------------------------+
   | Phase 4: 弱引用清理与并发安全终结 (Weakrefs & Deallocation)             |
   | ├── 触发不可达对象的弱引用回调 (Weakref Callbacks);                     |
   | └── 调用 tp_dealloc 物理释放循环垃圾内存。                              |
   +-------------------------------------------------------------------------+

5. QSBR 与 STW 垃圾回收的协同生命周期边界
-----------------------------------------------------------------------------

在自由线程 CPython 中，内存回收被划分为互补的双轨体系：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    QSBR 延迟释放 vs STW 垃圾回收对比                    |
   +====================+======================+=============================+
   | 维度               | QSBR 延迟释放体系    | STW 垃圾回收体系            |
   +====================+======================+=============================+
   | 核心使命           | 消除无锁并发读下的   | 破解对象拓扑图中的          |
   |                    | Use-After-Free 悬垂  | 有向循环引用死锁            |
   +--------------------+----------------------+-----------------------------+
   | 管理的目标对象     | 容器底层物理缓冲区   | Python 高层复合对象         |
   |                    | (_PyListArray, Dict) | (class, tuple, list, dict)  |
   +--------------------+----------------------+-----------------------------+
   | 停顿级别           | 零停顿 (Lock-Free)   | 全局安全点微停顿 (STW)      |
   +--------------------+----------------------+-----------------------------+
   | 触发频率           | 极高频 (容器扩容即发)| 低频 (分代阈值溢出触发)     |
   +--------------------+----------------------+-----------------------------+

二者紧密配合，构筑了 CPython 3.13+ 禁用 GIL 后坚不可摧的多核内存安全屏障。

小结与全模块总结导读
-----------------------------------------------------------------------------

本章系统解构了 CPython 3.13+ Free-Threading 模式下的全局停顿与垃圾回收机制：
1. 传统 GIL GC 在多核并发下的指针突变危机与废除全局链表锁的必然性；
2. 彻底移除 ``PyGC_Head`` 结构体，通过 ``ob_gc_bits`` 状态编码与 Mimalloc Segment/Page 物理位图实现数十 GB/s 的极速内存扫描；
3. ``_PyEval_StopTheWorldAll()`` / ``StartTheWorldAll()`` 全局安全点停顿协议与线程四态流转状态机；
4. 允许 ``DETACHED`` 脱附线程在 STW 期间无感继续并发执行系统调用的非阻塞性能优化；
5. STW 视界下的 Trial Deletion 四阶段循环垃圾回收流水线；
6. QSBR 细粒度缓冲区无锁延迟释放与 STW 宏观循环对象回收的双轨协同架构。

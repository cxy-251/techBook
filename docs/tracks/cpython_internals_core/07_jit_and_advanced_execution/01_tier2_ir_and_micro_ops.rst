=============================================================================
Tier 2 优化器架构、微指令 uops 轨迹提取与 Trace 执行
=============================================================================

.. note:: 前置背景与上下文承接
   在第 3 模块中，我们深入剖析了 PEP 659 自适应指令特化（Adaptive Specialization）与 Quickening 机制（即 **Tier 1 解释器**）。Tier 1 通过在字节码就地变异为特化操作码（如 ``BINARY_OP_ADD_INT`` 或 ``LOAD_ATTR_MODULE``），显著减少了通用类型分发的动态开销。然而，Tier 1 仍然受限于传统栈式虚拟机的基本块边界与操作码粒度，无法跨越多条指令进行死代码消除、冗余类型守卫剔除或寄存器分配。
   
   为了打破这一性能天花板，CPython 3.13 引入了划时代的 **Tier 2 优化器（Tier 2 Optimizer）与微指令中间表示（Micro-Operations IR, uops）**。这是 CPython 迈向现代 JIT 编译器的核心承重墙。
   
   本章作为**第 7 模块【Python 3.13+ Copy-and-Patch JIT 与未来展望】的开篇之作**，将深入 CPython 核心源码文件 ``Include/internal/pycore_uop.h``、``Include/internal/pycore_optimizer.h``、``Python/optimizer.c``、``Python/optimizer_analysis.c`` 以及 ``Python/tier2_optimizer.c``，全景式解构 Tier 2 优化器的分层架构、热点循环探测与 Trace 线性轨迹投射、微指令（uops）物理数据拓扑、基于 Bloom Filter 的依赖失效机制、抽象解释（Abstract Interpretation）类型推导与守卫消除优化，以及微指令解释器的执行与去优化回退（Deoptimization）状态机。

-----------------------------------------------------------------------------
1. CPython 执行引擎的三级火箭演进
-----------------------------------------------------------------------------

三层分级执行拓扑
~~~~~~~~~~~~~~~~

在 Python 3.13 中，虚拟机的执行架构演进为“三级火箭”式的多层级分层流水线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     CPython 3.13+ 三级执行分层拓扑                      |
   +=========================================================================+
   | [Tier 1] 经典 CEval 字节码循环 (PEP 659 Adaptive Interpreter)           |
   | └─ 基于栈帧的 Direct Threaded Code 解释器, 负责冷启动与单指令就地特化。    |
   +───────────────────────────────────┬─────────────────────────────────────+
                                       │ (逆向跳转热点计数器溢出: Hot Loop)
                                       ▼
   +-------------------------------------------------------------------------+
   | [Tier 2] 微指令 Trace 优化器 (Uop Optimizer & Abstract Interpreter)     |
   | ├── 展开宏字节码为微指令 (Micro-ops) 线性轨迹 (Trace Projection)         |
   | ├── 抽象解释推导类型, 执行冗余守卫消除 (Guard Elimination) 与常量折叠   |
   | └── 生成紧凑的 _PyExecutorObject 并在 Uop 解释器中高效执行。              |
   +───────────────────────────────────┬─────────────────────────────────────+
                                       │ (开启 JIT 编译: Copy-and-Patch)
                                       ▼
   +-------------------------------------------------------------------------+
   | [Tier 3] Copy-and-Patch JIT 机器码编译器                                |
   | └─ 将优化后的 uops 映射为原生机器指令模板, 拼接为本地机器码直接在 CPU 执行|
   +-------------------------------------------------------------------------+

为什么需要从字节码（Bytecode）降解为微指令（Uops）？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统的 Python 宏字节码（Macro Bytecode）将多个逻辑动作耦合在单个指令中。以 ``LOAD_ATTR_INSTANCE_VALUE`` 为例，它在底层同时包含了：
1. **类型守卫**：检查对象的 ``ob_type`` 与预期的版本号是否匹配；
2. **字典版本守卫**：检查类字典或实例属性表是否未发生突变；
3. **内存读取**：按固定偏移量从对象的属性数组中加载 ``PyObject*`` 并递增引用计数。

在 Tier 1 中，连续两条针对同一个对象的属性加载会执行两次完全相同的类型守卫检查。而 Tier 2 将其**拆解为不可分割的微指令（uops）**后，优化器便可利用静态分析直接将第二次冗余的类型守卫消除（Guard Elimination），从而实现数量级的指令精简！

-----------------------------------------------------------------------------
2. 热点循环探测与 Trace 轨迹投射
-----------------------------------------------------------------------------

逆向跳转计数器与退避机制（Backoff Counter）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Trace 的捕获起始于循环回边（Loop Back-Edge）。在 ``JUMP_BACKWARD`` 指令中，虚拟机维护了一个指数退避计数器（``_Py_BackoffCounter``）：
- 当循环高频执行时，计数器递减；
- 当计数器归零时，触发热点判定，虚拟机调用 ``_PyJit_TryInitializeTracing()`` 进入 **Tracing 录制模式**；
- 若优化生成失败或发生频繁去优化，计数器以指数级后撤（Backoff），防止在不可优化的冷代码上反复空耗 CPU 编译算力。

Trace 线性轨迹投射（Trace Projection）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

进入录制模式后，解释器继续正常执行代码，但每执行一条字节码，便会将其对应的微指令序列发射（Emit）到线程专有的缓冲区 ``_PyJitUopBuffer`` 中：
1. **跨基本块线性穿透**：Trace 沿着实际执行的分支路径记录，将条件跳转指令直接展开为前置的**守卫微指令（Guard Uops）**与后续的无条件直行指令；
2. **函数内联（Function Inlining）**：若在循环中遇到小函数调用（``CALL``），Trace 录制器可直接穿透函数栈帧，将子函数的微指令序列内联至主 Trace 中（最大内联深度受 ``MAX_ABSTRACT_FRAME_DEPTH`` 限制）；
3. **闭环收尾（Close Loop）**：当 Trace 再次执行到最初触发录制的 ``JUMP_BACKWARD`` 目标指令时，录制闭环，发射 ``_EXIT_TRACE`` 微指令并移交优化器。

3. 微指令（uops）物理数据拓扑与执行器结构
-----------------------------------------------------------------------------

`_PyUOpInstruction` 结构体物理内存布局
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Include/internal/pycore_uop.h`` 中，每条微指令被极致压缩在 **32 字节** 的结构体中：

.. code-block:: c

   typedef struct _PyUOpInstruction {
       uint16_t opcode:15;              /* 微指令操作码 (如 _GUARD_BOTH_INT, _BINARY_OP_ADD_INT) */
       uint16_t format:1;               /* 指令格式位 (UOP_FORMAT_TARGET 或 UOP_FORMAT_JUMP) */
       uint16_t oparg;                  /* 指令操作数 */
       union {
           uint32_t target;             /* 侧向出口 (Side Exit) 目标索引 */
           struct {
               uint16_t jump_target;    /* 条件跳转内部跳转目标 */
               uint16_t error_target;   /* 异常处理跳转目标 */
           };
       };
       uint64_t operand0;               /* 缓存载荷 0 (如预期的类型指针或版本号) */
       uint64_t operand1;               /* 缓存载荷 1 (如属性内存偏移量) */
   } _PyUOpInstruction;

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  _PyUOpInstruction 32 字节微指令内存拓扑                |
   +=========================================================================+
   | [00-01] opcode (15 bits) + format (1 bit)                               |
   | [02-03] oparg (16 bits): 微操作参数                                     |
   | [04-07] target / jump_target (32 bits): 侧向出口或跳转微指令偏移量        |
   | [08-15] operand0 (64 bits): 内联缓存数据 0 (类型指针 / 版本标记)         |
   | [16-23] operand1 (64 bits): 内联缓存数据 1 (属性偏移 / 常量载荷)         |
   | [24-31] 运行时统计与对齐填充 (8 字节)                                   |
   +-------------------------------------------------------------------------+

`_PyExecutorObject` 执行器拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当一条 Trace 经过分析与优化后，会被打包为一个一等公民的执行器对象 ``_PyExecutorObject``：

.. code-block:: c

   typedef struct _PyExecutorObject {
       PyObject_VAR_HEAD
       const _PyUOpInstruction *trace;  /* 指向优化后的静态微指令数组 */
       _PyVMData vm_data;               /* 虚拟机元数据 (关联的 CodeObject 与反向链表) */
       uint32_t exit_count;             /* 侧向出口总数 */
       uint32_t code_size;              /* 微指令数量 */
       size_t jit_size;                 /* JIT 机器码大小 (若已编译为机器码) */
       void *jit_code;                  /* 指向可执行机器码内存页的指针 */
       _PyExitData exits[1];            /* 动态侧向出口数组 (记录去优化回退信息) */
   } _PyExecutorObject;

Bloom Filter 依赖失效机制
~~~~~~~~~~~~~~~~~~~~~~~~~

为了让优化后的 Trace 能够安全地做出激进假设（例如假定全局内置字典未被修改、类型属性未被动态猴子补丁篡改），每个执行器关联了一个 **256 位的 Bloom Filter（``_PyBloomFilter``）**：
- 在生成 Trace 时，所有被该 Trace 依赖的全局对象指针（如 ``builtins.__dict__``、类型对象 ``PyTypeObject*``）通过 6 个 Hash 函数（$k=6$）投影至 Bloom Filter 位图中；
- 当 Python 程序动态修改某个类属性时，解释器调用 ``_Py_Executors_InvalidateDependency(interp, obj)``；
- 虚拟机通过位运算掩码（``bloom_filter_may_contain``）瞬间排查并仅失效（Invalidate）受影响的执行器，兼顾了激进优化的性能与动态特性的语义正确性！

4. 抽象解释与 SSA 优化流水线（optimizer_analysis.c）
-----------------------------------------------------------------------------

在原始 Trace 被执行之前，``Python/optimizer_analysis.c`` 会对其运行一轮基于**符号执行与抽象解释（Abstract Interpretation）**的高级优化流水线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Tier 2 抽象解释与优化流水线                         |
   +=========================================================================+
   | 原始 Uop 流 ──► [抽象栈与寄存器建模 (JitOptContext)]                    |
   |                     │                                                   |
   |                     ├── 1. 冗余类型守卫消除 (Redundant Guard Removal)   |
   |                     ├── 2. 常量折叠与常量传播 (Constant Propagation)    |
   |                     ├── 3. 栈顶缓存与内存载荷聚合 (Top-of-Stack Cache)  |
   |                     └── 4. 死代码消除与不可达分支修剪 (DCE)             |
   |                     │                                                   |
   |                     ▼                                                   |
   | 优化后紧凑 Uop 流 ──► 注入 _PyExecutorObject 或移交 JIT 编译器          |
   +-------------------------------------------------------------------------+

优化实战演推：类型守卫消除
~~~~~~~~~~~~~~~~~~~~~~~~~~

考虑简单的 Python 循环内累加 ``x = a + b``：
1. **未经优化的微指令序列**：

.. code-block:: text

   _GUARD_BOTH_INT (守卫 a 和 b 均为 int)
   _CHECK_PEP_523
   _BINARY_OP_ADD_INT (执行整数相加, 产出 c)
   ... (后续代码再次使用 a)
   _GUARD_TYPE_VERSION a (冗余守卫!)

2. **抽象解释器优化后**：
   - 符号执行引擎在第一次 ``_GUARD_BOTH_INT`` 之后，将抽象寄存器中的 ``a`` 和 ``b`` 的类型状态标记为确定性的 ``int (non-null)``；
   - 当遇到后续关于 ``a`` 的类型检查时，由于类型信息在当前 Trace 中未被破坏，直接**将后续守卫微指令整行抹除（NOP/Drop）**；
   - 最终生成的微指令流减少 30%~50%，为底层机器码生成扫清了全部障碍。

5. 微指令解释器执行与去优化回退（Deoptimization）
-----------------------------------------------------------------------------

执行器切入（`ENTER_EXECUTOR`）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 Tier 1 字节码循环在热点位置检测到已存在编译好的执行器时，将原字节码替换为 ``ENTER_EXECUTOR`` 指令：
- 虚拟机直接将执行权移交给 Tier 2 的微指令解释器循环（``_PyUop_Eval()``）或直接跳转至 JIT 机器码指针（``executor->jit_code``）；
- 执行器完全在连续的微指令缓冲区上高速推进，绕过传统 CEval 的巨大 ``switch-case`` 分发开销。

侧向出口与去优化（Side Exit & Deoptimization）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Trace 优化的核心在于“乐观假设”。一旦运行时的假设被打破（例如循环处理了 10,000 次整数后突然传入一个浮点数）：
1. **守卫断言失败**：微指令 ``_GUARD_BOTH_INT`` 判定失败；
2. **触发侧向出口（Side Exit）**：指令根据其 ``target`` 字段定位到对应的 ``_PyExitData``；
3. **状态重构与无缝回退**：
   - 执行器依据当前抽象栈的深度将寄存器值无损写回当前栈帧（``_PyInterpreterFrame``）；
   - 将虚拟机的指令指针（``frame->instr_ptr``）重置回 Tier 1 中对应的原始字节码物理地址；
   - 执行流程丝滑返回经典 CEval 解释器继续执行，**对用户代码完全透明，零崩溃风险**。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     守卫失效与去优化回退时序图                          |
   +=========================================================================+
   | [Tier 2 执行器] _GUARD_BOTH_INT (遇到 float 参数, 守卫失败!)            |
   |        │                                                                |
   |        ▼ (触发 Side Exit)                                               |
   | [_PyExitData] 提取回退字节码偏移与栈深度                                |
   |        │                                                                |
   |        ▼ (重构栈帧状态)                                                 |
   | [Tier 1 CEval] 从原始字节码位置无缝继续解释执行!                        |
   +-------------------------------------------------------------------------+

本章系统解构了 CPython 3.13+ Tier 2 优化器与微指令（uops）架构：
1. CPython 执行引擎从 Tier 1（就地特化）到 Tier 2（微指令 Trace）再到 Tier 3（JIT）的三级演进体系；

4. 基于 256 位 Bloom Filter 的毫秒级依赖精准失效模型；
5. 抽象解释流水线如何实现冗余守卫消除与死代码修剪；
6. ``ENTER_EXECUTOR`` 切入与基于 ``_PyExitData`` 的零崩溃去优化回退（Deoptimization）状态机。

JIT 守卫 Guard 指令、去优化 Deoptimization 与回退机制
=============================================================================

.. note:: 前置背景与上下文承接

-----------------------------------------------------------------------------
1. 动态语言 JIT 的核心基石：投机优化与守卫体系
-----------------------------------------------------------------------------

投机优化（Speculative Optimization）的必然性
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

若 JIT 编译器必须严格遵循 Python 的全动态语义（每次加法都检查是否重载了 ``__add__``、每次属性查找都扫描 MRO 链表），生成的机器码将充斥着数以百计的条件跳转与虚函数调用，执行效率与解释器相比毫无优势。

因此，现代高性能 JIT 的核心策略是**投机执行（Speculation）**：
- **乐观假设**：假定频繁执行的局部变量类型不会改变（如循环累加变量始终为 ``int``），全局环境未被破坏；
- **原生快轨（Fast Path）**：直接生成无保护的 CPU 算术指令（如单个 x86 ``add`` 寄存器加法）；
- **守卫护栏（Guards）**：在快轨之前插入微型断言指令，一旦运行时条件违背假设，立即跳出机器码并安全回退。

三大类核心守卫微指令
~~~~~~~~~~~~~~~~~~~~

在 CPython 3.13 中，守卫体系被抽象为多层次的专有微指令：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                        CPython JIT 核心守卫分类表                       |
   +====================+==========================+=========================+
   | 守卫类别           | 代表性微指令 (Uops)      | 验证的物理不变性        |
   +====================+==========================+=========================+
   | 1. 对象类型守卫    | _GUARD_BOTH_INT          | 验证操作数指针的类型    |
   |    (Type Guards)   | _GUARD_TYPE_VERSION      | 是否精确匹配目标类型与  |
   |                    | _GUARD_IS_TRUE_POP       | 类型版本号 (tp_version) |
   +--------------------+--------------------------+-------------------------+
   | 2. 结构与版本守卫  | _GUARD_KEYS_VERSION      | 验证对象属性字典或类    |
   |    (Struct Guards) | _GUARD_DORV_VALUES_INST  | 字典的键表版本未发生突变|
   +--------------------+--------------------------+-------------------------+
   | 3. 全局环境守卫    | _CHECK_PEP_523           | 验证全局内置命名空间    |
   |    (Global Guards) | _GUARD_BUILTINS_VERSION  | (builtins.__dict__) 与  |
   |                    | _CHECK_PERIODIC          | 帧评估钩子未被动态篡改  |
   +--------------------+--------------------------+-------------------------+

2. 守卫指令在底层机器码中的物理展开
-----------------------------------------------------------------------------

快轨直行与硬件分支预测友好性
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在编译期，Clang 将守卫微指令编译为硬件级的条件比较与相对跳转：

.. code-block:: nasm

   ; _GUARD_TYPE_VERSION 机器码模板 (x86-64 物理汇编展开)
   mov    rax, QWORD PTR [rdi+8]       ; 从 PyObject* 结构体偏移 8 字节处加载 ob_type
   mov    eax, DWORD PTR [rax+168]     ; 加载类型的 tp_version_tag 版本号
   cmp    eax, 0x1a2b3c4d              ; 比较是否与 JIT 编译期记录的期望版本一致
   jne    .L_side_exit_trampoline      ; 若不匹配: 触发侧向出口跳转!
   
   ; --- 命中快轨 (Fast-Path 直行执行, 0 分支预测惩罚) ---
   mov    rsi, QWORD PTR [rdi+24]      ; 直接从固定偏移加载属性指针...

- **分支预测器（Branch Predictor）优化**：由于 99.9% 的正常循环迭代均满足守卫条件，CPU 的动态分支预测单元（BPU）将条件跳转指令 ``jne`` 预测为“不发生跳转”，快轨代码保持单周期无气泡流水线推进；
- **冷慢路径隔离**：去优化跳转目标 ``.L_side_exit_trampoline`` 被放置在编译代码段的最末端（Cold Section），完全不污染 CPU L1-Instruction Cache。

3. 去优化（Deoptimization）与栈状态无损重构
-----------------------------------------------------------------------------

当守卫断言失败（例如循环处理了 10 万次整数后突然传入一个浮点数 ``float``），JIT 引擎必须触发**去优化（Deoptimization / On-Stack Replacement, OSR）**。

`_PyExitData` 侧向出口元数据结构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Include/internal/pycore_optimizer.h`` 中，每个侧向出口在物理内存中对应一个 ``_PyExitData`` 结构体：

.. code-block:: c

   typedef struct _PyExitData {
       uint32_t target;                 /* Tier 1 字节码回退目标偏移 (BC Offset) */
       uint16_t index:12;               /* 侧向出口在当前执行器中的索引号 */
       uint16_t stack_cache:2;          /* 栈顶寄存器缓存状态 */
       uint16_t is_dynamic:1;           /* 是否为动态出口 */
       uint16_t is_control_flow:1;      /* 是否为正常控制流分支出口 */
       _Py_BackoffCounter temperature;  /* 去优化温度退避计数器 */
       struct _PyExecutorObject *executor; /* 级联绑定的子执行器指针 (Trace Chaining) */
   } _PyExitData;

栈状态重构与无缝回退物理流水线
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    JIT 去优化 (Deoptimization) 物理时序                 |
   +=========================================================================+
   | 1. 守卫断言失败: 执行 jne 指令跳入 Side Exit 跳板                       |
   | 2. 寄存器同步: 将 CPU 物理寄存器中的临时值按抽象栈深度无损推入操作数栈  |
   | 3. 栈帧指针回填: 从 _PyExitData 中提取 target 原始字节码物理地址        |
   |    frame->instr_ptr = &code->co_code_adaptive[exit->target];            |
   | 4. 退出 JIT 机器码: 执行 ret 返回至 Tier 1 解释器循环 _PyEval_EvalFrameDefault|
   | 5. 解释器无感接管: CEval 从被中断的字节码处无缝恢复解释执行!             |
   +-------------------------------------------------------------------------+

整个去优化过程对用户 Python 业务逻辑**100% 透明**，不改变任何全局或局部变量状态，彻底杜绝了动态编译导致进程崩溃的系统风险。

4. 侧向出口级联（Trace Stitching / Chaining）
-----------------------------------------------------------------------------

单条 Trace 只能覆盖线性单路径。但在现实场景中，代码经常出现双分支多态（如 ``if/else`` 或双类型输入）。

如果某个侧向出口被频繁触发（去优化计数超过热点阈值）：
1. **多态探测**：虚拟机并不彻底废弃该 JIT 代码，而是捕获该侧向出口；
2. **挂载子 Trace**：JIT 针对该侧向出口的新执行路径录制第二条 Trace，并编译为子执行器；
3. **机器码热修补（Trace Stitching）**：直接修改原执行器对应侧向出口跳板处的跳转目标，将 ``jmp .L_deopt`` 原地改写为 ``jmp .L_sub_executor_jit_code``！
4. **生成网状 JIT 图（Trace Graph）**：多个 Trace 在原生机器码级别首尾级联拼接，形成一个完全无解释器介入的高性能机器码网状流。

5. 全局依赖失效机制（Invalidation）与 Bloom Filter 协同
-----------------------------------------------------------------------------

当 Python 程序在运行时执行动态修改（如 ``dict.__setitem__`` 篡改模块全局变量、修改类方法或动态添加方法）：
1. 解释器调用 ``_Py_Executors_InvalidateDependency(interp, obj)``；
2. **Bloom Filter 极速初筛**：
   - 虚拟机遍历当前解释器持有的所有执行器；
   - 通过执行器内置的 256 位 Bloom Filter 执行按位与判定（``bloom_filter_may_contain``）；
   - 若位图不匹配，说明该 JIT 机器码与被修改对象无任何依赖关系，直接跳过（单周期完成校验）；
3. **精准解绑与失效（Unlinking）**：
   - 若 Bloom Filter 判定可能命中，将执行器的 ``vm_data.valid`` 置为 0；
   - 将原字节码位置的 ``ENTER_EXECUTOR`` 指令原子还原为常规字节码操作码；
   - 后续执行自动回退至解释器，待热点稳定后再重新编译生成符合新环境的 JIT 机器码。

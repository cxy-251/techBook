=============================================================================
语法分析与 C 扩展模块加载、PyMethodDef 结构与 Stable ABI / Limited API 机制
=============================================================================

.. note:: 前置背景与上下文承接
   在前两章中，我们解构了 CPython 3.13+ 从 ``main()`` 到核心运行时就绪的初始化流水线，以及基于字节码冻结（Frozen Modules）与 PEP 451 协议的纯 Python 模块导入体系。然而，Python 之所以能在科学计算、人工智能与高性能后端领域占据统治地位，其真正的基石在于其与底层 C/C++、Rust 等原生语言无缝互操作的 **C 扩展机制（C Extension Modules）**。
   
   从 NumPy、PyTorch 到操作系统底层的 ``_socket`` 与 ``_ssl``，原生共享库是如何被 Python 虚拟机动态加载、符号绑定并封装为一等公民模块的？同时，面对 CPython 频繁的底层对象头重构与 Free-Threading 演进，C 扩展生态如何通过 **PEP 384 Limited API 与 Stable ABI（abi3）** 构筑跨版本的二进制兼容护城河？
   
   本章将深入 CPython 核心源码文件 ``Python/importdl.c``、``Python/import.c``、``Objects/moduleobject.c``、``Objects/methodobject.c`` 以及 ``Include/methodobject.h``，全景式剖析 C 扩展模块的动态链接加载流水线、``PyModuleDef`` 与 ``PyMethodDef`` 内存元数据拓扑、``METH_FASTCALL`` 向量调用分发状态机、参数解析器底层引擎，以及 Limited API 的不透明指针设计哲学。

-----------------------------------------------------------------------------
1. C 扩展模块物理形态与动态链接加载链路
-----------------------------------------------------------------------------

动态链接库物理载体
~~~~~~~~~~~~~~~~~~

在操作系统物理层，C 扩展模块本质上是一个标准的动态链接共享对象：
- **Linux / Android**：ELF 格式的 ``.so`` 文件（如 ``math.cpython-313-x86_64-linux-gnu.so``）；
- **macOS / iOS**：Mach-O 格式的 ``.so`` 或 ``.dylib`` 文件（如 ``math.cpython-313-darwin.so``）；
- **Windows**：PE 格式的 ``.pyd`` 文件（如 ``math.cp313-win_amd64.pyd``）。

动态符号探查流水线（`Python/importdl.c`）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当解释器在 ``importlib`` 流程中决定加载一个 C 扩展时，底层调用链路如下：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     C 扩展模块动态加载与初始化时序                      |
   +=========================================================================+
   | 1. importlib._bootstrap_external.ExtensionFileLoader.create_module()    |
   | └─ 调用内置模块函数 _imp.create_dynamic(spec)                           |
   +───────────────────────────────────┬─────────────────────────────────────+
                                       │ (进入 Python/import.c)
                                       ▼
   +-------------------------------------------------------------------------+
   | 2. _PyImport_FindSharedFuncptr() (Python/importdl.c)                    |
   | ├── POSIX: dlopen(pathname, RTLD_NOW | RTLD_LOCAL) 获得动态库句柄       |
   | ├── Windows: LoadLibraryExW(pathname, NULL, LOAD_WITH_ALTERED_SEARCH_PATH)|
   | └── 符号检索: dlsym(handle, "PyInit_" + modulename) 提取入口函数指针    |
   +───────────────────────────────────┬─────────────────────────────────────+
                                       │ 返回 PyModInitFunction 指针
                                       ▼
   +-------------------------------------------------------------------------+
   | 3. 执行模块初始化入口点 (PyInit_<name>)                                 |
   | ├── 单阶段初始化: 直接返回 PyModuleObject 指针                          |
   | └── 多阶段初始化 (PEP 489): 返回 PyModuleDef 指针, 执行两阶段装配        |
   +-------------------------------------------------------------------------+

单阶段初始化（Legacy） vs 多阶段初始化（PEP 489）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  单阶段初始化 vs 多阶段初始化 (PEP 489)                 |
   +====================+======================+=============================+
   | 维度               | 单阶段初始化 (Legacy)| 多阶段初始化 (PEP 489)      |
   +====================+======================+=============================+
   | 入口返回值         | PyObject* (模块实例) | PyModuleDef* (模块定义规格) |
   +--------------------+----------------------+-----------------------------+
   | 模块创建时机       | 在 PyInit 中立即创建 | 由 importlib 控制两阶段创建 |
   +--------------------+----------------------+-----------------------------+
   | 多解释器隔离支持   | 极差 (共享全局 C 变量)| 优秀 (支持 Per-Interpreter) |
   +--------------------+----------------------+-----------------------------+
   | Free-Threading 兼容| 需隐式启用全局 GIL   | 通过 Py_mod_gil 明确声明    |
   +--------------------+----------------------+-----------------------------+

在 Python 3.13 中，多阶段初始化通过槽位数组（``PyModuleDef_Slot``）声明核心能力：
- ``Py_mod_multiple_interpreters``：声明支持子解释器独立隔离（``Py_MOD_PER_INTERPRETER_GIL_SUPPORTED``）；
- ``Py_mod_gil``：声明支持自由线程无 GIL 运行（``Py_MOD_GIL_NOT_USED``）。若扩展未声明此槽位，CPython 将在加载该扩展时**瞬态重新激活全局 GIL 并发出运行时警告**，确保向后兼容安全性。

2. 核心元数据拓扑：PyModuleDef 与 PyMethodDef
-----------------------------------------------------------------------------

`PyModuleDef` 模块定义拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Include/moduleobject.h`` 中，每个 C 扩展模块必须静态声明一个 ``PyModuleDef`` 结构体：

.. code-block:: c

   struct PyModuleDef {
       PyModuleDef_Base m_base;         /* 运行时内部基类 (含 m_init, m_index, m_copy) */
       const char* m_name;              /* 模块名称 (如 "math") */
       const char* m_doc;               /* 模块文档字符串 __doc__ */
       Py_ssize_t m_size;               /* 模块状态空间大小 (字节数, 用于多解释器状态隔离) */
       PyMethodDef *m_methods;          /* 导出的 C 函数方法表数组 */
       PyModuleDef_Slot *m_slots;       /* PEP 489 执行期槽位定义 (多阶段初始化专享) */
       traverseproc m_traverse;         /* GC 遍历槽位 (用于扫描模块状态中的循环引用) */
       inquiry m_clear;                 /* GC 清理槽位 */
       freefunc m_free;                 /* 模块销毁析构释放函数 */
   };

`PyMethodDef` 方法表物理内存拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

模块中暴露给 Python 层调用的所有 C 原生函数，均通过以 ``{NULL, NULL, 0, NULL}`` 结尾的 ``PyMethodDef`` 结构体数组定义：

.. code-block:: c

   struct PyMethodDef {
       const char  *ml_name;            /* Python 层可见的方法名称 (8 字节指针) */
       PyCFunction ml_meth;             /* 底层 C 语言函数指针 (8 字节指针) */
       int         ml_flags;            /* 调用约定与参数特征标志位 (4 字节) */
       /* 4 字节编译器自动填充对齐 */
       const char  *ml_doc;             /* 方法文档字符串 (8 字节指针) */
   };

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PyMethodDef 32 字节内存对齐拓扑                     |
   +=========================================================================+
   | [00-07] ml_name: 指向方法名字符串的指针 (const char*)                   |
   | [08-15] ml_meth: 指向 C 实现函数的指针 (PyCFunction)                    |
   | [16-19] ml_flags: 标志位组合 (int, 如 METH_FASTCALL | METH_KEYWORDS)    |
   | [20-23] 64 位平台自动填充对齐 (Padding)                                 |
   | [24-31] ml_doc: 指向文档字符串的指针 (const char*)                      |
   +-------------------------------------------------------------------------+

`ml_flags` 调用约定全景状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

CPython 虚拟机依据 ``ml_flags`` 的位掩码组合，决定在 CEval 栈帧中如何将 Python 实参传递给底层的 C 函数指针：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                      ml_flags 调用约定与 C 函数签名表                   |
   +====================+====================================================+
   | 标志位组合         | 对应的 C 语言函数签名与参数传递机制                |
   +====================+====================================================+
   | METH_NOARGS        | PyObject* func(PyObject *self, PyObject *unused)   |
   |                    | 0 参数调用, 虚拟机不传递任何参数, 执行速度极快     |
   +--------------------+----------------------------------------------------+
   | METH_O             | PyObject* func(PyObject *self, PyObject *arg)      |
   |                    | 单参数调用, 直接传递单对象指针, 0 元组分配         |
   +--------------------+----------------------------------------------------+
   | METH_VARARGS       | PyObject* func(PyObject *self, PyObject *args)     |
   |                    | 传统变长参数, args 强制打包为 PyTupleObject        |
   +--------------------+----------------------------------------------------+
   | METH_VARARGS |     | PyObject* func(PyObject *self, PyObject *args,     |
   | METH_KEYWORDS      |                PyObject *kwargs)                   |
   |                    | 传统位置+关键字参数, 分别打包为 Tuple 和 Dict      |
   +--------------------+----------------------------------------------------+
   | METH_FASTCALL      | PyObject* func(PyObject *self,                     |
   |                    |                PyObject *const *args,              |
   |                    |                Py_ssize_t nargs)                   |
   |                    | 现代高性能向量调用, 直接传递 C 栈指针数组, 0 堆分配|
   +--------------------+----------------------------------------------------+
   | METH_FASTCALL |    | PyObject* func(PyObject *self,                     |
   | METH_KEYWORDS      |                PyObject *const *args,              |
   |                    |                Py_ssize_t nargs, PyObject *kwnames)|
   |                    | 向量调用+关键字参数, kwnames 传入只读键名元组      |
   +--------------------+----------------------------------------------------+
   | METH_METHOD        | PyObject* func(PyObject *self, PyTypeObject *cls,  |
   |                    |                PyObject *const *args, ...)         |
   |                    | 传递定义该方法的类类型, 用于显式超类调用与状态定位 |
   +--------------------+----------------------------------------------------+

3. 参数解析引擎与 Vectorcall 零开销分发
-----------------------------------------------------------------------------

传统 `PyArg_ParseTuple` 的开销瓶颈
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在传统 C 扩展中，通常在函数开头调用 ``PyArg_ParseTuple(args, "siO!", &str, &num, &PyList_Type, &list)``：
1. **格式化字符串扫描开销**：每次函数被调用时，解释器必须在运行时从头逐字符解析格式串 ``"siO!"``；
2. **堆内存分配与颠簸**：调用方在 CEval 栈上将实参先打包进一个临时的 ``PyTuple``（以及关键字 ``PyDict``），传递给 C 函数后，``PyArg_ParseTuple`` 再将其解包赋值给 C 局部变量，最后再将临时元组销毁。在高频循环中造成了极其严重的内存分配与引用计数颠簸。

Vectorcall 与 Argument Clinic 革命
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

CPython 3.13 内部全面转向 **Vectorcall 向量调用规范（PEP 590）** 与 **Argument Clinic 预编译代码生成器**：
- **调用方零堆分配**：虚拟机在值栈（Value Stack）上直接分配一个连续的指针数组 ``PyObject *const *args``，直接将栈指针传递给底层 C 函数；
- **编译期静态解析**：Argument Clinic 工具在 CPython 编译期间将格式约定预编译为专有 C 结构和跳转逻辑（如 ``_PyArg_ParseStack``），省去了全部格式化字符串的运行时扫描，将 C 扩展函数调用的分发延迟削减了 **40% 以上**！

4. ABI 兼容性护城河：Limited API 与 Stable ABI（PEP 384）
-----------------------------------------------------------------------------

C 扩展的跨版本二进制崩溃根源
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在标准的 CPython C API 中，由于暴露了过多底层 C 结构体的具体字段定义：
- 例如直接访问 ``op->ob_refcnt``、``op->ob_type`` 或 ``((PyTupleObject*)op)->ob_item[0]``；
- 一旦 CPython 次要版本升级（如 Python 3.11 引入指令特化导致栈帧变更，或 3.13 Free-Threading 将 ``PyObject`` 从 16 字节扩充为 32 字节）：
  - 结构体内部字段偏移量（Field Offsets）发生巨变；
  - 旧版本编译的动态链接库在运行时直接读取错误的物理内存地址，引发灾难性的内存破坏或段错误（Segmentation Fault）。
- 这导致每个 Python 次要版本都必须强制重新编译全部 C 扩展模块（生成形如 ``*.cpython-311-*.so``、``*.cpython-312-*.so`` 等版本绑定二进制包）。

Limited API 的不透明指针（Opaque Pointers）哲学
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了彻底解决 C 扩展生态的跨版本分发噩梦，**PEP 384** 提出了 **Limited API（受限 API）** 与 **Stable ABI（稳定 ABI，发布标识为 ``abi3``）**：

1. **结构体不透明化（Opaque Structs）**：
   在启用 ``#define Py_LIMITED_API 0x03080000``（锁定至 Python 3.8 基线）后，C 扩展代码中**无法直接访问任何 CPython 结构体的内部字段**（``struct _object`` 变为不透明类型，直接访问 ``op->ob_type`` 将在编译期报错）；
2. **纯函数式访问抽象（Accessor Functions）**：
   所有属性与字段访问被重定向为标准函数调用：
   - 获取类型：调用 ``Py_TYPE(op)``（宏展开为对动态库导出函数 ``PyType_Get(op)`` 的调用）；
   - 获取引用：调用 ``Py_REFCNT(op)``；
   - 访问元组：调用 ``PyTuple_GetItem(tuple, index)``；
3. **一次编译，永久运行（Write Once, Run on Any 3.x）**：
   开发者只需在 Python 3.8 下编译一次生成 ``package.abi3.so``（或打出通用 wheel 包 ``foo-cp38-abi3-manylinux_x86_64.whl``），该单一二进制文件即可直接在 Python 3.8、3.9、3.10、3.11、3.12、3.13 甚至未来的 3.14 上**免重新编译无缝动态加载运行**！

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Standard C API vs Limited API 对比                  |
   +====================+======================+=============================+
   | 维度               | Standard C API       | Limited API / Stable ABI    |
   +====================+======================+=============================+
   | 结构体可见性       | 暴露全部内部物理字段 | 纯不透明指针 (Opaque)       |
   +--------------------+----------------------+-----------------------------+
   | 字段访问方式       | 直接结构体指针偏移   | 必须通过导出函数 Getter/Setter |
   +--------------------+----------------------+-----------------------------+
   | 跨版本二进制兼容   | 否 (每个次要版本重编)| 是 (跨所有 Python 3.x 兼容)  |
   +--------------------+----------------------+-----------------------------+
   | 函数调用开销       | 0 (宏内联与直接内存) | 极小 (增加一层函数调用跳转) |
   +--------------------+----------------------+-----------------------------+
   | 典型应用场景       | PyTorch/NumPy (极速) | 多数纯工具库与跨版本发布包  |
   +--------------------+----------------------+-----------------------------+

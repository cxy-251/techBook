-----------------------------------------------------------------------------
1. 多子解释器演进哲学与 PEP 684 / PEP 554 愿景
-----------------------------------------------------------------------------

从共享全局 GIL 到独立 GIL 的历史跃迁
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

多子解释器（Sub-interpreters）概念早在 Python 1.5（1997年）便已引入 C API（``Py_NewInterpreter()``），允许在同一个操作系统进程内创建多个独立的 Python 运行上下文。然而在 Python 3.12 之前，所有子解释器存在一个致命的体系瓶颈：
- **全局 GIL 强锁死**：虽然每个子解释器拥有独立的 ``sys.modules``，但它们**必须竞争同一把进程级全局解释器锁（Global GIL）**；
- 结果是：多子解释器即使运行在不同的 OS 线程中，也无法实现真正的 CPU 多核并行计算，沦为纯粹的命名空间隔离工具。

PEP 684 与 PEP 554 的破局重构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Python 3.12+ 与 3.13 中，Eric Snow 主导的 **PEP 684（A Per-Interpreter GIL）** 与 **PEP 554（Multiple Interpreters in the Standard Library）** 正式完成了对 CPython 运行时的史诗级重构：
1. **GIL 所有权下沉**：将 GIL 从进程全局变量（``_PyRuntimeState``）剥离，下沉为每个 ``PyInterpreterState`` 实例内部私有的互斥锁（``interp->_gil``）；
2. **进程内微型容器**：每个子解释器拥有完全独立的堆内存空间（独立 ``obmalloc`` / ``mimalloc`` 堆）、独立的全局解释器状态、独立的内置类型字典与独立的垃圾回收器（GC）；
3. **标准库一等公民（``interpreters`` 模块）**：允许 Python 开发者无需编写复杂的 C 扩展或承担多进程（``multiprocessing``）庞大的 IPC 序列化与内存页复制（CoW）开销，直接在单进程内启动真正并行的多解释器集群。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     传统单进程 GIL vs PEP 684 独立 GIL 对比             |
   +=========================================================================+
   | 【传统 CPython (Python 3.11 以前)】                                     |
   |   进程全局共享唯一 Global GIL ──► 解释器 0 / 1 / 2 串行争抢锁 (0 并行)  |
   +─────────────────────────────────────────────────────────────────────────+
   | 【PEP 684 Per-Interpreter GIL (Python 3.12+ / 3.13+)】                  |
   |  [OS Thread 0] ──► [Interpreter 0] ──► 独占 GIL 0 ──► CPU Core 0 (全速) |
   |  [OS Thread 1] ──► [Interpreter 1] ──► 独占 GIL 1 ──► CPU Core 1 (全速) |
   |  [OS Thread 2] ──► [Interpreter 2] ──► 独占 GIL 2 ──► CPU Core 2 (全速) |
   +-------------------------------------------------------------------------+

2. `PyInterpreterState` 物理内存拓扑与状态下沉解耦
-----------------------------------------------------------------------------

全局状态下沉（Global State Demotion）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了实现解释器间的零锁竞争，CPython 团队将原本散落在进程全局变量中的绝大多数核心子系统全部迁移至 ``struct _is``（``PyInterpreterState``）内部：

.. code-block:: c

   struct _is {
       struct _ceval_state ceval;       /* 独立的字节码评估状态 (含 interp->ceval.gil) */
       struct _gil_runtime_state _gil;  /* 解释器私有的 GIL 状态机 ( Antoine Pitrou 锁) */
       struct _gc_runtime_state gc;     /* 独立的 3 代循环垃圾回收器链表与计数 */
       struct _import_state imports;    /* 独立的 sys.modules 字典与 importlib 实例 */
       struct _obmalloc_state *obmalloc;/* 独立的内存池状态 (或私有 Mimalloc Heap) */
       struct types_state types;        /* 静态内置类型 (type/object/int) 的私有 tp_dict */
       _PyXI_state_t xi;                /* 跨解释器通信与通道状态 */
       struct _stoptheworld_state stoptheworld; /* 独立的解释器内安全点暂停机制 */
       /* ... */
   };

.. code-block:: text

   +-------------------------------------------------------------------------+
   |               PyInterpreterState 独立隔离核心子系统拓扑                 |
   +=========================================================================+
   | 1. ceval & _gil: 独占的 _gil_runtime_state 结构体, 拥有独立的条件变量   |
   |    与 FORCE_SWITCHING 状态机, 跨解释器完全无锁交互。                   |
   +-------------------------------------------------------------------------+
   | 2. obmalloc 内存堆隔离: 每个子解释器拥有独立的 Arena/Pool 数组指针,     |
   |    对象分配与释放完全在本地堆中闭环, 彻底根除多核内存分配锁争用。       |
   +-------------------------------------------------------------------------+
   | 3. types 状态隔离: static builtin types (如 int, str) 的 tp_dict 被    |
   |    迁移至 types.builtins.initialized 数组中, 类属性修改互不干扰。        |
   +-------------------------------------------------------------------------+
   | 4. gc 隔离: 每个解释器拥有独立的分代双向链表, 执行 GC 仅暂停自身线程。  |
   +-------------------------------------------------------------------------+

3. 跨子解释器通信机制（Cross-Interpreter Data Sharing）
-----------------------------------------------------------------------------

为什么严禁跨解释器直接传递 `PyObject*` 指针？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Per-Interpreter GIL 架构下，**跨解释器直接传递裸指针（``PyObject*``）是绝对禁止的（Undefined Behavior）**：
1. **引用计数生命周期错乱**：解释器 A 的对象若被解释器 B 的线程执行 ``Py_DECREF``，由于各解释器内存分配器（``obmalloc``）与垃圾回收链表完全隔离，在解释器 B 中释放解释器 A 的内存会导致内存池元数据损坏；
2. **类型与方法缓存污染**：对象的 ``ob_type`` 指向的类字典属于创建它的解释器，跨解释器调用方法会破坏 MRO 属性查找缓存。

三大跨解释器通信通道（`_PyXI_state_t`）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了在保证严格隔离的前提下实现高效数据共享，CPython 提供了三大底层通信机制：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                      三大跨子解释器数据通信机制                         |
   +====================+======================+=============================+
   | 机制               | 物理实现原理         | 适用场景与性能特征          |
   +====================+======================+=============================+
   | 1. 结构化通道      | 基于 _interpchannels | 传递任意 Python 复合数据,   |
   |    (Channels/Queue)| 序列化 Marshal / 解包| 存在浅拷贝开销, 绝对内存安全|
   +--------------------+----------------------+-----------------------------+
   | 2. 共享只读缓冲区  | 共享底层 C 内存页    | 大规模张量/音视频流无拷贝   |
   |    (Shared Buffers)| (Shared Memory /     | 传递, 0 内存复制 (Zero-Copy)|
   |                    | Buffer Protocol)     |                             |
   +--------------------+----------------------+-----------------------------+
   | 3. 静态不朽单例    | 进程只读常量直接借用 | 基础不可变单例共享,         |
   |    (Immortal Objs) | (None, True, False,  | 0 引用计数加减, 0 数据转换  |
   |                    | 核心静态类型)        |                             |
   +--------------------+----------------------+-----------------------------+

通道（Channels）通信微观状态机
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Modules/_interpchannelsmodule.c`` 中：
- 通道由进程级的锁和双向环形缓冲区（Ring Buffer）保护；
- 发送方（Sender）将对象转换为跨解释器数据快照（``_PyXIData_t``，包含类型标记、析构钩子与序列化载荷）；
- 接收方（Receiver）在自身解释器的命名空间与堆中解包出全新的对等对象，实现完全解耦的 Actor 模型消息传递。

4. C 扩展多解释器兼容性挑战与隔离边界
-----------------------------------------------------------------------------

单阶段扩展模块的静态变量灾难
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传统 C 扩展往往在 C 代码中使用全局静态变量：

.. code-block:: c

   static PyObject *cached_data = NULL; // 静态全局变量!

当该扩展被多个子解释器同时导入时：
- 解释器 0 将自己的对象写入 ``cached_data``；
- 解释器 1 在并发执行时读取并修改 ``cached_data``；
- 导致跨解释器对象泄露与内存崩溃。

PEP 489 模块状态隔离规范
~~~~~~~~~~~~~~~~~~~~~~~~

为了在 Per-Interpreter GIL 下安全加载 C 扩展，扩展模块必须遵循 **PEP 489 多阶段初始化** 规范：
1. **声明状态大小（``m_size > 0``）**：在 ``PyModuleDef`` 中指定模块私有状态结构体的大小；
2. **通过 ``PyModule_GetState(module)`` 访问状态**：所有上下文变量必须存放在堆分配的模块私有状态中，每个子解释器在导入时分配独立的模块状态副本；
3. **声明隔离支持槽位**：必须显式设置 ``{Py_mod_multiple_interpreters, Py_MOD_PER_INTERPRETER_GIL_SUPPORTED}``。未声明该槽位的扩展，子解释器在加载时会直接抛出 ``ImportError: module does not support loading in subinterpreters``。

5. 架构对决：Free-Threading（PEP 703）vs Sub-interpreters（PEP 684）
-----------------------------------------------------------------------------

在 CPython 3.13+ 中，面对多核并行计算，开发者拥有两种截然不同但互补的体系路线：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |            Free-Threading (PEP 703) vs Sub-interpreters (PEP 684)       |
   +====================+======================+=============================+
   | 架构维度           | Free-Threading (无GIL)| Sub-interpreters (多解释器) |
   +====================+======================+=============================+
   | 并发模型           | 共享内存多线程模型   | CSP / Actor 消息传递隔离模型|
   +--------------------+----------------------+-----------------------------+
   | GIL 状态           | 彻底移除 (0 GIL)     | 各子解释器独占独立 GIL      |
   +--------------------+----------------------+-----------------------------+
   | 内存数据共享       | 直接共享原生对象指针 | 必须通过 Channel/Buffer 传递|
   +--------------------+----------------------+-----------------------------+
   | 引用计数机制       | 32B BRC 偏向引用计数 | 原生 16B 引用计数 (极速)    |
   +--------------------+----------------------+-----------------------------+
   | 单线程基准开销     | 约 5%~10% (BRC/锁开销| 0% (保持经典单线程极致性能) |
   +--------------------+----------------------+-----------------------------+
   | 锁竞争与死锁风险   | 存在 (需用户自行同步)| 零数据竞争与死锁风险        |
   +--------------------+----------------------+-----------------------------+
   | 最佳应用场景       | 大规模共享内存图计算 | 微服务任务隔离、并行流水线  |
   |                    | 高频多线程数据突变   | 高吞吐无状态请求处理 (Web)  |
   +--------------------+----------------------+-----------------------------+

小结与全模块总结导读
-----------------------------------------------------------------------------

本章系统解构了 CPython 3.13+ 多子解释器与 Per-Interpreter GIL 的底层拓扑与运行机制：
1. PEP 684 将 GIL 从全局运行时下沉至各个独立的 ``PyInterpreterState``，实现了单进程内的真正多核并行；
2. ``PyInterpreterState`` 对执行状态（``ceval._gil``）、内存堆（``obmalloc``）、类型字典（``types``）与 GC（``gc``）的四重物理隔离；
3. 跨解释器裸指针禁止原则与基于 Channels / Shared Buffers / Immortal Objects 的三大安全数据通信范式；
4. PEP 489 模块状态隔离规范（``PyModule_GetState``）消除 C 扩展静态变量污染；
5. Free-Threading（共享内存）与 Sub-interpreters（消息隔离）在现代多核架构下的工程权衡。

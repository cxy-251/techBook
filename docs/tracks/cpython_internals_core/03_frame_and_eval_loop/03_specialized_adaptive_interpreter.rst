=============================================================================
PEP 659 自适应指令特化机制 Adaptive Bytecode 与 Quickening 状态转换
=============================================================================

.. note:: 前置背景与上下文承接
   在前一章中，我们解构了 CPython 3.13+ 默认解释器主循环 ``_PyEval_EvalFrameDefault`` 的物理状态机、Direct Threaded Code 计算跳转分发以及基于 64 位原子位图 ``eval_breaker`` 的异步中断调度。在传统解释器中，由于 Python 的动态类型特性，每一条字节码指令（如 ``LOAD_ATTR`` 或 ``BINARY_OP``）在运行时都必须进行防御性的类型检查、MRO 继承链搜索或哈希字典查找。
   
   为了彻底解决这一性能瓶颈，Python 3.11+ 引入了**PEP 659 自适应指令特化体系（Specializing Adaptive Interpreter, 亦称 Quickening）**。它允许字节码在运行时自我感知操作数类型，并在物理内存中**原地动态变异（In-place Bytecode Mutation）**为专用特化操作码。本章将深入源码文件 ``Python/specialize.c``、``Include/internal/pycore_backoff.h``、``Include/internal/pycore_opcode_metadata.h`` 以及 ``Python/bytecodes.c``，全面推导局部单态假说、16 位指数退避计数器状态机、内联缓存（Inline Cache）物理拓扑、三大核心特化指令家族的微观机制，以及 Python 3.13+ Free-Threading 无锁并发下的线程局部字节码（TLBC）原子特化安全体系。

-----------------------------------------------------------------------------
1. PEP 659 核心设计哲学：局部单态假说
-----------------------------------------------------------------------------

动态类型语言性能低下的根源，在于其高度的多态性（Polymorphism）。以属性访问表达式 ``obj.x`` 为例，在通用语义下，解释器必须按序执行以下繁重步骤：
1. 检查 ``Py_TYPE(obj)`` 是否存在重载的 ``tp_getattro``；
2. 沿 MRO（方法解析顺序）链遍历基类查找是否存在 Descriptor（描述符）；
3. 检查描述符是否包含 ``__get__`` 槽位并分发；
4. 若无描述符，查找实例字典 ``obj.__dict__`` 进行哈希碰撞探测；
5. 若仍未找到，回退调用 ``__getattr__``。

这一系列防御性检查在单次属性访问中往往消耗数十至上百个 CPU 时钟周期。

局部单态假说（Locality of Monomorphism）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现代编译理论与大量生产环境追踪数据揭示了一个铁律：**虽然 Python 语言本身是全动态的，但特定源码位置（Call-site 或 Opcode-site）在绝大多数实际运行场景下，所处理的数据类型是高度单一且不变的（单态率通常超过 95%）**。

PEP 659 提出：与其每次都进行全量多态判定，不如**直接将字节码原地重写为针对特定类型的极速单态指令**，并在指令后预置由硬件对齐的 **内联缓存（Inline Cache, IC）** 槽位，直接记录对象的类型版本号与物理内存偏移量！

2. 指令特化生命周期与指数退避状态机
-----------------------------------------------------------------------------

在 CPython 中，每条支持特化的通用指令（如 ``LOAD_ATTR``、``CALL``、``BINARY_OP``）与紧随其后的 ``CACHE`` 条目共同构成一个**四态生命周期状态机**：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  PEP 659 指令特化与去优化四态状态机                      |
   +=========================================================================+
   | 1. 通用初始态 (Generic State: LOAD_ATTR, BINARY_OP)                     |
   | └─ 执行通用慢速查找，同时递减预热计数器 counter                         |
   +-------------------------------------------------------------------------+
                                     │
                                     ▼ (计数器归零: backoff_counter_triggers)
   +-------------------------------------------------------------------------+
   | 2. 尝试特化 (Specialize: Python/specialize.c)                           |
   | ├── 静态验证类型稳定性，提取物理内存偏移与版本标签 (tp_version_tag)     |
   | └── 原子改写操作码 ──► 特化态 (Specialized State)                       |
   +-------------------------------------------------------------------------+
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼ (守卫命中: 极速直行)                   ▼ (类型突变: 守卫失败)
   +---------------------------------------+ +-------------------------------+
   | 3. 特化高速态 (Specialized Hit)       | | 4. 去优化与指数退避 (Deopt)   |
   | ├── LOAD_ATTR_INSTANCE_VALUE          | ├── 恢复为通用操作码            |
   | ├── BINARY_OP_ADD_INT                 | ├── 将退避计数器指数级倍增惩罚  |
   | └── 仅需 1 条单周期内存加载指令！      | └── 抑制频繁震荡特化 (Cooldown)|
   +---------------------------------------+ +-------------------------------+

16 位指数退避计数器（``_Py_BackoffCounter``）拓扑
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了防止在多态交替震荡的代码点（如交替传入 ``int`` 与 ``str``）陷入“特化 $	o$ 失败 $	o$ 特化 $	o$ 失败”的严重性能颠簸，CPython 在 ``Include/internal/pycore_backoff.h`` 中设计了紧凑的 16 位位域计数器：

.. code-block:: c

   typedef struct {
       uint16_t value_and_backoff;
   } _Py_BackoffCounter;

   #define BACKOFF_BITS 3
   #define BACKOFF_MASK 7
   #define MAX_BACKOFF 6

- **高 13 位（``value``）**：当前倒计数值；
- **低 3 位（``backoff``）**：指数退避惩罚等级（0 ~ 6）。

每当一条特化指令遭遇类型不匹配触发去优化（``unspecialize()``）时，解释器会调用 ``restart_backoff_counter()`` 将退避等级递增，并从预编译的质数退避表 ``value_and_backoff_next[]`` 中加载更长的惩罚周期：

$$	ext{Next Count} \approx 2^{2 	imes 	ext{backoff} + 1}$$

- 第 1 次失败：冷却 6 次执行；
- 第 2 次失败：冷却 30 次执行；
- 第 3 次失败：冷却 126 次执行；
- 第 4 次失败：冷却 508 次执行；
- 达到上限：冷却 8190 次执行，彻底冻结特化尝试。

3. 内联缓存（Inline Cache）物理拓扑与版本守卫
-----------------------------------------------------------------------------

在代码生成阶段，编译器会根据每种指令的需求，紧随操作码之后预留若干个 16 位的 ``CACHE`` 槽位。

``LOAD_ATTR`` 内联缓存拓扑（``_PyAttrCache``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

以最典型的 ``LOAD_ATTR`` 为例，它占用了 9 个 16 位 Code Units（1 个主操作码 + 8 个 CACHE 单元或更紧凑结构）：

.. code-block:: c

   typedef struct {
       _Py_BackoffCounter counter;       /* 16 位自适应计数器 */
       uint32_t version;                 /* 32 位类型版本号 (tp_version_tag) */
       uint16_t index;                   /* 16 位物理字段偏移量 (或字典键索引) */
   } _PyAttrCache;

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                LOAD_ATTR_INSTANCE_VALUE 物理内联缓存布局                |
   +====================+====================================================+
   | Code Unit 0 (16b)  | LOAD_ATTR_INSTANCE_VALUE (oparg = name_index)      |
   +--------------------+----------------------------------------------------+
   | Code Unit 1 (16b)  | _Py_BackoffCounter (自适应退避计数器)               |
   +--------------------+----------------------------------------------------+
   | Code Unit 2-3 (32b)| uint32_t type_version (目标类的全局唯一版本标签)    |
   +--------------------+----------------------------------------------------+
   | Code Unit 4 (16b)  | uint16_t offset (实例内存中属性值的直接字节偏移)   |
   +--------------------+----------------------------------------------------+

特化执行的微观汇编级路径
~~~~~~~~~~~~~~~~~~~~~~~~

当解释器执行特化后的 ``LOAD_ATTR_INSTANCE_VALUE`` 时，其执行路径缩减为仅有 **3 步极速原子检查**（定义于 ``Python/bytecodes.c``）：

.. code-block:: c

   // 1. 类型守卫检查 (Type Guard Check)
   DEOPT_IF(Py_TYPE(owner)->tp_version_tag != cache->version);

   // 2. 托管字典有效性断言
   DEOPT_IF(!_PyObject_InlineValues(owner)->valid);

   // 3. 物理指针直接解引用 (Direct Memory Access)
   res = *(_PyStackRef *)((char *)owner + cache->index);
   *stack_pointer++ = res;

- **完全消除** 了哈希计算、字典数组遍历与 MRO 递归搜索；
- 将原来上百周期的调用规约为 **1 次指针对比 + 1 次内存读取**，执行性能直逼 C 语言原生结构体访问！

全局变量加载特化（``LOAD_GLOBAL`` 家族）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

对于 ``LOAD_GLOBAL`` 指令，由于模块全局字典 ``globals()`` 和内建字典 ``builtins`` 很少发生动态结构修改，CPython 引入了 **字典键版本标签（Dict Keys Version）**：
- ``LOAD_GLOBAL_MODULE``：缓存模块字典的 ``keys_version`` 与目标符号在哈希表中的线性索引 ``index``。执行时仅比对版本号，直接通过 ``dict->ma_values[index]`` 读取，使全局变量访问速度提升 3 倍；
- ``LOAD_GLOBAL_BUILTIN``：同时缓存全局字典版本与内建字典版本，当且仅当全局命名空间未覆盖该内建符号时，直接索引内建字典。

5. Free-Threading 自由线程下的并发特化安全
-----------------------------------------------------------------------------

在 PEP 703 引入的 Free-Threading（禁用 GIL）构建中，多个 OS 原生线程可能会在完全相同的时刻并发执行同一份 ``PyCodeObject`` 字节码。

并发数据竞争风险
~~~~~~~~~~~~~~~~

如果线程 A 正在将 ``LOAD_ATTR`` 特化为 ``LOAD_ATTR_INSTANCE_VALUE`` 并写入 ``_PyAttrCache``，而线程 B 同时读取该位置执行，可能会读取到撕裂的半写入操作码或损坏的内存偏移量，引发段错误（Segfault）。

三重并发安全防御体系
~~~~~~~~~~~~~~~~~~~~

CPython 在 ``Python/specialize.c`` 中构建了严密的并发安全屏障：

1. **原子操作码更新（Atomic CAS）**：
   修改操作码必须通过 ``_Py_atomic_compare_exchange_uint8`` 原子比较交换，确保操作码在单周期内瞬时替换，绝不产生非法中间态；
2. **线程局部字节码副本（Thread-Local Bytecode, TLBC）**：
   在多线程竞争激烈场景下，每个线程拥有独立的字节码镜像，各线程在其私有的指令副本上独立进行特化与退避，彻底消除跨核 Cache 伪共享与写竞争；
3. **临界区互斥（Critical Sections）**：
   在提取字典键版本与计算属性偏移时，使用 ``Py_BEGIN_CRITICAL_SECTION(owner)`` 锁定对象，保障缓存填写的内存可见性。

=============================================================================
元组不变性优化与列表过度分配 Over-allocation 扩容策略
=============================================================================

.. note:: 前置背景与上下文承接
   在前一章中，我们解构了 CPython 3.13+ Unicode 灵活字符串表示体系（FSR）的 1-byte/2-byte/4-byte 自适应紧凑编码、SIMD 掩码快速探测以及驻留单例池。在 Python 内建数据结构谱系中，除字符串外，最基础、最高频使用的连续线性序列是 **元组（``tuple``）** 与 **列表（``list``）**。
   
   虽然二者在 Python 语义层面同为按索引寻址的序列容器，但在物理内存布局、不可变性优化策略以及动态伸缩机制上有着本质的架构分歧。本章将深入 CPython 核心源码文件 ``Objects/tupleobject.c``、``Include/cpython/tupleobject.h``、``Objects/listobject.c`` 以及 ``Include/cpython/listobject.h``，深度剖析元组的单块内存内联拓扑、空元组单例与小对象 Free List 分级缓存池、不可变 GC 惰性摘除机制（Untracking），以及列表的双块内存拓扑、$\approx 1.125	imes$ 过度分配（Over-allocation）扩容数学模型、缩容滞后防抖机制，以及 Python 3.13+ Free-Threading 无锁读取与 QSBR 内存安全体系。

-----------------------------------------------------------------------------
1. 元组（PyTupleObject）：不可变性与单块内存极简设计
-----------------------------------------------------------------------------

物理内存单块内联排布（Single-Block Allocation）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Include/cpython/tupleobject.h`` 中，元组结构体定义如下：

.. code-block:: c

   typedef struct {
       PyObject_VAR_HEAD
       Py_hash_t ob_hash;               /* 缓存的哈希值 (-1 表示未计算) */
       PyObject *ob_item[1];            /* 柔性数组: 实际分配 ob_size 个元素指针 */
   } PyTupleObject;

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PyTupleObject 物理内存连续拓扑                      |
   +=========================================================================+
   | PyObject_VAR_HEAD (24 字节)                                             |
   | ├── ob_refcnt (8 字节)                                                  |
   | ├── ob_type (8 字节) ──► &PyTuple_Type                                  |
   | └── ob_size (8 字节): 元素个数 N                                        |
   +-------------------------------------------------------------------------+
   | ob_hash (8 字节): xxHash 计算的哈希值缓存                               |
   +-------------------------------------------------------------------------+
   | ob_item[0] (8 字节指针) ──► PyObject *                                  |
   | ob_item[1] (8 字节指针) ──► PyObject *                                  |
   | ...                                                                     |
   | ob_item[N-1] (8 字节指针) ──► PyObject *                                |
   +-------------------------------------------------------------------------+

- **单块内存分配**：元组在创建时一次性向内存分配器申请 ``sizeof(PyTupleObject) + (N - 1) * sizeof(PyObject*)`` 连续字节。对象头与元素指针数组紧密相连，无任何二级指针间接寻址，具有极佳的 CPU 空间局部性（Cache Locality）。

不可变性驱动的极致性能优化
~~~~~~~~~~~~~~~~~~~~~~~~~~

由于元组一旦初始化便不可修改，CPython 施加了四大激进优化：

1. **全局空元组单例（``tuple_empty``）**：
   进程全局维护唯一的静态单例 ``_Py_SINGLETON(tuple_empty)``。无论是字面量 ``()``、构造器 ``tuple()`` 还是任何返回 0 长度的切片操作，均直接返回该静态单例指针，**堆分配开销为 0**；
2. **切片与全拷贝的零开销共享（Zero-Copy Sharing）**：
   对元组执行全量切片 ``t[:]`` 或 ``tuple(t)`` 时，底层 ``tuple_slice()`` 直接通过 ``Py_NewRef(a)`` 返回原元组自身并递增引用计数，完全不产生新对象分配；
3. **分级空闲链表池（Tuple Free Lists）**：
   在 ``Objects/tupleobject.c`` 中，CPython 为长度在 $1 \sim 20$（``PyTuple_MAXSAVESIZE``）之间的小元组分别维护了定长空闲对象链表 ``tuples[index]``。被释放的小元组不会立即归还系统堆，而是直接推入对应长度的 Free List 槽位，供后续同尺寸元组瞬时复用；
4. **垃圾回收器惰性摘除（GC Untracking）**：
   在元组创建完毕后，解释器调用 ``_PyTuple_MaybeUntrack()`` 扫描其元素。如果元组内包含的所有对象均为不可变原子类型（如纯 ``int``、``str``、``float``、``bytes``），该元组绝不可能构成循环引用，解释器直接调用 ``_PyObject_GC_UNTRACK`` **将其彻底从 GC 分代追踪双向链表中剥离**，大幅削减垃圾回收扫描的 CPU 耗时！

2. 列表（PyListObject）：可变动态数组的双块内存拓扑
-----------------------------------------------------------------------------

双块内存分离排布（Two-Block Allocation）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

与元组不同，列表（``list``）支持高频动态插入、追加与删除。为了实现底层缓冲区的独立扩容而不改变列表对象自身的内存地址（保证 ``id(list)`` 恒定），列表采用了分离的双块内存模型：

.. code-block:: c

   typedef struct {
       PyObject_VAR_HEAD
       PyObject **ob_item;              /* 二级指针: 指向独立分配的连续指针数组 */
       Py_ssize_t allocated;            /* 当前 ob_item 缓冲区的总物理容量 */
   } PyListObject;

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     PyListObject 双块分离物理拓扑                       |
   +=========================================================================+
   | 【块 1: 列表头部对象 PyListObject】 (固定 40 字节, 堆地址恒定)          |
   | ├── PyObject_VAR_HEAD (ob_refcnt, ob_type, ob_size = 3)                 |
   | ├── allocated = 8 (底层物理缓冲区容量)                                  |
   | └── ob_item (二级指针) ──────────────┐                                  |
   +--------------------------------------┼----------------------------------+
                                          │
                                          ▼
   +-------------------------------------------------------------------------+
   | 【块 2: 独立元素指针缓冲区】 (由 PyMem_Realloc 动态伸缩)                |
   | ├── [0]: PyObject * ──► Item 0 (已用)                                   |
   | ├── [1]: PyObject * ──► Item 1 (已用)                                   |
   | ├── [2]: PyObject * ──► Item 2 (已用)                                   |
   | ├── [3]: NULL (未使用的空闲槽位, 预分配 Over-allocated)                 |
   | ├── ...                                                                 |
   | └── [7]: NULL                                                           |
   +-------------------------------------------------------------------------+

- **不变式约束（Invariants）**：
  $$0 \le 	ext{ob\_size} \le 	ext{allocated}$$

3. 列表过度分配（Over-allocation）扩容数学模型
-----------------------------------------------------------------------------

如果每次 ``append()`` 都向操作系统申请 ``realloc()``，频繁的系统调用与内存拷贝将导致追加操作的时间复杂度恶化为 $O(N^2)$。

CPython 扩容核心公式（``list_resize``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Objects/listobject.c`` 中，CPython 实现了一套兼顾空间利用率与平摊时间复杂度（Amortized Time Complexity）的黄金扩容算法：

.. code-block:: c

   static int
   list_resize(PyListObject *self, Py_ssize_t newsize)
   {
       size_t new_allocated;
       Py_ssize_t allocated = self->allocated;

       /* 1. 命中缓冲区宽限范围: 无需重新分配, 瞬时返回 */
       if (allocated >= newsize && newsize >= (allocated >> 1)) {
           Py_SET_SIZE(self, newsize);
           return 0;
       }

       /* 2. 过度分配核心递推计算公式 */
       new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3;

       if (newsize == 0)
           new_allocated = 0;

       /* 3. 物理重分配 */
       self->ob_item = (PyObject **)PyMem_Realloc(self->ob_item, new_allocated * sizeof(PyObject *));
       self->allocated = new_allocated;
       Py_SET_SIZE(self, newsize);
       return 0;
   }

扩容算法数学与物理剖析
~~~~~~~~~~~~~~~~~~~~~~

$$	ext{new\_allocated} = \left( 	ext{newsize} + \lfloor\frac{	ext{newsize}}{8}\rfloor + 6 \right) \ \& \ \sim 3$$

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     列表扩容阶梯增长序列全景                            |
   +====================+======================+=============================+
   | 目标元素数 newsize | 实际分配容量 allocated| 物理内存容量 (64-bit 指针)  |
   +--------------------+----------------------+-----------------------------+
   | 1                  | 4                    | 32 Bytes                    |
   | 5                  | 8                    | 64 Bytes                    |
   | 9                  | 16                   | 128 Bytes                   |
   | 17                 | 24                   | 192 Bytes                   |
   | 25                 | 32                   | 256 Bytes                   |
   | 33                 | 40                   | 320 Bytes                   |
   | 41                 | 52                   | 416 Bytes                   |
   +--------------------+----------------------+-----------------------------+

1. **增长系数 $\approx 1.125	imes$（$9/8$ 倍递增）**：
   相比经典教科书采用的 $2.0	imes$（倍增）或 $1.5	imes$ 增长，CPython 采用了更为温和的 $\frac{9}{8}$ 系数。在现代大内存数据处理场景下，极大地避免了在列表包含上千万元素时产生数以百兆计的空闲内存浪费；
2. **常数偏移 $+6$**：保证在列表极小时（如从 0 到 1 个元素）能够迅速跃升至 4 个槽位，避免连续小微扩容；
3. **低位掩码清零 ``& ~3``**：将分配容量强制向上对齐为 **4 的整数倍**（在 64 位平台对齐为 32 字节边界），与现代 CPU 缓存行（Cache Line, 64 字节）及操作系统分配器阶梯完美契合；
4. **平摊时间复杂度证明**：通过几何级数求和，连续执行 $N$ 次 ``append()`` 所触发的内存重分配与元素拷贝总开销严格收敛于 $O(N)$，即单次追加操作的 **平摊时间复杂度严格为 $O(1)$**。

缩容滞后防抖机制（Hysteresis Shrinking）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当从列表中通过 ``pop()`` 或切片删除元素时，如果元素一减少就立即缩容，在边界交替执行 ``append()`` 与 ``pop()`` 将导致灾难性的内存重分配抖动（Thrashing）。

CPython 设立了**滞后收缩屏障（Hysteresis Barrier）**：

$$	ext{当且仅当 } 	ext{newsize} < \frac{	ext{allocated}}{2} 	ext{ 时，才触发真正的物理内存缩容}$$

只要当前长度维持在已分配容量的 $50\% \sim 100\%$ 之间，列表仅修改 ``ob_size`` 计数，物理缓冲区尺寸保持不动，以零系统开销抵御所有瞬态数据波动。

4. Python 3.13+ Free-Threading 无锁与弱同步并发列表
-----------------------------------------------------------------------------

在 PEP 703 禁用全局解释器锁（GIL）后，多线程并发读取与修改列表成为核心挑战。

`_PyListArray` 包装结构与 QSBR 延迟回收
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在自由线程构建中，CPython 将列表缓冲区升级为独立的 ``_PyListArray`` 结构：

.. code-block:: c

   typedef struct {
       Py_ssize_t allocated;
       PyObject *ob_item[];
   } _PyListArray;

- **并发无锁读取（Lock-Free Read）**：
  通过 ``_PyList_GetItemRefNoLock()``，读线程无需获取对象的全局互斥锁，直接原子加载 ``ob_item`` 指针与数组元素，并通过 ``_Py_TryIncrefCompareStackRef`` 安全获取强引用；
- **扩容替换时的 QSBR 内存屏障**：
  当写线程执行 ``list_resize`` 导致旧的 ``_PyListArray`` 被废弃时，写线程调用 ``free_list_items(..., use_qsbr=true)`` 将旧缓冲区交由 QSBR 延迟队列处理，确保正在执行无锁读取的其他线程完全退出静止周期后才安全物理释放，彻底消除并发读写下的 Use-After-Free 崩溃。

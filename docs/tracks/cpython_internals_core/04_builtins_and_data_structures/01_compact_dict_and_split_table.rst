=============================================================================
字典紧凑哈希表 Compact Dict、DKIX 表与 Split Table 内存优化
=============================================================================

.. note:: 前置背景与上下文承接
   在前三个模块中，我们先后深入了 CPython 3.13+ 的底层对象模型与内存基石、前端编译与 AST 生成管线，以及虚拟机栈帧与 CEval 解释器执行引擎。在 Python 虚拟机的运行时世界中，字典（``dict``）是维系整个语言运行的最核心元数据枢纽——从模块命名空间（``f_globals``）、内建符号（``f_builtins``）、类属性表（``tp_dict``）到实例属性字典（``__dict__``），几乎所有的动态绑定均由字典承载。
   
   因此，字典的内存利用率与哈希检索速度直接决定了整个 Python 运行时的性能天花板。本章将正式开启**模块四【核心内建数据结构实现】**，深入源码文件 ``Objects/dictobject.c``、``Include/internal/pycore_dict.h`` 以及 ``Include/cpython/dictobject.h``，自底向上解构从传统稀疏哈希表向现代紧凑字典（Compact Dict）的架构革命、动态类型 ``dk_indices`` 索引表、基于位移与高位扰动的开放寻址探测算法（Perturbation Probing）、共享键拆分表（Split Table）与实例属性内联值（Inline Values）技术，以及 Python 3.13+ Free-Threading 无锁并发读与 QSBR 内存延迟回收机制。

-----------------------------------------------------------------------------
1. 字典内存布局革命：从经典稀疏表到紧凑字典（Compact Dict）
-----------------------------------------------------------------------------

旧版稀疏哈希表（Python $\le$ 3.5）的内存痛点
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Python 3.6 之前，CPython 的字典直接将哈希条目嵌入稀疏哈希桶中：

.. code-block:: c

   /* 传统稀疏字典条目 (24 字节) */
   typedef struct {
       Py_hash_t me_hash;
       PyObject *me_key;
       PyObject *me_value;
   } PyDictEntry;

- **内存浪费极其严重**：为了控制哈希碰撞率，哈希表的装载因子（Load Factor）必须限制在 $2/3$ 以下。这意味着一个包含 8 个槽位的哈希表中，至少有 3 个槽位（每个 24 字节）处于 ``NULL`` 闲置状态，在 64 位机器上产生高达 30%~50% 的物理空洞内存浪费；
- **完全丧失插入有序性**：遍历字典只能沿着稀疏数组线性跳跃扫描，使得 Python 早期字典是无序的。

现代紧凑字典架构（Compact & Ordered Dict）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

自 Python 3.6+ 起（基于 Raymond Hettinger 与 Inada Naoki 的设计），CPython 将哈希索引与数据存储彻底解耦为两层：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  现代 Compact Dict 双层分离物理拓扑                     |
   +=========================================================================+
   | 1. 稀疏索引表: dk_indices[] (仅存储索引小整数, 占 1/2/4/8 字节)         |
   |    [ 0 | -1 |  2 | -1 |  1 | -1 | -1 | -1 ]  (哈希桶, 仅存数组下标)     |
   +-------------------------------------------------------------------------+
                                     │ (间接映射)
                                     ▼
   +-------------------------------------------------------------------------+
   | 2. 密集数据表: dk_entries[] (连续紧凑排布, 0 空洞, 100% 内存利用)       |
   |    ├── Entry 0: { hash=..., key="a", value=1 }                          |
   |    ├── Entry 1: { hash=..., key="b", value=2 }                          |
   |    └── Entry 2: { hash=..., key="c", value=3 }                          |
   +-------------------------------------------------------------------------+

这种架构带来了双重革命性突破：
1. **内存占用锐减 30%~40%**：稀疏空洞部分仅由极小的整数（如 ``int8`` 仅 1 字节）承担，昂贵的 24 字节对象条目全部集中在密集连续数组中；
2. **原生插入保序（Insertion Ordering）**：新插入的键值对永远按序追加在 ``dk_entries`` 的末尾，遍历字典只需线性扫描密集数组，极大提升了 CPU L1 数据缓存的预取能效。

2. PyDictKeysObject 结构与动态 dk_indices 压缩
-----------------------------------------------------------------------------

在 ``Include/internal/pycore_dict.h`` 中，字典的核心哈希元数据封装于 ``PyDictKeysObject`` 中：

.. code-block:: c

   struct _dictkeysobject {
       Py_ssize_t dk_refcnt;            /* 引用计数 (支持多字典共享键) */
       uint8_t dk_log2_size;            /* 哈希表总槽位数的 log2 值 (8, 16, 32...) */
       uint8_t dk_log2_index_bytes;     /* 索引数组占用总字节数的 log2 值 */
       uint8_t dk_kind;                 /* 字典种类: GENERAL, UNICODE, SPLIT */
       uint32_t dk_version;             /* 字典键全局版本号 (供 JIT 与特化守卫) */
       Py_ssize_t dk_usable;            /* 剩余可插入槽位数 (<= 2/3 上限) */
       Py_ssize_t dk_nentries;          /* 密集数组中已占用的条目数 */
       
       /* 柔性数组: 紧随其后排布 dk_indices[] 稀疏索引与 dk_entries[] 密集数组 */
       char dk_indices[];
   };

动态定宽索引压缩（Int8 / Int16 / Int32 / Int64）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了进一步压缩稀疏索引表的内存，CPython 根据哈希表总容量 $	ext{DK\_SIZE}$ 动态选择最小的整数宽度（定义于 ``dictkeys_get_index``）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     dk_indices[] 动态数据宽度伸缩表                     |
   +====================+==========================+=========================+
   | 字典总容量 dk_size | 索引元素物理类型         | 单槽位内存占用          |
   +--------------------+--------------------------+-------------------------+
   | $\le 128$          | int8_t  (char)           | 仅 1 Byte (0x00 ~ 0x7F) |
   +--------------------+--------------------------+-------------------------+
   | $256 \sim 2^{15}$  | int16_t (short)          | 2 Bytes                 |
   +--------------------+--------------------------+-------------------------+
   | $2^{16} \sim 2^{31}$| int32_t (int)           | 4 Bytes                 |
   +--------------------+--------------------------+-------------------------+
   | $\ge 2^{32}$       | int64_t (long long)      | 8 Bytes                 |
   +--------------------+--------------------------+-------------------------+

- **特殊哨兵常量**：
  - ``DKIX_EMPTY (-1)``：该槽位从未被使用过；
  - ``DKIX_DUMMY (-2)``：伪删除标记（Tombstone），表明该槽位曾被使用但已被删除，探查链在此不可中断。

3. 哈希冲突探测算法：扰动开放寻址法（Perturbation Probing）
-----------------------------------------------------------------------------

为什么不使用线性探查（Linear Probing）？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Python 中，整数对象的哈希值就是其自身（例如 ``hash(1) == 1, hash(2) == 2``）。如果采用简单的线性探查（$j = j + 1$），连续到达的整数键会在哈希表局部迅速堆积形成长链集群（Primary Clustering），使冲突解决急剧恶化。

扰动递推数学模型
~~~~~~~~~~~~~~~~

CPython 在 ``Objects/dictobject.c`` 的 ``do_lookup()`` 中实现了一种精妙的非线性双重扰动探查递推序列：

$$j_0 = 	ext{hash} \pmod{2^i}$$

$$j_{k+1} = \left( 5 	imes j_k + 1 + 	ext{perturb}_k \right) \pmod{2^i}$$

$$	ext{perturb}_{k+1} = 	ext{perturb}_k \gg 5$$

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                 扰动探查算法的两大数学物理保证                          |
   +=========================================================================+
   | 1. 全周期遍历保证: 线性同余发生器 (5*j + 1) mod 2^i 在数学上严格保证    |
   |    在 2^i 步内能且仅能遍历 [0, 2^i - 1] 内的所有整数各一次 (满周期定理)  |
   +-------------------------------------------------------------------------+
   | 2. 高位熵注入打散: 每次递推将 perturb 右移 5 位并注入低位, 使得高位哈希  |
   |    参与早期探测, 迅速放大细微哈希差异, 彻底消除连续整数聚集冲突         |
   +-------------------------------------------------------------------------+

当探查持续进行时，``perturb`` 最终会衰减为 0，此时序列平滑退化为纯粹的伪随机置换群序列，结合装载因子上限 $	ext{USABLE\_FRACTION}(N) = \frac{2}{3} N$，在数学上 100% 保证必定能在常数步内找到目标键或空槽位。

4. 共享键拆分表（Split Table）与实例属性内联优化
-----------------------------------------------------------------------------

面向对象内存爆炸痛点
~~~~~~~~~~~~~~~~~~~~

在面向对象编程中，一个类可能被实例化 1,000,000 次（例如 ``class Point: def __init__(self, x, y): ...``）。每个实例都有自己的 ``__dict__`` 字典。
如果每个实例都分配一个独立的 ``PyDictKeysObject``，这 1,000,000 个实例将重复存储 1,000,000 份一模一样的键名 ``"x"`` 和 ``"y"`` 及其哈希表索引结构。

Split Table（拆分表）共享架构
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

CPython 引入了 **Split-table Dict（``DICT_KEYS_SPLIT``）** 机制：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                     Split Table 属性共享内存模型                        |
   +=========================================================================+
   | 类元类型 PyHeapTypeObject                                               |
   | └── ht_cached_keys (唯一共享的 PyDictKeysObject, dk_refcnt = N)          |
   |     ├── 密集键数组: [ "x", "y" ]                                        |
   |     └── 稀疏索引表: dk_indices (记录 "x" 位于 slot 0, "y" 位于 slot 1)   |
   +-------------------------------------------------------------------------+
                         ▲                               ▲
                         │ 共享引用                      │ 共享引用
         ┌───────────────┴───────────────┐               │
         ▼                               ▼               ▼
   【实例 1: Point(10, 20)】       【实例 2: Point(30, 40)】   ...
   ├── ma_keys ──► (指向共享键)     ├── ma_keys ──► (指向共享键)
   └── ma_values:                  └── ma_values:
       values = [ 10, 20 ]             values = [ 30, 40 ]

- 所有同类实例的 ``ma_keys`` 强引用类对象上的全局单例 ``ht_cached_keys``；
- 每个实例字典仅需维护一个极其轻量的属性值指针数组 ``PyDictValues.values[]``，内存占用直接降低 **70% 以上**！

Python 3.11+ 内联属性值（Inline Values）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Python 3.11 中，解释器更进一步引入了 ``Py_TPFLAGS_INLINE_VALUES``：
- **完全免除实例字典的堆分配**：``PyDictValues`` 数组直接内联嵌入在实例对象 ``PyObject`` 物理内存的最尾部；
- 在用户没有显式调用 ``obj.__dict__`` 之前，实例在堆上甚至**不存在任何独立的字典对象**，属性读取直接映射为固定的 C 结构体物理内存偏移寻址。

5. Free-Threading 自由线程下的无锁读与 QSBR 内存回收
-----------------------------------------------------------------------------

在 PEP 703 移除全局解释器锁后，字典作为最高频共享的数据结构，面临极端的多线程读写并发挑战。

无锁快速读取（Lock-Free Read Protocol）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Python/dictobject.c`` 中，``_Py_dict_lookup_threadsafe()`` 支持在不加任何互斥锁的前提下进行并发读取：

1. **原子指针消费（Consume Load）**：
   使用 ``FT_ATOMIC_LOAD_PTR_CONSUME`` 读取密集数组中的 Key 指针；
2. **轻量引用计数尝试（``_Py_TryIncrefCompare``）**：
   在读取 Value 时，原子性地尝试增加其共享引用计数并比对地址一致性；若检测到正在发生并发覆写，则安全回退至慢速临界区加锁重试。

基于 QSBR（静止状态周期）的延迟内存回收
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当线程 A 正在无锁遍历读取某字典的 ``ma_keys`` 时，线程 B 可能正在向字典插入大量新键并触发了扩容（``dictresize``），导致旧的 ``PyDictKeysObject`` 被替换。

.. warning:: 如何防止旧表被 free() 导致线程 A 遭遇 Use-After-Free 崩溃？
   CPython 引入了 **QSBR（Quiescent State Based Reclamation）内存延迟释放队列**。

1. 当字典被多线程共享访问时，调用 ``_PyDict_EnsureSharedOnRead()`` 标记为 ``IS_DICT_SHARED``；
2. 扩容释放旧内存时，不调用底层的 ``free()``，而是调用 ``_PyMem_FreeDelayed()`` 将旧表指针推入当前线程的 QSBR 延迟队列；
3. 只有当进程中所有并发工作线程均穿过至少一次执行安全点（Quiescent State）后，系统确认无任何线程持有旧表指针，才物理释放该段内存，从根本上保障了无锁并发读取的绝对内存安全。

=============================================================================
Unicode 紧凑字符串表示 FSR：1-byte, 2-byte, 4-byte 字符紧凑编码
=============================================================================

.. note:: 前置背景与上下文承接
   在前一章中，我们剖析了 CPython 3.13+ 字典核心的 Compact Dict 架构、稀疏索引表与密集数组分离、以及针对类实例属性的 Split Table 与 Inline Values 内存优化。在解释器运行期间，几乎所有字典的键名、代码标识符、属性名以及文本数据，都是以 **字符串（``str`` / ``PyUnicodeObject``）** 的形式存在的。
   
   在早期 Python 中，Unicode 采用固定的 2 字节（UCS-2）或 4 字节（UCS-4）定宽存储，造成了灾难性的内存膨胀或对补充平面字符（如 Emoji、古代字符）的支持断层。自 Python 3.3（PEP 393）起，CPython 确立了**灵活字符串表示体系（Flexible String Representation, FSR）**。本章将深入 CPython 核心源码文件 ``Include/cpython/unicodeobject.h``、``Include/internal/pycore_unicodeobject.h`` 以及 ``Objects/unicodeobject.c``，深度解构 FSR 的自适应物理内存三态拓扑、基于 SIMD 与 64 位整数字节掩码的极速 ASCII/非 ASCII 探测算法、字符串按需升格与编码转换机制、四态字符串驻留（String Interning）单例池拓扑，以及基于 SipHash 的安全哈希与惰性 UTF-8 缓存体系。

-----------------------------------------------------------------------------
1. PEP 393 灵活字符串表示（FSR）设计哲学
-----------------------------------------------------------------------------

历史痛点：UCS-2 vs UCS-4 构建两难
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 Python 3.2 及以前，Python 在编译时必须通过编译选项二选一：
1. **Narrow Build（UCS-2）**：每个字符占用 2 字节（16-bit）。
   - **致命缺陷**：无法原生容纳大于 ``0xFFFF`` 的 Unicode 字符（如 Emoji、CJK 扩展字），必须使用代理对（Surrogate Pairs）拼凑，导致 ``len("𝄢") == 2``，彻底破坏了 $O(1)$ 随机按索引访问字符（Random Access）的底层语义；
2. **Wide Build（UCS-4）**：每个字符占用 4 字节（32-bit）。
   - **致命缺陷**：内存浪费达到极致。在以纯 ASCII 英文为主的源码或数据中，每个 ASCII 字符原本只需 1 字节，却强制占用 4 字节，造成高达 **400% 的物理内存膨胀**。

PEP 393 核心原则：按需动态自适应
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

PEP 393 提出了现代 FSR 架构的核心原则：
- **逻辑统一，物理按需**：无论底层采用何种物理存储，Python 层面均保持严格的定长逻辑码点索引（Unicode Code Points），确保所有字符的索引访问时间复杂度严格为 $O(1)$；
- **自适应选择最小编码宽度**：在字符串创建时扫描其最大码点（``maxchar``），从 1-byte、2-byte、4-byte 三种紧凑格式中选择最小的物理容器。

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                    PEP 393 字符存储类型与码点区间对照                   |
   +====================+==================+=================================+
   | 物理 Kind 类型     | 字符底层 C 类型  | 覆盖的 Unicode 码点区间         |
   +--------------------+------------------+---------------------------------+
   | PyUnicode_1BYTE    | Py_UCS1 (8-bit)  | U+0000 ~ U+007F (ASCII)         |
   | (ASCII 标记置 1)   |                  |                                 |
   +--------------------+------------------+---------------------------------+
   | PyUnicode_1BYTE    | Py_UCS1 (8-bit)  | U+0000 ~ U+00FF (Latin-1)       |
   | (ASCII 标记置 0)   |                  |                                 |
   +--------------------+------------------+---------------------------------+
   | PyUnicode_2BYTE    | Py_UCS2 (16-bit) | U+0000 ~ U+FFFF (基本多语言平面)|
   +--------------------+------------------+---------------------------------+
   | PyUnicode_4BYTE    | Py_UCS4 (32-bit) | U+0000 ~ U+10FFFF (全量 Unicode)|
   +--------------------+------------------+---------------------------------+

2. Unicode 对象的微观物理布局三态体系
-----------------------------------------------------------------------------

在 ``Include/cpython/unicodeobject.h`` 中，CPython 将字符串划分为三种高度特化的 C 结构体形态：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                  CPython 3.13+ Unicode 物理对象变体拓扑                 |
   +=========================================================================+
   | 1. Compact ASCII 字符串 (PyASCIIObject)                                 |
   | ├── PyObject_HEAD (16 字节)                                             |
   | ├── length (8 字节): 逻辑字符数                                         |
   | ├── hash (8 字节): 缓存的哈希值 (-1 表示未计算)                         |
   | ├── state (4 字节位域): kind=1, compact=1, ascii=1                      |
   | └── char data[length + 1]: 紧随其后的纯 ASCII 连续字符 (含 '\0')       |
   +-------------------------------------------------------------------------+
   | 2. Compact Non-ASCII 字符串 (PyCompactUnicodeObject)                    |
   | ├── _base (包含完整的 PyASCIIObject 头部, 36 字节)                      |
   | ├── utf8_length (8 字节): UTF-8 编码后的字节数                          |
   | ├── utf8 (8 字节指针): 惰性分配的 UTF-8 字节缓存 (可为 NULL)            |
   | └── data[length + 1]: 紧随其后的 UCS-1/UCS-2/UCS-4 字符数组             |
   +-------------------------------------------------------------------------+
   | 3. Legacy Non-Compact 字符串 (PyUnicodeObject, 仅用于 C 扩展子类)       |
   | ├── _base (PyCompactUnicodeObject)                                      |
   | └── union { void *any; Py_UCS1 *latin1; Py_UCS2 *ucs2; Py_UCS4 *ucs4; }|
   |     data (独立堆内存缓冲区分离指针)                                     |
   +-------------------------------------------------------------------------+

紧凑位域元数据（``_PyUnicodeObject_state``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

为了在 64 位系统上将元数据开销压至极限，对象的关键状态全部被压缩在一个 4 字节对齐的位域中：

.. code-block:: c

   struct _PyUnicodeObject_state {
       unsigned int interned:2;          /* 驻留状态 (0:未驻留, 1:普通, 2:不朽, 3:静态) */
       unsigned int kind:3;              /* 字符宽度: 1 (1-byte), 2 (2-byte), 4 (4-byte) */
       unsigned int compact:1;           /* 紧凑单块内存分配标记 */
       unsigned int ascii:1;             /* 纯 ASCII 标记 */
       unsigned int statically_allocated:1; /* 静态内建常量标记 */
   };

- **对齐与零拷贝优化**：对于最普遍的纯 ASCII 字符串，其 ``PyASCIIObject`` 头部仅占用 **40 字节**（含对齐填充），且由于 ASCII 本身就是合法的 UTF-8，其 ``utf8`` 字节流直接复用物理数据区 ``data``，**完全不需要额外的 UTF-8 内存指针与堆分配**！

3. 字符 Kind 探测与 SIMD 级字节掩码算法
-----------------------------------------------------------------------------

当从外部输入（如 UTF-8 字节流）构建一个新字符串时，解释器必须以极高吞吐扫描输入流，判定其是否为纯 ASCII。

64 位整数字节掩码并行探测（``find_first_nonascii``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在 ``Objects/unicodeobject.c`` 中，CPython 放弃了低效的单字节循环比较，采用 64 位整数字长掩码进行 **SIMD 级字节并行探测（SWAR - SIMD Within A Register）**：

.. code-block:: c

   #define ASCII_CHAR_MASK 0x8080808080808080ULL

   static Py_ssize_t
   find_first_nonascii(const unsigned char *start, const unsigned char *end)
   {
       const unsigned char *p = start;
       while (p + sizeof(size_t) <= end) {
           size_t u = *(const size_t *)p;
           /* 只要 8 个字节中任意一字节的最高位 (Bit 7) 为 1, (u & MASK) 即非零 */
           if (u & ASCII_CHAR_MASK) {
               /* 命中非 ASCII 字节: 利用硬件指令 __builtin_ctzll 极速定位首个非 ASCII 字节偏移 */
               return p - start + (__builtin_ctzll(u) - 7) / 8;
           }
           p += sizeof(size_t); // 每次跳跃推进 8 个字节！
       }
       ...
   }

通过这种单指令测试 8 字节的技术，ASCII 字符串的校验与解析吞吐量轻松突破 **10 GB/s**。

动态升格机制（Character Widening）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在执行字符串拼接（``+``）或追加（``+=``）时，如果左操作数是 1-byte（ASCII），而右操作数包含了 2-byte（如中文字符），解释器通过 ``_PyUnicode_CONVERT_BYTES`` 宏在物理层将原数组原地或重新分配升格：

.. code-block:: c

   #define _PyUnicode_CONVERT_BYTES(from_type, to_type, begin, end, to) \
       do {                                                            \
           to_type *_to = (to_type *)(to);                             \
           const from_type *_iter = (const from_type *)(begin);         \
           const from_type *_end = (const from_type *)(end);           \
           while (_iter < _end) {                                      \
               *_to++ = (to_type) *_iter++; /* 编译器自动矢量化扩宽 */ \
           }                                                           \
       } while (0)

4. 字符串驻留（String Interning）与单例池架构
-----------------------------------------------------------------------------

在 Python 运行时中，同一个标识符（如变量名 ``"self"``、属性名 ``"name"``）会在成千上万个函数和字典中反复出现。如果为每个出现都分配一个独立的字符串对象，不仅浪费内存，还会摧毁哈希表的检索效率。

驻留四态拓扑
~~~~~~~~~~~~

CPython 维护了四级驻留生命周期状态（``PyASCIIObject.state.interned``）：

.. code-block:: text

   +-------------------------------------------------------------------------+
   |                      字符串驻留生命周期状态机                           |
   +=========================================================================+
   | SSTATE_NOT_INTERNED (0)                                                 |
   | └─ 普通动态分配字符串, 遵守标准生命周期与引用计数回收                   |
   +-------------------------------------------------------------------------+
                                     │ (调用 _PyUnicode_InternMortal)
                                     ▼
   +-------------------------------------------------------------------------+
   | SSTATE_INTERNED_MORTAL (1)                                              |
   | ├── 插入解释器级 interned_strings 弱引用字典                            |
   | └── 当外部引用归零时, 自动从字典中 Pop 移出并安全销毁 (避免内存泄漏)     |
   +-------------------------------------------------------------------------+
                                     │ (调用 _PyUnicode_InternImmortal)
                                     ▼
   +-------------------------------------------------------------------------+
   | SSTATE_INTERNED_IMMORTAL (2)                                            |
   | ├── 引用计数被锁定为不朽 (_Py_IMMORTAL_REFCNT)                          |
   | └── 进程退出前永不析构, 全局线程安全共享                                |
   +-------------------------------------------------------------------------+
                                     │
                                     ▼
   +-------------------------------------------------------------------------+
   | SSTATE_INTERNED_IMMORTAL_STATIC (3)                                     |
   | └── 静态嵌入在 _PyRuntime 结构体中的内建字符串 (如空串、常见魔术方法名)  |
   +-------------------------------------------------------------------------+

标识符指针比较的性能飞跃
~~~~~~~~~~~~~~~~~~~~~~~~

所有 Python 源码在编译阶段产生的变量名和属性名，均会被强制进行**不朽驻留（Immortal Interning）**。
- 当比较两个驻留字符串时（如在 ``dict`` 查找或解释器比较操作中）：

.. code-block:: c

   if (str1 == str2) {
       return 1; // 仅需 1 条 CPU 指令比较指针物理地址, 耗时 0.2 ns！
   }

彻底免除了昂贵的 ``memcmp()`` 全量字节扫描。

单字符 Latin-1 单例池
~~~~~~~~~~~~~~~~~~~~~

CPython 在运行时初始化阶段（``init_global_interned_strings``），预先分配了覆盖全量 Latin-1 字符集（``0x00 ~ 0xFF``）的 **256 个静态单字符单例（``LATIN1(ch)``）**。
任何长度为 1 的 Latin-1 字符操作（如 ``chr(65)`` 或 ``"A"[0]``）均直接返回静态单例指针，**堆分配开销绝对为零**。

5. SipHash-1-3 / 2-4 哈希安全与惰性 UTF-8 缓存
-----------------------------------------------------------------------------

SipHash 安全哈希算法
~~~~~~~~~~~~~~~~~~~~

为了防御利用哈希碰撞实施拒绝服务攻击（HashDoS），CPython 采用加密级伪随机哈希算法 **SipHash-1-3 / SipHash-2-4**（定义于 ``Python/pyhash.c``）：
- 在每次 Python 进程启动时，通过操作系统熵源随机生成全局密钥 ``_Py_HashSecret``；
- 当首次调用 ``hash(str)`` 时，计算出的哈希值被缓存在 ``PyASCIIObject.hash`` 字段中；
- 后续所有哈希调用直接读取缓存字段，实现 $O(1)$ 常数级极速返回。

惰性 UTF-8 导出（Lazy UTF-8 Caching）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

当 C 扩展模块调用 ``PyUnicode_AsUTF8AndSize()`` 需要 UTF-8 格式的 C 字符串指针时：
1. 若为 ASCII 字符串，直接返回数据区首地址（0 开销）；
2. 若为 Non-ASCII 紧凑字符串且 ``utf8`` 字段为 ``NULL``，触发惰性编码器 ``unicode_fill_utf8()``：
   - 临时分配一段内存将 UCS-2 / UCS-4 转换为标准 UTF-8 字节流；
   - 将结果指针原子性地挂载于 ``PyCompactUnicodeObject.utf8``；
   - 后续调用直接复用该指针，直到字符串销毁时统一释放。

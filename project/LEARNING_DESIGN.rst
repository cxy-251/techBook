学习设计
========

``techBook`` 的目标不是批量生产文章，而是把 ``aiBook/docs`` 中的技术方向重做成一套
面向零基础程序员、可以从入门走向独立解决问题的学习系统。

学习是否发生
------------

读者看懂一段文字不代表已经学会。一个学习单元完成后，读者至少应当能够：

#. 预测一个最小示例的结果；
#. 根据输出或现象解释为什么；
#. 修改一个条件并重新判断；
#. 识别一个常见错误理解；
#. 在不照抄原示例的情况下完成一个小型迁移任务。

缺少其中关键步骤时，内容只能算资料说明，不能标记为完成的学习单元。

零基础读者模型
--------------

* 不假设读者知道尚未在当前学习路径中建立的术语。
* 一个新术语第一次出现时，必须绑定当前代码、对象、状态或现象。
* 内容需要前置能力时，必须链接到已有单元，不能用一句“需要基础知识”跳过。
* 源码阅读是较高阶段的学习工具，不是所有主题的开场方式。
* 一次只引入解决当前困惑所需的最少概念。

能力层级
--------

``L1 运行``
   能写出或运行最小示例，知道结果是什么。

``L2 解释``
   能指出关键对象、调用、状态变化和结果之间的关系。

``L3 修改``
   改变参数、数据或场景后仍能预测结果，并解释边界。

``L4 排错``
   面对错误输出，能够提出假设并设计验证步骤。

``L5 迁移``
   面对未见过的代码或系统，能够查文档、读源码、构造实验并形成判断。

每条学习路径必须明确从哪个层级开始，以及最终要求读者达到哪个层级。

学习单元结构
------------

一个 unit 只负责一次清晰的能力变化。默认结构如下：

#. ``为什么现在需要它``：给出真实场景或可观察困惑；
#. ``先预测``：在解释出现前让读者作出判断；
#. ``最小示例``：只保留触发现象所需内容；
#. ``真实结果``：展示可运行输出、界面现象、编译结果或源码证据；
#. ``逐步推理``：把每个结论连接到具体代码、对象和结果；
#. ``改变一个条件``：建立边界，防止只记住单个答案；
#. ``常见误解``：直接指出错误模型及其错误原因；
#. ``能力检查``：问题必须来自前面的预测与证据；
#. ``答案与推理``：说明答案来源，也说明常见错误答案为什么错；
#. ``独立任务``：要求读者完成一个小型迁移；
#. ``完成标准``：定义何时算学会，而不是何时算读完。

不是所有单元都需要机械保留全部标题。删减时不能删除预测、证据、推理和迁移这条主链。

证据类型
--------

证据必须与学习阶段匹配：

* 语言基础可以使用运行结果、对象状态和官方语言文档；
* 编译与类型问题可以使用编译错误、警告、AST 或中间表示；
* Web 与系统内容可以使用请求、日志、网络面板、进程状态和最小服务；
* 源码级内容需要固定实现、版本、commit、源码符号和可复现观察；
* 架构内容需要具体场景、边界、失败路径和可定位的系统组件。

禁止为了显得“底层”而强行加入源码。也禁止在需要源码证明时只写抽象描述。

问题设计
--------

问题不是正文结束后的装饰。每个问题必须记录：

* 它来自哪个现象、代码行或输出；
* 正确答案需要经过哪些推理步骤；
* 哪项证据支持答案；
* 常见错误答案依赖了什么错误模型；
* 答错后应该回到哪个步骤重新观察。

无法回答“为什么要问这个问题”的题目必须删除。

解释标准
--------

解释应当使用可追踪语言：

* 指明是哪一行代码、哪个对象、哪个函数或哪个状态；
* 说明输入发生了什么变化；
* 说明输出为什么随之变化；
* 区分事实、推断和约定；
* 每段只增加一个新的判断。

避免使用“系统进行处理”“框架负责协调”“底层完成转换”等无法定位的句子。

学习路径与单元计划
------------------

路径开始时固定：目标读者、入口能力、最终能力、阶段顺序、范围和明确排除项。

完整章节数量不在开头冻结。每个阶段开始前设计一个小批次 unit，并在实际阅读、实验和
能力检查后校准下一批。这样既不会每次临时选题，也不会在没有学习反馈时提前填满整本书。

黄金样例
--------

批量迁移 ``aiBook/docs`` 前，需要完成三类黄金学习单元：

* 一个语言基础单元；
* 一个系统或框架行为单元；
* 一个源码级单元。

黄金单元用于校准篇幅、解释密度、问题设计、答案推理、实验比例和 RST 阅读体验。三个样例
没有通过实际阅读检查前，不进行大规模内容生成。

Linux Kernel稳定生产与回溯审查合同
===================================

本合同把Linux Kernel正文的技术质量、跨章连续性、跨对话接续和提交边界固定为一套
可重复执行的流程。它解决的不是某一章的措辞问题，而是防止随着章节和对话增长出现
事实漂移、状态丢失、机械压缩和未经验证的连续生产。

权威顺序
--------

发生冲突时依次服从：

#. 用户当前明确指令；
#. 根目录 ``AGENTS.md``；
#. 本合同；
#. ``project/STATE.rst`` 的当前动态状态；
#. 当前批次审计报告；
#. 固定提交的一手源码和架构文档；
#. 既有正文、README、index与旧manifest描述。

既有正文只能证明过去写过什么，不能证明技术事实正确。旧聊天记录不属于项目依赖。

工作模式
--------

``retrospective-audit``
   从第001章开始顺序核验现有正文，发现问题就在当前批次修复。第193章审查完成前，
   禁止生产后续章节。

``forward-production``
   回溯审查闭合以后，从重新核定的最后状态继续生成新章。每批仍先研究、再逐章写作、
   最后整批复核。

``blocked``
   固定源码、平台条件或关键边界无法确定，继续写作会把猜测变成事实。报告必须记录
   缺口；不能用概括性语言绕过问题，也不能推进 ``verified_through``。

只有 ``project/STATE.rst`` 可以声明当前模式。模式切换必须更新长期决策和接续状态。

批次与上下文预算
----------------

默认批次是连续三章。三章是交付事务，不是一次性生成三篇正文：

::

   固定批次边界
   → 建立整批状态账本
   → 审查/编写第一章
   → 固定第一章结束状态
   → 审查/编写第二章
   → 固定第二章结束状态
   → 审查/编写第三章
   → 整批交叉复核
   → 一致性检查
   → 原子提交

新对话只读取稳定合同、动态状态、当前批次、相邻边界和当前需要的源码。不得为了
“了解全书”一次性读取全部正文、完整manifest和全部历史审计报告。需要历史事实时，
沿审计索引精确打开对应报告或章节。

固定源码工作树
--------------

源码版本以 ``AGENTS.md`` 的commit为准。当前固定源码使用大小写敏感卷上的完整工作树：

::

   /Volumes/LinuxKernel/seabios
   /Volumes/LinuxKernel/qemu
   /Volumes/LinuxKernel/grub
   /Volumes/LinuxKernel/linux-7.2-rc1

只允许以上四个工作树作为正文证据。不得使用项目内 ``.sources/``、
``/Volumes/LinuxKernel/linux`` 或其他副本，也不得自动克隆、下载、拉取或补齐源码。使用任一
源码工作树前必须确认：

* remote与固定仓库一致；Linux工作树必须存在指向 ``gregkh/linux`` 的remote；
* ``HEAD`` 等于固定commit；
* 整个工作树没有本地修改；
* ``git rev-parse --is-shallow-repository`` 返回 ``false``；
* sparse checkout未启用，也没有活动的sparse规则。

任一条件不满足时停止正文生产并报告，不得切换到其他源码副本绕过。搜索不到符号时仍要核对
仓库、commit和生成条件，不以一次搜索结果推断源码不存在。

源码核验优先使用本地 ``rg``、 ``git show`` 和带行号视图。正文资料链接指向固定commit，
关键路径优先带 ``#Lx-Ly`` 行锚点。架构行为使用处理器手册或规范；平台行为使用固定
QEMU、SeaBIOS、GRUB或Linux源码。真实PC但未固定主板的模拟电气过程只能作为明确标注的
范围说明，不能冒充当前q35执行事实。

证据账本
--------

修改正文前，当前批次报告至少记录：

* 审查文件与编号；
* 固定仓库、commit和关键符号；
* 批次开始状态；
* 每章入口、出口及相邻交接；
* 执行者、CPU/mode与调用上下文；
* 关键对象、所有权、引用、锁、队列、hash、timer或设备状态；
* 成功路径实际选择的条件分支；
* 失败、回滚或未发生行为中与结论相关的边界；
* 发现的问题、修复内容和仍然存在的不确定性。

报告保存审查过程，正文保存读者理解结论所需的证据。报告不能代替正文里的源码推理。

事实硬门
--------

一章只有同时满足下列条件才能标记为 ``verified`` 或 ``repaired``：

#. 标题问题与正文实际闭合的源码边界一致；
#. 开始状态等于上一已验证章节的结束状态；
#. 调用顺序能在固定源码中逐段定位；
#. 执行者、CPU/mode、锁域和上下文没有混写；
#. 对象、引用和身份没有无来源地产生或消失；
#. 固定条件足以排除正文省略的竞争、失败或替代分支；
#. “不调度”“不发包”“不释放”“尚未hash”等否定结论有分支或状态依据；
#. 章末结束状态与正文最后一步一致；
#. 下一入口与下一章真实第一步一致；
#. 资料全部绑定固定版本，没有用分支最新源码替代固定commit；
#. 推断、约定、预期现象与源码事实被明确区分；
#. 没有为了补齐叙事而编造寄存器值、地址、对象名或精确顺序。

任一项无法确认时，状态必须是 ``blocked``，不能以“基本正确”推进审计游标。

连续叙事合同
------------

正文沿真实时间线推进，而不是罗列函数百科。每段只承担一个可追踪判断，并在需要时说明：

* 当前是谁在执行；
* 位于什么CPU和mode；
* 进入了哪个函数或硬件边界；
* 哪个对象、字段、寄存器或队列发生变化；
* 哪把锁或哪份引用保证这一步安全；
* 下一步为什么进入后续入口。

不是每段都机械重复六项；但任何影响执行顺序或对象生命期的结论都不能缺少相关上下文。
不使用“系统完成处理”“底层负责转换”一类无法定位的句子。

篇幅由自然源码边界决定。较短不等于低质量，较长也不等于充分；禁止设置行数下限来
诱导填充，也禁止用摘要替代关键推理。第176—178章只提供结构和叙事密度参照，不享有
免审资格。

章末合同
--------

每章最后依次包含四个一级小节：

``本章结束状态``
   条目式记录可被下一章直接继承的状态，不重复整批历史。

``关键边界``
   记录最容易混淆、顺序不可交换或需要否定说明的技术边界。

``下一入口``
   只指定下一章第一处真实入口及开始前固定条件。

``资料``
   统一放在最后，链接固定commit的一手资料。关键代码优先精确到行范围。

回溯审查规则
------------

审查从001开始，按编号严格递增。状态含义如下：

``pending``
   文件存在，但尚未按本合同核验。

``in-review``
   当前批次正在读取源码与正文，不能被后续批次越过。

``verified``
   原文事实与边界通过本合同，无需技术修订；允许仅做合同格式补全。

``repaired``
   发现并修复了事实、连续性、版本、来源或结构问题，修订后通过全部硬门。

``blocked``
   存在无法从固定条件与一手源码解决的关键问题。

审查批次必须处理正文问题，而不是只写问题列表。尚未轮到的全局结构问题可以登记为
``known debt``，除非它会破坏当前批次的一致性，否则在编号到达时修复，避免审查游标
四处跳动。

第001章的开始边界由固定q35机器创建、固件映射和BSP复位状态共同建立；后续每章从上一章
已验证结束状态开始。审查到第193章后，必须重新计算最后对象状态和下一主线，不能直接
继承历史UDP建议。

生产规则
--------

只有 ``verified_through=193`` 且回溯审查没有 ``blocked`` 批次，才能进入
``forward-production``。新章生产时：

* 先按源码边界规划三章，不从固定“三章”反推虚假的三个等长主题；
* 整批先建立入口、出口与失败回滚；
* 每次只写当前一章，确认出口后再写下一章；
* 三章全部通过事实硬门后才登记complete；
* 任何一章失败，整批不提交为完成。

状态文件职责
------------

``AGENTS.md``
   稳定接入入口、固定版本和最短执行规则。不得每批复制最新调用链。

``project/LINUX_KERNEL_CONTRACT.rst``
   本文件。只在用户改变质量或流程决定时修改。

``project/STATE.rst``
   唯一动态接续状态：模式、已验证范围、下一批、阻塞和明确读取清单。

``project/LINUX_KERNEL_FORWARD_CHECKPOINT.rst``
   保存回溯审查开始前第193章的历史前向终点。它不是已验证事实，审查期间无需读取。

``project/audits/linux-kernel/index.rst``
   轻量审计账本，只登记批次、状态、范围和报告链接。

``project/audits/linux-kernel/<range>.rst``
   单批证据、问题、修复和验证结果。新对话只读当前批次及必要相邻批次。

``manifests/tracks/linux-kernel.toml``
   章节与主线机器可读库存。必须区分 ``present`` 与 ``audit-verified``。

README和章节index面向读者导航，不承担Agent精确接续，不复制动态对象账本。

一致性检查
----------

``tools/check-linux-kernel-track.sh N`` 只检查001到N的已审范围，并报告全局已知结构问题。
它至少检查文件编号唯一、连续存在、固定版本旧标签、章末四节存在且顺序正确。

检查器不能证明技术正确。技术正确性仍由固定源码审查、批次报告和diff复核保证。允许这
一个只读检查器是“不建立构建/CI系统”的窄例外；不得借此引入Sphinx、生成流水线或批量
改写正文。

提交与失败原子性
----------------

每批正文、报告、审计索引、动态状态和必要manifest更新组成一个原子提交。提交前必须：

* 工作树只包含本批授权修改；
* 一致性检查通过已审范围；
* 审计报告没有未解决的关键问题；
* ``project/STATE.rst`` 的下一批与本批结果一致；
* diff中没有把未审章节顺手标记为verified。

直接提交 ``main`` 并推送 ``origin/main``。如果失败，保留可检查工作树并报告原因，不用
多个“修状态”“补索引”提交掩盖中间不一致。

防止越写越差
------------

本合同通过四个机制限制长期退化：

#. 每批结束即切断聊天上下文，仓库文件承担接续；
#. 稳定规则与动态状态分离，避免每批重写规则造成语义漂移；
#. 先证据后正文，模型不能靠上一章语气继续猜测；
#. 未过硬门的结果不能推进状态或进入完成提交。

因此，质量目标不是要求模型每次发挥完全一致，而是让波动在提交前被发现并阻断。

从 aiBook 得到的经验
===================

``aiBook`` 中需要区分两类资产：文章生成控制文件，以及生成后的 ``docs`` 正文。它们的价值完全不同。

值得保留：知识需求
------------------

Roadmap、Roadmap 配套规范和文章生成控制文件体现了用户真正想获得的知识，例如：

* 想进入哪些技术领域；
* 希望覆盖哪些核心机制；
* 哪些主题需要工程实践或源码层级；
* 不同知识块原本希望建立什么联系。

这些内容是 ``techBook`` 的知识范围输入。迁移时应尽量保留知识覆盖，不应因为旧正文失败就把目标知识一起删除。

不能继承：生成方式
------------------

旧 ``docs`` 是控制文件经过自动扩充后的成品。它主要用于观察失败，不作为新内容底稿。

失败一：一个知识项被扩成完整文章
--------------------------------

旧生成流程容易把 Roadmap 中一个简单知识点扩充为定义、背景、分类、历史、实现、边界、工程实践、总结和检查题。

结果是 Roadmap 中真正想学的内容只占很小一部分，大量篇幅来自文章结构本身。

新仓库把 Roadmap 条目视为覆盖要求，不视为章节。知识点讲清并形成能力变化后立即结束。

失败二：承诺与实际能力不一致
----------------------------

旧章节开头经常承诺“深入理解”“掌握完整机制”“建立工程认知”，正文结束后读者只能复述几个术语，无法预测代码、解释结果或独立完成任务。

``techBook`` 的学习结果必须描述一个可以检查的动作，例如：

* 能预测 ``list.append`` 的返回值；
* 能解释文件描述符如何关联到打开文件；
* 能根据编译错误定位模板推导失败的位置。

失败三：把覆盖完整当成教学完整
------------------------------

旧内容倾向于同时介绍所有相关概念。每项都出现一点，读者得到的是名词地图，没有形成可以使用的思考路径。

新单元只引入解决当前困惑所需的内容。Roadmap 的全部知识通过多个有前置关系的单元逐步覆盖，而不是在一篇文章中全部出现。

失败四：问题在正文完成后才被附加
------------------------------

旧章节的结尾问题经常缺少动机。读者不知道为什么需要回答，也不知道答案从哪段代码或哪个现象推出来。

新问题必须从开头预测、最小示例和真实结果自然产生。答案必须包含推理过程、证据位置和错误答案所依赖的错误模型。

失败五：总结很多，关键推理很少
------------------------------

开头总结、段落总结和结尾总结会重复同一结论，却没有展示结论形成的过程。读者可能觉得句子都看懂了，合上页面后仍然无法解释原因。

新内容优先展示输入、调用、对象、状态变化、输出和验证。重复结论必须删除。

失败六：代码只是文章插图
------------------------

旧代码常被嵌在正文中，用来证明文章“有示例”。它没有预测、实际输出、失败变体和完成标准。

新示例必须承担教学作用。读者需要先预测，再观察，再修改。代码、命令和输出直接保存在当前 RST 中，使问题、证据和解释处在同一个文件里。

失败七：源码内容没有固定真实实现
--------------------------------

一些旧章节使用“常见实现”“通常会”“主流实现大致如此”描述源码机制。读者无法定位真实代码，也无法判断不同实现之间的差异。

需要源码证明的单元必须重新固定 repository、release、commit、平台和工具链。旧正文中的源码路径只能作为待核实线索。

失败八：统一模板压过内容差异
----------------------------

语言基础、Linux 内核、Web 架构和移动系统被要求使用相似的章节结构。模板越完整，Agent 越容易机械填充段落。

``techBook`` 只固定学习主链：预测、证据、推理、变化、迁移。具体标题、证据类型和呈现结构由内容决定。

失败九：预先冻结大量章节
------------------------

大型 Roadmap 被直接解释成章节目录后，后续工作退化为填目录。即使实际学习反馈表明顺序错误、章节重复或某个问题没有独立成章价值，Agent 仍倾向于继续生成。

新仓库保留 Roadmap 的知识项，重新安排学习顺序。一个知识项可以被合并、拆分、延后或在多个单元中逐步建立。

失败十：把文件完成当成学会
--------------------------

旧内容的完成标准通常是页面已经生成、结构已经齐全。它没有要求读者独立预测、修改或迁移。

新 unit 只有在完成标准可以验证学习行为时才能标记为 ``complete``。是否学会依靠真实阅读与任务表现，不能由文件状态代替。

事实可信度
----------

Roadmap 和生成控制文件能够证明“用户想学什么”，不能证明技术结论正确。

旧 ``docs`` 中的以下内容默认都需要重新核实：

* 技术结论；
* 官方链接；
* 示例代码；
* 运行输出；
* 源码路径；
* 版本信息；
* 调用链和架构判断。

新内容的事实依据必须重新来自一手资料和真实可确认的行为。

迁移规则
--------

从 ``aiBook`` 建立新内容时按以下顺序处理：

#. 读取 Roadmap 和生成控制文件，提取用户真正想获得的知识；
#. 把知识项从旧章节结构中分离出来；
#. 根据前置能力重新安排、合并或拆分；
#. 为当前知识项定义读者完成后能做的动作；
#. 从官方资料、真实源码或实际行为重新建立事实；
#. 设计需要先预测的最小示例或现象；
#. 在同一 RST 中提供真实结果和逐步推理；
#. 增加变化、误解、答案推理和独立任务；
#. 使用旧正文检查新内容是否仍然出现过度扩充。

最终保留的是 Roadmap 中的知识意图，不是旧正文，也不是旧正文的章节规模。
